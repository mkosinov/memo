# Brainstorming: идея → концепт (G1a)

Host-порт `.opencode/skills/brainstorming` (канон superagents), обрезан до ядра G1a: оркестрацию фазы (спека, панель, план, борд, шов) ведёт скилл `design-phase`. Контейнерный оригинал не трогаем — там он часть full-pipeline fallback менеджера.

## Контракт

- Вход: идея или issue. В DESIGN-сессии `design-phase` передаёт отчёты скаутов (fact sheet) + номер issue; standalone-вызов — контекст собираем сами (файлы, доки, недавние коммиты), компактно, без сырых дамб.
- Выход: концепт «что делаем / что сознательно НЕ делаем (границы скоупа)», явно одобренный юзером. После одобрения — стоп: спеку, панель и план ведёт `design-phase` (при standalone-вызове — обычный workflow юзера). Реализационных действий внутри этого скилла нет.
- Anti-pattern «это слишком просто для брейншторма»: через диалог проходит всё. Для тривиального концепт — 2–3 предложения, но предъявить и получить одобрение — обязательно. Простые задачи — ровно те, где непроверенные допущения дороже всего.

## Процесс

1. **Осмотр контекста** — что уже есть по теме: файлы, доки, недавние коммиты (в DESIGN-сессии — только отчёты скаутов).
2. **Уточняющие вопросы** — по одному на сообщение; multiple choice предпочтителен. Цель: purpose / constraints / success criteria. Если идея распадается на несколько независимых подсистем — сначала флаг декомпозиции юзеру, детали недекомпозированного не выпрашиваем.
3. **2–3 подхода** с трейд-оффами и рекомендацией; рекомендованный — первым, с обоснованием «почему».
4. **Презентация концепта** секциями, масштаб секции — по её сложности; после каждой — «так ли выглядит?». Покрыть: архитектуру, компоненты, потоки данных, обработку ошибок, тестирование. Для каждого компонента: что делает / как используется / от чего зависит — границы, за которые можно менять внутренности, не ломая потребителей. В существующей кодовой базе — сначала существующие паттерны; улучшения, затрагивающие работу, — частью дизайна, посторонний рефакторинг — нет.
5. **Финал = гейт:** концепт «делаем / НЕ делаем» → явное одобрение юзера. В DESIGN-сессии это G1a; управление возвращается `design-phase`.

## Key Principles

- One question at a time — не заваливать юзера списком вопросов.
- Multiple choice preferred — легче отвечать, чем формулировать.
- YAGNI ruthlessly — из концепта режется всё без явной потребности.
- Explore alternatives — 2–3 подхода до фиксации, не после.
- Be flexible — если что-то не сходится, возвращаемся и уточняем.
