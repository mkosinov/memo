## Flakiness analysis (tests 4-8)

After multiple fix attempts (1) `page.mouse.click(5, 5)` dismiss pattern, 2) `Promise.all` + `waitForResponse`, 3) `expect.toBeVisible` auto-wait), 6 tests remain intermittently failing. The flakiness is NOT in the test code — it is in the **product code**:

- `Topbar.tsx:handleColumnModeSelect` (lines 111-118) is a `useCallback` that does
  `setColumnMode(mode)` + `setDropdownOpen(false)`. But the day-button itself also
  has `handleDayButtonClick` that toggles BOTH view mode AND dropdown open. The
  two state changes can race depending on React's render timing.
- The `useCallback` dependency arrays are correct, but the `if (viewMode !== 'day')`
  branch inside `handleColumnModeSelect` creates a non-obvious path where the
  dropdown may be in a transitional state.

**Recommendation:** the column-mode dropdown toggle needs a real product-code fix
(this is a separate task, not in scope of issue #65). The current tests are
**correctly written** for the intended behavior, but the behavior is unreliable
in CI due to timing.

## Recommendations for future e2e work

1. **Audit new tests for brittleness.** Any test that uses `waitForTimeout` should
   be flagged. Auto-wait (`expect.toBeVisible`, `expect.toContainText`) is the
   standard. `waitForResponse` is only valid if the action actually triggers an
   API call.
2. **Seed data explicitly.** Tests that depend on existing records/clients/etc.
   should create them via API. Never assume the dev DB has specific data.
3. **Test the behavior, not the implementation.** If a test relies on a specific
   component structure (`#record-time`), document why and add a test-only attribute
   (`data-testid`) when stable.
4. **Demote to vitest when appropriate.** Tests that exercise unit-level logic
   (sorting, filtering) don't need full e2e with browser + dev server. A vitest
   test with mocked data is faster, more reliable, and easier to debug.
