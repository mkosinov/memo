# Domain events — сервис доменных событий (журнал, ретранслятор, подписки)

Спека-контракт: [2026-11-08-domain-events-service-580-design.md](../specs/2026-11-08-domain-events-service-580-design.md) (#580). Модуль `src/domain_events`.

## Журнал

- Событие (`domain_events`) пишется **в транзакции сценария** — третьим аккумулятором `@transactional` рядом с аудитом и инвалидацией кэша; событие появляется ровно тогда, когда зафиксировано доменное изменение. Актор не требуется (в отличие от аудита — это данные, а не журнал действий).
- Журнал — **источник истины и архив**: Redis-стримы перестраиваемы из него, наоборот — никогда. Прямая запись в Redis из транзакции запрещена (двойная запись без атомарности).
- Снапшот события самодостаточен: собирается до коммита только локальными чтениями; продюсер не знает потребителей. События «жирные» — со снимком; подписчик читает БД только для своих предикатов. Сборка снимка — обязанность продюсера (семейская §4.1): пилотный сборщик `new_record` живёт у продюсера записей (`src/usecases/record_snapshots.py`); продюсер не импортирует notify.
- Тип события задаётся декларативным словарём в реестре (`src/domain_events/types.py`, без импорт-побочных регистраций); `mark_domain_event` с незарегистрированным типом — `ValueError` в транзакции (откат вместе с доменным изменением).

## Реестр типов

- Единственный способ объявления типа — декларативный блок в `src/domain_events/types.py` (`register_type`); поведение не зависит от графа импортов: потребитель видит те же типы без импорта продюсера. Пилот — единственный тип `new_record`.
- Ключ стрима типа — `stream_key(code) = domain_events:<код>`; имена стримов подписчика валидируются по реестру.
- Марка валидируется до проверки аккумулятора: незарегистрированный тип и марка **без снимка** — одна и та же `ValueError` (NULL-снимок в стрим не публикуется); ошибка программиста падает громко даже вне открытой транзакции, внутри транзакции — откат доменного изменения вместе с событием.

## Ретранслятор

- Отдельный процесс `python -m src.domain_events.relay`, гейт `DOMAIN_EVENTS_ENABLED` (зеркало `NOTIFY_ENABLED`, по умолчанию выключен; тестовый профиль принудительно гасит случайное включение), тик `DOMAIN_EVENTS_POLL_INTERVAL` (сек). Батч и интервалы — константы модуля, не настройки. Общий каркас цикла — `run_loop`/`install_signal_handlers` из `src/util/process` (префикс лога параметризован; notify передаёт свой исторический «notify dispatcher»).
- Единственный читатель хвоста журнала: батч `published_at IS NULL ORDER BY occurred_at, id LIMIT POLL_BATCH_SIZE (20)`, публикация XADD в стрим типа `domain_events:<тип>` (запись §4.1: `event_id`, `type`, `occurred_at` ISO naive UTC, `snapshot`), каждый вызов Redis — через `asyncio.to_thread`; пометка `published_at` одним коммитом на батч. Курсор — состояние строк, не запомненный id: окно переключения «стоп диспетчера → миграция → старт ретранслятора» ничего не теряет.
- Транспортный сбой XADD глобален, не пособытиен: батч остаётся непомеченным (без `finally`-пометки и пособытийных учётов), ошибку ловит изоляция цикла, повтор — следующим тиком. Падение между публикацией и отметкой — дубль в стриме; дубли поглощаются идемпотентностью подписчиков.
- Пособытийный НЕ-транспортный сбой (неисправимый payload — баг кода) выделяется: строка помечается опубликованной с ERROR-логом (одна битая строка не стопорит хвост навечно); повтор после исправления — процедурный `--republish-since` (задача 7).
- Каждый тик логирует глубину неопубликованного хвоста (row count): INFO при непустом хвосте, DEBUG при нулевом — отставание видно оператору до того, как станет потерей.

## Подписки

- Подписка сервиса = **группа потребителей** на стримах нужных типов; разные сервисы — разные группы, каждая получает все записи стрима независимо. **Имя группы глобально уникально**: два сервиса в одной группе делят записи — тихая потеря для обоих. Pub/Sub Redis не используется: без сохранения, потеря при отключении.
- Публичный API подписки — `Subscriber` (`src/domain_events/subscribe.py`, §3.4): конструктор принимает `redis_url` и `group` (= имя сервиса, контракт именования выше); `ensure(streams)` — валидация имён по реестру (`stream_key(<тип>)`, незарегистрированное имя — `ValueError` до любого вызова Redis) + XGROUP id=0 MKSTREAM; `claim(streams, count)` — неблокирующий XREADGROUP > (count — потолок на стороне сервера, не срез), возвращает `ClaimedEvent` — распарсенную запись §4.1 c `qid` (id записи стрима — ручка ack); `ack(stream, qid)`; `reclaim(streams, min_idle_ms)` — сырой XAUTOCLAIM ядра: заявленные записи возвращаются подписчику как есть, пере-XADD запрещён; `close()` — keep_if_pending. Поверх общего ядра `src/streams` — своих механик Redis подписчик не содержит.
- Гарантия «как минимум один раз»: подтверждение (XACK) — после материализации результата (включая парковку после 3 неудач); возврат зависших (XAUTOCLAIM) — на старте процесса **и периодическим циклом** (интервал — константа модуля подписчика). Порядок стрима — best-effort: подписчик не опирается на порядок доставки, детерминизм строится по данным события. Остановка подписчика держит потребителя с непустым PEL (`XGROUP DELCONSUMER` уничтожает учёт выдачи).
- **Идемпотентность подписчика обязательна** — часть публичного контракта: повторная выдача события не должна создавать дубль результата (у notification — частичный уникальный индекс корней цепочек `UNIQUE(event_id, scenario) WHERE parent_task_id IS NULL`, вводится миграцией #580). Транспортная ошибка попыток подписчика не сжигает — запись остаётся неподтверждённой.
- Состояние потребления (попытки, ошибки) живёт у подписчика в его таблицах, не на строке события; `processed_at`/`attempts`/`processing_error` события не существуют.
- Стрим — внутренний транспорт: запись несёт замороженный снимок (включая контактные данные клиента) до предикатов подписчика; читатели — только сервисы с реквизитами Redis; логирование тел записей запрещено (правила транспорта — `src/streams`, раздел ниже).

## Транспорт стримов (`src/streams`)

Общее ядро `src/streams/transport.py` — вынесено из notify (#580 §3.6): механики Redis Streams без имён стримов; словарь потоков и групп передаёт вызывающий (notify — `notify:*` через `RedisQueue`, доменные события — `domain_events:<тип>`). `src/notify` зависит от `src/streams`, обратное запрещено.

- Пул соединений: ретраи выключены явно (тихий ретрай скрыл бы аварию — сбой обязан быть громким), явный потолок пула, `socket_timeout` больше любого `BLOCK` читающего. Любая ошибка Redis нормализуется в типизированную `StreamTransportError` и не гасится; в notify это псевдоним `NotifyTransportError` (тот же класс). Текст ошибки несёт класс и сообщение исходной ошибки, но не тела записей и не значение URL.
- Запись — единственное JSON-поле `payload`, XADD с `MAXLEN ~ 10_000` (приблизительно, узлами): стрим — только транспорт, не архив (архив — журнал в БД); запись у потолка не отклоняется. Ожидающая запись, урезанная под потолком, невосстановима — терминальный лог (id записи + стрим, без тела).
- Выдача — неблокирующий `XREADGROUP >` с конвертом `_qid` (id записи; ключ зарезервирован транспортом). Чтение своего PEL по id `0` внутри цикла запрещено — возврат только через XAUTOCLAIM. Подтверждение — XACK по `_qid` после материализации результата; повторный XACK безвреден.
- Группа потребителей: `XGROUP CREATE id=0 MKSTREAM` — записи, накопленные до создания группы, остаются доставляемыми; подавляется только конкретный BUSYGROUP. NOGROUP — штатный случай (группы пересоздаются на старте потребителя).
- **Сырой XAUTOCLAIM — передача PEL без пере-XADD**: ядро отдаёт заявленные записи вызывающему как есть (id + поля). Повторный XADD + ack — обёртка очереди notify (семантика свежей доставки); подписчики доменных событий пере-XADD НЕ делают — возврат обработкой заявленной записи (иначе churn стрима ретранслятора, #580 рев.2).
- Остановка: потребитель с непустым PEL не снимается (`XGROUP DELCONSUMER` уничтожил бы учёт выдачи) — правило keep_if_pending; отсутствие группы/ключа при снятии — тихий no-op.
- Имя потребителя уникально на живой процесс (`<группа>-<pid>`). `connect_or_exit` — fail-fast гейт: пустой URL или недоступный Redis → выход с кодом 2; значение URL нигде не логируется.

## Восстановление

- Потеря Redis: группы пересоздаются на старте подписчиков (NOGROUP — штатный случай); раздача восстанавливается `python -m src.domain_events.relay --republish-since <ISO>` от точки потери, дубли поглощаются.
- Границы модулей: `src/domain_events` не импортирует notify; подписчики импортируют только реестр, марку и `Subscriber`.
