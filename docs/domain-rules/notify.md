# Notify — подсистема оповещений (журнал событий, задачи доставок)

Спека-контракт: [2026-10-11-notify-system-476-design.md](../specs/2026-10-11-notify-system-476-design.md) (семья #476); часть 1 — [2026-10-19-notify-events-482-design.md](../specs/2026-10-19-notify-events-482-design.md) (#482).

## Журнал доменных событий

- Событие (`domain_events`) пишется **в транзакции сценария** — третьим аккумулятором `@transactional` рядом с аудитом; событие появляется ровно тогда, когда зафиксировано доменное изменение. Актор не требуется (в отличие от аудита — это данные, а не журнал действий).
- Снапшот события самодостаточен: собирается до коммита только локальными чтениями; продюсер не знает потребителей.
- Диспетчер — единственный писатель БД подсистемы (кроме API ручного повтора, часть 5). Читает журнал по частичному индексу `processed_at IS NULL AND processing_error IS NULL`, батчем, курсором по состоянию строк.
- `processed_at` ставится в одной транзакции с созданием задачи — повторная обработка события дубль задачи не создаёт.
- Ошибка сценария (включая отсутствие шаблона): до 3 попыток (`attempts`), затем `processing_error` и событие поллингом не берётся. Ошибка сборки текста в воркере — `app_error` попытки канала: транспортные ретраи не выполняются, цепочка идёт к следующему каналу (рев. части 4).

## Сценарий «новая запись» (пилот)

- Флаг записи `records.notify` уважается только при **аутентифицированном акторе** (маршрут бронирования публичен — анонимный вызов не может навязать рассылку).
- Предикат: флаг записи ∧ получатель (клиент жив, не мягко удалён, телефон не пуст) ∧ согласие `clients.notify_enabled` ∧ событие в будущем. Согласие и флаг читаются **живыми записями** на момент обработки по идентификаторам из снапшота; порядок причин фиксирован: `notify_off` → `no_recipient` → `no_consent` → `past_event`. Удалённая к обработке запись закрывает событие без задачи.
- Отказ — задача `skipped` с причиной; успех — в задаче первого канала приоритета замораживаются данные рендера, шаблон канала (песочница Jinja2, строгие неопределённые, шаблон из базы) и адрес; адреса **никогда не переразрешаются** — задачи цепочки наследуют адрес корня (рев. части 4, ADR 014).
- Время — наивный настенный часы явной бизнес-зоны (`BUSINESS_TIMEZONE`) в одной интерпретации для предиката «будущее» и текста (`activities.start` как хранится; `business_now()` — та же шкала).
- Экранирование определяется форматом канала задачи (рев. части 4): значения экранируются при подстановке (HTML — для telegram) независимо от происхождения шаблона; универсальный шаблон (без канала) — простой текст без разметки, отправляется без канального parse-режима. Разметка принадлежит только шаблону канала, данные остаются данными.

## Задачи доставок

- Задача = один канал (рев. части 4, ADR 014); цепочка задач каналов — доставка; идемпотентность спавна — `UNIQUE(root_task_id, channel)`; итог цепочки пишет диспетчер на корневую задачу.
- Состояния: `queued → sending → sent | failed`; терминальное `skipped` (в очередь не идёт).
- Текст собирает воркер из замороженных данных и шаблона один раз на задачу; повторные попытки шлют тот же текст; отчёт попытки несёт фактически отправленный текст (`sent_text`).
- Состояние выводится диспетчером из событий статусов (первый `sent` любой попытки → `sent`, терминально); попытки — только добавляемые строки `notify_task_attempts`.
- Перезаливка — повторная постановка сохранённого payload; не трогает задачи, заявленные воркером (PEL группы); потолок перезаливок, после которого задача `failed`.
- Лимиты отправки — общий механизм каналов реестра (рев. части 4): параметры декларирует канал (`ChannelLimits`: потолок, пауза, адрес служебных сообщений), механизм живёт на стороне воркера. Суточное окно — счётчик Redis `notify:{channel}:cap:<ГГГГММДД>` (атомарный INCR после **успешной** отправки, первый INCR ставит EXPIRE 48 ч; дата — наивное UTC процесса). Перед отправкой — проверка: исчерпано → `app_error` попытки «суточный лимит исчерпан». При первом исчерпании окна — одно служебное сообщение админу (`limits.admin_address`) через тот же канал: счётчик не растит, паузу соблюдает, флаг окна `notify:{channel}:cap-notified:<ГГГГММДД>` (TTL 48 ч) ставится **после** успешной отправки (дубль при краше принят); адрес не задан — сообщения нет, причина остаётся в журнале попыток. Пауза между последовательными отправками канала — асинхронная выдержка в процессе воркера (один воркер в пилоте).
- Гарантия «хотя бы один раз»: редкий дубль принят.
