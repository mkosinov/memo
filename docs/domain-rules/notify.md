# Notify — подсистема оповещений (журнал событий, задачи доставок)

Спека-контракт: [2026-10-11-notify-system-476-design.md](../specs/2026-10-11-notify-system-476-design.md) (семья #476); часть 1 — [2026-10-19-notify-events-482-design.md](../specs/2026-10-19-notify-events-482-design.md) (#482).

## Журнал доменных событий

- Событие (`domain_events`) пишется **в транзакции сценария** — третьим аккумулятором `@transactional` рядом с аудитом; событие появляется ровно тогда, когда зафиксировано доменное изменение. Актор не требуется (в отличие от аудита — это данные, а не журнал действий).
- Снапшот события самодостаточен: собирается до коммита только локальными чтениями; продюсер не знает потребителей.
- Диспетчер — единственный писатель БД подсистемы (кроме API ручного повтора, часть 5). Читает журнал по частичному индексу `processed_at IS NULL AND processing_error IS NULL`, батчем, курсором по состоянию строк.
- `processed_at` ставится в одной транзакции с созданием задачи — повторная обработка события дубль задачи не создаёт.
- Ошибка сценария/рендера: до 3 попыток (`attempts`), затем `processing_error` и событие поллингом не берётся.

## Сценарий «новая запись» (пилот)

- Флаг записи `records.notify` уважается только при **аутентифицированном акторе** (маршрут бронирования публичен — анонимный вызов не может навязать рассылку).
- Предикат: флаг записи ∧ получатель (клиент жив, не мягко удалён, телефон не пуст) ∧ согласие `clients.notify_enabled` ∧ событие в будущем. Согласие и флаг читаются **живыми записями** на момент обработки по идентификаторам из снапшота; порядок причин фиксирован: `notify_off` → `no_recipient` → `no_consent` → `past_event`. Удалённая к обработке запись закрывает событие без задачи.
- Отказ — задача `skipped` с причиной; успех — рендер текста один раз при создании задачи (песочница Jinja2, строгие неопределённые, шаблон из базы), готовый текст **и адреса каналов** замораживаются в задаче и никогда не переразрешаются.
- Время — наивный настенный часы явной бизнес-зоны (`BUSINESS_TIMEZONE`) в одной интерпретации для предиката «будущее» и текста (`activities.start` как хранится; `business_now()` — та же шкала).
- Экранирование на границе рендера: строковые значения снапшота экранируются перед подстановкой — разметка принадлежит только шаблону, данные остаются данными.

## Задачи доставок

- Состояния: `queued → sending → sent | failed`; терминальное `skipped` (в очередь не идёт).
- Состояние выводится диспетчером из событий статусов (первый `sent` любой попытки → `sent`, терминально); попытки — только добавляемые строки `notify_task_attempts`.
- Перезаливка — повторная постановка сохранённого payload; потолок перезаливок, после которого задача `failed`.
- Гарантия «хотя бы один раз»: редкий дубль принят.
