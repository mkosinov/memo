# Service Layer — канон слоёв

Утверждён 2026-09-18 (#171, «оркестратор вместо трактора»); rev2 — 2026-09-19 по итогам панели и диалога; rev3 — 2026-09-19: полная карта коридоров (добавлен третий — читающие композиты) и дерево выбора «куда положить новый код»; rev4 — 2026-09-20: канон внедрён (#171) — слой `backend/src/usecases/` создан (спецификация `usecases/records.py`: `create_record`, `update_record`, `patch_record`, `delete_record`), `RecordService` сужен до своей сущности (без импортов чужих ORM-моделей), табличные bulk-команды — в репозиториях владельцев, контракт #285 не изменён. Подробности — спека `docs/specs/2026-09-18-service-usecases-design.md` (rev2). Действует на бэкенд (`backend/src/`).

## Слои

```
api          — транспорт: разобрать запрос → вызвать ОДНО действие → сформировать ответ
  ↓
usecases     — сценарии: мульти-сущностные бизнес-действия, одна транзакция
  ↓
services     — именованные операции своей сущности (двух разновидностей)
  ↓
repositories — единственное место табличных команд своей сущности
  ↓
таблицы      + domain — бизнес-правила (статусы, удаление, пересчёты; доступ к сессии разрешён)
```

## Коридоры обращения (полная карта)

```
Коридор 1 — простая операция (одна сущность)
  Эндпоинт → метод сервиса (декорирован: 1 транзакция + события) → репозиторий

Коридор 2 — составное действие (несколько сущностей)
  Эндпоинт → сценарий usecases (декорирован: 1 транзакция + 1 пакет событий)
               → методы сервисов без транзакции → репозитории

Коридор 3 — читающий композит (своя сущность + агрегаты чужих)
  Эндпоинт → свободная функция в модуле своего сервиса
               (без декоратора — чтению не нужна транзакция изменений;
                один эффективный запрос с подзапросами)

Сквозной слой — домен (правила, пересчёты, проверки зависимостей):
  вызывается из коридоров 1 и 2; имеет доступ к сессии;
  правит только строку своей сущности (прецедент: пересчёт статуса правит запись);
  шире одной сущности — значит, это сценарий, не домен
```

### Дерево выбора «куда положить новый код»

- меняю одну сущность со своего эндпоинта → декорированный метод сервиса;
- действие охватывает несколько сущностей → сценарий usecases;
- читаю свою сущность, обогащаю агрегатами чужих → свободная читающая функция в модуле своего сервиса (имя — глагол действия: `list_clients_with_stats`, `get_payment_totals`);
- правило/пересчёт, общий для нескольких вызывающих → доменная функция.

## Правила

1. **Один писатель.** Табличные команды живут только в репозитории своей сущности. Сервис владеет именованной операцией, репозиторий — исполнением. Собственные дочерние строки/связки без самостоятельного жизненного цикла обслуживает владелец: тарифы и связки `service_tags` — сервис услуг, `record_tags` — сервис записей.
2. **Сценарий.** Публичная функция `usecases/<сущность>.py`, названа глаголом бизнес-действия (`create_record`, `delete_record`). Декорирована `@transactional`: открывает транзакцию, коммитит, публикует накопленные события (#239). Составляет только вызовы сервисов и домена; модели напрямую не импортирует. Файл usecases = семейство сценариев одной центральной сущности.
3. **Два вида методов сервиса.** Декорированные — для собственных эндпоинтов сущности («удалить один платёж по номеру»). Без транзакции — для сценариев («снести все платежи записи»). Перекрывающиеся операции строятся как «декорированный тонкий метод поверх общего ядра без транзакции» (прецедент: каскадное удаление посетителя).
4. **Bulk = одна множественная команда**, не цикл по строкам. Именованные bulk-команды живут в репозитории владельца (`delete_by_record_id` и аналогичные), фильтр — по собственной колонке-ссылке сущности. Методы-помощники получают идентификаторы-значения (`record_id`), не чужие объекты; импорт чужих моделей запрещён.
5. **Вложенные декорированные вызовы запрещены:** сценарий не вызывает декорированные методы сервисов. Механизм вложенных транзакций не строится; при реальной потребности (веб-бронирование #48) — отдельная задача (кандидат — сохраняемые точки SQLAlchemy).
6. **Транзакция = граница бизнес-действия**, не HTTP-запроса: простая операция — своя, сценарий — одна на всю цепочку. Декоратор на роутах не используется.
7. **Помощник не ловит исключения молча** — иначе сценарий закоммитит частичный результат.
8. **Читающие композиты** (коридор 3) — свободные функции в модуле сервиса своей сущности: чтение чужих таблиц в одном запросе — нормальная реляционная выборка; правила канона ограничивают запись. Пересборка в «сервисные вызовы» не требуется; будущее читающего слоя — #217.
9. **Терминология:** «сервис» в этом проекте — узкий владелец таблицы своей сущности; роль, которую литература называет application service / service layer, здесь выполняет слой `usecases`. Не называть сценарии «сервисами».
10. **Известные исключения (долг, вне #171):** каскад удаления занятия (сносит записи/визиты/платежи/теги), операции сотрудников (создают/удаляют строки мастеров и пользователей), удаление клиента (каскад посетителя стирает его визиты). Задокументированы отдельными задачами; новый код пишет по канону.

## Схема-пример (коридоры 1 и 2)

```
Простой эндпоинт «удалить платёж»
  → PaymentService.delete (декорирован)      [1 транзакция + события]
      → репозиторий платежей

Сценарный эндпоинт «удалить запись»
  → usecases.delete_record (декорирован)     [1 транзакция + один пакет событий]
      → VisitService.delete_visits_by_record (без транзакции)
          → репозиторий посещений
      → PaymentService.delete_by_record      (без транзакции, id на входе)
          → репозиторий платежей: delete_by_record_id
      → репозиторий записей: снос связок record_tags (своё ребро)
      → RecordService: строка записи
```
