# План #271: Закалка e2e-набора server-push-invalidation против CI-флейка С3

Спека: `docs/specs/2026-09-19-e2e-push-invalidation-flake-271-design.md` (Behavioral Delta — там, здесь не дублируется).

## Goal

Полные CI-прогоны shard-rest перестают красить спеку `server-push-invalidation` из-за
тайминговой гонки: push-утверждения получают окно, покрывающее один цикл переподключения
SSE-канала (10с вместо 5с), ограниченный повтор и внятную диагностику при падении.
Продуктовый код (SSE-сервер, hub, клиентский провайдер) не меняется. Условие готовности
issue (DoD): три подряд полных shard-rest прогона на фиче-ветке, в каждом по этой спеке
failed=0 **и** flaky=0 в сводке Playwright.

## Architecture

```
SSE-канал #239: сервер (retry: 5000, hub с вытеснением медленных) → EventSource в провайдере
   ↓ событие об изменённых сущностях → инвалидация кэша запросов → перечитывание
e2e-слой (правки ТОЛЬКО здесь):
   fixtures/server-push.ts      PUSH_WINDOW 5_000 → 10_000 (одна разделяемая константа;
   │                            офлайн-спека/С1/С4/тост-хелпер сдвигаются вместе с ней —
   │                            больше запаса, инвариант «строго ниже staleTime 30с» сохранён)
   server-push-invalidation.ts  test.setTimeout(120_000) — worst-case цепочки ≈90с, чтобы
   │                            диагностика успевала печататься до внешнего таймаута;
   │                            inline-повтор push-утверждений С3 (бюджет 1, пассивное
   │                            пере-вооружение; навигационное — повторный переход);
   │                            пробник openFrameLogger (независимый контекст-слушатель
   └                            к бэкенду) + сообщение при исчерпании: попытка/утверждение/перечитывание/трафик
CI: полные shard-прогоны ×3 (failed=0 и flaky=0) + разовая ручная анти-маскировка
    (route-abort `**/api/v1/events` → тест обязан упасть)
```

## Tech Stack

Playwright (TypeScript): `frontend/admin/e2e/fixtures/server-push.ts`,
`frontend/admin/e2e/server-push-invalidation.spec.ts`; шардовая среда `scripts/test-all.sh`
(стеки поднимает скрипт, конфиг Playwright при `SHARD_ID` свой webServer не стартует).
Юнит/vitest не затрагиваются; продуктовый код не затрагивается.

**Required Docs:** спека §7.1, §5e (пониженная точность — нет sibling-нагрузки rest-шарда)

  шардовые копии и поднять стек через `scripts/e2e-shard-start.sh` с тем же набором

  BACKEND_URL, NEXT_PUBLIC_API_URL). При заданном SHARD_ID конфиг Playwright свой webServer
  не стартует — точечный прогон идёт против живого стека: `server-push-*.spec.ts`,
  проект shard-rest, `--repeat-each=3`.
- Зафиксировать результат (воспроизводится / не воспроизводится, сколько попыток из скольких)
  — строка в описании будущего PR. Никаких правок кода в этой задаче.
- Если флейк воспроизводится — сохранить вывод падения (полный текст ошибки) как приложении
  к PR-описанию: это единственное живое доказательство «до».

## Task 3 — Inline-повтор push-утверждений С3 + диагностика исчерпания

**Классификация:** standard
**Сценарии:** С1 (единичный обрыв подписки не роняет прогон), С3 (диагностика в сообщении об ошибке)
**Required Docs:** спека §4 (строки «Push-утверждения С3» и «Диагностика»), §5b, §5d, §6

- Повтор — встроенный в файл спеки (без общей фикстуры, без нового DSL): локальная функция
  обёртки с бюджетом 1 повторная попытка на утверждение.
  - DB-poll и push-1 (`card not.toBeVisible`) — пассивное пере-вооружение ожидания;
  - push-2 — конверт из трёх ожиданий: `waitForResponse` GET /records/view, переход
    «Записи» и `recordRow not.toBeVisible` (это утверждение входит в конверт push-2 и
    пере-вооружается вместе с ним, отдельного бюджета не получает — так арифметика
    «два push-конверта по 2×10с» из спеки остаётся верной); повтор конверта — с повторным
    переходом (клик по навигационной ссылке заново; waitForResponse вооружается заново);
  - суммарное время наблюдения одного утверждения (окно × (1+повторы) + накладные) обязано
    оставаться ниже staleTime 30с — инвариант «тест не проходит за счёт истечения свежести
    кэша»; кэш-обходящих действий (перезагрузка страницы, обход кэша) в повторе нет.
- Предупреждение при съеденном повторе: `console.warn` с именем утверждения — зелёный прогон
  остаётся интерпретируемым в логе.
- Диагностика при исчерпании бюджета — в сообщении об ошибке обёртки: номер попытки, какое
  утверждение, началось ли перечитывание (взведён/сработал ли waitForResponse), наблюдался
  ли трафик событий. Трафик — существующий пробник `openFrameLogger` из общих фикстур:
  вызвать `openFrameLogger(browser)` в начале С3 — хелпер сам создаёт независимый
  контекст-слушатель к бэкенду (единственный существующий потребитель, офлайн-спека,
  вызывает его так же); подписка страницы A не затрагивается, подписка наблюдателя — тем
  более. Сигнатуру фикстуры не менять. Только метаданные: тела кадров/ответов, URL с
  query-параметрами, токены — никогда.
- С2 не трогается (у него активная семантика повтора — пере-набор входа); офлайн-спека не
  трогается.

## Task 4 — Локальная верификация после правок

**Классификация:** small
**Сценарии:** С2 (повтор в шардовой среде стабильно зелёный)
**Required Docs:** спека §7.2

- Та же механика, что в Task 1 (стек через `scripts/e2e-shard-start.sh` + `server-push-*.spec.ts`, shard-rest,
  `--repeat-each=3`): обе push-спеки зелёные, включая офлайн-спеку (сдвиг константы).
- В логе нет предупреждений о съеденных повторах на зелёном прогоне (если есть — это не
  падение, но строка для PR-описания: где именно сработал повтор).
- Юнит-слоя нет; витальные проверки набора — на CI (Task 5).

## Task 5 — CI-верификация DoD: три полных прогона + анти-маскировка

**Классификация:** standard
**Сценарии:** С1 (DoD: три прогона failed=0 и flaky=0), С4 (тест ловит смерть канала)
**Required Docs:** спека §7.3, §7.4, §1 (почему читается сводка, а не код выхода)

- Фича-ветка с правками Task 2–4: три полных shard-rest прогона подряд. В каждом — сводка
  Playwright по `server-push-invalidation`: failed=0 **и** flaky=0 (flaky = упало на первой
  попытке, прошло на ретрае — читается сводка/аннотации, не только зелёный код выхода).
- Разовая ручная проверка анти-маскировки (не коммитится): в контексте страницы A перехват
  маршрута `**/api/v1/events` с abort — С3 обязан упасть (перехват убивает и реконнекты,
  EventSource — обычный HTTP). Не использовать симуляцию «офлайн»: возврат сети вызывает
  шторку инвалидации на переподключении — ложно-зелёный результат. Результат проверки —
  строкой в PR-описании.
- Итог PR-описания: baseline «до» (Task 1) + итоги трёх прогонов + анти-маскировка.
