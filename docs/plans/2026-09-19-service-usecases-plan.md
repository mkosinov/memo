# План: слой сценариев usecases — «оркестратор вместо трактора» (#171)

- **Issue:** #171 · **Спека:** `docs/specs/2026-09-18-service-usecases-design.md` (rev2) · **Дата:** 2026-09-19
- Поведенческая дельта — в спеке (`## Behavioral Delta`): для пользователя изменений нет; задачи ниже реализуют пользовательские сценарии US1–US4 спеки без изменения поведения.

## Goal

Убрать cross-entity записи из `RecordService`: четыре сценария записи (создание, полное обновление, частичное обновление, удаление) переезжают в новый слой `usecases`; табличные команды — в репозитории владельцев; канон слоёв (`docs/domain-rules/service-layer.md`) — единственный источник правил. Существующий тестовый набор API проходит без правок.

## Architecture

Канон слоёв: api → usecases (сценарии, `@transactional`, одна транзакция + один пакет событий #239) → services (методы двух разновидностей) → repositories (единственное место табличных команд). Полная карта коридоров и дерево выбора — `docs/domain-rules/service-layer.md` (rev3).

## Tech Stack

FastAPI, SQLAlchemy async, pytest; фронтенд не затрагивается.

## Task 1: Репозитории — bulk-команды платежей и посещений

### Classification: small

Именованные множественные команды в репозиториях владельцев (если специализированных репозиториев нет — заводятся наследники базового, механика врезки по месту): `delete_by_record_id` для платежей; для посещений — снос по `record_id` и вставка пачки; для записей — снос собственных связок `record_tags` по `record_id` (своё ребро записи, канон правило 1). Фильтр — по собственной колонке-ссылке сущности; одна команда, не цикл по строкам.

### Required Docs

- `docs/domain-rules/service-layer.md` (правила 1, 4)

### DoD

- Команды живут в персистенс-слое владельца; вызываются только методами своего сервиса.

## Task 2: Методы сервисов без транзакции — для сценариев

### Classification: small

`PaymentService.delete_by_record`; у посещений — снос по записи и вставка пачки (без пересчётов — тайминг за сценарием); `ClientService` — «найти или создать клиента по телефону» и `VisitorService` — «найти или создать посетителя по имени» (перенос внутренних помощников RecordService поведение-в-поведение, включая канал по умолчанию). Методы получают идентификаторы-значения; импорт чужих моделей запрещён.

## Task 4: Сценарии update_record и patch_record

## Task 5: Сценарий delete_record — вся бизнес-цепочка

### Classification: standard

Каскад — строго в сегодняшнем порядке: посещения → платежи → связки `record_tags` (команда из Task 1) → строка записи. Контракт #285 не меняется.

## Task 6: Сужение RecordService и перепривязка тестов

### Classification: small
