# План #341: Фиксированные created_at в сид-фото — календарь-независимые photos-базлайны

Спека: `docs/specs/2026-09-20-photos-seed-fixed-dates-341-design.md` (Behavioral Delta — там,
здесь не дублируется).

## Goal

Visual-базлайны таблицы фото перестают зависеть от календаря: семь сид-фото получают фиксированные
нарастающие `created_at` (неделя 2026-06-15…21, 12:00), юнит-страж фиксирует контракт дат в
`test_seed.py`, затронутые photos-базлайны перегенерируются один раз. Ночные прогоны e2e,
пересекающие UTC-полночь, больше не красят `photos-table-*`; прод-код, API и «текущая» неделя
занятий не затрагиваются.

## Architecture

```
backend/src/seed/seed.py (_seed_photos)
   ↓ явные created_at: PHOTO_FIXED_DATES, ph1→ph7 нарастающе 2026-06-15…21 12:00 (naive)
   ↓ пришивает фото к тому же приёму, что WEEK_FIXED_START для записей/занятий
AbstractModel.created_at (default=datetime.utcnow) больше не срабатывает для сид-фото
   ↓
photos API (sort_by=created_at, sort_order=desc — дефолт) → разные даты = детерминированный DESC-порядок (ph7 первым, как сейчас)
   ↓
formatDate (photoColumns) рендерит фиксированные «15 июня»…«21 июня»
   ↓
toHaveScreenshot: прогоны календарь-независимы; разовая регенерация базлайнов (прецедент 550fe238)
```

Остаточные ограничения (в спеке, отдельными задачами не покрываются): прод-сортировка без
tie-breaker при равных `created_at`; таймзона браузера в playwright-конфиге не пинится.

## Tech Stack

Backend: Python (SQLAlchemy-сид `backend/src/seed/seed.py`), pytest (`backend/tests/test_seed.py`).
Frontend e2e: Playwright (`frontend/admin/e2e/`), проект `shard-rest`, регенерация базлайнов
`pnpm test:e2e:update` (`frontend/admin/package.json`).

## Task 1 — Сид: фиксированные нарастающие `created_at` у семи фото

**Классификация:** small
**Сценарии:** С1 (календарь-независимость базлайнов), С2 (детерминированный порядок строк)
**Required Docs:** спека §«Решение» п.1

- `backend/src/seed/seed.py`:
  - константа рядом с `WEEK_FIXED_START` (кластер фиксированных дат сида), naive-литералы:
    `PHOTO_FIXED_DATES: dict[str, datetime]` — ph1 → `datetime(2026, 6, 15, 12, 0, 0)`, …,
    ph7 → `datetime(2026, 6, 21, 12, 0, 0)` (нарастающие дни, полдень; aware-объекты запрещены —
    колонка naive);
  - в `_seed_photos` каждый из 7 словарей получает `created_at=PHOTO_FIXED_DATES[p["id"]]`
    (значения идут в словари явно — дефолт `datetime.utcnow` из `AbstractModel` перестаёт
    срабатывать для сид-фото);
  - остальные поля (владельцы, теги, `is_public`) не меняются.
- Юнит-проверка задачи — Task 2 (отдельный страж); в этой задаче тесты не пишутся.

## Task 2 — Юнит-страж фиксированных дат фото

**Классификация:** small
**Сценарии:** С5 (правка дат сида ловится стражем, а не красным CI)
**Required Docs:** спека §«Решение» п.2

- `backend/tests/test_seed.py` — новый тест по паттерну существующего стража фиксированной недели
  `test_seed_fixed_week_dates_in_range` (`:392`):
  - после `seed_data(db_manager)`: `SELECT id, created_at FROM photos ORDER BY id`;
  - семь ожиданий **жёстко прописаны в тесте литералами** (id → точное `datetime(2026, 6, …, 12,
    0, 0)`), НЕ импортируются из `PHOTO_FIXED_DATES` — иначе правка константы сида молча пройдёт
    страж;
  - SQLite хранит datetime ISO-строкой — парсинг `_dt.fromisoformat(...) if isinstance(row…, str)`,
    как в существующем страже;
  - отдельная проверка нарастания: даты ph1 < ph2 < … < ph7 (контракт детерминизма DESC-порядка,
    сценарий С2).
- Запуск `pytest backend/tests/test_seed.py` — новый страж зелёный (Verification п.1 спеки).
