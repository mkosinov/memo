# План #319 — Гарантированные настройки пользователя (`UserSettings`)

- **Спека:** `docs/specs/2026-09-20-user-settings-guarantee-319-design.md` (rev2)
- **Issue:** #319 (depends-on: #171 — слой сценариев `usecases`)
- **Дата:** 2026-09-20

## Goal

Инвариант «на покое»: у каждого пользователя есть строка `UserSettings` — она создаётся вместе с пользователем (все пути), дописывается в базу при первом чтении (get-or-create), удаление строки работает как «сброс к дефолтам», а смерть пользователя сносит строку каскадом. Behavioral Delta — в спеке §8.

## Architecture

- Бэкенд: сервис настроек получает метод-ядро «создать дефолты» без собственной транзакции и декорированный `get_or_create_by_user_id` (коридор 1); сценарий `create_user` в `usecases/user.py` (коридор 2, после #171) собирает `User` + `UserSettings` одной транзакцией; флоу «учётки» карточки сотрудника в переходный период зовёт ядро внутри своей транзакции (кадровый долг — #326); каскад удалений (`Staff → users`) дополняется сносом настроек bulk-командой репозитория; `POST` берёт `user_id` из сессии; сид и тестовая фабрика создают строки настроек.
- Фронт: из `UserSettingsContext` убирается POST-фолбэк; из клиента API удаляются методы без потребителей; кэш подчиняется ответу сервера.
- Канон обновлён вместе со спекой (коммит `b20bc6c`): `user_settings.md`, `deletion.md`, `auth.md`.

## Tech Stack

FastAPI + SQLAlchemy async (SQLite, WAL), слой `usecases` из #171, pytest (сервисные и HTTP-тесты), Playwright e2e, vitest, `@memo/api-client`.

## Task 1 — Сервис настроек: ядро дефолтов + get-or-create + POST из сессии

standard · Сценарии: С2, С6 (защитный контракт не меняется)

Required Docs: спека §4, §5.1, §5.3; канон `docs/domain-rules/user_settings.md` (Invariants, Business Logic, API Endpoints).

- Метод-ядро «создать дефолты» без декоратора (переиспользуется сценарием, «учёткой», get-or-create).
- Новый декорированный `get_or_create_by_user_id`: атомарный `INSERT ... ON CONFLICT(user_id) DO NOTHING` (диалект SQLite) + `SELECT`; без перехвата исключений; отказ по блокировке/недоступности — честная 500.
- Роутер: `GET` переводится на новый метод; ответ помечается `Cache-Control: no-store`; существующий `get_by_user_id` НЕ меняется (им пользуются `PUT`/`PATCH` и контракт #179).
- `POST`: `user_id` из сессии, поле тела игнорируется.
- Тесты (pytest): GET без строки → 200 + дефолты + строка в БД (перепись старого HTTP-теста «GET → 404»); POST с чужим `user_id` в теле создаёт свою строку; дубль POST → 422 `INTEGRITY_VIOLATION`; контракт #179 (`test_standalone_patch_contract.py`) зелёный без правок.

## Task 3 — Каскад смерти: настройки сносятся вместе с учёткой

small · Сценарии: С5

Required Docs: спека §5.4; канон `docs/domain-rules/deletion.md` (строка UserSettings).

- Bulk-команда `delete_by_user_ids` в репозитории настроек (фильтр по собственной колонке `user_id` — канон bulk-правила).
- Обработчик каскада `Staff → users` (`domain/deletion.py`) сносит строки настроек сносимых пользователей.
- Тесты: удаление карточки с учёткой (execute-режим) → в БД нет ни `User`, ни `UserSettings`; сухой прогон (dry-run) показывает зависимости как раньше.

## Task 4 — Сид и тестовая фабрика создают настройки

small · Сценарии: С2 (база закрыта с рождения), С1 (сид)

Required Docs: спека §5.5.

- Сид: обоим пользователям (админ, мастер) — строки настроек с дефолтами.
