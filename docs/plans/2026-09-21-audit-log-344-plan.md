# План #344 — Журнал действий пользователей (audit log)

- **Спека:** `docs/specs/2026-09-20-audit-log-344-design.md` (rev2, коммит `b7b0660d`)
- **Issue:** #344 (depends-on: пуст)
- **Дата:** 2026-09-21

## Goal

Каждое законченное действие пользователя над данными оставляет атомарную запись в журнале (кто / что / над чем / когда / что именно изменилось), и администратор видит историю в новом разделе «Журнал» с фильтрами. Behavioral Delta — в спеке §10, не дублируется.

## Architecture

- **Механика записи (сквозная, зеркалит #239):** запросный аккумулятор аудита на contextvar в `backend/src/events/audit.py` (пометки `mark_audit`, владение токеном, канонический сериализатор, маскирование, словарь подписей); автор — contextvar, который ставит общее ядро резолва сессии (`resolve_authed` — покрывает строгий guard и мягкий резолвер); вставка накопленных строк — в `@transactional` после метода до коммита, только обёрткой-владельцем накопителя. Контракт событий #239 (накопитель имён, публикация) не меняется.
- **Сбор:** авто-сбор в общем репозитории (`BaseRepository.create/update/patch/delete/reorder`) с правилом целевой сущности и старшинства (явная пометка вытесняет авто-сбор); явные пометки — архивация/восстановление (`ArchiveService` + собственные `StaffService`), сценарии записей, фото, профиль, визиты, платежи, настройки, сотрудники. Отложенные удаления (#285/#286): строка на финальном DELETE.
- **Чтение:** `GET /api/v1/audit-logs` (+`/authors`) — `require_admin`, коридор 3 (свободная читающая функция с join users → staff; роль — из строки журнала).
- **Фронт:** маршрут `/audit` в `ADMIN_ONLY_SECTIONS` + пункт меню; `DataTable` по канону; фильтры (автор, действие, сущность, период); api-client.
- Канон `docs/domain-rules/` не меняется: журнал — новый сквозной механизм, не меняющий коридоры и правила слоёв.

## Tech Stack

FastAPI + SQLAlchemy async (SQLite, WAL), alembic, pytest; Next.js admin (`DataTable`, фильтры страницы клиентов), Playwright e2e (двухконтекстная фикстура server-push), vitest, `@memo/api-client` (zod).

## Task 2 — Аккумулятор аудита, автор, вставка в `@transactional`

standard · Сценарии: базовая механика С1–С6

Required Docs: спека §4.1, §4.2 (правило старшинства), §4.4, §5.1; прецедент `backend/src/events/emitter.py`; WARNING о цикле импортов в `backend/src/events/entities.py`; канон `docs/domain-rules/service-layer.md` (правила транзакций).

- `backend/src/events/audit.py`: `mark_audit(...)`, открытие/закрытие накопителя с токеном владения, actor-contextvar (`user_id`, `role`); канонический сериализатор значений (дата → ISO-строка, десятичное → строка, перечисление → значение); маскирование `phone`/`phone_digits` → `mask_phone`, `email` → без полной строки; словарь подписей `entity_label` с обрезкой до 255; потолок длины строковых скаляров в `changes` — 500 символов, обрезка с суффиксом «…»; свободно-текстовые поля в снимок не попадают.
- `resolve_authed` ставит actor (общее ядро — строгий и мягкий резолверы покрыты разом).
- `@transactional` (`backend/src/services/decorators.py`): после успешного метода, до коммита — вставка накопленных строк в ту же сессию; вставляет только обёртка-владелец накопителя (для бес-`self` обёрток-сценариев накопитель открывается пустым — как у аккумулятора имён; каскадные пометки для дочерних сущностей сценарий не ставит, действует правило «одно действие — одна строка»); импорт модуля аудита — ленивый (прецедент `entities`).
- Тесты (pytest): нет автора → нет вставки; ошибка метода → откат действия и журнала вместе; вложенные декорированные уровни → одна вставка на проводку; тесты #239 (полнота сущностей, публикация имён) зелёные без правок.

## Task 3 — Автосбор в общем репозитории

standard · Сценарии: С2 (изменение платежа), С5 (маскирование), С6 (удаление)

Required Docs: спека §4.2, §4.6; `backend/src/repositories/generic.py`; словарь имён `backend/src/events/entities.py`.

- `BaseRepository.create/update/patch/delete/reorder` формируют сырые записи `{entity, action, entity_id, before, after}` (старые значения — из прочитанной строки; для `create` `before=None`, снимок — ключевые поля по словарю модуля аудита, §5.1; no-op без изменений поля не пишется); имя сущности — из словаря #239, импорт ленивый.
- Правило целевой сущности: репозиторий читает целевую сущность из аккумулятора аудита (ту же contextvar-переменную, которую открыла обёртка `@transactional`) и пишет запись журнала только при совпадении с ней; каскадные дочерние строки не пишутся.
- Правило старшинства: явная `mark_audit` (совпадение сущности + идентификатора) вытесняет авто-собранную строку.
- `reorder`: одна строка на операцию (`entity_id` null, подпись «N объектов»); порядок не изменился → нет строки.
- Тесты: представители каждого мутационного метода; каскад сценария записи не порождает строк визитов/платежей; no-op PATCH; дублирование «явная + авто» не даёт двух строк.

## Task 4 — Явные пометки нестандартных мутаций

standard · Сценарии: С2, С6

Required Docs: спека §4.3, §4.5, §8 (таблица охвата); живые сервисные файлы по перечню §8.

- `ArchiveService.archive/restore` — действие `archive`/`restore`, без снимка; перед пометкой сверка состояния (no-op не пишется); авто-строка `update` по `is_active` вытесняется.
- Собственные `StaffService.archive/restore` (самостоятельные декорированные методы, реализованные без делегирования в общий `ArchiveRepository.patch`) — явная `mark_audit` внутри тела метода, плюс та же сверка текущего `is_active`: повторная архивация архивированного (восстановление активного) не пишется.
- Сценарии `backend/src/usecases/records.py` (`create_record`/`update_record`/`patch_record`/`delete_record`) — строка записи; отложенное удаление: `mark_audit(entity="records", action="delete")` ставится в `delete_record` рядом с `mark_changed("records")`, до финального удаления строки записи; каскадные визиты/платежи журналом не пишутся и пометок не требуют; отдельного перехвата «постановки» и «отмены» нет — до API они не доходят.
- Фото: массовые операции — одна `mark_audit(entity="photos", action="create"|"delete", entity_id=null, entity_label="N фото", changes={filenames: [...]})` на операцию пользователя, не на каждый файл; одиночные — стандартно. Профиль, визиты, платежи, настройки пользователя, сотрудники (`create`/`update`/`delete`) — явные пометки по перечню §8.
- Тесты: каждый путь §8 закрыт тестом-представителем (строка с корректным действием и подписью); двойных строк нет.

## Task 5 — API чтения журнала

standard · Сценарии: С1 (открыть журнал), С3 (фильтры), С4 (мастер не допущен)

Required Docs: спека §6; канон `docs/domain-rules/service-layer.md` (коридор 3); образцы пагинации/фильтров — `backend/src/api/v1/position.py`, фильтры платежей/записей.

- `GET /api/v1/audit-logs`: параметры `page`/`per_page`/`user_id`/`action`/`entity`/`entity_id`/`date_from`/`date_to`, сортировка `created_at DESC`, ответ `PaginatedResponse[AuditLogResponse]` (`user: {id, label}` из join users → staff, `user_role` из строки журнала); доступ `require_admin`. Запрос — один `select(AuditLog)` с `join(User)` и `outerjoin(Staff)`, `user: {id, label}` подтягивается тем же запросом — без N+1 по строкам журнала.
- `GET /api/v1/audit-logs/authors`: уникальные авторы `[{user_id, label}]`, `require_admin`.
- Граница дня периода — общий канон `backend/src/domain/dates.py`: `date_from` от 00:00:00 включительно, `date_to` до конца дня (те же семантики, что у фильтров платежей/записей).
- Тесты (pytest): 403 мастеру, 401 анониму; каждый фильтр + пагинация + сортировка; `/authors` на пустом журнале.
