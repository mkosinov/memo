# План #232: Deep-link клиентов — машинный фильтр по идентификаторам

- Issue: [#232](https://github.com/mkosinov/memo/issues/232)
- Спека: docs/specs/2026-09-21-clients-deeplink-id-param-232-design.md (rev4)
- Дата: 2026-09-21
- Behavioral Delta — в спеке §1, здесь не дублируется.

## Goal

Заменить транспорт deep-link «UUID в поисковом поле» на машинный фильтр по набору идентификаторов: адрес страницы — единственный источник сужения; закрытие карточки ничего не трогает; автооткрытие карточки только при одном идентификаторе; фильтр `id` — общий кирпень всех списочных эндпоинтов (поле в базовом классе параметров, применение в универсальном пути и вью-сборщиках).

## Architecture

```
адрес ?clientId=… (повторения ключа)
        ↓ эффект синхронизации (единственный писатель — адрес)
ClientFilters.clientIds (машинное поле, вне поискового бокса)
        ↓ явные ключи query
GET /api/v1/clients?id=…&id=… (PaginationParams.id: list[UUID], кап 100)
        ↓ предикат IN
GenericService._list_stmt (простые списки) | вью-сборщики
(list_clients_with_stats — клиенты; записи, мастера, фото)
        ↓
суженная таблица + чип; один id → автооткрытие карточки
```

Фронт-механика снятия: крестик чипа и полный сброс удаляют параметр из адреса (с сохранением прочих query-параметров); фильтр доводится эффектом. Удаляются скрытые мутации адреса (onClose-replace, dead-link cleanup). Совместимо с будущим #349 (общий URL-хук) и #217 (переименование сборщика в `list_clients_view`).

## Tech Stack

FastAPI + pydantic v2 (Depends-модели, `BeforeValidator` на уровне поля), SQLAlchemy 2 async (`ColumnElement`-предикаты), packages/api-client (zod), Next.js App Router (`useSearchParams` под Suspense), React Query, vitest + pytest + Playwright.

## Task 1. Backend: поле `id` в базовых параметрах списка

Классификация: small. Сценарии: US-6 (контракт мусора), фон всех списков.

- `PaginationParams` (backend/src/schemas/pagination.py): поле `id: list[UUID] | None = None`; ввести именованную константу `MAX_LIST_IDS = 100` рядом с потолком `per_page` и использовать её в `Field(..., le=MAX_LIST_IDS)` (сегодня потолок страницы — литерал `le=100`; без имени константа «размажется» по двум литералам); дедуп повторов через `BeforeValidator` на уровне поля (НЕ модельный валидатор — на Depends()-моделях модельные ловят 500, правило зафиксировано в `schemas/client.py`).
- Контрактные 422: невалидный UUID в любом значении; >100 значений — единообразно для всех списочных эндпоинтов (поле наследуется всеми списочными схемами).
- pytest: контрактные 422 (мусор, переполнение) на представителе-эндпоинте.

Required Docs: спека §3.1; `docs/domain-rules/` — правило валидаторов Depends()-моделей (комментарий-канон в `schemas/client.py`).

## Task 2. Backend: применение IN-предиката — универсальный путь и вью-сборщики

Классификация: standard. Сценарии: US-1, US-5, US-8. Зависит от Task 1 (поле `PaginationParams.id`).

- `GenericService._list_stmt` (backend/src/services/generic.py): типизированный предикат `id IN (…)` из поля параметров отдельным случаем, МИМО мешка `**filters` (мешок остаётся равенствами «колонка = значение»).
- Общий однострочный хелпер сужения для вью-сборщиков; применить: `list_clients_with_stats` (клиенты; после реализации #217 — `list_clients_view`) + вью-сборщики записей, мастеров, фото — по строке хелпера.
- Порядок строк — стандартная сортировка эндпоинта; скоуп мастера и маскировка D3 наследуются (предикат скоупа навешивается до фильтров).
- pytest (`test_api_clients.py` — полный набор): ровно указанные клиенты; дедуп на уровне строк; порядок не по адресу; AND с `status`/`q` (безвредность `?id=X&q=X`); скоуп мастера — недоступные не возвращаются, маскировка на месте (seed: клиент без записей + клиент с записями только к чужим активностям). Тесты-представители остальных путей: справочник через универсальный путь (локации) + записи, мастера, фото. Страж: `id` не попадает в мешок `**filters`.

Required Docs: спека §3.1; `docs/domain-rules/service-layer.md` (исключение «ручной сборщик списка клиентов», канон слоёв); `docs/domain-rules/clients.md` («Two mapper paths», маскировка D3).

## Task 4. Frontend: машинное поле, синхронизация «адрес → фильтр», жизненный цикл модалки

Классификация: standard. Сценарии: US-1, US-2, US-5, US-6, US-7.

- `ClientFilters.clientIds?: string[] | null` (frontend/admin/contexts/ClientsContext.tsx): машинное, вне поискового бокса и его контролируемого состояния; сборка query — явные ключи.
- Чтение адреса (clients/page.tsx, под Suspense #231): `getAll('clientId')` → покомпонентная строгая валидация UUID → дедуп → пусто = параметра нет; иначе `initialFilters = {clientIds, status: 'all'}`.
- Правило автооткрытия: после валидации и дедупа ровно один → модалка автоматически; ≥2 — нет.
- Эффект живой синхронизации адрес → `clientIds` (mount, «назад/вперёд», ручная правка, снятие); обратного потока нет.
- Удалить скрытые мутации адреса: в `onClose` модалки сохранить обнуление `selectedClient`/`isCreateMode`, удалить ветку `if (clientIdFromQuery) router.replace('/clients', { scroll: false })`; удалить целиком dead-link cleanup-эффект при пустом результате.
- Latch #216 (`consumedClientIdRef`): инвариант — блокирует авто-переоткрытие, пока в адресе ровно один валидный идентификатор; уход параметра сбрасывает. Условие эффекта автооткрытия — `clientIds.length === 1` (после валидации и дедупа); при ≥2 идентификаторах автооткрытие не срабатывает ни при монтировании, ни при изменениях (US-3).
- Unit (vitest): парсинг адреса (один/несколько/повтор-дедуп/мусор покомпонентно/все невалидны); эффект синхронизации; `ClientsPage.test.tsx` — initialFilters-утверждение переписать (`{search: id, status:'all'}` → `{clientIds, status:'all'}`).

Required Docs: спека §3.3–3.4; `docs/domain-rules/` — комментарий-канон #216/#231 в clients/page.tsx.

## Task 5. Frontend: чип сужения и снятие

Классификация: small. Сценарии: US-3, US-4.

- Чип над таблицей при активном сужении: «Открыт по ссылке» / «Открыто по ссылке: N»; без UUID и имён; крестик — доступная кнопка (`aria-label`, фокус). Компонент — новый файл `frontend/admin/app/(main)/clients/components/ClientDeepLinkChip.tsx`, рендерится между блоком фильтров и таблицей в `clients/page.tsx`.
- Крестик: удалить все вхождения `clientId` из адреса (`URLSearchParams.delete` → `router.replace`, `scroll: false`), прочие query-параметры сохранить; фильтр доводится эффектом (Task 4) — без `setFilters` в обработчике.
- `resetFilters`: чистит адрес от `clientId` в той же точке (новая документируемая ответственность; прочие query-параметры сохраняются).
- Unit: рендер чипа (один/N), крестик чистит только адрес, `resetFilters` чистит адрес, пользовательские фильтры при точечном снятии сохраняются.

Required Docs: спека §3.5; `docs/design-system.md` (стили чипа/кнопок).
