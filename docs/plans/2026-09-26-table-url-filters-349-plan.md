# План: фильтры табличных страниц в URL (#349)

- Дата: 2026-09-26
- Спека: `docs/specs/2026-09-26-table-url-filters-349-design.md` (ревизия 3, Gate B пройден) — Behavioral Delta и User Scenarios там, здесь не дублируются.

## Goal

Все табличные страницы админки держат фильтры (включая пагинацию: `page` + `per_page`) в URL через один общий хук `useTableUrlState`: ссылка открывает таблицу в нужном состоянии одним запросом, перезагрузка не теряет состояние, «назад» пошагово отменяет изменения таблицы (все пользовательские записи — `push`, служебная коррекция страницы — `replace`).

## Architecture

```
страница (Suspense-граница)
  ↓ создаёт
useTableUrlState(config) — единственный писатель URL: парсеры-пресеты, атомарный update, push/scroll:false
  ↓ передаётся как опциональная интеграция (управляемый режим)
createPagedListContext — page/perPage/sort/status/search/filters берёт из хука, сеттеры → update одним батчем
  ↓ рендерит
DataTable — черновик поиска (дебаунс 300 мс) ресинхронизируется с q из URL; коммит = update({q})
```

- Первая миграция — клиенты (проверка контракта на живой посадочной площадке deep-link #231), затем волна по чеклисту спеки §5.
- `useRecordsPeriod` упраздняется на этапе записей (один писатель на страницу); `useScheduleView` не трогается.
- Backend не меняется: имена URL-параметров совпадают с каноном API.

## Tech Stack

Next.js 14 App Router (`useSearchParams`/`useRouter`), React Query, существующие vitest + Playwright. Новых зависимостей нет (ни nuqs, ни Zod).

## Task 1. Хук `useTableUrlState`: пресеты, чтение, запись

Классификация: standard. Required Docs: спека §1, §2.

- Хук в `frontend/admin/hooks/`: конфиг = имена + дефолты + пресеты `enum` / `int` (границы) / `string` (кап 200) / `datePair` (частичная смена, инверсия пары; дефолт конфигурируем — «текущая неделя» у записей, «не задано» у журнала) / `arrayOf` (повторение параметра, поэлементная валидация, дедуп, ≤ 20).
- Чтение: вывод `state` из URL при рендере, тихий фолбэк на дефолт по невалидному, `page` 1…10⁴, `per_page` ∈ {10, 20, 50, 100}; осиротевший `sort_order` без `sort_by` игнорируется (параметры сортировки на сервер не шлются).
- `update(patch)`: атомарный батч (фильтр + `page→1` — одна навигация), дефолты из URL удаляются, неуправляемые параметры сохраняются, коалесценция быстрых записей в пределах кадра, `router.push` + `{ scroll: false }`; служебный режим `replace` для коррекции страницы.
- Сценарии: US-2 (одно взаимодействие = один шаг истории), US-3 (невалидные значения → дефолты).
- DoD: vitest — пресеты (валид/невалид/капы/белый список per_page), сериализация (дефолты не пишутся, неуправляемые сохраняются), атомарный батч, коалесценция, StrictMode-двойной рендер без второй записи.

## Task 2. Управляемый режим фабрики `createPagedListContext`

Классификация: large. Required Docs: спека §3, §2 (коррекция страницы).

- Опциональная интеграция: при подключённом хуке `page`/`perPage`/`sortBy`/`sortOrder`/`status`/`search`/`filters` управляемые (без собственных `useState`); `initialFilters` на мигрировавших страницах упраздняется.
- Сеттеры (`setPage`/`setPerPage`/`setSort`/`setStatus`/`setFilters`/`setSearchWithReset`) → `update(...)` одним батчем; смена `per_page` при `page>1` сбрасывает страницу той же записью.
- Замена авто-декремента пустой страницы (`page−1` штормом) одиночной коррекцией: `total>0` → `ceil(total/per_page)` служебным `replace`, `total=0` → дефолт.
- Без интеграции фабрика работает как сегодня (обратная совместимость до волны).
- Сценарии: US-2 (батч), US-5 (коррекция устаревшей ссылки).
- DoD: vitest фабрики в управляемом режиме (батчи, коррекция, отсутствие второго запроса на монтировании).

## Task 3. DataTable: ресинхронизация черновика поиска

Классификация: small. Required Docs: спека §1 («Черновик поля поиска»).

- Эффект ресинхронизации `draft` со значением `q` из URL по примитиву (сегодня — снимок при монтировании, `DataTable.tsx:70`); сброс поиска — через ту же запись `update({ q: дефолт })`.
- Сценарии: US-2 (поле после «назад/вперёд» синхронно фильтру), US-1 (адрес соответствует выполненному запросу).
- DoD: vitest — черновик следует за внешним изменением `q`, дебаунс-коммит = одна запись.

## Task 4. Клиенты: первая миграция

Классификация: standard. Required Docs: спека §3 (deep-link), §4.

- Хук на странице клиентов, управляемый режим фабрики; deep-link `?clientId=` остаётся отдельным параметром; эффективный статус = `status ?? (clientId → 'all' : 'active')`, без записи в URL.
- Сценарии: US-1, US-3, US-4.
- DoD: e2e — открытие ссылки с фильтрами + счётчик «ровно один запрос»; dirty-URL → дефолты + `q`; существующие deep-link-сценарии #232 зелёные.

## Task 5. Волна, группа 1: должности, теги, локации

Классификация: standard. Required Docs: спека §5.

- Suspense-граница уровня страницы (проверка/добавление — сегодня есть только у клиентов, записей, расписания и логина) + подключение хука: должности (`sort_*`/`page`/`per_page`), теги и локации (+ `q`).
- Сценарии: US-5 (ядро: ссылка → состояние восстановлено, один запрос).
- DoD: параметризованный e2e-каркас волны с этими страницами; дым на каждую.

## Task 6. Волна, группа 2: услуги + материалы

Классификация: standard. Required Docs: спека §5, §2 (префикс `mat_`).

- Сценарии: US-5 + точечный доп-сценарий «оба набора фильтров в одной ссылке».
- DoD: e2e на комбинированную ссылку; дым.

## Task 7. Записи: недопериодные фильтры + порт периода, упразднение `useRecordsPeriod`

Классификация: large. Required Docs: спека §Концепт (один писатель), §5 пункт 4.

- Период `from`/`to` переносится в конфиг хука (пресет `datePair`: частичная смена, инверсия, дефолт «текущая неделя»); фильтры `q`/`status`/`location_id`/`service_id`/`master_id` + сортировка/пагинация — через хук; `useRecordsPeriod` удаляется.
- Полный круг потребителей порта (все переподключаются на хук): дата-инпуты `RecordsFilters.tsx` (`explicitFrom`/`explicitTo` — отсутствующая сторона остаётся отсутствующей), `RecordsContext.tsx`, независимый читатель периода `Menubar.tsx` (`readPagePeriod` — календарь-индикатор в меню остаётся консистентен).
- Перенос тестов: `__tests__/useRecordsPeriod.test.tsx`, `RecordsPeriodContext.test.tsx`, `RecordsFiltersUrl.test.tsx`, `RecordsFilters.test.tsx`, `RecordsContext.test.tsx` — ассерты политики истории `replace`→`push` (решение Gate B), остальные зелёные.
- Сценарии: US-1/US-2 на странице записей.
- DoD: e2e записи — ссылка с периодом+фильтрами восстанавливается одним запросом; «назад» отменяет смену периода; Suspense-граница уже есть (проверка).

## Task 10. Сквозная верификация волны

Классификация: standard. Required Docs: спека §Тестирование, §5.

- Параметризованный e2e по всему чеклисту (ссылка → восстановление, ровно один запрос) + точечные доп-сценарии (массив `tag_id`, префиксы `mat_`, журнал, форс `status=all`, односимвольный `q` — текст в поле, серверный фильтр не активен).
- Регресс: счётчики запросов расписания/записей/клиентов не меняют чисел; полный витр/линт/тайпчек.
- Сценарии: US-5 целиком.
- DoD: все e2e зелёные в полном прогоне.
