# План: #397 — страж ухода со страницы во время окна отмены (beforeunload на конвейере отложенных удалений)

- **Issue:** #397
- **Спека:** `docs/specs/2026-09-27-beforeunload-guard-397-design.md` (rev2). Behavioral Delta — в спеке §3, здесь не дублируется.

## Goal

Пока в общем конвейере отложенных удалений (`PendingActionsProvider`) есть незавершённые действия — ожидающие окно отмены или отправки в полёте, — страница ставит стандартный браузерный страж ухода (`beforeunload`); конвейер опустел — страж снят. Принудительный уход на /login при истечении сессии (401) диалог не поднимает. Сервер и потребители конвейера не меняются.

## Architecture

```
lib/forcedNavigation.ts (новый, ~10 строк) — признак «навязанный системой уход»
        ↓
AuthContext (401-перехватчик) — ставит признак перед полным переходом на /login
        ↓
PendingActionsContext — реактивный счётчик {ожидающие, отправки} рядом с картой таймеров;
        hasPending = суммарный счётчик > 0 → useUnsavedChangesGuard(hasPending) (существующий хук)
        ↓
vitest __tests__/PendingActionsContext.test.tsx (9 групп проверок) + e2e С3 (best-effort)
```

**Изменяется:** `frontend/admin/lib/forcedNavigation.ts` (новый); `frontend/admin/contexts/AuthContext.tsx` (2 строки в 401-перехватчике); `frontend/admin/contexts/PendingActionsContext.tsx`; `frontend/admin/__tests__/forcedNavigation.test.ts` (новый); `frontend/admin/__tests__/PendingActionsContext.test.tsx`; `frontend/admin/e2e/pending-delete-unload-guard.spec.ts` (новый, best-effort); `CHANGELOG.md`.
**Не изменяется:** контракт `PendingAction`, порядок «запись из карты удаляется до коммита» (#285 rev8), обработка ошибок коммита (#243), потребители, сервер. Канон-документы не меняются — решение плана: спека §5.4 перечисляет контракты/потребителей/сервер и канон не затрагивает, новый страж ничего в доменных правилах удаления не меняет; если архитектор IMPL сочтёт строку в deletion.md нужной — это отдельная канон-правка с ОК пользователя, не здесь.

Решение Gate B (27.09, ответ пользователя): покрытие «отправок в полёте» (С5) — **да**, счётчик двухкомпонентный; спека §8 дополнена отметкой о решении.

Ключевые инварианты (спека §5.1): дедупликация повторной постановки того же id — нетто-ноль по счётчику; одно функциональное обновление на переход (без мгновенных нулей); декремент «отправок» — одна точка на любой исход коммита (ранние ветки возврата не должны уметь его пропустить); страж активен при суммарном счётчике > 0 (либо ожидающие, либо отправки).

## Tech Stack

React 18 + Next.js админка (клиентский провайдер); TypeScript; vitest + jsdom; Playwright e2e; CHANGELOG (Keep a Changelog).

Координация (не блокирует): #345 в IMPL не трогает конвейер — слияние с ней в любом порядке, страж покрывает её 5 сущностей автоматически. Обратная сторона из плана #345: её e2e-сценарии при слиянии после этого стража обрабатывают браузерный диалог ухода по рецепту и под регресс-аудитом задачи 4 ниже.

## Task 2 — Счётчик незавершённых действий + подключение стража в конвейере
- **Классификация:** standard
- **Файлы:** `frontend/admin/contexts/PendingActionsContext.tsx`
- Новое состояние: `useState`-объект `{ pending, inflight }`; все переходы — функциональные обновления от предыдущего значения, одно обновление на переход (спека §5.1).
- Переходы:
  - enqueue нового id → `pending + 1`;
  - повторная постановка существующего id (ветка дедупликации перед созданием нового таймера) — счётчик не трогается (нетто-ноль; в коде комментарий-ограничение «правило дедупликации #397»);
  - клик «Отменить» по защищённому пути (запись в карте есть, за существующим гейтом `if (!t) return`) → `pending − 1`;
  - истечение окна (внутри таймера, после удаления записи из карты) — один объединённый переход `pending − 1, inflight + 1`;
  - завершение коммита → `inflight − 1` в единственной точке: существующее тело коммита (try/catch с ранними возвратами 404/onError) выносится во внутреннюю функцию, декремент — в `finally` обёртки, чтобы ранние возвраты физически не могли его пропустить.
- `hasPending = pending + inflight > 0`; в теле провайдера `useUnsavedChangesGuard(hasPending)`.
- Размонтирование провайдера: отдельного сброса счётчика не нужно — состояние умирает с провайдером, слушатель снимает очистка эффекта хука (спека §5.3).
- Контракты не трогаются: `PendingAction` (id/commit/undo/onError), порядок «запись из карты до коммита», обработка ошибок #243 (404-тихий успех, ветка 5 deletion.md), потребители.
- **DoD:** lint/tsc зелёные; существующие тесты конвейера и потребителей зелёные (поведение без ухода не меняется).
- **Сценарии:** С1, С2, С4, С4а, С5, С6, С7 (поведенческая основа; автотесты — задача 3).
- **Required Docs:** спека §5.1, §5.2, §5.3, §5.4.

## Task 3 — vitest-покрытие конвейера
- **Классификация:** standard
- **Файлы:** `frontend/admin/__tests__/PendingActionsContext.test.tsx` (расширяется), при необходимости мини-хелпер рендера провайдера с постановкой действия.
- Основные утверждения — шпионы `addEventListener`/`removeEventListener` на `window` (паттерн `__tests__/useUnsavedChangesGuard.test.tsx`); синтетическая отправка отменяемого `beforeunload` с проверкой `defaultPrevented` — дополнительный слой (jsdom сам событие при выгрузке не возбуждает). Группы (спека §7):
  1. страж поставлен при постановке в конвейер; снят, когда оба счётчика пусты (С1);
  2. дедупликация повторной постановки того же id — нетто-ноль: счётчик не раздут, страж снялся ровно один раз (С1);
  3. снятие на каждом исходе коммита: успех; 404-тихий успех; ошибка по умолчанию (откат + тост); ошибка с обработчиком потребителя (путь `staleAwareOnError`) (С1);
  4. клик «Отменить» в тосте по защищённому пути: страж снят сразу после декремента, следующий синтетический уход не подтверждается (С4);
  5. поздний клик «Отменить» после истечения окна — декремента нет, страж держится до завершения отправки (С4а);
  6. страж держится, пока отправка в полёте (С5); при двух незавершённых действиях — до завершения последнего (С6);
  7. сосуществование со вторым подключённым стражем — оба обработчика живут, конфликта нет (С1);
  8. принудительная навигация: `markForcedNavigation()` при незавершённом действии → `defaultPrevented === false`; без признака → `defaultPrevented === true` (С8, С2);
  9. вне конвейера `beforeunload` не подтверждается (С7);
  10. С2/«Остаться»: после отклонённого ухода страж остаётся и снова подтверждает следующее событие.
- Минимальный пол на случай отказа от e2e (задача 4): группа «синтетическая отправка при незавершённом действии даёт `defaultPrevented === true`» обязательна независимо от судьбы e2e.
- **DoD:** все группы зелёные локально и в CI; lint/tsc зелёные.
- **Сценарии:** С1–С8 (vitest-доля).
- **Required Docs:** спека §7.

## Task 4 — e2e сценарий С3 (best-effort, с зафиксированной границей)
- **Классификация:** small
- **Файлы:** `frontend/admin/e2e/pending-delete-unload-guard.spec.ts` (новый)
- Рецепт постановки отложенного удаления — из `e2e/activity-deferred-delete.spec.ts`. Предусловия детерминизма (спека §7): обработчик `page.on('dialog')` зарегистрирован ДО действия; жест — клик удаления; путь закрытия — `page.close({ runBeforeUnload: true })`, путь перезагрузки — `page.reload()` с принятым диалогом.
- Проверки:
  - С3 «Покинуть»: удаление → в окне перезагрузка с принятым диалогом → после загрузки строка на месте;
  - С3 «Остаться»: удаление → перезагрузка с отклонённым диалогом → после окна строка исчезла;
  - негативный: конвейер пуст (окно дотикало) → `page.close({ runBeforeUnload: true })` закрывает страницу без события диалога;
  - позитивный на закрытие: удаление → в окне `page.close({ runBeforeUnload: true })` → событие диалога пришло (факт вооружённости стража; состояние строки после закрытия не проверяется).
- Регресс-аудит чужих e2e (страж ловит только уходы в окне отмены/отправки, но в e2e-наборе сотни goto/reload, часть внутри флоу удалений): полный прогон admin e2e; если какой-то существующий сценарий реально упирается в диалог (уход в окне без обработчика — навигация отменяется автосбросом диалога и тест виснет/падает) — минимальная правка именно этого сценария по рецепту выше (дождаться истечения окна до перехода либо явно обработать диалог). Превентивно чужие файлы не трогаются.
- Граница (фиксированная, решение на IMPL без возврата к дизайну): флейм на нативном диалоге в двух прогонах CI подряд или падение локального полного прогона → файл сносится, vitest-пол задачи 3 объявляется достаточным; в отчёте задачи фиксируется снос и причина.
- **DoD:** файл зелёный в CI, либо снесён по границе с записью в отчёте; полный e2e-прогон зелёный — существующие сценарии со стражем совместимы (или минимально поправлены по факту столкновения).
- **Сценарии:** С3.
- **Required Docs:** спека §7.
