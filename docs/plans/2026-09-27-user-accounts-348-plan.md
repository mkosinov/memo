# План #348 — Управление учётками пользователей: телефон, сброс пароля по одноразовой ссылке, создание учётки без пароля

> Предусловие: спека и правки канона `docs/domain-rules/auth.md` уже в main (коммит 73399f2d, пуш 27.09) — план ссылается на существующие разделы.

## Goal
Админ управляет учётками сотрудников, не зная их паролей: учётка создаётся без пароля (только телефон), пароль владелец задаёт сам по одноразовой ссылке, которую система показывает админу для ручной передачи; той же ссылкой работает сброс пароля («Сбросить пароль» в блоке «Учётка»); телефон существующей учётки редактируется. Роль учётки редактируется уже сегодня (задача 263, D10) — не трогаем.

## Architecture
- **Бэкенд — новая вертикаль users** по правилу «у каждой содержательной таблицы своя вертикаль»: эндпоинты → сервис (`UserService`, существует) → сценарии (`usecases/user.py`, безельная конвенция). Публичная установка пароля — в auth (проверка + установка), оба маршрута вносятся в список анонимно доступных.
- **Новая таблица `password_setup_tokens`**: PK — SHA-256 дайджест токена (сырой токен живёт только в ссылке); `user_id` FK с каскадом и индексом; `expires_at` (UTC); `used_at`; частичный уникальный индекс «один живой токен на учётку» (`user_id` среди неиспользованных). Хэш пароля учётки становится nullable: NULL = пароль ещё не установлен.
- **Атомарность**: перевыпуск — «удалить все прежние токены пользователя + создать новый» в одной транзакции (гонку двух выдач гасит частичный уникальный индекс); установка — условное поглощение (обновляется только строка с `used_at IS NULL`), проверка активности учётки, сброс всей лестницы блокировок (три поля), отзыв всех сессий. Хэширование пароля — до транзакции записи.
- **Путь логина**: учётка без установленного пароля (NULL-хэш) не должна падать в 500 на аргон-проверке — нужен явный null-guard с обычным отказом и тайминг-паритетом.
- **Фронт**: блок «Учётка» в модалке сотрудника (телефон, статус ссылки, кнопка выдачи/сброса) + диалог ссылки + публичная страница `/password-setup` вне защищённой группы маршрутов. Ссылку собирает фронт: `window.location.origin` + `/password-setup#token=…` (токен — фрагментом, страница очищает его после чтения). Инвариант: админка и страница установки на одном origin; каналы доставки (задача 398) позже введут настройку публичного адреса.
- **Аудит**: выдача ссылки (автор — админ) и смена телефона журналируются; публичная установка — нет («нет автора → нет записи»). Подписи действий журнала живут на фронте — новый тип действия требует пункта в словаре подписей.

## Tech Stack
FastAPI + SQLAlchemy + alembic (backend), Next.js admin + react-query (frontend), packages/api-client (ручной, zod), pytest, Playwright (e2e).

Behavioral Delta — в спеке (раздел 3), здесь не дублируется. Нумерация сценариев S1–S8 — из спеки (раздел 2).

## Task 1 — Модель и миграция: таблица токенов + nullable хэш пароля
**Классификация:** standard
**Сценарии:** инфраструктура для S2, S3, S4, S8.
- Модель `PasswordSetupToken` (PK — дайджест; `user_id` FK каскад + индекс; `expires_at` UTC; `used_at` NULL; `created_at`), регистрация в реестре моделей.
- Частичный уникальный индекс: `user_id` по строкам с `used_at IS NULL`.
- Миграция alembic: создание таблицы + `users.password_hash` → nullable (существующие строки не трогаются — у всех есть хэш).
- Проверка: upgrade/downgrade симметричны; коллекция тестов зелёная.

**Required Docs:** спека §4; канон auth.md («Одноразовая ссылка установки пароля»).

## Task 2 — Сценарии токенов: выдача и установка
**Классификация:** standard
**Сценарии:** S3 (перевыпуск + сброс лестницы), S4 (недействительная ссылка), S8 (отзыв сессий).
**Зависимости:** Task 1.
- `issue_password_link`: отказ для деактивированной учётки (422 `ACCOUNT_DEACTIVATED`); в одной транзакции удаляет **все** прежние токены пользователя (включая использованные) и создаёт новый; срок жизни — параметр сценария, по умолчанию 24 часа; запись аудита «password_link_issued» (автор — админ).
- `set_password_by_link`: валидация парольной политики и хэширование — **до** транзакции; в транзакции: условное поглощение токена (обновилась 0 строк → отказ), проверка активности учётки, запись нового хэша, сброс лестницы (`failed_login_attempts = 0`, `lock_level = 0`, `locked_until = NULL`), отзыв всех сессий пользователя; записи аудита нет (публичный вызов).
- Тайминговая чёткость: все отказные пути (нет токена / истёк / использован / учётка неактивна) отвечают одинаково — 422 `PASSWORD_LINK_INVALID`, в дешёвых ветках фиктивная работа (образец — вход с несуществующим телефоном).
- Юнит-тесты: одноразовость (второй запрос с тем же токеном отклонён), деактивированная учётка, лестница с жёсткой блокировкой снимается полностью, сессии удалены, аудит выдачи есть / установки нет, срок жизни как параметр.

**Required Docs:** спека §4, §8; канон auth.md.

## Task 3 — Учётка без пароля + правка телефона (сервис и сценарий)
**Классификация:** standard
**Сценарии:** S1 (создание без пароля), S5 (правка телефона).
**Зависимости:** Task 1.
- Существующий метод сервиса `create_staff_account` (строительный блок составного создания сотрудника, НЕ новый сценарий) переводится на создание **без пароля** (`password_hash` NULL); явная проверка занятости телефона → доменная ошибка (сегодня путь составного создания ловит только глобальный обработчик нарушения уникальности БД); составной сценарий создания сотрудника сохраняет гарантию строки настроек по умолчанию (задача 319: `UserSettings` в той же транзакции — композиция не меняется); схема `CreateUserSection` — поле пароля удалено (breaking); служебный сценарий `create_user` (вызывается из `cli.py`, разработчик) не меняется — остаётся с паролем.
- Единая функция валидации телефона (используют создание и правка): существующее ограничение схемы — 20 символов после обрезки пробелов (`User.phone` — String(20), так же в схеме создания) — выносится в общую функцию с доменной ошибкой `PHONE_INVALID`; семантика уникальности «по точной строке» сохраняется, нормализация не вводится.
- `update_user_phone`: сценарий с записью аудита (обновление; телефон в снимке маскируется по канону аудита); сессии не отзываются.
- Тесты: создание учётки без пароля, дубликат телефона, валидация, аудит смены телефона.

**Required Docs:** спека §4, §5; канон auth.md (User lifecycle).

## Task 5 — Публичные эндпоинты установки + null-guard логина
**Классификация:** standard
**Сценарии:** S2 (установка по ссылке), S4 (недействительная ссылка), S6 (вход без пароля — серверная сторона).
**Зависимости:** Task 2.
- auth-роутер: `POST /api/v1/auth/password-setup/validate` (проверка токена: существует / не истёк / не использован / учётка активна) и `POST /api/v1/auth/password-setup` → 204.
- Обе записи в списке анонимно доступных маршрутов (default-deny; контрактный тест держит список точным).
- Попытки с недействительным токеном на **обоих** публичных маршрутах считаются счётчиком неудач по IP (расширение существующих счётчиков входа; окно 15 минут — существующее значение счётчиков, не новое).
- **Null-guard логина**: учётка без установленного пароля (NULL-хэш) на пути логина → фиктивная проверка (тайминговая чёткость как для несуществующего телефона), обычный отказ «неверные учётные данные» (422 `AUTH_INVALID_CREDENTIALS`); лестницу учётки не кормить (перебираемого секрета нет), счётчики неудач по IP/телефону — как в ветке несуществующего телефона.
- Интеграционные тесты: validate 200/422; установка — полный путь, повторное использование токена, просрочка (срок подменяется параметром), неактивная учётка, отказ политики (422 `PASSWORD_POLICY`), форма кодов ошибок; логин учёткой без пароля — отказ без 500 и без изменения лестницы.

**Required Docs:** спека §4 (вход без пароля), §5, §7; канон auth.md (Public Access, Sessions).

**Сценарии:** S1 (создание), S3 (сброс), S5 (правка телефона), S6 (состояния).
**Зависимости:** Task 3, Task 4, Task 6.

## Task 8 — Фронт: публичная страница установки пароля
**Классификация:** standard
**Сценарии:** S2 (установка), S4 (недействительная ссылка).
**Зависимости:** Task 5.
- Маршрут `/password-setup` вне защищённой группы маршрутов (как страница входа; клиентский гард её не трогает), переиспользование компонентов и стиля формы входа.
- Логика: токен читается из фрагмента адреса (`#token=`), фрагмент очищается после чтения; при открытии — проверка (`validatePasswordSetup`) и сразу выбор экрана: форма или «Ссылка недействительна или истекла»; форма «Придумайте пароль» + подтверждение, inline-ошибка политики (одно сообщение, 422 `PASSWORD_POLICY`); успех → переход на отдельный публичный адрес `/password-setup/success` («Пароль установлен, войдите с телефоном и новым паролем», кнопка «Войти») — обновление страницы не повторяет запрос.
- api-client: `validatePasswordSetup`, `passwordSetup` (+ тесты в `endpoints.test.ts`).
- Юнит-тесты страницы (три экрана, очистка фрагмента, inline-ошибка).

**Required Docs:** спека §5, §6; design-system (формы).
