# План: метка visits в событийной сетке удалений (#375)

- **Спека:** `docs/specs/2026-10-10-visits-event-mark-design.md` — единственный источник поведения; план не пересказывает её, задачи ссылаются на секции.
- **Goal:** после каскадного удаления клиента и одиночного удаления посетителя событийный пакет называет стёртые посещения меткой `visits`; открытая таблица «Записи» и карточка клиента обновляются сами, серверные сетки зафиксированы тестами.
- **Architecture:** один слой правок — сервер: снятие подавления метки в двух существующих точках (сценарий `delete_client` фаза 7 и `VisitorService.delete`), оба переходят на значение по умолчанию готового параметра `mark_visits`; тексты подавления (докстринги, инлайн-комментарий) обновляются в тех же файлах. Юнит-слой: инверсия зафиксированных сеток + новый emit-тест одиночного удаления. E2E: новая спека с двумя страницами (удаление в одной — наблюдение обновления в другой). Фронт не меняется.
- **Tech Stack:** Python/FastAPI/SQLAlchemy (событийный накопитель `mark_changed`), pytest, Playwright (контекст из двух страниц).

## Task 1 — Снятие подавления метки и фиксации сетки

- **Классификация:** standard
- **Файлы:** `backend/src/usecases/clients.py` (фаза 7: снять `mark_visits=False`; инлайн-комментарий подавления и докстринг сценария), `backend/src/services/visitor.py` (`VisitorService.delete`: снять подавление; докстринг «NO visits mark»), `backend/tests/test_events_emit.py` (сетка resolve-удаления клиента пополняется `visits`; NB-комментарий паритета #327 §8 снимается со ссылкой на #375; новый emit-тест одиночного удаления с сеткой `{visitors, visits}`), `backend/tests/usecases/test_clients_delete.py` (обе сетки пополняются `visits`; `test_grid_no_visits_mark` инвертируется и переименовывается — метка присутствует).
- **Работа:** обе точки используют значение по умолчанию параметра (явный аргумент удаляется); семантика «mark by dispatch fact» — метка ставится и при нуле строк (спека §Контекст, свойства пакета). Параметр `mark_visits` и его контракт остаются в коде: существующий тест подавления у пакетного метода (`backend/tests/services/test_visit_service.py`, `test_delete_visits_by_visitor_mark_false_suppresses_mark`) НЕ инвертируется и остаётся зелёным — он проверяет сам параметр, а не путь удаления. Никаких правок resolve-маршрута удаления посетителя и сеток других сценариев (спека §Границы).
- **Юнит-тесты** (спека §Тесты): execute-сетка полного каскада `{clients, records, photos, visitors, client_tags, visits}`; сетка «чистого» клиента — та же с `visits`; переименованный тест утверждает `visits` в сетке; новый emit-тест одиночного удаления — `{visitors, visits}`.
- **Required Docs:** `docs/domain-rules/visits.md`, `docs/domain-rules/clients.md`, `docs/domain-rules/deletion.md`.
- **Соответствие сценариям:** US-3 (сетка execute-пакета), контрактная основа US-1/US-2.

## Task 2 — E2E-спека обновления экранов после удаления

- **Классификация:** standard
- **Файлы:** новый `frontend/admin/e2e/visitor-delete-invalidation.spec.ts`.
- **Работа:** три проверки из спеки §User Scenarios, каждая на двух страницах одного контекста (удаление в одной, наблюдение в другой; шаги удаления и локаторы окна подтверждения — действующие из `visitors-deferred-delete.spec.ts`, диалог с чекбоксом; ожидание изменений — `waitFor`/`expect` без снов): US-1 — удаление посетителя из карточки клиента, открытая таблица «Записи» обновляется (посещение исчезает, места пересчитаны); US-2 — удаление в первой странице, открытая в другой карточка клиента на вкладке записей обновляется без перезагрузки; US-3 — каскадное удаление клиента (окно подтверждения, шаги из действующих e2e удалений клиента), таблица «Записи» обновляется — проверка-охрана, зелёная и до правки Task 1.
- **Required Docs:** спека §User Scenarios US-1–US-3; `docs/domain-rules/visits.md` (карта инвалидаций: метка `visits` → семейство записей).
- **DoD:** E2E test for scenario US-1, US-2, US-3 passes (RED-GREEN-REFACTOR).
- **Соответствие сценариям:** US-1, US-2, US-3.

## Task 3 — Регрессионный прогон семейства удалений

- **Классификация:** trivial
- **Работа:** без правок кода — юнит-прогон событийных тестов (`test_events_emit.py`, `test_clients_delete.py`, `backend/tests/services/test_visit_service.py`) и e2e семейства удалений (`visitors-deferred-delete.spec.ts`, спекы каскада клиента из `clients`-семейства) — ожидается зелёное; при регрессии — разбор против спеки, в границы задачи правки не входят (возврат на дизайн).
- **Required Docs:** спека §Границы (что не меняется), §Тесты (охрана resolve-пути).
- **Соответствие сценариям:** охрана всех трёх.
