# План: проекция ответа PATCH посещения в кэш записи (#359)

- **Спека:** `docs/specs/2026-10-09-visits-patch-cache-projection-359-design.md` (ревизия 2) — единственный источник поведения; план не пересказывает её, задачи ссылаются на секции.
- **Goal:** конкурентные правки посещения (назначение клиента, тариф/цена, статус) сходятся в кэше записи сразу и без инвалидации: ответ применяется проекцией по полям запроса, по полю побеждает последний выпущенный запрос.
- **Architecture:** два слоя правок — (1) `frontend/admin/lib/cache/recordCacheSync.ts`: helper частичной правки посещения поверх действующего обходчика кэша; (2) `frontend/admin/hooks/useRecordMutations.ts`: счётчик правок по посещению и защита применения ответа, смена статуса добавляет проекцию к действующей инвалидации. Проверки: расширение действующих юнит-тестов + новая e2e-спека с управляемым порядком ответов (`page.route`). Сервер и контракты не меняются.
- **Tech Stack:** TypeScript/React (React Query), vitest, Playwright (route-перехват).

## Task 1 — Helper проекции в recordCacheSync

- **Классификация:** small
- **Файлы:** `frontend/admin/lib/cache/recordCacheSync.ts` (новый helper), `frontend/admin/__tests__/recordCacheSync.test.ts` (расширение).
- **Работа:** helper частичной правки посещения поверх действующего обходчика (канонический ключ записи + зеркала списков; нового реестра ключей не заводить). Семантика — спека §Технические изменения п.1 (а)–(д): только перечисленные поля; `updated_at` — неявное всегда-применяемое поле; посещения нет в кэше — no-op без вставки; иммутабельная сборка объектов (новые ссылки); список полей — по ключам сериализованного тела запроса.
- **Юнит-тесты** (спека п.4): проекция перечисленных полей; null-значение поля запроса очищает поле кэша; отсутствующее посещение — no-op; зеркала списков обновлены; ссылки на объекты новые.
- **Required Docs:** спека §Технические изменения п.1, п.4.
- **Соответствие сценариям:** механизм под US-1..US-3.

## Task 2 — Счётчик правок и защита применения в useRecordMutations

- **Классификация:** standard (семантика конкуренции + две мутации + статус-путь)
- **Файлы:** `frontend/admin/hooks/useRecordMutations.ts`, `frontend/admin/__tests__/useRecordMutations.test.ts` (расширение).
- **Работа:** по каждому посещению монотонный счётчик правок; запрос фиксирует номер и состав полей; ответ правки вызывает helper из Task 1 только с полями, не перекрытыми более поздним запросом (спека §Технические изменения п.2). Мутация `patchVisit` переключается с цельной перезаписи на helper; `updateVisitStatus` применяет своё поле (`status`) проекцией поверх действующей инвалидации (инвалидация остаётся ради статуса родительской записи). Путь ошибок не меняется: проекция только на успехе.
- **Юнит-тесты:** ответ, перекрытый более поздним запросом того же поля, не пишется; поздний ответ раннего запроса другого поля своё поле пишет; статус-мутация пишет поле и сохраняет инвалидацию.
- **Required Docs:** спека §Технические изменения п.2, §Допущения и риски (остаточные окна).
- **Соответствие сценариям:** US-2, US-3 (защита одного поля), US-1 (паритет полей).

## Task 3 — E2E-спека управляемого порядка ответов

- **Классификация:** standard
- **Файлы:** новый `frontend/admin/e2e/visits-patch-consistency.spec.ts`.
- **Работа:** три проверки из спеки §User Scenarios с перехватом PATCH посещений (`page.route`, асинхронный хендлер с паузой ≥ 0.5 с перед пропуском выбранного ответа; ожидания через waitFor): US-1 — удержание ответа `visitor_id` при свободном ответе тарифа/цены, сверка API (`visitor_id` + `tariff_id`/`price` вместе — единственная проверка со сверкой API, в US-2/US-3 её нет); US-2 — удержание ответа статуса, отпускание последним (его инвалидация-рефетч читает состояние после обоих коммитов), проверка бейджа статуса записи; US-3 — удержание первого ценового ответа при свободном втором, ассерты строки и итога записи (итог показывает вторую цену).
- **Required Docs:** спека §User Scenarios (вводная часть про детерминированный порядок и прецеденты перехвата).
- **Соответствие сценариям:** US-1, US-2, US-3.

## Task 4 — Регрессии превращения и undo

- **Классификация:** trivial
- **Работа:** прогон действующих e2e превращения анонимного посещения и undo удаления посещения — без правок кода, ожидается зелёное; при регрессии — разбор против спеки (в границы задачи правки не входят, возврат на дизайн).
- **Required Docs:** спека §User Scenarios US-4, US-5; §Границы (что не меняется).
- **Соответствие сценариям:** US-4, US-5.
