# План: инфраструктура доставки оповещений — часть 2 (#483)

**Goal:** построить транспортную инфраструктуру подсистемы оповещений — адаптер очереди на Redis Streams, настройка `REDIS_URL`, скелет воркера, Redis в dev/e2e-стеках и включённый тестовый контур; по умолчанию поведение системы не меняется (семейская US-7: стандартный прогон без Redis).

**Architecture:** часть 2 из 5 семейства #476 (семейная спека рев.4, ADR 008–013). Адаптер `RedisQueue` реализует порт `NotifyQueue` из части 1 поверх синхронного redis-py: три стрима `notify:tasks/statuses/inbound`, группы `worker`/`dispatcher`, конверт `_qid`, возврат зависших через `XAUTOCLAIM`. Диспетчер части 1 получает выбор адаптера с fail-fast-гейтами; воркер-скелет — вторая процесс-точка входа без потребления. Поведенческая дельта — в спеке `docs/specs/2026-10-21-notify-infra-483-design.md` §5.

**Tech Stack:** Python 3.12+ (uv, pydantic-settings), redis-py (синхронный клиент), pytest (маркер `redis`), Playwright (включённый e2e), GitHub Actions (сервис-контейнер Redis), bash (dev.sh, e2e-shard-start.sh).

Спека: `docs/specs/2026-10-21-notify-infra-483-design.md` (рев.3). Ссылки § — на её разделы.

## Task 3: Адаптер RedisQueue и маркированный контур его тестов

### Classification: large

Модуль `backend/src/notify/redis_queue.py`, класс `RedisQueue(NotifyQueue)`: три стрима с `XADD ... MAXLEN ~ 10000`; группы создаются процессом-потребителем при старте (`XGROUP CREATE ... MKSTREAM`, подавляется только `BUSYGROUP`) — часть 2 создаёт только `dispatcher`-группы статусных стримов, группа `worker` для `notify:tasks` — часть 3; `enqueue_task` пишет в стрим без группы (стрим создаётся записью); `claim_statuses`/`claim_inbound` — неблокирующий `XREADGROUP` со знаком `>` (чтение `0` — слив собственного PEL — запрещено анти-паттерном спеки), конверт `_qid`; `ack_*` — `XACK` по `_qid`; `reclaim_hanging` — `XAUTOCLAIM` (курсор до `0-0`, `min-idle-time` ≥ `NOTIFY_REENQUEUE_AFTER`, явный `COUNT`, терминальная обработка удалённых подрезкой записей третьего элемента ответа); продюсерские `publish_status`/`publish_inbound` вне протокола; имя потребителя уникально на живой процесс, `XGROUP DELCONSUMER` при штатной остановке; пул с явным `max_connections` (≈10) и `socket_timeout` больше любого BLOCK-параметра чтения (диспетчер читает неблокирующе; запас — требование воркеру части 3); retry-политика без тихих ретраев (redis-py ≥6 включает их по умолчанию — отключить явно). Свой тип транспортного исключения (`NotifyTransportError`) — им диспетчер отличает отказ транспорта от ошибки сценария (Task 4). Допущение «один диспетчер и один воркер на инстанс Redis» фиксируется докстрином модуля.

Докстрин порта `backend/src/notify/queue.py` обновляется: контракт `InboundEvent` — фиксированный формат и правила спеки §3.2 (убрать «payload contract is fixed in part 2»), упоминания arq заменить на транспорт ADR 013, описать конверт `_qid`; контракт входящих в коде — докстрин порта (типизированную схему не заводим, она прибудет с первым продюсером, часть 4).

Контур тестов: маркер `redis` в `backend/pyproject.toml`; страж — декоратор `skipif` по отсутствию `REDIS_URL`; файл(ы) `backend/tests/test_notify_redis_*.py`: постановка и чтение задачи, надёжное чтение (claim/ack/reclaim), дубль ack безвреден, fail-fast-гейты запуска (пустой URL, недоступный Redis → PING-отказ, код 2), громкость отказов (транспортное исключение не глушится), каждый тест в выделенном индексе БД (или уникальный префикс) с очисткой. Модули `redis_queue.py` и `worker.py` — в `[tool.coverage.run] omit` с указателем «измеряется контуром notify-tests» (образец — `src/seed/*`), чтобы порог 80% стандартной джобы не сдвигался.

- спека §3.1, §3.2, §3.6; порт `backend/src/notify/queue.py` (докстрин — правила конверта и надёжного чтения); ADR 013

## Task 4: Интеграция диспетчера

### Classification: standard

`backend/src/notify/dispatcher.py`: удалить заглушку FakeQueue из `main()`; выбор адаптера — `REDIS_URL` непуст → `RedisQueue`; включённый флаг + пустой URL → выход с кодом 2 и стабильным сообщением «notify: transport not configured» (без значения URL); заданный, но недоступный Redis → PING при старте, отказ громко, код 2. Код выхода проводится явно: `main()` поднимает `SystemExit(2)`, блок `__main__` не глотает его (сегодня `main()` возвращает None и код игнорируется). Обёртки `asyncio.to_thread` в точках вызова очереди; отказ соединения не роняет циклы — очередной тик повторяет попытку, отказ остаётся громким. Транспортное исключение в точке постановки ловится по типу `NotifyTransportError` (не любой исключительный случай): `attempts` события не растёт (громкий журнал, задача остаётся «в очереди»), ошибки сценария продолжают считать попытки как сегодня; неудачная постановка увеличивает `reenqueues` — по `REENQUEUE_CAP` задача завершается «не доставлено» существующим путём потолка. Гигиена логов: класс и сообщение исключения + идентификаторы, без тел сообщений, адреса маскируются.

### Required Docs

- спека §3.1 (выбор адаптера, громкость отказов, сбой постановки); семейная §3.3

### DoD

- юнит-тесты гейтов (часть S3: пустой URL и недоступный Redis → код 2, стабильное сообщение); тест «транспортный сбой не сжигает attempts» (различение `NotifyTransportError` от ошибки сценария); тест «неудачная постановка растит reenqueues, cap завершает failed»; существующие тесты части 1 зелёные (путь с FakeQueue через инъекцию очереди не меняется).

## Task 8: Включённый режим e2e-стека и сценарий S1

### Classification: large

`scripts/e2e-shard-start.sh`: режим `NOTIFY_E2E_ENABLED=1` — своя пара портов вне диапазона шардов (по умолчанию 8005/3006, значения параметрами окружения). Контракт скрипта соблюдается явно: допустимое значение идентификатора стека расширяется с `SHARD_ID ∈ {1..4}` на включённый режим (свой тег вместо номера шарда → своя порт-пара и свой `SHARD_RUN_TAG`/lease, без коллизий с шардами), `TEST_DB_PATH` включённого режима содержит `test_memo` (проверка пути не срабатывает), обязательные переменные (`BACKEND_URL`, `NEXT_PUBLIC_API_URL` и пр.) выставлены на свою пару портов. `REDIS_URL` только из явно переданного значения (локально без явного — дочерний `redis-server`), диспетчер дочерним процессом, trap-очистка расширена на новые дочерние процессы; режим по умолчанию ничего не меняет. Сухой прогон скрипта (`scripts/e2e-shard-start.dryrun.test.sh`, джоба `shard-script-checks`) пополняется случаем включённого режима — правка стека покрыта автоматической проверкой по конвенции репозитория.

Playwright-сценарий S1 (включённый стек): создание записи с чекбоксом «отправлять оповещения» на будущего клиента проходит штатно, UI записей не изменился; после него маркированная проверка очереди — в стриме ≥ 1 задача, payload семейской §4.2 корректен. Предположение зафиксировано: чекбокс «отправлять оповещения» в форме записи существует и подключён флагом части 1 (семейная §3.8) — фронтенд-правок в части 2 нет.

### Required Docs

- спека §3.5, §4 S1; канон e2e (`docs/tests/` — паттерны Playwright); `scripts/e2e-shard-start.sh` (контракт SHARD_ID, lease, trap)
