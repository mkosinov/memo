# План #499: клиентские учётки и реальное бронирование из веба — срез «вход + форма»

- **Issue:** #499
- **Спека:** `docs/specs/2026-10-20-web-client-auth-booking-design.md` (рев.2, Gate B OK 2026-10-21, main `17d0ff9c`)
- **Дата плана:** 2026-10-21

## Goal

Клиент подтверждает телефон кодом, получает клиентскую сессию и бронирует из веб-формы по реальным тарифам услуги: `POST /api/v1/my/records` со строгой схемой, ценой из тарифа на сервере и владельцем из сессии. Чтение кабинета — вне среза (#513).

## Architecture

Backend расширяет существующие механизмы, ничего параллельного не строится: сессии — та же таблица с отдельным именем cookie и отдельной зависимостью резолва; создание записи — существующий сценарий с двумя отличиями (владелец из сессии, цена сервером); код подтверждения — новая таблица `otp_codes` + транспорт-интерфейс fail-closed. Веб переходит с мок-формы на реальные данные через `packages/api-client`; точка входа формы — оверлей карточки активности на главной, мок-страница `/booking` и мёртвый самодельный API-путь удаляются.

## Tech Stack

Backend: Python, FastAPI, SQLAlchemy + миграции, pytest (контрактные тесты `backend/tests/`). Фронт: TypeScript, Next.js App Router (`frontend/web`), react-query, vitest (`frontend/web`). Общий контракт: `packages/api-client` (zod-схемы + функции). Веб-сценарии закрываются парой pytest + vitest — браузерного e2e-харнеса для `frontend/web` в репозитории нет (спека §6).

## Решения уровня плана (не из спеки — вынесены ревьюером плана)

- Задача 8: вошедшему клиенту телефон в форме предзаполнен и readonly из сессии (контракт спеки: `phone` обязателен в схеме; UX-деталь формы).
- Задача 9: вместе с мок-страницей `/booking` удаляется мёртвый самодельный путь `frontend/web/app/lib/api/records.ts` (не вызывается UI — проверено скаутом; спека §7 требует только `/booking`).

## Task 2: Код подтверждения телефона: хранение и лимиты

### Classification: standard

### Required Docs

- `docs/domain-rules/auth.md` — «Клиентская аутентификация (#499)», «Sessions» (паттерн счётчиков)
- Спека §4.1

### Что делаем

- Таблица `otp_codes` (`phone`, `code_hash`, `expires_at`, `created_at`) + миграция; один код на телефон, ротация отправкой.
- Код 6 цифр, TTL 5 минут; `code_hash` = HMAC-SHA-256 с серверным перцем из настроек окружения (вне БД), сравнение за постоянное время.
- Счётчик неудачных вводов — 5 за 15 минут на телефон, отдельно от строки кода, ротацией не сбрасывается; просроченные строки удаляются при обращении к телефону.
- Лимиты отправки в существующем in-memory сторе, одно окно 15 минут: 5/телефон, 20/IP, 5 разных номеров/IP; отказы verify считаются в IP-счётчик.

### DoD

- pytest: TTL/ротация/поглощение/лимиты по спеке §4.1 (сценарий US-4, серверная часть; RED-GREEN-REFACTOR).

## Task 3: OTP-эндпоинты и транспорт

### Classification: large

**Порядок:** после задачи 4 (эндпоинт `verify` выдаёт сессию механикой и cookie-именем из задачи 4).

### Required Docs

- `docs/domain-rules/auth.md` — «Клиентская аутентификация (#499)», «Public Access», «CSRF Posture»
- `docs/domain-rules/clients.md` — поиск клиента по точному телефону
- Спека §4.2, §3 (создание учётки)

### Что делаем

- `POST /api/v1/auth/otp/request` `{phone}`: доменная валидация телефона (422 `PHONE_INVALID`); всегда 202 на валидный номер; для телефона сотрудника код молча не генерируется и не отправляется.
- `POST /api/v1/auth/otp/verify` `{phone, code}`: проверка HMAC+срок+попытки с атомарным поглощением кода; находится/создаётся клиентская учётка (`user(role=client, phone)` + карточка «найди-или-создай по точному телефону» — только активные карточки, при дублях первая активная по стабильной сортировке; `UserSettings` в той же транзакции, `phone_is_confirmed=true`); конфликт уникальности телефона → перечитать и продолжить (идемпотентность). **Успех verify выдаёт клиентскую сессию** — `Set-Cookie memo_client_session` (механика задачи 4).
- Публичность: обе точки явно в `PUBLIC_ROUTES` (точные пары); контракт-тест allowlist остаётся арбитром.
- Origin-сверка против CORS-списка при наличии заголовка (несовпадение → 403) на обеих точках.
- Транспорт-интерфейс fail-closed: без настроенного транспорта — 503 `NOTIFY_TRANSPORT_UNAVAILABLE`; dev-транспорт и `dev_code` — только при точном `ENV == "development"`, в лог — маскированная запись без сырого кода.

### DoD

- pytest: контракт обеих точек по спеке §4.2 — 202-всегда, молчание для сотрудников, поглощение кода, идемпотентный verify, `Set-Cookie` клиентской сессии на успехе, 503 без транспорта, dev_code только в development, единые отказные сообщения и тайминги на шагах кода (сценарий US-4; RED-GREEN-REFACTOR).

## Task 4: Клиентская сессия, `/my/client`, общий выход

### Classification: small

**Порядок:** до задачи 3 — её эндпоинт `verify` выдаёт сессию cookie-именем и резолвером из этой задачи.

### Required Docs

- `docs/domain-rules/auth.md` — «Sessions», «Клиентская аутентификация (#499)»
- Спека §4.3

### Что делаем

- Cookie `memo_client_session` (те же атрибуты, что у `memo_session`); зависимость `require_client_session`: только эта cookie, `role=client`, активная учётка; staff-резолвер не меняется — перекрёстное предъявление даёт 401.
- `GET /api/v1/my/client` → `{phone, name}` (клиентская сессия).
- `POST /api/v1/auth/logout` расширяется: удаляет предъявленную сессию любого вида, идемпотентен.

### DoD

- pytest: резолв клиентской сессии, 401 перекрёстно и без сессии, `/my/client`, выход обеих видов сессий (сценарий US-5, серверная часть; RED-GREEN-REFACTOR).
- pytest: инвариант спеки §3 — архивация карточки клиента не разрывает связь и не блокирует вход/бронирование, владелец определяется по `client_id` учётки.

## Task 5: Бронирование `POST /api/v1/my/records`

### Classification: large

### Required Docs

- `docs/domain-rules/auth.md` — «Клиентская аутентификация (#499)», «CSRF Posture»
- `docs/domain-rules/records.md` — «Business Logic → Backend» (включая session-based ветку), «VisitItem»
- Спека §5

### Что делаем

- Схема `MyRecordCreate` (`extra="forbid"`): `activity_id`, `phone` (доменная валидация, 422 `PHONE_INVALID`), `comment?`, `visits` 1..20 (`name?`/`age?`/`tariff_id?`, границы как у `VisitItem`); из провода нет `client_id`/`visitor_id`/`price`/`custom_price`/`notify`/`status`.
- Цена сервером: `tariff_id` → цена тарифа, обязателен (422 `TARIFF_REQUIRED`), если у услуги активности есть тарифы; без тарифов — 0 (422 `TARIFF_NOT_FOUND` на чужой тариф); тарифы услуги загружаются одним запросом.
- Владелец из сессии (`require_client_session`); наследуются проверки существующего сценария: 404 активность, 409 вместимость.
- Защита мутации: `Sec-Fetch-Site`-линия + Origin-сверка; CORS: точные origin с credentials, `*` запрещён, origin веб-приложения добавлен.
- Анти-спам: 20 записей и 40 визитов за 15 минут на учётку → 429.
- Ответ 201 `MyRecordResponse` `{id, activity_id, start, comment, visits[{name, age, tariff_id, price}]}`.

### DoD

- pytest: полный контракт по спеке §5 — счастливый путь US-1, без-тарифов случай US-2, отказные коды US-3/US-6 (401/404/409/422 всех видов/429; RED-GREEN-REFACTOR).

## Task 7: Веб — реальные тарифы в форме бронирования

### Classification: large

### Required Docs

- Спека §2 (веб-часть), §7 (дельта), §8 (визуальные проверки)
- `docs/tests_workflow.md` — паттерны vitest веба

### Что делаем

- Тарифы услуги доходят до модели экрана активности (маппер расписания) и в оверлей бронирования.
- Оверлей: счётчик мест на каждый тариф (`data-testid="tariff-counter-{id}"`, цена рядом; компонент `Counter`); услуга без тарифов — один счётчик + «Стоимость уточняется» (`data-testid="booking-price-hint"`).
- Кнопка «Указать имена посетителей» → таблица (`data-testid="visitors-names-table"`): строка на выбранное место, колонки имя (ввод) / возраст (ввод) / тариф (read-only); незаполненные имена уходят анонимными визитами.
- Селектор канала остаётся видимым и нерабочим (не трогаем).
- Состояние загрузки/ошибки тарифов в оверлее.

### DoD

- vitest: рендер тарифов/без-тарифов случая/таблицы имён по спеке §8 (сценарии US-1, US-2 — витest-часть; RED-GREEN-REFACTOR).

## Task 8: Веб — вход при отправке и создание записи

### Classification: standard

### Required Docs

- Спека §4.2 (поведение шага кода), §5 (ответ/ошибки), §8
- `docs/tests_workflow.md`

### Что делаем

- Отправка без клиентской сессии → шаг «подтвердите телефон»: телефон из формы, «Отправить код» → ввод кода (`data-testid="otp-code-input"`) → «Подтвердить» → автоматическая повторная отправка записи; ошибки шага — в самом шаге, при 503 — «Вход временно недоступен».
