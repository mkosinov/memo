# План: вход по звонку (sms.ru callcheck) — метод авторизации (#593)

Спека: `docs/specs/2026-11-11-auth-callcheck-design.md` (рев.7). Сценарии US-1…US-7 закрыты задачами ниже; DoD задач несёт их тесты. Дом-правило уже в main вместе со спекой (`docs/domain-rules/auth.md`, раздел «Методы авторизации клиента»).

## Goal

Анонимный клиент входит, подтверждая телефон звонком на бесплатный номер (sms.ru callcheck), выбирая способ входа из доступных (пикер; SMS-метод появляется, когда #586+#587 включены). После подтверждения — клиентская сессия общим с SMS-кодом финализатором; запись и кабинет работают существующими путями. Записи и админка не меняются.

## Architecture

Реестр методов (`GET /auth/methods`, доступность = резолвер транспорта вернул объект) → пикер единого экрана авторизации (форма записи и кабинет). Метод `call`: `initiate` (валидация 422 → стафф-пропуск → гейты 5/20/5 + глобальный потолок → `callcheck/add` → строка `auth_calls` (PK — телефон, последняя выигрывает) + журнал) → экран звонка (`tel:+7…`, таймер, опрос 4 с) → `status` (хэшированный одноразовый хэндл; маппинг кодов; статус провайдера раньше локальной экспирации окна 5 минут; атомарное погашение хэндла + финализация одной транзакцией; параллельные опросы — ровно одна сессия). Провайдер-специка целиком в `SmsRuClient` за `CallcheckProvider`; httpx per-call. Дев-транспорт + дев-имитация звонка (двойной гейт) для разработки и e2e.

## Tech Stack

Python 3.12 / SQLAlchemy async + alembic / httpx (зависимость объявлена — первый продовый вызов) / React + react-query (`refetchInterval`) / Playwright web-e2e на дев-транспорте.

## Task 1: Провайдер-клиент sms.ru + реестр методов + конфиг и валидатор

### Classification: standard

- `backend/src/auth/callcheck_provider.py` — Protocol `CallcheckProvider`: `create(phone, ip) -> CheckCreated(check_id, call_phone, window_seconds)`, `status(check_id) -> waiting | confirmed | expired`; исключение провайдера не несёт тела запроса и ключа.
- `backend/src/auth/smsru_client.py` — `SmsRuClient`: база `https://sms.ru/callcheck/`, `api_id` (`SecretStr`), `json=1`; конвертация `+7…` → `7…`; окно — константа 300 с (в ответе `add` поля времени нет); парсинг терпим к `call_phone`/`call_number` и к коду ошибки строкой/числом; любая неудача (HTTP ≠ 2xx, код ≠ 100, таймаут, сеть) → исключение; httpx `AsyncClient` per-call с таймаутом (паттерн #586).
- Wiring по образцу `otp_transport.py`: `get_callcheck_transport()` — `""`/unknown → None, `dev` → только `ENV=development`, `smsru` → `SmsRuClient`; валидатор настроек (fail-fast): `smsru` + пустой `SMSRU_CALLCHECK_API_KEY` → ошибка старта; `dev` при `ENV=production` → ошибка старта.
- `GET /api/v1/auth/methods` (публичный): `[{ "id": "sms_otp" | "call", "available": bool }]` — `available` = резолвер вернул объект (`sms_otp` — `get_otp_transport()`, `call` — `get_callcheck_transport()`), не «переменная непуста».

### Required Docs

`docs/domain-rules/auth.md` (раздел «Методы авторизации клиента»), спека §Реестр, §Клиент провайдера, §Конфигурация; `docs/research/2026-11-11-smsru-callcheck-api.md`.

### DoD

- Контракт `SmsRuClient` на httpx `MockTransport`: тело запроса (`api_id`, `phone` без `+`, `ip`, `json=1`), обе формы ответа (`call_phone`/`call_number`, код строкой/числом), исходы 100/202/400/401/402, HTTP ≠ 2xx, таймаут → корректные типы; текст ошибки не содержит тело запроса и ключ; окно — константа, не поле ответа.
- Матрица wiring `CALLCHECK_TRANSPORT` × `ENV` и матрица реестра `OTP_TRANSPORT` × `CALLCHECK_TRANSPORT` × `ENV` — включая появление/скрытие `sms_otp` при включении транспорта #586; тесты валидатора (`smsru`+пустой ключ; `dev`+production).
- US-3 (бэкенд-половина): реестр честно отражает выключенные методы (`dev` вне development и unknown → `available:false`); `smsru` реально доходит до стаба клиента, а не отвечает вхолостую.

## Task 2: Хранение — `auth_calls` + `auth_call_attempts`

### Classification: standard

- Модели в домене auth (рядом с `otp_codes`): `auth_calls` — `phone` PK, `provider_check_id`, `call_phone`, `handle_hash`, `status` (`pending` | `consumed` | `expired`), `created_at`; TTL-очистка по образцу `otp_codes` (окно + запас). `auth_call_attempts` — дописываемый журнал: `id` uuid, `phone`, `ip_hash`, `provider_check_id`, `outcome` (`created` | `confirmed` | `expired`), `created_at`, `checked_at` nullable. Без ключа, хэндлов и тел запросов.
- Alembic-ревизия на обе таблицы; сырой хэндл в БД не попадает (хэшируется при записи).

### Required Docs

`docs/domain-rules/auth.md` (раздел «Методы авторизации клиента»), спека §Хранение.

### DoD

- Миграции — roundtrip-тест.
- Замещение: после нового initiate по тому же телефону старая строка заменена (PK), **старый хэндл больше не валиден** (404 на статус-запрос).
- TTL-purge: истёкшие строки удаляются при касании по образцу `otp_codes`.

## Task 3: `POST /auth/call/initiate` — валидация, гейты, вызов провайдера, журнал

### Classification: standard

- Роут (публичный, `verify_origin`): телефон канонический `+7XXXXXXXXXX`, иначе 422 до гейтов и провайдера; **стафф-номера — молчаливый 202 без проверки** (тот же предикат, что у `otp/request`; оракула перечисления нет).
- Гейты по образцу `otp_send_gate` (in-memory, окно 15 минут): 5/телефон, 20/IP, 5 разных номеров/IP; **регистрация лимитов только на успех провайдера** (отклонение от порядка `otp_service.issue` — сознательное, спека §Гейты). **Глобальный потолок** — константа 100 initiate/15 мин на процесс, при превышении fail-closed 503.
- Порядок: валидация → стафф-пропуск → гейты → `callcheck/add` → при успехе одна транзакция: upsert `auth_calls` (новая строка заменяет старую; хэш хэндла) + строка журнала `created`. Ответ 202: `handle` (uuid4-hex, только в ответе), `call: { phone: +7…, pretty, expires_at }` — номер клиенту строго с «+» (без плюса часть операторов не пропускает, особенно из-за рубежа).
- IP: из ASGI-клиента, валидация формата, передача провайдеру (роуминг-подмена 8-800); доверие proxy-headers — инвариант развёртывания.
- Любая неудача провайдера → 503 `NOTIFICATION_TRANSPORT_UNAVAILABLE`; строка не пишется, лимит телефона не расходуется; журнал `ip_hash` пишется только на успех.

### Required Docs

`docs/domain-rules/auth.md`, спека §Эндпоинты (initiate), §Гейты.

### DoD

- Integration (TestClient + стаб провайдера), US-6: 503 при выключенном транспорте; 429 по всем трём правилам гейтов; глобальный потолок → 503.
- 422 на неканоническом телефоне (до провайдера — стаб не вызывался); стафф-номер — неотличимый 202, проверка не создана (паритет с OTP-путём, тест на том же предикате).
- Ответ: `phone` начинается с `+7`; `handle` в ответе, в БД — только хэш; `expires_at` = момент add + константа.

## Task 4: `POST /auth/call/status` + общий финализатор + дев-маршрут

### Classification: standard

- Хелпер финализации выделяется из OTP-верификации (кука сегодня ставится инлайн в роутере `otp/verify`): find-or-create клиента по телефону, `phone_is_confirmed=true`, установка `memo_client_session`; **без ротации** — предъявленная сессия не аннулируется, параллельные живут (решение владельца). Используется `otp/verify` и `call/status`.
- Роут `status` (публичный, `verify_origin`): тело `{ handle }`; невалидный/погашенный хэндл → 404. Дебаунс провайдера 3 с на телефон (in-memory, TTL-очистка карты). Маппинг кодов: `100`/`400` → `waiting`; `401` → `confirmed`; `402` → `expired` (свои `check_id` всегда корректны); прочее (иной код, HTTP ≠ 2xx, таймаут) → `waiting` без смены состояния и журнала. Порядок: **статус провайдера раньше локальной экспирации** (`created_at + 300 с`); отдельного капа обращений нет — объём ограничен окном и дебаунсом (~100 на проверку).
- `401`: **атомарное погашение + финализация одной транзакцией** — условный апдейт `pending → consumed` (`UPDATE … WHERE status='pending' RETURNING` / row-lock): параллельные опросы дают ровно одну сессию, второй — 404; при сбое транзакции строка остаётся `pending` (повторный опрос повторяет попытку); кука ставится после коммита; строка журнала `confirmed`.
- Дев-маршрут `POST /auth/call/dev-done` — имитация звонка; регистрируется **только при дев-транспорте в development** (двойной гейт, как `dev_code`) + `verify_origin`.
- Координация с #586 (решение, делегированное спекой §Финализация): общий файл роутера `otp/verify` — параллельная имплементация #586 и #593 исключена; **#593 строго первым** выделяет хелпер-финализатор, #586 при своей реализации наследует его (фиксируется в плане #586 на его гейте C).

### Required Docs

`docs/domain-rules/auth.md` (методы; сессии без ротации), спека §Эндпоинты (status, дев-режим), §Финализация.

### DoD

- Integration, US-5: истёкшая проверка → `expired`; приоритет провайдера — поздний звонок подтверждается до конца окна.
- Хэндл: 404 на невалидный/погашенный; до подтверждения кука не ставится ни на один ответ; replay погашенного — нет сессии; **параллельные опросы одного хэндла — ровно одна сессия**.
- Дебаунс: серия быстрых poll → у стаба ≤1 вызов `status` на 3-с окно.
- Финализатор переиспользуется `otp/verify` — его существующие тесты зелёные без правки ассертов; параллельные сессии живут (без ротации).
- US-7: капча логов и тел ответов — ключ и сырой хэндл отсутствуют в успехе и сбое.
- Дев-маршрут: 404, когда резолвер не вернул дев-транспорт (включая дефолтный `ENV=development` без `CALLCHECK_TRANSPORT=dev`).

## Task 5: Единый экран авторизации web — пикер, экран звонка, «Связаться»

### Classification: standard

- Компонент экрана авторизации (**один для формы записи и кабинета**): пикер `auth-method-picker` из `GET /auth/methods` («Подтвердить звонком» / «Код по SMS»; пустой реестр → «Вход временно недоступен» + «Связаться»); экран звонка `auth-call-screen`: номер `+7…` крупно, кнопка-ссылка `tel:+7XXXXXXXXXX` (`auth-call-number`, в href плюс и цифры, видимый текст — формат `+7 …`), подсказка «звонок бесплатен (в т.ч. в роуминге и из-за рубежа), прозвучит сообщение-гудок, звонок сбросится и не тарифицируется», видимый таймер остатка окна (мм:сс), ссылка «Другой способ»; опрос ~4 с (react-query `refetchInterval` функциональной формы: `false` на терминальных `confirmed`/`expired` и на 404; `refetchIntervalInBackground: false`); результат опроса побеждает отсчёт.
- Состояния: 404 опроса → останов, «Проверка недействительна» + «Начать заново» + «Связаться»; истечение → «Время вышло» + «Позвонить ещё раз» (новый initiate) + «Связаться».
- Панель «Связаться» `auth-contact-channels` (видна на экране входа постоянно): текст (в форме записи — предзаполнен данными заявки: услуга/МК, дата, время, гости, имя, телефон; в кабинете — приветствие), кнопка «Скопировать текст» (clipboard), мессенджеры администратора: WhatsApp `https://wa.me/<7XXXXXXXXXX>?text=…`, Telegram `https://t.me/<user>?text=…`; контакты `NEXT_PUBLIC_CONTACT_TELEGRAM` / `NEXT_PUBLIC_CONTACT_WHATSAPP`: пустой — кнопка скрыта, оба пустые — панель скрыта целиком (остаётся текст и копирование).
- Интеграция: `BookingActivityOverlay` — шаг `otp` переименовывается в `auth` и использует общий компонент (после `confirmed` — существующая авто-отправка записи); `CabinetLogin` — тот же компонент (после `confirmed` — существующий редирект). Ввод телефона — существующее поле (нормализация клиента; серверная 422 — страховка). Ошибки — серверные структурные сообщения существующим каналом, новых текстов не вводится.
- api-client: `getAuthMethods`, `initiateCallAuth`, `callAuthStatus` (+ типы).

### Required Docs

`docs/domain-rules/auth.md`, `docs/design-system.md`, спека §Фронт web.

### DoD

- Компонентные/unit: пикер рендерится из реестра (включая пустой); **на `/cabinet` пикер рендерится при загрузке, до ввода телефона** (рев.8 спеки — достижимость визуального гейта); экран звонка — `tel:` href, таймер, подсказка; «Связаться» — текст, копирование, ссылки, скрытие при пустых контактах (компонентный тест с пустыми `NEXT_PUBLIC_CONTACT_*`); состояния 404/истечения.
- Существующие unit-тесты `BookingActivityOverlay`/`OtpStep` обновлены под шаг `auth`; SMS-ветка кода остаётся рабочей (dev).
