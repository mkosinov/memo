# План #553 — Честная календарная дата в редактировании занятия

## Goal

Редактирование занятия во вкладке настроек сохраняет ровно выбранную в календаре дату и время — в том числе в другой неделе; успешный патч даты-времени подтверждается тостом «Сохранено: …»; модалка остаётся открытой при любом переносе (решение гейта B, рев.2 спеки). Drag&drop сетки, сервер, api-client, разметка и якоря формы — без изменений. Спека: `docs/specs/2026-10-25-activity-edit-honest-date-design.md` (рев.2).

## Architecture

Frontend-only, три точки правки: вкладка редактирования (`SettingsTab.tsx` — поле даты-времени отправляет `start`, guard пустого значения), контракт обновления (`ScheduleDataContext.tsx` — необязательный `start?: string` в union обновления занятия, приоритетная ветка в `updateActivityFn` по образцу `addActivity` после #280), тост успеха (уровень модалки `ActivityDetailsModal.tsx` — `handleActivityUpdate` резолвит промис мутации и при `updates.start` показывает тост). Отправители строго разделены: форма — только `start`, сетка (drag&drop, штампы слотов) — только `dayIndex + startMinutes`, их код не меняется.

## Tech Stack

Next.js (admin), TanStack Query v5 (промис мутации обновления), vitest (юниты), Playwright (e2e admin).

## Task 1: `start`-ветка контракта обновления в ScheduleDataContext

### Classification: small

### Required Docs

- `docs/domain-rules/activities.md`
- спека § «Контракт после», § «Риски»

### Steps

1. В union-тип обновления занятия (`updateActivityFn` первый параметр) добавить необязательное поле `start?: string` — полная локальная дата-время ISO; приоритетность и разделение отправителей задокументировать в комментарии типа, как сделано для union `addActivity` (комментарий «GH #280»).
2. В `updateActivityFn`: при `updates.start != null` — `payload.start` уходит как есть (конвертация от открытой недели не вызывается); иначе — прежняя ветка `composeLocalISO(dayIndexToDate(currentWeek, updates.dayIndex), updates.startMinutes)` с существующим условием обоих полей. Ветку не заменять — добавить приоритетной.
3. Мутация обновления сегодня fire-and-forget (интерфейс `updateActivity` объявлен `=> void`, внутри — `updateActivityMutate`). Перевести на `mutateAsync`: `updateActivityFn` возвращает промис с guard `promise.catch(() => {})` — зеркально `addActivity` в том же контексте (комментарий про fire-and-forget потребителей уже там); тип интерфейса обновить на `Promise<void>`. Существующие fire-and-forget потребители (сетка: drag&drop, штампы слотов) игнорируют промис — их код не меняется.

### DoD

Юниты (`frontend/admin/__tests__/`): при `start` в обновлении `payload.start` уходит как есть, конвертация открытой недели не вызывается; при `dayIndex + startMinutes` — прежняя конвертация (существующие тесты конвертации зелёные без правки ожиданий); оба набора сразу — побеждает `start` (документирующий приоритет ассерт); промис `updateActivity` резолвится на успехе и реджектится на ошибке (guard не создаёт unhandled rejection). Drag-тест сетки (US-4) — в Verification, не здесь.

## Task 2: Вкладка редактирования отправляет полную дату

### Classification: small

### Required Docs

- `docs/domain-rules/activities.md`
- спека § «Концепт» (пункт 1), § «Контракт после»

### Steps

1. В `SettingsTab.tsx` обработчик поля даты-времени: из значения `datetime-local` берутся `datePart` и `snappedMinutes` (существующий расчёт), отправляется `{ start: composeLocalISO(datePart, snappedMinutes) }` вместо `{ startMinutes, dayIndex }`. Выбранная дата больше не выбрасывается; хелперы `composeLocalISO`/`snapMinutes` уже импортированы вкладкой.
2. Guard пустого значения: очистка поля эмитит пустую строку — при пустом/частичном значении `onUpdate` не вызывается вовсе (патч не отправляется); «сломанный» `start` в PATCH невозможен по построению.
3. Прочие поля instant-patch (услуга/мастер/локация/длительность/вместимость/приватность) не трогаются.

### DoD

Юниты: вкладка при смене даты-времени отправляет `start` (не `dayIndex + startMinutes`); при пустом значении поля `onUpdate` не вызывается; остальные поля — прежние payload-ассерты (правка ожиданий только у поля даты-времени — предмет изменения).

## Task 3: Тост успеха патча даты-времени

### Classification: small

### Required Docs

- `docs/domain-rules/activities.md` (тост-канон #261 — общий тост-стек)
- спека § «Концепт» (пункт 3), § «Контракт после»

### Steps

1. В `ActivityDetailsModal.tsx` (`handleActivityUpdate`): при `updates.start != null` — `updateActivity(...).then(() => showToast(\`Сохранено: ${услуга} — ${formatDateRu(дата)}, ${время}\`)).catch(() => {})` — дефолтный вид (info → `toast-info`), текст зеркален тосту создания; catch-guard зеркален контекстному (реджект не создаёт unhandled rejection — ошибка уже обработана откатом в мутации); название услуги — из списка услуг контекста по `activity.serviceId` (тот же источник, что у автозаполнения вкладки); дата-время — из `updates.start` (`formatDateRu` + формат времени общего хелпера).
2. Ошибка мутации — существующая семантика без изменений: оптимистическая запись откатывается, патч молчит (error-тоста у обновления занятия сегодня нет — глобальный error-тост покрывает только запросы чтения, не мутации; спека рев.2.1); успех-тост при реджекте не показывается.
3. На патчи остальных полей (без `start`) тост не показывается — молчаливый instant-patch, как сегодня. Модалка не закрывается ни при каком исходе патча даты-времени (решение гейта B).

### DoD

Юниты: на `start`-патч с резолвом тост показан с текстом «Сохранено: …» и тестидом `toast-info`; на патч без `start` — тоста нет; на реджект `start`-патча — успех-тоста нет (молчаливый откат, как сегодня).
