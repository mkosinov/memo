# Исследование API sms.ru: авторизация звонком (callcheck)

- Дата: 2026-11-11. Для: #593 (вход по звонку — метод авторизации наряду с SMS-кодом). Обновлено 11.11: полная статья ЛК «Авторизовать пользователя по звонку с его номера» — подтверждения ниже (формат телефона, вебхук, `callto:` в `call_phone_html`); цена из ЛК (см. §Цена).
- Метод: 11.11 — только документация и лендинг провайдера (живых вызовов не было, аккаунта не было). 25.11 — первая живая проверка настоящим провайдером (#597): см. раздел «Живая проверка», расхождения с документацией сведены там в таблицу. Источник: `https://sms.ru/api`, `https://sms.ru/api/call`, `https://sms.ru/call`, `https://sms.ru/price`.

## Модель (важное отличие от flash call)

Это НЕ «сервис звонит клиенту, код = последние цифры входящего номера». У sms.ru обратная модель: **клиент сам звонит** на выданный сервисом номер; сервис опознаёт номер звонившего (АОН) и подтверждает совпадение с заявленным телефоном. Кода и ввода кода нет вообще; подтверждение = факт звонка с заявленного номера.

- Звонок сбрасывается — бесплатен для клиента, «даже для тех, кто звонит из-за рубежа» (лендинг). (25.11: выданный номер был московским `+7 499 …`, а не 8-800 — бесплатность звонка для клиента не подтверждена, см. «Живая проверка».)
- Окно проверки: 5 минут.
- Для роуминга: необязательный параметр `ip` (реальный IP клиента) — по нему сервис подставляет обычный номер вместо 8-800. «Никаких ограничений или блокировок по нему не применяется» (доки).

## Эндпоинты

### Создание проверки — `POST https://sms.ru/callcheck/add`

Параметры: `api_id` (ключ; либо `login`+`password` по HTTPS), `phone` (проверяемый номер — **формат подтверждён статьёй ЛК: `79996531803`, `7XXXXXXXXXX` без плюса**), `ip` (необяз., см. выше), `json=1` (рекомендуется). `check_id` в ответе — строка вида `201737-542`. `call_phone_html` в примере провайдера использует нестандартный `callto:` — #593 строит собственную `tel:`-ссылку (RFC 3966). Фактически 25.11: `check_id` приходит как `202648-80664981` (6 цифр, дефис, 8 цифр), `call_phone_html` — обычная `tel:`-ссылка; собственная `tel:`-ссылка #593 остаётся, формат поля в документации не гарантирован.

Ответ (цитата из доков):

```json
{
  "status": "OK",
  "status_code": 100,
  "check_id": "201737-542",
  "call_phone": "78005008275",
  "call_phone_pretty": "+7 (800) 500-8275"
}
```

Плюс `call_phone_html` — готовая `callto:`-ссылка для одной кнопки на мобильном.

### Статус проверки — `POST https://sms.ru/callcheck/status`

Параметры: `api_id`, `check_id`, `json=1`. Ответ (цитата):

```json
{
  "status": "OK",
  "status_code": 100,
  "check_status": "401",
  "check_status_text": "Авторизация по звонку: номер подтвержден"
}
```

### Коды `check_status`

| Код | Смысл |
|---|---|
| 100 | проверка принята, ждём звонка |
| 202 | неверный формат телефона |
| 400 | звонка ещё не было (не подтверждён) |
| 401 | номер подтверждён (звонок с заявленного номера зафиксирован) |
| 402 | время истекло / неверный `check_id` |

Фактически 25.11: `check_status` приходит числом (`401`, не `"401"`); свежая проверка без звонка сразу отвечает `400` — код `100` в этом поле не встретился. Оба кода клиент относит к ожиданию.

Несогласованность в доках: PHP-пример читает поле `call_number`, а JSON-спека даёт `call_phone` — клиент должен терпеть оба имени (аналог нестабильных доков Notificore, риск №5 спеки #586). Фактически 25.11 пришло только `call_phone`, со знаком «+» (`+74995555555`); клиент оставляет терпимость к обоим именам.

### Вебхуки

Статья ЛК подтверждает: вебхук для статусов проверок существует, бесплатен и «настоятельно рекомендуется» провайдером. Формат оповещения (payload) и способ регистрации в статье callcheck **не описаны** — отдельный общий API `callback_add/del/get`. Решение #593 v1: НЕ строим — фронт всё равно опрашивает наш бекенд, вебхук лишь переносил бы исходящий цикл на приёмный эндпоинт с аутентификацией источника; при появлении документированного формата — возможен второй итерацией.

## Цена и аккаунт

- **Подтверждено из личного кабинета sms.ru (2026-11-11, владелец): сейчас система бесплатна; планируется 0,8 ₽ за каждую успешную авторизацию.** Успешная = клиент позвонил на выданный номер в течение 5 минут с момента подачи номера; неуспешные (без звонка) не тарифицируются. Решающая ячейка — пессимистично 0,8 ₽ за успешную.
- На сайте цена не публикуется (лендинг и тарифы молчат; на `/price` только SMS по прямым каналам операторов «от 8,36 ₽» с абонплатой за имя). Внешний обзор называл 0,40 ₽ (РФ) / 1 ₽ (мир) — источник ненадёжен (ошибся в механизме).
- Живой проверкой 25.11 (#597) подтверждено: формат телефона `7…` без плюса принимается; ошибок и отказов квоты не было на 3 опросах интерфейса и 2 прямых запросах `callcheck/status`. Интерфейс опрашивает примерно раз в 10 секунд — около 30 запросов за 5-минутное окно, расчётные ~100 обращений на проверку не достигаются. Не проверено: лимиты аккаунта при больших объёмах. Формат номера **пользователю** — строго `+7…` (см. §Факты провайдера для UI).

## Факты провайдера для UI (2026-11-11)

- **Номер клиенту — строго с «+»**: передавать `+7499…` или ссылкой `<a href="tel:+7499…">`. Номер без плюса (`7499…`) часть операторов не пропускает («неправильно набран номер»), особенно звонящих из-за рубежа. Вариант с ведущей `8` (`8499…`) подходит только звонящим из РФ.
- **Звонок бесплатен конечному пользователю** — в роуминге и с зарубежного номера тоже: голосовое сообщение об успешности передаётся как мелодия гудка, затем звонок сбрасывается; звонок не считается установленным (голос не получают) и операторами не тарифицируется.

## Живая проверка (2026-11-25, #597)

Первая проверка настоящим провайдером. Стенд: playground в контейнере opencode на актуальном main, `CALLCHECK_TRANSPORT=smsru`, метод SMS выключен — путь клиента прода v1. Владелец с телефона: занятие → форма записи → «Подтвердить звонком» → звонок на выданный номер → вход → запись создана. Одна попытка прошла целиком; `SmsRuClient` не менялся — расхождения с документацией он покрывает терпимым разбором.

### Ответы провайдера (дословно)

- `add` → `{"status": "OK", "status_code": 100, "check_id": "202648-80667517", "call_phone": "+74995555555", "call_phone_pretty": "8-499-555-5555", "call_phone_html": "<a href=\"tel:+74995555555\">8-499-555-5555</a>"}`.
- `status` подтверждённой проверки → `{"status": "OK", "status_code": 100, "check_status": 401, "check_status_text": "Авторизация по звонку: номер подтвержден"}`.
- `status` свежей проверки без звонка → `"check_status": 400`, «Авторизация по звонку: номер пока не подтвержден».

### Ход попытки

- Создание проверки — 10:23:55, подтверждение — 10:24:26 (31 с); запись создана в секунду подтверждения.
- Интерфейс: 1 запрос на проверку и 3 опроса статуса; журнал попыток получил строки `created` и `confirmed`, строка проверки погашена.
- Ответ провайдера — 0,5–0,8 с на запрос.

### Расхождения с документацией

| Что | Документация | Фактически |
|---|---|---|
| Имя поля номера | JSON-спека — `call_phone`, PHP-пример — `call_number` | только `call_phone`, со знаком «+» |
| Номер для звонка | `78005008275`, без «+», 8-800 | `+74995555555` — московский; тот же с параметром `ip` и без него |
| `call_phone_html` | нестандартный `callto:` | обычный `tel:` |
| `check_id` | `201737-542` | `202648-80664981` — 6 цифр, дефис, 8 цифр |
| Тип `check_status` | строка `"401"` | число `401` |
| Свежая проверка | код 100 «ждём звонка» | сразу 400 |

### Ещё факты

- Повторный `add` на тот же номер при открытой проверке вернул тот же `check_id` — у провайдера одна открытая проверка на номер, как и в модели #593.
- Ошибок и отказов квоты не было на 5 запросах `status`. Интерфейс опрашивает примерно раз в 10 секунд — около 30 запросов за окно.
- В playground Docker Desktop подменяет адрес клиента шлюзом `192.168.65.1` — провайдер принял такой `ip` без ошибки.

### Не закрыто — проверка на проде в ночь запуска

- Номер 8-800 вместо московского при настоящем публичном адресе клиента. От этого зависит, бесплатен ли звонок клиенту.
- Передача настоящего адреса клиента через прокси-сервер прода.

## Ограничения модели

- Подтверждение фиксирует только факт звонка с заявленного номера: скрытый АОН — проверка не подтвердится; городской/корпоративный номер, с которого не набрать — не подходит.
- Один `check_id` — одно окно 5 минут; повторная проверка = новый `callcheck/add` (новая строка расходов).
