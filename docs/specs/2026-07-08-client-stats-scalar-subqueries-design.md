# Спецификация: структурное исправление подсчёта статистики клиентов (GH #105)

**Дата:** 2026-07-08
**Issue:** [#105](https://github.com/mkosinov/memo/issues/105)
**Тип:** Backend, техдолг (Wave 1)
**Классификация:** standard

---

## Проблема

Функция `list_clients_with_stats` (`backend/src/services/client.py:32-211`) считает для
списка клиентов четыре показателя одним SQL-запросом:

- `visits_count` — сколько у клиента **записей** (не визитов);
- `total_paid` — сумма оплат;
- `missed_visits` — сколько визитов со статусом `missed`;
- `last_visit` — дата последнего визита.

### Суть бага (декартово произведение)

Если у клиента есть одна запись с **несколькими визитами** и при этом есть **оплата**,
старый способ «склеивал» (JOIN) таблицу визитов и таблицу оплат в одну общую. Строка с
оплатой дублировалась под каждый визит, после чего `SUM(Payment.amount)` суммировал её
несколько раз. Клиент видел завышенную сумму «Оплачено» (в issue — значения порядка
1,7 млн ₽ вместо реальных).

### Текущее состояние — заплатка, не структурное исправление

Код уже был частично исправлен: подсчёт визитов и подсчёт оплат **разделены** на два
подзапроса (`visits_subq` строки 39-52 и `payments_subq` строки 55-64). Благодаря этому
`total_paid` сейчас считается **правильно**.

**НО** сам опасный приём (`outerjoin` → `GROUP BY` → агрегатная функция) в подзапросах
остался. Показатель `missed_visits` (строка 44) считается верно **случайно** — потому что
после join к визитам получается ровно одна строка на визит. Стоит кому-то добавить в
`visits_subq` ещё один `outerjoin` (например, чтобы посчитать новый показатель) или
агрегат по другой связи — задвоение вернётся молча, без предупреждения.

Это латентная мина. Цель issue #105 — обезвредить её структурно, а не только заплаткой.

---

## Решение: скалярные подзапросы

Заменить два подзапроса на основе `outerjoin` на **четыре независимых коррелированных
скалярных подзапроса** — по одному на каждый показатель. Каждый подзапрос читает **ровно
одну** связь (только записи, только оплаты, или только визиты), поэтому перемножение строк
между разными таблицами становится **физически невозможным**.

### Аналогия на Python

Сейчас (опасно — сначала смешиваем, потом суммируем):
```python
смесь = склеить(визиты, оплаты)          # строки дублируются
оплачено = sum(с.оплата for с in смесь)   # задвоилось
```

Станет (безопасно — каждая цифра из своего источника):
```python
записей   = посчитать(записи_клиента)
оплачено  = sum(оплаты_клиента)           # только оплаты — задваивать нечего
пропущено = посчитать(пропущенные_визиты_клиента)
```

### Форма запроса (SQL-уровень)

Каждый показатель становится помеченным `.scalar_subquery()`, коррелированным по
`Client.id`:

- **`visits_count`** — `select(func.count(Record.id))` где `Record.client_id == Client.id`
  и `Record.is_active`.
- **`last_visit`** — `select(func.max(Visit.created_at))` из `Record` join `Visit`, те же
  условия по клиенту и активности записи.
- **`missed_visits`** — `select(func.count(Visit.id))` из `Record` join `Visit`, плюс
  `Visit.status == "missed"`.
- **`total_paid`** — `select(func.coalesce(func.sum(Payment.amount), 0))` из `Record` join
  `Payment`, те же условия по клиенту и активности записи.

Основной запрос становится `select(Client.<колонки>, <4 скалярных подзапроса>)` с обычным
`WHERE Client.is_active` — **без** `outerjoin` к подзапросам статистики.

Сортировка (`sort_column_map`) и фильтры по статистике (`min_visits`, `max_visits`,
`min_paid`, `max_paid`, `missed_from`, `missed_to`) ссылаются на выражения скалярных
подзапросов напрямую — это допустимо в `ORDER BY` и `WHERE`. Пагинация не меняется.

### Компромисс по производительности

Вместо 2 присоединённых подзапросов будет 4 коррелированных мини-запроса на каждую строку
клиента. Для списка клиентов (максимум 100 строк на страницу) это ничтожно — SQLite
выполняет такое мгновенно. Ясность и безопасность важнее микро-оптимизации.

Изменение затрагивает **только** SQL внутри `list_clients_with_stats`. Снаружи ничего не

- схемы Pydantic — без изменений;
- база данных / миграции — **не трогаем**;
- фронтенд — **не трогаем**.

Все существующие тесты `test_client_stats.py` (1075 строк) и `test_api_clients.py` должны
остаться **зелёными**. Это гарантия, что семантика не изменилась:

- `visits_count` считает **записи**, а не визиты;
- `missed_visits` считает визиты со статусом `missed`;
- `total_paid` суммирует оплаты **один раз**;
- `last_visit` = максимальная дата визита;
- все сортировки, фильтры и пагинация работают идентично.

## Новый тест-сторож (ровно один)

В `test_client_stats.py` сейчас **нет ни одного** теста на комбинацию «несколько визитов +
оплата в одной записи» — именно эта комбинация ловит задвоение (существующий
`test_total_paid_aggregates_payments` использует только 1 визит, а `test_missed_visits_count`
— без оплат).

Добавить **один** тест на результат (проверяет цифру, НЕ способ написания SQL):

> Клиент с 1 записью, 2 визитами и 2 оплатами → `total_paid == сумма(оплат)` (не удвоено),
> при этом `visits_count == 1` и `missed_visits` не искажены.

Если в будущем кто-то вернёт мину — сумма станет удвоенной, и этот тест сразу покраснеет.

## Пометка на будущее (архитектура)

Во всех четырёх скалярных подзапросах будет повторяться условие `Record.is_active`
(«запись активна»). Это дублирование — кандидат на вынос в общий помощник, но оно
пересекается с issue **#98** (единое определение «активной записи» для всей системы).
Поэтому здесь его **не трогаем** — пометка добавлена в #98, разберём там, чтобы не
раздувать текущую задачу.

**Ответ на открытый вопрос issue** («есть ли другие места с той же ошибкой?»): аудит
(2026-07-08) подтвердил — **нет**. Единственное место с агрегацией по нескольким связям —
это `client.py`. Файл `search.py:67` использует одиночный `join` без агрегации и безопасен.

## User Scenarios

Функция внутренняя (SQL-агрегация), поэтому сценарии сформулированы как наблюдаемое
поведение через API `GET /api/v1/clients`:

1. **Клиент с несколькими визитами и оплатой видит корректную сумму.** Клиент с 1 записью,
   2 визитами и оплатой 3000 ₽ → в списке `total_paid == 3000` (не 6000). → покрывается
   новым тестом-сторожем.
2. **Суммирование оплат по нескольким записям корректно.** Оплаты по разным записям одного
   клиента складываются один раз. → покрыто существующим `test_total_paid_across_multiple_records`.
3. **Подсчёт записей не зависит от числа визитов.** Клиент с 1 записью и 3 визитами →
   `visits_count == 1`. → покрыто существующим `test_visits_count_with_multiple_visits_in_one_record`.
4. **Пропущенные визиты считаются по визитам.** Клиент с 2 пропущенными визитами →
   `missed_visits == 2`. → покрыто существующим `test_missed_visits_count`.
5. **Сортировка и фильтры по статистике продолжают работать.** `sort_by=total_paid`,
   `min_paid`, `missed_from` и др. дают те же результаты, что и раньше. → покрыто
   существующими тестами сортировки/фильтров.
