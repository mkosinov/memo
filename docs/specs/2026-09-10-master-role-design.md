# Спека #263: Роль мастера v1 — свой скоуп данных, маска телефона, оплаты, фото, меню по роли

- Дата: 2026-09-10
- Issue: #263
- Статус: G1a одобрен 2026-09-10; ревизия 3 — все 5 ревьюеров отработали (consistency/feasibility — с третьей попытки), находки внесены; часть «противоречий со спекой #247» отклонена фактчеком как исторический текст (см. «Правки текста спеки #247»)
- Очередь: IMPL строго после мержа #247 (auth) → #266 (staff) → #262 (кабинет); якорь модели — post-#266
- **Гейт:** код #263 не мержится в main, пока #247, #266 и #262 не смержены и CI main зелёный (в плане — задачей 0 с проверкой, паттерн T0 из #266).

## Контекст

#247 дал ролям вход и гварды, но сознательно вынес за скобки две вещи (§8 спеки #247): per-master data scoping («мастер видит только свои записи» — там доступ студийный) и per-role интерфейс (меню одинаково для ролей, `AuthContext.can()` — заготовка). #266 развёл «сотрудника» и «мастера» (staff + masters-строка, `users.staff_id`). #262 дал кабинет. Эта спека закрывает обе дыры: серверный скоуп «только своё» для роли `master` и урезанный интерфейс.

Терминология — по D2 #266: «мастер» = ведущий (masters-строка), «сотрудник» = staff. Роль — на учётке (`users.role`), скоуп — по masters-строке учётки.

## Отличия от текста issue

Issue фиксировал права из G1a-диалога #262; диалог G1a #263 (10.09) уточнил и местами сузил:

1. **Раздела «Клиенты» у мастера нет вообще** (issue содержал его в меню) — поиск клиента живёт только внутри формы записи (typeahead по номеру). Экран списка клиентов мастеру не нужен.
2. **Оплаты: полный контроль своих записей** — не только «сумма и статус», но и удаление, и создание (мастер принимает оплату на месте) — решение юзера 10.09.
3. **«Своё фото» = фото своей активности.** Фото «своих клиентов» как категория отпала (юзер: «мой клиент в фотках не актуален»).
4. **Маска телефона: последние 4 цифры** — `+7 909 •••-••-1234` (юзер выбрал из трёх вариантов; 4 цифры различают одинаковые имена в typeahead).
5. **Загрузка файлов-фото не вводится** — фото создаётся указанием filename строкой, как у админа сегодня; file-upload — отдельная будущая задача.
6. **Мастер может создавать клиентов** (необходимый флоу записи новому клиенту), но не править и не удалять существующих — расширение против read-only #247, скомпенсировано запретом мутаций.
7. **Аватар мастера — публичный URL в статике** (#262: `/api/v1/files/avatar`), вне скоупа и масок.

## Решения (из диалога G1a)

**D1. Скоуп — серверный, один якорь.** «Своё» определяется одной точкой: `master_key` = masters-строка учётки (цепочка `users.staff_id` → staff → `masters.staff_id`, post-#266; один join). Роль admin → скоупа нет. Роль master без masters-строки → **пустой скоуп: заведомо пустое множество, никогда «всё»** (безопасностное правило; пустой скоуп ≠ отсутствие скоупа).

**D2. Правило «своё» — всё через записи.** Единая арифметика владения, без новых колонок и миграций:

| Сущность | «Своё» |
|---|---|
| активность | `activity.master_id = master_key` |
| запись | активность записи — своя |
| визит, посетитель | запись (визита / любого визита посетителя) — своя |
| оплата | запись оплаты — своя |
| фото | фото привязано к своей активности (фото клиентов/услуг/локаций и без владельца — чужие) |
| клиент | есть неархивная запись клиента к своей активности; **исключение**: поиск по номеру телефона — по всем неархивным клиентам студии (см. D4) |

Словари **services / locations / tags — без скоупа**: мастер видит полный словарь (read-only, право из #247) — они нужны для отображения расписания, записей и фото; разделы Локации/Теги в UI при этом скрыты (D8). **Материалы** — прав нет (#247): API-гварды дают 403, блок в UI скрыт.

Скоуп не зависит от `masters.is_active`: архив распределения не прячет историю (мастер продолжает видеть свои прошлые записи — паритет с D3 #266, где архивная masters-строка хранит историю).

**D3. Маска телефона и вырезание контактов — на уровне API.** Для роли master в **каждом** ответе, содержащем клиентские данные:

- `phone` → маска «последние 4 цифры»: `+7 909 •••-••-1234` (все нецифровые разделители сохраняются, прочие цифры → `•`; телефоны короче 4 цифр маскируются целиком; `null` остаётся `null`);
- `email` → `null` (вырезается, не маскируется);
- имя и `channel` — видны.

Точки: клиентские схемы (`ClientResponse`, `ClientWithStats`) и выдача typeahead (в ответах записей телефона клиента нет — `phone` встречается только во входной схеме создания записи). Маска применяется серверно при сборке ответа — фронт получает уже замаскированную строку и отдельной логики не имеет. Полный номер живёт только как **ключ поиска** (вход запроса), не как данные ответа. Маскированный хвост — не идентификатор: при ~10 тыс. клиентов совпадения хвостов нормальны, ключ выбора — всегда id клиента.

**D4. Поиск клиента по номеру — по всем, для формы записи.** `?phone=` (digits-mode, #221) и `GET /clients/get?phone=` для мастера работают по **всем активным** клиентам студии (10 тыс. — по имени не найти), ответ маскирован по D3. Список `GET /clients` без phone-фильтра — скоуп D2 (только свои; фронтом мастера не используется, но API остаётся консистентным). **Осознанное отклонение (юзер 10.09, по итогам панели): phone-поиск не троттлится** — мастер = сотрудник студии с учёткой, риск перебора номеров принят для внутреннего инструмента (паритет со списком осознанных отклонений #247, конец §9).

**D5. Оплаты — полный CUD своих.** Дельта к #247 (там master `payments:read`): мастер создаёт, изменяет и удаляет оплаты **своих** записей. Чужие оплаты: list не отдаёт, точечные операции → 404 (не 403 — не раскрываем существование). `GET /payments/totals` — суммы только по запрошенным record_id своих записей (чужие id молча исключаются из выдачи, контракт ответа не меняется).

**D6. Фото — полный CUD своих фото активностей.** Создание (filename строкой — как у админа), правка метаданных, удаление — только для фото своей активности. Список `/photos` для мастера — только свои; get/мутации чужих → 404. Публичная галерея `/photos/web` не трогается (публичный сайт). Загрузки файлов нет (отличие 5).

**D7. Создание клиентов — можно, правка — нельзя.** Мастеру нужен флоу «записал нового клиента по телефону» (typeahead не нашёл → создаём). `POST /clients` — разрешён (201). `PUT/PATCH/DELETE/archive/restore` клиентов — 403 `AUTH_FORBIDDEN` (мастер не владелец клиентской базы; исправление профиля — задача админа). В матрице прав это отражается токеном `clients:write` у мастера; запрет мутаций существующих — скоуп-правило D7, а не матрица.

**D8. Меню и экраны по роли.** Один build админки. Мастер видит: **Расписание / Записи / Услуги (только просмотр) / Фото**. Скрыты: **Клиенты, Локации, Теги** (разделы), **легенда «Мастера»** в сайдбаре, **блок материалов** внутри страницы «Услуги» (после #223 материалы живут там; права `materials:*` у мастера нет по #247). Прямой URL скрытого раздела → экран **«Нет доступа»** (нового паттерна в репо нет — компонент на базе существующих error-экранов). Кнопки правки без права скрыты через `can()` (#247 seam): таблица услуг — без create/edit, фото — create/edit/delete только своих (UI не различает — сервер режет). `users.is_active`-логика, логин, кабинет — без изменений (#247/#262).

**D9. Герметичность API — страховка, фронт — косметика.** Скоуп и маска живут на сервере. Фронт-скрытие меню/кнопок — удобство, не защита: прямой вызов API под сессией мастера всё равно вернёт только своё (S6).

## Backend

**Scope-слой.** Новый модуль `backend/src/auth/scope.py`: `ScopeContext {user_id, role, master_key: str | None}` + зависимость, собирающая контекст из сессии (#247) одним join `users → staff → masters`. `master_key` не None **только** при `role=master` и существующей masters-строке. Для `role=master` без masters-строки — sentinel пустого скоупа (D1). Роль admin — контекст без скоупа.

**Применение скоупа** — существующие точки фильтрации, ноль новых эндпоинтов. Общее правило: скоуп ложится **только в штатные точки расширения** generic-механизма (kwargs-фильтры сервисов, сервисный stmt-билдер + общий repo-кор счёта/сортировки/пагинации — паттерн #213 записей и фото); уникальных запросных путей под скоуп не появляется (преемственность с выравниванием #139/#206/#213).

- **activities**: list — where `master_id = master_key` (паттерн kwargs в `services/activity.py:69`); точечные get/мутации — у мастера прав на мутации нет (#247), get чужой → 404.
- **records**: `_build_list_stmt` (`services/record.py:129`) — серверный where по `Activity.master_id` добавляется **конъюнктивно (AND)** к любым клиентским фильтрам (клиентский параметр `master_id` ≠ свой → просто пустой результат; скоуп не снимается клиентским фильтром). Композитный `list_view` делит тот же билдер — скоуп одной точкой покрывает оба списка. Точечные get/update/delete и каскады визитов/посетителей — owner-проверка через активность записи, чужое → 404.
- **payments**: списком оплат никогда не фильтровали — generic-путь без кастомного билдера. Скоуп оформляется **сервисным stmt-билдером через штатную точку расширения** (как у записей/фото: сервис собирает stmt с `join payment → record → activity.master_id`, общий repo-кор делает счёт/сортировку/пагинацию; у оплаты нет колонки мастера — владелец только через запись); точечные create/update/delete — owner-проверка записи, не билдер. `get_payment_totals` предварительно фильтрует `record_ids` по своим перед агрегацией.
- **photos**: list — **новая EXISTS-ветка** в существующем билдере (`EXISTS(activity: photo.activity_id → master_id = master_key)`; LEFT JOIN путь `service_id`-фильтра не трогаем); точечные — owner-проверка.
- **clients**: list без `phone` — скоуп D2; list с `phone` и `GET /get?phone=` — все активные (D4); get/{id} — свой → 200 (маска), чужой → 404; мутации по D7.
- **visitors**: list — скоуп через визиты (`visitor → visit → record`); мутации — в контексте своих записей (посетитель без визитов мастера для него невидим).
- **visits**: скоуп через запись.

**Маска.** `mask_phone()` рядом со scope-модулем (одна реализация), применяется в сервисах при сборке клиент-содержащих ответов для роли master (D3). Мутации не маскируются: мастер создаёт клиента с полным номером (WYSIWYG #221), сервер хранит полный номер — маска только на чтение.

**Матрица прав (дельта к `ROLE_PERMISSIONS` #247).** Мастер добавляет: `payments:write` (полный CUD — скоуп D5 режет до своих записей), `photos:write` (CUD — скоуп D6 режет до своих фото активностей), `clients:write` (семантика D7: только создание — мутации существующих блокирует скоуп-правило). Остальные токены без изменений; скоуп — слой поверх матрицы, матрица остаётся про HTTP-глаголы. `PUBLIC_ROUTES` не меняется.

**Новых кодов ошибок нет.** Чужое под скоупом → 404 существующим кодом сущности (`RECORD_NOT_FOUND` и т.п. — не раскрывает существование); мутации клиентов мастером → 403 `AUTH_FORBIDDEN`.

**Правки текста спеки #247** (код-блок матрицы §3.5 и таблица гвардов §3.7 — там фиксируется pre-#263 состояние) — отдельной задачей плана **после мержей**, паттерном T12 из #266. Канон прав до того — `docs/domain-rules/auth.md` (обновлён этим коммитом) и код `ROLE_PERMISSIONS`.

## Frontend (админка)

- **Меню** (`Menubar.tsx`): константный список admin-only разделов `['/clients', '/locations', '/tags', '/staff', '/positions']` (последние два появляются после #266 — «Сотрудники» и «Должности») — пункты `NAV_ITEMS`/`DIRECTORY_ITEMS` фильтруются для роли master; легенда «Мастера» (`:566-600`) не рендерится; блок материалов на странице услуг скрыт по `can('materials:read')`.
- **Guard прямых URL**: в `(main)/layout.tsx` (клиентский, паттерн #247 §4.4) — pathname входит в admin-only список и роль master → экран «Нет доступа» (компонент на базе `ErrorState`, `data-testid="no-access"`). Middleware не вводится (решение #247).
- **`can()` становится потребляемым**: таблица услуг — кнопки create/edit скрыты без `services:write`; модалки справочников — read-only рендер (существующий проп-паттерн `isReadOnly` — источником становится `can()`). Записи/оплаты/фото мастеру разрешены — без изменений.
- **Typeahead без правок**: маска приезжает с сервера; строка `Имя · +7 909 •••-••-1234` отображается как есть; флоу unpicked-save (создание клиента с полным номером) работает — POST разрешён (D7).
- **Кабинет #262, логин, юзер-блок** — без изменений.

## Пограничные случаи

- **Учётка `role=master` без masters-строки** (легальна по #266): пустой скоуп — все списки пусты, создание записей недоступно (нет своих активностей), typeahead работает (поиск по всем + создание клиентов и записей — к каким активностям? **своих активностей нет → селектор пуст → запись не создать**). Вход жив, кабинет жив. Пустой селектор активностей — штатный пустой стейт (EmptyState); создание активностей — право админа, мастеру не даётся.
- **Архивная masters-строка** (`masters.is_active=false`, учётка жива): скоуп по master_key сохраняется — история видна, новых активностей у него нет (их создаёт админ).
- **SSE #239**: события инвалидаций приходят всем; мастер-фронт перечитывает — данные приходят скоупированными, отдельных правил не нужно.
- **`GET /payments/totals` с чужими id**: молча исключаются (D5) — контракт ответа неизменен; все id чужие → `200 {"totals": {}}`.
- **Клиент с одинаковой маской**: два клиента с хвостом `1234` различаются именем; полный номер не восстановим из ответа.

## User Scenarios (→ e2e)

- **S1. Своё расписание.** Мастер открывает /schedule — видит только свои активности (чужие недели/дни пусты).
- **S2. Запись с поиском клиента.** Мастер создаёт запись: в селекторе активностей только его; typeahead по полному номеру находит клиента по всей студии, телефон в выдаче замаскирован (`…•••-••-1234`); запись создаётся. Не найден — клиент создаётся с введённым номером, запись создаётся.
- **S3. Оплаты.** Мастер создаёт оплату своей записи, меняет сумму/статус, удаляет — применяется и виден пересчёт статуса оплаты записи.
- **S4. Нет доступа.** Мастер открывает прямой URL /clients, /locations, /tags, /staff или /positions → экран «Нет доступа»; в меню этих пунктов нет; блок материалов на «Услугах» скрыт.
- **S5. Свои фото.** Мастер создаёт фото (filename строкой) к своей активности — видит его в списке; фото чужих активностей и клиентов в его списке отсутствуют.
- **S6. API герметичен.** Под сессией мастера: любой ответ с клиентом отдаёт маскированный phone и email=null; чужие record/payment/photo/client по id → 404; PATCH клиента → 403; totals по чужим record_id не содержит их сумм.
- **S7. Админ без регрессий.** Под админом все разделы, полные телефоны, все записи/оплаты/фото — поведение идентично до #263.

## Границы (не делаем в #263)

- Фото чека оплаты, клиентская галерея «посмотреть/скачать» (#48), веб-приложение бронирования — не трогаем.
- Админ-доступ к данным сотрудников (кто что видит), управление ролями/учётками из админки — вне скоупа (sqladmin/справочник #266).
- Отдельный интерфейс мастера (мобильный/упрощённый) — та же админка.
- Маска в sqladmin, логах и бекапах — не вводим (маска про HTTP-ответы API).
- `PUBLIC_ROUTES`, сессии, лестница блокировок, CSRF — без изменений (#247).

## Тестирование
