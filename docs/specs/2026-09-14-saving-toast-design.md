# Спека: индикатор «Сохраняем…» — тост в общем стеке (#261)

- **Дата:** 2026-09-14
- **Issue:** #261
- **Статус:** rev2 — панель G1b отработана, правки внесены; на утверждение G1b
- **Ревизии:** rev1 → rev2 по итогам панели (см. §10)
- **Связанные:** supersede §5 спеки #141 (`2026-09-06-schedule-context-split-design.md` — «Topbar renders the „сохраняем…" chip»); совместимость с §4.3 спеки #239 (`2026-09-08-server-push-invalidation-design.md`); очерёдность с #258/#259 и #260 (см. §9)

## 1. Проблема

Во время любой мутации расписания (создание / перенос / удаление занятия) в Topbar загорается отдельная плашка «Сохраняем…» со спиннером. Решение пользователя (09.09.2026, фиксируется этой спекой как смена решения спеки #141 §5): индикатор должен жить в **общем стеке тостов** как обычный тост, а не отдельной плашкой в Topbar.

Это не регрессия, а смена решения: плашку зафиксировала спека #141 §5. Вероятный источник смены: #239 уже выбрал тост для «Данные обновлены» (внешние SSE) — юзеру единообразнее, когда и собственные мутации видны в том же стеке.

## 3. Решения

**D1 — новый общий вид тоста `loading`.** В `ToastKind` добавляется `'loading'`. Семантика вида: спиннер + текст, **без таймера автоскрытия**, **без кнопки закрытия**; тост снимается только программно через существующий `hideToast(id)`. Вид — первоклассный и общий: любой будущий код может его использовать, «Сохраняем…» — лишь первый потребитель. Дефолтные таймеры существующих видов (4500/5000) не меняются; опции «своя длительность» не вводится (YAGNI — не нужен ни одному из 40+ вызовов). Механика в коде — 4 точки: (1) `'loading'` в union `ToastKind` (`UIContext.tsx:5`); (2) в `showToast` ветка «вид `loading` → таймер не заводится» (сигнатура и поведение остальных видов без изменений); (3) явная нейтральная запись для `loading` в `BORDER_BY_KIND` (`ToastContainer.tsx:13-17`); (4) кнопка закрытия не рендерится для `loading` (`ToastContainer.tsx:43-49`). Клавиатурного закрытия у `loading` нет и не появляется: контейнер не обрабатывает Escape, единственный путь снятия — `hideToast(id)`.

**D2 — хук индикатора.** Новый хук (размещение — `frontend/admin/hooks/useSavingToast.ts`, доступ к `showToast`/`hideToast` — через `useUI`, потребитель — Topbar): через `useMutationState` по `SCHEDULE_ACTIVITY_MUTATION_KEY` следит за пачкой незавершённых мутаций расписания. Механика: select возвращает статусы мутаций; **незавершённая = `pending` или `paused`** (офлайн-пауза — не завершение); счётчик незавершённых как переходы: «0 → ≥1» — показать **один** тост «Сохраняем…» (вид `loading`), id запоминается в ref; «≥1 → 0» — снять его. Успех и ошибка — одинаково settle. При размонтировании хука при живом тосте — снять в cleanup (единственная защита от «вечного» тоста; страховочный kill-таймер не вводим: HTTP-таймауты сервера гарантируют settle). Три параллельных переноса = один тост (как сейчас один флаг). Ошибку показывает существующий красный тост `providers.tsx:23`.

**D3 — плашка удаляется.** Блок `Topbar.tsx:338-363` удаляется вместе с спиннером чипа. `useUnsavedChangesGuard(isSaving)` **остаётся** как есть (`:55-59`): guard про beforeunload, к индикатору отношения не имеет. Вызов хука D2 размещается в Topbar там же, где жил чип.

**D4 — результат приносят существующие тосты.** Вид `loading` никогда не конвертируется в успех/ошибку. Последовательность в стеке: «Сохраняем…» → (снят) → «Создано: …» / «удалено»+undo / красная ошибка. Отдельный тост результата не добавляем.

**D5 — рендер вида `loading` в контейнере.** `ToastContainer` для вида `loading`: рисует спиннер (переиспользуется SVG-спиннер из удаляемого чипа `Topbar.tsx`, помечен `aria-hidden="true"` — скринридер озвучивает текст тоста, спиннер молчит), **не рендерит** кнопку закрытия, testid `data-testid="toast-loading"` получается штатно из шаблона `:28`. Стилевое оформление — как у остальных тостов (нейтральная рамка — явная запись в `BORDER_BY_KIND`); нажатие на тело тоста ничего не делает.

**D5a — `loading` вне лимита стека (решение юзера 14.09).** Лимит «видимо 5» (`slice(-5)`, `ToastContainer.tsx:11`) применяется только к обычным тостам: видимое окно = последние 5 обычных + все `loading`-тосты. Индикатор не может быть вытеснен стопкой результатов — иначе он не выполняет свою задачу (файндинг best-practices/феасабилити). Порядок — хронологический, как у обычных тостов («складывается в стопку как остальные» — формулировка issue); `loading` просто не участвует в лимите. Практически `loading`-тост один (дедуп хука D2).

**D6 — скоуп индикатора.** «Сохраняем…» появляется только на мутациях расписания (ключ D2). Мутации записей, справочников, фотографий, платежей индикатора не получают — у них нет такого запроса; их текущее поведение не трогается.

**D7 — уборка тестов.**
- Удалить `Topbar.saving-indicator.test.tsx` (целиком про чип).
- `Topbar.test.tsx:321-355`: ассерты чипа убрать; ассерт «guard активен при pending-мутации» сохранить (поведение guard не меняется); проверить `CellHeight.Topbar.test.tsx:40` — мок остаётся валидным.
- Новые unit-тесты: `UIContext` — вид `loading` не автоскрыается (таймер не заводится), снимается `hideToast(id)`; `ToastContainer` — для `loading` есть спиннер и нет кнопки закрытия; хук — показывает один тост, снимает по завершении всех, ошибка снимает, повторный показ при новой пачке мутаций работает.
- Ассерт 4500 мс в `UIContext.test.tsx:168` остаётся валидным (дефолты не меняются).

**D8 — согласование с параллельными дорожками.** См. §9: IMPL строго после мержа #258/#259; z-токен и `data-testid="toast-container"` от #260 не блокируют, но строки соседние.

## 4. Детали поведения и края

- **Переполнение стека:** решено D5a — `loading` вне лимита 5, вытеснение невозможно. Для обычных тостов лимит работает как раньше.
- **a11y:** контейнерный `role="status" aria-live="polite"` уже объявляет появление тостов; «Сохраняем…» озвучивается один раз при вставке (один DOM-узел, перерендеры хука его не переозвучивают). Спиннер `aria-hidden="true"` (D5). Отдельных aria-атрибутов для вида `loading` больше не добавляем; батчинг/дебаунс озвучивания всего стека — существующее поведение контейнера, вне скоупа.
- **Визуальные базлайны:** e2e-visual маскирует `[role="status"]` (`visual-regression.spec.ts:134-138`) — контейнер тостов под маской, чип удаляется; новых базлайнов и регрессий пикселей Topbar в тестах не ожидается (чип виден только во время мутации, визуальные тесты не мутируют в момент снапшота).
- **Быстрые повторы:** повторная пачка мутаций после settle показывает новый тост (новый id). Дедупликация — по переходу счётчика «0 → ≥1» (D2): сколько бы мутаций ни стартовало одновременно, тост один.
- **Гонки снятия/результата:** снятие «Сохраняем…» и появление результатного тоста могут попасть в один React-батч или в соседние — допустимый микроскопический фликер, не обрабатываем (решение 14.09).

## 5. Что сознательно НЕ строим

- Опцию произвольной длительности (`duration`) для любых тостов — нет ни одного потребителя.
- Конвертацию `loading` → результат в одном тосте.
- Индикатор для не-расписаний (записи/справочники/фото).
- Изменения текстов/таймингов существующих тостов результата.
- Отдельную a11y-семантику прогресса (`aria-busy`, прогрессбар) — YAGNI.

## 6. User Scenarios (каждая → e2e)

- **S1. Создание занятия.** Админ создаёт занятие на /schedule: во время запроса в стеке тостов виден «Сохраняем…» со спиннером; после успеха тост исчезает, следом появляется «Создано: …». (e2e: перехват API с задержкой)
- **S2. Изменение занятия.** Админ меняет существующее занятие (перенос перетаскиванием или правка в модалке): на время update-мутации виден один «Сохраняем…», по завершении он исчезает. (e2e идёт через правку в модалке — устойчивый путь; сам drag уже покрыт существующими e2e переноса)
- **S3. Параллельные операции.** Несколько мутаций с перекрытием (например, второе создание стартует, пока первое ещё в полёте): тост «Сохраняем…» всегда один и гаснет только после завершения последней.
- **S4. Ошибка сервера.** Сервер отклоняет создание: «Сохраняем…» исчезает, появляется тост ошибки; зависшего индикатора нет.
- **S5. Удаление с отменой.** *(Актуализировано #286, 18.09: удаление занятия переведено на общий отложенный пайплайн и **больше не идёт через mutation-key расписания** — «Сохраняем…» на deferred-удалении отсутствует; undo-тост «Удалено. Отменить» (5 с, кольцо) появляется сразу, commit по таймеру окна тихий. Прежняя формулировка «„Сохраняем…“ на время удаления, затем последовательно тост» устарела.)* Админ удаляет занятие: карточка исчезает сразу, в стеке — undo-тост с кнопкой отмены; «Отменить» возвращает карточку, по истечении окна идёт commit.

## 7. Тест-план

- **Unit:** UIContext (D1: вид `loading` без таймера, `hideToast` снимает, дефолты остальных видов не тронуты), ToastContainer (D5: спиннер `aria-hidden`, нет кнопки закрытия, testid; D5a: `loading` виден при переполнении стека), хук D2 (один тост / снятие по settle при успехе и ошибке / `paused` считается незавершённым / новая пачка / cleanup при размонтировании), Topbar (чипа нет, guard жив).
- **E2E (решение юзера 14.09 — все 5 сценариев):** S1–S5 из §6. Один общий хелпер задержки API (`page.route` на мутационные эндпоинты активностей с задержкой фулфилмента ~1.5 с) — им достигается устойчивая фиксация перехода «Сохраняем…» → результат. S3 — два создания с перекрытием (второе стартовать, пока первое в полёте); S2 — через правку в модалке; S4 — отклонение запроса перехватом.
- **Visual:** без новых базлайнов (см. §4); прогон visual-набора на регресс после удаления чипа.

## 8. Definition of Done

- Плашки «Сохраняем…» в Topbar нет ни в одном состоянии; при мутациях расписания в общем стеке живёт тост «Сохраняем…» (спиннер, без таймера, без кнопки закрытия).
- Вид `loading` — общий механизм тост-системы, документирован в спеке, покрыт unit-тестами.
- Guard beforeunload при незавершённой мутации работает как раньше.
- Все сценарии S1–S5 покрыты e2e (RED-GREEN-REFACTOR); unit-набор зелёный; visual-набор зелёный.
- Тесты чипа удалены/переписаны (D7), висячих ассертов на `[role="status"]` чипа нет.
