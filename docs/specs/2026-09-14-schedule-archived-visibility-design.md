# Спека #267: занятия архивированных мастеров/локаций в расписании

## Контекст

Бизнесу нужно видеть занятия, оставшиеся на архивированных мастерах и локациях (сверка прошлых недель: увольнение в середине недели — занятия числятся, но в сетке их нет). Данные не теряются: API занятий фильтрует только по датам (`backend/src/api/v1/activities.py:59-77`) и возвращает занятия архивных сущностей. Занятия исчезают на рендере — цепочка скрытия из четырёх слоёв:

1. Справочники для расписания приходят только активными: `ScheduleDataContext` зовёт `useMastersRaw`/`useServicesRaw`/`useLocationsRaw` без параметра статуса (~строки 100–102); локации/услуги на бэке по умолчанию отдают `active`, мастера — только действующих по своей природе. Сырые и преобразованные хуки справочников делят одни ключи React Query (сознательный дедуп — один запрос на страницу), и на этих ключах сидят посторонние потребители: фильтры записей (`BookingFilters`), меню, карточка клиента.
2. Сборка сетки выбрасывает сироту: `frontend/admin/lib/buildSchedule.ts` — `if (!master || !service || !location) continue;` — карточка не строится вовсе, без лога.
3. Инициализация фильтров сеет только активные id (`ScheduleDataContext` ~115–126, `setFilterMasterIds`/`setFilterLocationIds`).
4. Колонки DayView строятся из тех же списков справочников (`DayView.tsx` ~195).

Ландшафт после влития #266 (PR #269, `bf6877f`):

- `/api/v1/masters` и `/masters/all` — read-only view «действующие мастера» (`backend/src/schemas/master.py`: проводные поля `id`(=staff_id), имена, `specialty`, `color`, `avatar_url`, `sort_order`); параметра `status` нет, архивность в ответе не отдаётся («archived — the list only ever returns acting masters»). Архивная masters-строка хранит имя/специальность/цвет (#266 D7).
- `/locations/all` и `/services/all` имеют параметр `status` (`active`/`archived`/`all`, по умолчанию `active`); в ответах есть вычисляемое `archived: bool` (паттерн #207 §3.1, `backend/src/schemas/location.py`, `service.py`).
- user.settings: `GET/POST/PUT/PATCH /api/v1/user-settings`, плоские snake_case ключи, по строке на пользователя (`backend/src/models/user_settings.py`); фронт маппит в camelCase (`UserSettingsContext.tsx`, `DEFAULT_SETTINGS` :23–28, при отсутствии строки — авто-POST).

## Цель

Занятия архивированных мастеров, локаций и услуг видны в расписании (сетка недели, день, карточки) с явной меткой архивности; видимость архивных мастеров и локаций регулируется двумя переключателями в попапе фильтров topbar с сохранением в user.settings; архивные услуги видимы всегда.

## Отличия от текста issue

Issue написана 10.09, до влития #266 — три поправки:

1. Issue предполагала «бэкенд уже умеет `status=all`» для мастеров и «изменений API не требуется». После #266 у `/masters/all` параметра нет и архивность не отдаётся. Решение (юзер, 14.09): расширить `/masters/all` параметром `status` + вычисляемым полем `archived` (вариант «брать из `/staff`» отвергнут: календарь не должен зависеть от формы кадрового справочника).
2. Issue рекомендовала «карточки вне фильтров, всегда видимы». Решение юзера (14.09): два отдельных чекбокса — архивные мастера показываются по умолчанию, архивные локации скрыты по умолчанию, состояния хранятся в user.settings. Для услуг переключателя нет — видны всегда.
3. e2e-сценарий решено добавить отдельным файлом, а не в `archive-restore-parity.spec.ts` (тот остаётся про справочники).

## Решения (из диалога G1a)

### D1. API: `/masters/all?status=…`

- На `GET /api/v1/masters/all` добавляется опциональный параметр `status`: `active` (по умолчанию) / `archived` / `all` — тот же контракт, что у `/locations/all` и `/services/all` (переиспользовать `ArchiveStatus`). Пагинированный `GET /api/v1/masters` не меняется (потребители — дропдауны/таблица — ждут только действующих). Параметр заводится именно на `/all`: внутренний запрос в `backend/src/services/master.py` обслуживает оба маршрута, его ветка статуса по умолчанию обязана сохранять «только действующих» для пагинированного.
- В `MasterViewResponse` добавляется вычисляемое поле `archived: bool` (= не активный мастер), по паттерну `archived` у локаций/услуг (#207 §3.1). Изменение аддитивное — существующие потребители не ломаются.
- Значение `archived` параметра в #267 потребителя не имеет (расписание использует `all`) — оставлено для симметрии контракта; в тестах проверяются разбор параметра и 422 на неверное значение.
- Поправка к #266 D8 (фиксируется здесь): формулировка «GET /all — действующие мастера» уточняется до «по умолчанию — действующие; `status=all|archived` — для сборки расписания (#267)». «Только чтение» сохраняется. Клиентский сайт (#48) продолжает получать дефолт — только действующих.
- Следствие для тестов: устаревший `endpoints.test.ts:1686` (`getAllMasters({status:'all'})`) снова становится актуальным — сверить в IMPL.

### D2. user.settings: два переключателя

- Новые булевы ключи (плоские, snake_case, в ряд с существующими): `show_archived_masters` — по умолчанию **true**; `show_archived_locations` — по умолчанию **false**. Решение юзера: разные дефолты — кейс «уволен в середине недели, сверяем прошлую неделю» закрывается сразу, а архивных локаций в сетке по умолчанию не видно, чтобы не захламлять.
- Бэкенд: две колонки с server_default (миграция проставляет дефолты существующим строкам), поля во всех схемах user_settings (Create/Response/Update/Patch).
- Фронт: маппинг в `showArchivedMasters`/`showArchivedLocations` в `UserSettingsContext`, добавить в `DEFAULT_SETTINGS`. Точек маппинга в контексте три (провод → внутренний вид, внутренний вид → API, частичный PATCH) — пополняются все три. При отсутствии новых ключей в localStorage-кэше прошлой сессии или в серверной строке применяется дефолт из этого пункта: «первый кадр» до ответа GET рендерится с дефолтами (мастера показываются), а не как «выключено».
- Источник истины — серверные настройки; переключение чекбокса сохраняется через штатный `updateSettings` и переживает перезагрузку и другие устройства.

### D3. Данные расписания

- Запросы справочников для расписания получают **собственные ключи React Query**, не общие с `useMasters`/`useServices`/`useLocations`: на общих ключах `status=all` утёк бы архивным строкам в фильтры записей, меню и карточку клиента. Цена — три дополнительных лёгких запроса при входе на расписание; инвалидация по префиксу (`['masters']`, …) достаётся обоим наборам ключей.
- Контекст при этом отказывается от вторых (преобразованных) хуков: полный список приходит один, активный срез для опций MultiSelect и инициализации `filterMasterIds`/`filterLocationIds` контекст производит сам. Полный список идёт в `buildAdminSchedule` и доступен из контекста (нужен для шапок архивных колонок, D8).
- Ограничение «голого списка» (BareListLimit, ~1000 строк) действует и на `status=all`; при текущих объёмах справочников оно недостижимо, превышение всплывает как ошибка запроса — пагинацию в v1 не делаем.

### D4. Сборка сетки без дропа

- `buildAdminSchedule`: карточка строится и для архивной сущности (по данным полного списка); DTO дополняется флагами `masterArchived` / `serviceArchived` / `locationArchived` (из поля `archived`/`is_active` элементов списков).
- Молчаливый `continue` сохраняется только для отсутствующей строки справочника (FK-сирота; при целостности не случается) — карточку без имени строить не из чего.

### D5. Гейты видимости (единая точка)

В `ScheduleDataContext`, до сборки индекса, занятие проходит гейт:

- услуга — проходит всегда;
- мастер — активен ИЛИ `show_archived_masters` включён;
- локация — активна ИЛИ `show_archived_locations` включена.

Карточки, прошедшие гейт архивности, **обходят фильтр по id**: фильтр `filterMasterIds`/`filterLocationIds` включающий и по умолчанию содержит всех активных — архивные карточки в его списках не состоят и без этого правила отбрасывались бы им до отрисовки (ломало бы S1/S4). Фильтр по id применяется только к занятиям активных сущностей.

Следствия: карточка, у которой архивны и мастер, и локация, видна только при обоих включённых переключателях; гейты действуют одинаково на неделю и день; переключение чекбокса меняет сетку мгновенно. Гейт читает user settings через `useUserSettings` — провайдер настроек обёртывает дерево расписания. Архивация, случившаяся при открытом расписании, подхватывается при следующем рефетче справочников (инвалидация/SSE) — realtime-пуш не требуется.

### D6. Переключатели в topbar

- В попапе фильтров topbar (`Topbar.tsx`: MultiSelect мастеров :225–242, локаций :243–250) в каждом дропдауне под списком — футер-строка с чекбоксом «Показывать архивные» (мастеров / локаций соответственно; механизм — проп футера в `shared/MultiSelect.tsx`, футер вне скроллируемого контейнера списка).
- Чекбоксы не входят в список сущностей и в выбор фильтра — это гейты видимости (D5), их значения живут в user.settings (D2).

### D7. Визуальная метка

- Карточка (`ActivityCard`): при любом из трёх флагов архивности — приглушение (opacity) и одна пилюля «Архив» (паттерн готового `StatusBadge` + конфиг-мапа стилей). Бейдж один независимо от числа архивных сущностей в карточке. Приглушение обязано сохранять читаемость: контраст итогового (после opacity) цвета текста с фоном карточки — по WCAG 1.4.3, значение opacity выбирается с этой проверкой. Бейдж несёт aria-label с перечнем архивного: «Архив: мастер» / «Архив: мастер, локация» — для этого DTO и хранит три отдельных флага (потребители: бейдж — «хоть один», aria-label — перечень).
- DayView: шапка архивной колонки — приглушённая, с той же пилюлей (проверка контраста — та же).

### D8. Колонки DayView

- Режимы «по мастерам» и «по локациям»: колонки активных — как сейчас (с учётом выбора фильтров). Архивная колонка мастера/локации добавляется после активных, приглушённая, при одновременном условии: её переключатель включён И на видимый день есть ≥1 занятие, прошедшее гейты (D5). В дни без занятий колонки нет. Порядок нескольких архивных колонок — по общему правилу сортировки справочника (sort_order, имя). Шапка строится из полного списка справочников, доступного контексту (D3).
- Архивные колонки живут **вне** перемещаемого и сохраняемого набора колонок: не передаются в хук переупорядочивания, не пишутся в `column_order_*`, для локаций не участвуют в `reorderLocations` — иначе id архивной колонки попадал бы в персональный порядок и не восстанавливался бы при следующем входе.
- Архивные колонки — не цели переноса: dnd занятия на них отключён, иначе бросок отправлял бы на бэкенд перенос на архивную сущность, получал 422 `MASTER_NOT_ACTIVE` и молча откатывался.
- В выбор фильтра архивные колонки не входят — фильтр-идентификаторы по-прежнему только активных.

### D9. Тестирование

- Unit: `buildAdminSchedule` — флаги архивности, отсутствие дропа архивной сущности, дроп FK-сироты.
- Integration: гейты D5 и обход фильтра в `ScheduleDataContext` (в духе существующего `__tests__/schedule/ScheduleDataContext.test.tsx`).
- Backend (pytest): `status` на `/masters/all` (разбор параметра, 422 на неверное значение; `archived` отдельного теста не имеет — потребителя нет), поле `archived`, неизменность пагинированного `GET /masters`, новые поля user_settings (дефолты, PATCH).
- E2E: новый файл `frontend/admin/e2e/schedule-archived-visibility.spec.ts`, 7 тестов — по сценарию ниже (инфра per-test seed reset #252; мастер/локация/услуга + занятие создаются через API, затем архивация; занятия фиксируются внутри навигируемой недели — дефолт фабрики «текущий момент UTC»). Инфра reset дополняется сбросом `user_settings` (сейчас таблица переживает reset: включённый одним тестом чекбокс делает недетерминированными S2/S5 у всех последующих) и чистым localStorage перед тестом.

## User Scenarios (→ e2e)

Каждый сценарий = один тест в `schedule-archived-visibility.spec.ts`:

1. **S1. Мастер архивирован** → его занятия видны в сетке сразу (дефолт `show_archived_masters=true`): карточка с бейджем «Архив», приглушена, имя и цвет мастера на месте.
2. **S2. Локация архивирована** → по умолчанию её занятия скрыты (сегодняшнее поведение); включение чекбокса «показывать архивные» у локаций показывает карточки и добавляет колонку в DayView «по локациям».
3. **S3. Услуга архивирована** → её занятия видны всегда; чекбоксы мастеров/локаций на них не влияют; карточка с бейджем.
4. **S4. Фильтр по активному мастеру** (гейт мастеров включён) → архивные карточки остаются видимы — вне фильтров.
5. **S5. Перезагрузка страницы** → состояния обоих чекбоксов восстановлены из user.settings.
6. **S6. DayView «по мастерам»** → колонка архивного мастера есть только в дни с его занятиями; в дни без занятий колонки нет.
7. **S7. Архивны мастер и локация одновременно** → карточка видна только при обоих включённых чекбоксах; при выключенном любом из двух — скрыта.

## Границы (не делаем в #267)

- Периоды работы / показ архивных только на прошлых неделях — дат трудоустройства в модели нет.
- Участие архивных в выборе фильтра (архив фильтруется только гейтом, не чекбоксами сущностей).
- Отдельный переключатель для услуг — архивные услуги видны всегда.
- Создание/перенос занятий на архивные сущности — закрыто #266 (`MASTER_NOT_ACTIVE`); здесь только чтение.
- Клиентский сайт `frontend/web` (свой `buildSchedule`) — территория #48.
- Страницы справочников — архивирование там уже работает.

## Правки domain-rules (тем же коммитом)

- `docs/domain-rules/activities.md` — новое правило: занятия архивных сущностей не исчезают из расписания; видимость архивных мастеров/локаций регулируется user.settings, архивные услуги видимы всегда.
- `docs/domain-rules/user_settings.md` — два ключа `show_archived_masters` (по умолчанию true) и `show_archived_locations` (по умолчанию false).
