# Спека: единая модель посетителей — аноним как визит (issue #257, переформат)

Дата: 2026-09-16. Статус: G1b принят юзером (панель 5/5, файндинги внесены).
Переформатировано из исходного запроса #257 («показывать N анонимных мест вместо "Нет посетителей"») — текстовая заплатка superseded: проблема решается структурно, удалением dual-модели «счётчик + строки».
Решение зафиксировано в дизайн-диалоге с юзером 16.09 (все гейты G1a пройдены).

## Проблема

Сейчас в записи сосуществуют два представления «безымянных мест»:

1. **Счётчик** `records.anonym_visits` — число. Его крутит степпер в шапке карточки
   (`RecordHeader.tsx`), оно участвует в `seats = len(visits) + anonym_visits`.
   В таблице «Посетители» счётчик невидим → исходный баг #257: при `visits=[]` и
   `anonym_visits>0` показывается «Нет посетителей», хотя места заняты.
2. **Настоящие визиты без посетителя** (`visits.visitor_id = NULL`) — уже легальны и
   работают end-to-end: черновик с пустым именем сохраняется как анонимный визит
   (e2e `unified-rows.spec.ts:451` «scenario 11», плейсхолдер «Аноним»), резолв
   трёх режимов в create-пути (`record.py:474–488`: по имени / по ID / анонимный).

Два пути к одному понятию дают весь класс дефектов: врущее пустое состояние (#257),
невозможность конвертировать анонимное место в именованное одним действием (добавление
именованного на полном занятии ловит 409, `visit.py:94` не уменьшает счётчик),
невозможность задать тариф/цену/статус анонимному месту (у числа нет данных).

## Решение (утверждено юзером)

**Каждое место = визит. Аноним = визит с `visitor_id = NULL`. Счётчик удаляется
целиком, без слоя совместимости** (прод-данных нет — тестовая база пуста, 0 записей).

### D1. Доменная модель
- Место в записи = запись в `visits`. Именованный визит ссылается на visitor;
  анонимный — `visitor_id = NULL`. Имя и возраст живут на visitor — аноним не имеет
  ни того, ни другого (возраст без имени невозможен и не вводится).
- Тариф, цена, кастомная цена, статус — поля визита: у анонима они **настоящие и
  редактируемые** (механизм `onPatchVisit` уже построен, `RecordVisitsTable.tsx:125`).

### D2. Удаление счётчика (breaking; чек-лист потребителей)
- Backend: колонка `models/record.py:25`; поля из 4 схем `schemas/record.py:54,74,87,98`
  (RecordBase/Create/Update/Patch); ветки счётчика в `services/record.py`
  (create:465,500; update:590–625; patch:660–698) и **сборщик ответа
  `_to_response` (`services/record.py:100` — `anonym_visits=record.anonym_visits`;
  без правки — AttributeError на каждом чтении записи)**;
  view-сортировка «guests» (`services/record.py:351`) — это **SQL-выражение в
  ORDER BY** (`Record.seats - Record.anonym_visits`): после drop колонки выражение
  падает при построении запроса; замена — коррелированный подзапрос
  `count(visits where visitor_id IS NOT NULL)` (или питонья сортировка, если
  подзапрос дорог для сортировки списка — решить в плане по факту объёма списка).
- `packages/api-client`: поле из RecordResponse (`schemas.ts:388`) + `schemas.test.ts`;
  `endpoints.ts` — правки типов. Путь создания записи во фронте шлёт
  `anonym_visits: input.seats` (`useRecordMutations.ts:171`) — **заменить на
  анонимные элементы в массиве `visits`** (элементы без `visitor_id`), иначе
  новые записи будут терять безымянные места.
- Frontend admin (исходники): `RecordHeader.tsx` (степпер), `RecordVisitsTable.tsx`
  (проп `anonymVisits`, `anonymInput`), `ActivityDetailsModal.tsx:160`,
  `ClientTab.tsx`, `ClientRecordTab.tsx`, `useRecordMutations.ts:328`
  (`updateAnonymVisits` → удалён). `RecordSummary.tsx` и `ClientLabelById.tsx`
  содержат только слово «аноним…» без поля — проверить при правке, поля не касаются.
- Производный счётчик в UI: `visits.filter(v => v.visitor_id === null).length` —
  визиты карточки уже загружены, отдельных запросов не нужно.
- **Полный инвентарь регенерировать строгим grep (`anonym_visits|anonymVisits`)
  первым шагом IMPL**: поле встречается в ~21 frontend-файле (включая тестовые
  `RecordHeader.test.tsx`, `ClientTab.integration.test.tsx`, `mockData.ts:154`,
  `clientRecordTabSetup.ts:20`, `recordsColumns/RecordsTable/RecordsContext/
  ClientQuickCard/ClientsIntegration/recordsTimeParity/useDeleteRecord/
  useReactQueryHooks/recordCacheSync/ActivityDetailsModal` тесты) и ~7 backend-тестах
  + `tests/conftest.py` + одна alembic-версия. Чистый разрыв = compile-error
  радиус: пропущенный потребитель падает громко и рано — инвентарь и есть защита.
- frontend/web чист (grep пуст) — web-сценарий (#48) попадёт в чистую модель сразу.

### D3. `records.seats` остаётся
Денормализация нужна: `check_activity_capacity` суммирует колонку одним запросом по
всем записям активности (`record_visits.py:106–113`). Формула упрощается:
`seats = len(визитов)` (`recompute_record_seats`, `record_visits.py:43` — член
`anonym_visits` исчезает; то же в update/patch:622,698). Инвариант от дрейфа:
`seats` меняется ТОЛЬКО через точки пересчёта (create/update/patch записи,
`VisitService.create/delete`) — перечислить их в плане и покрыть тестом
«seats == len(visits) после каждой мутации».

### D4. Статус записи — полное участие (вариант A, выбор юзера)
Правило не меняется (`visit_status.py:39–45`: any visited > all missed > all
cancelled > waiting, 0 → waiting) — меняется состав входа: **все** визиты, включая
анонимные. Новые анонимные визиты создаются в статусе `waiting` (дефолт
`record.py:712`). Следствия:
- Анонимной строке можно поставить «пришёл» — запись честно станет «Пришли».
- Видимое изменение на старых данных: «все именованные missed/cancelled + анонимы»
  после миграции остаётся MISSED/CANCELLED (см. D5), но новые записи с анонимами
  живут по единому правилу без исключений.
- **Каскад отмены — новая логика**: сегодня «отменить запись» = отменять визиты по
  одному, каскада нет. Вводится: действие отмены записи отменяет все её визиты,
  включая анонимные (работа на уровне визитов, не записи — `docs/domain-rules/
  records.md:75`: статус записи никогда не ставится независимо). Зафиксировать в
  domain-rules и покрыть тестом.

### D5. Миграция
Разовое разворачивание счётчика: для каждой записи `anonym_visits = N` создать N
визитов `visitor_id = NULL`, `price = 0`, `tariff_id = NULL`, **статус = текущий
статус записи** (не waiting!). Обоснование: наследование сохраняет и статус записи,
и занятость мест в capacity — иначе запись в статусе missed/cancelled после
разворачивания waiting-визитов «воскресла» бы в WAITING и снова занимала места
(`active_record_filter` считает waiting/visited). Затем — drop column.
Порядок операций строго: (1) создать визиты с наследованным статусом → (2)
пересчитать `seats = len(визитов)` → (3) drop column; обратный порядок даёт
неверные seats (двойной счёт или потеря счётчика).
Это первая дата-миграция проекта (18 существующих — schema-only; FK в
миграционном соединении отключены, `alembic/env.py:68–88`) — паттерн: один
`op.bulk_insert` батчем, без построчного ORM.
Фактически миграция схемная: сид-конвейер данных со счётчиком не создаёт.
Дев-база рождается скриптом `backend/scripts/recreate_dev_db.sh` (drop → alembic
upgrade head → `src/seed/seed.py`); seed-записи r1–r6 (`seed.py:432–437`) поле
`anonym_visits` не задают (0 по умолчанию), e2e-данные с анонимами создаются
фабриками самих тестов и стираются каноническим RESET_SQL
(`fixtures/seed-reset.ts`, короткие сид-ID r1..r6 переживают сброс — все без
анонимов). Найденная копия `~/dev/opencode/workspace/memo/memo.db` пуста и старой
схемы — артефакт вне конвейера. Правило наследования статуса — инвариант на
будущее (первая же запись с анонимами на проде).

### D6. Степпер шапки
+1/−1 = создание/удаление одного анонимного визита (POST/DELETE `/visits` с
`visitor_id: null`); capacity-проверка штатная, внутри `VisitService.create/delete`
— это живой путь сегодняшнего «+ Добавить» (+1 место к занятым), отдельный паттерн
сброса seats из `RecordService.update/patch` не нужен (тот — для замены массива).
Массовый ввод мест остаётся в форме бронирования (US1: N строк-заготовок), степпер
— только поштучно.

### D7. Конвертация анонима в именованного
В строке «Аноним» — инлайн-ввод имени (+возраст), механика черновиков уже в таблице.
Сабмит = `createVisitor` + `PATCH /visits/{id} {visitor_id}` — один точечный вызов,
без пересоздания массива визитов записи, места не меняются → 409 невозможен даже на
полном занятии. При ошибке API строка возвращается в состояние «Аноним».
`VisitPatch` уже поддерживает `visitor_id` (`schemas/visit.py:37`).

### D8. Деньги
`totalCost` и «к оплате» начинают включать цены анонимных визитов (сегодня счётчик в
деньгах не участвует вовсе). Это намеренное поведенческое изменение (юзер: «хотел бы
иметь возможность менять тариф и цену» — иначе оно бессмысленно). Оплаты живут на
записи (`deletion.py:614`) — конвертация/удаление анонима оплат не двигают.

### D9. UI-детали
- Анонимные строки отображаются в общей таблице (уже работают, сценарий 11);
  плейсхолдер «Аноним», возраст — прочерк. Порядок строк — наблюдение, не
  требование: колонки сортировки в модели нет, анонимные строки естественно
  оказываются в хвосте по порядку создания; сортировку не вводим и не тестируем.
- Пустое состояние «Нет посетителей» — только при `visits=[]` (истинный ноль мест);
  врущее состояние исчезает структурно, текст не меняется.
- `isReadOnly` глушит конвертацию, удаление и правку анонимных строк так же, как
  именованных. Зона прав — правка визитов записи.

### D10. API-контракт (breaking) и порядок
- `anonym_visits` исчезает из RecordCreate/RecordUpdate/RecordPatch/RecordResponse.
  Клиенты считают производное из `visits` (поле в ответе остаётся).
- Создание записи: массив `visits`, незаполненные места — элементы без `name` и
  `visitor_id` (режим уже поддержан, `VisitItem` несёт `tariff_id/price/status`).
- Разрыв без депрекейшн-окна — осознанное юзер-решение для внутреннего API с одним
  потребителем; риск закрыт исчерпывающим чек-листом D2.
- Порядок с #134 (дедуп VisitStatus, Ready to IMPL, тот же район
  `domain/visit_status.py`) — деталь порядка слияния, не архитектурная зависимость;
  уточнить в плане (IMPL после мержа #134 — рекомендация).

## User Scenarios (основа — сценарии юзера, 16.09)

1. **US1 · Админ, новый клиент.** Бронирование по телефону: активность, телефон,
   имя, N мест → N строк-заготовок; заполненные (имя+возраст) — именованные визиты,
   незаполненный хвост сохраняется анонимными визитами с тарифом по умолчанию.
   E2E: booking-flow спека (существующая) + кейс «хвост уходит в анонимов» в новой
   `anonymous-visits.spec.ts`.
2. **US2 · Админ, существующий клиент.** Выбор сохранённых посетителей клиента в
   строки + ввод новых; незаполненный хвост — анонимные визиты.
   E2E: та же booking-спека, кейс выбора сохранённых.
3. **US3 · Конвертация.** В записи есть строка «Аноним» (в т.ч. активность заполнена
   до предела) — админ вписывает имя → визит становится именованным; места и
   «к оплате» не меняются, 409 не возникает.
   E2E: `anonymous-visits.spec.ts` (конвертация на полном занятии).
4. **US4 · Правка денег анонима.** Смена тарифа/цены анонимной строки → totalCost и
   «к оплате» пересчитываются. E2E: `anonymous-visits.spec.ts`.
5. **US5 · Удаление анонима.** Удаление строки освобождает место, seats и шапка
   пересчитываются. E2E: `anonymous-visits.spec.ts`.
6. **US6 · Статус.** Анонимной строке ставится «пришёл» → запись «Пришли»; отмена
   записи гасит анонимные визиты. E2E: `wave6-record-status-derived.spec.ts`
   (расширение) + unit на compute.
7. **US7 · Миграция.** Запись со счётчиком `anonym_visits = N` после миграции имеет
   N анонимных визитов, статус и занятость мест не изменились.
   Тест: unit на функцию разворачивания (наследование статуса) + штатный alembic
   upgrade-тест; E2E на сид-копии не нужен (базы пусты — покрыть синтетикой в unit).
