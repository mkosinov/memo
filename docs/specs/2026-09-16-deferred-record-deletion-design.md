## 1. Проблема и поправка предпосылки issue

Issue #285: удаление записи сегодня мгновенное (`deleteMutation` + тост «Запись удалена», 409 → DeleteDialog), для визитов и оплат уже работает отложенное удаление с undo-тостом (`PendingActionsContext`). Хочется тот же pipeline для записей.

Два факта, определяющих решение (скаут 16.09):

- **«Dry-run» бэкенда разрушающий:** `DELETE /records/{id}` без тела при пустом списке зависимостей **реально удаляет** запись и возвращает 204; 409 с деревом зависимостей возвращается только когда зависимости есть (`backend/src/api/v1/records.py:191-199`). Отдельного не-разрушающего предпросмотра нет — значит «проверка 409 до enqueue» существующими средствами невозможна, а undo требует, чтобы в окне 5 секунд сервер был не тронут.
- **Реверс решения Addendum 13:** домен-правила `docs/domain-rules/records.md:126` фиксируют «Delayed delete: REMOVED — old 5-second setTimeout + undo toast replaced by DeleteDialog dry-run flow». Спека #285 **осознанно возвращает** отложенное удаление записей (решение юзера 16.09) — но не как возврат старого bespoke-механизма, а как подключение к общему `PendingActions`-пайплайну, на котором уже живут визиты и оплаты.

## 3. Решения

**D1 — бэкенд: явный dry-run-флаг (решение юзера 16.09 — подход B; имя флага возвращено решением юзера, rev4).** Режим выносится наружу аргументом вызывающего: `DELETE /api/v1/records/{id}?dry_run=true` — **чистый предпросмотр, никогда не изменяет строки**: `collect_dependencies` → пусто → **204 без удаления**; непусто → **409** с тем же телом `{detail, dependencies}`; записи нет → 404; комбинация `dry_run=true` + тело `resolutions` → **422** (явно запрещённая комбинация). **Голый DELETE упраздняется (rev7, решение юзера).** `DELETE /records/{id}` без флага и без тела → **422** `{"detail": "expected_state_required"}`; DELETE с телом без `expected` (не dry_run) → та же 422. Каждое реальное удаление обязано нести заявленное состояние: чистое — `{"expected": {}}`, каскадное — `{resolutions, expected}`; предпросмотр — только через `?dry_run=true` (тела не требует). Полурурушающая ветка «execute-if-clean» у записей исчезает: контракт записей сознательно отклоняется от общего паттерна (у 5 архивных сущностей no-body DELETE остаётся) — отклонение фиксируется в домен-правилах (D8). Бывший e2e-гард `records.spec.ts:915-967` (bare DELETE → 409) переписывается под новый контракт (голый → 422; preview-409 уже покрыт тестами dry-run) — ломающее изменение, одобрено юзером (D7). Терминология (rev4, решение юзера): имя `dry_run` — у настоящего чистого dry-run (новый флаг); легаси-метка «dry-run» на голом DELETE переименовывается (см. D8) — она описывала «dry-run только при конфликте», что по смыслу не dry-run. Параметр объявляется в современном стиле `Annotated[bool | None, Query(description=...)] = None` (FastAPI ≥0.95, попадает в OpenAPI; выбор query-параметра — de facto конвенция: RFC 9110 dry-run-вариантов DELETE не стандартизует). **Почему не `If-Match`/ETag (rev8, панель best-practices):** канонический optimistic-механизм для DELETE — `If-Match` (RFC 9110 §13), но он opaque — не выражает «какие именно строки зависимостей пользователь подтвердил», тогда как `expected`-тело переносит ровно тот снапшот, который диалог/окно показали юзеру, а 409-ответ возвращает живое дерево в той же форме для повторного подтверждения; per-resource ETag над множеством зависимостей потребовал бы инфраструктуру версионирования без выигрыша для этого UX. Ветке dry-run нужен **явный probe существования записи** (тот же repository-get, что в execute-пути): `collect_dependencies` на отсутствующем id возвращает пустой список, и без probe ветка отвечала бы 204 вместо 404.

**Механизм гонки — expected-сверка (rev5/rev6, решение юзера): commit отложенного удаления всегда несёт тело с ожидаемым состоянием.** DELETE с телом расширяется аддитивно: `{resolutions?, expected}`, где `expected` — **id-множества зависимостей per-энтити** (rev6: id, не счётчики — сверка ловит и обмен зависимости при равном счётчике; у чистого пути — пусто; ок пользователь даёт окном отмены или диалогом, D2/D3). Порядок обработки: существование → `collect_dependencies` → **сверка `expected` по id-множествам** → расхождение → **409** `{detail: 'stale_dependencies', dependencies: <текущее дерево с items>}` (форма 409-пейлоада уже парсится в `ApiError.dependencies`) → и только затем валидация `resolutions` → исполнение (пустые `resolutions` + пустые зависимости = обычный hard delete). Семантика сверки — **subset** (сведение с планом Task 2, rev8): 409 только если на сервере есть зависимости, **отсутствующие в `expected`** — появление сверх подтверждённого и обмен ловятся (один визит удалён, другой добавлен — счётчик совпал бы, id-множество нет); зависимость, исчезнувшая за окно, commit не блокирует (её чужое удаление не нарушает цель операции, equality делал бы commit падающим без причины). **Auto-зависимости (`record_tags`, `auto=True`) из сверки исключаются** (панель rev8): они не показывались в dry-run/диалоге (нет в `items`), expected их не содержит — без исключения каждое каскадное удаление падало бы 409. Механизм покрывает **оба** пути удаления записи. Пейлоад dry-run/409 для записей дополняется per-dep `items` (id + человекочитаемая метка) — см. D9.

**Единый контракт отложенного удаления (rev8, решение юзера 17.09).** Механизм expected-сверки — общий контракт отложенного удаления; **критерий подключения сущности — наличие серверных зависимостей (запись в FK_MATRIX), а не «не-архивность» и не само undo-окно** (панель wave 2, простота: у листовых сущностей сверка нечему расходиться — expected был бы мёртвым механизмом). Снапшот `expected` строится из состояния на экране: источник — **серверное дерево зависимостей, которое пользователь подтвердил** (диалог/окно; у записей — dry-run/диалог, D3); per-entity расширение `items` — предварительное условие подключения сущности к контракту (без него expected не из чего строить). Развёртывание: записи — эта спека (ядро IMPL #285: зависимости visits/payments/record_tags есть); занятия — #286 (в FK_MATRIX нет — серверных зависимостей нет; конверсия = пайплайн + undo + D4-обработка, без expected — уточнение их спеки); визиты — #297 и оплаты — #298 — **листовые (нет в FK_MATRIX, `deletion.py:126-229`; DELETE без тела и без 409 — `visits.py:232-249`, `payments.py:212-228`; коммиты шлют bare DELETE — `useRecordMutations.ts:440-445`, `:471-479`): expected не несут и серверных правок не требуют — их скоуп сводится к наследованию дефолтной обработки ошибок commit (D4) и верификации** (панель wave 2, простота+феасабилити). Расхождение с сервером — не молчаливое игнорирование и не авто-диалог: честная ошибка + предложение обновить (D4, rev8). Конверсия визитов/оплат/занятий — работа их собственных issues; в скоуп IMPL #285 не входит.

**D2 — фронт: чистый путь (без зависимостей) — отложенный.** `useDeleteRecord` перестраивается на отложенную схему (имя хука сохранено; все 3 call sites подключаются к новой схеме — их локальная обвязка и сигнатура onResolve адаптируются). Поверхность ошибок хука — **один механизм, thrown `ApiError`** (rev3): dry-run 409-with-dependencies → call site открывает DeleteDialog как сегодня (**строка не исчезает**); не-409 (404/500/сеть) → существующие catch показывают error-тост, как сегодня (три разные поверхности ошибок не унифицируем); возвращаемый объект мутации контракту не задаётся. Штатный путь: `removeRecord(record)` → `dryRunDeleteRecord(id)` (новая функция api-client, DELETE `?dry_run=true`) → 204: по-ключевой item-level снапшот (D5) → optimistic `removeRecordFromCaches` → `enqueuePendingAction({id: 'delete-record-${id}', message: 'Удалено. Отменить', delayMs: 5000, undo: восстановление снапшота (D5), commit: await resolveDeleteRecord(id, {expected: {}}) + invalidateAfterDelete})`. Инвалидации — только в commit (зеркало `deletePaymentDeferred` :476-478), в момент enqueue — никаких.

**D3 — каскадный путь тоже отложенный (решение юзера 16.09: да).** Подтверждение в DeleteDialog строит `resolutions` как сегодня, но вместо мгновенного `resolveDelete.mutateAsync` — `removeRecordResolved(record, resolutions)`: тот же enqueue с `commit = await resolveDeleteRecord(id, {resolutions, expected: {visits: [...ids], payments: [...ids]}})` — id-множества из `items` дерева dry-run (D9) + `invalidateAfterDelete`, optimistic-удаление + undo-тост; диалог закрывается немедленно (enqueue синхронен). Оба пути удаления записи получают одно окно 5с, одну механику undo и один commit-механизм (expected-сверка, D1) — двух поведений удаления записи нет.

**D4 — обработка ошибки commit — в общем пайплайне (решение юзера 16.09: вариант 2).** В `PendingAction` добавляется `onError?: (err: unknown) => void`; `enqueuePendingAction` оборачивает `commit` в try/catch. Дефолтная обработка (домен-независимая, общий контекст не знает про records): **404 — тихий успех** (DELETE идемпотентен — запись уже удалена конкурентом, цель commit достигнута: ни undo, ни тоста, удаление в кэше остаётся; SSE-инвалидация конкурента к этому моменту уже отрисовала исчезновение — rev8, панель); прочие ошибки → `action.onError?.(err)`, а при отсутствии — `action.undo()` + `showToast('Не удалось удалить. Изменение отменено', 'error')`. **Ветвь `stale_dependencies` (409 expected-сверки, rev8 — решение юзера «честная ошибка + предложение обновить») живёт в onError ПОТРЕБИТЕЛЯ записей, не в общем контексте** (панель wave 2, простота: общий контекст домен-независим, `invalidateEntities(['records'])` — знание records): хук `useDeleteRecord` передаёт `onError` в свои enqueue — `err.status === 409 && err.dependencies` → undo штатно + тост «Не удалось удалить: данные изменились» с действием «Обновить» (инвалидация `['records']`-family — перечитываются списки; канонический `qk.record(id)` не покрыт, но модалка к моменту commit закрыта — снапшот-логика D5). Дискриминатор без расширения `ApiError`: 409-with-dependencies внутри commit — всегда `stale_dependencies` (`has_dependencies` отвечает только голому/dry-run-пути без тела, коммиты тело несут — панель, простота). Тост с «Обновить» — не-undo ветка, живёт 4500мс (дефолт не-undo тостов, `UIContext.tsx:99-104`) — e2e S6 кликает сразу (панель). Действие требует **обобщения action-слота тоста** (панель rev8): сегодня `Toast` хранит только `undo?: () => void`, а текст кнопки «Отменить» захардкожен в `ToastContainer.tsx:50-59` — план (Task 6) добавляет опциональный `action {label, onAction}` аддитивно (undo остаётся для undo-тостов — их lifetime-логика «5с от undoFn» не задевается, S2/S4 безопасны). DeleteDialog автоматически не открываем (редкая гонка — §4). Гонки «undo после commit-fail» нет: undo снимает таймер, commit при отмене не срабатывает вовсе; **undo гейтится и при in-flight commit** (панель, феасабилити: сегодня клик по «Отменить» во время незавершённого DELETE локально воскресил бы строку, которую сервер уже удалил — таймер-запись снимается до `await commit`, §8 DoD «undo не воскрешает сервер-удалённое» переносится в механику). Визиты/оплаты получают обработку без правок своего кода (это чинит их существующий молчаливый unhandled rejection, `useRecordMutations.ts:439-443`). Инвалидации после успешного DELETE — **не-фатальные**: их собственные ошибки не попадают в onError (состояние сервера после 204 авторитетно, undo никогда не воскрешает запись, удалённую сервером; экран сходится по SSE/следующей загрузке). Гонки «undo после commit-fail» нет: undo снимает таймер, commit при отмене не срабатывает вовсе.

**D5 — undo: точечное восстановление по ключам, без broadcast.** Снапшот при клике — item-level по ключам (rev3): `getQueriesData({queryKey: qk.records})` возвращает **полные значения кэшей** (конверт `PaginatedResponse<RecordView>` для таблицы, `RecordResponse[]` для списков клиента/активности — все под одним префиксом `['records', ...]`); из каждого значения, где строка есть, захватываем **сам объект строки** в его исходной форме. Канонический `qk.record(id)` optimistic **не трогается и не снапшотится**: `removeRecordFromCaches` не достаёт до этого ключа (другой префикс — `queryKeys.ts:37` vs `:46`), модалка к моменту клика закрывается навигацией (D6), а commit-инвалидация `qk.record(id)` остаётся как сегодня — снапшот канона был бы мёртвым кодом. Optimistic-удаление убирает строку из захваченных списочных кэшей; **undo: для каждого захваченного ключа берём текущее значение кэша и вставляем захваченную строку replace-by-id** (строка вернулась через refetch — заменяем, дублей нет; пришедшие за окном SSE-обновления не откатываются — восстанавливается одна строка, а не целое значение кэша). Никаких broadcast-вставок через `mapRecordsListCache`: список другого клиента/активности чужую строку не получает, формы не перемешиваются. Серверных вызовов у undo нет — dry-run (D1) гарантирует, что в окне удалять нечего. Инвалидаций при undo нет (как у визитов).

**D6 — навигация ClientTab.** `onDeleteRecord(recordId)` срабатывает в момент клика (сразу после результата dry-run/диалога) — по времени как сегодняшний success-путь; pending-действие переживает unmount модалки (провайдер app-level, §2). Если после перехода в список нажать «Отменить» — строка возвращается в таблицу записей.

## 4. Детали поведения и края

- **Гонка середины окна — expected-сверка (rev5/rev6):** зависимость появилась после dry-run → commit несёт `expected` (id-множества), сервер не находит совпадения → **409 `stale_dependencies`** → дефолтный `onError`: строка вернулась + error-тост, БД не тронута (юнит на api-client подтверждает парсинг 409-пейлоада). DeleteDialog автоматически не открываем — редкий race, повторный клик даст штатный dry-run→диалог.
- **Сеть пропала в окне:** commit-фейл (fetch) → тот же дефолт `onError`.
- **Refetch в окне:** если список перезагрузился до commit, запись вернётся на экран (сервер ещё жив); после commit следующая загрузка чистая. Принятая eventual-consistency схемы визитов/оплат — не чиним.
- **Быстрый повтор того же id (удалил → отменил → удалил):** enqueue дедупится по id — старый таймер снят, новое окно/тост с нуля (как у визитов, `PendingActionsContext.tsx:44-49`).
- **Две разные записи подряд:** два независимых тоста/таймера; лимит стека тостов 5 работает как раньше.
- **Undo и кнопка «×»:** семантика тоста наследуется от #94 D9 без правок — «×» скрывает тост, commit всё равно выполнится; «Отменить» отменяет. Окно/время жизни тоста = 5000 мс (`UIContext.tsx:88-89`) — с `countdownMs` из #94 сходятся без рассинхрона (§9).
- **`total` конверта устаревает на окно 5с:** `mapRecordsListCache` сознательно не правит `total` (инвариант хелпера, `recordCacheSync.ts:36-37`); сегодня этот разрыв закрывался мгновенной инвалидацией, теперь — только в commit. Принято: «Всего N» может расходиться с числом видимых строк до commit; удаление последней строки последней страницы даёт пустую страницу до commit-рефетча. Самокорректируется, явное поведение-изменение против сегодняшнего.
- **Покрытие краёв тестами:** race-ветки этого раздела (409 `stale_dependencies` в commit, 422 на протухших resolutions) покрываются юнит-тестами `onError` и expected-сверки (D7); e2e — S5 (offline) и S6 (гонка середины окна).
