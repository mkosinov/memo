## 1. Проблема и поправки предпосылок

Issue #286: удаление занятия — единственное undo-удаление вне общей отложенной схемы. Сегодня ДВА живых пути удаления:

- **Карточка сетки** (`ActivityCard.tsx:71-93`): режим удаления → клик → guard `deletingRef` + `setTimeout(150ms)` → `deleteActivity(activity.id)` (контекст → `apiDeleteActivity`, 204 blind) → тост, чей «Отменить» **пересоздаёт** занятие через `addActivity` по сырым полям (:78-88) — без записей, без id, фото отвязаны.
- **Модалка деталей** (`ActivityDetailsModal.tsx:206-210`): кнопка «Удалить активность» (`btn-delete-activity`, рендерится безусловно :299-305) → тот же контекстный `deleteActivity` + мгновенный тост «Активность удалена» + `onClose()` — без диалога, без expected, без undo. **BLOCKER wave 1:** под новым контрактом (bare DELETE → 422) этот второй путь ломается молча; спека wave 1 его не учитывала — исправлено (D3 покрывает оба call sites, DoD ассертит оба).

Два факта, определяющих решение (скауты 16–17.09):

- **Каскад занятия разрушает данные безвозвратно.** Сервис (`backend/src/services/activity.py:229-274`, @transactional): собирает `Record.id` по занятию → удаляет `Visit`, `Payment`, `record_tags`, `Record` (все по `record_ids`); фото → `activity_id=NULL` (`:265-267`, SET NULL #194); `activity_tags` и само занятие. Recreate-undo возвращает голую карточку — визиты/платежи/записи потеряны навсегда. 409-условий нет, только 404 (`activities.py:178-193`).
- **У занятия ЕСТЬ серверные зависимости — записи.** `Record.activity_id` — FK `ondelete="CASCADE"` (`models/record.py:19`); визиты/платежи/record_tags — дети записей (`record_id`), у Visit/Payment своего `activity_id` нет (`models/visit.py:20`, `models/payment.py:12`). **Поправка к rev8 #285 (§3/§9) — ПРИНЯТА её rev9 (`80aa34f`, 17.09):** формулировка «занятия — в FK_MATRIX их нет (серверных зависимостей нет)» ошибочна фактологически — в матрице их нет потому, что каскад рукописный в сервисе, мимо deletion-домена; критерий контракта («серверные зависимости») для занятий выполняется **по существу**. #286 исправляет прокси: проводит Activity в матрицу — критерий становится истинным и буквальным. Скоммутировано консистенси-ревьювером: это исправление фактической ошибки, а не ревизия контракта.

Решения юзера (16–17.09, диалог): перевести занятия на общую схему обязательно («5 секунд ничего не удаляем, потом commit»); единый контракт из #285, не лоскутный; expected строится из того, что **показано** пользователю; расхождение с сервером — честная ошибка + «Обновить»; проверка актуальности кэша при клике с сообщением об обновлении карточки; индикатор «Сохраняем…» на deferred-удалении подавлен; e2e-правки в этом issue; depends-on: #94, #285.

## 3. Решения

**D1 — бэкенд: Activity заводится в deletion-домен — матрица + collect + label-билдеры (execution не трогаем).** `FK_MATRIX` дополняется `Activity: [records (cascade, НЕ auto), photos (nullify, auto=True), activity_tags (cascade, auto=True)]` — прямые FK-дети по факту модели (`models/record.py:19`; фото SET NULL #194; activity_tags — link-строки). **Дерево занятия собирается на два уровня (решение юзера 17.09):** collect для занятия берёт прямых детей (записи) и для каждой записи её детей из `FK_MATRIX[Record]` — визиты и платежи (record_tags — auto, исключён; глубже рекурсия останавливается — у Visit/Payment новых не-auto узлов нет). Сухое дерево = три узла с `items`: **records** («{услуга}, {дата}, {клиент|Аноним}» — услуга через `record.activity_id → activity.service_id`, клиент через `client_id`, nullable → fallback; join из того же запроса, без отдельных lookup), **visits** и **payments** — label-билдеры #285 Task 3 переиспользуются как есть (визит «{услуга}, {цена}», платёж «{сумма}, {метод}»). PII-граница #285 D9б — только поля, видимые вызывающему (имя клиента не маскируется для admin — `scope.py:95-106`, `client.py:55-65`). Запись матрицы — **preview-only**: её потребляет только collect (диалог/expected); исполнение остаётся рукописным сервисом без изменений (generic-резолвер для (Activity, photos) не заводится) — закрепляется тестом.

**D2 — контракт DELETE /activities/{id}: полное зеркало записей (#285 rev7/rev8).** (а) `?dry_run=true` (Annotated-стиль, как D1 #285) — чистый предпросмотр: пусто → **204 без удаления**; есть записи → **409** с деревом (три узла с `items`: records/visits/payments); занятия нет → **404** (probe существования — тот же repository-get, без него dry-run дал бы 204 на отсутствующем id); **`dry_run=true` + тело → 422 `invalid_delete_request`** (зеркало #285 D1 — явно, чтобы не оставить неоднозначность). (б) Тело реального DELETE: `{expected: {records: [...], visits: [...], payments: [...]}}` — id-множества per-entity из **подтверждённого пользователем** dry-run-дерева (все три узла; **полный список id** — display-cap 10 в диалоге косметика, фронт шлёт все); **subset-сверка per-entity** (409, когда на сервере есть id ЛЮБОГО из трёх узлов, отсутствующие в expected — ловит и появление записи, и появление визита/платежа внутри уже подтверждённой записи; исчезнувшие за окно не блокируют; auto-зависимости исключены из сверки по `auto=true` — механика #285 Task 2, обобщается на activities; flat-параметры тела, не embed — урок wave 2 #285); сверка **до** исполнения — fail-closed, частичного каскада нет. (в) **Bare DELETE (без тела и флага) → 422 `expected_state_required` безусловно** — зеркало rev7 (у записей 422 и на чистом пути); слепое исполнение у занятий упраздняется целиком. Формат 422 — `ErrorDetail(ErrorCode.EXPECTED_STATE_REQUIRED)` по канону соседних эндпоинтов. Ломающее изменение (в т.ч. для e2e-хелпера cleanup и бэкенд-тестов — D7).

**D3 — фронт-поток (сходимость с юзером 17.09, поток v4; оба call sites).** Владелец механики — `ScheduleDataContext` (кэш недели и `activityQueryKey` — его; карточка/модалка только инициируют): контекстный метод `deleteActivityDeferred(id)` + хелперы. Поток: (1) **проверка актуальности кэша при клике — вручную, не `ensureQueryData`** (v5: `ensureQueryData` не дожидается рефетча — возвращает stale-кэш и prefetch-ит в фон, `@tanstack/react-query@5.100.x`): `const st = queryClient.getQueryState(weekKey)`; если `st.isInvalidated || (Date.now() - st.dataUpdatedAt > staleTime)` → `await queryClient.fetchQuery({queryKey: weekKey, staleTime: 0, meta: {silent: true}})`, флаг `refetched=true`; иначе — ноль запросов. `meta: {silent: true}` обязателен (best-practices, MAJOR): глобальный `QueryCache.onError` (`providers.tsx:17-24`) тостит на любой упавший query — без escape hatch свежестный фетч дал бы двойной error-тост (глобальный + catch-ветка потока); dry-run — прямой api-client-вызов, вне QueryCache, глобальным обработчиком не задевается. (2) `dryRunDeleteActivity(id)` (новая функция api-client, `DELETE ?dry_run=true`). (3) Ветвление: **пусто (204)** → без диалога: `await cancelQueries(weekKey)` → snapshot → optimistic map-remove → enqueue `{id: 'delete-activity-${id}', kind: 'delete', message: 'Удалено. Отменить', delayMs: 5000, undo: restore, commit: apiDeleteActivityWithExpected(id, {expected: {}}) + invalidateEntities(['activities'])}`; `refetched=true` на чистом пути НЕ показывает отдельный нотис (карточка видимо обновилась; undo-тост — feedback; решение юзера «меньше шума»). **Непусто (409+dependencies)** → `DeleteDialog` (`entityType: 'activity'`; заголовок «занятия»): **три группы однострочниками — «Записи — будут удалены:», «Посещения — будут удалены:», «Платежи — будут удалены:»** (каждая cap 10 + «и ещё N» — cosmetics), **при `refetched=true` — баннер первой строкой «Карточка обновлена по данным сервера»** (честен и при неизменившихся данных — «перепроверено»; diff содержимого не строим); подтверждение — **тот же сущностный чекбокс диалога, что у записей (D9в #285)**: каскад подтверждается целиком, выбора отдельных строк нет; confirm → enqueue с `expected` из **всех** items всех трёх узлов (не только показанных 10). Диалог и deferred-механика разведены: `onResolve` = enqueue (синхронен, всегда резолвится — busy/error-ветки диалога не задействуются), `onDone` = только закрытие **без инвалидации** (иначе рефетч вернёт карточку в окне); диалог монтируется на уровне WeekView/DayView (переживает unmount карточки). `expected` в коммите = подтверждённое дерево (контракт #285); в окне undo чистый (сервер не тронут).

**D4 — optimistic-удаление и undo — replace-by-id, не restore значения.** Перед optimistic: `await cancelQueries(weekKey)` (иначе week-GET, запущенный кликом/SSE, приземлится после удаления и вернёт карточку в кэш до commit); snapshot **текущих значений** захваченных ключей (weekKey; `activitiesForRecords` при наличии в кэше) → из каждого значения захватывается **объект строки занятия** → `setQueryData` map-remove. Undo: в **текущее** значение каждого ключа вставляется захваченный объект replace-by-id (SSE-обновления других карточек за окно не откатываются — паттерн D5 #285; восстановление целого значения ключа запрещено тем же решением #285 rev3). Инвалидаций при enqueue/undo нет. Guard `deletingRef` сбрасывается в finally на всех ветках (fail-closed: карточка не остаётся «мёртвой»); 150мс-анимация сохраняется как отклик клика до завершения dry-run; юнит `ActivityCard.test.tsx:413-452` обновляется под async-поток.

**D5 — Recreate-undo удаляется как механизм, не как функция.** Из `ActivityCard.tsx:78-88` уходит ветка `addActivity`-undo (сама `addActivity` остаётся публичным API контекста — у неё 4 других потребителя: `DayView.tsx:155`, `WeekView.tsx:112`, `CreateActivityTab.tsx:62`, `useDnD.ts:188`). Кнопка модалки `btn-delete-activity` маршрутизируется в **тот же** поток D3 (ensure- freshness → dry-run → ветвление → enqueue) — второй call site того же контекста; тост «Активность удалена» модалки удаляется (общий тост потока), `onClose()` сохраняется (закрытие модалки немедленно, pending-действие переживает unmount — провайдер app-level).

**D6 — индикатор «Сохраняем…» на deferred-удалении подавлен (решение юзера — (б)).** Контекст: `deleteMutation` и обёртка `deleteActivityById` удаляются; `SCHEDULE_ACTIVITY_MUTATION_KEY` остаётся только у create/update — `useSavingToast` на удалении не загорается; deferred commit = прямой api-client + инвалидация (как визиты/оплаты, `useRecordMutations.ts:440-483`). Следствие принято: **Topbar `useUnsavedChangesGuard(isSaving)` (beforeunload-guard) отложенное удаление не покрывает** — commit уходит из useMutation-семантики; принято как следствие решения (б). Сценарий S5 спеки #261 для занятия переворачивается (тост → индикатора нет) — правка формулировки в `docs/specs/2026-09-14-saving-toast-design.md` входит в финальную задачу плана.

**D7 — обработка ошибок commit — наследование паттерна #285 без копии.** `staleAwareOnError` #285 (Task 5) параметризуется целью инвалидации: `staleAwareOnError(queryClient, 'activities')` — activities уже в `INVALIDATION_MAP` (`invalidate.ts:82`), один хелпер/один юнит вместо копии. Ветвь: 409-with-dependencies → undo штатно + тост «Не удалось удалить: данные изменились» с действием «Обновить» (action-слот `{label, onAction}`, lifetime 4500мс — не-undo ветка) → инвалидирует `['activities']`; канонический `qk.activity(id)` не покрыт (детальные потребители не в потоке удаления). 404 — тихий успех (DELETE идемпотентен; SSE конкурента уже отрисовал исчезновение); прочие ошибки → дефолт: undo + «Не удалось удалить. Изменение отменено». Undo-гейт при in-flight commit: таймер снимается до `await commit` — «Отменить» во время DELETE не воскресит карточку, удалённую сервером (#285 D4).

**D8 — кольцо отсчёта — автоматически (#94 смержен `8520609`).** `enqueuePendingAction` передаёт `delayMs` как `countdownMs` — тост занятия получает кольцо без правок; визуальная цель «все undo-тосты одинаковы» (#94) закрыта самим переходом на общий пайплайн.

## 4. Детали поведения и края

- **Гонка середины окна — subset-сверка на обоих уровнях (решение юзера 17.09):** новая запись ИЛИ новый визит/платёж внутри уже подтверждённой записи → их id нет в expected → 409 → откат + «данные изменились» + «Обновить»; исчезнувшие за окно (запись/визит удалены конкурентом) не блокируют (subset, #285 D9а). Вне сверки — auto-узлы (record_tags/activity_tags/photos): link-строки и SET NULL — их дрейф данные не разрушает.
- **Auto-зависимости (photos/activity_tags) не показываются в диалоге** и не входят в expected (исключение по `auto=true`, #285 rev8) — их каскад неявен и не требует подтверждения; занятие с 0 записей, но с фото/тегами идёт чистым путём (без диалога) — фото отвяжутся, теги удалятся неявно, как и сегодня.
- **In-flight `updateMutation` + клик удаления:** если PATCH в полёте падает, его onSettled-инвалидация перетирает optimistic-remove — карточка возвращается с серверными данными при живом undo-тосте; commit DELETE может упасть 409 `stale_dependencies` — ожидаемое: undo возвращает карточку со свежими серверными данными, повторный клик даёт штатный поток.
- **Вытеснение undo-тоста из стопки (лимит 5):** пятый undo-тост вытесняет первый визуально, но commit не отменяется — таймеры живут в `PendingActionsContext` ref, не в тостах; undo вытесненного действия невозможен (тоста нет) — заложенное поведение пайплайна.
- **Быстрый повтор того же id (удалил → отменил → удалил):** dedupe снимает прежний таймер, прежний undoFn не вызывается — первая карточка уже не возвращается (штатное поведение пайплайна, `PendingActionsContext.tsx:44-49`).
- **Сеть пропала:** в клике (ensure/fetchQuery или dry-run падают) → error-тост, удаления нет (fail-closed, `deletingRef` сброшен); в окне → дефолт onError (undo + красный тост).
- **Refetch в окне** (SSE/навигация): занятие вернётся на экран до commit (сервер жив); после commit чисто. Принятая eventual-consistency всей схемы (§4 #285).
- **Undo и кнопка «×»:** наследие #94 D9 — «×» скрывает тост, commit выполнится; «Отменить» отменяет (undo-гейт при in-flight commit — таймер снимается до `await commit`).
- **Покрытие краёв:** race-ветки — юниты (subset, staleAwareOnError) + e2e S5/S6-аналоги; 422-ветки — бэкенд-юниты.

## 5. Что сознательно НЕ строим

- Изменение рукописного каскада сервиса — execution не трогается; меняется контракт вызова и проводка в матрицу (preview-only, D1/D2).
- **Вложенные counts-превью (`cascade_preview`) в диалоге** — глубина подтверждения достигается рекурсивным деревом (три узла items), preview-счётчики не нужны (механизм в коде существует только у `Client→visitors`, рендер захардкожен — волна 1); глубже двух уровней не идём — у Visit/Payment новых не-auto узлов нет.
- Диалог на чистом пути (без зависимостей) — undo-окно достаточно (зеркало чистого пути записей, D2 #285).
- Отдельный тост-нотис на чистом пути — карточка видимо обновляется при рефетче, undo-тост — feedback (решение юзера «меньше шума»).
- Авто-баннер «данные реально изменились» — diff содержимого не строим (баннер = «перепроверено», честен всегда).
- Конверсия визитов/оплат — #297/#298 (листовые; expected не несут — вне скоупа).
- Архивные сущности — вне контракта (решение #285 §5).
- Обобщение optimistic-хелпера недели на create/update мутации.
- GET-эндпоинт дерева зависимостей — хватает dry-run.
- Отмена после commit — окно только 5с.
- Перевод пайплайна на useMutation-канон — вне скоупа (решение #285 §5).

## 6. User Scenarios (каждая → e2e)

- **S1. Отложенное удаление свободного занятия** (карточка или модалка): карточка исчезает, undo-тост «Удалено. Отменить» с кольцом; сервер не тронут; через окно — занятия нет в БД. (e2e: новый тест)
- **S2. Отмена чистого удаления в окне.** «Отменить»: карточка вернулась, DELETE не уходил, БД не тронута. (e2e: новый тест)
- **S3. Каскадное удаление через диалог.** Занятие с записями: клик → (проверка кэша → dry-run) → DeleteDialog «занятия»: записи однострочниками; при рефетче — баннер «Карточка обновлена по данным сервера». - **S4. Отмена каскадного удаления в окне.** После confirm «Отменить»: карточка вернулась, БД не тронута. (e2e: новый тест)
- **S5. Провал commit.** Сеть off в окне: карточка вернулась, красный тост. (e2e: новый тест, setOffline-паттерн #239)
- **S6. Гонка середины окна (subset, оба уровня).** Занятие с записями: confirm → окно; в окне через API создаётся **визит в уже подтверждённой записи** (вложенный уровень) → commit: id визита не в expected.visits → 409 → карточка вернулась, тост «Не удалось удалить: данные изменились» с действием «Обновить» (клик инвалидирует `['activities']`), визит жив в БД.
