# Спека: ge=0 для числовых фильтров ClientListParams (#149)

- Дата: 2026-09-17. Issue: [mkosinov/memo#149](https://github.com/mkosinov/memo/issues/149) — закрывается IMPL-PR, не этим коммитом.
- Ревизия: rev2 — панель G1b 6/6 вернулась (5×PASSED_WITH_CONCERNS, security PASSED), 2 MAJOR + MINOR внесены, G1b OK юзера 17.09.
- Статус решения: G1a утверждён юзером 17.09 (подход A, ge=0; явный 422 без фронтенда; HTTP-422 тесты).

## 1. Проблема

`GET /api/v1/clients` принимает шесть числовых фильтров статистики: `min_records`, `max_records`, `min_paid`, `max_paid`, `missed_from`, `missed_to`. Все шесть объявлены голыми `int | None = None` без ограничений (класс `ClientListParams`, backend/src/schemas/client.py:117, поля :145–150; модель — params эндпоинта через `Depends()`, backend/src/api/v1/clients.py:99).

Отрицательные значения (например `min_records=-5`) семантически бессмысленны, но проходят Pydantic и уходят в SQL как сравнение вида `records_count >= -5` — тихий no-op: фильтр применяется, но не отфильтровывает ничего (backend/src/services/client.py:343–365). API контракт пропускает мусор и маскирует ошибки клиентов API (перепутанный знак, неверная переменная).

## 2. Решение

Schema-level Pydantic-ограничение: `Field(default=None, ge=0)` на все шесть полей `ClientListParams`. Значение < 0 → FastAPI прерывает запрос 422 (`RequestValidationError`) до входа в сервисный слой.

Формат тела 422 — **не** дефолтный: в приложении стоит кастомный обработчик `RequestValidationError` (backend/src/main.py:163–180), который переформирует тело в `{detail: {code, message}}` и берёт только первую ошибку — массива ошибок с указанием полей в ответе нет. Тесты ассертят 422 и эту форму, а не дефолтный detail-массив.

Обоснование выбора уровня:

- Schema-level `Field()` — канон репозитория для query-параметров: `page`/`per_page` уже валидируются `Field(ge=1)` / `Field(ge=1, le=100)` (backend/src/schemas/pagination.py:16–17). Замечание панели: `ClientListParams` наследует `PaginationParams`, так что `ge=1` живёт в базовом классе — новые ограничения добавляются только в подкласс, дублировать их не нужно.
- Model-level `@field_validator` на params-модели, собираемой через `Depends()`, в репозитории запрещён: превращает ошибку валидации в 500 (предупреждение из df0e205 зафиксировано в комментариях backend/src/schemas/client.py:126–136).
- Сервисный clamp (сервер молча исправляет значение) отвергнут: тихая смена семантики против явной ошибки.

Почему `ge=0`, а не `ge=1`: `missed_from`/`missed_to` фильтруют по счётчику MISSED-записей клиента (backend/src/services/client.py:242–250), ноль — легитимное значение («клиенты без пропущенных записей»), уже используемое в позитивных тестах. Все шесть полей — счётчики/суммы, ноль осмыслен для каждого.

## 3. User Scenarios

Для backend-only изменения E2E-уровень = интеграционные API-тесты (backend/tests). Каждая сценарная строка — пользовательская задача фичи и якорь теста.

1. **«Отрицательный фильтр отклонён с явной ошибкой»** — consumer API (админ ввёл минус в числовой фильтр на «Клиентах», либо прямой вызов API) передаёт отрицательное значение любого из шести полей → ответ 422, молчаливого пустого фильтра больше нет. Тест: параметризованный HTTP-тест (6 полей × значение −1) в backend/tests/test_api_clients.py.
2. **«Ноль легален»** — админ фильтрует «Пропущенные: до 0» (клиенты без пропущенных записей) → работает как сейчас. Тест: существующий позитивный тест с `missed_to=0` в backend/tests/test_client_stats.py остаётся зелёным.
3. **«Штатные фильтры не сломались»** — комбинированные и одиночные фильтры (`min_records=2`+`max_records=4` и прочие) работают как раньше. Тесты: существующие позитивные тесты фильтров backend/tests/test_client_stats.py:850–892 остаются зелёными — регрессионный гард.

## 4. Тесты

- Новый параметризованный тест в backend/tests/test_api_clients.py — размещение подтверждено юзером на G1b: файл владеет 422-контрактом `/clients` (существующие HTTP-422 паттерны: :266–272, :402–407). Родственные конвенции: test_api_pagination_params.py:1–22 — конвенция 422 для query-параметров (волна ge=1); позитивные тесты тех же шести фильтров живут в test_client_stats.py:850–892.
- Параметризация: по каждому из шести полей — негативы `-1` и `-42` (второй негатив защищает от sentinel-теста на единственном `-1`) → 422; позитив границы `0` для всех шести полей → 200 (сейчас `=0` покрыт только у `missed_to` — без этого будущий сдвиг до `ge=1` на остальных пяти не поймался бы).
- RED→GREEN (по issue): тест падает до добавления `Field(ge=0)`, зелёный после.
- На одном из полей ассертится форма тела кастомного обработчика (`{detail: {code, message}}`, main.py:163–180) — пин хвоста «дефолтная форма detail-массива» не нужна.
- Чистые schema-тесты ValidationError в test_schemas_client.py НЕ пишем — юзер-решение: HTTP-уровень покрывает контракт целиком, дублирование не нужно.
- Существующие позитивные тесты не изменяются.
- Пустая строка (`?min_records=`) и дробные значения (`1.5`) отвергаются 422 по типу `int` — это существующее поведение Pydantic v2, тем же контрактом; отдельными кейсами не перечисляем.

## 5. Скоуп (осознанно НЕ делаем)

- **Фронтенд не трогаем**: `ClientsFilters.tsx` (шесть `<input type="number">` без min-атрибута, :112–142) остаётся как есть. Юзер-решение «явный 422»: отрицательное значение в фильтре даёт 422, ошибка запроса видна через штатный механизм ошибок paged-list-фабрики (#140/#205). Пользовательский итог зафиксирован панелью: виден общий тост «Проверьте правильность заполнения полей» (main.py:170–171) — указания на конкретное поле в ответе и UI нет, это и есть принятый trade-off.
- **Другие сущности не трогаем**: ListParams визитов/записей/материалов и прочих — вне этого issue; найденные там же числовые list-фильтры без границ — отдельный issue. (Поля create/update-DTO — `min_age`/`max_age`/`duration`/`capacity` — другой класс: их границы задаются доменными правилами, а не list-фильтрацией; к этому issue не относятся.)
- **SQL/семантика фильтров не меняется**: services/client.py не правится, меняется только входная валидация.
- **page/per_page-волна `ge=1`** — уже слита ранее, к этому issue отношения не имеет.

## 6. Риски и ограничения

- Pydantic v2 (приходит через fastapi, backend/pyproject.toml:7,13): `Field(ge=0)` на `int | None` валидирует только переданное значение; `None` (фильтр не задан) проходит без изменений — поведение запросов без фильтров сохраняется.
- Формат ошибки — кастомный обработчик `RequestValidationError` (backend/src/main.py:163–180): тело `{detail: {code, message}}`, только первая ошибка, поля в ответе нет; пользовательский тост общий. Отдельный обработчик под это изменение не вводим — консистентно с page/per_page.
- Контекст issue устарел: упомянутые там 4 xfail-теста (tests/test_client_stats.py:857–892) в backend/tests не существуют — область давно GREEN (сейчас там позитивные тесты фильтров, :850–892). IMPL не должен искать xfail для снятия.

## 7. Решения дизайн-диалога (зафиксированы)

1. Подход A — schema-level `Field(ge=0)` на все шесть полей. Альтернативы: B (A + фронтенд-кламп тем же issue) и C (сервисный clamp) отвергнуты юзером.
2. UX отрицательных в UI: явный 422, фронтенд не правим.
3. Уровень тестов: только HTTP-422 в test_api_clients.py, без дублирующих schema-тестов.
4. Граница: `ge=0` (не `ge=1`) — ноль легален для всех шести полей.
5. Размещение нового теста: `test_api_clients.py` (юзер-решение на G1b).

## 8. DoD и откат

**DoD (всё должно быть зелёным):**
1. `Field(ge=0)` стоит на всех шести полях `ClientListParams`; `page`/`per_page` не дублируются.
2. Новый параметризованный тест: 6 полей × (`-1`, `-42`) → 422; 6 полей × `0` → 200; одна ассерша формы тела кастомного обработчика (`{detail: {code, message}}`).
3. Существующие позитивные тесты фильтров (test_client_stats.py:850–892) и прочий тестовый набор — зелёные; RED-фаза нового теста зафиксирована до GREEN.
4. Линт/тайпчек бэкенда чисты; CHANGELOG-строка по конвенции репозитория.

**Откат:** изменение — чистый schema-only дифф (один файл + тесты), миграций нет; откат = `git revert` PR-коммитов, состояние API возвращается к прежнему (минусы снова тихий no-op).
