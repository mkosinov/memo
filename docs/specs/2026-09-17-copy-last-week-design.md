# Спека: «Копировать прошлую неделю» для расписания (#242)

- **Issue:** #242 (feat(schedule), app:admin, frontend+backend)
- **Дата:** 2026-09-17. Статус: G1a OK получен (17.09), спека — до панели G1b.
- **Ход решения:** auto-DESIGN watcher, юзер вёл диалог G1a в сессии (все развилки закрыты его решениями — §11).

## 1. Проблема и поправка предпосылки issue

В тулбаре расписания кнопка «копировать прошлую неделю» ничего не делает: под ней пустая заглушка. Точная картина по живому коду отличается от тела issue в двух пунктах:

1. Тост под кнопкой **уже есть, но лжёт**: `Toolbar.tsx:52-58` вызывает заглушку и безусловно показывает «Прошлая неделя скопирована». Чинить нужно не «молчание», а фейковый успех.
2. Заглушка переехала из `contexts/ScheduleContext.tsx` в `frontend/admin/contexts/schedule/ScheduleDataContext.tsx:281-283` (интерфейс :77, юнит-тест «does not throw» `__tests__/schedule/ScheduleDataContext.test.tsx:576`).

Бизнес-смысл (issue): админ быстро собирает расписание просматриваемой недели, повторив предыдущую — все занятия появляются на те же дни/время (мастер/услуга/локация/длительность/ёмкость — как в оригинале).

Ключевой факт бэкенда: **никакой защиты от дублей нет** — ни unique-констрейнтов, ни валидации пересечений (занятия-параллели легальны по дизайну, #258/#259); единственная валидация create — `check_master_active` (422 MASTER_NOT_ACTIVE, `src/services/activity.py:33-52`). Защита от повторного нажатия — целиком дизайн-вопрос этой спеки.

## 2. Решение

Выделенный бэкенд-эндпоинт «copy week» — одна атомарная серверная операция «всё или ничего»; фронт вызывает её и перечитывает сетку.

Отклонённые альтернативы:
- **B (клиентский цикл):** фронт читает прошлую неделю и создаёт занятия по одному — не атомарно (обрыв = полупустая неделя), десятки запросов, дубли при повторе. Отвергнут телом issue.
- **C (generic bulk-create эндпоинт):** переиспользуемая примитива, но домен-логика копирования уезжает на клиент, нет единой точки гарды от дублей, YAGNI — второго потребителя сегодня нет.

Готовый образец атомарной многострочной операции уже в коде: `@transactional` (`src/services/decorators.py:57+`) + `mark_changed` SSE на каждую строку — образец `ActivityService.delete` (`src/services/activity.py:213-258`). Копия ляжет ровно на этот паттерн. Серверная копия не связана капом `per_page=100` публичного фетча недели (он остаётся как есть для сетки).

## 3. Зафиксированные решения юзера (G1a, 16–17.09)

1. **«Прошлая неделя» = относительно просматриваемой недели** (не календарно-текущей): админ листает недели, кнопка копирует в ту, что перед ним.
2. **Дедуп = merge, не 409:** в непустую целевую неделю копируем недостающее; «уже есть» по ключу ниже.
3. **Индивидуальные занятия (`is_private=true`) НЕ копируются** — бизнес-логика юзера.
4. **Архивная локация → занятия не копируются**; **архивный мастер → авто-ремап** на первого активного мастера с пересекающейся speciality (см. §5.3).
5. **Пикер локаций включён в v1:** клик по кнопке открывает попап с выбором локаций.
6. **Состав полей:** всё как в оригинале, включая `comment`, связи `tags` и `record_info` («копируем на всякий случай» — копируем на будущее; поле сейчас мёртвое: единственный путь создания шлёт `null`, читателей нет, `ScheduleDataContext.tsx:241`).
7. **Тай-брейк «первого мастера»** — не самодельный алфавит, а канонический порядок борда мастеров: `sort_order ASC, first_name ASC, id ASC` (`masters.py:33-35`) — тот же мастер, что админ видит первым в списках (решение D4, 17.09).
8. **Список локаций передаётся ВСЕГДА явным списком** (чекбоксы попапа, все включены по умолчанию): серверная операция обязана точно совпадать с тем, что видит юзер; кодировка «None = все» убрана (решение юзера, 17.09).
9. **Кап объёма копии = 100 занятий** за один вызов (решение D3, 17.09); превышение — честная ошибка с советом скопировать в несколько заходов по локациям.
10. **Гонка одновременных копий из разных вкладок принята без защиты** (решение D1, 17.09: вероятность ничтожна, lock не строим — §5.6).

## 4. Контракт эндпоинта

`POST /api/v1/activities/copy-week`

- **Гварды:** те же, что у create — `activities:write` + fetch-metadata CSRF (декларация `_WRITE_GUARD`, `activities.py:36-39`).
- **Request** `ActivityCopyWeekRequest`:
  - `week_start: date` — понедельник **целевой** недели (YYYY-MM-DD). Фронт всегда передаёт понедельник просматриваемой недели (`getMonday`); сервер валидирует: не понедельник → `422 COPY_WEEK_START_NOT_MONDAY` (новый ErrorCode + запись в `ERROR_MESSAGES` в `src/errors.py` — без неё KeyError в рантайме).
  - `locations: list[str]` — **обязательное** поле: явный список id локаций, отмеченных в попапе (все включены по умолчанию). Пустой список → `422 VALIDATION_ERROR` (Pydantic `min_length=1`); id, которых нет в базе → `422 COPY_WEEK_INVALID_LOCATION` (fail-fast; SQLAlchemy-параметризация сама по себе инъекцию исключает).
- **Семантика окон:** source = `[week_start−7д .. week_start−1д]` включительно, target = `[week_start .. week_start+6д]`; оба — целые дни через штатный `day_range()` (`backend/src/domain/dates.py`; граничные строки ровно 00:00 понедельника / 23:59 воскресенья разделены включительно-мин/макс — двойного копирования нет).
- **Кап объёма (D3):** набор **к вставке** (после фильтров §5.1 и дедупа §5.2) ограничен 100 занятиями; больше → `422 COPY_WEEK_SOURCE_TOO_LARGE` с сообщением «В выбранной области более 100 занятий — скопируйте в несколько заходов, сузив выбор локаций». Кап не обрезает молча: успешная копия всегда точна и полна, поэтому ограничение фигурирует в заметке попапа (§6) и в ошибке, но не в успешном тосте.
- **Response `200`** `CopyWeekResult` (разбивка честнее кортежа — каждое поле независимо ассертится тестами):
  ```json
  { "copied": 8, "skipped_duplicates": 2, "skipped_filtered": 1, "skipped_no_master": 0 }
  ```
  - `copied` — создано занятий;
  - `skipped_duplicates` — не скопировано: ключ дедупа совпал с существующим в target ИЛИ с созданным в этом же прогоне (§5.2);
  - `skipped_filtered` — не скопировано по общим правилам: `is_private=true` или локация заархивирована;
  - `skipped_no_master` — не нашли замену мастеру (ремап не удался).
  Пустой source → `200` с нулями (не ошибка; UI знает состав прошлой недели ещё до копии из попапа).
- **Ошибки:** `422 VALIDATION_ERROR` (типы Pydantic, пустой `locations`), `422 COPY_WEEK_START_NOT_MONDAY`, `422 COPY_WEEK_INVALID_LOCATION`, `422 COPY_WEEK_SOURCE_TOO_LARGE`. 409 нет — merge всегда доводит операцию до конца.

## 5. Правила копирования (доменные)

### 5.1 Фильтры источника (строка не является кандидатом, если)
- `is_private = true` (решение юзера §3.3);
- локация занятия заархивирована (`locations.is_active=false`; у create-пути такой гарды нет — фильтр реализует правило юзера §3.4);
- локация строки не входит в обязательный список `locations` запроса (§3.8). Архивные локации в попапе не показываются → в списке не оказываются; серверный фильтр остаётся как вторая линия.
- **Занятия архивных услуг копируются осознанно** — правило юзера покрывает только локации и мастеров; на услугу гварда в проекте нет (зафиксировано по замечанию панели безопасности).

### 5.2 Дедуп-ключ (merge)
Ключ занятия: **(master_id, service_id, start, duration)** — после сдвига `start + 7 дней`.
Локация и `capacity` **вне ключа**: ручная правка этих полей в целевой неделе не превращает повторный клик в дублепорождение. Повторный клик без правок копирует ровно ноль (DoD issue). Занятие-параллель (тот же слот, другой мастер или услуга) ключом ловится — оно и есть другой кандидат, копируется отдельно.
- **Дедуп внутри одного прогона:** ключи уже вставленных в этом же вызове строк попадают в тот же набор — два source-кандидата, сходящиеся в один ключ после сдвига/ремапа (параллель одной пары мастер+услуга+время в разных локациях; два архивных мастера, ремапнутые в одного кандидата), дают второму `skipped_duplicates`, а не дубль.
- **Это НЕ общий констрейнт:** merge-дедуп — поведение только copy-эндпоинта; никакого DB unique-констрейнта и никакой валидации пересечений для create/update он не добавляет (домен-инвариант #258/#259 «no uniqueness constraint, no 409» не трогается).

### 5.3 Ремап архивного мастера
- «Архивный» = `masters.is_active = false` ИЛИ строка расширения отсутствует. Это ровно то, что проверяет `check_master_active` (`activity.py:33-52`), — распределительный флаг, не кадровый.
- `specialty` мастера — **CSV-список** («живопись, керамика», `master.py:38-40`), поэтому «аналогичная speciality» = **непустое пересечение** списков source-мастера и кандидата (split по «,», strip, регистронезависимо).
- Кандидаты: активные мастера (`masters.is_active=true`) с непустым пересечением; **«первый» = канонический порядок борда мастеров** `sort_order ASC, first_name ASC, id ASC` (`masters.py:33-35`) — тот же порядок, в котором мастера видны в списках админки (решение D4). Поля `staff.name` не существует (`staff.py:32-33` — `first_name`/`last_name`) — сортировка по паре имён, а не по вымышленному полю.
- Замены нет → строка **пропускается** (`skipped_no_master`), симметрично правилу архивной локации.
- **Инвариант алгоритма ремапа** (не «структурный» — это свойство алгоритма, не схемы БД; терминология по замечанию панели): копия всегда получает активного мастера, т.к. ремап вычисляется сервером на живых данных внутри транзакции. Поэтому `check_master_active` на копируемые строки **не вызывается** — это отдельный путь валидации (id мастеров приходят не от юзера, а от серверного ремапа), а не обход гварда create.

### 5.4 Поля копии
Копируется всё, кроме `id`/`created_at`/`updated_at`: master (с ремапом при необходимости), service, location, `start + timedelta(days=7)` (чистая арифметика над stored-значением, floating-local канон #142 — TZ-сдвигов нет, DST не влияет на naive-даты), `duration`, `capacity`, `comment`, связи `tags`, `record_info`. `is_private` у копий всегда `false` — приватные отфильтрованы на входе.
- **Связи tags — явная работа:** `ActivityCreate` не содержит `tags` и штатный create не пишет `activity_tags` (`schemas/activity.py:8-26`, `repositories/generic.py:153`) — копия вставляет join-строки `activity_tags` явно (по образцу, обратному каскаду delete `activity.py:252-257`), после flush новых занятий, внутри той же транзакции.

### 5.5 Целостность и события
- **Один метод — одна транзакция:** весь конвейер (прочитать source/target, отфильтровать, ремапнуть, дедупнуть, вставить) выполняется в одном методе под **одним** `@transactional`: любой сбой → полный rollback, ничего не скопировано. **Зацикливать штатный `ActivityService.create` нельзя** — каждый его вызов сам `@transactional` и коммитит свою строку (`decorators.py:128`, create `activity.py:136-146`), атомарность исчезнет. Внутри — прямые ORM-вставки (`table(**data)`-стиль repo) + один flush; теги — после flush (§5.4).
- **SSE:** семейство `activities` помечается авто-меткой декоратора (`decorators.py:120`, аккумулятор — набор имён сущностей, `emitter.py:50-61`) — построчные `mark_changed` не нужны; ЯВНО помечается только `tags` (join-строки создаются напрямую, §5.4).
- Внутренний запрос source-недели — без пейдж-конверта и без капа 100 публичного фетча; объём сверху ограничен капом §4 (100 к вставке).

### 5.6 Принятая гонка (юзер-решение D1, 17.09)
Две одновременные копии одной недели (две вкладки, ретрай) могут обе прочитать пустой target и обе вставить → точные дубли. Защита (lock/индекс) сознательно НЕ строится: внутренний тул с одним админом, вероятность ничтожна, главный случай — повторный клик в одной вкладке — закрыт disabled-кнопкой и merge-дедупом. Последствие гонки: видимые дубли, удаляемые вручную. Фиксируется здесь и в domain-rules как принятый риск.

## 6. UX: кнопка и попап

- Клик по «Копировать прошлую неделю» открывает **попап** (компонент рядом с Toolbar, по design-system.md); безусловный фейковый тост из `Toolbar.tsx` удаляется.
- Попап при открытии подтягивает **прошлую неделю** (`getActivities` на `[viewedMonday−7 .. viewedMonday−1]`, `per_page=100`; ключ `qk.activityRange` — тот же queryFn и семейство инвалидации, что у сетки; явный `staleTime` 5 минут на попап-фетч — TanStack-рекомендация для `fetchQuery`).
- Содержимое попапа:
  - список локаций прошлой недели с чекбоксами и числом **к копированию** у каждой — уже минус ключи, существующие в целевой неделе (кэш просматриваемой недели доступен клиенту), минус приватные; архивные локации не показываются; по умолчанию все включены;
  - при наличии — подсказка «K индивидуальных занятий не копируются» (вычислима: `is_private` есть в payload);
  - **подсказки «не найдут замену мастера» НЕТ** — она не вычислима на клиенте честно (трансформер мастеров роняет `is_active` и имя, слайс мастеров страницы — только активные, `transformers.ts:7-16`, `ScheduleDataContext.tsx:117-118`); факт пропуска рапортует сервер после копии (решение D2=а);
  - если в прошлой неделе всего занятий больше 100 (`total > items.length`): честная заметка «Показаны первые 100 из N занятий; за один заход копируется до 100 — сузьте выбор локаций или скопируйте в несколько заходов»;
  - пустая прошлая неделя → пустое состояние, кнопка «Скопировать» неактивна;
  - кнопка «Скопировать» = подтверждение; неактивна, пока нечего копировать (итоговое «к копированию» = 0) или мутация в полёте.
- **По успеху копии попап закрывается** (счётчики в нём не меняются; открытый попап провоцирует бессмысленный второй клик).
- Тосты (UIContext, общий стек; kinds из `UIContext.tsx:5`):
  - `copied > 0` → kind `success`: «Скопировано N занятий» + при `skipped_duplicates > 0` — «(пропущено M — уже есть)»; при `skipped_filtered + skipped_no_master > 0` — вторая строка «не скопировано ещё K — индивидуальные, архивная локация или без замены мастера»;
  - `copied == 0 && skipped_duplicates > 0` → kind `info`: «Всё уже есть»;
  - `copied == 0 && skipped_duplicates == 0` → kind `info`: «Нечего копировать»;
  - ошибка запроса → kind `error`, тост с серверским сообщением, сетка не тронута.

## 8. Тест-план

- **pytest unit (сервис):** фильтры (private/архивная локация/список локаций), ремап (пересечение CSV, канонический порядок борда, нет замены → skip), дедуп-ключ (+ сдвиг +7д) **и дедуп внутри прогона** (два кандидата в один ключ), полный rollback при сбое вставки, поля копии, явная вставка `activity_tags` + метка `tags`, кап 100 к вставке.
- **pytest API:** гварды (401/403/CSRF), 422 не-понедельник, 422 пустой/несуществующий список локаций, 422 кап, форма ответа, merge-сценарий end-to-end на API.
- **vitest:** контекст-мутация + инвалидация; попап: счётчики «к копированию» (минус дубли target, минус приватные), подсказка приватных, заметка «первые 100 из N», disable-состояния, закрытие по успеху.
- **e2e:** см. §9.

## 9. User Scenarios (каждая → e2e)

- **S1 «Чистая неделя ← копия прошлой»:** пустая целевая неделя; копия переносит все занятия прошлой на те же слоты; поля совпадают; тост с числом; попап закрылся.
- **S2 «Повторное копирование не дублирует»:** сразу второй клик → copied=0, тост «Всё уже есть», сетка не меняется.
- **S3 «Merge в частично занятую неделю»:** в целевой уже есть занятия (не совпадающие по ключу); копируются только недостающие, совпавшие пропущены; счётчики попапа честно уменьшены на дубли.
- **S4 «Индивидуальные не копируются»:** в прошлой неделе есть `is_private=true` → в целевой их нет; в попапе подсказка «K индивидуальных…».
- **S5 «Архивная локация пропускается»:** занятие прошлой недели в архивной локации не копируется; локации нет в попапе. *В тесте сущность архивируется предварительно через штатный API — сид архивных не содержит.*
- **S6 «Ремап архивного мастера»:** занятие архивного мастера копируется под первого активного мастера с пересекающейся speciality **в каноническом порядке борда**; если замены нет — не копируется, серверный тост рапортует «без замены мастера». *Архивация — предварительно в тесте.*
- **S7 «Выбор локаций»:** снятая галка локации в попапе → её занятия не скопированы, остальные скопированы; запрос всегда уходит с явным списком отмеченных локаций.
- **S8 «Пустая прошлая неделя»:** в прошлой неделе нет занятий → пустое состояние попапа, «Скопировать» неактивна (добавлена по замечанию панели полноты).

## 10. Что сознательно НЕ строим

- undo для копии (additive-операция; обратная операция = масс-удаление — кандидат в follow-up рядом с #286/PendingActions);
- выборочные дни / сдвиги «копировать день» / копирование вперёд на N недель;
- merge-политика сложнее точного ключа §5.2 (fuzzy-совпадения, «обновить существующее»);
- generic bulk-create эндпоинт;
- правка капа `per_page=100` сетки недели;
- валидация пересечений занятий (параллели легальны — #258/#259, инвариант в domain-rules);
- отдельный выбор «на какого мастера переназначить» в попапе — ремап автоматический (юзер-решение §5.3); точечная замена мастера — штатное редактирование занятия после копии;
- сериализация одновременных копий (lock/advisory/уникальный индекс) — гонка принята (§5.6, юзер-решение D1); «created»-список в ответе — фронт перечитывает сетку через инвалидацию, поле без потребителя.

## 11. Протокол G1a (история решений юзера)

- v1 концепт: 4 вопроса (семантика недели / дедуп 409 vs merge / неактивный мастер / состав полей).
- Юзер: неделя относительная; **409 отверг — «надо копировать»** (merge); архивная локация → skip, архивный мастер → копируем; «is_private пропускаем» + «какие там ещё поля?»; идея пикера локаций.
- v2: пушбэк по `is_private` (живой флаг — ромбик в `recordsColumns.tsx:95`) отвергнут в пользу новой бизнес-логики: **приватные не копируются вовсе**; `record_info` — копировать; ремап вместо обхода гварда: первый активный с пересекающейся speciality; пикер — включить.
- Живые факты, снявшие споры: `specialty` = CSV (master.py:38-40) → правило «пересечение списков»; `check_master_active` = `masters.is_active` → гвард остаётся нетронутым.
- Два производных дефолта (приняты «всё ок»): нет замены → skip; «первый» = канонический порядок.
- **Ревизия v2 по панели G1b (17.09, решения D1–D4 юзера):** D1 — гонка принята без lock (§5.6); D2=а — подсказка «L не найдут замену» убрана из попапа (не вычислима на клиенте), сервер рапортует в тосте; D3 — кап 100 к вставке с честным сообщением (заметка в попапе при >100 raw; 422 COPY_WEEK_SOURCE_TOO_LARGE при попытке; в успешном тосте ограничения нет, т.к. обрезки не бывает); D4 — тай-брейк = канонический порядок борда мастеров. Плюс: locations — всегда явный список (кодировка None убрана); дедуп внутри прогона; один-метод-одна-транзакция (не зацикливать create); явные вставки activity_tags + метка tags; запись в ERROR_MESSAGES; закрытие попапа по успеху; S8; счётчики попапа нетто-от-дублей.
