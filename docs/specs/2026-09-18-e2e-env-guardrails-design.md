# Спека: e2e-инфраструктура — guardrails на входе шардов и канон регенерации снапшотов

- Issue: #209 (post-mortem сессии #191: 10 провальных попыток перегенерации визуальных снапшотов 10–14.08)
- Дата: 2026-09-18 (rev2 после панели; rev1 — утренняя)
- Статус: на утверждении (Gate B)
- Область: test-инфраструктура (`scripts/`, `frontend/admin/e2e/`, `.github/workflows/`, скилл `dev-workflow`). Продуктовый код не затрагивается.

## Контекст (самодостаточный — панель не читает issue)

10 августа сессия, доводившая серверные фильтры записей (#191), 10 попыток подряд не могла поднять/переиспользовать e2e-стек в отдельной рабочей копии (worktree). Ни одна из причин не была в продуктовом коде — всё ловушки окружения:

1. `SHARD_ID=rest` принят стартовым скриптом без вопросов → получилась БД `test_memo_shardrest.db`, которой не существует в каноническом потоке.
2. Переменная `TEST_DB_PATH` молча игнорировалась при заданном `SHARD_ID` — диспетчеры думали, что она работает.
3. «Рабочий» порт оказался чужим устаревшим стеком другого шарда — переиспользование по признаку «порт отвечает» скрыло проблему на 3 попытки.
4. Регулярное выражение фильтра тестов (testMatch) матчилось по абсолютному пути → в worktree с «records» в имени пути проект находил 0 тестов.
5. Два `next dev` на одной папке `.next` портили манифесты маршрутов.

### Актуальность на 2026-09-18 (частично устарел — корректировки зашиты в этот дизайн)

Четыре из пяти причин уже закрыты смежными смерженными PR (сверено скаутом по живому дереву):

- Фильтр тестов (№4) — закрыт: оба regex заякорены на имя файла (`frontend/admin/playwright.config.ts:118` и `:125`).
- Общий `.next` (№5) — закрыт #264 (PR #277, 15.09): сборка каждого шарда изолирована (`next.config.mjs:6` + `scripts/e2e-shard-start.sh:51-55`).
- Зависание очистки шардов (#122-класс) — закрыт тем же PR #277: ограниченная лестница очистки в `scripts/lib/shard-helpers.sh` (~строки 115–198).
- Доки про браузеры Playwright — переписаны: проверка перед установкой (`.opencode/skills/dev-workflow/SKILL.md:118-131`).

Живой остаток, который закрывает эта спека:

- **RC1:** `SHARD_ID` не валидируется нигде. `scripts/e2e-shard-start.sh` проверяет только непустоту переменных (цикл ~строк 35–40); TS-слой молча выводит из него имя БД.
- **RC2:** `TEST_DB_PATH` молча игнорируется при заданном `SHARD_ID` — причём **разрешение пути БД продублировано в шести местах** TS-слоя, с разными приоритетами (см. §2). Конфликт латентный: в CI переменные совпадают по разрешённому абсолютному пути в playwright-шаге (`test.yml:207`), но в шаге старта стека тот же workflow передаёт `TEST_DB_PATH` **относительным** (`test.yml:178`), т.е. «совпадение» — следствие того, где именно случится сравнение, а не гарантии.
- **RC3 (процесс):** переиспользование чужого стека по живости порта — протокол проверки идентичности нигде не записан.
- **CI-guard:** ни один workflow не проверяет, что проект Playwright резолвит > 0 тестовых файлов. Регрессия фильтров тестов снова прошла бы незамеченной до подъёма серверов.
- **Канон регенерации:** сегодня канон — ручной GitHub-workflow `.github/workflows/update-snapshots.yml` (запуск вручную, `SHARD_ID=2`, результат — артефакт на 7 дней, PNG скачиваются и коммитятся руками; `update-snapshots.yml:95-101`). Частично канон описан в `docs/tests_workflow.md` (~:120-135, :245-255), но дрилл «артефакт → скопировать → коммит» и протокол идентичности стека в скилле сессий отсутствуют.
- Мелочь: устаревший комментарий «1-5» в шапке `frontend/admin/e2e/globalSetup.ts` (канон — шарды 1 и 2).

Дополнительно обнаружено: существует сухой тест стартового скрипта `scripts/e2e-shard-start.dryrun.test.sh` (заглушки вместо `uv`/`pnpm`), но он нигде не подключён — ни CI, ни `test-all.sh`, ни `package.json`. Мёртвый тест.

## User Scenarios

Каждый сценарий — задача, которую пользователь фичи (разработчик или автоматическая сессия) решает с этими изменениями, и механическая проверка:

1. **Опечатка в SHARD_ID отсекается на входе.** Запуск `SHARD_ID=rest bash scripts/e2e-shard-start.sh …` → мгновенный отказ (код 1) с ошибкой, содержащей подстроку `must be 1 or 2` и называющей допустимые значения; стек не поднимается, мусорная БД не создаётся.
   Проверка: новый кейс в `scripts/e2e-shard-start.dryrun.test.sh` (невалидный id → exit 1 + grep на `must be 1 or 2`; валидные 1 и 2 → проходят как раньше).
2. **Конфликт переменных окружения громкий — во всём TS-слое, не в одном месте.** Прямой запуск Playwright с `SHARD_ID=2` и чужим `TEST_DB_PATH` (например, унаследованным из `.env.test`) → падение с ошибкой, называющей обе переменные и способ починки — в любом из шести мест разрешения пути БД, а не только в globalSetup. Совпадающие пути работают тихо, как сейчас.
   Проверка: юнит-тест `frontend/admin/__tests__/db-path.test.ts` (vitest, `pnpm test`) на общий хелпер: конфликт бросает ошибку; совпадение и одиночные переменные — проходят; существующий `__tests__/seed-reset.test.ts` (~строки 101–131, assertion «shard wins, TEST_DB_PATH ignored» на :115) обновлён под новый контракт.
3. **Фильтры тестов резолвят ноль — CI падает рано и понятно.** Регрессия testMatch (проект резолвит 0 spec-файлов) → job CI падает на guard-шаге до подъёма серверов, с сообщением о классе этой ошибки и указанием на regex в `playwright.config.ts`. Граница: guard ловит «ноль тестов»; перекос «тесты утекли в чужой проект» он не ловит (осознанно вне скоупа).
   Проверка: guard-шаг в `test.yml` (в каждой шард-джобе, до старта стека) и в `update-snapshots.yml` (перед реген-шагом); в PR с этими изменениями оба workflow зелёные с guard-шагом.
4. **Каноничный запуск продолжает работать.** Все нынешние потребители (`test-all.sh` — шарды 1, 2; `test.yml` — матрица 1, 2; `update-snapshots.yml` — шард 2) проходят без изменений поведения — при `SHARD_ID` из {1, 2} и согласованных переменных, т.е. во всех реально существующих конфигурациях.
   Проверка: happy-path кейсы dryrun-теста (шарды 1 и 2) + зелёный CI в PR с изменениями.

Отдельно (без автоматической проверки, осознанно не автоматизируем): протокол проверки идентичности стека перед переиспользованием и дрилл регенерации снапшотов фиксируются в скилле `dev-workflow`.

## Решение (концепт — Gate A)

Рассмотренные варианты (из issue, после сверки с актуальностью):

- **B — только процесс** (дисциплина диспетчеров, без кода). Отклонён: сам постмортем — контролируемый эксперимент, 10 процессно-дисциплинированных попыток провалились на ловушках, которые отсекает только валидация на входе. Оставшиеся живые дыры (RC1/RC2) процессом не закрываются.
- **A — только правки кода** (валидация `SHARD_ID` + конфликт `TEST_DB_PATH`). Отклонён как недостаточный: оставляет открытой дверь регрессии testMatch (причину №1 по числу провальных попыток — ~6 из 10) и незакрытым канон регенерации из-за которого сессии тратят часы на изобретение пути.
- **C — урезанный A+B+CI-guard. Выбран.** Совпадает с рекомендацией в issue («Option C with A as the mandatory first step»), сжатой на уже сделанное другими PR: валидация на входе, громкий конфликт переменных, CI-guard «ноль тестов», канон и протоколы в доках.

### Что сознательно НЕ строим (границы скоупа)

- **Pidfile/`--detach`-режим для `e2e-shard-start.sh`.** Практический вред RC4 снят лестницей очистки (#277) и тем, что канон регенерации уехал в CI-workflow.
- **Предустановка браузеров Playwright в образы / правки контейнера.** Поток «проверь → ставь» в доках уже есть.
- **Регулярный (по расписанию) job визуальных снапшотов и детекция дрейфа.** Регенерация остаётся ручной; дрейф рендера — отдельный класс проблем (#226/#229), не эта спека.
- **Автоматизированный инструмент проверки идентичности стека.** Протокол фиксируется документально, без скрипта-надзирателя.
- **Shellcheck/тесты для `test-all.sh` как такового.** Подключаем существующий dryrun-тест стартового скрипта — и только.
- **Детекция «тесты утекли в чужой проект»** (guard ловит только ноль spec-файлов) — класс ошибки другой, диагностика сложнее, в постмортеме не встречалась.
- **Любые изменения схемы портов, имён БД, канонического набора шардов {1, 2}.**

## Технический дизайн

### 1. Белый список SHARD_ID в `scripts/e2e-shard-start.sh`

Сразу после цикла проверки непустоты переменных (~строка 40), до `ROOT_DIR=` (~строка 42) и `export SHARD_ID` (~строка 49):

```sh
case "$SHARD_ID" in
  1|2) ;;
  *)
    echo "ERROR: SHARD_ID must be 1 or 2 (canonical shards; got '$SHARD_ID')" >&2
    exit 1
    ;;
esac
```

Основание: все три потребителя сегодня используют ровно {1, 2} (`scripts/test-all.sh:163` — `seq 1 2`; `.github/workflows/test.yml:134-139` — матрица shard-id 1/2; `.github/workflows/update-snapshots.yml:24` — 2). Явный белый список вместо проверки «целое число»: верхняя граница нигде не определена, а мусорное имя БД — тот вред, который отсекаем.

**Граница ответственности:** скрипт валидирует только сам id. Пару `SHARD_ID × TEST_DB_PATH` валидирует TS-хелпер (§2) — потому что прямые запуски Playwright (без стартового скрипта, например локально с `SHARD_ID` в окружении) проходят мимо скрипта, и только TS-слой их накрывает.

**Синхронизация канонического набора.** {1, 2} теперь зафиксировано в четырёх местах: белый список в `e2e-shard-start.sh`, `seq 1 2` в `test-all.sh`, матрица в `test.yml`, env в `update-snapshots.yml`. Добавление третьего шарда — правка всех четырёх (+ комментарий в хелпере §2); это осознанный ценой явности.

### 2. Единый хелпер пути тестовой БД: `frontend/admin/e2e/lib/db-path.ts`

Сегодня разрешение пути БД продублировано в шести местах с расходящимся поведением (сверено панелью по живому дереву):

| Место | Строки | Приоритет сегодня |
|---|---|---|
| `frontend/admin/e2e/globalSetup.ts` | ~79–83 | shard побеждает, `TEST_DB_PATH` игнорируется |
| `frontend/admin/e2e/fixtures/db-query.ts` | ~26–32 | тот же |
| `frontend/admin/e2e/fixtures/seed-reset.ts` | ~107–112 | тот же |
| `frontend/admin/e2e/fixtures/factories.ts` | ~385–390 | тот же |
| `frontend/admin/e2e/unify-caches.spec.ts` | ~45–47 | тот же |
| `frontend/admin/e2e/visual-compliance-checks.spec.ts` | ~42–45 | **обратный**: `TEST_DB_PATH` побеждает |

Изменение: вся шестёрка переходит на один экспортируемый хелпер `resolveTestDbPath({ shardId?, testDbPath? })`:

- относительный `testDbPath` разрешается **от корня репо** (хелпер сам знает корень через `path.resolve(__dirname, '../../..')` от `e2e/lib/`) — не от `process.cwd()`, который зависит от каталога запуска;
- задан `shardId` → канонический путь `test_memo_shard${shardId}.db` (в бэкенде); если при этом задан и `testDbPath`, и его абсолютное разрешение **отличается** → бросается ошибка с текстом: какой `SHARD_ID`, какой путь он даёт, какой `TEST_DB_PATH` передан, что убрать одну из переменных;
- пути совпали, либо задана только одна переменная — прежнее поведение;
- **возвращённое значение — единственный источник пути**: все шесть мест используют именно его (включая сборку строки `sqlite3 "${dbPath}"` в `globalSetup` — сырой env-значение больше нигде не расходуется).

Прецедент контракта: громкая явная ошибка вместо молчаливого приоритета (как #149 для фильтров).

Тесты:

- новый `frontend/admin/__tests__/db-path.test.ts` (vitest-сюита админки, `pnpm test`; файл именно в `__tests__/` — vitest исключает `e2e/**` из коллекции, импортировать хелпер оттуда можно, тесты внутрь `e2e/` класть нельзя): конфликт бросает; совпадение (в т.ч. относительный + абсолютный вид одного пути) проходит тихо; только `shardId`; только `testDbPath`;
- существующий `frontend/admin/__tests__/seed-reset.test.ts` (~101–131) обновляется: assertion «shard wins, TEST_DB_PATH ignored» (:115) заменяется на новый контракт (конфликт → ошибка).

### 3. Правка устаревшего комментария

Шапка `frontend/admin/e2e/globalSetup.ts`: `test_memo_shard{1-5}.db` → `{1, 2}`. Одна строка.

### 4. CI-guard «в проекте 0 spec-файлов»

В обеих джобах матрицы `.github/workflows/test.yml` — шаг сразу после установки зависимостей (включая Playwright-браузеры) и **до** старта стека:

- `working-directory: frontend/admin`; env шага повторяет матрицу джобы (`SHARD_ID`, `SHARD_PORT`, `BACKEND_PORT`, `BACKEND_URL`/`NEXT_PUBLIC_API_URL`) — чтобы конфиг резолвился в том же shard-режиме, что и реальный прогон;
- команда: `pnpm exec playwright test --project=<проект джобы> --list` с перехватом **только stdout** (stderr отдельно: трейс ошибки загрузки конфига содержит абсолютные пути `.spec.ts` и его нельзя засчитывать);
- ненулевой код выхода — отдельная ошибка с своим сообщением (опечатка в имени проекта/матрице), не смешивается с «нулём тестов»;
- ноль строк с `.spec.ts` в stdout → шаг валит job с сообщением о классе ошибки (регрессия фильтра тестов / путь worktree) и указанием на regex в `playwright.config.ts:118,125`;
- формат вывода `--list` сверен на установленной версии (1.60.0): строки вида `[project] › file.spec.ts:12:1 › title`; подсчёт по строкам, не по парсингу сводки.

Тот же guard — в `update-snapshots.yml` перед реген-шагом (проект `shard-rest`, до старта стека). Уровень доверия тот же, что у самого реген-шага (ручной `workflow_dispatch`, выполнение кода репо). Новый код джоб секретов не потребляет; `GITHUB_TOKEN` остаётся с дефолтным read-скоупом.

### 5. Подключить существующий dryrun-тест стартового скрипта

- В `scripts/e2e-shard-start.dryrun.test.sh` добавляется кейс: невалидный `SHARD_ID=rest` → exit 1 и stderr содержит `must be 1 or 2`. Существующие кейсы (все с `SHARD_ID` ∈ {1, 2}) не ломаются: белый список стоит до всей машинерии, заглушки не успевают ничего увидеть.
- Подключение в **двух** местах: новая лёгкая джоба в `test.yml` (параллельно матрице, без `needs`; шаг `bash scripts/e2e-shard-start.dryrun.test.sh`) **и** ранний шаг в `scripts/test-all.sh` перед поднятием шардов. Локальная проводка — после находки панели: постмортем-герой (worktree-сессия) CI не запускал, а тест работает на заглушках миллисекунды.
- DoD: dryrun-тест зелёный локально до мержа и зелёный в новой джобе в PR с изменениями. Нюанс среды: тест обрывает запуск, если реальный `pnpm` виден по пути `/root/.npm-global/bin/pnpm` (~строки 69–75) — в GitHub-раннере путь установки pnpm может отличаться; зелёность джобы в PR это и проверяет.
- В сухом тесте кейс 1 использует `TEST_DB_PATH` с именем, **не** совпадающим с `test_memo_shard${SHARD_ID}.db` — это намеренно (стартовый скрипт не выводит имя БД из `SHARD_ID`); при будущих правках не «затягивать» проверку имени.

### 6. Канон и протоколы в скилле `dev-workflow` (`.opencode/skills/dev-workflow/SKILL.md`, английский — конвенция харнесса)

- Новый подраздел «Visual snapshot regeneration»: дрилл — ручной GitHub-workflow `update-snapshots.yml` (workflow_dispatch, шард 2) → скачать артефакт `updated-snapshots-shard-rest` → скопировать PNG в дерево → коммит; локальная регенерация — только для итераций, с `SHARD_ID` из {1, 2}. 1. **Жёсткий белый список {1, 2}** — если появится третий шард, правится четыре места (перечислены в §1). Альтернатива «любое целое» отклонена (нет определённой верхней границы). Подходит ли {1, 2}?
