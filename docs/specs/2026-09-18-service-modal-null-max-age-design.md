# ServiceModal: NULL max_age — пустое поле вместо нуля (design)

- **Issue:** #203 (`app:admin`, bug). Найдено автономным visual-гейтом #178 (spec §7 smoke: services edit-save); байт-идентично main — не регрессия #178.
- **Дата:** 2026-09-18. **Статус:** Gate B пройден (OK пользователя 2026-09-19). **Ревизия:** rev4 (rev2 — после панели; rev3 — e2e срезан до дымовой пары, прецедент #94; rev4 — решение пользователя на гейте C «вариант B»: клиентская валидация вложенных полей тарифов включена в скоуп).
- **Разведка:** факт-лист скаута от 2026-09-18 (вердикт `actual`).

## 1. Контекст и проблема

Услуга может не иметь верхней возрастной границы посетителя — в данных это `max_age = null`. Заявление issue подтверждено скаутом с одним уточнением механизма:

- При открытии **редактирования** форма подставляет в поле «Возраст до» ноль вместо пустоты (`ServiceModal.tsx:370-371`: `service[f.key] ?? (f.type === 'number' ? 0 : ...)`; конфиг поля `serviceFields.tsx:101-105`: `type: 'number'`, `min: 0`, `max: 18`, необязательное).
- Уточнение механизма: ноль НЕ нарушает диапазон (min = 0, range-проверка `val < field.min` его пропускает). Сохранение блокирует перекрёстное правило «Возраст от ≤ Возраст до» (`ServiceModal.tsx:413-419`): у всех услуг с пустым максимумом `min_age` = 5–12, и подставленный 0 всегда его нарушает. Итог для пользователя совпадает с issue: сохранить правку нельзя.
- Затронуты 6 из 7 seed-услуг (`seed.py:297-315`: `max_age: None` в 6; единственный не-null — `max_age: 12`).

**Второй дефект того же класса, в issue не заявленный (найден скаутом):** в ветке **редактирования** при сабмите таблица услуг принудительно подставляет 18 вместо пустоты (`ServicesTable.tsx:74`, внутри `handleEditSubmit` → PUT: `max_age: (data.max_age ...) ?? 18`). Даже при починенной форме «пусто» доехало бы до сервера как 18. Ветка **создания** (`handleCreateSubmit`, `ServicesTable.tsx:108-115`) coercion не имеет и уже передаёт payload как есть — создание с пустым `max_age` сегодня сохраняет null (уточнение панели rev2; в rev1 create-дельта была описана ошибочно).

Серверная часть уже корректна: `ServiceBase.max_age: int | None` (`schemas/service.py:75`), `ServiceUpdate`/`ServicePatch` тоже `int | None` (`:124`), колонка nullable (`models/service.py:24`, миграция `275ba490cab8`). Доменной логики на бэкенде, читающей `max_age`, нет — только read-схема и колонка админ-таблицы (`admin/setup.py:185`). Фронтенд-потребители уже различают null и 0 (`transformers.ts:24`, `buildSchedule.ts:79`: `max_age != null ? ... : undefined`) — сохранённый 0 рисовался бы ложной плашкой возраста.

## 2. Решение (Gate A, авто — выжил один концепт)

max_age в форме становится честным необязательным числом: пусто ↔ null. Клиентские правки в трёх местах, сервер не трогаем:

1. **Инициализация формы:** `max_age: null` → пустая строка, а не 0. `FieldRenderer` уже отдаёт `''` при очистке числового инпута (`ServiceModal.tsx:104`), форма живёт в `Record<string, unknown>` — микс `''` и number типобезопасен. Список полей с пустой инициализацией фиксируем явно: **только `max_age`** (не по флагу `required` из конфига — у `min_age` флага нет, но его нулевая инициализация и семантика «с N лет» сохраняются; тарифы и `duration` — обязательные нули как прежде).
2. **Валидация:** range-проверка уже пропускает пустые значения (`:400`); перекрёстное правило «от ≤ до» (`:414-419`) сейчас guard-ится только `!== undefined` — дополнить условием «значение заполнено» (`'' ` и `null` = не заполнено), иначе `minAge > ''` при коэрции даёт ложную ошибку снова. Проверки писать явным «не пусто» (`value !== '' && value != null`), без truthy-проверок: 0 — валидное значение числовых полей (цены, длительность), `if (value)` молча бы его отбросил.
3. **Сабмит:** нормализация `'' → null` **только для `max_age`** (по образцу `MyDataModal.tsx:142`, но не генерически на все поля — иначе очищенное обязательное `min_age` в create уехало бы как null; замечание панели rev2). В `ServicesTable.tsx:74` (edit/PUT) coercion `?? 18` убирается — null проходит как null. Create-ветку не трогаем.
4. **Валидация элементов тарифов (новый скоуп, решение пользователя «вариант B» на гейте C 2026-09-19).** Сегодня required-флаги вложенных полей тарифов рисуют только звёздочку: клиентская проверка обходит только поля верхнего уровня, пустая цена тарифа отклоняется лишь сервером (тост). `validate` дополняется обходом элементов тарифа: обязательность и диапазоны берутся из тех же конфигов полей (`itemFields`), ошибки выводятся у соответствующих полей элемента — тот же механизм, что и для основных полей, без исключений.

Поле получает placeholder «без ограничения», чтобы пустое состояние читалось (ожидаемое поведение issue: «пустое поле / "без ограничения"»). A11y-полировка (постоянная подсказка под полем вместо placeholder-only) — возможное улучшение на IMPL-ревью, в скоуп не входит.

### Рассмотренные и отклонённые подходы

- **B. Поле read-only с надписью «без ограничения»** — отклонён: противоречит ожидаемому поведению issue (поле должно оставаться редактируемым, иначе верхнюю границу не (пере)задать).
- **C. Смена модели данных (0 = «без ограничения» или NOT NULL с дефолтом)** — отклонён фильтром расхождений (reuse wins): null-семантика уже зафиксирована в БД/АПИ/отображениях, потребители различают null и 0.

### Не строим (границы скоупа)

- Сервер, миграции, API-контракт — не трогаем (уже принимают null).
- Инициализацию нулём в `NestedList.addItem` (тарифы) — не баг: поля тарифов обязательные.
- «Дефолтный тариф по возрасту» — отдельный бэклог #284, вне скоупа.
- Семантику `min_age` (пустое → 0 = «с рождения») — существующее поведение, не меняем.
- Жизненный цикл модалки: `formData` пересобирается при каждом открытии — правка его не меняет.

## 3. Behavioral Delta

| Сценарий | Было | Стало |
|---|---|---|
| Открыть редактирование услуги без верхней границы | В поле «Возраст до» подставлен 0 | Поле пустое, placeholder «без ограничения» |
| Сохранить правку такой услуги (имя/цена/что угодно) | Блокировано: 0 нарушает правило «от ≤ до» | Сохраняется; в данных по-прежнему `max_age = null` |
| Очистить заполненное «Возраст до» и сохранить (edit) | «Пусто» сохранялось бы как 18 (скрытая coercion в PUT-ветке) | Сохраняется как null = «без ограничения» |
| Создать услугу, оставив «Возраст до» пустым | Null сохранялся и раньше (create-ветка без coercion) — без изменений | Без изменений; сценарий получает компонентное покрытие |
| Сохранить услугу с тарифом без цены | Клиентских ошибок нет: пустая цена уезжает и отклоняется сервером (тост) | Ошибка обязательного поля у цены тарифа, запрос не уходит |
| Заполнить обе границы | Правило «от ≤ до» | Без изменений: правило действует, когда заполнены оба; пустое «до» правило не включает |
| Ошибка «Возраст до не может быть меньше Возраста от» | Появлялась ложно на null-услугах | Появляется только при реальном нарушении заполненных значений |
| Отображение после сохранения null | (недостижимо — edit-save был заблокирован) | Без плашки возраста (потребители различают null и 0) |

## 4. User Scenarios (→ тесты)

**Раскладка по уровням (решение пользователя 2026-09-19, «вариант A»):** e2e — только дымовая пара сценариев 1–2 (именно этот класс проверки поймал баг, и живая склейка «страница → форма → сохранение» не покрыта больше нигде); сценарии 3–5 — компонентные тесты (vitest + testing-library, монтируем модалку с фикстурой) — та же логика в разы дешевле. Полный Playwright-набор в репо ~45 минут, поэтому пятёрка e2e признана непропорциональной для формового фикса.

1. **Правка услуги без верхней границы.** Открыть seed-услугу с пустым «возраст до»: поле пустое (**отдельный именованный assert**: значение инпута `''`) и показывает placeholder «без ограничения» (**отдельный assert**); поменять название, «Сохранить» — сохранение проходит, в API-ответе `max_age: null`. → **e2e** `frontend/admin/e2e/services-null-max-age.spec.ts` (новый файл): `edit-save-null-max-age`.
2. **Снять верхнюю границу.** У услуги с `max_age = 12` очистить «Возраст до», сохранить → в GET-ответе `null`; в расписании у карточки услуги исчезает плашка возраста (поверхность с подтверждённым рендером плашки — `buildSchedule.ts:79`; для списка услуг поверхность плашки панелью не подтверждена, assert клеим к расписанию/API). → **e2e**, второй тест в том же файле: `clear-max-age-saves-null`.
3. **Перекрёстное правило живо.** Заполненные «от = 10» и «до = 5» → ошибка, сохранения нет; «до = 14» → сохраняется. Очистить «до» → правило не срабатывает, сохранение проходит. Ввести заново 0 при «от = 0» → диапазон 0–18 пропускает, сохраняется без ложных ошибок. → **компонентный тест** (vitest): `min-max-cross-rule`.
4. **Создание услуги с пустым «Возраст до».** Создать услугу с тарифом, «Возраст до» оставить пустым → в payload мутации `max_age: null` (регресс-щит create-ветки; готового create-save теста нигде нет). → **компонентный тест**: `create-null-max-age`.
5. **Обязательные числа и поля тарифов.** В create-модалке: пустая цена тарифа → клиентская ошибка обязательного поля у цены (до фикса — RED: ошибки нет, уезжает на сервер); цена 0 принимается; `min_age` пустое → 0; длительность 0 → «Минимум: 15» (диапазон жив, положительный assert). → **компонентный тест**: `required-numbers-regression`.

## 5. Тестирование

- **E2E (Playwright)** — только дымовая пара: сценарии 1–2 из §4 (один новый файл, два коротких теста). Сценарий 1 закрывает починенный smoke-шаг «services edit-save» из visual-гейта #178.
- **Component/unit (vitest + testing-library)** — сценарии 3–5 из §4 (монтируем `ServiceModal` с фикстурой услуги/создания), плюс юниты на `validate` (пустое «до» без перекрёстной ошибки), нормализацию `'' → null` (только max_age), edit-маппер `ServicesTable` (больше не подставляет 18, PUT-ветка) и клиентскую валидацию элементов тарифов (пустая цена → ошибка у поля).
- **Сервер** — без изменений; существующие API-тесты покрывают null (схема уже `int | None`).

## 6. Риски и заметки

- Убрать `?? 18` в `ServicesTable.tsx:74` — изменение только PUT-ветки (create уже проходит null; уточнение панели rev2). Скрытой зависимости от 18 в коде скаут не нашёл.
- **Документ доменных правил устарел:** `docs/domain-rules/services.md` помечает `max_age` обязательным (0–18) и цитирует zod-правило, которого в коде нет (живой zod: `maxAge: z.string().optional()`, `packages/domain/src/index.ts:47`). Задача IMPL: поправить строку поля (`max_age` — опционально, `null` = без верхней границы) и убрать несуществующее zod-упоминание. Правка документации, коммитится вместе с имплементацией.
- Panel rev2: пустое `min_age` в create инициализируется 0 и валидно — существующее поведение, вне дельты.
- **Расширение скоупа решением пользователя (гейт C, 2026-09-19, «вариант B»):** клиентская валидация обязательных полей тарифов (§2 п.4) включена в эту задачу; отдельный issue под неё не заводится. Найдено план-ревьюером: два утверждения сценария 5 в rev3 не соответствовали живому коду (required-флаг тарифов не проверялся; длительность имеет min 15).
