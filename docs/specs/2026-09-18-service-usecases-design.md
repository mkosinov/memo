# Спека: слой сценариев (usecases) — «оркестратор вместо трактора»

- **Issue:** #171 (Рефактор сервисного слоя: оркестратор вместо трактора)
- **Дата:** 2026-09-18 · **Ревизия:** rev2 (переработана по итогам панели 6 ревьюеров и диалога с пользователем 18–19.09; rev1 — транзакционная модель с ре-энтрантностью и перенос «клиентов со статистикой» — сняты)
- **Статус:** Gate B — ждёт OK пользователя

## Контекст и проблема

Бэкенд админки устроен слоями: API-роуты (транспорт) → сервисы сущностей → слой репозиториев → таблицы базы; отдельно живёт слой домена — бизнес-правила (статусы записей, правила удаления, пересчёты мест/статуса). Правило слоёв: у каждой сущности свой сервис, и только он пишет в свою таблицу.

Это правило нарушает сервис записей: он пишет в чужие таблицы напрямую, минуя сервисы и репозитории владельцев:

1. При создании записи сам строит строки посещений (в цикле).
2. Там же сам находит или создаёт клиента по телефону.
3. Там же сам находит или создаёт посетителя по имени.
4. При полном обновлении записи стирает все посещения и пересобирает заново.
5. То же — при частичном обновлении (patch): в таблице issue этого пункта не было, факт найден скаутом.
6. При удалении записи сам сносит таблицы посещений и платежей.

Практическая цена: любое изменение поведения посещений/платежей (недавно — #285 «отложенное удаление», далее — #297/#298 «контракт отложенного удаления») требует помнить про «спрятанные» места в чужом сервисе; правило молча нарушается, тесты это не ловят.

**Уточнения фактов против текста issue:**
- Отложенное удаление #285 — фронтенд-пайплайн плюс серверная **проверочная** часть (поля `expected`/`resolutions`, отказ 409 при устаревшем снимке, сухой прогон); серверного **хране­ния** отложенных удалений нет, каскад удаления записи остался «жёстким». Рефактор затрагивает живой код удаления записей, изменённый PR #308.
- Тарифы — дочерние строки услуги без собственного жизненного цикла (нет эндпоинтов, нет сервиса, схемы вложены в схемы услуги): управление ими в сервисе услуг — законное владение, не нарушение.
- Кросс-табличные каскады существуют ещё в трёх местах вне сервиса записей (удаление занятия сносит записи/визиты/платежи; операции сотрудников создают/удаляют строки мастеров и пользователей; удаление клиента сносит посетителей) — это известный задокументированный долг, он НЕ входит в этот рефактор и учитывается оговоркой в каноне слоёв.
- Сервисов в дереве 18, а не 13 (как в issue).
- «Клиенты со статистикой» — читающая операция сервиса клиентов (один эффективный запрос с агрегатами по четырём таблицам): чтение чужих таблиц — нормальная реляционная выборка, грех этого рефактора — только запись. Функция НЕ переносится и не переписывается.

## Целевая модель слоёв

```
API-роуты        — транспорт: разобрать запрос → вызвать ОДНО действие → сформировать ответ
  ↓
usecases         — сценарии: бизнес-действия из нескольких сущностей
  ↓                 (декорированы @transactional: одна транзакция + события)
сервисы          — именованные операции своей сущности (двух разновидностей, см. ниже)
  ↓
репозитории      — единственное место табличных команд своей сущности
  ↓
таблицы
```

Правила модели:

1. **Один писатель.** Табличные команды (вставка/изменение/удаление строк) живут только в репозитории своей сущности; сервис владеет операцией, репозиторий — исполнением. Сервис записей больше не касается таблиц посещений, платежей, клиентов, посетителей.
2. **Сценарий** — публичная функция `usecases/`, названная бизнес-действием (`create_record`, `delete_record`). Декорирована `@transactional` ровно как сегодняшние методы сервисов: открывает транзакцию, коммитит, публикует накопленные события (механика живых обновлений #239 не меняется). Составляет только вызовы сервисов и доменных функций.
3. **Два вида методов сервиса:** с собственной транзакцией (декорированные — обслуживают свои эндпоинты: «удалить один платёж по номеру», «сменить статус посещения») и без транзакции (для сценариев: «снести все платежи записи», «найти или создать клиента по телефону»). Канон «одна операция — два входа»: декорированный тонкий метод поверх общего ядра без транзакции (прецедент — каскадное удаление посетителя).
4. **Bulk-операции — одна множественная команда**, не цикл по строкам: «удали все платежи этой записи» — единая команда репозитория с фильтром по собственной колонке-ссылке. Помощники получают **идентификаторы-значения** (`record_id`), не чужие объекты; импорт чужих моделей запрещён.
5. **Вложенные декорированные вызовы запрещены:** сценарий не вызывает декорированные методы сервисов. В этом пулл-реквесте такие вызовы не возникают по построению; механизм вложенных транзакций не строится. Появится реальная потребность (веб-бронирование #48) — отдельная задача с каноническим механизмом сохраняемых точек SQLAlchemy.
6. **Роут вызывает одно действие:** мульти-сущностный поток — сценарий; простая операция — сервис напрямую. Композиция вызовов внутри роута запрещена; коды ошибок и формат ответа — транспорт и остаются в роуте.

Полная карта коридоров обращения (включая третий — читающие композиты, к которому этот рефактор не прикасается) и дерево выбора «куда положить новый код» — в каноне слоёв `docs/domain-rules/service-layer.md`.

### Решения пользователя (Gate A + диалог по панели, 18–19.09)

1. Слой — папка `usecases`, файлы сценариев, каждая публичная функция — сценарий. Группировка (делегирована): файл = семейство сценариев одной центральной сущности; сегодня только `usecases/records.py` (4 сценария записи). Будущее (`booking.py` #48, сценарии #297/#298) — отдельными задачами, никаких заготовок.
2. **Транзакции — «двухкоридорная» модель** (правила 2–5 выше). Отклонены альтернативы: ре-энтрантный декоратор (панель: проверка «открыта ли транзакция» лжёт из-за автобegin; механизм не имеет потребителя в этом ПР), декоратор на роуте (граница бизнес-действия ≠ граница запроса; чтения; тесты; не-HTTP потребители), цикл «for id → декорированное одиночное удаление» (теряется атомарность «всё или ничего»: падение на седьмом платеже из десяти оставляет полуснесённую запись; 13 транзакций и 13 событий вместо одного пакета), каскад на уровне базы (отбирает явный контроль удалений — мир #194/#285).
3. **Bulk-исполнение — одна множественная команда.** Именованные методы живут на уровне репозитория: `delete_by_record_id` у репозитория платежей и аналогичные у репозиториев посещений (снос по принадлежности; вставка пачки). Репозиторный слой сегодня общий (один базовый класс) — при необходимости заводится специализированный репозиторий-наследник; механика — уровень плана, спека фиксирует место и имена операций.
4. **«Клиенты со статистикой» не переносятcя** — остаётся читающей операцией сервиса клиентов. Usecases в этом ПР — только сценарии записи.
5. **`delete_record` забирает всю бизнес-часть отложенного удаления:** сбор зависимостей, сверка снимка, каскад; роут оставляет транспорт (коды 422/409, формат ответа).
6. Тарифы и связки «услуга–теги» — собственные дочерние данные сервиса услуг: не трогаем. TagLinkService/TariffService не создаём (TagService для строк тегов уже существует).
7. Один пулл-реквест; откат = revert (миграций и флагов нет).

## Behavioral Delta

**Для пользователя — изменений нет.** Интерфейс, API-контракты, схемы запросов/ответов, содержимое базы — без изменений.

Для разработчика:

- Появляется слой `usecases`: `usecases/records.py` с четырьмя сценариями (`create_record`, `update_record`, `patch_record`, `delete_record`), каждый декорирован `@transactional` — одна транзакция и один пакет событий на сценарий.
- Сервис записей сужается до чтений (список, вид, получение, скоуп) и операций строки записи; декорированные `create/update/patch/delete` из него исчезают — эндпоинты записей зовут сценарии; `resolve_delete` переезжает в сценарий `delete_record` (бизнес-часть), транспортные коды остаются в роуте.
- Сервисы платежей/посещений/клиентов/посетителей получают методы без транзакции для сценариев: bulk-снос по принадлежности (одна множественная команда), вставка пачки посещений, «найти или создать» клиента/посетителя (перенос из сервиса записей, поведение один в один).
- Репозитории платежей и посещений получают именованные bulk-методы (`delete_by_record_id` и аналогичные) — табличные команды концентрируются в персистенс-слое владельца.
- Сервис услуг, «клиенты со статистикой», домен и остальные 13 сервисов — не трогаются.

## Транзакции (итоговая модель)

```
Эндпоинт «удалить платёж»                  — простая операция
  → PaymentService.delete (декорирован)    [1 транзакция + события]

Эндпоинт «удалить запись»                  — сценарий
  → usecases.delete_record (декорирован)   [1 транзакция + один пакет событий]
      → VisitService.delete_visits_by_record (без транзакции)
          → репозиторий посещений: команда сноса по принадлежности
      → PaymentService.delete_by_record    (без транзакции; id-значение на входе)
          → репозиторий платежей: delete_by_record_id   [одна множественная команда]
      → репозиторий записей: снос связок record_tags (своё ребро записи)
      → RecordService: удалить строку записи (без транзакции)
```

- Декоратор `@transactional` не меняется: как сегодня, открывает транзакцию, коммитит и публикует накопленные события (механика #239 сохраняется без переделок — сценарий для него «просто ещё один декорированный вызов»).
- Падение любого шага сценария откатывает всё — частичных записей нет; инвариант «один HTTP-запрос = одна транзакция» сохраняется.
- Порядок шагов внутри сценариев — сегодняшний, включая interleaving пересчётов: снос посещений → пересчёт мест → проверка вместимости → вставка пачки (иначе двойной подсчёт мест).
- Пометки кэша (`mark_changed`) делают методы-помощники по своей сущности (посещения — «посещения», платежи — «платежи»); набор помеченных коллекций идентичен текущему.

## Тесты и критерии приёмки

1. Существующий API-набор записей (`test_api_records.py`, включая deferred-delete; `test_api_services.py`; клиентский набор) проходит **без правок** — контракт и поведение не меняются. Существующие тесты каскадов (`test_delete_cascades.py`) — зелёные.
2. Сервисные юнит-тесты перенесённых тел перепривязываются на сценарии (`services/test_record_service.py` — части create/update/patch/delete); тесты сервисов платежей/услуг — без правок.
3. Новые тесты атомарности — по одному на каждый сценарий (US1–US4): принудительный сбой шага в середине → в базе нет частичных изменений (ни осиротевших посещений, ни платежей, ни строки записи).
4. Инварианты слоёв (ревью + канон в domain-rules): сервис записей не импортирует модели посещений/платежей/клиентов/посетителей; сценарии не импортируют модели напрямую; табличные команды — только в репозиториях владельцев; скоуп мастера (`master_key`) передаётся роутом в сценарий без изменений.
5. Гонки «найти-или-создать» и поведение пустого списка посещений — семантика не меняется (не тестируется новыми случаями, фиксируется фразой «как сегодня»).

## Риски и смягчения

- **Перенос живого кода удаления записей** (вчера изменён #285): гарант — неизменность deferred-delete набора API-тестов.
- **Первые специализированные репозитории** (если наследники базового не существуют): новый узор для проекта; механика и точка врезки — план, риск локальный.
- **Помощник не глотает исключения молча** — иначе сценарий закоммитит частичный результат; правило в каноне, гарант — тесты атомарности.
- **Параллельные сессии** (IMPL #192, дизайн #138) — коммит строго своих файлов; push после fetch-верификации.
