# Спека: chore(admin) — спуск линт-порога 38→0 (#301)

Дата: 2026-09-19 · Статус: ожидает OK пользователя (Gate B) · Issue: #301
База: решение #143 для `frontend/admin` (порог-потолок, коммит `9852dd5` / PR #307); родственная дорожка #300 (зеркало для `frontend/web`).

## 1. Контекст и проблема

После #143/#307 линт в `frontend/admin` включён честным порогом-потолком:
`frontend/admin/package.json:9` — `"lint": "eslint . --max-warnings 38"`,
`frontend/admin/.eslintrc.json` — `ignorePatterns: [".next/", "e2e/", "__tests__/"]`.
Новый warning делает линт красным, но существующие 37 остаются навсегда.

Замер на живом дереве (2026-09-19, скаут, ESLint 8.57.1, конфиг legacy eslintrc):

| Правило | Шт. |
|---|---|
| `@typescript-eslint/no-unused-vars` | 15 |
| `react-hooks/exhaustive-deps` | 11 |
| `@next/next/no-img-element` | 6 |
| `@typescript-eslint/no-explicit-any` | 5 |
| **Итого** | **37** (0 errors) |

По каталогам: `app/` 31, `contexts/` 5, `hooks/` 1, `lib/` 0. CI гоняет ровно
этот скрипт: job `frontend-checks` (`.github/workflows/test.yml:93`) делает
`pnpm run lint`, а следом `pnpm run type-check` и z-token guard в том же job'е —
все три проверки должны оставаться зелёными на каждом шаге.

Поправки к телу issue по факту разведки (внесены комментарием на issue):

1. Порог в package.json **38, а не 37** — честный пересчёт сделан уже в #307
   (18.09); в момент слияния счёт был 38, с тех пор один warning ушли соседним
   PR, запас в 1 единицу остался.
2. Команда — `eslint .` с ignorePatterns; глобы из Verification-секции issue
   (`'app/**/*.{ts,tsx}' …`) остались от до-#143 скрипта и ни с чем не
   совпадают.
3. Сама перепись (37; 15/5/6/11; 31+6) подтверждена один в один.
4. Ко-локейшн тесты внутри `app/` **линтятся** (игнорится только top-level
   `__tests__/`): в `app/components/shared/record/InlineEditRow.test.tsx` два
   предупреждения — одно `no-unused-vars` (неиспользуемый `row`, строка 32) и
   одно `no-explicit-any` (строка 40).

Сценарии сформулированы для разработчика и CI; E2E-браузерные тесты к chore-задаче
неприменимы (поведения приложения правки не касаются) — у каждого сценария указан
тип механической проверки.

## 2. User Scenarios

- **S1. Новый warning ломает линт.** После спуска до 0 разработчик добавляет
  в `frontend/admin` код с новым предупреждением → `pnpm lint` завершается
  с ошибкой. Проверка: ввести тестовый warning, убедиться в exit ≠ 0, удалить.
- **S2. Каждая ступень ratchet'а зелёная — локально и в CI.** После каждой
  группы фиксов линт проходит при пороге, равном фактическому остатку, и
  «родственные» проверки того же CI-шага не ломаются. Проверка: `pnpm lint`,
  `pnpm run type-check` → exit 0 на каждом промежуточном коммите; зелёный
  прогон `frontend-checks` на ветке (чужой PR с новым warning получает красный
  линт тем же механизмом, что S1).
- **S3. Поведение хуков не изменилось.** Цель правок `exhaustive-deps` —
  сохранить видимое поведение (перерендеры, запросы, сбросы форм); сама правка
  зависимостей по определению может сдвинуть момент запуска эффекта, поэтому
  каждая — под проверкой. Проверка: витест-набор admin зелёный после группы;
  для каждого изменённого хука — ручная проверка поведения (открыть
  страницу/модалку, где хук живёт: данные грузятся, ничего не зациклилось,
  введённое пользователем не сбрасывается); перечень проверенных хуков с
  результатом фиксируется в описании PR.
- **S4. Картинки показываются как прежде.** Логотип и аватары отрисовываются
  через `next/image` и выглядят как раньше (круглые аватары в клетках таблиц,
  логотип в меню, превью при загрузке аватара); фото в таблице «Фото» —
  без изменений. Проверка: ручной осмотр перечисленных мест после группы
  картинок; существующие e2e зелёные.
- **S5. Подавления документированы.** Каждый новый `eslint-disable-next-line`
  имеет однострочное обоснование в комментарии; молчаливых подавлений среди
  новых нет. Проверка: grep `eslint-disable` (обе формы — next-line и
  trailing) по файлам правок; старые подавления в других файлах не трогаются
  и под критерий не попадают.

## 4. Решение (концепт единственный)

Спуск ratchet'а до нуля починкой всех 37 предупреждений группами, в порядке из
issue: **unused-vars (15) → no-explicit-any (5) → no-img-element (6) →
exhaustive-deps (11)**. После каждой группы: коммит, порог в package.json
опускается до фактического остатка (ориентиры 38 → 22 → 17 → 11 → 0), линт,
type-check и CI зелёные. Единственное правило ratchet'а — порог всегда равен
факту: если один фикс попутно убирает чужой warning, порог опускается на
фактический счёт, а не на план.

Политики по группам:

1. **`no-unused-vars` (15)** — распределение по живому прогону и политики:
   - **Мёртвые локальные сущности (3) — удалить целиком:** функция-обработчик
     `handleWeekClick` и внутренний компонент `MasterLegend` в `Menubar`,
     вычисляемое значение `dateTo` в `ScheduleViewContext`. Все три —
     присваивания без вызовов, побочных эффектов нет (проверено по коду).
     Уточнение по `MasterLegend`: это мёртвая копия функции в том же файле,
     нигде не отрисованная (не экспортирована, вызовов нет); видимый блок
     «Мастера» в меню — отдельный живой код, его правка не касается.
     Общий предохранитель остаётся: если инициализатор переменной вызывает
     функции (side effects) — только переименование, не удаление.
   - **Мёртвые props и аргументы (5) — удалить:** `onDelete` в
     `ClientInfoTab` (необязательный prop, ни один вызов не передаёт —
     удаление клиента живёт на уровне модалки карточки, не вкладки),
     `activity` в `NewRecordTab` (единственный вызов передаёт занятие
     целиком, вкладка его не читает — убрать prop и строку вызова;
     привязку записи к занятию добавляет сам обработчик сохранения
     в модалке), `recordStatus` в `RecordVisitsTable` (два вызова
     передают; внутри таблицы режим «только чтение» управляется отдельным
     явным prop `isReadOnly`, передаваемый статус никем не читается —
     убрать prop и строки вызовов; вычисление статуса в вызывающем коде
     остаётся, оно используется ещё в другом месте), `updated` в
     `RecordPaymentsTable` (не prop, а проигнорированный результат
     сохранения в callback — убрать параметр сигнатуры), `isPreview` в
     `VisitorRow` (задуманный «режим превью», ни один вызов не включает).
     Проверено по коду 19.09: удалённое никем не читается, поведение
     измениться не может.
   - **Параметры, остающиеся в контракте (6) — `_`-префикс:**
     `mode` в пяти модалках справочников и `value` в
     `RemoteSearchSelect` (правило игнорит `^_`; переименование внутреннее,
     вызывающие стороны и контракты не затрагиваются). Их судьба по
     существу — follow-up #368 (заведён по решению пользователя от 19.09).
   - **Аргумент в тесте (1) — `_`-префикс:** `row` в
     `InlineEditRow.test.tsx`. Ко-локейшн тесты остаются под линтом:
     выведение их в ignorePatterns меняет смысл счётчика и вне скоупа.
2. **`no-explicit-any` (5)** — по каждому месту, решение 19.09:
   - **`ClientTab` ×2** (`{visits} as any`, `{comment} as any`): касты-
     реликты — локальный тип обёртки `updateRecord` в админке
     (`RecordPatchData`) уже описывает оба payloads (comment; visits
     c `visitor_id`/`tariff_id`/`price`/`custom_price`/`status`).
     Исправление: убрать оба каста; поведение не меняется по построению
     (каст — инструмент компиляции, на выполнение не влияет). Гейт:
     type-check зелёный; если каст вдруг окажется несущим — честно
     расширить `RecordPatchData` (он живёт в админке, не в пакете).
   - **`ClientCardModal`** (`newClient as any`): создание клиента
     возвращает клиента без статистики, а колбэк ожидает «клиента со
     статистикой». Исправление: собрать объект честно — свежесозданный
     клиент реально имеет нули: `{...newClient, records_count: 0,
     last_record: null, total_paid: 0, missed_records: 0}`. Побочный
     эффект: блок статистики в карточке покажет нули вместо пустых
     значений (раньше туда попадал объект без полей статистики).
   - **`InlineEditRow` + его тест** (`value: any` в сигнатуре
     `handleChange`): заменить на объединение типов значений формы —
     `value: F[keyof F]`; тест зеркалит ту же аннотацию. Если внутренняя
     запись состояния не удовлетворит компилятор — сначала
     реструктуризация записи; единое обоснованное подавление — последнее
     средство по лестнице §4.4.
   Общее: без `@ts-ignore`; правки только в admin — пакеты-воркспейсы
   (`@memo/domain`, `@memo/api-client`) не затрагиваются (потребность
   не возникла: оба payloads уже покрыты локальным типом админки).
3. **`no-img-element` (6)** — решение пользователя от 19.09 (диалог Gate B),
   по фактам разведки: ни одна из шести картинок не защищена авторизацией
   бэкенда.
   - **Логотип и аватары (4 места: логотип меню, аватар сотрудника в таблице,
     аватар в меню пользователя, превью в «Моих данных») → `next/image`.**
     Все четыре публичны: логотип — статика самого приложения; аватары бэкенд
     раздаёт как публичную статику (осознанное решение #262 — маунт
     `/api/v1/files/avatar` без проверки входа). Хост бэкенда один и известный,
     адреса аватаров идут с отдельного от приложения хоста — в
     `next.config.mjs` добавляется одна запись `images.remotePatterns`.
     Польза: файл аватара может весить до 5 МБ, показывается в клетке 48 px —
     браузер получит сжатый размер. Сопровождение: правка разметки в четырёх
     местах (аватары круглые, клетка фиксированная — проверить раскладку),
     возможно добавление пакета `sharp` (оптимизатору в прод-сборке),
     обновление design-system (логотип там описан как `<img>`).
   - **Фото (2 места: миниатюра в таблице «Фото», превью в модалке
     редактирования) → остаются `<img>`** с локальным
     `eslint-disable-next-line @next/next/no-img-element` и однострочным
     обоснованием. Обоснование по существу: запись фото — внешняя ссылка в
     поле `filename` (файлов фото бэкенд не хранит, эндпоинта загрузки нет),
     хосты произвольные; разрешать оптимизатору «любой адрес» нельзя — он
     станет общедоступным прокси для чужих картинок (чужой трафик через нас
     + возможность зондировать внутренние адреса).
   - **Запасное решение на будущее** (в спеке, вне скоупа): если фото станут
     приватными файлами на нашем бэкенде — каноничный приём из документации
     и практики Next.js: собственный маршрут-прокси в приложении, проверяющий
     доступ (cookies браузера либо короткоживущий токен в адресе), как `src`
     для `next/image`; при отказе от оптимизации — `unoptimized`. Оптимизатор
     по документации не передаёт заголовки пользователя (с Next.js 15.4.5 —
     вообще никакие), поэтому приватная картинка напрямую ему не отдаётся
     никогда.
4. **`exhaustive-deps` (11)** — решение 19.09 по каждому месту (лестница:
   честный фикс по рецепту правила; подавление — только где фикс доказанно
   меняет поведение):
   - **Убрать лишнюю зависимость (2)** — `clientId` в `ClientRecordTab` и
     `ClientTab`: колбэки его не читают; удаление делает их стабильнее.
     Изменений поведения нет.
   - **Добавить неизменную зависимость (2)** — `initial` в `MyDataModal`
     (замороженный снимок формы: `useRef(...).current`, идентичность не
     меняется никогда — добавление инертно) и `resetActiveGroup` в
     `DayColumn` (`useCallback` с пустым списком — полностью стабилен).
     Изменений поведения нет.
   - **Деструктурировать стабильную функцию (3)** — `ScheduleDataContext`:
     вместо объектов мутаций (`createMutation`/`updateMutation`/
     `copyWeekMutation`, новая идентичность каждый рендер) в зависимостях —
     их стабильные `mutateAsync`; комментарий в коде прямо предупреждает,
     что объекты в зависимостях сломали бы мемоизацию значения контекста.
   - **Сначала мемоизировать, затем добавить (1)** — `Combobox`:
     `visible` (`useMemo`) и `optionDomId` (`useCallback`), затем оба —
     в зависимости эффекта; иначе эффект побежит на каждом рендере.
   - **Скопировать значение внутрь эффекта (1)** — `UIContext`: локальная
     копия `toastTimers.current` в начале эффекта, cleanup использует копию
     (рецепт самого правила; безопасно — ref не переприсваивается, только
     мутируется методами).
   - **Сделать повторные запуски нейтральными и добавить зависимость (1)** —
     `useColumnReorder`: `initialOrder` добавляется в зависимости
     синхронизирующего эффекта; повторные запуски гасятся коротким
     замыканием reconcile (нет новых колонок → вернуть прежний массив без
     смены идентичности) — заодно уходит лишний повторный вызов сохранения
     порядка. Первичная инициализация уже защищена рефом «только первый
     запуск».
   - **Подавление с обоснованием (1)** — `SettingsTab` (`gridFrequency`):
     честное добавление зависимости перезапускает эффект при смене сетки
     и сбрасывает незавершённые правки формы — единственный случай, где
     подавление оправдано по существу.
   Ручная проверка поведения (S3) по затронутым экранам: карточка клиента
   (вкладка записей), карточка записи (вкладка клиента, смена статусов,
   сохранение комментария), настройки занятия (смена сетки не сбрасывает
   правки), «Мои данные» (правка профиля), расписание (создание/перенос
   занятия, копирование недели, колесо мыши в колонке дня, порядок колонок
   сохраняется после перезагрузки), поиск-комбобокс (навигация стрелками),
   тосты (появление и исчезновение).

Форма подавлений: все новые — `eslint-disable-next-line <правило> -- причина`
в той же строке. Существующее подавление в `InlineEditCell.tsx` (next-line без
`-- причины`) и trailing-форма в `DayView.tsx` не переписываются — они вне
счёта этой задачи.

Подходы, отвергнутые на Gate A и в диалоге Gate B:

- **Перевести фото (внешние ссылки) на `next/image` с разрешением «любой
  хост»** — оптимизатор становится общедоступным прокси для произвольных
  адресов; отвергнуто.
- **`<Image unoptimized />` для всех шести картинок** — пользы нет, разметку
  править пришлось бы всё равно; для публичных мест выбран полноценный
  `next/image`, для фото — подавление.
- **Отключить правило `no-img-element` или оставить 37 как есть** — ломает
  конвенцию ratchet'а #143: правила не трогаем, порог только вниз.
- **Вывести ко-локейшн тесты из линта** — вне скоупа, меняет смысл порога
  (что считается — решено в #143).

## 5. Скоуп

- **В скоупе:** исходники `frontend/admin` с предупреждениями (точечные фиксы
  и обоснованные подавления), `frontend/admin/package.json` (число
  `--max-warnings`, возможно зависимость `sharp`),
  `frontend/admin/next.config.mjs` (одна запись `images.remotePatterns`),
  `docs/design-system.md` (фрагмент про логотип: `<img>` → `next/image`).
- **Вне скоупа:** `.eslintrc.json` (правила и ignorePatterns не меняются),
  flat config / обновление ESLint, модернизация фото-хранилища (маршрут-прокси,
  перенос файлов фото на бэкенд), выведение тестов из линта, чистка
  контрактов компонентов (например, отказ от `mode` в модалках),
  `frontend/web` (#300), бэкенд, пакеты-воркспейсы. Заметка на
  будущее: официальный механизм bulk-подавлений ESLint 9+ здесь недоступен
  вдвойне — требует новой версии ESLint (сейчас 8.57.1) и не подавляет
  правила уровня `warn`, а все четыре правила именно `warn`; конвенция
  «порог 0 + обоснованные локальные подавления» осознанно сохраняется и после
  любой будущей миграции на ESLint 9/10.

## 6. Открытые вопросы (Gate B)

1. Порог-ступени (22 → 17 → 11 → 0) — ориентиры; при имплементации порог
   каждый раз ставится по факту, отклонение от ориентира само по себе не
   проблема (возврат на Gate B нужен только если фактический счёт в какой-то
   группе не сходится с переписью 15/5/6/11 — значит, дерево ушло вперёд).

Решения, принятые в диалоге Gate B 19.09 (зафиксированы, вопросами не являются):
