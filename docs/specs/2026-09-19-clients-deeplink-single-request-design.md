# Спека: #231 — deep-link клиентов: один запрос вместо двух (инициализация фильтров из URL)

- **Issue:** #231 (enhancement, frontend, app:admin)
- **Дата:** 2026-09-19, rev3 (пересборка поверх смерженного #138 по решению пользователя; панель 6/6 отработала, правки внесены)
- **Статус:** Gate B (ждёт OK пользователя)
- **Зависимости:** нет — #138 смержен (In-main), строим поверх его результата

## 1. Контекст и проблема

#216 подарил deep-link: ссылка `/clients?clientId=X` открывает карточку клиента. Механика сегодня (перепроверено по живому дереву после мержа #138, 2026-09-20):

1. Страница `/clients` монтируется, контекст клиентов (`frontend/admin/contexts/ClientsContext.tsx` — экземпляр фабрики `createPagedListContext`) инициализирует фильтры дефолтами (`search: ''`, `status: 'active'`, страница 1).
2. Первый рендер -> React Query стреляет GET `/api/v1/clients` с дефолтными фильтрами.
3. Эффект `frontend/admin/app/(main)/clients/page.tsx:32-36` (эффекты идут **после** первого рендера) читает `?clientId=` и вызывает `setFilters({ search: X, status: 'all' })`.
4. Ключ запроса меняется -> второй GET, уже суженный (`q=<uuid>&status=all`). Ответ первого запроса выбрасывается.

Итог: **каждый переход по deep-link = два сетевых запроса, первый — мусорный**. Осознанная уступка #216 (§5.1 «Acknowledged cost», §10 cleanup (b)) — тогда минимизировали дифф. Мерж #138 эффекты deep-link не тронул — проблема жива.

Факты разведки (обновлены под ландшафт после #138):

- Контекст клиентов — экземпляр фабрики `createPagedListContext` (с #140); сид фильтров — обычный `useState` из `config.filters?.defaults` (`createPagedListContext.tsx:150`), провайдер принимает только `children` (:143), оба экспортных типа перегрузок — только `children` (:121, :125).
- Дерево страницы после #138 §2.5: `ClientsProvider` → `GridSettingsProvider` (стек расписания снят со страницы) → `Suspense` → `ClientsPageContent`, который читает `useSearchParams()` во время рендера (:19-21). Читатель параметра — **ребёнок** провайдера: затравку нельзя пробросить сверху — нужна перестройка границы (§5.2).
- #138 ввёл в репозиторий эталонный паттерн «URL как источник правды»: хук `hooks/useScheduleView.ts` — единственная точка чтения/записи URL-полей страницы, парсинг параметров **во время рендера**, строгие парсеры значений. Конвенция #138 §2.4 (запечатана на Gate A): фильтры любой табличной страницы в перспективе живут в её URL; каждая следующая страница повторяет паттерн schedule/records; на третьей странице паттерн сводится в общий хук (правило трёх).
- Deep-link продаётся ровно одним местом — `window.open` (полная загрузка страницы, `ActivityDetailsModal.tsx:177,183`).
- Производственная точка монтирования `ClientsProvider` одна: `page.tsx`. Тесты: `__tests__/ClientsContext.factory.test.tsx` (реальный провайдер), `__tests__/ClientsPage.test.tsx` — провайдер замокан простой обёрткой (:33-38), там же мок `GridSettingsProvider` и анти-регрессия на `ScheduleProvider` (:12-26), и два теста завязаны на умирающий эффект: `:337-350` ассертит вызов `setFilters` с затравкой deep-link, `:354-366` — «без параметра `setFilters` не вызывается». `__tests__/Providers.test.tsx` — про глобальное дерево `providers.tsx`, дерево страницы не стережёт.
- `setFilters` в фабрике — merge-патч поверх текущих фильтров (:201-204); `resetFilters` возвращает конфиговые дефолты (:206-209).
- e2e deep-link: `frontend/admin/e2e/clients.spec.ts:703`, тест 19; готовый приём подсчёта запросов — US-1 там же (:770-786): `page.on('request')` до `goto` + ожидание своего ответа + короткое окно (SSE-поток #239 никогда не даёт `networkidle`).

## 2. Концепт (Gate A)

**Выбрано: сид начальных фильтров из URL при монтировании.** Страница читает `?clientId=` во время рендера **над** провайдером и передаёт затравку однократным пропом; фабрика мержит её поверх дефолтов в ленивом инициализаторе `useState`. Это тот же идиомат, который #138 сделал фирменным стилем репозитория (чтение URL-полей во время рендера в хуке страницы) — применён к точечной задаче одного параметра. URL фабрика не читает — остаётся «тупой».

**Почему не другие подходы:**

- *URL-осведомлённая фабрика* (все paged-контексты читают URL при рождении) — отклонено: переусложнение ради одного сценария (YAGNI), меняет поведение всех 8 списков разом и упреждает #232, где архитектура deep-link будет пересматриваться по собственным условиям активации.
- *Подавление первого запроса флагом* (`enabled: false` до конца инициализации) — отклонено: то же видимое поведение, но внутри хуже — машина состояний «инициализация кончилась» и задержка первого запроса для ВСЕХ монтирований, включая обычный `/clients`. Различия только во внутренностях — не отдельный концепт.
- *Полный перенос фильтров клиентов в URL сейчас* (search/status/sort/page — живая синхронизация, правило трёх) — отклонено: скачок скоупа. #231 — точечная оптимизация мусорного запроса; конвенция #138 §2.4 сама говорит «в перспективе» и относит общий хук к будущему; сид и перестройка границы — посадочная площадка, делающая ту миграцию дешёвой (см. §5.4).

## 4. Behavioral Delta (до → после)

| | До | После |
|---|----|----|
| Переход по `/clients?clientId=X` (полная загрузка) | 2 GET списка: мусорный дефолтный + суженный; открытие карточки ждёт второго ответа | **1 GET**, сразу суженный (`q=<uuid>&status=all`); карточка открывается по первому ответу — лишний запрос исчезает |
| Открытие `/clients` без параметров | 1 дефолтный GET | без изменений: 1 дефолтный GET |
| Поиск, задержка 300 мс, порог 2 символов, сортировка, пагинация | — | без изменений |
| Снятие `?clientId=` с URL при закрытии модалки и у мёртвой ссылки | — | без изменений |
| «Сбросить фильтры» на deep-link-странице | возвращает дефолты | без изменений: возвращает дефолты (сид — только начальное состояние, сброс к нему не возвращается) |
| Параметр в URL меняется/появляется **после** монтирования (ручная правка адреса на живой странице) | эффект сужает таблицу под новый параметр | параметр больше не подхватывается: читается только при монтировании (продюсеров сценария нет — deep-link всегда полная загрузка через `window.open`) |
| Back после deep-link | снятие параметра идёт через replace (без записи в историю), поэтому back обычно не возвращает к `?clientId=`; если вернёт (двойной deep-link) — модалка переоткрывается: latch был сброшен после ухода параметра | без изменений: даже если провайдер перемонтируется, сид пересчитает то же значение из того же URL — поведение идентично свежему deep-link (1 запрос) |
| Мусорный параметр <2 символов (напр. `?clientId=x`) | кламп прячет его из запроса, список дефолтный непуст, параметр остаётся в URL | без изменений: сид переносит значение дословно, как сегодняшний эффект — quirk сохраняется |

## 5. Технический дизайн

### 5.1 Фабрика `createPagedListContext.tsx`

- Внутренний провайдер (:143): сигнатура получает `initialFilters?: Partial<F>`.
- Сид (:150): ленивый инициализатор `useState<F | undefined>(() => initialFilters ? { ...filtersDefaults, ...initialFilters } : filtersDefaults)` — однократно при монтировании; merge-семантика совпадает с `setFilters` (:201-204). Последующие смены пропа игнорируются: сид задаёт начальное состояние, не живую синхронизацию. StrictMode-двойной вызов безопасен (чистое чтение значения); каждый монтаж провайдера — новый экземпляр состояния.
- Экспортные типы обновить адресно: проп появляется только в типе провайдера **with-filters перегрузки** (:121, у неё есть `F`); классическая перегрузка без фильтров (:125) остаётся с типом `{ children }` — проп ей не доступен.
- Без изменений: `setFilters`/`resetFilters`, ключ запроса (:160-166), кламп ≥2 символов (:155), `keepPreviousData`. Прочие 7 экземпляров фабрики (Records и Photos — не экземпляры: импортируют только тип сортировки) проп не передают — путь по умолчанию не тронут.

### 5.2 Страница `app/(main)/clients/page.tsx` — перестройка границы

Сегодня (после #138): `ClientsProvider` → `GridSettingsProvider` → `Suspense` → `ClientsPageContent` (читает параметр). Читатель — ребёнок провайдера, сид сверху не пробросить. Структура меняется на:

```
ClientsPage (default export)
└── Suspense                      // граница поднимается на самый верх
    └── ClientsPageInner          // читает useSearchParams() во время рендера, считает затравку
        └── ClientsProvider initialFilters={...}
            └── GridSettingsProvider   // порядок #138 сохраняется
                └── ClientsPageContent   // прежнее содержимое, БЕЗ эффекта :32-36
```

- `ClientsPageInner`: при наличии параметра собирает `{ search: clientId, status: 'all' }` (остаток полей добьёт merge с дефолтами), иначе ничего не передаёт. Значение переносится дословно, без валидации — валидация изменила бы краевое поведение мусорных параметров (см. §4), а машина мёртвой ссылки уже разруливает невалидные значения.
- **Удаляется только эффект `setFilters` (:32-36).** Остальная механика #216 сохраняется построчно, у каждой своей роли:
  - сброс latch после ухода параметра с URL (:40-44) — close-race #216;
  - поиск клиента в суженной таблице и авто-открытие модалки (:49-61) — открывается по первому ответу;
  - зачистка параметра у мёртвой ссылки (:63-76, «0 строк и модалка не открылась» — E1 из #216);
  - снятие параметра при закрытии модалки (:117-120).
- Тайминг: провайдеры уходят внутрь `Suspense` — первый GET теперь стреляет после разрешения границы. Видимой разницы нет: снаружи границы сегодня не рендерится ничего наблюдаемого (только провайдеры-обёртки), фолбэк «Загрузка...» и сегодня первый видимый кадр.
- Переименование `search` → `q` при ≥2 символах (`ClientsContext.tsx:51-53`) накрывает UUID без изменений.

### 5.3 Что сознательно НЕ делаем

- Живая двусторонняя синхронизация URL ↔ фильтры клиентов — «в перспективе» по конвенции #138 §2.4; клиенты держат контекстное состояние между монтированиями, как сейчас.
- Параметр `?id=` с серверным разрешением страницы — #232, активируется по своим условиям.
- Подхват параметра, прилетающего **после** монтирования страницы: сегодня эффект (:32-36) реагирует на смену параметра, но продюсеров такого сценария нет (deep-link ездит только через `window.open`), back-повтор поглощён latch'ем — поведение сознательно сужается до «параметр читается при монтировании».
- Трогать задержку поиска, кламп, `keepPreviousData`, механику снятия параметров, обобщать URL-чтение внутрь фабрики.
- Верхний кламп длины затравки: не добавляется — администратор и сегодня может вбить в поиск строку любой длины руками; путь значения и обработка ошибок те же (безопасность: поверхность не меняется, вердикт панели).

### 5.4 Связь с #138: посадочная площадка для будущих URL-фильтров

Конвенция #138 §2.4: фильтры табличных страниц в перспективе живут в URL; на третьей странице паттерн сводится в общий хук (правило трёх). Эта спека строит ровно те два элемента, которые та миграция унаследует без переделки:

1. **Шов `initialFilters` на фабрике** — точка, куда будущий clients-URL-хук положит начальные значения, вычисленные из `?q=&status=`; когда это случится, сид станет частным случаем URL-инициализации (параметры deep-link + параметры фильтров мержатся в одну затравку).
2. **Перестройка границы страницы** (читатель параметра над провайдером, Suspense сверху) — необходимое условие любой URL-инициализации состояния списка; после этой спеки она уже сделана.

Переписывается при той миграции только парсинг «параметры → затравка» внутри `ClientsPageInner` (несколько строк). Инвариант «deep-link = ровно один запрос» переживает миграцию: e2e-счётчик из §6 остаётся стражем.

## 6. Тесты

- **Unit (фабрика, `ClientsContext.factory.test.tsx`):** провайдер с `initialFilters` сидирует merged-фильтры; без пропа — дефолты из конфига; смена пропа после монтирования не меняет состояние; `resetFilters` возвращает конфиговые дефолты, а не сид.
- **Unit (страница, `ClientsPage.test.tsx`):** два существующих теста эффект-эры переписываются под сид-эру — `:337-350` («deep-link сужает таблицу через setFilters») → ассерт, что мок `ClientsProvider` получил `initialFilters={search: id, status: 'all'}`; `:354-366` («без параметра setFilters не вызывается») → ассерт, что проп не передан. Новых тестов сверх переписанных не добавляется (границу «параметр после монтирования не подхватывается» покрывает сама переписанная пара: смена параметра после монтирования не меняет переданный проп).
- **E2E (`clients.spec.ts`, describe «Deep-link ?clientId=»):** новый тест S1 — счётчик через `page.on('request')`, зарегистрированный **до** `goto` (приём US-1 :770-786); слушатель считает **все** запросы `/api/v1/clients*` (предфильтрация по `q=` скрыла бы убитый дефолтный запрос — регрессия стала бы невидимой); окно закрывается ожиданием суженного ответа + 500 мс; ассерт: ровно 1 запрос, и его URL содержит `q=<uuid>&status=all`. Условия стабильности: контекст каждого теста холодный (нет `beforeEach`/`storageState`), `refetchOnWindowFocus`/`refetchOnReconnect` выключены, SSE-кадры инвалидации прийти не могут (все создания данных — до `goto`, EventSource не повторяет кадры до подключения). Принятый остаточный риск флейка: transient-ошибка сети в окне ретраится React Query (`retry: 2`) и читается как «два запроса» — тот же остаточный риск, что у US-1. Для S2 (обычный `/clients`) счётчик сознательно не строится: поведение не меняется, стражем регрессии остаётся S1-счётчик. Тест 19 не правится вообще (его 10-секундный таймаут модалки заодно подтверждает, что задержка первого GET до разрешения Suspense-границы неощутима).
