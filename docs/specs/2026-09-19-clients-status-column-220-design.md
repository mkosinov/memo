# Спека: Таблица клиентов — колонка «Статус» (архив/активен) — #220

Дата: 2026-09-19 · Issue: [#220](https://github.com/mkosinov/memo/issues/220) · Gate A: решён юзером 19.09 (вариант B — колонка скрыта) · Gate B: ОК 19.09 + унификация — колонка скрыта по умолчанию у всех архивируемых сущностей

## Контекст и проблема

На странице «Клиенты» таблица показывает пять колонок: Имя / Телефон / Всего записей / Последняя запись / Сумма оплат. Архивное состояние клиента нигде не видно — только по подписи кнопки в меню действий строки («В архив» / «Восстановить»).

Проблема обострилась после #216 (deep-link `/clients?clientId=N`): по такой ссылке может открыться архивный клиент (deep-link осознанно ставит фильтр статуса в «all», чтобы строка была видна), но пользователь не может понять, что клиент в архиве.

Архивируемые сущности системы (soft-delete, поле `archived` в схемах API-клиента): **клиент, сотрудник/мастер, локация, услуга, материал**. Теги, позиции, фото, записи — не архивируются (жёсткое удаление, #189/#194/#207).

## Решение (Gate A)

Добавить в таблицу клиентов колонку **«Статус»** с бейджем «Активен» / «Архив» по существующему паттерну таблиц справочников. Колонка **скрыта по умолчанию** (`defaultVisible: false`), включается через кнопку-шестерёнку «Настроить колонки» (ColumnPicker), выбор запоминается между сессиями.

**Унификация (решение юзера на Gate B):** колонка статуса/архива скрыта по умолчанию у **всех** архивируемых сущностей — у сотрудников и материалов она сейчас показывается сразу и переводится в скрытую. Разнообразия «у кого-то видна, у кого-то скрыта» больше нет; подписи колонок остаются без изменений (сотрудники — «Архив», остальные — «Статус»).

**Сознательно НЕ строим:**
- затемнение архивных строк (новый визуальный паттерн, которого нет ни у одной таблицы);
- изменения фильтров и deep-link-логики (они уже корректны);
- серверные правки (данные уже приходят; колонка создаётся несортируемой — см. техническое резюме);
- переименование подписи колонки сотрудников («Архив» → «Статус») — унифицируется только видимость по умолчанию, не подпись;
- починку существующих a11y-пробелов пикера (`aria-expanded`/Escape) — отдельная задача, не этот дизайн;
- отдельный live-region для объявления смены статуса скринридеру — полагаемся на существующий тост мутации.

## Аудит «архивируемая таблица → колонка в опциях» (требование юзера, Gate A)

Проверено по живому дереву (19.09, после мержа #139 — колонки в пер-сущностных конфигах):

| Сущность | Конфиг колонок | Колонка в «Настроить колонки» | Видна по умолчанию | Вердикт |
|---|---|---|---|---|
| Клиент | `clientColumns.tsx` | **нет** | — | **ФИКС 1 — добавить (скрытой)** |
| Сотрудники/мастера | `staffColumns.tsx` | да («Архив») | **да** | **ФИКС 2 — скрыть** |
| Локации | `locationColumns.tsx` | да («Статус») | нет | ок |
| Услуги | `serviceColumns.tsx` | да («Статус») | нет | ок |
| Материалы | `materialsColumns.tsx` | да («Статус») | **да** | **ФИКС 3 — скрыть** |
| Теги, позиции, фото, записи | — | не архивируются | — | не требуется |

Вывод: правки — клиенты (колонки нет, добавить скрытой) и сотрудники/материалы (видна по умолчанию, скрыть); локации и услуги уже соответствуют унифицированному правилу. Несоответствие подписи у сотрудников («Архив» vs «Статус») остаётся — унифицируется только видимость.

## User Scenarios

1. **Включение колонки.** Администратор открывает «Клиенты», жмёт шестерёнку «Настроить колонки», отмечает «Статус» → в таблице появляется колонка с бейджами «Активен» (активные) / «Архив» (архивные). Без включения таблица выглядит как раньше. → e2e-сценарий (включение и бейджи) + юнит-тест конфига/таблицы (колонка существует, скрыта по умолчанию, появляется через пикер).
2. **Deep-link на архивного клиента.** Пользователь переходит по ссылке `/clients?clientId=N`, где клиент архивный → строка открыта и выделена поиском; включив «Статус», он видит у неё бейдж «Архив» и понимает состояние клиента. Принятая остаточная ограниченность (выбор Gate A — скрытая колонка): до включения колонки deep-link сам по себе состояние по-прежнему не показывает. → e2e-сценарий в общем файле e2e клиентов (deep-link — предусловие входа).
3. **Реактивность после мутации.** Колонка «Статус» включена, фильтр статуса — «Все» (предусловие: при дефолтном «Активные» архивированная строка просто уходит из отфильтрованного вида, и флип бейджа не виден). Администратор архивирует/восстанавливает клиента через меню действий → бейдж строки меняется («Активен» ↔ «Архив») без перезагрузки страницы. → e2e-сценарий (мутация инвалидирует кэш списка — механизм уже есть).
4. **Память выбора.** Администратор включил «Статус», перезагрузил страницу → колонка осталась включённой. → покрывается существующими тестами персистентности DataTable (`usePersistedState`, ключ `clients-columns` уже передаётся таблицей); отдельного теста не требуется.
5. **Согласованность с фильтром.** Администратор ставит фильтр статуса «Неактивные» → все показанные строки при включённой колонке несут бейдж «Архив». → юнит-тест достаточен: бейдж и фильтр читают одно поле строки `archived`, отдельный e2e не нужен.
6. **Единое поведение справочников.** Администратор открывает таблицы сотрудников и материалов → колонка «Архив»/«Статус» больше не показывается сама, включается той же шестерёнкой, что и у клиентов. → юнит-тесты конфигов (`defaultVisible: false`) + обновление e2e `staff-crud.spec.ts`, ждущего «Архив» среди видимых заголовков.

## Behavioral Delta (до → после)

- **До:** в таблице клиентов нет колонки статуса; архивность видна только по подписи кнопки меню («В архив» / «Восстановить») и не видна вовсе у строк, к которым меню ещё не открывали. У сотрудников и материалов колонка статуса/архива показывается сразу — разнообразие «у кого-то видна, у кого-то скрыта».
- **После:** в таблице клиентов появляется колонка «Статус» (скрыта по умолчанию) с бейджами «Активен»/«Архив»; включается через «Настроить колонки», выбор запоминается. У сотрудников и материалов колонка скрывается по умолчанию — у всех пяти архивируемых сущностей правило единое: скрыта, пока сам не включишь. Кто не трогал пикер, увидит колонку скрытой (пустой сохранённый выбор откатывается к новому дефолту); явные выборы пикера сохраняются как были. Бэкенд и API-контракт не меняются.

## Техническое резюме

- **Что меняется:** (1) одна запись в конце конфига колонок клиентов (после «Сумма оплат») — колонка `archived` с подписью «Статус», `defaultVisible: false`, **`sortable: false`**, inline-бейдж по образцу услуг (CSS-переменные), текст «Активен» / «Архив» (род по сущности «клиент»); (2) унификация — в конфигах сотрудников (`staffColumns.tsx`, колонка «Архив») и материалов (`materialsColumns.tsx`, колонка «Статус») `defaultVisible: true → false`.
- **Почему несортируемая:** серверный whitelist сортировки клиентов не содержит `archived` (`backend/src/services/client.py`, `sort_column_map` — 7 ключей), неизвестный ключ молча падает на сортировку по имени; колонка без `sortable: false` показала бы «сортировку по Статусу», реально сортируя по имени. Прецедент — бейдж-колонки услуг помечены `sortable: false` по той же причине (#139 §6.2).
- **Критерий приёмки бейджа:** контраст текста ≥ 4.5:1 (WCAG 2.2 AA при размере 12px). Пары «успех/фон успеха» и «приглушённый текст/поверхность» из CSS-переменных проверить на контраст при импл; при необходимости скорректировать значения переменных, не меняя структуру.
- **Где:** `frontend/admin/app/(main)/clients/components/clientColumns.tsx`, `frontend/admin/app/(main)/staff/components/staffColumns.tsx`, `frontend/admin/app/(main)/services/components/materialsColumns.tsx`; юнит-тесты в `frontend/admin/__tests__/ClientsTable.test.tsx` (+ тесты конфигов на `defaultVisible: false` по паттерну соседних сущностей, если заведены).
- **Как тестируется:** e2e — сценарии 1–3 (один e2e-файл клиентов: включение колонки и бейджи, deep-link на архивного клиента, флип бейджа при мутации с фильтром «Все») + обновление существующего `frontend/admin/e2e/staff-crud.spec.ts`, чей список ожидаемых заголовков включает «Архив» (сценарий 6); юнит — сценарии 5–6 + существующее покрытие пикера/персистентности DataTable для сценария 4.
- **Персистентность выбора:** бесплатно через существующий механизм DataTable (`usePersistedState`, ключ `clients-columns`), без нового кода; добавление ключа колонки не ломает существующие сохранённые выборы (неизвестный ключ отбрасывается, пустой/битый — откат на `defaultVisible`).
- **Бэкенд/API:** ноль изменений — поле `archived` уже в ответе списка клиентов (`ClientWithStats`).

## Исправленные премиссы issue (по разведке 19.09)

1. Поле называется `archived` (инверсия `is_active`, решение #207), а не `is_active`.
2. Фильтр клиентов работает по параметру статуса `all|active|archived` (не `include_inactive`); по умолчанию `active` — архив скрыт фильтром; «Неактивные» = `archived`.
3. У сотрудников колонка называется «Архив» и видна по умолчанию (в issue — «Статус», скрытая); у локаций/услуг — как в issue.
4. #139 полностью смержен, все таблицы на generic DataTable, колонки — в пер-сущностных конфигах → правка конфиг-уровня, тривиальна.
5. Серверный whitelist сортировки клиентов не содержит `archived` — новая колонка создаётся несортируемой (см. техническое резюме), иначе заголовок молча сортировал бы по имени.
