# #330 — Индикатор потери связи с сервером + таймауты запросов (дизайн)

Дата: 2026-09-19. Статус: на согласовании (Gate B), ревизия 2 (после панели 6/6).
Затрагивает: `frontend/admin` (SSE-провайдер, провайдеры React Query, UIContext, контейнер тостов, разбор ошибок) и общий `packages/api-client` (таймауты). Серверных правок нет.

## 1. Сводка

В admin-приложении нет единого состояния «связь с сервером есть/нет»:

- при сетевом сбое каждая упавшая загрузка сыплет отдельным тостом «Ошибка сети» (автоскрытие 4,5 с, без дедупа) — `frontend/admin/app/providers.tsx:17-25` (QueryCache.onError) + `frontend/admin/app/lib/api/parseApiError.ts:86-89` (TypeError → «Ошибка сети»);
- у API-клиента нет таймаутов — зависший запрос висит до браузерного таймаута (`packages/api-client/src/client.ts:54-60`, голый `fetch`);
- SSE-канал из #239 отслеживает потерю связи, но прячет её в приватный ref и молчит (`frontend/admin/app/ServerEventsProvider.tsx:36,53-55`); решение #239 «тихий реконнект» сознательно не показывает пользователю ничего.

Дизайн вводит: SSE-канал как единственный источник истины о связи (решение пользователя 2026-09-19), один персистентный тост «нет соединения» на существующем примитиве, дедуп транспортных тостов на время сбоя, таймауты запросов в общем клиенте и отказ от ретраев для прерванных по таймауту запросов.

## 2. User Scenarios

| # | Сценарий | Тест |

| S1 | Обрыв связи во время работы: администратор работает в админке, сеть пропадает. Через ~5 с появляется один тост «Нет соединения с сервером», который не исчезает сам и не закрывается крестиком. Интерфейс и уже загруженные данные остаются видимыми. E2E различает источники по последовательности: после навигации тостов 0, после действия появляется один. | E2E `server-push-offline.spec.ts`: offline → навигация (0 тостов) → действие (+1 тост) |

## 3. Behavioral Delta (до → после)

1. **Потеря связи.** До: интерфейс молчит — обновления прекращаются незаметно, пользователь работает с устаревшими данными. После: через 5 с устойчивой потери появляется один персистентный тост «Нет соединения с сервером. Обновления приостановлены.», исчезает при восстановлении; крестиком не закрывается и из очереди не вытесняется.
2. **Сетевые тосты.** До: каждая упавшая загрузка показывает свой тост «Ошибка сети» на 4,5 с, без дедупа. После: пока SSE-канал в сбое, транспортные тосты загрузок не показываются вовсе (кроме возможного одного первого — R3); при здоровой связи поведение прежнее.
3. **Зависшие запросы.** До: запрос висит до браузерного таймаута (минуты), а ретраи React Query умножали бы ожидание. После: клиент обрывает запрос через 30 с (загрузка файлов — 120 с), ретраи для прерванных по таймауту/отмене запросов отключены, пользователь видит «Превышено время ожидания запроса».
4. **Восстановление.** До: невидимо (тихий реконнект + инвалидация). После: то же самое плюс явный сигнал — тост убирается; «Данные обновлены» на этом пути по-прежнему не показывается (конвергенция — не уведомление).
5. **Мутации и ошибки сервера.** Без изменений: 4xx/5xx-ответы тостятся как раньше; действия показывают per-action ошибки (совместимо с #243/deletion.md — ветка «ответа не было» получит состояние соединения из §5.1).
6. **Сервер и web-витрина.** Серверных правок нет (`retry: 5000` остаётся). Web-витрина кода не меняется, но унаследует таймауты через общий api-клиент (§6.7 — сознательное следствие).

## 4. Концепт (выбранный подход)

**SSE-канал — единственный источник истины о связи** (решение пользователя 2026-09-19: воспользоваться SSE). Провайдер SSE-событий уже владеет EventSource и его событиями `onopen`/`onerror` — состояние связи выводится оттуда, а не из опросов, флага браузера или обёртки fetch.

Три фазы (программно — один булев флаг «канал в сбое» + локальные для провайдера таймер и ref «тост показан»):

- **Связь есть** — канал открыт. Дедуп выключен.
- **Сбой канала** — EventSource выдал ошибку при живой попытке переподключения (`readyState CONNECTING`; нативный реконнект `retry: 5000` идёт). Дедуп транспортных тостов включён, пользователю ничего не показывается — это окно кратковременной дрожи.
- **Устойчивая потеря** — ошибка канала держится дольше 5 с. Показывается один персистентный тост; дедуп остаётся включённым.

Переходы:

- `onerror` при `readyState === CONNECTING` → флаг «в сбое» + запуск таймера 5 с (если ещё не запущен; повторные `onerror` во время устойчивой потери состояние не меняют и таймер не перезапускают);
- таймер сработал → персистентный тост (строго один, id в ref);
- `onopen` → отмена таймера, сброс флага, скрыть тост если показан; blanket-инвалидация уже есть и не меняется (`ServerEventsProvider.tsx:46-52`);
- `onerror` при `readyState === CLOSED` (фатальное закрытие: ответ HTTP не 200 — например 401 при истёкшей сессии, или прокси вернул 502/HTML, или неверный MIME; по WHATWG reconnect не выполняется никогда) → это НЕ потеря сети: сервер доступен и ответил. Отменить таймер, сбросить флаг, скрыть тост если показан, ничего не показывать. Истёкшая сессия обрабатывается штатно: следующий REST-запрос получит 401 → редирект на вход (`packages/api-client/src/client.ts:104-110`, `AuthContext.tsx:66-68`).

Почему EventSource, а не `navigator.onLine`: EventSource ошибается немедленно при обрыве сети, флаг браузера ненадёжен (VPN/виртуальные адаптеры всегда «онлайн») и не даёт выигрыша в скорости детекта. Почему тост, а не плашка в Topbar: направление «зафиксированный тост на существующем persistent-примитиве» зафиксировано в issue (решение 2026-09-19); механизм id + скрытие кодом уже есть в UIContext.

## 5. Техническая архитектура

### 5.1 Новый модуль `frontend/admin/app/lib/connectionHealth.ts`

Модульный синглтон-флаг (прецедент в кодовой базе: модульный `unauthorizedHandler` в `packages/api-client/src/client.ts:33-37`):

- `let channelDown = false` (начальное значение — «связь есть»; эксплицитно, чтобы избежать слепого окна при старте);
- `setChannelDown(v: boolean)`, `isChannelDown(): boolean` — без React-реактивности: читатели — синхронный колбэк `QueryCache.onError` и в будущем ветка «ответа не было» контракта удаления (docs/domain-rules/deletion.md:23 явно откладывает на #330 опору на состояние соединения);
- различие «сбой/устойчивая потеря» наружу не выставляется: оно нужно только провайдеру (§5.2) и живёт в его локальных ref'ах;
- юнит-файл для геттера/сеттера не заводится (тривиальный seam; поведение покрывается e2e).

Модуль админ-локальный: SSE-потребитель существует только в admin.

### 5.2 `ServerEventsProvider.tsx` — владелец состояний и тоста

- при монтировании: сброс `setChannelDown(false)` (StrictMode-перемонтирование не оставляет протухший флаг; реальный сбой переустанавливается первым же `onerror`);
- `onerror`: если `es.readyState === EventSource.CLOSED` — фатальное закрытие (§4): отменить таймер, сбросить флаг, скрыть тост, выйти. Иначе — восстановимый сетевой сбой: `setChannelDown(true)`; если таймер устойчивой потери не запущен — запустить на `LOST_DEBOUNCE_MS = 5000`;
- таймер сработал: если персистентный тост ещё не показан — `showToast('Нет соединения с сервером. Обновления приостановлены.', 'error', undefined, undefined, undefined, /* persistent */ true)` и запомнить id в ref (защита от повторного навешивания);
- `onopen`: отменить таймер; `setChannelDown(false)`; если тост показан — `hideToast(id)`, сбросить ref. Blanket-инвалидация уже есть и не меняется;
- unmount: очистить таймер и тост (провайдер топ-уровневый, но правило гигиены то же, что для существующего таймера батча);
- `showToast`/`hideToast` стабильны (`useCallback` с пустыми зависимостями) — добавление `hideToast` в зависимости эффекта не пересоздаёт EventSource;
- `retry: 5000` сервера и нативный реконнект EventSource не трогаются — «тихий реконнект» сохранён.

### 5.3 `UIContext.tsx` + `ToastContainer.tsx` — персистентный тост

Минимальное аддитивное расширение существующего примитива (механизм id + `hideToast` уже есть, `kind: 'loading'` уже не ставит авто-таймер):

- 6-й опциональный параметр `showToast(..., persistent?: boolean)` — по образцу 5-го параметра `action` из #285; в `Toast` добавляется `persistent?: boolean`; блок авто-таймера: `if (kind !== 'loading' && !persistent)`;
- `ToastContainer`: крестик «Закрыть» (сейчас он у каждого тоста кроме `loading`, `ToastContainer.tsx:72-80`) для persistent-тостов не рендерится — иначе пользователь может закрыть «Нет соединения» и остаться без индикатора до конца сбоя;
- `ToastContainer`: обрезка очереди до последних 5 тостов (`ToastContainer.tsx:13`) persistent-тост не вытесняет — иначе шквал ошибок действий временно убрал бы индикатор без действия пользователя, что ломает обещание S1 «не исчезает сам» (очередь может стать 5 + 1 persistent — приемлемо);
- существующие вызовы совместимы без правок; на вызов-точку §5.2 — именующий комментарий (шестой позиционный параметр).

### 5.4 `providers.tsx` — дедуп транспортных тостов

В `QueryCache.onError` порядок проверок: `meta.silent` → `console.error('[Query]', ...)` → гейт дедупа → тост. Гейт после `console.error` — диагностика в консоли не глушится даже для дедупированных ошибок:

```
if (isNetworkError(err) && isChannelDown()) return; // транспортный сбой на время потери связи
```

- немонетворенные ошибки (ApiError с кодом, 4xx/5xx) тостятся как раньше; 401/403 — это `ApiError`, гейт их заглушить не может ни при каком состоянии канала;
- MutationCache в файле отсутствует, мутации не затрагиваются (per-action ошибки — §3.5);
- почему первый тост всё же может просочиться: гейт опирается на то, что `onError` у загрузок стреляет только после двух ретраев (~3–4 с), а SSE-канал ошибается в первые секунды обрыва. Для самого первого одновременного отказа порядок не гарантирован платформой (событие `onerror` ставится в очередь задач) — принятая остаточная R3 с потолком «не более одного тоста».

### 5.5 `packages/api-client/src/client.ts` — таймауты

- константы `REQUEST_TIMEOUT_MS = 30_000` и `UPLOAD_TIMEOUT_MS = 120_000` (тело `FormData` — загрузки фото);
- в `api()`: `signal: options?.signal ?? AbortSignal.timeout(body instanceof FormData ? UPLOAD_TIMEOUT_MS : REQUEST_TIMEOUT_MS)` — ключ ставится ПОСЛЕ разворота `...options`, поэтому явный caller-signal не перекрывается; сегодня ни один вызов signal не передаёт (ветка — страховка, §8 — отдельного теста на неё нет);
- важная платформенная деталь: `AbortSignal.timeout()` прерывает запрос с `DOMException` имени **`TimeoutError`** (не `AbortError` — имя `AbortError` несёт явная отмена через собственный сигнал); fetch отклоняется именно причиной сигнала. Разбор — §5.6;
- `AbortSignal.timeout` прерывает и чтение тела ответа (`res.json()` входит в бюджет);
- поддержка: Chrome 103+, Safari 16+, Firefox 100+, Node 17.3+ (юнит-тесты); API уже используется в `e2e/globalSetup.ts` — Node-сторона проверена;
- точка одна на все запросы (`client.ts:54`) — ни один вызов сегодня не идёт мимо обёртки.

### 5.6 `parseApiError.ts` — ветки прерываний + классификатор сети

Классификация строго по `err.name` (не `instanceof DOMException` — в средах вроде jsdom/global-полифилов тип бывает другим; `DOMException` наследует `Error` в браузерах и Node 18+):

- `name === 'TimeoutError'` → `{ message: 'Превышено время ожидания запроса' }` (сейчас попадает в «Неизвестная ошибка»);
- `name === 'AbortError'` → `{ message: 'Запрос отменён' }` (явная отмена caller-сигналом; сегодня недостижимо — callers без signal);
- `TypeError` → «Ошибка сети» (как сейчас);
- новый экспорт `isNetworkError(err)`: `TypeError` или имя `TimeoutError`/`AbortError` — транспортный класс для дедупа §5.4;
- новый экспорт `isAbortClass(err)`: имя `TimeoutError`/`AbortError` — для отключения ретраев §5.7;
- прочее поведение разбора не меняется.

### 5.7 `providers.tsx` — ретраи для прерванных запросов

Сейчас `retry: 2` (`providers.tsx:29`) ретраит и прерванный по таймауту запрос: каждый повтор получает свежие 30 с, тост уезжает на ~90–95 с (панель: MAJOR, трижды). Правка:

```
retry: (failureCount, error) => failureCount < 2 && !isAbortClass(error)
```

- `TimeoutError`/`AbortError` не ретраятся — S4 даёт честные ~30 с; повторять 30-секундное зависание бессмысленно;
- `TypeError` (сетевой сбой) ретраится как раньше: миг полезен, а задержка ретраев закрывает окно гонки дедупа (§5.4).

## 6. Границы скоупа и осознанные остаточные ограничения

Что сознательно НЕ строим:

1. **Фоновый retry упавших запросов** — вне скоупа по issue (п.5: «отдельное решение, не обязательная часть»): канал реконнектится нативно, данные сходятся blanket-инвалидацией на `onopen`, мутации повторяет пользователь (#243 даёт честные тексты ошибок).
2. **`navigator.onLine` / события online-offline** — ненадёжный источник, выигрыша в скорости детекта нет (§4).
3. **Плашка-баннер в Topbar** — направление зафиксировано на персистентном тосте (решение 2026-09-19 в issue).
4. **Дедуп мутаций** — обратная связь действий (тексты #243, undo-тосты) остаётся per-action; глушим только транспортные тосты загрузок.
5. **Индикатор для web-витрины** — не строится (web в Hold); в web нет ни SSE-провайдера, ни этих тостов.
6. **Серверные правки** — нет: `retry: 5000`, кадры событий и keepalive-пинги не добавляются.
7. **Изоляция web от таймаутов** — не делается: общий клиент — естественная точка, таймаут для витрины такой же положительный эффект. Если когда-нибудь понадобится иной порог для web — это опция в `api()`, тривиальное расширение.
8. **Интеграция с TanStack `onlineManager`** (`setOnline(false)` на потерю — queries паузятся, мутации не уходят в мёртвую сеть; рекомендация панели best-practices) — отвергнуто: пауза мутаций убирает per-action обратную связь (#243 строится на честных ошибках действий, а не на молчаливых очередях); выбранные дедуп + таймауты дают ту же защиту загрузок без изменения семантики действий.

Осознанные остаточные ограничения (документируем, не строим):

- **R1. «Тихая смерть» канала.** Полуоткрытое/зависшее TCP-соединение SSE (сервер завис без сброса, NAT-таймаут) не вызывает `onerror` — канал читается живым, тоста нет; зависшие REST-запросы получают фидбек через таймауты 30 с (S4). Клиентский сторож «нет кадров N секунд» невозможен без серверных пингов: отсутствие кадров ≠ мёртвый канал (тишина — нормальное состояние потока событий). Серверные пинги = серверные правки, вне скоупа (п.6). Этот же компромисс уже задокументирован в `providers.tsx:35-39` (#239).
- **R2. Фатальное закрытие при недоступном бэкенде за прокси.** Если прокси отвечает 502/HTML на упавший бэкенд, EventSource закрывается фатально (§4) — индикатора не будет, а разрозненные тосты ошибок вернутся к поведению «до». Это текущее поведение, не регресс; при прямом соединении (дев) упавший бэкенд даёт отказ соединения — восстановимый путь, индикатор работает.
- **R3. Один просочившийся тост.** На самый первый одновременный отказ (обрыв в момент запроса) транспортный тост может показаться до переключения канала в сбой (§5.4). Потолок — один; e2e-утверждение S3 — «не более одного».
- **R4. Позиция тоста.** Контейнер тостов живёт в правом нижнем углу и перекрывает FAB штампов на время всего сбоя. Приемлемо: сбой — редкое состояние, серверные действия в нём всё равно не проходят. Смещение контейнера — отдельная UI-работа, не этого дизайна.

## 7. Константы и формулировки

- `LOST_DEBOUNCE_MS = 5000` — порог «устойчивой потери» (кратковременная дрожь не показывает ничего);
- `REQUEST_TIMEOUT_MS = 30_000`, `UPLOAD_TIMEOUT_MS = 120_000`;
- тексты: «Нет соединения с сервером. Обновления приостановлены.» (персистентный тост, kind `error`), «Превышено время ожидания запроса» (таймаут), «Запрос отменён» (явная отмена). Все — обычные строки в коде, правятся без пересогласования.

## 8. Тест-план

- **Юнит `client.test.ts`** (без fake timers — они не управляют внутренним таймером `AbortSignal.timeout`): spy на `AbortSignal.timeout` — `api()` запрашивает порог 30 000 для JSON-запроса и 120 000 для FormData-запроса; прерывание через короткий реальный caller-signal (10 мс) доходит до fetch (passthrough).
- **Юнит `parseApiError.test.ts`**: `TimeoutError` → «Превышено время ожидания запроса»; `AbortError` → «Запрос отменён»; `TypeError` → «Ошибка сети»; `isNetworkError` распознаёт все три и не распознаёт `ApiError`; `isAbortClass` распознаёт только `TimeoutError`/`AbortError`.
- **E2E `server-push-offline.spec.ts`** (расширение S1/S2/S3/S6): offline → персистентный тост ≤ 8 с; навигация по разделам → не более 1 тоста «Ошибка сети»; offline-действие → +1 тост действия после 0 тостов от навигации; online → тост скрыт, данные сошлись (существующие проверки С5 остаются). У персистентного тоста нет крестика (assert по aria/разметке).
- **E2E `server-push-invalidation.spec.ts`** (S5, отрицательная проверка): на здоровом прогоне с реконнектами тост «Нет соединения» не появляется.
- S4 (реальное ожидание 30 с) в E2E не переносится — осознанное решение: юнит-покрытие + ручная проверка; E2E-вариант потребовал бы либо 30-секундного ожидания в общем прогоне, либо перенастройки константы на сборку.
