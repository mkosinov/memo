# #271 — e2e-флейк С3 (server-push-invalidation) в полных CI shard-rest прогонах — дизайн

- **Issue:** #271 (app:admin, test-infra)
- **Дата:** 2026-09-19, rev2 (после панели 6 ревьюеров)
- **Статус:** In Design → Gate B
- **Тип:** тестовая инфраструктура. Продуктовый код (SSE-сервер, SSE-клиент, hub) не меняется.

## 1. Контекст

Тест «С3: B deletes an activity via UI → A's grid refetches and records converge» из набора
`server-push-invalidation.spec.ts` периодически падал по таймауту в полных CI-прогонах
shard-rest (два шарда по два полных стека на одной машине), оставаясь стабильным локально.
Ошибка — `TimeoutError: page.waitForResponse`: push-событие не доходило до второго браузера
в пределах окна ожидания, инвалидация кэша не срабатывала, перечитывания не было.

Флейк впервые зафиксирован 2026-09-12 (прогоны PR #269). С тех пор тест переписан дважды:

1. `eb35a9c` (2026-09-10, #252) — по-тестовый сброс сидов БД, убрана зависимость тестов
   друг от друга через общий шардовый sharding-DB.
2. `d417cd4` (2026-09-19, #286) — сценарий удаления переведён на отложенный конвейер
   (#285): undo-тост, коммит-запрос DELETE отстреливается ~5 секунд спустя, добавлены
   новые push-утверждения с поллингом БД.

Часть фактов из issue устарела (номер строки, 15-секундный бюджет, формулировка ожиданий) —
поправки вынесены комментом на issue. С 15.09 в CI нет красных прогонов, упоминающих эту
спеку. Оговорка о «тихом CI»: в CI настроен один ретрай теста; прогон с упавшей первой
попыткой получает зелёный код выхода, но Playwright помечает такой тест как **flaky** в
итоговой сводке, HTML-отчёте и аннотациях. Поэтому «нет красных прогонов» не доказывает
исчезновение флейка — доказательством будет ноль упавших И ноль flaky в сводке (см. DoD).
DoD issue остаётся живым: корневая причина + фикс + три подряд полных shard-rest прогона
на фиче-ветке.

## 2. Root-cause анализ (структурный)

Три независимых механизма способны съесть текущее окно push-утверждений (5 секунд) —
все подтверждены живым кодом и остаются актуальными для переписанного С3:

1. **Окно равно pacing'у реконнекта.** Клиент подписки (`EventSource` в провайдере
   серверных событий) при обрыве переподключается не раньше, чем через 5 секунд — столько
   задаёт сервер первым кадром (`retry: 5000`; подтверждено документацией SSE). Один обрыв
   соединения занимает всё 5-секундное окно целиком: событие доставки не успевает даже при
   идеальной работе сервера после реконнекта.
2. **Вытеснение подписчика на сервере.** Hub серверных событий держит каждому подписчику
   очередь на 64 события; при переполнении подписчик выбрасывается и обязан
   переподключиться. Под нагрузкой шарда (два полных стека на одной 4-ядерной машине,
   sibling-спеки генерируют собственные события) переполнение реалистично. На реконнекте
   клиент накрывает кэш «шторкой» (полная инвалидация), что в итоге догоняет состояние,
   но укладывается ли это в 5 секунд — не гарантировано.
3. **Процессорная конкуренция шарда.** Полный прогон держит два стека параллельно;
   компиляция страниц Next dev в sibling-спеках замедляет и доставку событий, и обработку
   перечитывания. Дополнительный фактор — цепочка самого С3 удлинилась после #286
   (undo-окно 5с → коммит → поллинг БД → два push-утверждения) при таймауте теста 60с.

Вывод: окно 5 секунд систематически меньше, чем один цикл реконнекта (5с pacing +
рукопожатие + шторка инвалидации). Значит нужно одновременно поднять окно и дать
утверждениям ограниченный повтор; и пересчитать бюджет таймаута самого теста (см. §4, §5).

## 3. User Scenarios

Каждый сценарий мапится на проверку в E2E/CI.

| № | Сценарий | Проверка |
|---|----------|----------|
| С1 | Разработчик открывает PR → полный CI shard-rest → спека проходит без единого падения и без flaky-пометок с первой попытки | сводка Playwright в CI: failed=0 и flaky=0 по этой спеке; DoD: так три прогона подряд на фиче-ветке |
| С2 | Разработчик локально запускает предварительную проверку (повтор push-спек в шардовой среде) → стабильно зелено; baseline до правки задокументирован | --repeat-each на push-спеках локально; результат в описании PR |
| С3 | При редком падении разработчик читает CI-лог и видит диагностику: какая попытка, какое утверждение не дождалось, началось ли перечитывание, был ли виден трафик событий | диагностика в сообщении об ошибке (см. §5d) |
| С4 | Происходит реальная регрессия push-канала — канал не доставляет события вовсе → тест её ловит | разовая ручная проверка «канал заблокирован» → тест падает (см. §7.4); частичная деградация, догоняемая шторкой реконнекта в пределах 30с, — допустимое поведение, не флейк |

## 4. Behavioral Delta

| Область | До | После |
|---|---|---|
| Окно `PUSH_WINDOW` | константа 5_000 | константа 10_000 — покрывает один цикл реконнекта; остаётся втрое ниже staleTime (30с). Константа разделяемая: вместе с ней сдвигаются утверждения С1/С4, хелпер тоста обновления и офлайн-спека (все получают больше запаса; семантика «строго ниже staleTime» сохраняется); синхронно обновляется устаревший комментарий-заголовок спеки (сейчас «PUSH_WINDOW = 5s») |
| Push-утверждения С3 | одна попытка в окне 5с; единичный обрыв подписки = падение | ограниченный повтор: каждое push-утверждение С3 может быть повторено один раз (семантика — пассивное пере-вооружение ожидания; для навигационного утверждения — повторный переход). Суммарное время наблюдения остаётся ниже staleTime 30с; кэш-обходящих действий в повторе нет |
| Push-утверждения С2 | ручной одношаговый ретрай с активным пере-набором (паттерн работает, т.к. повторный ввод перезапускает запрос) | без изменений: семантика другая (активный пере-запуск vs пассивное дожидание), обобщение в общий хелпер не делается |
| Таймаут тестов набора | глобальный 60с | 120с для описанного блока этой спеки (test-level override; глобальный конфиг не трогается). Обоснование — арифметика бюджета: worst-case цепочка С3 (сетапы ~20с + ожидание коммита 20с + поллинг БД 10с + два push-утверждения по 2×10с) ≈ 90с — диагностика helper'а обязана успевать печататься до убийства теста внешним таймаутом |
| Диагностика падения | голый `TimeoutError` без контекста | сообщение об ошибке: номер попытки, какое утверждение, началось ли перечитывание, наблюдался ли трафик событий (пробник открывает независимый контекст-слушатель). Только метаданные — никогда тела кадров/ответов, URL с query-параметрами, токены |
| Продуктовый код | — | без изменений |

## 5. Решение

**Выбрано:** закалка тестового слоя минимальными средствами на существующих механизмах:

a) **Окно 5с → 10с** — одна константа в общих фикстурах, без env-переменных. 10с покрывает
   один цикл реконнекта и остаётся существенно ниже staleTime 30с (инвариант «тест не
   должен проходить за счёт истечения свежести кэша» сохраняется; `RECONNECT_WINDOW`
   офлайн-спеки уже 10_000).
b) **Ограниченный повтор только в С3** — встроенный (inline) повтор с бюджетом 1 попытка
   на утверждение, по образцу уже доказанного локального паттерна; семантика пассивная
   (пере-вооружение ожидания, повторный переход для навигационного утверждения), суммарное
   наблюдение < staleTime 30с. Выбор встроенного повтора вместо общего хелпера-фикстуры:
   у С2 и С3 разная семантика повтора (активный пере-запуск vs пассивное дожидание),
   общий хелпер потребовал бы callback-API ради двух разнородных мест. Выбор inline
   повтора вместо документированного `expect.toPass`: toPass не умеет сообщать, какая
   попытка упала и что наблюдалось — а это суть диагностики.
c) **Таймаут описанного блока спеки 120с** (test-level override) — чтобы арифметика
   бюджета (§4) помещалась и диагностика печаталась до внешнего таймаута. Глобальный
   конфиг Playwright не меняется.
d) **Диагностика** при исчерпании бюджета: номер попытки, какое утверждение, началось ли
   перечитывание, был ли виден трафик событий. Трафик наблюдается существующим пробником
   (`openFrameLogger` из общих фикстур, уже используемым офлайн-спекой): хелпер открывает
   собственный независимый контекст-слушатель к бэкенду — подписка страницы наблюдателя не
   затрагивается, помех нет (проверено ревью feasibility; эратум rev2: пробник —
   независимый слушатель, а не подключение к странице наблюдателя). Только метаданные: тела
   кадров, тела ответов, URL с query-параметрами и токены в логи не попадают никогда.
   Попытка, прошедшая лишь со второй попытки, печатает предупреждение в лог теста — зелёные
   прогоны остаются интерпретируемыми (см. §1 о flaky-пометках).
e) **Baseline до правки**: воспроизводится ли флейк на текущем коде — фиксируется в PR.
   Механика: локальный повтор только push-спек в шардовой среде (--repeat-each=3) —
   явно помечено как проверка пониженной точности (нет sibling-нагрузки rest-шарда;
   полная точность достигается только в полных CI-прогонах — см. §7.3). Полный локальный
   прогон ×3 (30–60+ минут на повтор) не делается.

**Отвергнутые подходы:**

- **Продуктовый фикс push-канала** (увеличить очередь hub, участить ping, агрессивный
  reconnect): нет ни одного воспроизведённого факта продуктовой потери события — правка
  работающего канала без доказательств даёт риск без выгоды (YAGNI). Если диагностика
  позже покажет реальный продуктовый дефект — отдельный follow-up issue (DoD #271 это
  прямо разрешает).
- **Общий хелпер-фикстура для С2+С3**: разнородная семантика повтора (см. §5b) — дедуп
  ради дедупа. С2 не трогается.
- **Закрыть issue как неактуальный:** DoD (три зелёных прогона нового С3) не выполнен,
  структурные слабости подтверждены живым кодом; вердикт разведки — partially stale.
- **Skip/карантин теста:** запрещён DoD («NOT a skip without diagnosis»).

## 6. Что сознательно НЕ строим

- Правки `backend/src/events/` (hub, роутер) и клиентского провайдера событий.
- Env-переменные для окна/бюджетов — одна константа в фикстурах.
- Изменение глобального конфига Playwright (retries, глобальный timeout) — правки
  конфигурации только внутри файла этой спеки (test-level override таймаута).
- Общий хелпер-фикстура ожиданий / новый DSL — встроенный повтор в С3 по образцу С2.
- Изменения паттерна С2 и офлайн-спеки (сдвиг их утверждений вместе с константой —
  единственный затрагивающий их эффект).

## 7. Верификация

1. **Baseline (до правки):** локальный повтор push-спек в шардовой среде (--repeat-each=3,
   пониженная точность — §5e); результат (воспроизвёлся / не воспроизвёлся) фиксируется в PR.
2. **После правки локально:** тот же повтор — зелено; офлайн-спека зелено (сдвиг константы).
3. **После правки в CI (авторитетная проверка):** фиче-ветка, три подряд полных shard-rest
   прогона, в каждом сводка Playwright по этой спеке: failed=0 **и flaky=0** (читается
   сводка/аннотации, не только код выхода — см. §1). Это и есть DoD issue.
4. **Строгость (разовая ручная проверка, не коммитится как тест):** заблокировать доставку
   событий наблюдателю через перехват маршрута `**/api/v1/events` (abort) в контексте
   страницы A — тест обязан упасть. Механизм выбран намеренно: перехват маршрута убивает и
   реконнекты (EventSource — обычный HTTP), тогда как симуляция «офлайн» при возврате сети
   вызывает шторку инвалидации на переподключении и может дать ложно-зелёный результат.
   Цель проверки: helper не маскирует полную смерть канала (бюджет повтора конечен).
