# #243 — Единый контракт удаления: зона записи (фаза 1)

- Дата: 2026-09-19 (rev6 — решение пользователя: честный текст тоста для ошибок без ответа сервера; карточка потери связи #330)
- Issue: [#243](https://github.com/mkosinov/memo/issues/243) — «удаления визитов и платежей — при ошибке сервера экран расходится с сервером»
- Статус: дизайн (Gate B)
- Зона: `frontend/admin` — зона записи (визиты, платежи)

## Контекст и актуальность (сверка 2026-09-19)

Issue (2026-09-06) описывал четыре пути удаления без страховки при ошибке сервера. Мержи #285
(`37645b2`) и #286 (`d417cd4`) закрыли три из них: появился общий пайплайн отложенных удалений
(`PendingActionsContext`) с контрактом ошибок D4 rev8. Остался один дефектный путь — мгновенное
удаление платежа (`useRecordMutations.ts:294-306`): строка убирается из кэша до запроса, при
ошибке — ни отката, ни тоста (вызывающий компонент ошибку не перехватывает).

Глубокая разведка (2026-09-19, вторая) показала, что дефект — верхушка более широкой проблемы:
зона записи живёт в двух механиках удаления одновременно. Настоящее решение — не чинить
мгновенный путь, а привести зону записи к единому контракту (решение пользователя 2026-09-19).

## Действующий канон и что им нарушено

### Действующее состояние (docs/domain-rules/_overview.md:74-120, #194/#195/#207/#285)

Таблица удаления в доменных правилах делит сущности так: архивируемая пятёрка (Staff,
Location, Service, Material, Client — hard-delete с разбором зависимостей + отдельные
«в архив»/«восстановить»); hard-delete без архива (Tag, Photo, Visitor, Activity, Record,
UserSettings; Payment и Visit помечены «already hard-delete, untouched»); User и Tariff —
неявный soft-delete вне скоупа. Контракт отложенного удаления (:115-120) закреплён за зоной
записи: критерий подключения — наличие серверных зависимостей (FK_MATRIX), «не архивность
и не окно отмены»; архивируемым он сознательно не положен (решение 17.09).

### Целевое состояние — решение пользователя (2026-09-19)

### Найденные нарушения (одна сущность — две механики)

- **Платёж**: на странице клиентов удаляется мгновенно, без отмены (`ClientRecordTab.tsx:350`
  → `deletePayment`), в модалке расписания — отложенно с отменой (`ActivityDetailsModal/ClientTab.tsx:294`
  → `deletePaymentDeferred`). Тот же общий UI-блок «Удалить платёж».
- **Визит — внутри одной вкладки**: анонимный визит удаляется мгновенно
  (`ClientRecordTab.tsx:112-119` → `deleteVisit`), именованные строки — отложенно
  (`:330` → `deleteVisitDeferred`).
- **Внутренний рассинхрон мгновенной пары**: мгновенный визит при ошибке возвращал строку,
  мгновенный платёж — нет (дефект #243).

### Решение пользователя (2026-09-19) — новая формулировка канона

> Единый отложенный контракт удаления (окно отмены + контракт ошибок) — для действия
> «удалить» ВСЕХ сущностей. Архивирование не меняется (оно обратимо и в окне отмены
> не нуждается).

Решение упрощает действующий критерий (зависимости больше не критерий — «удалить = всегда
отложенно») и расширяет решение от 17.09 для архивируемых: только действие «удалить»,
«в архив» остаётся как есть. Формулировка — целевое состояние, а не описание текущего кода.

**Фиксация канона:** новый файл `docs/domain-rules/deletion.md`: формулировка целевого
контракта; таблица «сущность → класс → фаза перевода» по ВСЕМ сущностям, сведённая с
действующей таблицей `_overview.md` (Position в таблице доменных правил отсутствует —
переводится в фазе 2 как листовой справочник; UserSettings — пользовательского удаления
через UI нет, помечается «не применимо»); явная отметка, что контракт заменяет критерий
FK_MATRIX и расширяет решение 17.09 для действия «удалить» архивируемых — это снимает окно
противоречия со старой формулировкой `_overview.md:120`. Сам `_overview.md` в этой фазе
не правится: в рабочем дереве в нём лежат несмёрженные правки параллельного дизайна
(сверено по `git status`); строка-ссылка на новый файл будет добавлена в фазе 2.

## Концепт: приведение зоны записи к единому контракту (фаза 1)

Все поверхности зоны записи используют только отложенные варианты удаления. Мгновенные
варианты — легаси до пайплайна #285 (исторически: мгновенные функции созданы при рождении
хука `3c65d04`, отложенные добавлены `da25ac1`, миграция #285 прошла только по записям) —
удаляются как мёртвый код.

1. **Удаление платежа на странице клиентов** (`ClientRecordTab.tsx:350`) — передаётся
   `deletePaymentDeferred` (как в модалке расписания).
2. **Удаление анонимного визита** (`ClientRecordTab.tsx:112-119`) — вызывается
   `deleteVisitDeferred`; локальный catch с тостом убирается (пайплайн сам владеет ошибками).
3. **Удаление мгновенных функций** `deletePayment` (:294-306) и `deleteVisit` (:385-406) из
   `useRecordMutations` вместе с их юнит-тестами.
4. **Честный текст тоста для ошибок без ответа сервера** (решение пользователя 2026-09-19):
   одна ветка в дефолтном обработчике ошибок пайплайна по типу ошибки. Если ответа сервера
   не было (сетевая ошибка без статуса, не ApiError) — тост «Не удалось подтвердить
   удаление»: исход неизвестен, мы не утверждаем, что удаление отменено. Если сервер
   ответил ошибкой — прежний текст «Не удалось удалить. Изменение отменено». Возврат
   строки из снимка — в обеих ветках, без изменений; текст применяется ко всем отложенным
   удалениям (визиты, платежи, записи, занятия) — контракт остаётся единым.

Дефект #243 закрывается схемой: путь «платёж пропадает навсегда при ошибке» перестаёт
существовать — везде контракт D4 (возврат строки + тост при ошибке коммита).

Связь с #330 (потеря связи, заведена 2026-09-19): до появления настоящего детекта
состояния соединения (SSE, отсылка к #239) честный текст — лучший доступный сигнал;
после реализации #330 ветка «нет ответа» должна опираться на состояние соединения.

### Фазирование (решение пользователя охватывает всё приложение)

- **Фаза 1 — эта спека, закрывает #243:** зона записи (визиты, платежи).
- **Фаза 2 — follow-up issue:** листовые справочники (теги, фото, посетители, должности) —
  перевод удаления на отложенный контракт; координация с открытой карточкой #318 (контракт
  ошибок удаления занятого тега). Примечание о пересечении: карточки #297/#298 (листовые
  визиты/платежи — наследование контракта ошибок D4 + верификация) пересекаются с фазой 1 —
  она закрывает их конверсионную часть (перевод поверхностей на отложенный контракт);
  остаток — верификация — покрывается тестами S3; судьбу карточек (закрыть как поглощённые)
  решает пользователь после ОК спеки.
- **Фаза 3 — follow-up issue:** архивируемая пятёрка — действие «удалить» после диалога
  зависимостей становится отложенным с окном отмены; «в архив»/«восстановить» без изменений.

Карточки фаз 2-3 заводятся после ОК спеки (черновые названия — в конце документа).

### Отвергнутые подходы

- **Заплатка мгновенного пути** (возврат строки + тост внутри мгновенного удаления) —
  оставляет одну сущность в двух механиках; отвергнуто пользователем 2026-09-19.
- **Пессимистичное удаление** (ждать сервера) — ломает UX-решение #141 «быстрый экран».
- **Отложенный контракт для архивирования** — не нужен: архив обратим, «отменой» служит
  «восстановить».
- **Все фазы одной спекой** — нарушает принцип «один дизайн за прогон», план стал бы
  неконтролируемым; фазы 2-3 не зависят от фазы 1 технически.

## User Scenarios

### S1. Удаление платежа на странице клиентов — окно отмены
Администратор на вкладке записи клиента нажимает «Удалить платёж». **Ожидание:** строка
исчезает, появляется тост «Удалено. Отменить» с кольцом обратного отсчёта (5 сек). Нажал
«Отменить» — платёж вернулся, запрос на сервер не уходил. Не нажал — через 5 секунд удаление
уходит на сервер.
E2E: `admin-manages-payments.spec.ts` — новое поведение (окно отмены). **Новый тест.**

### S2. Удаление анонимного визита — окно отмены
Администратор уменьшает счётчик анонимных визитов («−»). **Ожидание:** как S1 — строка/счётчик
обновляется, тост с отменой на 5 сек.
E2E: `anonymous-visits.spec.ts` — расширение на новое поведение. **Новый тест.**

### S3. Ошибка при коммите отложенного удаления — строка возвращается, текст тоста честный
Окно отмены истекло, запрос ушёл. Два варианта: сервер ответил ошибкой (HTTP) — строка
возвращается, тост «Не удалось удалить. Изменение отменено»; ответа не было (обрыв сети) —
строка возвращается, тост «Не удалось подтвердить удаление» (исход неизвестен).
**Ожидание:** в обоих вариантах строка на экране, тост соответствует варианту.
E2E: `records.spec.ts` — оба перехвата (ошибка с ответом; обрыв без ответа) после
истечения окна → строка видна, текст тоста правильный. **Новые тесты** — защита
контракта D4 для обеих поверхностей.

### S4. «Уже удалён» (404) при коммите — тихий успех
Сущность удалили параллельно: 404 считается успехом, без тостов и возврата. Контракт D4,
не меняется. Покрытие: unit `PendingActionsContext.test.tsx` (E2E не пишется — поведение
не меняется, имитируется тем же моком, что в unit).

### S5. Отмена в окне 5 секунд
Как в S1: отмена возвращает строку, DELETE не уходит. Строка возвращается на исходную
позицию в списке, не в конец. Покрытие: unit `useRecordMutations.test.ts` (восстановление
+ позиция) + существующие E2E-потоки отложенных удалений.

### S6. Модалка расписания и именованные визиты — без изменений
Существующие поверхности с отложенным удалением работают как раньше.
Покрытие: существующие unit/E2E (`activity-deferred-delete.spec.ts` и др.). Регрессия.

## Behavioral Delta

| Поведение | До | После |
|---|---|---|
| Удаление платежа, страница клиентов | мгновенно, без отмены; при ошибке сервера строка пропадает навсегда, тоста нет (дефект #243) | окно отмены 5 сек; при ошибке коммита — возврат строки + тост |
| Удаление анонимного визита («−») | мгновенно, без отмены (при ошибке — возврат был) | окно отмены 5 сек; контракт ошибок единый |
| Именованные визиты, модалка расписания, удаление записи/занятия | отложенный контракт | без изменений |
| Позиция строки после «Отменить» (обе поверхности зоны записи) | строка возвращается в конец списка | строка возвращается на исходную позицию |
| Тост при ошибке удаления без ответа сервера (все отложенные удаления) | «Не удалось удалить. Изменение отменено» — утверждает больше, чем известно | «Не удалось подтвердить удаление» — честно об исходе; строка возвращается как раньше |
| Архивирование и удаления в справочниках | — | без изменений в этой фазе (фазы 2-3) |
