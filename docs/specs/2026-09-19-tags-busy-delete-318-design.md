# Спека: #318 — удаление занятого тега: подключение к семейному контракту честного удаления

- **Issue:** #318 (Tags: удаление занятого тега — безликий 422 вместо общего контракта удалений)
- **Дата:** 2026-09-19
- **Статус:** rev9 — семейное правило переработано: деление по ДЕЙСТВИЮ (удаление «навсегда» — один флоу для всех, включая архивируемые; архивирование — вне схемы, обратимо restore; отмена #285 §5); rev8 — механизм целиком на всей неархивной семье (dry_run + обязательный expected у каждого DELETE, кольцо у каждого удаления, голой формы нет); rev7 — expected для семьи; rev6 — панель wave 2; rev5 — expected+items+голый-422; rev4 — кольцо; rev3 — dry_run; rev2 — панель wave 1. Ждёт Gate B
- **Связанные:** #285 (эталон контракта, смержен), #286 (занятия, смержено), #297/#298 (визиты/оплаты — листовые, закрыты), #324 (остаток семьи + тест-страж, Backlog), #207 (архивный контракт), docs/domain-rules/_overview.md, docs/domain-rules/tags.md

## 1. Проблема и поправка премиссы issue

Issue предполагал: DELETE занятого тега упирается во внешние ключи → 422 `INTEGRITY_VIOLATION` с безликим сообщением. **Живая проверка (19.09, скретч-база aiosqlite + `PRAGMA foreign_keys=ON`) премиссу опровергла:** все 8 m2m-связей Tag держит через `relationship(secondary=...)` без `passive_deletes` (`backend/src/models/tag.py:74-97` + `photo_tags` в `backend/src/models/photo.py:61`), поэтому при `session.delete(tag)` SQLAlchemy сам вычищает join-строки до удаления тега — FK не нарушается. Реальное поведение: **DELETE → 204, тег молча снимается со всех объектов**.

Реальный пробел — молчаливая массовая правка: пользователь удаляет словарную запись, а система без предупреждения меняет данные до 8 видов объектов (услуги, занятия, мастера, локации, клиенты, посетители, записи, фото). Тестов, фиксирующих поведение, нет (`backend/tests/test_api_tags.py` не содержит delete-тестов).

Семейство сущностей без is_active переводится на контракт честного удаления (показ зависимостей до удаления): records — эталон #285, activities — #286; visits/payments — листовые (#297/#298); остаток — #324. Тег перечислен в семье (#324), но сегодня вне контракта: `Tag` — не ключ `FK_MATRIX` (`backend/src/domain/deletion.py:139+`), DELETE-рут тега — голый hard delete (`backend/src/api/v1/tags.py:182-196`). Канон (`_overview.md:119`) ошибочно записывает Tag как «no FK-matrix deps — nothing to match» — эта спека исправляет строку.

## 2. Решение

Gate A закрыт направлением юзера (19.09): ландшафт уже зафиксирован — «честное превью на всех сущностях без архивного статуса» (семья #285/#286/#297/#298/#324). Единственный концепт: **тег входит в семейный контракт как полный участник** — по архивному образцу #207 (путь материалов/клиентов, самый обкатанный фронтовый образец).

**D1 — матрица.** `FK_MATRIX[Tag]`: 8 зависимостей-join-таблиц — `service_tags`, `activity_tags`, `master_tags`, `location_tags`, `client_tags`, `visitor_tags`, `record_tags`, `photo_tags`; у каждой `action="cascade"`, `allowed_actions=["cascade"]`, **`auto=False`**; relation-метки — «Услуга», «Занятие», «Мастер», «Локация», «Клиент», «Посетитель», «Запись», «Фото» (другая сторона join от лица тега).

*Почему auto=False (видимые), хотя канон сегодня считает `*_tags`-join авто-зависимостями — обоснование асимметрии.* С родительской стороны потеря тег-ссылок — побочный эффект удаления родителя (у Records `record_tags` остаётся `auto=True` — не меняется). Сторона тега — другая семантика: изменение ссылок и есть главный эффект удаления тега; скрывать их значило бы воспроизвести сегодняшний молчаливый каскад (превью из одних auto-узлов пусто). Auto-ность — свойство записи матрицы (перспективы), не таблицы: та же join-таблица остаётся auto в родительских матрицах и видима в матрице Tag. Правило фиксируется в `_overview.md`.

**D2 — контракт DELETE /api/v1/tags/{id}** (полный флейвор #285 — единый стиль, решение юзера 20.09):
- `?dry_run=true` — чистое неразрушающее превью: занятый → **409** `{detail: "has_dependencies", dependencies: [8 узлов: счётчики + items]}` (D6), строки не изменяются; чистый → 204 без удаления; несуществующий id → 404 (probe существования, как у записей);
- **голый DELETE упраздняется** (зеркало rev7 #285): без флага и без тела → **422** `expected_state_required`; ветка «исполнить-если-чисто» исчезает — молчаливое исполнение невозможно и для вызовов мимо фронта (внешний потребитель идёт через dry_run + expected);
- DELETE с телом `{resolutions?, expected}`: существование → `collect_dependencies` → **сверка `expected` по id-множествам** (subset-семантика #285 rev8: 409 `stale_dependencies` с живым деревом, если на сервере есть зависимости, отсутствующие в `expected` — появление сверх подтверждённого и обмен ловятся; исчезнувшая за окно не блокирует) → валидация `resolutions` (семейная семантика: занятая зависимость без действия/с недопустимым действием → 422; неизвестные ключи тела молча игнорируются — S6 пинит 422 только за действие) → `resolve_delete` → 204. Сверка и исполнение — **одна транзакция** (как у записей; SQLite однописатель, при гипотетическом переезде на Postgres инвариант сохраняется внешней транзакцией);
- **комбинаторика (зеркало records.py:322-364):** `?dry_run=true` + тело с `resolutions` → 422 `dry_run_with_resolutions_forbidden` (проверяется до probe существования); `dry_run` + expected-only тело — игнорируется молча; голый DELETE на **неизвестном id** → 422 раньше 404 (проверка формы предшествует probe);
- несуществующий id с телом → 404 `TAG_NOT_FOUND`.

Все 8 зависимостей тега не-auto → в `expected` попадают все подтверждённые id-множества (исключений вида record_tags у записей нет).

Исполнитель `resolve_delete` удаляет строку тега Core bulk-запросом — **мимо ORM-каскада**: m2m-чистка join-строк (подтверждённая живой проверкой) работает только на голом пути. Обязательная проводка домена — D8.

**D3 — dry_run-флаг вводится (rev3, направление юзера).** Форма превью семьи для не-архивных сущностей — `?dry_run=true` (записи #285, занятия #286): безопасный «просто посмотреть» и фронтовому, и внешним потребителям; после упразднения голого DELETE (D2) — единственная форма превью. items/expected флага — D6/D4. Это полный records-флейвор для hard-delete-семьи: #324 (visitors/positions) наследует шаблон один-в-один.

**D4 — отложенное удаление с кольцом отмены (rev4, решение юзера 20.09).** Линия семьи (#285 §5): архивируемые не получают кольцо — у них настоящий откат «восстановить из архива»; семейство полного удаления получает окно отмены (записи, занятия). Тег — из второго семейства: оба пути удаления идут через общий PendingActions-конвейер (окно 5000 мс, кольцо отсчёта #94, commit после окна):
- чистый путь: `?dry_run=true` → 204 → optimistic-удаление строки из кэшей `['tags']` → enqueue; commit = DELETE `{expected: {}}`;
- занятый путь: dry_run → 409 → `DeleteDialog` → confirm → optimistic-удаление + enqueue; commit = DELETE `{resolutions, expected: {id-множества из items дерева}}`;
- undo в окне: тост снят, строка возвращается в таблицу item-level снапшотом кэша `['tags']` (механика D5 #285, проще записей: одно семейство ключей, без канонических ключей и модалок); DELETE на сервер не уходил вовсе;
- **`expected`-сверка (rev5, решение юзера 20.09 — единый стиль):** commit обоих путей несёт ожидаемое состояние (как записи #285); ссылка, появившаяся за окно, → 409 `stale_dependencies` → undo + «Не удалось удалить: данные изменились» + «Обновить» — непоказанное снятие невозможно; исчезнувшая за окно ссылка commit не блокирует (subset-семантика);
- обработка ошибок commit наследуется из общего пайплайна (#285 D4): 404 = тихий успех; прочее = undo + error-тост; 409-ветка в onError хука: «Не удалось удалить: данные изменились» + действие «Обновить» (инвалидация `['tags']`).

**D5 — фронт: поток удаления тега перестраивается по образцу записей (`useDeleteRecord`, отложенная схема).** Окно `window.confirm('Удалить тег?')` в `TagsTable` убирается. Хук `useDeleteTag`: первый вызов всегда `dryRunDeleteTag(id)` (новая функция api-client) → 204 → optimistic-удаление + enqueue с commit = `resolveDeleteTag(id, {expected: {}})`; 409 + `err.dependencies` → состояние `dependencies` → `DeleteDialog` (D9) → confirm → optimistic-удаление + enqueue с commit = `resolveDeleteTag(id, {resolutions, expected: {id-множества из items}})` (одна функция api-client по образцу `resolveDeleteRecord`, `endpoints.ts:619-625`). Тосты — pending-стек конвейера («Удалено. Отменить» с кольцом), не success-тост «Тег удалён». Инвалидации — только в commit; undo — без серверных вызовов (D4). Устаревший комментарий «§6.9 locked window.confirm flow» (`TagsTable.tsx:60`; ссылка не резолвится ни в один живой документ канона) убирается в IMPL.

**D6 — items: однострочники вводятся (rev5, единый стиль).** Узлы dry_run/409-дерева тега получают `items: [{id, label}]` (#285 D9): из id строится `expected`, а пользователь в диалоге видит, **с каких именно объектов** снимается тег — не только счётчики (прямой ответ на «объект, о котором не предупредили»). Рендер — общая ветка D9в `DeleteDialog`: заголовок группы + до 10 строк + «и ещё N» (счётчиковую строку заменяют строки, как у записей). `items.id` = **id родителя** (не join-строки: у m2m-таблиц суррогатного id нет). PII-граница #285 D9(б): **без телефонов** (имена лиц входят — маршрут админ-only, `tags:write`, уже уже аудитории записей, чьи items несут Client.name); источник — поля, видимые вызывающему. Источники меток 8 родителей: Service/Location — title; Client/Visitor — name (Client.name nullable → fallback «Аноним», образец `deletion.py:629-652`); Staff — имя через двухтабличный билд `masters.staff_id → staff` (id узла = staff_id); Record/Activity — дата-однострочники по образцу записей; Photo — title-поля нет, метка из `filename`. Точные форматы — план. Популярный тег → длинный items: отображение капировано, `expected` несёт все id — как у записей, без ограничения.

**D7 — домен-правила (правки едут вместе со спекой).**
- `_overview.md:119`: «Tag / Photo / Visitor / UserSettings — instant hard-deletes (no FK-matrix deps)» → Tag выбывает из строки; строка получает уточнение про Visitor (#324 доведёт матрицу). В таблицу матрицы добавляются 8 строк `Tag → *_tags` (cascade, не-auto) + правило перспективы auto (D1); строка контракта (`_overview.md:116-118`) дополняется тегом — полный records-флейвор (dry_run/expected/кольцо). **+:** исключение «no-body упразднён» в `_overview.md` двустишье (:113 и :173, «records dropped the no-body mode») дополняется тегом — иначе канон противоречит контракту (панель wave 2). **Семейное правило (решение юзера 20.09, финальная формулировка):** весь механизм разворачивается на **всей неархивной семье** — `dry_run`-параметр и обязательное тело `{expected}` у каждого DELETE семьи (листья — photos/user_settings и visits/payments — несут `expected: {}`, их dry_run всегда пуст-204), кольцо отмены 5 с — у каждого удаления; голой формы DELETE в семье нет вообще (422). При появлении у листа зависимостей расширение = только доменные записи (матрица/реестры), API и вызывающий код не мигрируют. Уточняет критерий #285 rev8 («expected только при зависимостях»); дотяжка визитов/оплат (роуты начинают требовать тело, коммиты несут `{}` — вывод закрытых #297/#298 «серверных правок нет» отменяется) — #324. **Удаление vs архивирование (решение юзера 20.09, отменяет #285 §5 от 17.09): деление идёт по ДЕЙСТВИЮ, не по типу сущности.** Любое удаление «навсегда» — включая архивируемые (staff/location/service/material/client) — идёт по этому же флоу (сухой прогон + диалог выбора, включая «архивировать вместо» + кольцо + expected, голый DELETE → 422; отмена execute-if-clean у их роутов) — реализация в отдельном follow-up issue. Архивирование остаётся вне схемы: обратимо через «Восстановить», без превью и кольца.
- `tags.md` §Delete: «Hard delete» дополняется контрактом records-флейвора: превью `?dry_run=true` (занятый → 409 с деревом+items), реальное удаление — только с `{resolutions?, expected}` (голый → 422 `expected_state_required`), отложенный commit после окна отмены; перечисление связей дополняется activity/client/visitor/record/photos-join'ами (сегодня только Service/Master/Location/Photo).

**D8 — проводка домена (обязательная, из панели).** Семейное правило: новая пара «(модель, зависимость)» требует запись в `FK_MATRIX` И запись в реестре обработчиков/счётчиков (`deletion.py:1269-1273`). Для тега добавляются:
- **8 счётчиков** в `_COUNTERS` (образец `_count_m_master_tags`, `deletion.py:352-356`) — подсчёт строк каждой join-таблицы по `tag_id == entity_id`. Без них `collect_dependencies` молча пропускает зависимость (`deletion.py:765-767`) → пустое дерево → занятый тег снова удаляется молча 204-м — ровно тот баг, который чинит #318. Родительские счётчики (по `service_id`/`master_id`/…) не переиспользуются — они считают другую колонку.
- **8 каскад-хендлеров** в `CASCADE_HANDLERS` (образец `_h_cascade_service_tags`, `deletion.py:1196-1202`) — join-delete по `tag_id`; пропущенный хендлер исполняются «тихо» (`generic.py:384-389`) → сироты-join-строки → FK-нарушение → 500 на подтверждении. Альтернатива «ORM-удаление вместо хендлеров» (панель, simplicity) отклонена: семейный принцип — детерминированный исполнитель по матрице независимо от PRAGMA-состояния (прецедент Staff, `deletion.py:141-148`) + тест-страж #324 строится на парах «матрица+хендлер».
- **8 id-коллекторов** в `_ID_COLLECTORS` (образец `_ids_r_record_tags`, `deletion.py:824-828`; потребляет `collect_dependency_ids` из роутера, `records.py:346`) — parent-id по `tag_id`; **без них expected-сверка молча пуста** (`deletion.py:929-930` — тот же тихий пропуск, что у счётчиков) и главный гейс rev5 — «непредпосредованное снятие невозможно» — мёртвый код (панель wave 2, блокер ×3).
- **8 item-коллекторов** в `_ITEM_COLLECTORS` (образец — visits/payments у записей): `{id, label}` каждой связи; без них items=None (`exclude_none` выкидывает) — `expected` строить не из чего (D6). Билдеры меток по 8 родительским сущностям, PII-граница — D6.
- **Контрактные ветки живут в роутере** `tags.py` (зеркало `records.py:322-364`: 422-формы, dry_run-ветка, subset-сверка, `ResolutionError`); подъём `resolve_delete` (ниже) покрывает только исполнение — сервис проверки не делает (панель wave 2). Структурно однотипные счётчики/коллекторы/хендлеры допустимо сворачивать параметризованной фабрикой — решает план (панель, simplicity).
- **`resolve_delete` поднимается с `ArchiveService` на общий базовый `GenericService`** (сегодня `generic.py:212/313`): метод не завязан на soft-delete-семантику (тело работает от `self._model` и доменных реестров), `TagService` получает его наследованием; тип-хинты хендлеров расширяются до базового класса (косметика). Вариант «TagService наследует ArchiveService» отклонён: `ArchiveService` документирован для `AbstractModelSoftDelete`-моделей — тег не из них, тянуть archive/restore на тег = семантический дрейф.
- **docstring-обновления** в `deletion.py` (модульный `:41-42` и docstring `validate_resolutions` `:1008`, где «`*_tags`» перечислены auto-зависимостями без уточнения стороны) — после правила перспективы (D1) уточняются: «`*_tags` с родительской стороны».

**D9 — DeleteDialog: подписи тег-стороны (из панели).** Переиспользование диалога требует точечных правок подписей:
- `depLabel` предпочитает `AUTO_ENTITY_LABEL[dep.entity]` (`DeleteDialog.tsx:162-164`), а пять из восьми join-сущностей уже заняты там родительской стороной (`service_tags`…`record_tags` → «Теги», `:73-84`) — тег-сторона рендерила бы «Теги: N» вместо «Услуги: N». Фикс: пять `*_tags`-строк убираются из `AUTO_ENTITY_LABEL`; родительская сторона падает в fallback `RELATION_PLURAL['Тег'] = 'Теги'` (relation родительских записей — «Тег») — **рендер родительских диалогов не меняется** (та же строка, другой путь); тег-сторона получает правильные подписи из relation.
- `RELATION_PLURAL` дополняется: Занятие→Занятия, Мастер→Мастера, Локация→Локации, Клиент→Клиенты, Фото→Фото (Услуга/Запись/Посетитель/Тег уже есть).
- Суффикс каскада «удалён/удалены» (`actionSuffix`, `:154-160`) для тег-диалога неверен семантически (услуги не удаляются — снимаются ссылки): per-type суффикс «снят/сняты» для `entityType='tag'` (паттерн per-type уже есть — `AUTO_LINES_HIDDEN`).
- `'tag'` добавляется в `DeleteDialogEntityType` (`:32`) и `TITLE_BY_TYPE` (`:107-116`).

## 3. Что сознательно НЕ строим

- Ничего из контракта записей больше не исключается (rev4/rev5, решения юзера): кольцо, dry_run, items, expected — всё переносится; не переносится только канонический item-ключ модалки записи (D5 #285) — у тега модалки нет;
- изменение обращения с `*_tags`-join в родительских матрицах (остаются auto);
- остаток семьи без is_active: visitors/positions/photos/user_settings — #324;
- массовые операции с тегами, restore/архив тегов.

## 4. User Scenarios (каждая → тест)

- **S1. Удаление занятого тега через диалог.** Админ в справочнике тегов нажимает «Удалить» у тега, проставленного на 2 услуги и 3 записи: сервер отвечает 409 с деревом; открывается диалог «тег будет снят» с поимёнными строками («Стрижка», «Маникюр», «Запись от 12.05 …», до 10 + «и ещё N»); подтверждение → строка исчезает, тост «Удалено. Отменить» с кольцом; после окна commit — тег удалён, ссылки сняты (у услуги и записи тег исчез). (e2e: новый spec `tags-delete-contract.spec.ts`)
- **S2. Удаление чистого тега — отложенное.** Тег без связей: «Удалить» → строка исчезает сразу, тост «Удалено. Отменить» с кольцом; после окна — тега нет в БД. (e2e: тот же spec, DB-полл-паттерн #285)
- **S3. Отмена в диалоге.** Занятый тег: открыть диалог → «Отмена» → тег и все ссылки на месте, DELETE не исполнен. (e2e)
- **S9. Отмена в окне (undo).** Удаление (чистое или после подтверждения диалога) → «Отменить» до истечения окна: строка тега вернулась в таблицу, DELETE на сервер не уходил, БД не тронута. (e2e — чистый путь; каскадный — vitest)
- **S4. Прямой API-вызов без подтверждения блокируется.** Голый DELETE `/api/v1/tags/{id}` → 422 `expected_state_required` (молчаливого исполнения больше нет ни для занятого, ни для чистого); `?dry_run=true` занятого → 409 с деревом, тег и ссылки не тронуты. (pytest-контракт)
- **S5. Исполнение с resolutions и expected.** DELETE с `{resolutions: {все 8: cascade}, expected: {id-множества из items}}` → 204; join-строки всех 8 таблиц вычищены, родительские строки целы — включая `photo_tags`/`visitor_tags`, не покрытые родительскими матрицами. (pytest-контракт)
- **S6. Негативы контракта.** Неизвестный id с телом → 404 (голый DELETE на неизвестном id → 422 раньше 404 — форма предшествует probe); resolutions с недопустимым действием у занятой зависимости (или без действия) → 422; `dry_run=true` + тело с `resolutions` → 422 `dry_run_with_resolutions_forbidden`; неизвестный ключ тела игнорируется → 204 (семейная семантика §16 пинится тестом). (pytest-контракт)
- **S7. Провал исполнения.** Сеть пропала в окне: commit падает → строка вернулась + error-тост. Тег удалён конкурентом (commit → 404): тихий успех — удаления цель достигнута, тоста нет (D4-семья; 404 ≠ ошибка). (vitest-ветки; e2e по setOffline-паттерну #239 — по объёму решит план)
- **S10. Гонка окна — expected-сверка.** Ссылка появилась между подтверждением и commit (чистому пути — через API в окне): commit → 409 `stale_dependencies` → строка вернулась + тост «Не удалось удалить: данные изменились» с «Обновить»; тег и новая ссылка живы в БД. Обратная гонка (ссылка исчезла за окно) commit не блокирует. (pytest subset-юниты — зеркало D7 #285; e2e — по объёму плана)
- **S8. Превью без разрушения.** `DELETE ?dry_run=true`: занятый тег → 409 с деревом (счётчики + items), тег и ссылки НЕ тронуты; чистый → 204, тег НЕ удалён. (pytest-контракт)

## 5. Behavioral Delta (до → после)

| Ситуация | До | После |
|---|---|---|
| Удаление занятого тега (UI) | confirm «Удалить тег?» → тег удалён, молча снят с 8 видов объектов | диалог с поимёнными строками («с каких объектов снимется», до 10 + «и ещё N») → подтверждение → строка исчезает, тост «Удалено. Отменить» с кольцом (5 с) → после окна удаление на сервере |
| Удаление чистого тега (UI) | confirm → удаление | строка исчезает сразу + тост «Удалено. Отменить» с кольцом (5 с); окно истекло — удаление на сервере |
| Отмена удаления (UI) | невозможно (confirm до удаления — единственная точка) | «Отменить» в тосте возвращает строку, сервер не тронут |
| Удаление тега (API, голый DELETE) | 204 + молчаливое снятие ссылок | 422 `expected_state_required` — исполнитель обязан нести ожидаемое состояние; превью — `?dry_run=true` |
| Удаление занятого тега (API, dry_run) | — | 409 `has_dependencies` (дерево: счётчики + items) |
| Ссылка появилась в окне отмены | — (сегодня окна нет) | commit отказывает 409 `stale_dependencies`, ничего не снято, тост «данные изменились» с «Обновить» |
| Родительские каскады (удаление записи/услуги/мастера… снимает тег-ссылки) | auto, молча | без изменений (auto остаётся) |
| Экраны связанных объектов после удаления тега | устаревают до следующей загрузки | без изменений: SSE публикует имена join-таблиц — фронт дропает их как неизвестные семейства, инвалидация только `['tags']` (паритет с каскадом клиентов, осознанно) |

## 7. Риски и допущения (для панели)

- Проводка домена (счётчики/хендлеры/подъём `resolve_delete`) — D8; «бесплатного реюза» коллектора нет: `_COUNTERS` не содержит теговых ключей, пропуск молчалив (панель, подтверждено по коду).
- Гонка «ссылка добавлена между подтверждением и commit» ловится `expected`-сверкой (D4/S10) — непоказанное снятие невозможно; исчезнувшая за окно ссылка commit не блокирует (subset). Популярный тег → большой items-пейлоад: отображение капировано (10 + «и ещё N»), `expected` несёт все id — как у записей.
- Тест-страж #324 («схема ↔ матрица») накроет теги автоматически, когда приедет с #324 — конфликтов нет: #318 только декларирует зависимости.
- Форма тела ошибки (`detail` как машинный код `has_dependencies`) расходится с RFC 9457 (`detail` — человекочитаемое поле) — осознанно: форма зафиксирована семьёй #207/#285 и уже в проде; формализация problem+json — семейный follow-up, не #318.
- DELETE с телом — осознанное отклонение от доминирующей конвенции «DELETE без тела» (Google AIP-135 прямо запрещает тело на delete, прецедент «за» — Kubernetes DeleteOptions): семья #285 уже в проде с телом; внешние потребители документируются через dry_run + expected (best-practices wave 2).
- Безопасный просмотр для внешних скриптовых потребителей — `?dry_run=true` (D3, rev3); для #324 — готовый шаблон формы.
