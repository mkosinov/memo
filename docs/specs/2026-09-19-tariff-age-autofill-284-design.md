# #284: Автоподстановка тарифа по возрастной группе посетителя

Дата: 2026-09-19 · Статус: Gate B (ждёт ОК владельца) · Источник: issue #284, дизайн-диалог 19.09

## 1. Проблема

Тарифы услуги (`{название, описание, цена}`) вложены в услугу и никак не связаны с возрастом
посетителя. Дефолтный тариф строки посетителя везде — «первый в списке»: черновик строки
(`makeEmptyVisitRow`), форма бронирования (`NewRecordTab`), быстрое добавление анонима
(`ClientRecordTab` через параметр `defaultTariff` в `useRecordMutations`), форма посетителя
(`AddVisitorForm`); сервер присланный тариф просто сохраняет как есть — дефолт он не вычисляет.
Смена возраста в строке сегодня не влияет на тариф и цену.

Детей приходит больше взрослых, и админ вручную правит тариф в каждой строке. Система не может
подсказать: у тарифа нет признака аудитории — название свободный текст.

Правило студии-владельца: детский тариф действует до 11 лет включительно, с 12 лет — взрослый.
Граница осознанно захардкожена (решение владельца 19.09): настройки «границы детского возраста»
не заводим, конфигурация сводится к пометке тарифов.

## 2. Концепт (утверждён владельцем в диалоге 19.09)

1. У тарифа появляется один новый признак — **возрастная группа** (`audience`):
   enum `TariffAudience` в общем модуле перечислений; в БД хранится строкой
   `"kid" / "adult" / "all"`, колонка NOT NULL со значением по умолчанию `"all"`.
   Русские подписи — только в интерфейсе, строчными: «детский», «взрослый», «единый».
2. Название тарифа остаётся свободным текстом и остаётся первичным отображением. Тарифы могут
   различаться не только возрастом (пример владельца: размер холста), поэтому на услуге
   допускается несколько тарифов одной группы — уникальности нет, никакой валидации формы
   услуги нет.
3. Классификатор посетителя: возраст из группы «Дети» селекта возраста (числа 3–11) →
   «детская» сторона; всё остальное (12–17, «Взрослый», пустой возраст) → «взрослая» сторона.
   Граница 11/12 уже существует в коде как деление на группы «Дети»/«Подростки» — она
   становится доменным правилом и выводится из одного общего источника (константа диапазона,
   из которой собираются и опции селекта, и классификатор).
4. Подстановка — **правило первого совпадения**, вычисляется единым резолвером (один владелец
   правила дефолтного тарифа; все клиентские места выбора дефолта зовут его, дублирующих
   реализаций больше нет):

```
строка посетителя: услуга X, возраст A
        ↓
A ∈ диапазон «Дети» (3–11)?
        ↓ да                              ↓ нет
первый тариф услуги X с               первый тариф услуги X с
audience = "kid"                      audience = "adult"
        ↓ нет такого → первый в списке (поведение как сегодня)
        ("all" в подстановке не участвует никогда)
```

   Уточнения контракта резолвера: «первый» — по порядку списка тарифов услуги, как его
   отдаёт API; пустой список тарифов → тарифа нет (строка создаётся/остаётся без тарифа);
   fallback «первый в списке» может оказаться тарифом чужой группы (услуги только с
   «детскими» тарифами легальны) — это легаси-поведение, принято владельцем; повторный вызов
   с тем же возрастом — видимая пустая операция (тариф уже резолверный).

5. Явная переподстановка (решение владельца): смена возраста **всегда** переподставляет тариф
   по правилу п.4 — в том числе затирая ручной выбор (в услугах с несколькими «детскими»
   тарифами ручной выбор сбрасывается на первый — норма, админ перевыбирает; механизма отмены
   нет). Смена тарифа переписывает цену строки — как сегодня. Подтверждений и плашек нет:
   админ контролирует итог.
6. Сервер в подстановке не участвует: клиент всегда отправляет явный тариф, сервер сохраняет
   его как есть (пустое значение остаётся пустым — серверного вычисления дефолта нет).
7. Случай «лет не знаем, но это ребёнок»: любое число из группы «Дети» (3–11) — подстановка
   сработает одинаково. Новых сущностей для этого нет.

## 3. Behavioral Delta (до → после)

| Ситуация | До | После |
|---|---|---|
| Создание строки, возраст пустой | первый тариф в списке | первый тариф с `adult`; если нет — первый в списке |
| Выбран возраст 6 | тариф не меняется | переподставился первый `kid`, цена строки переписалась |
| Выбран возраст 14 | тариф не меняется | переподставился первый `adult`, цена переписалась |
| Ручной выбор тарифа, затем смена возраста | тариф не менялся | ручной выбор затёрт переподстановкой (норма) |
| Услуга с одним «единым» тарифом | первый в списке | без изменений (`all` не участвует) |
| Услуга, где никто не помечен | первый в списке | без изменений |
| Услуга с несколькими `kid` (холсты) | — | подставляется первый `kid`, второй осью админ управляет вручную |
| Услуга только с «детскими» тарифами, возраст взрослый | первый в списке (= детский) | без изменений: fallback может пересекать группы (легаси, принято) |
| Редактор услуги, тариф | название/описание/цена | + выпадающий «возрастная группа» (детский/взрослый/единый) |
| Существующие услуги до настройки | — | поведение не меняется (бэкфилл: «детский»→kid, «взрослый»→adult, остальное→all) |
| После миграции: названия вне канона | — | группа «единый», автоподстановка выключена; админ один раз пробегает справочник услуг (сигнала об этом нет) |

## 4. User Scenarios (каждый сценарий → E2E-тест)

1. **Детская строка.** Услуга с парой «детский»+«взрослый»; админ создаёт строку посетителя и
   выбирает возраст 6 → в строке детский тариф, цена = детская. → E2E
2. **Взрослая строка.** Там же выбирает возраст 14 → взрослый тариф, цена взрослая. → E2E
3. **Год неизвестен.** Админ не знает точного возраста, но знает, что ребёнок: выбирает 8
   (группа «Дети») → детский тариф, как и для 6. → E2E
4. **Ручной выбор затирается.** Админ вручную ставит взрослый тариф в строке с возрастом 6,
   затем меняет возраст 6→7 → тариф вернулся к детскому (переподстановка сильнее ручного);
   возврат возраста на «Взрослый» → переподставился взрослый тариф. → E2E
5. **Единый тариф.** Услуга с одним «единый»: любые смены возраста не меняют тариф и цену. → E2E
6. **Ничего не помечено.** Услуга, у всех тарифов группа «единый» (или только «детские» при
   взрослом возрасте): поведение идентично сегодняшнему (первый в списке, группы могут
   пересекаться). → E2E
7. **Настройка в редакторе.** Админ открывает услугу, назначает группам тарифы «детский/
   взрослый/единый», сохраняет; после переоткрытия группы на месте. → E2E
8. **Две детские (холсты).** Услуга с тарифами «детский малый», «детский большой» (оба `kid`),
   «взрослый» (`adult`): возраст 6 подставляет «детский малый» (первый), админ вручную
   переключает на «большой» — цена переписалась; смена возраста 6→7 возвращает «малый». → E2E

## 5. Технические изменения

### Backend
- `backend/src/models/enums.py`: новый enum `TariffAudience(str, enum.Enum)` —
  `KID = "kid"`, `ADULT = "adult"`, `ALL = "all"` (канон значений — строчные, как у всех
  перечислений системы).
- `backend/src/models/tariff.py`: колонка `audience` (строка, NOT NULL, `server_default "all"`).
- Миграция alembic (одна ревизия): добавить колонку (NOT NULL, `server_default "all"`) +
  бэкфилл по названию тарифа — точное совпадение без регистра: «детский» → kid,
  «взрослый» → adult, «единый» и всё несовпавшее → all. Бэкфилл накрывает и мягко удалённые
  строки. Даунгрейд определён явно (drop колонки; бэкфилл необратим — это принято).
  Ничего не удаляем, название остаётся.
- `backend/src/schemas/service.py`: `audience` в `TariffBase` / `TariffCreate` /
  `TariffUpdate` / `TariffResponse` — типизировано перечислением `TariffAudience` со
  значением по умолчанию `ALL`: отсутствующее поле → `all` (совместимость со старыми
  клиентами), неизвестная строка → 422 (не тихая запись мусора).
- Валидации формы услуги и уникальности групп НЕТ (ни в схемах, ни индексом в БД) —
  решение владельца (сценарий холстов).
- Сервер при сохранении записи тариф не вычисляет — сохраняет присланный `tariff_id`
  как есть (пустое остаётся пустым). Это поведение не меняется (вне скоупа; уходить
  из зоны дизайна #171).

### api-client (packages/api-client)
- Рукописные zod-схемы: `TariffResponseSchema`, `TariffCreateSchema` (+ типы) — поле
  `audience` (в Response — обязательное перечисление, в Create — опциональное с дефолтом
  `"all"`); отдельной TariffUpdate-схемы в пакете нет — обновляются ровно два места.

### Доменная схема фронта (packages/domain) — обязательно, иначе пометка теряется
- `TariffSchema` (сейчас только `id/title/price/description`) + маппинг в
  `frontend/admin/lib/transformers.ts` (`transformService`) — добавить `audience`.
  Без этого PUT услуги пересоздал бы тарифы без признака, и пометки молча сбрасывались
  бы в «единый» (панель: BLOCKER, подтверждено по коду).

### Frontend (frontend/admin)
- **Единый источник границы:** константа диапазона «Дети» (3–11) в одном месте; из неё
  собираются опции селекта возраста и классификатор резолвера (сегодня списки 3–11 и 12–17
  захардкожены в `AgeSelect` раздельно).
- **Единый резолвер** `resolveDefaultTariff(tariffs, age)`: первый `kid` / первый `adult` /
  fallback «первый в списке» (порядок — как отдаёт API); пустой список → тарифа нет. Все
  места дефолта переводятся на него: `makeEmptyVisitRow`, обработчик смены возраста в строке
  (сегодня меняет только age), `NewRecordTab`, `ClientRecordTab.addAnonymousVisit`,
  начальный `tariffId` в `AddVisitorForm`. В плане также проверить параметр `defaultTariff`
  хука `useRecordMutations` — его вызывающие должны передавать результат резолвера.
- Смена возраста в строке → всегда вызывать резолвер заново (п.2.5).
- `ServiceModal` (NestedList тарифов): в строке тарифа выпадающий «возрастная группа» с
  опциями «детский / взрослый / единый» (нижний регистр — решение владельца), без проверки
  дубликатов групп; у селекта программная метка с названием строки тарифа (a11y — колонка-заголовок
  не связывается с контролами ячеек).
- Сентинел «Взрослый» в селекте возраста — строковое значение `'adult'`, не число: при
  вынесении общего источника диапазона не смешивать его с возрастами 3–17.
- Отображение тарифов (таблицы, селекты строк) — по названию, как сегодня.

### Порядок и целостность (примечание для плана)
- PUT услуги пересоздаёт все тарифы (DELETE+CREATE) — id тарифов меняются при каждом
  сохранении услуги. Это существующее поведение, бэкфилл миграции его не касается; сохранённые
  `tariff_id` в строках визитов не мигрируют. Резолвер работает только по живому списку
  тарифов услуги в порядке API — контракта «стабильный id тарифа» в спеке нет.
- Редактор архивной услуги ведёт себя как сегодня: новый селект доступен там же, где остальные
  поля тарифа (отдельной логики архивности не заводим).

## 6. Отвергнутые альтернативы (решения дизайн-диалога 19.09)

- **Число-граница в настройках студии** — поверхность общих настроек в системе не существует,
  заводить ради одного числа; владелец принял захардкоженную границу (группы селекта уже
  кодируют 11/12).
- **Тип из названия тарифа (подстрока/точное совпадение)** — невидимый договор: переименование
  молча выключает подстановку; полусостояния недиагностируемы. Используется ровно один раз —
  как бэкфилл при миграции, дальше название — просто текст.
- **Диапазоны возрастов на каждом тарифе** — YAGNI; потребность одна: «детский или взрослый».
- **Колонки `service.kids_price/adult_price` (id на услуге) и связующая таблица** — встречные
  стрелки услуга↔тариф; связующая таблица для не-M:N связи; bulk-доступность даёт сам признак,
  а не его размещение.
- **Гардсл-плашка «не перетирать ручной выбор»** — отменена владельцем: подстановка явная,
  админ контролирует итог.
- **Валидация «ровно два вида услуги»** — отменена владельцем вместе с уникальностью групп:
  тарифы могут различаться второй осью (холсты); вместо неё — правило первого совпадения.
- **Обучаемый дефолт** — холодный старт, непредсказуемость; правило владельца детерминировано.

## 7. Границы скоупа (сознательно НЕ строим)

- Серверную подстановку и валидацию возраста против тарифа (индустриальная норма: подстановка
  предлагает, не запрещает).
- Настройку границы 11/12, подсказки/предупреждения в редакторе, отдельный документ правил
  тарифов (всё живёт в services.md).
- Вторую ось тарифов (холсты и пр.) как модель — только гарантия совместимости: несколько
  тарифов одной группы легальны, подстановка берёт первый.
- Изменения серверного сохранения тарифа в записи (сервер и так сохраняет присланный
  `tariff_id` как есть) и сервисного слоя (#171).
