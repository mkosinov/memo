# Спека: #325 — удаление занятия переносится в сценарий `delete_activity` + аудит каскадов

- Issue: #325 (app:admin), depends-on: #171 (в main), #286 (в main) — оба закрыты.
- Дата: 2026-09-20; Gate B ОК 2026-09-21. Rev2 2026-09-21: точечная правка секции «Аудит каскадов» по решению пользователя из #326 (Gate A, вариант A — своя вертикаль слоёв у каждой содержательной таблицы): записи `masters` из StaffService переведены из «легитимных» в нарушения (дорожка #326). Концепт, Behavioral Delta, сценарии и план не затронуты.
- Тип: рефактор бэкенда, поведение и контракты не меняются.

## Контекст и проблема

`ActivityService.delete` (`backend/src/services/activity.py:259–299`, декорированный `@transactional`) при удалении занятия сам, сырыми табличными командами, сносит чужие таблицы:

- `delete(Visit)` по набору id записей занятия — чужая таблица (владелец — сервис визитов);
- `delete(Payment)` — чужая таблица (сервис платежей);
- `delete(record_tags)` — чужая связка (канон: `record_tags` — сервис записей);
- `delete(Record)` — чужая таблица (сервис записей);
- `update(Photo) SET activity_id = NULL` — чужая таблица (сервис фото);
- свои: `delete(activity_tags)`, `delete(Activity)` — законны.

Это нарушает канон слоёв `docs/domain-rules/service-layer.md` (rev4):

- правило 1 «Один писатель»: табличные команды — только в репозитории владельца; `record_tags` обслуживает сервис записей;
- правило 2 «Сценарий»: действие, охватывающее несколько сущностей, — публичная функция `usecases/<сущность>.py`, декорированная `@transactional`;
- дерево выбора «куда положить новый код»: «действие охватывает несколько сущностей → сценарий usecases».

При этом сам эндпоинт `DELETE /api/v1/activities/{id}` (`backend/src/api/v1/activities.py:236`) уже на едином контракте удалений #286 D2: `?dry_run=true` — превью 204/409; без тела — 422 `EXPECTED_STATE_REQUIRED`; с телом `{expected}` — коммит с проверкой снимка (409 `stale_dependencies` при расхождении). Исполнение коммита сегодня — «handwritten `ActivityService.delete`». Переносится только исполнение; контракт эндпоинта и фронт (пайплайн PendingActions, окно отмены) не трогаются.

Ровесный прецедент уже существует: удаление записи идёт через сценарий `usecases/records.py::delete_record` (`@transactional`), который составляет без-транзакционных помощников владельцев: `visit_service.delete_visits_by_record` → `payment_service.delete_by_record` → `record_service.delete_row_with_tags` (`backend/src/usecases/records.py:426–428`).

## Выбранный концепт

**Сценарий `delete_activity` в новом модуле `backend/src/usecases/activities.py`** (selfless-вызов, `@transactional`: одна транзакция + один пакет событий), роут коммита вызывает его вместо `ActivityService.delete` (по образцу `records.py:387`). Состав сценария:

1. Существование занятия: нет → `False` (роут отдаёт 404) — как сейчас.
2. Сбор id записей занятия: переиспользуется готовый `collect_dependency_ids` (`backend/src/domain/deletion.py:1266`) — тот же вызов, который роут уже делает сегодня для верификации `expected` (`activities.py:335`); двухуровневый обход #286 D2 отдаёт id записей занятия. Отдельный новый помощник сбора НЕ создаётся (защита от расхождения с FK-матрицей). Две оговорки: (а) модель занятия сценарий берёт из загруженной при проверке существования строки (`type(loaded)`, прецедент `usecases/records.py:396–398` — ORM-модели в сценарий не импортируются); (б) принимается компромисс по стоимости: сегодня сбор id — один запрос, через `collect_dependency_ids` — все пять коллекторов (visits/payments/record_tags/photos/activity_tags), из них каскадом потребляются не все; расхождение с FK-матрицей дороже лишних чтений на пути удаления.
3. Если записи есть — каскад по НАБОРУ id (правило 4 «bulk = одна множественная команда», не цикл по строкам):
   - визиты: новый bulk-вариант помощника визитов по набору `record_id` IN (…), марка «visits»;
   - платежи: новый bulk-вариант помощника платежей по набору, марка «payments»;
   - связки `record_tags` + строки записей: bulk-вариант помощника записей по набору, марки «records» и «tags» (за `record_tags`).
   Существующие помощники (`delete_visits_by_record`, `delete_by_record`, `delete_row_with_tags`) принимают один `record_id` и остаются для сценария записи; bulk-версии добавляются рядом (без-транзакционные, правило 3), существующая логика не переопределяется.
4. Фото: новый без-транзакционный помощник у сервиса фото — открепить (`activity_id = NULL`) по id занятия, марка «photos». Открепление (не удаление) и условие «даже без записей» — как сейчас.
5. Свои таблицы занятия: `delete(activity_tags)` + `delete(Activity)` через слой сервиса занятия (его владение), марка «tags» (за `activity_tags`) и «activities» — своя сущность сценария.

**Марки событий — две сетки, обе идентичны текущим** (`activity.py:289–302`): с записями — `{records, visits, payments, tags, photos, activities}`; без записей (чистое занятие) — `{photos, tags, activities}` (блок «records/visits/payments/tags» условный, фото и `activity_tags` — безусловны). Нюансы, зафиксированные панелью: «tags» ставится дважды (`record_tags` — условно, `activity_tags` — безусловно; аккумулятор — множество, дубли безвредны); «activities» сегодня сеется декоратором bound-метода (`decorators.py:118–126`), а selfless-сценарий стартует с ПУСТЫМ аккумулятором — сценарий ставит `mark_changed("activities")` явно. Юнит-тест фиксирует сетку чистого занятия `{photos, tags, activities}` (сегодня сетка чистого занятия тестом не покрыта).

Не меняются: порядок «визиты → платежи → связки/записи → фото-открепление → activity_tags → занятие», обе сетки марок событий (перечислены выше; состав пакета SSE-инвалидации прежний), коды и тела ответов, fail-closed семантика (проверка `expected` до исполнения), атомарность (всё или ничего). Побочно обновляются устаревающие упоминания удаляемого метода в документации кода: докстринг роута (`activities.py:274–278`), комментарий FK-карты (`domain/deletion.py:36–39`) и комментарии тестов (`tests/test_events_emit.py:120`, `tests/domain/test_deletion.py:413`).

Альтернативы (отсеяны на Gate A):
- «Оставить в сервисе, чужие команды вынести в помощники» — против правила 2: мульти-сущностное действие обязан выполнять сценарий; повторное нарушение воспроизводится при следующем расширении.
- «FK `ON DELETE CASCADE` на уровне базы» — меняет схему и делает каскады молчаливыми; связки без `ondelete` — зафиксированное решение #194/канона; необратимо по схеме.

## Behavioral Delta

Для пользователя: **без изменений (до = после)**. Все ветки эндпоинта идентичны:

| Ветка | До | После |
|---|---|---|
| `DELETE` без флага и тела | 422 `EXPECTED_STATE_REQUIRED` (ErrorDetail) | 422 `EXPECTED_STATE_REQUIRED` (ErrorDetail) |
| `?dry_run=true` + тело | 422 `invalid_delete_request` (до любого чтения базы) | 422 `invalid_delete_request` (до любого чтения базы) |
| `?dry_run=true`, без зависимостей | 204 (ничего не тронуто) | 204 (ничего не тронуто) |
| `?dry_run=true`, есть зависимости | 409 + двухуровневое дерево | 409 + двухуровневое дерево |
| Коммит, занятия нет | 404 | 404 |
| Коммит, `expected` разошёлся | 409 `stale_dependencies` + дерево, ничего не удалено | 409 `stale_dependencies` + дерево, ничего не удалено |
| Коммит, всё совпало | 204, каскад одной транзакцией | 204, каскад одной транзакцией |

Для разработчика: проводка коммита меняется с `ActivityService.delete` на сценарий `usecases.activities.delete_activity`; `ActivityService.delete` удаляется (тонкий дубликат с транзакцией над сценарием запрещён правилом 5 «вложенные декорированные вызовы»).

## User Scenarios

Каждый сценарий — существующее поведение, закреплённое e2e; после рефактора тесты остаются зелёными без правок.

1. **Чистое занятие** (без записей): карточка исчезает, тост отмены с кольцом, по истечении окна — коммит, в базе занятия нет. → E2E `frontend/admin/e2e/activity-deferred-delete.spec.ts` S1, S1m.
2. **Отмена**: в окне 5 секунд нажата «Отменить» — карточка возвращается, запрос на сервер не уходит. → E2E S2, S4.
3. **Занятие с записями** (каскад): диалог подтверждения показывает зависимости; после коммита записи (и их визиты/платежи/тег-связки) исчезают, фото остаются (откреплены). → E2E S3/S3m (диалог), S4 (каскадная ветка); бэкенд-контракт — `backend/tests/test_api_activities.py:820`.
4. **Dry-run превью**: 409 с деревом зависимостей без изменения строк. → `backend/tests/test_api_activities.py` (dry-run-ветки), E2E S3.
5. **Гонка в окне отмены**: визит добавлен между превью и коммитом → 409 `stale_dependencies`, карточка возвращается с плашкой «Обновить», неделя перечитывается. → E2E S6; `backend/tests/test_api_activities.py:859`.
6. **Обрыв сети при коммите**: карточка возвращается с красным тостом, занятие выживает. → E2E S5.
