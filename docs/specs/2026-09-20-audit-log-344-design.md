# Спека #344: Журнал действий пользователей (audit log)

- Issue: #344 (feat(admin): журнал действий пользователей — таблица в админке)
- Дата: 2026-09-20. Статус: Gate B (ожидает ОК пользователя).
- Решения Gate A (пользователь, 2026-09-20): **1-А** — семантичный журнал действий (запись рождается в границах транзакции действия); **2-Б** — факт + снимок изменений «было → стало» с маскированием персональных данных; **3** — охват: все изменяемые сущности.

## 1. Постановка

В админке работают несколько пользователей с ролями (администраторы, мастера). Если сумма платежа оказалась неверной, запись изменилась или услуга заархивировалась — восстановить картину «кто и когда» сегодня невозможно: post-commit события push-инвалидации (#239) не сохраняются и автора не несут (payload = имена сущностей + вкладка-источник).

Журнал действий даёт администратору таблицу «кто / что / над чем / когда (+ что именно изменилось)» с фильтрами. Доступ — только роли администратора.

## 2. Разведка (вердикт: актуальна)

Все премиссы issue подтверждены по живому дереву:

- Хаб событий in-memory, подписчики — SSE-соединения; публикация контрактуально неблокирующая (`put_nowait`-only), payload — множество имён сущностей + конверт происхождения `{type: "tab", id}`. Автора нет, персистенции нет.
- Конверт происхождения сам задокументирован как точка расширения будущими типами писателей (`user`, `system`).
- Авторизация (#247/#263): кука `memo_session` → `require_session` → `AuthedUser` (id, phone, role, staff_id); зависимость `require_admin` уже существует для admin-only роутов.
- Мутации унифицированы: одиночные create/update/patch/delete/archive/restore всех сущностей идут через общий репозиторий (`BaseRepository`/`ArchiveRepository`), который **сначала читает строку, затем меняет** — старые значения для снимка доступны в точке мутации без дополнительных запросов.
- Канонические имена сущностей уже есть (словарь #239: модель → snake-plural имя).
- Маскировка телефона уже существует (`mask_phone`, последние 4 цифры).
- Двухпользовательский e2e-паттерн существует (фикстура двух браузерных контекстов из server-push тестов).
- Существующего аудита нет нигде (grep пуст).

Уточнение премиссы issue: post-commit механизм **не переиспользуется как канал записи** (его контракт это запрещает), но переиспользуются его строительные блоки: словарь имён сущностей, паттерн запросного аккумулятора на contextvar, точка перехвата `@transactional`.

## 3. Концепция (выбранный и отвергнутые подходы)

Выбрано (решение 1-А): **транзакционный аудит** — запись журнала рождается в той же транзакции, что и само изменение. Действие и журнал атомарны: не бывает изменения без строки журнала и строки без изменения.

Отвергнуто:

- **Подписчик хаба событий** — ломает зафиксированный контракт #239 (неблокирующая публикация; payload без действия и идентификаторов); запись после коммита терялась бы при сбое.
- **HTTP-журнал в middleware** (решение 1-Б, отвергнуто пользователем) — журнал про запросы, а не про действия: ложные строки от служебных и пробных запросов (dry-run превью удалений), нет семантики действия, запись вне транзакции.

Правило наполнения: **журнал — про действия пользователя, а не про строки БД**. Одно законченное действие пользователя = одна строка журнала о целевой сущности; каскадные дочерние строки (визиты и платежи удаляемой записи и т.п.) не журналируются.

## 4. Механика записи (бэкенд)

### 4.1 Автор

`resolve_authed` — общее ядро резолва сессии, через которое проходят И строгий guard (`require_session`), И мягкий резолвер скоупа (`get_optional_scope`, публичное создание записи до веб-бронирования #8) — дополнительно кладёт автора в запросный contextvar: `user_id`, `role`. Дополнительных обращений к БД нет — резолв сессии уже происходит на каждом маршруте. Автор берётся только из серверной сессии, не из данных запроса — подделать его из клиента нельзя. Правило: **нет автора → нет записи журнала** (системные записи — сиды, CLI, тестовые фикстуры без сессии, анонимное создание записи — не журналируются, см. §12; создание записи мастером через мягкий резолвер автором покрывается — ядро общее).

### 4.2 Точка сбора

Сырая запись `{entity, action, entity_id, before, after}` формируется в общем репозитории (`BaseRepository.create/update/patch/delete/reorder`) — единственном месте, где естественно доступны и старые, и новые значения строки. Имя сущности берётся из словаря #239 (модель → каноническое имя). Записи накапливаются в отдельном запросном аккумуляторе (contextvar, по образцу аккумулятора имён #239); **контракт существующего аккумулятора имён и публикации не меняется**.

Архивация/восстановление — исключение из авто-сбора: по факту кода это сервисные операции, исполняемые общим `patch` с единственным полем `is_active`, и репозиторного метода `archive`/`restore` не существует. Эти действия помечаются **явно** в `ArchiveService.archive/restore` (действия `archive`/`restore`, без снимка полей), а для сотрудников — в их собственных переопределённых `StaffService.archive/restore` (реализованы без вызова общего кода); авто-собранная для той же строки запись `update` вытесняется (правило старшинства ниже). No-op не журналируется и здесь: повторная архивация уже архивированной строки (или восстановление активной) поля не меняет — перед пометкой сверяется текущее состояние строки.

Словарь имён сущностей репозиторий импортирует лениво (внутри функции) — модуль словаря при верхнеуровневом импорте обходит все сервисы, и репозитории входят в этот же граф (задокументированный риск цикла; прецедент — ленивый импорт в `@transactional`).

Правило «одно действие — одна строка»: журналируются только изменения **целевой сущности действия**. Целевая сущность коридора 1 (простая операция) — сущность сервиса, которую `@transactional` уже резолвит для авто-пометки; репозиторий пишет записи журнала только по совпадению с ней. Каскадные дочерние изменения игнорируются.

Правило старшинства: **явная пометка вытесняет авто-сбор** — если в транзакции есть явная `mark_audit` для строки (совпадение сущности и идентификатора), авто-собранная репозиторием запись этой же строки отбрасывается; двойных строк одна операция не порождает (актуально для фото, сотрудников, архивации и сценариев записей — сценарий помечает строку записи явно, а репозиторий авто-собирает её же).

Сериализация снимка: значения в `changes` проходят канонический кодировщик до записи — даты → ISO-строка, десятичные (суммы) → строка, перечисления → значение; иначе вставка в JSON-колонку упала бы и откатила всю транзакцию действия вместе с журналом. Инвариант корректности «было»: старое значение фиксируется до первой мутации строки в сессии — доменные функции и сценарии не меняют поля строки до вызова репозитория (закрепляется в плане).

### 4.3 Сценарии (коридор 2) и нестандартные мутации

Сценарии usecases (создание/изменение/удаление записи и будущие) и мутации мимо общего репозитория помечают журнал **явно** (`mark_audit(...)`, по образцу `mark_changed`): целевая сущность, действие, идентификатор, снимок. Полный перечень точек явной пометки — в плане; по разведке это: сценарии записей, фото (загрузка/массовые операции), сотрудники (создание/изменение/удаление с каскадами учёток), профиль, визиты (standalone-сервис), настройки пользователя.

### 4.4 Вставка

`@transactional` после успешного выполнения метода, **до коммита**: вставляет накопленные строки журнала в ту же сессию → один коммит. Ошибка метода → откат действия и журнала вместе.

Владение накопителем: вставку и очистку выполняет **только обёртка, открывшая накопитель** (внешняя граница проводки — той же токенной схемой, какой открывается накопитель имён #239); внутренние декорированные обёртки видят уже открытый накопитель и ничего не вставляют. Это защищает проводки, где декорированный сценарий вызывает другие декорированные методы (сегодняшние сценарии записей зовут сервисы визитов/платежей), от повторной вставки одних и тех же строк на каждом уровне.

Внимание к циклу импортов: модуль аудита импортирует модели, из `decorators` — лениво (прецедент — WARNING в словаре имён #239).

### 4.5 Отложенные удаления (#285/#286)

Окно отмены — чисто клиентское: до API доходит только финальный запрос удаления (dry-run превью ничего не мутирует и не журналируется). Журналируется **финальный DELETE** — момент, когда данные реально исчезли. Отдельных точек перехвата для «постановки» и «отмены» на бэкенде не существует и искать их в плане не нужно.

### 4.6 Границы охвата

- Вход/выход и смена пароля — вне журнала (не данные предметной области; при потребности — отдельная задача).
- reorder (изменение порядка справочника) — одна строка на операцию: действие `reorder`, без идентификатора строки, подпись «N объектов», без снимка; если фактический порядок не изменился — строка не пишется (no-op).
- archive/restore — действия `archive`/`restore` без снимка полей (суть изменения очевидна из действия); no-op (повторная архивация архивированного) не пишется.

## 5. Схема данных

Миграция: таблица `audit_logs` (alembic, `add_audit_logs_table`). Модель — append-only на `Base`: собственные `id` + `created_at` (без `updated_at`, без soft-delete).

| Колонка | Тип | Содержимое |
| --- | --- | --- |
| `id` | String(36) PK | UUID |
| `created_at` | DateTime, индекс | момент действия (UTC) |
| `user_id` | String(36) FK users.id (ON DELETE SET NULL), индекс | автор (имя читается при выводе — join users → staff, актуальное имя полезнее для расследования); сегодня учётки удаляются только мягко (архивация), но если удаление появится — журнал не блокирует его: ссылка обнуляется, роль-снапшот и строки остаются |
| `user_role` | String(20) | роль автора **на момент действия** (снапшот: после повышения мастера до администратора история не переписывается задним числом) |
| `action` | String(16) | `create` / `update` / `delete` / `archive` / `restore` / `reorder` |
| `entity` | String(32), индекс (с entity_id) | каноническое имя #239 (`records`, `payments`, `clients`, …) |
| `entity_id` | String(36), nullable | идентификатор строки (null для reorder) |
| `entity_label` | String(255) | человекочитаемая подпись цели на момент действия («Иванов Иван», «Стрижка мужская», «Платёж …») |
| `changes` | JSON, nullable | снимок: `{поле: [было, стало]}` |

Индексы: `created_at`; `user_id`; `(entity, entity_id)`; `action`.

Таблица append-only: ни API, ни сервисный слой не изменяют и не удаляют строки журнала.

### 5.1 Снимок изменений (`changes`) и маскирование

- `update`/`archive-restore`-семейство PUT/PATCH: только поля, чьи значения фактически изменились. **No-op не журналируется:** если после сравнения ни одно поле не изменилось, строка журнала не пишется — действия не было.
- `create`: снимок ключевых полей созданного.
- `delete`: снимок ключевых полей удалённого (что исчезло).
- Маскирование: `phone`/`phone_digits` → `mask_phone` (последние 4 цифры); `email` → маскированное значение без полной строки (по образцу маскирования в скопе мастера). Паролей и токенов в payload'ах схем нет; содержимое файлов (фото) не пишется — только имена/пути. В `changes` попадают только скалярные поля и списки идентификаторов (например, `tag_ids`).
- Перечень «ключевых полей» для снимка create/delete — словарь на уровне модуля аудита (заголовок сущности + 2–4 несущих поля), без blob'ов.

## 6. API чтения

- `GET /api/v1/audit-logs` — параметры `page`, `per_page`, `user_id`, `action`, `entity`, `entity_id`, `date_from`, `date_to`; сортировка `created_at DESC`; ответ `PaginatedResponse[AuditLogResponse]` (`id`, `created_at`, `user: {id, label}`, `user_role` (из строки журнала), `action`, `entity`, `entity_id`, `entity_label`, `changes`). Доступ — `require_admin` (мастер → 403, аноним → 401). Чтение — коридор 3 (свободная читающая функция в модуле своего сервиса, один запрос с join).
- `GET /api/v1/audit-logs/authors` — `require_admin`; уникальные авторы журнала `[{user_id, label}]` для фильтра-дропдауна.
- Ретенция: в v1 не строится (допущение: журнал растёт от всех охраняемых мутаций всех пользователей, не только администраторов; для масштабов проекта объём мал — при росте отдельная задача о чистке/архивации).

## 7. Фронтенд (admin)

- Новый раздел **«Журнал»**, маршрут `/audit`, только для администраторов: маршрут добавляется в `ADMIN_ONLY_SECTIONS` (меню скрывается у мастеров, прямой заход — экран запрета; по образцу #263 T9), пункт меню — после «Справочников».
- Таблица на `DataTable` по канону дизайн-системы: колонки «Когда / Кто / Действие / Над чем / Изменения». Автор — имя + бейдж роли (роль из строки журнала — на момент действия). Действие и сущность — русские подписи из словаря на фронте (создал / изменил / удалил / заархивировал / восстановил / переставил).
- Пустые состояния: пустой журнал (до внедрения истории нет) — заглушка «Нет действий»; пустой список авторов — пустой дропдаун фильтра.
- «Изменения»: компактная расшифровка «поле: было → стало» (раскрывающаяся строка или тултип).
- Фильтры (по образцу страницы клиентов): автор (дропдаун из `/audit-logs/authors`), действие, сущность, период (`date_from`/`date_to`).
- Сортировка — серверная, `created_at DESC`; переключение сортировок в v1 не строится.
- api-client: схемы + функции `getAuditLogs`, `getAuditLogAuthors`.

## 8. Охват мутаций

| Семейство | Путь записи журнала |
| --- | --- |
| услуги, локации, материалы, теги, должности, клиенты, посетители, фото (удаление), настройки, занятия — одиночные CRUD | автоматически: общий репозиторий |
| архивация/восстановление архивируемых сущностей | явная пометка в `ArchiveService.archive/restore` и собственных `StaffService.archive/restore` (действие определяется сервисом, не `patch` по `is_active`) |
| записи (сценарии usecases), платежи, визиты, фото (загрузка/массовые), сотрудники, профиль | явная пометка `mark_audit` в сервисе/сценарии; массовая операция пользователя (загрузка N фото) — одна строка на операцию |
| reorder справочников | общий репозиторий, одна строка на операцию |
| каскадные дочерние строки (визиты/платежи записи и т.п.) | не журналируются |
| отложенные удаления (#285/#286) | строка на коммите удаления |
| вход/выход/смена пароля, системные записи без сессии, анонимное создание записи (публичный маршрут до веб-бронирования #8) | вне журнала (§12 — осознанные границы) |

Полный перечень точек явной пометки фиксируется в плане по живым файлам (разведка: сервисы платежей, визитов, фото, сотрудников, профиля, настроек; сценарии записей).

## 9. User Scenarios (каждый → E2E)

1. **Открыть журнал.** Администратор открывает «Журнал» — таблица истории действий с колонками «кто / что / над чем / когда / изменения». → `e2e/audit-log.spec.ts`.
2. **Чужое действие видно.** Два браузерных контекста (паттерн server-push): пользователь Б меняет сумму платежа; администратор А видит в журнале строку «изменил платёж … сумма: 500 → 700». → там же.
3. **Фильтры.** А фильтрует по автору, действию, сущности и периоду — таблица сужается; фильтры сбрасываются — возвращается полная лента. → там же.
4. **Мастер не допущен.** У мастера нет пункта «Журнал»; прямой заход на `/audit` — экран запрета; прямой запрос API — 403. → там же (по образцу auth-roles).
5. **Маскирование.** Через UI меняется телефон клиента — в журнале видно изменение поля, но номер замаскирован (последние 4 цифры). → там же.
6. **Снимок удаления.** Администратор удаляет посетителя — в журнале строка «удалил посетителя …» с подписью удалённого. → там же.

## 10. Behavioral Delta (до → после)

| Аспект | До | После |
| --- | --- | --- |
| Автор изменения | узнать нельзя (косвенные признаки) | раздел «Журнал»: кто, что, над чем, когда — по каждому действию |
| Что именно изменили | не видно | снимок «поле: было → стало»; телефоны замаскированы |
| Хранение истории | события летят вкладкам и исчезают | каждая завершённая мутация пишет запись в той же транзакции (для пользователя невидимо, кроме новой страницы) |
| Доступ | — | раздел и API только для администраторов; у мастеров интерфейс без изменений |
| Отложенные удаления | — | журналируется фактическое удаление (коммит), постановка и отмена — нет |

## 11. Тестирование

- **Backend (pytest):** запись на create/update/patch/delete/archive/restore (по представителю каждого пути из §8); атомарность (ошибка метода → нет строки журнала); «одно действие — одна строка» (каскад записи не порождает строк визитов/платежей; вложенные декорированные уровни — одна вставка на проводку); no-op PATCH без изменений, повторная архивация и reorder без перестановки → нет записи; нет автора → нет записи (в т.ч. анонимное создание записи); маскирование телефона и email в снимке; каноническая сериализация (дата/десятичное/перечисление) в JSON; коммит отложенного удаления → одна строка; `require_admin`: 403 мастеру, 401 анониму; фильтры и пагинация эндпоинта; `/authors`.
- **Инвариант #239:** существующие тесты событий (полнота сущностей, публикация имён) остаются зелёными без правок — контракт не меняется.
- **Frontend:** vitest на словарь подписей и рендер снимка; e2e — сценарии §9.
- Нагрузка: +1–2 INSERT на транзакцию — для админки пренебрежимо (зафиксировано допущением).

## 12. Риски и допущения

- Правка центрального `@transactional` — самая чувствительная точка; параллельный аккумулятор, владение накопителем внешней обёрткой и ленивый импорт снимают циклы и дубли; регресс ловится тестами #239.
- Граница дня в фильтре периода (`date_from`/`date_to`, локальная полночь vs UTC) — по канону дат проекта, уточняется в плане по образцу фильтров платежей/записей.
- Маскирование: телефоны и email (§5.1); свободно-текстовые поля (заметки, описания), если появятся, в снимок не включаются вообще — там может быть что угодно; строковые значения в снимке обрезаются до фиксированного потолка длины.
- `entity_label` для безымянных сущностей (платёж) — типовая подпись («Платёж …», дата/сумма); словарь полей подписи — в плане; подпись обрезается до 255 символов на уровне словаря подписей (политика длинных названий).

**Осознанные границы v1** (отвергнуто сознательно, не недоработка):

- Журнал фиксирует только **успешно завершённые** действия; сорванные и запрещённые попытки (в т.ч. 403 мастера к API журнала) следа не оставляют.
- События входа/выхода/смены пароля вне журнала — по практикам безопасного журналирования (OWASP) провалы входа и смена пароля логируются всегда; кандидат в отдельную задачу «журнал безопасности» (backlog), не расширение v1.
- Анонимное создание записи (публичный маршрут до веб-бронирования #8) не журналируется — нет автора; при запуске публичного бронирования пересмотреть.
- Защита целостности журнала — только прикладной уровень (ни API, ни сервис не меняют строки); триггеры/права на уровне БД не строятся.
- IP-адрес источника не сохраняется — внутренний журнал админки.
- Ретенция не строится: маскированные телефоны и имена в подписях хранятся бессрочно — журнал осознанно выведен из-под жизненного цикла удаления данных; триггер пересмотра — порядка 100 тыс. строк или 12 месяцев роста.
