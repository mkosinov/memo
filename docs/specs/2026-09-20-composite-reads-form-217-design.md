# Спека #217: составные чтения — единая форма свободных функций + ADR по слою запросов

- Issue: #217 (маркер «evaluate CQRS read-side layer», активирован: композитных чтений ≥ 2)
- Дата: 2026-09-20, Gate A: вариант A+ (выбор пользователя)
- Ревизия: 2 — панель security: сохранение скоупа мастера в №2/№4, скоуп-гейты в тестах, привязка `_model` при расформации №3. Остальные 5 ревьюеров тогда упали на отказе авторизации их моделей — skipped.
- Ревизия: 3 — позапросный разбор путей исполнения (диалог с пользователем): №3 переводится на `list_custom` (дублировал его механику вручную); №1 остаётся документированным исключением (ручной count дешевле); правило пути исполнения уточнено «страница+итог vs итоги/словари».
- Ревизия: 4 — полный повтор панели (6/6, см. «Итоги панели»): привязка `_model = Staff` признана МЁРТВОЙ (реестр событий не читает её — проверено по коду), требование «сохранить» заменено осознанным удалением; у №3 названы охранный предел плоского списка и статусы архива; у №2 — вынос общих строительных блоков на уровень модуля; тестовая поверхность названа пофайлово; ASCII-схемы в ADR — опциональны, не обязательны.
- Ревизия: 5 — переименования и конвенция имён (решение пользователя, 2026-09-21): №1 `list_clients_with_stats` → `list_clients_view` и схема `ClientWithStats` → `ClientViewResponse` (внутренние имена Python, HTTP-контракт и JSON не меняются); №4 → `list_photos_view`; закреплена конвенция `list_<сущность>_view` для табличных страниц; префикс `list_` сохранён (глагол действия по канону, словарь стека чтения); ручной оптимизированный счётчик клиентов сохраняется.

## Контекст

Маркер #217 сработал: на текущем дереве (HEAD `a615a863`, после мержа #171) в бэкенде **7 композитных чтений** из 113 эндпоинтов (5–6 из ~32 пагинированных списков). Композитное чтение (= коридор 3 канона слоёв) — чтение чужих таблиц для своей сущности в одном эффективном запросе.

Перечень (текущее состояние, `backend/src/services/`):

| # | Композит | Форма сегодня | Эндпоинты |
|---|----------|---------------|-----------|
| 1 | `list_clients_with_stats` (client.py) | свободная функция ✓ | GET /clients |
| 2 | `RecordService.list_view` (record.py) | метод класса | GET /records/view |
| 3 | `MasterViewService` (master.py, отдельный класс) | класс с двумя кэшированными фабриками | GET /masters, GET /masters/all |
| 4 | `PhotoService.list` (photo.py) | метод класса | GET /photos, GET /photos/web |
| 5 | `get_payment_totals` (payment.py) | свободная функция ✓ | GET /payments/totals |
| 6 | `ActivityService.sum_active_seats_bulk` (activity.py) | метод класса | GET /activities (обогащение карточек) |
| 7 | `MaterialService._attach_counts` (material.py) | приватный метод класса | внутренний: после list/create/update/delete материала |

Факты разведки:
- Общая механика чтений уже вынесена в репозиторий: `BaseRepository.list` / `list_custom` / `list_entity` (repositories/generic.py) — репозиторий владеет count и slice, вызывающий строит statement; count выполняется по НЕупорядоченному подзапросу (сортировка применяется после подсчёта — сортировочные подзапросы в count не попадают). Имена из issue (`list_paginated`, `paginate_stmt`) в коде не прижились.
- Путь исполнения у композитов сегодня разный: через репозиторий ездят №2 и №4 (механика списков `list_custom`); напрямую через сессию — №1 (свой count-запрос ради производительности — «осознанное исключение» с #206), №3 (свой hand-written count + свой порядок/лимит/смещение в `_fetch`), №5, №6, №7 (итоги и batch-агрегаты без пагинации — механика списков к ним неприменима). Репозиторий в проекте — владелец CRUD своей сущности и механики списков, а не единая труба к базе.
- Канон слоёв (docs/domain-rules/service-layer.md, rev4 — после мержа #171): правило 8, коридор 3 — «читающие композиты — свободные функции в модуле своего сервиса… будущее читающего слоя — #217». Дерево выбора называет образцами `list_clients_with_stats` и `get_payment_totals`.
- #171 смержен (PR #340): слой сценариев записи `backend/src/usecases/` создан (records.py), композиты не тронуты — спека #171 их явно исключала (в т.ч. решение пользователя №4: «Клиенты со статистикой» не переносятся). Пересечения нет.
- `backend/src/queries/` не существует.
- Привязка `MasterViewService._model = Staff` (master.py:67) реестром событий **не читается**: обход `_build_maps` (events/entities.py:120–138) маппит только инстансы `GenericService`, `MasterViewService` пропускается (аналогично HealthService), а `Master` покрыт явной записью карты сущностей. Привязка — мёртвый код.

## Решение (Gate A — вариант A+, выбрал пользователь)

**Слой `queries/` не заводим.** Все 7 композитов выравниваем до единой канонической формы: **свободная функция в модуле своего сервиса** (коридор 3). Списочные композиты — через механику списков репозитория. Решение фиксируем ADR 007 с триггером пересмотра. Код подтягивается к канону, канон меняется минимально (правило 8 получает ответ вместо делегирования).

**Конвенция имён (решение пользователя, 2026-09-21):** читающая функция табличной страницы — `list_<сущность>_view`: `list_clients_view`, `list_records_view`, `list_masters_view`, `list_photos_view`; будущие таблицы следуют ряду. Словарные композиты остаются с глаголом содержания (`get_payment_totals`, `sum_active_seats_bulk`) — «view» зарезервирован за табличными страницами. Префикс `list_` сохранён: глагол действия по канону и словарь всего стека чтения (методы репозитория и сервисов).

Отвергнутые альтернативы:
- **A-минимум** (ничего не трогать, только ADR): остаётся расслоение форм — 5 композитов-методов выглядят исключением из правила 8. Пользователь выбрал выравнивание.
- **B** (слой `queries/` сейчас): механически = A+ плюс переезд в другую папку и перекройка канона; общей механики слой не добавляет; «чистого CQRS» не даёт — простые CRUD-списки остаются в сервисах, а композит №7 потребляется самим сервисом изнутри. Известный риск CQRS-папок — свалка «всего читающего». Отложено триггером ADR.
- **Выравнивать только 3 самостоятельных чтения** (№2–4): №6–7 — те же композиты коридора 3, их конверсия наименее инвазивна, оставлять их методами = воссоздавать расслоение форм.

## Behavioral Delta

- **Пользователь: до = после.** Ни один экран, контракт API или формат ответа не меняется.
- **Разработчик: до → после.**
  - До: 7 композитов в двух формах — 2 свободные функции (канонические образцы) + 5 методов/классов сервисов (легаси-форма, старше канона).
  - После: все 7 — свободные функции уровня модуля своего сервиса; `MasterViewService` расформирован; правило 8 канона выполняется на 100% и подтверждено ADR 007.

## Техническое содержание

Преобразования (поведение и HTTP-контракты неизменны, имена — по канону «глагол действия», паттерн `list_<сущность>_<особенность>` — как `list_clients_with_stats` и текущий `list_view`):

1. №1 — переименование (решение rev5): `list_clients_with_stats` → `list_clients_view`, схема `ClientWithStats` → `ClientViewResponse` — внутренние имена Python, HTTP-контракт и форма JSON не меняются; ручной оптимизированный счётчик сохраняется; перепривязать импорты/тесты клиентов. Докстринг обновить: «future — #217» → «решение — ADR 007», ссылка на #206 (обоснование дешёвого count) остаётся. №5 `get_payment_totals` — не трогаем (образец словарного композита).
2. №2 `RecordService.list_view` → свободная функция `list_records_view`. Общие строительные блоки (поля поиска `search_fields`, строитель запроса `_build_list_stmt`, колонки сортировки `_sort_columns`) выносятся на уровень модуля как общие помощники и используются ОБЕИМИ потребителями — свободной функцией и простым списком сервиса ( поведение простого списка не меняется). Из обработчика GET /records/view сервисная зависимость убирается (в остальных роутах модуля остаётся — там CRUD). **Обязательно сохранить параметр скоупа мастера** `master_key` в сигнатуре функции и его передачу из роута (`get_scope`): фильтр «только свои записи» (#263) живёт в этой арматуре, гарды доступа остаются в роутах.
3. №3 `MasterViewService` расформировать → `list_masters_view` (GET /masters, пагинированный) и `list_all_masters_view` (GET /masters/all, плоский список). Обе кэшированные фабрики умирают: `get_master_view_service` (master.py:140–142) и `_get_master_view_service` в роуте (masters.py:32–38) вместе с `_ServiceDep`. Пагинированный список переводится на `list_custom` (порядок — параметром, предусловие: statement без запечённого порядка; count эквивалентен — INNER JOIN один-к-одному, дублей нет; эквивалентность закрепить тестом). Статусы архива (#267: active/archived/all) сохраняются параметром. У плоского списка охранный предел `BARE_LIST_MAX_ROWS + 1` с ошибкой `BareListLimitExceededError` остаётся на стороне функции (механика списков пределов не предоставляет). **Привязка `_model = Staff` — мёртвый код** (реестр событий обходит не-GenericService классы, `Master` покрыт явной записью карты): удаляется осознанно; обновить докстринг реестра событий (events/entities.py:30–33, называет класс по имени) и перепривязать test_events_entities.py — гейт: разрешение сущностей мастеров в событиях не ломается.
4. №4 `PhotoService.list` → свободная функция `list_photos_with_client` (ревизия 5: имя — `list_photos_view`); роуты GET /photos и GET /photos/web зовут её напрямую (DI меняется только в этих двух обработчиках); `PhotoService` остаётся для создания/изменения/удаления. **Как и №2 — сохранить `master_key` в сигнатуре и передачу из роута** (фильтр «фото только своих клиентов», #263; скоуп-предикат EXISTS и условный outerjoin переезжают в функцию как есть).
5. №6 `ActivityService.sum_active_seats_bulk` → модульная функция `sum_active_seats_bulk`; единственный вызывающий — обработчик GET /activities, метод из класса удаляется без остаточного шима.
6. №7 `MaterialService._attach_counts` → модульная функция `_attach_counts`; подчёркивание сохраняется как конвенция «внутренняя для модуля» (осознанная читаемость, не требование канона); все 5 внутренних вызовов material.py (после list/create/update/delete ×2) перепривязываются с `self._attach_counts(...)` на `_attach_counts(...)`.
7. `services/__init__.py` реэкспортов не вводит — текущий паттерн прямых импортов `from src.services.X import …` сохраняется.

**ADR 007** (docs/decisions/007-composite-reads-free-functions.md, по TEMPLATE.md, имя по формату NNN-title-with-hyphens): контекст (7 композитов, механика count/slice в репозитории), решение (свободные функции в модулях своих сервисов, коридор 3), критерий композита (чтение чужих таблиц для своей сущности), правило пути исполнения (запросы формы «страница строк + общее число» — механика списков репозитория `list_custom`; итоги, словари-агрегаты и пакетовые обогащения — прямая сессия в функции коридора 3; записи — только через сервис/сценарий; жизненный цикл сессии: открывает инфраструктурная зависимость src/db на время HTTP-запроса, сервисы и функции получают её аргументом, границу транзакции записи держит сервисный декоратор `@transactional` (коммит до отправки ответа, единственная точка публикации событий), репозиторий делает только flush), отвергнутые альтернативы (полный CQRS-раздел; репозиторий-как-единая-труба) — по абзацу на каждую, ASCII-схемы опциональны; триггер выделения `queries/` (расширяемый список): (а) модель чтения расходится с хранилищем — кеширование, денормализация, читающая реплика; (б) один и тот же композит нужен двум и более модулям одновременно; (в) рост N+1, требующий проекций/материализованных представлений; (г) аналитические/отчётные эндпоинты со стабильно иной формой ответа; (д) версионирование API с расходящимися read-моделями.

**Канон** (docs/domain-rules/service-layer.md, правило 8): хвост «будущее читающего слоя — #217» заменить на «решение — ADR 007 (свободные функции; выделение queries/ — по триггеру ADR)». Ревизия канона +1.

## Что сознательно не строим

- Слой `queries/` и любые Query-базовые классы/контракты.
- Автоматический страж формы композитов (контроль формы — ревью; задокументировано в ADR как принятый остаточный риск).
- Выравнивание простых CRUD-чтений (не композиты).
- Перевод №1 `list_clients_view` (клиенты) на `list_custom`: подсчёт общего числа выполняется по подзапросу, проекция которого несёт четыре коррелированных стат-подзапроса — гарантии их невычисления оптимизатором нет; исключение #206 существует ради явного дешёвого count. Только с замером на реальных данных, вне объёма этой спеки.
- Перевод №5/№6/№7 под механику списков: результат этих функций — итоги и словари-агрегаты, у них нет страницы и «общего числа»; limit/offset обрезали бы группы, count считал бы число групп — механика не подходит по смыслу.
- Изменения HTTP-контрактов, схем ответов, фронтенда.
