# #341 — Фиксированные created_at в сид-фото: календарь-независимые visual-базлайны

- **Issue:** #341 (test(e2e): visual-базлайны с сид-датами падают при UTC-rollover, photos-table кейс #138)
- **Статус:** спека (rev1), ожидает ОК пользователя (Gate B)
- **Дата:** 2026-09-20
- **Вердикт разведки:** actual — все утверждения issue подтверждены по живому дереву (см. «Корень»)

---

## Контекст

Visual-базлайны (Playwright `toHaveScreenshot`) фиксируют отрисованный контент таблиц. В таблице
фото есть колонка «Дата», которая рендерит `created_at` сид-записей. Сид выполняется при старте
каждого e2e-шарда и записывает в `created_at` реальный момент запуска — поэтому отрисованная дата
равна «сегодня» на момент старта прогона. Прогон, чей сид выполнился после UTC-полуночи, сеет
«новый день»: базлайны, снятые накануне, перестают совпадать — тест падает детерминированно,
включая retry (шард-БД на retry не пересоздаётся, дата в данных та же).

Реальный кейс: CI PR #335, run 35477565278 — `photos-table-filled` + `photos-table-dropdown-open`
красные в окне 23:59–00:16 UTC; базлайны были обновлены под новый день коммитом `550fe238`
(«seed created_at date-column drift (UTC-day rollover)»). Утром того же дня та же пара была
зелёной при неизменном коде — базлайны всегда отстают от календаря ровно на полночь.

## Корень (подтверждено по коду)

1. `_seed_photos` создаёт 7 фото **без** `created_at` — `backend/src/seed/seed.py:552–582`.
2. Базовая модель проставляет реальный момент: `AbstractModel.created_at = Column(DateTime,
   default=datetime.utcnow)` — `backend/src/models/abstract.py:24–26`.
3. Сид выполняется на старте каждого шарда: `scripts/e2e-shard-start.sh:147`
   (`uv run python -m seed.seed` после пересоздания шард-БД, `:88–90`).
4. Колонка «Дата» рендерит `formatDate(p.created_at)` —
   `frontend/admin/app/(main)/photos/components/photoColumns.tsx:117–122`;
   формат «день месяц» в **локальной** таймзоне браузера — `frontend/admin/lib/utils.ts:140–142`.
5. Дефолтная сортировка таблицы — `sort_by="created_at", sort_order="desc"` —
   `backend/src/schemas/photo.py:102–103`.

Радиус (проверено, других плывущих дат в visual-базлайнах нет):

- записи r1–r6 сидируются в **фиксированную** неделю `WEEK_FIXED_START = 2026-06-15`
  (`backend/src/seed/seed.py:69–77, 176–181`, занятия `ev_fixed_*`);
- `last_record` клиентов (колонка «Последняя запись», видимая по умолчанию) вычисляется от
  фиксированных записей — не плывёт;
- `week-view.spec.ts` и `wave6-status-snapshots.spec.ts` держат мок часов браузера
  (`page.clock.install({ time: new Date('2026-06-15T10:00:00') })`,
  `frontend/admin/e2e/visual-regression.spec.ts:48, 99, 583`) и фиксированные даты данных;
  **но** мок часов не влияет на даты, приходящие из БД, — он не спасает photos;
- смежный класс glyph/env drift закрыт: #307 MERGED, #182 CLOSED — дубля нет.

## Выбор концепта (Gate A)

**Принят — концепт 1: фиксированные `created_at` в сид-фото** (приведение к канону: сид уже
несёт `WEEK_FIXED_START` для записей и занятий — фото просто присоединяем к тому же приёму).

Отвергнутые альтернативы:

- **Маскировать колонку дат в скриншотах** (`mask:` в `toHaveScreenshot`) — решает падение, но
  навсегда выводит колонку «Дата» из визуальной проверки (изменения форматирования даты перестанут
  ловиться); прецедентов `mask:` в проекте нет. Потеря покрытия без компенсирующего выигрыша.
- **Мок часов на сервере** (заморозка времени бэкенда в e2e-окружении) — сид-дизайн намеренно
  держит «текущую» неделю относительной (`WEEK3_START = _THIS_WEEK_MONDAY`,
  `backend/src/seed/seed.py:64–71, 151`; комментарий `scripts/e2e-shard-start.sh:89–90`:
  «seed then populates with current-week dates»), чтобы функциональные e2e находили занятия
  «на этой неделе». Глобальная заморозка времени сломала бы относительные сценарии
  (текущая неделя, «копировать прошлую неделю» и т.п.).

Различия между подходами не затрагивают видимое поведение приложения, схему данных и контракты
API — развилки для пользователя нет, концепт один.

## Решение

### 1. Фиксированные нарастающие даты в `_seed_photos`

Каждому из 7 сид-фото назначается явный фиксированный `created_at` — нарастающие дни фиксированной
визуальной недели, время 12:00:00 UTC:

| фото | created_at (UTC)      |
|------|-----------------------|
| ph1  | 2026-06-15T12:00:00   |
| ph2  | 2026-06-16T12:00:00   |
| ph3  | 2026-06-17T12:00:00   |
| ph4  | 2026-06-18T12:00:00   |
| ph5  | 2026-06-19T12:00:00   |
| ph6  | 2026-06-20T12:00:00   |
| ph7  | 2026-06-21T12:00:00   |

Почему именно так:

- **Разные дни, нарастающие от ph1 к ph7.** Дефолтная сортировка — `created_at DESC`: при
  одинаковых датах порядок строк стал бы недетерминированным (равные ключи сортировки), при
  нарастающих — ph7 первой строкой, как и сейчас (сегодня порядок диктуют микросекунды вставки,
  которые нарастают от ph1 к ph7).
- **12:00:00, naive-литералы.** Колонка — naive `DateTime` (`backend/src/models/abstract.py`),
  Pydantic сериализует naive-значение как ISO **без** смещения (`2026-06-15T12:00:00`), и фронтовый
  `new Date(...)` парсит такую строку как локальное время — календарный день отрисовки не зависит
  от таймзоны браузера вообще. Полдень выбран как запас прочности: если сериализация когда-нибудь
  станет aware (суффикс `Z`), полдень UTC сохранит календарный день при смещениях до ±11 часов.
  В сид-литералах используется наивный `datetime(2026, 6, 15, 12, 0, 0)` — aware-объект на
  naive-колонке уронил бы вставку.
- **Неделя 2026-06-15…21.** Та же «визуальная неделя», что уже зафиксирована в сиде для записей и
  занятий и в моке часов браузера (`2026-06-15T10:00:00`) — все даты базлайна живут в одном окне.

Константа объявляется рядом с `WEEK_FIXED_START` в `backend/src/seed/seed.py` (например,
`PHOTO_FIXED_DATES`), значения передаются в словарях `_seed_photos`.

### 2. Юнит-тест сида (страж контракта)

Новый тест в `backend/tests/test_seed.py` — по паттерну существующего стража фиксированной недели
`test_seed_fixed_week_dates_in_range` (`backend/tests/test_seed.py:392`): после прогона сида все
7 фото имеют ровно ожидаемые фиксированные `created_at`. Ожидаемые семь дат/времён **жёстко
прописываются в тесте** (как в страже недели — год/месяц/день литералами), а НЕ импортируются из
`PHOTO_FIXED_DATES` сида — иначе правка константы молча пройдёт тест, и страж не выполнит своё
назначение (сценарий С5): при изменении дат сида тест падает и требует осознанной регенерации
базлайнов.

### 3. Регенерация затронутых базлайнов (один раз)

Фиксирование дат меняет отрисованные значения колонки «Дата» → базлайны photos обновляются один
раз (по канону `550fe238`), после чего календарь на них не влияет:

- `photos-table-filled`, `photos-table-dropdown-open`, `photos-table-sort-active` — строки с
  датами в кадре;
- `photos-table-picker-open` — пикер поверх таблицы со строками (проверить при регенерации:
  если строки в кадре — обновится, иначе нет);
- `photos-table-empty / -skeleton / -error` — без строк, не затрагиваются.

Механика — штатная: `pnpm test:e2e:update` (`frontend/admin/package.json:14`,
`playwright test --update-snapshots`) на shard-rest окружении.

### Что НЕ меняется

- Прод-поведение, API, схема БД — не затрагиваются (сид и e2e-артефакты).
- Функциональные фото-тесты: созданное через UI фото получает реальный «сейчас» `created_at` и
  по-прежнему встаёт первой строкой (DESC; реальное «сегодня» новее июня 2026-го) —
  `photos-crud.spec.ts`, `master-role-photos.spec.ts` без правок.
- «Текущая» неделя занятий (`WEEK3_START`) остаётся относительной — функциональные e2e не
  затронуты.
- Дев-база: `scripts/recreate_dev_db.sh` + сид — таблица фото в дев-окружении начинает показывать
  фиксированную неделю июня вместо «сегодня» (осознанная плата, та же, что уже принята для
  записей r1–r6).
- Прод-сортировка `ORDER BY created_at DESC` не получает tie-breaker (остаточный риск равных
  `created_at` у двух фото — на практике исключён микросекундной точностью; вне скоупа этого
  дизайна).
- Таймзона браузера в playwright-конфиге не пинится (`timezoneId`): текущая naive-ISO сериализация
  нейтральна к таймзоне, а пин менял бы окружение всех e2e с риском чужих базлайнов
  (week-view и др.).

## Behavioral Delta

- **До:** базлайны photos содержат дату старта сида («сегодня» на момент снятия); любой прогон,
  чей сид выполнился после UTC-полуночи последней регенерации, детерминированно красный
  (`photos-table-filled`, `photos-table-dropdown-open`); базлайны приходится обновлять каждую
  полночь (фактически — при каждом задокументированном падении, как `550fe238`).
- **После:** базлайны photos содержат фиксированные даты 15–21 июня 2026; прогоны зелёные в любой
  момент суток; обслуживание базлайнов photos прекращается. Для конечного пользователя админки
  ничего не меняется; в дев-окружении колонка «Дата» сид-фото показывает фиксированную неделю
  июня вместо текущей даты (как уже принято для записей r1–r6).
