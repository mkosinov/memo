# #328 — ServiceModal: поле тегов услуги (починка молчивого стирания связей)

Дата: 2026-09-20. Статус: Gate B (ожидает ОК пользователя).
Концепт выбран пользователем (Gate A, 2026-09-20): **вариант 2 — достроить выбор тегов в форму услуги** по образцу формы фото.

## 1. Контекст и проблема

Услуга поддерживает теги (`service_tags`, M2M) — таблица услуг показывает их колонкой, но **ни одна форма ими не управляет**: модальное окно услуги не содержит поля тегов. Из-за этого каждое сохранение редактирования молча стирает связи услуги с тегами:

```
ServiceModal — форма без поля тегов
        ↓  возвращает данные формы (tag_ids в форме отсутствует)
ServicesTable — собирает canonical PUT-payload, tag_ids подставляется как []
        ↓
PUT /api/v1/services/{id} — контракт «полного обновления»
        ↓
бэкенд стирает все связи с тегами и вставляет заново из payload → связи потеряны
```

Баг не регрессия — так было с момента введения тегов; вскрыт в #203 (e2e приходилось снапшотить теги через sqlite и восстанавливать после каждого теста).

## 2. Факты разведки (проверено по живому дереву, 2026-09-20)

1. Форма услуги не собирает теги: payload строится инлайн в `handleSubmit` модалки (`ServiceModal.tsx:491–495`: спред формы + `max_age` + `materials`); состав полей задаёт локальный `SERVICE_FIELDS` (`serviceFields.tsx:63–165`: title, description, specialty, duration, min_age, max_age, materials, record_info, image_url, tariffs — тегов нет). Правка #203 затронула только `max_age`.
2. `ServicesTable.tsx:80`: `tag_ids: (data.tag_ids as string[] | undefined) ?? []` — поскольку форма `tag_ids` не отдаёт, всегда уходит `[]`. Payload строится по канону #178 «полное обновление, каждое поле явно».
3. Бэкенд `ServiceService.update` (`backend/src/services/service.py:269–308`): DELETE всех связей (`:292–294`) → INSERT из payload (`:295–301`). Схема `ServiceUpdate.tag_ids: list[str] = []` (`backend/src/schemas/service.py:97`) — пропущенный список трактуется как «стереть всё». Это **корректная** семантика полного обновления (канон `docs/domain-rules/services.md:41` и таблица PATCH `:59`) — меняется только тем, что фронт теперь присылает честные данные.
4. Управление тегами услуги негде вести: страница `/tags` редактирует только имена тегов; `serviceColumns.tsx:116–122` показывает теги услуги read-only. Выбор тегов существует у фото (`PhotoModal.tsx:74–120`) и локаций.
5. Обход в e2e: `services-null-max-age.spec.ts` — `captureService()` (`:54–66`) читает теги сида напрямую из sqlite, `restoreService()` (`:89–102`) восстанавливает их PUT'ом в `finally` (`:172–174`, `:239–243`); комментарий `:89–91` называет причину дословно.
6. **Комментарий e2e «`tags` приходит пустым» (`:61–64`) ошибочен — разрешено разведкой 2026-09-20.** Код противоречит ему: `get()`/`list()`/`list_all()` явно жадно грузят `Service.tags` (`backend/src/services/service.py:170–172`, `:93–95`, `:143–145`; докстринг: без этого — краш `MissingGreenlet`, а не пустой массив), и жадная загрузка появилась раньше комментария (f4192ba, 2026-08-18, против e2e-правки 8e94989, 2026-09-19). Контракт закреплён тестом: `backend/tests/test_api_services.py:149–165` — GET услуги с тегом отдаёт `len(body["tags"]) == 1`, тесты зелёные в CI на main. Похоже, в ту сессию sqlite-чтение и бэкенд смотрели в разные базы (классический разъезд путей), и наблюдение списали на API. Следствие: предзаполнение из `service.tags` корректно; битый комментарий удаляется в S5.
7. Контракты готовы, менять не нужно: read-схема услуги несёт `tags: [{id, title}]` (`packages/api-client/src/schemas.ts:281`); `ServiceUpdateSchema.tag_ids: z.array(z.string()).default([])` (`:586`); `getTags({ q, per_page })` экспортирован из api-client и используется пикером фото.
8. Готовый образец ровно нужного поля: `photoFields.tsx:81–84` — поле `type: 'tags', key: 'tag_ids', label: 'Теги'`; рендер в `PhotoModal.tsx:74–120` — чипы выбранных тегов с крестиками + `RemoteSearchSelect` (общий контрол `@/app/components/shared/RemoteSearchSelect`) с поиском `getTags({ q, per_page: 10 })`, `minChars: 2`; предзаполнение из `photo.tags` (`:233–234`); маппинг `{id,title}[] → string[]` делает таблица перед вызовом API (`PhotosTable.tsx:52–54`, `:69–78`).
9. Тесты мутаций `useServicesMutations.test.ts` (строки с `tag_ids: []`) — pass-through хука (payload входит и уходит без изменений), от формы не зависят, остаются валидными.

## 3. Концепт

**Выбрано (пользователь, Gate A):** добавить в `ServiceModal` полноценное поле выбора тегов по образцу формы фото. Баг исчезает как побочный эффект: форма знает актуальные теги и честно их передаёт. Отвергнутые альтернативы:

- *Точечный фикс без UI* (ServicesTable подставляет теги из загруженного объекта) — отклонён: оставляет функцию «теги услуги» видимой, но неуправляемой, и добавляет компенсирующий код, который обязан помнить каждый будущий сохраняющий.
- *Научить PUT «не прислано — не трогать»* — отклонён: размывает канон полного обновления (`docs/domain-rules/services.md`, контракт GenericService); частичность — прерогатива PATCH.
- *Перевод услуг на PATCH* — отклонён: раскол единого потока редактирования ради одного поля.

Сноска (панель best-practices): «полная замена» в PUT соответствует RFC 9110; известная цена — last-write-wins при двух одновременных редакторах одной услуги (перезапись набора тегов целиком). Риск уже существует для всех полей PUT в однопользовательской админке и этим изменением не усугубляется; стандартное лекарство на будущее (ETag/If-Match) — вне скоупа.

## 4. Behavioral Delta (до → после)

| Ситуация | До | После |
|---|---|---|
| Сохранение редактирования услуги с тегами | Связи с тегами молча стираются | Связи сохраняются (форма передаёт актуальный набор) |
| Привязать/снять тег услуги | Невозможно нигде в интерфейсе | Поле «Теги» в форме услуги: чипы + поиск по названию (от 2 символов) |
| Создание услуги сразу с тегами | Невозможно | Возможно в той же форме |
| Снятие всех тегов | Происходит случайно, незаметно | Осознанное действие: чипы сняты пользователем вручную |
| e2e `services-null-max-age` | Возится со снапшотом/восстановлением тегов через sqlite | Обход удалён, восстановление только изменяемых полей |

Бэкенд, контракт API и api-client **не меняются** — по-прежнему «полное обновление»: бэкенд заменяет набор тегов на присланный; меняется лишь то, что фронт присылает честные данные.

## 5. User Scenarios (каждый мапится на E2E)

- **S1. Редактирование не трогает теги (исходный баг).** Услуга с тегом создана через API; админ открывает редактирование, меняет только длительность, сохраняет. Ожидание: в таблице услуг чип тега на месте, связь в API жива. → e2e `services-tags.spec.ts` (новый).
- **S2. Изменение набора тегов.** Услуга с тегом A; админ в форме снимает A, добавляет B, сохраняет. Ожидание: в таблице B, A исчез. → e2e `services-tags.spec.ts`.
- **S3. Создание с тегом.** Админ создаёт услугу, в форме добавляет тег, сохраняет. Ожидание: связь создана, чип виден. → e2e `services-tags.spec.ts`.
- **S4. Снятие всех тегов.** Услуга с двумя тегами; админ снимает оба чипа, сохраняет. Ожидание: чипов нет, связей нет — без ошибок. → e2e `services-tags.spec.ts`.
- **S5. Чистка обхода.** После фикса из `services-null-max-age.spec.ts` удалены sqlite-чтение тегов и битый комментарий «`tags` приходит пустым»; снапшот берётся через GET (теги из ответа), восстановление отправляет полный payload c `tag_ids` из снапшота — оба теста остаются зелёными, тег сида жив после прогона. → правка существующего e2e.

Архивированные услуги правятся той же модалкой (PUT никогда не трогает признак архива) — поле тегов ведёт себя идентично, отдельный сценарий не нужен; S1–S4 гоняются на активных услугах.

Сопутствующие компонентные тесты (vitest, к S1–S3): `ServiceModal.test.tsx` — предзаполнение из `service.tags`; `tag_ids: string[]` в payload `handleSubmit`; повторное добавление существующего тега не создаёт дубль чипа; снятие/добавление чипа помечает форму «грязной» (закрытие спрашивает подтверждение); поле тегов реально рендерится (не пустое место при рассинхроне конфигурации и рендер-ветки). `ServicesTable.test.tsx` — payload редактирования несёт `tag_ids` из формы (не `[]` при непустых тегах).

## 6. Техническое решение (фронт-only)

Конвенция `serviceFields.tsx` — «Local field types, no shared modal imports»: конфигурация поля объявляется локально, общими могут быть только контролы. Фото-прецедент этому следует.

1. **`serviceFields.tsx`**: новый локальный тип `tags` (конфиг `{ type: 'tags'; key: 'tag_ids'; label: 'Теги'; placeholder }`) и запись в `SERVICE_FIELDS` — после поля материалов (группировка «связи с другими сущностями»).
2. **`ServiceModal.tsx`**:
   - Предзаполнение: в инициализации формы спец-случай для `type: 'tags'` — `initial['tag_ids'] = service?.tags ?? []` (read-схема несёт `tags`, не `tag_ids`; создание — пустой массив). Зеркало `PhotoModal.tsx:233–234`.
   - Рендер: ветка `tags` в локальном `FieldRenderer` — чипы выбранных тегов с крестиком удаления + `RemoteSearchSelect` (`onSelectItem` добавляет `{id, title}` без дублей, `onSearch: getTags({ q, per_page: 10 })`, `minChars: 2`; фиктивные управляемые пропсы `value={null}`, `onChange={() => {}}` — как в образце). Зеркало `PhotoModal.tsx:74–120` с одной локальной поправкой доступности (панель best-practices): видимый лейбл связывается с полем поиска через `htmlFor`/`id` (`useId`), а кнопкам-крестикам чипов задаётся `aria-label={'Удалить тег ' + title}` — у образца лейбл не связан, новое поле делаем сразу правильно, общий код фото не трогаем.
   - Отправка: в `handleSubmit`, рядом с существующим маппингом материалов, `tag_ids` из `{id,title}[]` → `string[]`. Маппинг в модалке (а не в таблице, как у фото), потому что у услуг payload строит `ServicesTable` по канону #178 «каждое поле явно», и модалка уже является точкой трансформации (материалы). Изменение набора чипов идёт через общий `handleChange` — флаг «грязной» формы и подтверждение закрытия работают без отдельной проводки.
3. **`ServicesTable.tsx`**: без правок. Строка `tag_ids: (data.tag_ids as string[] | undefined) ?? []` начинает получать честный массив из формы; `?? []` остаётся безопасным дефолтом. Create-поток (`createService.mutateAsync(data)`) получает корректный payload из модалки без изменений.
4. **e2e `services-null-max-age.spec.ts`**: убрать sqlite-чтение тегов — `captureService` берёт снапшот только через GET (`tag_ids` маппится из `row.tags`), `restoreService` по-прежнему отправляет **полный** payload (частичный PUT при семантике полного обновления сам бы стёр теги дефолтом `[]`); удалить битый комментарий «`tags` приходит пустым» (разрешён в §2.6). Сужаются только утверждения тестов, не тело восстановления.
5. **Бэкенд, api-client, domain-rules**: без изменений.
6. **Инвалидация кэша**: существующая `invalidateEntities(['services'])` с префиксным сопоставлением TanStack Query покрывает и колонку тегов таблицы — новая проводка не нужна, карту инвалидации не расширять (PUT услуги меняет связи, а не сущности тегов).

## 7. Границы скоупа (сознательно не строим)

- Контракт PUT и бэкенд — не трогаем (канон полного обновления остаётся).
- Переход услуг на PATCH — нет.
- Массовое навешивание тегов из таблицы услуг (bulk) — нет (YAGNI).
- Колонку/фильтры тегов в таблице услуг — не трогаем (уже есть).
- Переиспользование/вынос общего «тегового поля» в shared-слой — нет: у сервиса локальная конвенция полей, дублирование ~40 строк рендера осознанное (цена унификации модалок — отдельная тема, не этого бага).

## 8. Риски и заметки

- `RemoteSearchSelect` и `getTags` — общие контролы/клиент, общение с ними у модалок уже установлено (фото) — новогоshared-кода не появляется.
- Валидации на теги не нужны: поле опциональное, дубли блокирует пикер, ограничений на количество в схеме нет. Нота (панель security, 2026-09-20): несуществующий id тега в `tag_ids` бэкенд встречает ошибкой целостности внешнего ключа (ответ 500 вместо аккуратного 422) — поведение существующее, всех писавших в услугу, не вводится этой спекой и остаётся вне скоупа (кандидат в будущий проход по бэкенду).
- #203-логика (`max_age`, перекрёстная валидация) не затрагивается — правки в тех же функциях, но других ветках.
- Сценарий «сервер отклонил PUT» не меняется: тост ошибки, модалка открыта, состояние формы с тегами сохранно (существующее поведение `handleSubmit`).
