# Спека #319 — Гарантированные настройки пользователя (`UserSettings`)

- **Issue:** #319 (depends-on: #171 — слой сценариев `usecases` ещё не в main; задачи плана стартуют после его мержа)
- **Ревизия:** rev2, 2026-09-20 — Gate B (ожидает ОК пользователя). rev2 — правки по панели ревью (5/6 агентов, согласованность пропущена из-за провайдера): механизм upsert вместо перехвата исключений, `user_id` на POST из сессии, удаление мёртвых клиентских методов, протокол отказа самолечения
- **Родственный выпуск:** #348 — админ-управление учётками и паролями (вынесено из этого дизайна решением пользователя 2026-09-20)

## 1. Контекст и проблема

Сегодня сервер допускает состояние «пользователь есть, строки `UserSettings` нет». Единственный создатель строки — фронт админки: `UserSettingsContext` при ошибке чтения настроек сам вызывает `POST` с дефолтами. Отсюда три провала (подтверждены разведкой по живому коду, вердикт «актуально»):

1. Любой клиент кроме админки (скрипты, будущий web-клиент #48, прямые вызовы API): чтобы менять настройки, нужно «догадаться» сначала создать строку `POST`-ом — иначе `PATCH` даёт 404 `SETTINGS_NOT_FOUND`.
2. Гонка двух вкладок: обе видят отсутствие строки → обе шлют `POST` → вторая ловит 422 `INTEGRITY_VIOLATION` (глобальный обработчик нарушения уникальности).
3. `DELETE /api/v1/user-settings/{id}` удаляет строку навсегда; после удаления `PATCH` ломается (404), пока фронт снова не «догонит» созданием.

Уточнения разведки к формулировкам issue: фронт шлёт `POST` при **любой** ошибке чтения с пустым локальным кэше (не только при 404); проигравший гонку получает именно 422 `INTEGRITY_VIOLATION`, а не 409.

Инвентаризация баз (2026-09-20): прода не существует (майлстоун «Админка v1 → прод» пуст, деплой-конфигураций в репозитории нет); непересеваемых баз нет — все живые базы скретч-базы. При этом оба дефекта уже проявились вживую: в рабочей копии контейнера разработки лежит пользователь без строки настроек, в основной копии — строка настроек-сироты от удалённого пользователя. Вывод: миграция-бэкфилл не нужна, все случаи закрываются механизмами этой спеки. Существующая настройка-сирота в скретч-базе целенаправленно не чистится кодом — она уйдёт при очередном пересеве базы.

## 2. Решения Gate A (диалог 19–20.09.2026)

1. **Гарантия при создании — слой сценариев.** Создание `User` вместе с `UserSettings` — составное действие, коридор 2 канона слоёв (`usecases`). Реализация зависит от #171.
2. **Чтение = get-or-create.** `GET /user-settings` без строки не отдаёт 404, а **пишет в базу** строку с дефолтами и возвращает её. Это самолечение любых баз (существующие пользователи, любые аномалии).
3. **Полный CRUD сохраняется** («как у всех сущностей», решение пользователя): `POST` остаётся (дубль → обычная ошибка уникальности 422), `DELETE` остаётся — его смысл теперь «сброс настроек к дефолтам»: строка сносится, следующее чтение пересоздаёт дефолты.
4. **Каскад: строка настроек не переживает пользователя.** Удаление карточки сотрудника уже сегодня автоматически сносит связанную учётку (контракт удалений, зависимость «Пользователь», авто-каскад) — в этот же каскад добавляется снос строки настроек.
5. **Админ-управление учётками и паролями вынесено в #348** (правка телефона/роли, сброс пароля по ссылке на телефон, пароль при создании задаёт сам пользователь). В этом дизайне его нет.
6. **Пути вне приложения не проектируем:** sqladmin — аварийный инструмент оператора, не путь пользователя; CLI первого админа — бутстрап-инструмент, но переводится на тот же сценарий, чтобы инвариант держался везде; сид создаёт строки настроек обоим своим пользователям.

## 3. Концепция: инвариант «на покое»

Состояние «пользователь есть, строки нет» перестаёт быть багом системы и становится самолечимым промежуточным состоянием:

```
СОЗДАНИЕ (все пути)
  карточка сотрудника «Учётка»  ──┐
  CLI первого админа             ──┼─→ одна транзакция:
  тестовые фабрики               ──┘    строка User + строка UserSettings (дефолты)
  сид базы                       ──→ обе строки создаёт сид

ЧТЕНИЕ
  GET /user-settings: строки нет → INSERT дефолтов → 200 (строка в БД, не в памяти)
  гонка двух читателей: второй INSERT ловит нарушение уникальности → перечитать → 200

ИЗМЕНЕНИЕ
  POST   — ручное создание (дубль → 422, как у всех)
  PUT/PATCH — без строки → 404 SETTINGS_NOT_FOUND (контракт #179 не тронут)

СБРОС
  DELETE — строка сносится (204); следующее чтение пересоздаёт дефолты

СМЕРТЬ ПОЛЬЗОВАТЕЛЯ
  удаление карточки сотрудника → авто-каскад сносит учётку
  ↓ добавляем
  вместе с учёткой сносится её строка настроек (сирот не осталось)
```

## 4. Контракт API

Новых эндпоинтов в #319 нет (роутер пользователей — #348). Изменения существующих:

| Эндпоинт | До | После |
|---|---|---|
| `GET /api/v1/user-settings` | нет строки → 404 `SETTINGS_NOT_FOUND` | нет строки → INSERT дефолтов → 200 со строкой; ответ помечен `Cache-Control: no-store` |
| `POST /api/v1/user-settings` | 201; `user_id` принимается из тела запроса (включая чужой); дубль → 422 `INTEGRITY_VIOLATION` | 201; **`user_id` берётся из сессии**, клиентское поле игнорируется (закрытие дыры записи чужой строки — находка панели безопасности); дубль → 422 `INTEGRITY_VIOLATION` |
| `PUT/PATCH /api/v1/user-settings` | без строки → 404 `SETTINGS_NOT_FOUND` | без изменений (контракт #179 цел) |
| `DELETE /api/v1/user-settings/{id}` | 204, строка исчезает навсегда | 204; смысл = «сброс к дефолтам»: следующее чтение пересоздаёт |
| `DELETE /api/v1/staff/{id}` (карточка) | каскад сносит учётку, настройка-сирота остаётся | каскад сносит учётку **и** строку настроек |

Нюансы контракта (сознательные решения):

- `PATCH` сразу после `DELETE` без промежуточного чтения даёт 404 — строгий контракт правки существующего сохраняется, «сброс» — это `DELETE` → `GET`.
- `GET`, который пишет строку, — отклонение от семантики «безопасного метода» (RFC 9110). Отклонение сознательное: это отложенная инициализация, идемпотентная при повторах; отдача промежуточным кэшам исключена заголовком `Cache-Control: no-store`.
- `DELETE` различает «строки нет» (404) и «строка чужая» (403) — раскрытие факта существования чужого идентификатора; риск пренебережим при UUID-ключах, поведение сохраняется осознанно.

## 5. Механизмы

### 5.1. Сценарий `create_user`

Слой сценариев (`usecases/user.py`, коридор 2 канона слоёв; появляется после #171): одна транзакция — вставка `User` и вставка `UserSettings` с дефолтами. Составляется из методов сервисов **без собственной транзакции** (канон: сценарий не зовёт декорированные методы). В сервисе настроек под это появляется метод-ядро «создать дефолты» без декоратора (сегодня метод создания только декорированный) — его вызывают сценарий `create_user`, флоу «учётки» (переходный период) и get-or-create на чтении. Именно это ядро — переиспользуемый кусок для будущих сценариев (кадровые — долг #326).

События: создание строки настроек внутри транзакции родителя не публикует отдельное событие шины инвалидации — сознательное упрощение (строка персональная, чужих кэшей у неё нет).

Вызователи: CLI `create-user` (первый админ) и любые будущие создатели пользователей.

### 5.2. «Учётка» в карточке сотрудника — переходный период

Флоу карточки сотрудника — задокументированный долг (перевод кадровых операций в сценарии — #326). До перевода: внутри существующей транзакции флоу, сразу после вставки `User`, вызывается тот же метод сервиса настроек без транзакции. Инвариант закрыт с первого дня; структурный перенос целиком — #326, поведение не меняется.

### 5.3. Get-or-create на чтении

Новый метод сервиса настроек `get_or_create_by_user_id` (декорированный, коридор 1: одна сущность, свой эндпоинт). Существующий `get_by_user_id` остаётся чистым чтением — им пользуются `PATCH`/`PUT` (контракт 404) и контракт-тест #179; его семантика не меняется, поэтому заявление «тест #179 без изменений» остаётся прочным.

Механизм (по находке панели — без перехвата исключений): атомарная команда SQLite `INSERT ... ON CONFLICT(user_id) DO NOTHING` (диалект `sqlalchemy.dialects.sqlite.insert`) с дефолтами, затем обычный `SELECT`. Писатели SQLite сериализуются, поэтому после «пропущенного» INSERT строка гарантированно видна — своя или закоммиченная конкурентом. Перехват `IntegrityError` не нужен вовсе; после неудачного INSERT внутри транзакции сессия требует отката, чего атомарный upsert избегает по построению.

Протокол отказа (честный, не «никогда»): ожидание писателя покрывается штатным `busy_timeout`; если INSERT упал по иной причине (блокировка дольше таймаута, недоступность базы) — ошибка уходит наружу как 500, без молчаливых дефолтов в памяти и без бесконечных повторов. Нарушение уникальности при гонке клиенту не отдаётся никогда — этот случай закрыт upsert-ом.

Запись именно в базу. Ответ `GET` помечается `Cache-Control: no-store`.

Существующий HTTP-тест «GET без строки → 404» переписывается на «GET без строки → 200 + дефолты + строка создана».

### 5.4. Каскад смерти пользователя

Сегодня: удаление карточки сотрудника сносит учётку сервисным обработчиком зависимостей (матрица удалений, `Staff → users`, авто-каскад). Добавить: тот же обработчик сносит строки настроек этих пользователей — bulk-командой репозитория настроек по собственной колонке `user_id` (канон bulk-правила). FK-уровень (`ON DELETE`) не используется — в проекте обработчики каскадов сервисные, детерминированные независимо от состояния PRAGMA. Увольнение-архив настройки **не трогает** (архив — не смерть).

### 5.5. Сид и тестовые фабрики

Сид создаёт строки настроек обоим пользователям (админ, мастер) с дефолтами. Тестовая фабрика `User` создаёт строку настроек по умолчанию (тесты, которым нужна аномалия «без строки», удаляют её явно).

### 5.6. Фронт

`UserSettingsContext`: убрать фолбэк «ошибка чтения → `POST` создания» — чтение самолечивает. Кэш в localStorage остаётся ускорителем первого рендера; правило: кэш всегда подчиняется ответу сервера — любой ответ `GET` перезаписывает кэш (в том числе после сброса `DELETE` → `GET` дефолтов).

Методы клиента API `createUserSettings` и `deleteUserSettings` удаляются: после снятия POST-фолбэка у первого не остаётся потребителей, у второго их никогда не было. Серверные эндпоинты остаются полным CRUD — удаляется только мёртвый клиентский код.

## 6. Канон (правки вносятся вместе со спекой после ОК)

- `docs/domain-rules/user_settings.md` — правки по пунктам:
  - инвариант «на покое» — у каждого пользователя есть строка настроек; отсутствующая строка создаётся при первом чтении (get-or-create); создаётся вместе с `User` (сценарий создания, сид); `DELETE` = сброс к дефолтам (строка пересоздаётся чтением); строка умирает вместе с пользователем (каскад удаления карточки сотрудника);
  - инвариант уникальности: заменить устаревшую формулировку «uniqueness enforced at service level» на фактическую — уникальность `user_id` держится ограничением уровня базы (UNIQUE в модели/миграциях);
  - Business Logic: `POST` больше не принимает `user_id` из тела — идентификатор берётся из сессии (own-only, как остальные операции);
  - Relationships: заменить «logical, not enforced FK» на фактическое — FK и UNIQUE на уровне базы;
  - таблица API Endpoints: GET — чтение с get-or-create и `no-store`; POST — `user_id` из сессии; DELETE — сброс к дефолтам.
- `docs/domain-rules/deletion.md`, матрица: `UserSettings` — «пользовательское удаление = сброс к дефолтам (пересоздаётся чтением); смерть пользователя — каскад вместе с учёткой».
- `docs/domain-rules/auth.md`, раздел «User lifecycle»: дополнить — создание `User` создаёт `UserSettings`.

## 7. User Scenarios (мапа на тесты)

- **С1. Создание с гарантией.** Админ создаёт карточку сотрудника с «учёткой» → строка настроек уже в базе **до** первого входа; новый пользователь входит и меняет тему — сохраняется без какого-либо предварительного создания. → E2E: создать карточку с учёткой → проверить строку → вход → смена темы → перезагрузка → тема сохранилась.
- **С2. Самолечение.** В базе пользователь без строки (создан до фикса / строка удалена) → первое чтение возвращает дефолты, строка появляется в базе. → pytest: удалить строку → GET → 200 + дефолты + строка в БД.
- **С3. Сброс к дефолтам.** Пользователь менял тему → `DELETE` своей строки → следующее чтение возвращает дефолты (тема light), строка пересоздана. → E2E: смена темы → DELETE → GET → дефолты.
- **С4. Гонка вкладок.** Пользователь без строки, два одновременных чтения → оба получают 200 с одной и той же строкой, ни одной ошибки уникальности наружу. → pytest (две реальные сессии с собственными соединениями к файловой SQLite — не общий in-memory).
- **С5. Каскад смерти.** Карточка сотрудника с учёткой удаляется → в базе нет ни учётки, ни строки настроек (сирот не осталось). → E2E: создать с учёткой → удалить карточку → проверка БД.
- **С6. Защитный контракт.** `PATCH`/`PUT` без строки → 404 `SETTINGS_NOT_FOUND`; в том числе сразу после `DELETE` без чтения. → pytest (контракт #179 без изменений).

## 8. Behavioral Delta (до → после)

1. Создание «учётки» в карточке сотрудника: строка настроек появлялась при первом заходе в админку → создаётся сразу, в той же транзакции.
2. Чтение настроек без строки: 404 → 200 + дефолты + запись строки в базу.
3. Сторонний клиент (скрипт, будущий web): должен был «догадаться» создать строку POST-ом → работает сразу через `GET`/`PATCH`.
4. Две вкладки после входа: вторая ловила 422 нарушение уникальности → обе получают одну и ту же строку.
5. `DELETE` настроек: строка исчезала навсегда, правки ломались до «догона» фронта → сброс к дефолтам, следующее чтение пересоздаёт.
6. Удаление карточки сотрудника: строка настроек оставалась сиротой → сносится вместе с учёткой.
7. Сид: два пользователя без настроек → оба со строками настроек.
8. Фронт: скрытое автосоздание настроек в контексте → убрано (чтение самолечивает).
9. `POST` настроек: принимал `user_id` из тела запроса (включая чужой — дыра записи) → `user_id` берётся из сессии, клиентское поле игнорируется.
10. Клиент API: методы `createUserSettings`/`deleteUserSettings` → удалены (мёртвый код; серверные эндпоинты не тронуты).

## 9. Вне скоупа

- Админ-управление учётками и паролями (правка телефона/роли, сброс пароля по ссылке на телефон, пароль при создании задаёт сам пользователь) → #348.
- UI-кнопка «сбросить настройки»: эндпоинт даёт возможность, кнопки в интерфейсе не строим (запроса не было).
- Общий каркас «гарантированных дочерних записей» для прочих сущностей: только доменное правило для `User` → `UserSettings`; каркас не строим.
- Миграция-бэкфилл: не нужна (инвентаризация 2026-09-20 — непересеваемых баз нет; самолечение на чтении закрывает любые существующие).

## 10. Открытые допущения

- «Учётка» карточки сотрудника остаётся единственной пользовательской точкой создания учёток (до #348).
- Слой сценариев приходит из #171 — зависимость уже в карточке #319; задачи плана стартуют после его мержа.
- `PATCH` сразу после `DELETE` (без чтения) даёт 404 — сознательное сохранение строгого контракта правки (#179); «сброс» = `DELETE` → `GET`.
