## 0. Контекст и выбранная концепция

Глубокая ссылка `/clients?clientId=<uuid>` открывается из карточки занятия (`ActivityDetailsModal`, единственный продюсер). Сегодня после мержа #231 страница читает параметр при монтировании и превращает его в **поисковый** фильтр: `initialFilters = {search: <uuid>, status: 'all'}`. Серверный поиск `q` (#212) матчит exact-UUID, таблица сужается до одной строки, модалка открывается из этой строки.

Дефекты текущей схемы:

1. Служебный UUID попадает в пользовательское поисковое поле и остаётся там после закрытия карточки (адресная часть при этом вытирается — фильтр и адрес рассинхронизируются).
2. Закрытие карточки — скрытая мутация адреса (`router.replace('/clients')`), не влияющая на фильтры: таблица остаётся суженной «без причины», видимой пользователю только через UUID в поиске.
3. Мёртвая ссылка (клиент удалён) вытирает адрес, но оставляет пустую таблицу с UUID в поиске до ручного сброса.

**Решения пользователя (Gate A, диалог в сессии 2026-09-21):**

- Сужение таблицы до отмеченных клиентов при переходе по ссылке — желаемое поведение, сохраняется.
- Единственный носитель идентификаторов — адрес страницы; поисковое поле их не показывает.
- Закрытие карточки не влияет на список отображаемых записей (включая установленные пользователем фильтры) и не трогает адрес.
- Ручной клик по строке таблицы — без сужения (сегодняшнее поведение, не меняется).
- **Формат адреса — сразу список идентификаторов** (`?clientId=a&clientId=b&…`): сужение до любого числа клиентов. Один идентификатор — частный случай: модалка открывается автоматически. Несколько — модалка не открывается, пользователь открывает карточки кликами по строкам.

Отвергнутые подходы (Gate A):

- **Page-resolution** (сервер вычисляет страницу клиента в полном списке при текущей сортировке/фильтрах, из оригинального предложения #232) — отвергнуто: сужение является целевым поведением; механика count-before неоправданно сложна.
- **Single-entity payload** (открывать модалку отдельным запросом `GET /clients/{id}` с агрегатами `ClientWithStats`, без сужения таблицы) — отвергнуто пользователем: сужение при переходе из расписания желательно; list-запрос закрывает и строку таблицы, и данные карточки одним запросом.
- **Ничего не делать** (триггеры #232 не сработали) — отвергнуто пользователем в диалоге.

## 1. Behavioral Delta (до → после)

| Сценарий | До | После |
|---|---|---|
| Открытие ссылки с одним идентификатором | Таблица сужена до 1 строки; в поисковом поле сырой UUID; карточка открыта; адрес содержит `?clientId=` | Таблица сужена до 1 строки; **поиск пуст**; карточка открыта автоматически; адрес содержит `?clientId=`; чип «Открыт по ссылке» |
| Открытие ссылки с несколькими идентификаторами | Невозможно | Таблица сужена до этих клиентов (стандартная сортировка таблицы); **модалка не открывается**; чип «Открыто по ссылке: N»; карточки — кликами по строкам |
| Открытие ссылки на архивного клиента | Находится через `status:'all'`, карточка открывается | Без изменений: находится и открывается (фильтр статуса `all` при deep-link сохранён — поведение #216) |
| Закрытие карточки (ссылка с одним) | Адрес молча вытирается, фильтр поиска остаётся: таблица сужена, UUID в поиске, рассинхрон адреса и фильтров | **Ничего не меняется**: таблица остаётся суженной, адрес прежний, поиск пуст; карточку можно открыть снова кликом по строке |
| Снятие сужения | Только полный сброс фильтров (кнопка «Сбросить»), при этом адрес уже вытерт ранее | Крестик на чипе — точечное снятие; полный сброс фильтров — тоже снимает; оба чистят адрес только от `?clientId=` |
| Мёртвая ссылка | Адрес вытирается, остаётся пустая таблица и UUID в поиске до ручного сброса | Один идентификатор на удалённого/чужого по скоупу: пустая таблица + чип; в списке идентификаторов — частично: показываются найденные, отсутствующие молча пропадают из выборки. Арес не вытирается молча |
| Ручные фильтры поверх сужения | Не определены; UUID «прилипает» к поиску | AND-семантика: сужение и пользовательские фильтры действуют вместе; чип остаётся; точечное снятие пользовательские фильтры не трогает |
| Мусор в параметре (не UUID, пробелы) | Сужение по «поиску» мусором → пустая таблица, dead-link cleanup | Невалидные значения отбрасываются; если валидных не осталось — параметр игнорируется, полная таблица |
| Ручной клик по строке | Карточка поверх таблицы, без сужения | Без изменений |

## 2. User Scenarios (каждый мапится на E2E)

- **US-1. Переход из расписания (один идентификатор).** Администратор из карточки занятия открывает клиента в новой вкладке. Страница «Клиенты» загружается: таблица сужена ровно до этого клиента, поисковая строка пуста, карточка клиента открыта автоматически, адрес содержит `?clientId=<uuid>`. Перезагрузка страницы (F5) восстанавливает то же состояние из адреса. → e2e: `clients.spec.ts` (расширение deep-link-кейса).
- **US-2. Закрытие карточки не трогает таблицу.** Администратор закрывает карточку. Таблица остаётся суженной до одного клиента, адрес не меняется, поиск пуст. Повторный клик по строке открывает карточку снова; авто-переоткрытие блокируется (см. 3.4, latch). → e2e: закрытие + повторное открытие.
- **US-3. Ссылка с несколькими идентификаторами.** Адрес `/clients?clientId=a&clientId=b&clientId=c`: таблица сужена до этих трёх клиентов в стандартной сортировке страницы, модалка автоматически не открывается, чип «Открыто по ссылке: 3». Клик по строке открывает карточку, закрытие — таблица прежняя. → e2e: multi-id кейс.
- **US-4. Точечное снятие сужения.** При активном сужении над таблицей виден чип «Открыт по ссылке» (или «Открыто по ссылке: N»). Клик по крестику снимает сужение: полная таблица, адрес без параметра, пользовательские фильтры (если были установлены поверх) сохраняются. → e2e: чип + снятие.
- **US-5. Мёртвая ссылка.** Один идентификатор на удалённого клиента: пустая таблица, чип сужения, адрес не меняется; снятие чипа → полная таблица. В списке — частичный случай: отсутствующие клиенты молча пропадают, найденные показываются. Ссылка на **архивного** клиента — не мёртвая: клиент находится (фильтр статуса `all`) и карточка открывается. → e2e: dead-link (удалённый) + архивный + частичный список.
- **US-6. Мусорный параметр.** `?clientId=abc` (не UUID, с пробелами) и микс `?clientId=abc&clientId=<valid>`: невалидные значения отбрасываются, валидные работают; если валидных нет — полная таблица, чипа нет. Повтор одного идентификатора дедуплицируется (`?clientId=a&clientId=a` — сужение до одного, модалка открывается — как US-1). → unit-покрытие парсинга адреса + e2e-кейс микса.
- **US-7. Ручной клик без сужения.** На полной таблице клик по строке: карточка поверх, фильтры и адрес не меняются; закрытие — таблица прежняя. → e2e: статус-кво-регресс (существующие тесты, добавить утверждение «адрес не содержит параметр»).
- **US-8. Скоуп мастера (#263).** Мастер открывает ссылку на клиента(ов), недоступных его скоупу (нет записей к его активностям, включая случай «записи есть, но все к чужим активностям»): недоступные не показываются (при одном — пустая таблица + чип), без утечки данных. → pytest (scope-кейс с `master_key`); отдельный e2e не заводится — инфраструктура сессии мастера для этой страницы дороже ценности кейса.

## 3. Техническое решение

### 3.1. Backend: общий фильтр по набору идентификаторов (все списочные эндпоинты)

Решение ревизии 4: фильтр `id` — общий кирпень всех табличных списков, не клиентская особенность.

- **Поле — в общем базовом классе списочных параметров** (`PaginationParams`, backend/src/schemas/pagination.py): `id: list[UUID] | None = None`; наследуют все списочные схемы. Валидация в одном месте кода: только UUID; потолок 100 значений — та же каноническая константа, что у размера страницы (#206), объявленная рядом с ней; дедупликация повторов (паттерн уровня поля — `BeforeValidator`, не модельный валидатор: модельные на Depends()-параметрах ловят 500, см. правило в `schemas/client.py`). Контрактные 422 (невалидный UUID, >100) единообразны для всех списочных эндпоинтов; фронт мусор и переполнение не шлёт (см. 3.3), 422 — защита контракта для внешних потребителей.
- **Применение — два потребителя одного механизма:**
  - универсальный сборщик простых списков (`GenericService._list_stmt`): предикат `id IN (…)` применяется из типизированного поля параметров отдельным случаем, МИМО мешка `**filters` (мешок остаётся только для равенств «колонка = значение»);
  - вью-функции табличных страниц: общий однострочный хелпер сужения. В объём #232 входят сборщик клиентов (сегодня `list_clients_with_stats`; после реализации #217 — `list_clients_view`) и остальные вью (записи, мастера, фото) — по строке хелпера и тесту-представителю, чтобы параметр не молчал ни на одном списочном эндпоинте.
- Сужение и пагинация действуют друг поверх друга: при числе идентификаторов больше размера страницы строки раскладываются по страницам (чип показывает число заданных в адресе).
- Порядок строк — стандартная сортировка list-эндпоинта (`sort_by`/`sort_order`), порядок идентификаторов в адресе на порядок строк не влияет.
- Скоуп `master_key` и маскировка D3 (#263) наследуются автоматически: предикат скоупа навешивается до фильтров и от них не зависит; отдельной точки входа нет.
- Существующий exact-UUID матч в q-матрице (`SearchField(Client.id, kind="uuid")`) сохраняется: ручной поиск со вставленным UUID продолжает находить клиента. Пересечение `?id=X&q=X` безвредно, фиксируется утверждением в тесте.

### 3.2. api-client

- Параметры list-функции клиентов (packages/api-client/src/endpoints.ts, `getClientsWithStats`): добавлен необязательный `ids?: string[]` → query-ключ `id` повторением значения для каждого элемента. Ключи собираются явно, не spread'ом фильтров.

### 3.3. Frontend: машинное поле фильтра и адрес — единственный источник сужения

- `ClientFilters` (frontend/admin/contexts/ClientsContext.tsx): новое необязательное поле `clientIds?: string[] | null` — машинное, не рендерится в поисковом поле и не участвует в его контролируемом состоянии.
- Контекст при сборке query: `clientIds` → повторение ключа `id` (наравне с `q`, `status` и т.д.).
- Чтение адреса — под существующей Suspense-границей #231 (`clients/page.tsx`), без изменений её положения. Правила парсинга:
  - `searchParams.getAll('clientId')` — все значения параметра;
  - покомпонентная строгая валидация UUID (регистр hex не важен; пустая строка, пробелы, любой мусор — не UUID); невалидные значения отбрасываются, валидные работают;
  - дедуп повторов одного идентификатора;
  - если после валидации и дедупа список пуст — параметра нет: `initialFilters = undefined`, дефолтные фильтры;
  - иначе `initialFilters = {clientIds: [...], status: 'all'}` (статус `all` — ссылка находит и архивных, поведение #216 сохраняется).
- **Правило автооткрытия:** после валидации и дедупа ровно один идентификатор → модалка открывается автоматически (как сегодня); два и больше — не открывается, карточки открываются кликами по строкам.
- **Живая синхронизация адрес → фильтр (единственный писатель).** Помимо посева при монтировании, машинное поле `clientIds` следует за адресом: изменение параметров адреса внутри вкладки (навигация «назад/вперёд», ручная правка адреса, снятие сужения) одним эффектом доводит фильтр до значения из адреса. Обратного потока нет: фильтр никогда не пишет адрес. Все прочие фильтры (поиск, статус, числа) в адрес не пишутся и из адреса не читаются — это территория #349; до его мержа `clientId` — единственный параметр адреса, отражаемый во фильтрах.
- Поисковое поле: `filters.search` больше не получает UUID ни на каком этапе; render-adjust паттерн (`ClientsFilters`) не затрагивается.
- Ручные фильтры поверх сужения — AND-семантика: сужение действует вместе с ними; чип остаётся, точечное снятие пользовательские фильтры не трогает. Ручная установка `?clientId=` в адрес при живых фильтрах — тот же принцип: сужение добавляется к текущим фильтрам, ничего не затирается.

### 3.4. Frontend: жизненный цикл модалки

- `onClose` модалки (`clients/page.tsx`): убрать `router.replace('/clients')`. Закрытие карточки не трогает адрес и фильтры.
- Авто-переоткрытие — только одноэлементный случай: latch #216 (`consumedClientIdRef`) сохраняется с инвариантом: пока в адресе ровно один валидный идентификатор, модалка автоматически не переоткрывается (после закрытия, при перезапросах списка); когда параметр уходит из адреса — latch сбрасывается, новая навигация с тем же идентификатором открывает модалку заново. При двух и более идентификаторах автооткрытия нет вовсе (3.3), latch не участвует. Снятие сужения (3.5) не открывает модалку: параметр уходит из адреса, эффект открытия деактивируется.
- Dead-link cleanup (сегодняшний effect с `router.replace` при пустом результате) — удаляется целиком: адрес не вытирается молча; пустой (или частичный) результат показывается явно (пустое состояние таблицы + чип).

### 3.5. Frontend: чип сужения и снятие

- При активном сужении (валидные `clientId` в адресе) над таблицей рендерится чип с крестиком: «Открыт по ссылке» (один идентификатор) или «Открыто по ссылке: N» (несколько). Без UUID в тексте; имена клиентов в чипе не показываются — строки и так видны в таблице, а у пропавших имён нет. Крестик — доступная кнопка (`aria-label` «Снять сужение», фокус с клавиатуры).
- Крестик выполняет ровно одно действие: удаляет все вхождения параметра `clientId` из адреса (`URLSearchParams` → `router.replace` с `scroll: false`), **сохраняя все прочие query-параметры страницы**. Фильтр доводится эффектом синхронизации (3.3) — ручной `setFilters` в обработчике не нужен, двойной писатель исключён.
- Полный сброс фильтров (`resetFilters`): сбрасывает все фильтры контекста; если в адресе есть `clientId`, эта же точка удаляет его из адреса (единственное место, где сброс касается адреса; прочие query-параметры сохраняются). Это новая документируемая ответственность `resetFilters`.
- Комбинация с пользовательскими фильтрами: см. 3.3 (AND, чип остаётся, точечное снятие не трогает пользовательские фильтры).

### 3.6. Что сознательно НЕ строим

- Page-resolution (позиция клиента в полном списке) — сужение целевое поведение.
- Single-entity payload `GET /clients/{id}` с агрегатами — модалка открывается из строки суженной таблицы, второй запрос не нужен.
- Двусторонний синк «все фильтры ↔ адрес» — вне скоупа; это #349 (общий URL-хук табличных страниц). В рамках #232 адрес отражает только сужение по идентификаторам.
- **Продюсеров списочных ссылок** — формат адреса поддерживает список, но в #232 никто не генерирует ссылок с несколькими идентификаторами: продюсер остаётся один (карточка занятия, один клиент). Появление генераторов списков — отдельная задача.
- Переименование параметра `clientId` → `id` в адресе страницы — не делаем: имя живёт в продюсере (`ActivityDetailsModal`), e2e и привычке; `id` — имя query-параметра API.
- Ручной клик по строке не пишет идентификатор в адрес.
- Удаление exact-UUID матча из q-матрицы поиска — не делаем: это публичное поведение API поиска, ортогональное задаче.

## 4. Тестирование

- **Backend (pytest, test_api_clients.py):** фильтр `?id=` возвращает ровно указанных клиентов; повторённый id дедуплицируется на уровне строк; порядок — стандартная сортировка, не порядок адреса; комбинируется AND с `status`/`q` (включая безвредность `?id=X&q=X`); мусор в значении → 422; >100 значений → 422; скоуп мастера: недоступные клиенты не возвращаются, маскировка на месте; generic-путь ПРИМЕНЯЕТ `id` типизированным ин-предикатом, мешок `**filters` остаётся равенствами (страж-утверждение); тесты-представители остальных списков: справочник через универсальный путь (например, локации) + вью-функции записей, мастеров и фото.
- **Frontend unit:** ClientsContext — `clientIds` → повторение `id` в query (явные ключи), поиск не затронут; парсинг адреса: один/несколько/повтор (дедуп + правило автооткрытия)/мусор отбрасывается покомпонентно/все невалидны; эффект синхронизации адрес → фильтр (установка, снятие, back-навигация); чип: рендер при `clientIds` (один/N), крестик чистит только адрес; `resetFilters` чистит адрес от `clientId`.
- **E2E (Playwright):** US-1…US-7 по списку выше. **Масштаб правок тестов — переписывание, не только дополнение:** существующие утверждения старой схемы «UUID в поиске» заменяются (`clients.spec.ts` deep-link-кейс, `admin-opens-profile.spec.ts`, `unify-caches.spec.ts`, `clients-status-column.spec.ts`, unit `ClientsPage.test.tsx` — initialFilters-утверждение).
- Seed-данные для скоуп-кейса: клиент без записей + клиент с записями только к чужим активностям (оба не возвращаются под `master_key`).

## 5. Риски и допущения

- **Допущение (UX-текст чипа):** формулировки «Открыт по ссылке» / «Открыто по ссылке: N» — рабочие; финальный текст уточняется при реализации.
- **Допущение (чип — единственный новый визуальный элемент страницы):** сегодня у клиентов нет чипов фильтров; без чипа сужение стало бы «невидимой магией» после ухода UUID из поиска. Полный сброс не подходит как единственный путь снятия — он сносит пользовательские фильтры.
- **Кап 100 идентификаторов** — зашит в общем коде базовых параметров рядом с потолком размера страницы (одна канонная константа, #206); спека цитирует, не выбирает. Защита от неограниченного IN-набора. Фронт адрес не обрезает молча: ручной ввод >100 приведёт к видимой ошибке запроса списка (честнее тихой усечки).
- **Кросс-вкладочный фон (унаследованный):** ссылка открывается в новой вкладке (`window.open _blank`); при удалении/архивации клиента в первой вкладке вторая живёт на кэше до ручного обновления — фон всего приложения, не специфичный для #232.
- **Enumeration-фон (унаследованный):** `?id=` под скоупом мастера различает «свой/чужой» клиент по известному UUID — тот же бит информации, что уже выдаёт внутренний точечный запрос с 404 на чужого; не регрессия #232.
- **Наследник #349:** когда #349 введёт общий URL-хук фильтров, эффект синхронизации `clientId` (3.3) становится частным случаем общего механизма; спека спроектирована совместимой с этим переходом (адрес — единственный писатель).
- Двойной механизм exact-UUID (q-матрица + id-фильтр) — осознанно: q остаётся для ручного поиска, id — машинный контракт (см. 3.6).
