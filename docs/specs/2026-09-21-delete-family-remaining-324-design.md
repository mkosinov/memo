## 2. Решение (Gate A — единственный концепт)

**Приведение к канону #318, без новых решений: шесть сущностей входят в семейный контракт один-в-один с тегами/записями.** Открытые вопросы самого issue («форма превью no-body 409 или dry_run», «нужен ли диалог листьям», «вгонять ли в undo-конвейер») закрыты каноном: `?dry_run=true`, листья без диалога, кольцо у каждого удаления.

Отвергнутые альтернативы:

- **No-body 409-превью** (архивный флейвор #207) — отменено семейным правилом #318: голый DELETE нигде не существует, превью только через флаг.
- **Рантайм-предпроверка «кто ссылается» при каждом DELETE** — отвергнута юзером 19.09 (неокупаемость); вместо неё декларативная матрица + тест-страж (D7).
- **Убрать роут `DELETE` настроек** — ломает полноту CRUD-контракта (#184) и API-стабильность; канон явно пре-армит листья (зависимости появятся — меняются только реестры домена).
- **Анонимизация визитов (nullify) при удалении посетителя** — меняет семантику истории (сегодня визиты умирают вместе с посетителем) и усложняет пересчёт мест/статусов; отклонено, поведение сохранено (см. D5).
- **If-Match/ETag-версии вместо `expected`-снапшотов, коды 412/428 вместо 422/409** — в репозитории нет системы версий строк; `expected`-снапшоты — семейный механизм (#285 rev8, смержен). Коды и форма (тело у DELETE, `?dry_run=true`, 422 на голую форму, 204 на пустое превью) — **осознанное отклонение от буквы RFC**, уже принятое и смерженное для records/activities/tags; консистентность семьи выше переосмысления кодов, отклонение фиксируется в каноне (`_overview.md`). Развязка фронт/бэк не грозит: клиенты живут в этом же репо и правятся синхронно (api-client — в плане), внешних потребителей у API нет.

## 3. Матрица зависимостей (FK_MATRIX)

Новые ключи в `backend/src/domain/deletion.py` (ниже запись сокращённая; в коде — полные `FKDependency(...)` по стилю существующих строк):

```
Visit:  []                                    # лист: входящих FK нет
Payment: []                                   # лист
Photo:  [photo_tags — cascade, non-auto, «Тег»]
UserSettings: []                              # лист
Visitor: [visits — cascade, non-auto, «Посещение»,
          visitor_tags — cascade, auto, «Тег»]
Position: [staff_positions — cascade, non-auto, «Сотрудник»]
```

- **Асимметрия перспектив** (правило Tag): одна и та же join-таблица легитимно встречается в нескольких матрицах с разной auto-ностью (`visitor_tags` — auto у Visitor-строки родителей и в матрице Visitor; `photo_tags` у Tag — non-auto, см. `deletion.py:321`). Видимость = главный эффект удаления показывается: у фото — отвязка тегов, у посетителя — гибель визитов.
- `visits` у посетителя: колонка `visit.visitor_id` nullable (анонимные визиты) — матрица зеркалит колонку (`nullable=True`), но действие назначено явно: `allowed_actions=["cascade"]` — единственное, без выбора; эвристика «nullable ⇒ nullify жизнеспособен» перекрывается явным списком. Поведение «визиты умирают с посетителем» сохранено (§2).
- `staff_positions` — `allowed_actions=["cascade"]` (снять должность у сотрудников).
- Узлы 409-дерева всех новых зависимостей несут `allowed_actions: ["cascade"]` — фронтовый диалог выбора не рисует (зеркало тегов).

## 4. Контракты DELETE-рутов (зеркало tags.py:216)

Единая форма для всех шести. **Порядок проверок** (защищает скоуп-модель — панель безопасности, BLOCKER rev1):

1. **Форма** (флаг/тело): `?dry_run=true` + `resolutions` → 422 `dry_run_with_resolutions_forbidden`; без флага и без тела → 422 `expected_state_required`; тело с `resolutions`, но без `expected` → 422 `expected_state_required` (семейная форма; неизвестность id не важна — форма ничего не сообщает о существовании).
2. **Скоуп-проба существования — через существующие хелперы, первой строкой обеих веток** (dry_run и коммит): `*_scoped_or_404` (`visits.py:69`, `payments.py:41`, `photos.py:43`, `visitors.py:41`) → 404 на чужое и на несуществующее; `user_settings` — probe-чтение строки + own-only 403 (`user_settings.py:113`). Проба возвращает строку (нужна позициям, см. ниже). Отдельного «голого» probe мимо хелперов нет — чужой id не становится оракулом существования и не раскрывает дерево.
3. **Guard субъекта (positions):** прочитанная пробой строка `is_system` → 422 `POSITION_IS_SYSTEM` до развилки dry_run/commit — системная должность не превьюируется и не удаляется ни в какой форме (поведение «встроенная не удаляется» сохранено, проверка раньше сегодняшней исполнения-времени).
4. **Ветка dry_run**: чистое превью, строки не меняются, SSE нет — зависимости есть → **409** `{detail: "has_dependencies", dependencies: [дерево]}`; пусто → **204** без удаления.
5. **Ветка коммита** (тело `{resolutions?, expected}`): сбор дерева → сверка `expected` id-множествами (subset-семантика #285 rev8: появившаяся за окно зависимость → **409** `stale_dependencies` + живое дерево; исчезнувшая не блокирует — исчезновение неопасно, семейное решение) → валидация `resolutions` → исполнитель → 204. Сверка и исполнение — одна транзакция.

Особенности по сущностям:

- **visits** (`visits.py:232`): dry_run всегда 204 (лист); коммит `{expected: {}}`; **сохраняется существующий пересчёт статуса/мест родительской записи** (`visit.py:179–180`).
- **payments** (`payments.py:212`): аналогично, без пересчёта (платёж не входит в статус записи).
- **photos** (`photos.py:234`): с тегами dry_run → 409 (узел «Тег», счётчик + items); коммит `{expected: {photo_tags: [...]}}`; чистое — `{expected: {}}`. Скоуп-охрана #263 не меняется (первая строка, п.2).
- **user_settings** (`user_settings.py:113`): dry_run → 204; коммит `{expected: {}}`. UI нет — только API-контракт.
- **visitors** (`visitors.py:183`): dry_run с визитами → 409 (узел «Посещение»: счётчик + items); коммит `{expected: {visits: [...], visitor_tags: [...]}}` (auto-строка тоже входит в сверку — исполнитель удаляет обе группы).
- **positions** (`position.py:162`): не-системная занятая: dry_run → 409 (узел «Сотрудник»); коммит `{expected: {staff_positions: [...]}}`; чистая — `{expected: {}}`. **Scope-модели у должностей сознательно нет** (справочник студии): доступ = роль `positions:write` (`_WRITE_GUARD`), дерево «Сотрудник: N» видит держатель роли — фиксируется как решение.

## 5. Исполнители (resolve_delete): реестры и порядок

Матричной строки недостаточно — проводка каждого нового субъекта **полным комплектом реестров** (образец — теговые строки #318):

- `FK_MATRIX[M]` — строки зависимостей (§3);
- счётчики `_COUNTERS[(M, entity)]` и item-коллекторы для узлов дерева (образцы: `_count_t_photo_tags` `deletion.py:652`, `_count_m_staff_positions` `deletion.py:433`);
- id-сборщики `expected` (по одному на ключ `(M, entity)`, маппинг на целевую таблицу): `visits` → `visit.id` по `visitor_id`; `visitor_tags`/`photo_tags`/`staff_positions` → id-строки join-таблиц по колонке владельца;
- join-delete-хендлеры с ключами `(M, entity)` — `(Photo, "photo_tags")`, `(Visitor, "visitor_tags")`, `(Position, "staff_positions")`. Ключ = (модель, entity), поэтому одна таблица в нескольких матрицах конфликтов не создаёт (прецедент: `(Tag, "photo_tags")` уже в реестрах).

**Порядок исполнения:** сначала join-чистка (Core bulk), затем Core bulk-удаление строки субъекта — мимо ORM-каскада, детерминированно при любом PRAGMA.

**Visits-пачка посетителя — единый строительный блок.** Метод сервиса визитов «удалить визиты посетителя пачкой + пересчитать затронутые записи»: сбор `record_id` затронутых записей → bulk-удаление визитов → для каждой записи переиспользовать `recompute_record_seats` + `recompute_record_status` (`backend/src/domain/record_visits.py:25,51`; так делает одиночный путь — `visit.py:179–180`). Готового блока в коде нет (`delete_visits_by_record` — сценарный хелпер без пересчёта) — заводится здесь. Блок помечает SSE-маркеры `visits` + `records` (как одиночный путь). Использование: (а) исполнитель `Visitor`; (б) `VisitorService._delete_cascade` — **внутренности делегируют блоку, сигнатура сохраняется** (тест атомарности клиент-каскада с `monkeypatch` подменяет `_delete_cascade` целиком и остаётся зелёным); (в) в будущем — сценарий `delete_client` (#327).

**Наследование пересчёта клиент-каскадом** (`Client → visitors → visits`): клиентский путь вызывает `_delete_cascade`, поэтому пересчёт записей включается в нём автоматически, отдельного кода для клиент-флоу не пишется — поведение фиксируется тестом (сегодня каскад оставляет статусы/места stale, это тот же инвариант «визит удалён → запись пересчитана»).

## 7. Тест-страж «схема ↔ матрица» (этап 3 трекера)

Новый контрактный тест `backend/tests/test_delete_matrix_guard.py`, две стороны:

1. **Схема → матрица:** для каждого ключа `FK_MATRIX[M]` интроспекция `Base.metadata`: каждое **входящее** FK-ребро субъекта (другая таблица ссылается на M, включая join-таблицы m2m) объявлено строкой зависимости в `FK_MATRIX[M]`. Исходящие рёбра субъекта не проверяются в его собственной матрице — они принадлежат матрицам владельцев (`visit.record_id`/`visit.visitor_id` — строки `visits` в `FK_MATRIX[Record]` и новой `FK_MATRIX[Visitor]`, в `FK_MATRIX[Visit]` их нет и не должно быть). Появилась входящая FK-связь без декларации → тест красный в том же PR.
2. **Роуты → матрица:** обход `app.routes` (переиспользовать существующую в тестах обёртку — прецедент `test_auth_contract.py`, включая обработку `_IncludedRouter`): каждый `DELETE /api/v1/.../{id}` отображается на субъекта (нормализация префиксов, в т.ч. `/my/settings/...` → UserSettings), субъект обязан быть ключом матрицы (у листв — пустой список). Новый DELETE-рут без декларации → красный.

Известная граница: ребро, заведённое мимо `Base.metadata` (raw SQL/миграция без модели), стражем не ловится — фиксируется как ограничение, а не покрытие.

## 8. Behavioral Delta (до → после)

| Действие | До | После |
|---|---|---|
| Удалить фото с тегами | безликая ошибка «Database integrity constraint violated» (422), фото не удаляется | диалог «Теги: N будут отвязаны» → кольцо 5 с → отмена возможна; после окна теги отвязаны, фото удалено |
| Удалить чистое фото | мгновенно, без отмены | кольцо 5 с, отмена возвращает |
| Удалить посетителя с визитами | мгновенно; визиты стираются молча; статус/места записей остаются stale | диалог «Посещения: N будут удалены» → кольцо 5 с → отмена; после — честный пересчёт статуса/мест затронутых записей |
| Удалить посетителя без визитов | мгновенно | кольцо 5 с |
| Удалить занятую должность | мгновенно; сотрудники молча теряют должность | диалог «Сотрудники: N потеряют должность» → кольцо 5 с → отмена |
| Удалить чистую должность | `window.confirm` + мгновенно | кольцо 5 с |
| Системная должность | 422 «Встроенная должность не удаляется» | без изменений (проверка стала раньше — до превью) |
| Удалить визит/платёж (UI) | кольцо 5 с (уже было) | видимо без изменений; коммит несёт `{expected: {}}` |
| `DELETE` без тела (API, все 6) | работает как мгновенное удаление | 422 `expected_state_required`; доступ — `?dry_run=true` или тело |
| Новая FK-связь у удаляемой сущности | незамеченной проходит мимо контракта | тест-страж краснеет в том же PR |

## 9. User Scenarios (→ E2E)

1. **Чистое фото с отменой.** Админ удаляет фото без тегов → появляется кольцо 5 с → «Отменить» → фото на месте, запроса удаления не было. → e2e: photos — удаление с undo.
2. **Фото с тегами.** Админ удаляет фото, у него 2 тега → диалог «Теги: 2 будут отвязаны» → подтвердить → кольцо → после окна фото нет в галерее, теги остаются в справочнике. → e2e: photos — удаление с превью зависимостей.
3. **Посетитель с визитами.** В карточке клиента админ удаляет посетителя с 3 визитами → диалог «Посещения: 3 будут удалены» → подтвердить → кольцо → после окна посетитель и визиты удалены, статус/места записей пересчитаны. → e2e: clients — удаление посетителя с зависимостями.
4. **Гонка в окне отмены.** Кольцо удаления посетителя активно; второй пользователь добавляет визит этому посетителю → коммит → честная ошибка устаревшего состояния + «Обновить», строка возвращена. → e2e: mirror тегового сценария #318 (stale_dependencies).
5. **Занятая должность.** Справочники → должность, носимая 2 сотрудниками → удалить → диалог «Сотрудники: 2 потеряют должность» → подтвердить → кольцо → должность снята у обоих. → e2e: positions — удаление с превью.
6. **Системная должность.** Попытка удалить встроенную должность → понятная ошибка, ничего не меняется. → e2e: positions — системная охрана (api-тест + дым).

Визиты/оплаты новых e2e не требуют (видимое поведение не меняется) — покрываются api-контрактными тестами и вит-проверкой тела коммита.

## 10. Тесты

- **Контрактная форма — один параметризованный api-тест** (полный набор: dry_run 204/409-дерево, голый 422, `resolutions`-без-`expected` 422, dry_run+resolutions 422, dry_run+expected-only игнор, коммит, stale 409, **dry_run на неизвестном/чужом id → 404**, `allowed_actions: ["cascade"]` в узлах) — прогоняется на зависимых (photos/visitors/positions); **листья (visits/payments/user_settings) — сокращённый набор** (голый 422, dry_run 204, коммит `{expected: {}}`, неизвестный id 404): их превью структурно пусто, мёртвые ветки комбинаторики не тестируются. По-сущностные отличия поверх: системная охрана должности (422 до развилки), own-only 403 настроек, скоуп-404 четырёх охраняемых рутов.
- **Исполнители:** каскад посетителя (визиты+теги удалены, записи пересчитаны — включая клиент-каскад через `_delete_cascade`), join-очистка трёх таблиц (порядок join→субъект, детерминированность), SSE-метки `visits`+`records`.
- **Страж:** §7 (схема↔матрица с определением входящего ребра; роуты↔матрица с нормализацией префиксов).
- **Фронт:** vitest — хуки photos/positions/visitors (кольцо, диалог, undo, инвалидация) и **тело коммита визитов/платежей** (`{expected: {}}` уходит в DELETE) + правка мок-обвязки; e2e по сценариям §9.
