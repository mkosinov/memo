# #327 — Каскадный долг 3/3: удаление клиента в сценарий `delete_client` + пачковый метод визитов посетителя

- **Issue:** #327 (`refactor(services)`, depends-on #171 — смержен PR #340, канон `docs/domain-rules/service-layer.md` действует)
- **Дата:** 2026-09-26
- **Статус:** rev2 (панель 6/6 отработала; BLOCKER событийной сетки и находки панели внесены), ожидает ОК пользователя (Gate B)
- **Прецеденты:** #325 (сценарий `delete_record`, GH #171 Task 5), #171 Task 1–2 (own-edge команды и сценарные кирпичи)
- **Вердикт разведки:** actual — пробел подтверждён живым кодом (см. «Актуальность»)

## 1. Контекст и проблема

Каскадное удаление клиента сегодня исполняется общим движком `GenericService.resolve_delete` (services/generic.py): route `DELETE /clients/{id}` с телом резолюций → `ClientService.resolve_delete` → диспетчеризация по `FK_MATRIX[Client]` через `CASCADE_HANDLERS`. Хендлер `Client → visitors` (`_h_cascade_client_visitors`, domain/deletion.py) в цикле вызывает `VisitorService._delete_cascade`, а тот **прямым SQL стирает визиты** (`DELETE FROM visits WHERE visitor_id = …`, services/visitor.py) — таблицу, которой владеет сервис визитов, а не посетителя. Это зафиксированное нарушение канона слоя сервисов: «табличные команды живут у владельца таблицы»; в правиле 10 канона (`service-layer.md`) этот случай прямо числится в реестре долга третьей строкой — после тегов (#318) и занятий (#325) остаётся последним неперенесённым каскадом.

Issue предписывает решение по уже дважды применённому паттерну: бизнес-цепочка удаления уезжает в слой сценариев (`usecases/`) свободной функцией, а удаление визитов посетителя становится пачковым методом сервиса-владельца — полным аналогом `delete_by_record` у платежей и `delete_visits_by_record` у визитов, только с фильтром по собственной колонке-ссылке `visitor_id`.

## 2. Актуальность (разведка по живому дереву, 2026-09-26)

Проверено скаутом по main (после мержей #369/#370/#372):

| Утверждение issue | Факт | Вердикт |
|---|---|---|
| Каскад посетителя стирает визиты прямым SQL | `VisitorService._delete_cascade` выполняет `delete(Visit).where(Visit.visitor_id == …)` | подтверждено |
| Вызов идёт из сервиса клиентов канонным делегированием | `_h_cascade_client_visitors` → цикл `_delete_cascade`; регистрация `(Client, "visitors")` в `CASCADE_HANDLERS` | подтверждено |
| Слой сценариев и прецедент существуют | `usecases/records.py::delete_record` — тот же перенос для занятий (#325) | подтверждено |
| Пачковый прецедент у платежей существует | `PaymentService.delete_by_record` → `PaymentRepository.delete_by_record_id` | подтверждено |
| У визитов пачкового метода по `visitor_id` нет | есть только `delete_visits_by_record` (по `record_id`) | подтверждено |

Дополнительные факты, учтённые в дизайне:

- `_delete_cascade` вызывается ровно из двух мест: хендлер клиентского каскада и собственный декорированный `VisitorService.delete` (standalone-роут `DELETE /visitors/{id}` существует). Любая правка метода затрагивает оба пути.
- После #325 каскад-хендлеры записей из `deletion.py` **удалены** — прецедент чистки после переноса в сценарий.
- Событийная сетка (SSE-инвалидация, #239) execute-удаления клиента сегодня: `{"clients", "records", "photos", "visitors", "client_tags"}` — `"clients"` сеет декоратор `@transactional` (авто-метка сущности сервиса при вызове метода с `self`, services/decorators.py), остальные — по одной метке на каждую зависимость матрицы, безусловно, по факту диспетчеризации (даже при нуле строк зависимости). Метки `"visits"` сетка **не содержит**. Закреплено тестом tests/test_events_emit.py (execute-ветка клиента). На ветке 404 (клиент не найден) декоратор всё равно публикует `{"clients"}` — публикация идёт после возврата метода, без проверки результата; ветки 422 (исключение) не публикают ничего.
- Тест атомарности (tests/test_api_clients.py, «§8 atomicity») симулирует сбой патчем `VisitorService._delete_cascade` на синглтоне — сценарий обязан продолжать вызывать именно этот метод, иначе тест перестаёт быть зелёным без правок (запрещено критериями приёмки).
- Структурный тест (tests/services/test_visitor_service.py) требует `hasattr(VisitorService, "_delete_cascade")` и проверяет свойство «не коммитит» по выживанию строки **посетителя** — удаление визитов в нём не проверяется, правка метода его не ломает.

## 3. Цели и границы

**Цели.**

1. Каскад удаления клиента (execute-ветка с резолюциями) исполняется сценарием `usecases.clients.delete_client` — одна транзакция, один пакет событий.
2. Каскад посетителя больше не пишет в таблицу визитов напрямую: визиты удаляет сервис-владелец пачковым методом по `visitor_id`.
3. Поведение для пользователя не меняется: HTTP-контракт, дерево зависимостей, эффекты в БД, событийная сетка, атомарность — байт-в-байт как сегодня.

**Границы (что сознательно НЕ делаем).**

- **Не трогаем dry-run-путь без тела:** `DELETE /clients/{id}` без body при пустых зависимостях вызывает `service.delete` (простое удаление строки без каскада). Перевод этого пути на сценарий изменил бы событийную сетку для «чистого» клиента (простое удаление публикует только авто-метку `"clients"`, без меток зависимостей) — паритет важнее унификации.
- **Не добавляем `"visits"` в событийную сетку** клиентского удаления и standalone-удаления посетителя: сегодня её нет, добавление — изменение поведения. Если дыра инвалидации визитов когда-то станет проблемой — отдельное решение, не в этом рефакторинге.
- **Не трогаем standalone-контракт `DELETE /visitors/{id}`:** видимое поведение (визиты + теги + строка удаляются, статус 204/404) сохраняется; меняется только внутренняя композиция.
- **Не переносим другие сущности** (Staff, Location, Service, Material, Tag остаются на общем `resolve_delete`) — это их собственные строки долга.
- **Не переименовываем `_delete_cascade`:** имя держит структурный тест и точка патча теста атомарности; переименование = правки тестов = нарушение «тесты зелёные без правок».

## 4. Решение

### 4.1. Новые кирпичи визитов (канон, правила 3–4)

- `VisitRepository.delete_by_visitor_id(session, visitor_id)` — один set-based `DELETE FROM visits WHERE visitor_id = :vid`, без коммита. Полный аналог `delete_by_record_id`; шапка репозитория визитов уже предписывает «bulk-команды фильтруют по собственной колонке-ссылке».
- `VisitService.delete_visits_by_visitor(db_session, visitor_id, *, mark_visits=True)` — недекорированный сценарный кирпич: делегирует в репозиторий, помечает `"visits"`. Параметр `mark_visits` — зеркально `delete_visits_by_record`: оба текущих вызова (клиентский сценарий, standalone-удаление посетителя) передают `False` (владелец сетки — оркестратор, паритет), True-ветка остаётся для будущих сценариев, которым понадобится метка; симметрия сигнатур двух братских методов визитного сервиса сознательно выбрана вместо экономии одного параметра.

### 4.2. Перестройка `VisitorService`

- `_delete_cascade(db_session, visitor_id)`: из тела удаляется строка прямого удаления визитов; метод становится own-edge командой «теги посетителя + строка посетителя» (visitor_tags перед строкой — FK без ondelete). Имя и сигнатура сохраняются; docstring переписывается под новую роль.
- Декорированный `delete` (standalone-роут посетителей) перед `_delete_cascade` вызывает `get_visit_service().delete_visits_by_visitor(db_session, id, mark_visits=False)` — итоговое поведение и событийная сетка ровно прежние. Импорт `services.visit` в `services.visitor` цикла не образует (проверено: `visit.py` не импортирует `visitor.py`).

### 4.3. Own-edge клиента

- Новый специализированный `repositories/client.py::ClientRepository` (наследник `ArchiveRepository`, фабрика-синглтон `get_client_repository`) с методом `delete_tags_by_client_id(session, client_id)` — один set-based DELETE джойн-строк `client_tags`; точный аналог `RecordRepository.delete_tags_by_record_id`. Сегодня клиентский сервис сидит на generic-репозитории — специализация появляется вместе с первой собственной табличной командой.
- `ClientService.delete_row_with_tags(db_session, client_id)` — недекорированный кирпич: теги клиента + строка клиента, без коммита, без меток (аналог `RecordService.delete_row_with_tags`); фабрика сервиса переключается на `get_client_repository()`.
- Из `ClientService` удаляется DI-инъекция `_visitor_service` (конструктор и фабрика возвращаются к стандартной форме): после удаления хендлера инъекцию никто не читает; сценарий берёт синглтон `get_visitor_service()` напрямую — тест атомарности патчит тот же синглтон и продолжает работать.

### 4.4. Сценарий `usecases/clients.py::delete_client`

Сигнатура: `delete_client(db_session, id, resolutions) -> bool`, `@transactional`, вызов с ведущим `None` и ключевыми аргументами (конвенция слоя сценариев — обёртка занимает первый слот `self`; бесклассовый вызов открывает аккумулятор пустым — все метки сценарий ставит сам, зеркально прецеденту `delete_record`). Сервисные синглтоны резолвятся фабриками **внутри тела сценария** при каждом вызове (не захватом на уровне модуля) — иначе monkeypatch-патч теста атомарности на синглтоне посетителя перестанет перехватываться. Фазы, в порядке сегодняшнего `resolve_delete`:

1. **Проверка существования** — сервисный точечный `get`; сразу после неё — `mark_changed("clients")`: у бесклассового сценария нет авто-метки декоратора, а сегодня `"clients"` публикуется на **каждой** непасходной ветке execute (включая 404 — публикация после возврата без проверки результата). `None` → `False` (роут отдаёт 404, событие `{"clients"}` опубликовано — паритет). Модель для доменных реестров — импорт класса `Client`: задокументированное отклонение от буквы прецедента `delete_record` (тот берёт `type(строки)`, потому что его сервисный `get` возвращает ORM-строку; клиентский `get` возвращает Pydantic-схему). Импорт — статический ключ реестров `FK_MATRIX`/`NULLIFY_HANDLERS`, сценарий не строит ORM-строки.
2. **Сбор зависимостей** — `collect_dependencies` (общий движок чтения из `domain/deletion.py`, остаётся на месте).
3. **Защитный блокирующий контроль** — `has_blocking_deps` → `BlockingDepsError` (для клиента недостижим — все зависимости cascade/nullify; сохранён для паритета с прецедентом `delete_record`, матрица — данные: будущая block-зависимость оживит проверку без правки сценария).
4. **Валидация резолюций** — `validate_resolutions` → `InvalidResolutionError` (роут — прежние 422; исключение → аккумулятор сбрасывается без публикации, как сегодня).
5. **Nullify-фаза** — диспетчеризация по `FK_MATRIX[Client]` через `NULLIFY_HANDLERS` (записи: `client_id → NULL`; фото: отвязка владельца), после каждого хендлера `mark_changed(dep.entity)` — безусловно, по факту диспетчеризации, как в executor'е.
6. **Каскад посетителей** — список посетителей через существующий `VisitorService.list_by_client(db_session, client_id, master_key=None)` (админ-режим, без scope-предиката; сценарий не пишет SQL сам и не импортирует модель посетителя); для каждого: `delete_visits_by_visitor(..., mark_visits=False)` → `VisitorService._delete_cascade(...)`; после цикла `mark_changed("visitors")` — безусловно, даже при пустом списке. Порядок «визиты раньше посетителя» сохранён (FK).
7. **Строка клиента** — `delete_row_with_tags` + `mark_changed("client_tags")`.
8. `True` (роут — 204).

Событийная сетка успеха — ровно `{"clients", "records", "photos", "visitors", "client_tags"}`, метки зависимостей безусловны (ставятся и при нуле строк — паритет с executor'ом), порядок фаз как сегодня (nullify → visitors → client_tags). Ветка 404 публикует `{"clients"}`, ветки 422 не публикают ничего — байт-в-байт как сегодня.

### 4.5. Роут и чистка реестров

- `api/v1/clients.py`: execute-ветка (тело с `resolutions`) вызывает сценарий вместо `service.resolve_delete`; маппинг `ResolutionError → 422`, `False → 404` не меняется. Dry-run-ветка не трогается.
- `domain/deletion.py`: удаляются `_h_cascade_client_visitors`, `_h_cascade_client_tags` и их регистрации в `CASCADE_HANDLERS` (мёртвый код после ухода executor'а — прецедент #325). `FK_MATRIX[Client]` и клиентские записи `NULLIFY_HANDLERS` остаются: матрицу читают dry-run-дерево и валидация, nullify-хендлеры диспетчеризует сценарий.
- Защита от тихой деградации: после удаления хендлеров вызов `resolve_delete` для `Client` молча пропустил бы каскад (executor пропускает депы без хендлера). Инвариант «execute-удаление клиента — только через сценарий» закрепляется структурным регрессионным тестом: в `CASCADE_HANDLERS` нет клиентских ключей, а маршрут вызывает сценарий (см. верификацию).

## 6. Behavioral Delta (до → после)

**Для пользователя: ничего не меняется.** Статусы и тела ответов `DELETE /clients/{id}` (204/404/409/422 + дерево зависимостей), эффект в БД (те же таблицы, тот же порядок), атомарность отката, состав событий SSE, поведение `DELETE /visitors/{id}` — идентичны. Существующие тесты проходят без правок — это главный критерий приёмки.

**Для системы (внутренняя архитектура):**

| Было | Стало |
|---|---|
| Каскад исполняет `ClientService.resolve_delete` через реестр хендлеров `deletion.py` | Бизнес-цепочка — сценарий `usecases.clients.delete_client`, одна `@transactional`-транзакция |
| `VisitorService._delete_cascade` прямым SQL стирает чужую таблицу визитов | Визиты удаляет владелец: `VisitService.delete_visits_by_visitor` → `VisitRepository.delete_by_visitor_id` (один set-based DELETE) |
| Строка и теги клиента — два разнесённых шага executor'а | Own-edge `ClientService.delete_row_with_tags` + репо-метод |
| `ClientService` несёт DI `_visitor_service` ради хендлера | Инъекция удалена; хендлеры клиентского каскада и их регистрации в `CASCADE_HANDLERS` удалены |

## 7. Верификация

1. **Паритет без правок (существующие тесты):** весь `test_api_clients.py` (bare delete, 409-дерево, 204-execute, 422-резолюции, атомарность §8), `tests/test_events_emit.py` (событийная сетка execute-ветки клиента — главный контракт SSE-паритета), `tests/services/test_visitor_service.py` (структурный + no-commit), `test_delete_cascades.py::test_visitor_delete_cascades_to_visits`.
2. **Новые тесты:** (а) юнит `delete_visits_by_visitor` — один DELETE, no-commit, `mark_visits=False` подавляет метку; (б) юнит сценария — сетка успеха `{"clients","records","photos","visitors","client_tags"}` (включая execute с пустыми резолюциями `{}` на клиенте без зависимостей — метки зависимостей безусловны), на ветке 404 ровно `{"clients"}`, на ветках 422 пустая; (в) структурный регрессионный: в `CASCADE_HANDLERS` нет клиентских ключей (прецедент — Activity-guard в tests/domain/test_deletion.py), execute-ветка роута клиентов импортирует сценарий — эта часть и есть нагружающая защита.
3. **Механика:** линт/тайпчек бэкенда, полный pytest бэкенда.

## 8. Риски и допущения

- **Молчаливый пропуск каскада при возврате к `resolve_delete` для клиента** (executor пропускает деп без хендлера) — закрыт структурным регрессионным тестом (см. 7.2в) плюс якорем U1: возврат к executor'у оставил бы БД без каскада и упал на существующем тесте.
- **Сетку `"visits"` сознательно не публикуем** (паритет). Допущение: дыра инвалидации визитных таблиц при клиентском удалении существовала и до рефакторинга; её закрытие — отдельное решение, если понадобится.
- **Посетитель, появившийся в окне между dry-run и подтверждением, удаляется молча вместе со старыми** — сверки снимка `expected` у клиентского удаления нет: подтверждение несёт только действия по сущностям, без снимка увиденного (сверка реализована у удаления занятий, #285). Это отступление от универсального контракта удаления «удаляем только то, что пользователь видел и подтвердил» (решение пользователя 2026-09-26: контракт относится ко всем сущностям, не только к занятиям). В рамках #327 поведение сохраняется — рефакторинг не меняет API-контракт; исправление (внедрение expected-сверки по образцу #285) — отдельная задача.
- **Имя `_delete_cascade` больше не отражает состав каскада** (теперь только теги + строка) — цена сохранения теста атомарности и структурного теста без правок; роль раскрыта в docstring. Точка мока приватного метода в тесте атомарности — задокументированный компромисс; при ближайшей возможности править тесты перенести её на публичный шов.
- Кнопка «удалить» в UI и мастер-скоп не затрагиваются: guard'ы роута и маскирование не меняются.
