# Фильтры табличных страниц в URL: общий хук + волна миграции (#349)

- Дата: 2026-09-26, ревизия 3 (панель: интеграционный контракт фабрики, единый писатель, коррекция страницы, ресинхронизация поиска, Suspense-границы волны; Gate B: push-политика истории, `per_page` в URL, журнал действий подтверждён)
- Статус: спека согласована (Gate B пройден 26.09)
- Связь: конвенция — закрытый issue #138 (спека §2.4); посадочная площадка deep-link — #231/#232 (в main); канон имён list-параметров — #212; прецедент большого паттерн-issue волной — #139 (DataTable)

## Контекст

Конвенция #138: **фильтры любой табличной страницы живут в её URL** — двусторонняя синхронизация (страница читает параметры при монтировании, пишет при изменении), шаринг ссылок работает из коробки. Сейчас конвенция выполнена только для двух страниц:

- расписание `/schedule` — хук `useScheduleView` (`view`/`date`/`col`): строгие парсеры с тихим фолбэком на дефолты, единая точка записи URL (композиция последовательных синхронных записей через ref поверх актуальных параметров), `push` для навигационных переключений (back = предыдущая неделя) и `replace` для переключателя отображения;
- записи `/records` — хук `useRecordsPeriod` (`from`/`to`): только период, всегда `replace` («правки фильтров частые — не пачкать историю»), сохранение нетронутой стороны при частичной смене, инвертированная пара инвалидирует обе.

Все табличные страницы стоят на общем `DataTable` и фабрике контекстов `createPagedListContext` (клиенты, теги, локации, должности, материалы, услуги, сотрудники, фото, журнал действий); записи и фото имеют локальные отклонения от фабричной формы. Фильтры этих страниц живут в контекстном стейте — перезагрузка и скопированная ссылка их теряют. Фабрика управляет `page`/`perPage`/`sortBy`/`sortOrder`/`status`/`search` через `useState`, засеивает только структурированные `initialFilters` (однократно, при монтировании) и содержит авто-декремент пустой страницы (`page → page−1`, `createPagedListContext.tsx:250`) и сброс `page → 1` во всех сеттерах фильтров.

Клиенты уже имеют deep-link `?clientId=` (посадочная площадка #231/#232): параметры читаются выше провайдера, передаются в контекст через шов `initialFilters`; инвариант «deep-link = ровно один запрос на монтировании» зафиксирован e2e-счётчиком запросов списка.

Канон имён параметров списка задан API-клиентом (`packages/api-client`, сериализация `listQuery`): `q`, `page`, `per_page`, `sort_by`, `sort_order`; у клиентов дополнительно `status`, у фото `tag_id`, у записей `location_id`/`service_id`/`master_id`, у журнала `user_id`/`action`/`entity`/`date_from`/`date_to`. Поиск `q` отправляется на сервер только при ≥ 2 символах (правило #212).

Правило трёх (#138): расписание и записи дали два постраничных решения; клиенты — третья страница, на которой паттерн сводится в общий хук, дальше он расходится волной на все таблицы.

## Цель

Все табличные страницы админки держат фильтры в URL: ссылка с фильтрами открывает страницу сразу в нужном состоянии ровно одним запросом списка; перезагрузка не теряет состояние; «назад/вперёд» ведут себя предсказуемо и история не замусоривается.

## Концепт

Общий хук URL-состояния таблицы + интеграционный контракт с фабрикой контекстов + волна миграции всех табличных страниц. URL — единственный источник правды для параметров таблицы: состояние выводится из URL при рендере, пользовательские обработчики пишут только через хук (единый писатель), зеркальный эффект «стейт → URL» не строится — циклов «записал→прочитал→записал» нет по построению.

Отвергнутые альтернативы:

- **сторонняя библиотека** (nuqs, use-query-params): два живых собственных хука уже задали паттерн и семантику Suspense/навигации; замена на зависимость меняет поведение всей админки. Из консенсуса по библиотекам заимствованы приёмы (батчинг/троттлинг записей, `scroll: false`), не сама зависимость;
- **синхронизация только внутри фабрики `createPagedListContext`** (без отдельного хука): записи и фото отклоняются от фабричной формы, а deep-link клиентов читает параметры выше провайдера — хук обязан работать и вне фабрики. Фабрика получает подключаемую интеграцию (§3), но не является единственным потребителем хука;
- **зеркальный паттерн «стейт → URL»**: признан источником циклов и гонок; вместо него — вывод состояния из URL при рендере.

`useScheduleView` не переписывается (расписание — не таблица, вне волны; его навигационная семантика push/back = предыдущая неделя — отдельная ценность). `useRecordsPeriod` упраздняется: на странице записей должен быть ровно один писатель URL, поэтому период портируется в общий хук как тип «пара дат» (§2), поведение заперто существующими тестами провайдера/страницы (`__tests__/useRecordsPeriod.test.tsx`, `RecordsPeriodContext.test.tsx` — переносятся на общий хук; ассерты политики истории обновляются с `replace` на `push` по решению Gate B, остальные остаются зелёными). Долгосрочно в кодовой базе остаются два паттерна URL-состояния (календарь и таблицы) — принято, точка пересмотра вне скоупа.

## Решение

### 1. Общий хук `useTableUrlState`

Владелец URL-состояния таблицы (frontend/admin, общий hooks-слой). Конфигурация на страницу — только имена, дефолты и типы значений из набора пресетов: `enum` (белый список), `int` (границы), `string` (максимум длины), `datePair` (пара `from`/`to` с семантикой частичной смены и инверсии), `arrayOf` (повторение параметра). Без Zod и иных схемных зависимостей.

Интерфейс: `state` — текущие значения всех параметров, выведенные из URL при рендере; `update(patch)` — единственный писатель.

- **Чтение**: строгий парсинг каждого параметра по пресету; невалидное значение → тихий фолбэк на дефолт, валидная часть URL сохраняется. Ограничения на разборе: строка ≤ 200 символов, массив ≤ 20 значений, `page` — целое 1…10⁴. Состояние выводится из URL синхронно при рендере — инициализация до первого запроса, инвариант «монтирование/deep-link = ровно один запрос» наследуется от #231.
- **Запись**: `update(patch)` атомарно меняет несколько параметров одной навигацией (смена фильтра и его обязательный сброс `page → 1` — всегда одна запись, не две). Параметры, равные дефолтам, из URL удаляются; неуправляемые хуком параметры (в т.ч. `clientId`) сохраняются при записи и на состояние не влияют. Быстрые последовательные записи коалесцируются (батчинг в пределах кадра) — защита от браузерных лимитов `pushState`. Все навигации — `{ scroll: false }` (клик по фильтру не прыгает к началу страницы).
- **История — везде `push`** (решение пользователя, Gate B 26.09): каждое взаимодействие пользователя с таблицей — переключение фильтра, сортировки, страницы, размера страницы, коммит поиска, смена периода — создаёт ровно один шаг истории. Кнопка «назад» предсказуемо отменяет последнее изменение таблицы, «вперёд» — повторяет. Смешение `push`/`replace` на одной странице отвергнуто: непонятно, что сделает «назад». Это заменяет политику #138 «правки фильтров — `replace`, не пачкать историю» на табличных страницах (включая период записей при порте в общий хук). Инвариант «одно взаимодействие = ровно одна запись» (дедуп: батч «фильтр + page→1» — один push; вспышка набора поиска в дебаунсе — один push) фиксируется тестом.
- **Служебные записи без пользователя — только `replace`** и только две: коррекция вышедшей за диапазон страницы (§2; будучи `push`, «назад» возвращала бы битую страницу и зацикливала коррекцию). Грязный URL при чтении не переписывается вовсе.
- **Черновик поля поиска**: локальный стейт `DataTable` (существующий дебаунс 300 мс, Enter — немедленный коммит). Коммит дебаунса/Enter — единственная запись `q`; адресная строка отстаёт от ввода не больше чем на дебаунс (ссылка всегда соответствует фактически выполненному запросу). При внешнем изменении URL (назад/вперёд, открытие ссылки) черновик ресинхронизируется со значением `q` из URL (эффект по примитивному значению; сегодня поле — снимок при монтировании, `DataTable.tsx:70`, — это чинится). Кнопка сброса поиска идёт через ту же запись `update({ q: дефолт })` — поле и URL не расходятся.
- Хук потребляется внутри Suspense-границы страницы (требование `useSearchParams` в Next 14).

### 2. Контракт параметров

- Имена — дословно канон API каждой страницы: `q`, `status`, `sort_by`, `sort_order`, `page`; фото — `tag_id` (повторением: `tag_id=1&tag_id=2`; элементы валидируются поэлементно, невалидные отбрасываются, дубли схлопываются, пустой массив — параметр отсутствует); записи — `from`, `to` (существующее отклонение, введённое #138) + `location_id`, `service_id`, `master_id`, `status`, `q`; журнал — `user_id`, `action`, `entity`, `date_from`, `date_to`; материалы (вложенная таблица страницы услуг) — префикс `mat_`: `mat_q`, `mat_status`, `mat_sort_by`, `mat_sort_order`, `mat_page` — оба набора фильтров живут в одном URL `/services`.
- **Пагинация в URL полностью** (решение пользователя, Gate B 26.09): `page` — целое 1…10⁴, пишется только при > 1; `per_page` — целый из белого списка селектора таблиц {10, 20, 50, 100}, дефолт страницы не пишется, невалидное значение — тихий фолбэк на дефолт. Ссылка восстанавливает и размер страницы, поэтому расхождение «страница указывает на другую строку набора» не возникает. Пустой `q` не пишется.
- `q` в URL хранит введённый текст; правило «серверный поиск только при ≥ 2 символах» остаётся на уровне сборки запроса (как сегодня). Следствие задокументировано: ссылка с односимвольным `q` открывает страницу с этим текстом в поле и без серверного фильтра — ровно как при ручном вводе одного символа.
- Сортировка: дефолт каждой страницы — сортировки нет (`sort_by` отсутствует, параметры сортировки на сервер не шлются — текущее поведение фабрики); невалидный или осиротевший `sort_order` без `sort_by` игнорируется. У журнала сортировка зафиксирована сервером — параметры сортировки им не управляются и в URL не пишутся.
- **Вышедший за диапазон `page`**: текущий авто-декремент по одному (шторм запросов на `?page=99`) заменяется одиночной коррекцией — при пустой странице и `page > 1`: если `total > 0`, одной служебной записью `replace` страница становится `ceil(total / per_page)`, если `total = 0` — сброс в дефолт. Одна корректирующая перезагрузка списка, не N, и ни одного шага истории. Корректная ссылка по-прежнему стоит ровно один запрос; коррекция — только для устаревших/кривых ссылок.
- **Грязный URL не переписывается**: невалидные значения молча заменяются дефолтами в состоянии, адрес остаётся как есть (нет канонизирующих записей без пользователя — нет второй навигации и второго запроса).
- Состояния загрузки/ошибки/пустого результата — существующее поведение `DataTable` (включая показ предыдущего набора строк на время запроса), миграция их не меняет; фильтр, под который 0 строк, показывает штатную пустую таблицу — для пользователя это неотличимо от «плохой» ссылки и ошибкой не является.

### 3. Интеграция с фабрикой `createPagedListContext`

Страница создаёт хук внутри своей Suspense-границы и передаёт его в фабрику как опциональную интеграцию (управляемый режим):

- при подключённом хуке поля `page`, `perPage`, `sortBy`, `sortOrder`, `status`, `search` и структурированные `filters` фабрики становятся управляемыми: значения берутся из `state` хука, собственные `useState` для них не создаются; `initialFilters` как отдельный шов упраздняется на мигрировавших страницах (хук выдаёт затравку тем же контрактам);
- все сеттеры фабрики (`setPage`, `setPerPage`, `setSort`, `setStatus`, `setFilters`, `setSearchWithReset`, авто-сброс `page → 1`) превращаются в вызовы `update(...)` — один атомарный батч на взаимодействие (смена размера страницы при `page > 1` сбрасывает страницу в 1 той же записью);
- авто-коррекция пустой страницы (§2) в управляемом режиме пишет служебной записью `replace` через хук;
- фабрика без интеграции работает как сегодня — страницы входят в волну по одной, промежуточных гибридов нет.

Deep-link клиентов: `?clientId=` остаётся отдельным параметром поверх фильтров (модальность ≠ фильтры). Эффективный статус при монтировании выводится правилом `status из URL ?? (присутствует clientId → 'all' : 'active')` — форс `status=all` в URL не пишется, запись без пользователя не выполняется. Если пользователь затем меняет статус — появляется обычная запись `status`. Хук управляет только своими параметрами: `clientId` при записях сохраняется.

### 4. Первая миграция: клиенты

Фильтры `q`/`status`/`sort_by`/`sort_order`/`page`/`per_page` переезжают в URL через хук; парсинг «параметры → затравка» на шове `initialFilters` переписывается на управляемый режим фабрики, остальная посадочная площадка #231 не меняется. Существующий e2e-счётчик «deep-link = ровно один запрос» остаётся зелёным — регрессионный замок миграции. Сброс фильтров = дефолты = URL без фильтров-параметров.

### 5. Волна (фаза 2)

Чеклист страниц, порядок от дешёвых к дорогим (меньше параметров — раньше; финальный порядок — план):

1. должности — `sort_by`/`sort_order`/`page` (поиска нет);
2. теги, локации — `q` + `sort_by`/`sort_order`/`page` (серверный поиск уже подключён);
3. услуги (+ вложенная таблица материалов с префиксом `mat_`) — `q` + `status`;
4. записи — недопериодные фильтры (`q`, `status`, `location_id`, `service_id`, `master_id`, сортировка, страница) через хук; период `from`/`to` портируется в хук тем же задачным шагом, `useRecordsPeriod` упраздняется (§Концепт);
5. сотрудники — одна страница управления (после #266); read-only экран `/masters` волной не трогается (фильтров нет);
6. фото — `q` + `tag_id` + `page`;
7. журнал действий (#344, страница появилась после формулировки issue; включена по канону «любая табличная страница», подтверждено пользователем на Gate B) — `user_id`/`action`/`entity`/`date_from`/`date_to` + `page` (+ `per_page` по общему правилу).

Каждая страница волны: подключение хука, **проверка/добавление Suspense-границы** уровня страницы (сегодня границы есть только у клиентов и записей; без неё статическая сборка падает), дым-тест. Правило волны: страница либо полностью на двусторонней схеме, либо не тронута (полуперемиграции «читаем, но не пишем» запрещены — состояние без пользователя, тестировать нечем).

Тестирование волны: общий параметризованный сценарий «открытие ссылки с фильтрами → состояние восстановлено, ровно один запрос списка» по всему чеклисту + точечные доп-сценарии на специфичное (массив `tag_id`, префиксы `mat_`, дискретные фильтры журнала, форс `status=all` у клиентов).

## User Scenarios

Каждый сценарий мапится на E2E-тест.

- **US-1 Шаринг ссылки (клиенты).** Администратор настраивает «поиск „анна“ + статус „все“ + страница 2», копирует адрес из строки браузера и отправляет коллеге; коллега открывает ссылку — таблица сразу в том же состоянии, список запрошен ровно один раз. → e2e: открытие URL с фильтрами + счётчик запросов списка (расширение существующего счётчика deep-link).
- **US-2 «Назад» отменяет последнее изменение таблицы.** Администратор переключает статус, листает страницы, набирает поиск — каждое взаимодействие создаёт ровно один шаг истории; кнопка «назад» пошагово возвращает предыдущие состояния таблицы, «вперёд» — повторяет их; посимвольной перемотки набора нет (вспышка ввода в дебаунсе = один шаг), двойных шагов от одного клика нет (фильтр + сброс страницы = одна запись). → e2e: клик по фильтру → «назад» → фильтр вернулся, страница та же; набор поиска с паузами → «назад» шагает по коммитам, не по символам.
- **US-3 Грязная ссылка не ломает страницу.** В присланной ссылке `status=xyz&page=0&sort_order=sideways&q=ма` — страница молча открывается с дефолтами по невалидным полям, валидный `q` применяется, адрес не переписывается; экрана ошибки нет. → e2e: dirty-URL → применены дефолты + `q`, URL не изменился.
- **US-4 Deep-link клиента поверх фильтров.** Ссылка `/clients?clientId=X&status=all` открывает карточку клиента поверх списка с фильтром; на монтировании ровно один запрос; закрытие карточки оставляет фильтры. → e2e: существующие deep-link-сценарии #232 остаются зелёными + комбинированный сценарий `clientId` × фильтры.
- **US-5 Волна: любая таблица восстанавливается ссылкой.** На каждой странице чеклиста ссылка с её фильтрами открывает страницу в нужном состоянии одним запросом; устаревшая страница (`page` за диапазоном) один раз корректируется на последнюю валидную. → e2e: параметризованный прогон по чеклисту + точечные доп-сценарии §5.

## Границы (явно НЕ делаем)

- Полуперемиграции «читаем из URL, но не пишем» — страница либо на полной схеме, либо не тронута.
- Перенос в URL состояний, не являющихся фильтрами (выбранные строки, открытые модалки) — кроме deep-link `?clientId=`.
- Смешение `push`/`replace` в пользовательских записях одной страницы (все — `push`; `replace` — только служебная коррекция страницы).
- Переписывание `useScheduleView` (расписание вне волны; его смешанная политика #138 остаётся как есть).
- Отдельный дизайн/спека на каждую страницу волны.
- Изменения backend: имена параметров URL уже совпадают с каноном API.
- Выравнивание девиаций `RecordsContext`/`PhotosContext` от фабричной формы (их касается только точка подключения хука).
- Канонизация грязных URL записью без пользователя.

## Тестирование

- vitest: пресеты парсеров (валид/невалид/дефолт-фолбэк, капы длины/массива, белый список `per_page`, поэлементная валидация массива), сериализация (дефолты не пишутся, неуправляемые параметры сохраняются, атомарный батч «фильтр + page→1»), коалесценция быстрых записей, `{ scroll: false }`, StrictMode-двойной рендер без второй записи/запроса.
- e2e: US-1–US-5, включая «одно взаимодействие = один шаг истории» и служебную коррекцию страницы без шага; регресс — существующие счётчики запросов расписания/записей/клиентов не меняют чисел; тесты периода записей переносятся на общий хук (ассерты политики истории обновляются с `replace` на `push`).
- Дым на каждую страницу волны (открытие ссылки с фильтрами).

## Решения Gate B (26.09, пользователь)

1. **История — везде `push`**: смешение `push`/`replace` на одной странице делает кнопку «назад» непредсказуемой — все пользовательские записи табличных страниц единообразно создают шаг истории. Решение заменяет политику #138 «правки фильтров — `replace`» на табличных страницах (в том числе период записей при порте в общий хук). Принятое следствие: после N взаимодействий уход со страницы кнопкой «назад» стоит N нажатий.
2. **Журнал действий — в волне** (подтверждено; последний пункт чеклиста).
3. **Пагинация в URL полностью**: и номер страницы, и размер (`per_page` из белого списка селектора) — ссылка восстанавливает набор строк без расхождений.
