## 1. Контекст: что уже стоит и чего не хватает

Сегодня у 5 архивируемых сущностей (staff, locations, services, materials, clients):

- **Бэкенд — двухформенный контракт #207** (`backend/src/api/v1/clients.py:192-238` и зеркала в `staff.py:350-412`, `locations.py`, `services.py`, `materials.py`): голый DELETE → `collect_dependencies` → 409 `has_dependencies` + дерево (есть зависимости) **или 204 — строка удаляется сразу** (ветка «исполнить-если-чисто»); DELETE с телом `{resolutions}` → исполнение. `?dry_run` и `expected` у этих роутов **нет**.
- **Фронт — мгновенное удаление.** `DeleteDialog.tsx` (Mode A: выбор действий + confirm-чекбокс; Mode B: «Архивировать вместо») открывается от 409-дерева голого DELETE; после подтверждения мутация (`useStaffMutations.ts:56-62` и зеркала) исполняет DELETE с `{resolutions}` сразу. PendingActions-конвейер (кольцо 5 с, undo) для этих 5 сущностей не задействован (`DeleteDialog.tsx:27-30`: отложенная схема только у activity и tag).
- **«В архив»/«Восстановить»** — отдельные POST-роуты, обратимы, в контракт удалений не входят и **не меняются вовсе** (этот скоуп закрыт навсегда).

Канон уже предписывает целевое состояние: `docs/domain-rules/deletion.md` — «Действие „удалить“ у ЛЮБОЙ сущности выполняется только через единый отложенный контракт», строка таблицы Staff/Location/Service/Material/Client — «отложенный контракт; фаза 3 (follow-up)». #345 — исполнение этой строки.

**Факты о матрице зависимостей, определяющие форму флоу** (`domain/deletion.py:166-289`):

- В дерево 409/превью входят **и auto-узлы** с ненулевым счётчиком (`collect_dependencies:1051-1073`): у сотрудника с картой ведущего всегда есть узел `masters` (extension-строка 1:0..1), у услуги — `tariffs`, у клиента — `client_tags`/`photos`. «Чистая» ветка (пустое дерево) у каждой сущности достижима, но у занятых связями строк дерево почти никогда не пусто.
- **Non-auto зависимости (те, что показывает выбор):** Client — `records` (только nullify) и `visitors` (только cascade); Staff/Location/Service — только `activities` с `allowed_actions=[]` (**блок**: выбор запрещён, единственный путь — архив); Material — non-auto зависимостей **нет** (`service_materials` — auto).
- **Сверка expected игнорирует auto-узлы** (`stale_expected_entities:1351-1352`): auto-связи пользователь не подтверждает, их изменение за окно — не гонка.

| Сценарий | Сегодня | После #345 |

Отменить» с кольцом 5 с; commit после окна: DELETE `{resolutions, expected}`; undo возвращает строку без серверных вызовов |
| Строка без выбора (чистая или только auto-связи: материал с услугами, сотрудник-админ) | 204 мгновенно или диалог с информационными auto-строками → мгновенно | превью `?dry_run=true` → 204 или 409 (только auto-узлы) → диалог с информационными строками + confirm → кольцо; commit = DELETE `{expected: {}}` |
| Заблокированная строка (сотрудник/локация/услуга с занятиями) | диалог «Архивировать вместо», удалить нельзя | **без изменений** (Mode B), кроме источника дерева — dry_run вместо голого DELETE |
| Голый DELETE (API мимо фронта) | 204 при чистой строке (тихое исполнение!), 409 при занятой | **422 `expected_state_required` всегда**, включая тело без `expected` и неизвестный id (форма раньше probe) — ветка execute-if-clean упразднена; превью — только `?dry_run=true` |
| Зависимость появилась, пока открыт диалог/окно отмены | молча удаляется вместе со строкой | commit → 409 `stale_dependencies` → строка вернулась, тост «Не удалось удалить: данные изменились» + «Обновить» |
| 404 после commit (строку удалил другой) | ошибка | тихий успех (общий контракт #285 D4) |
| «В архив»/«Восстановить» | отдельные POST-роуты | **без изменений** |

Главный выигрыш — **безопасность**: сверка ожидаемого состояния (защита от гонки «диалог показал одно, сервер уже другое») и упразднение последнего молчаливо-разрушительного пути.

## 3. Решение Gate A (единственный концепт)

**Концепт: каждая из 5 сущностей становится полным участником семейного контракта** — флейвор #318 (теги) один-в-один, фронт — отложенная схема #285. Это не выбор из альтернатив, а прямое следствие двух зафиксированных решений: семейное правило #318 rev9 («любое удаление „навсегда“ — один флоу; голой формы DELETE в семье нет вообще») и дословный скоуп issue.

Отвергнутые подходы (по каким правилам отсеяны):

1. **«Только кольцо на фронте, без expected»** (минимальный diff поверх сегодняшнего контракта) — нарушает семейное правило rev8/rev9 (у каждого DELETE семьи обязательное тело `{expected}`, голой формы нет) и дословный скоуп issue; оставляет гонку окна нерешённой.
2. **«Сохранить execute-if-clean для чистых строк»** — нарушает скоуп issue («отмена execute-if-clean») и семейное правило.
3. **«Своя форма превью для архивируемых»** (оставить 409 голого DELETE как превью) — переизобретение `?dry_run=true`, готового механизма (#285/#318/#324).

Открытых развилок для пользователя нет: HTTP-контракт, схема данных и видимое поведение полностью определяются референсом. Различие с тегами только в наполнении: у 5 сущностей **смешанные действия (nullify/cascade) и blocked-зависимости** — матрица потоков в §4.4.

## 4. Backend: контракт каждого из 5 роутов

Контрактные ветки живут **в роутере** (зеркало `records.py:297-364`, `tags.py:216-300`); для staff — в сценарии (см. «Владение транзакцией»).

### 4.1 Формы запроса и комбинаторика (зеркало `tags.py:268-282`)

1. **`?dry_run=true`** — чистое неразрушающее превью: существование probe → 404; `collect_dependencies` → пусто → **204** без удаления; непусто → **409** `{detail: "has_dependencies", dependencies: [дерево: счётчики + items + cascade_preview]}`.
2. **Голый DELETE упраздняется:** без флага и без тела → **422** `expected_state_required`. Тело **без `expected`** (только `resolutions` или только неизвестные ключи) — тот же 422 (отвергнутая легаси-форма, `tags.py:254-256`). Проверка формы предшествует probe: неизвестный id тоже получает 422, не 404.
3. **DELETE с телом `{resolutions?, expected}`** — отложенный commit: probe существования → `collect_dependencies` → **subset-сверка `expected`** (`stale_expected_entities:1321`: `set(now_ids) ⊆ set(expected[entity])` по каждому non-auto узлу; 409 `stale_dependencies` с живым деревом; исчезнувшая за окно зависимость не блокирует, появившаяся — блокирует; обмен ловится — новый id не входит в подтверждённое множество) → валидация `resolutions` (занятая зависимость без действия/с недопустимым действием → 422; blocked-зависимость при любом теле → 422; неизвестные ключи тела молча игнорируются) → исполнение → 204; неизвестный id → 404.
4. **`?dry_run=true` + тело с `resolutions` → 422** `dry_run_with_resolutions_forbidden` (до probe); `dry_run` + expected-only тело — молча игнорируется.

### 4.2 Семантика expected

- `expected` несёт **id-множества подтверждённых non-auto зависимостей**; auto-узлы в сверке не участвуют (пользователь их не подтверждает — `stale_expected_entities` пропускает). Смешанные действия (nullify/cascade) на состав expected не влияют.
- `expected` строится фронтом из **полного дерева ответа** (все `items` каждого узла), а не из отрисованных строк — рендер урезает до 10 + «и ещё N», payload несёт все id (унаследовано у #318).
- Пейлоад не ограничен (клиент с тысячами посетителей несёт все id) — осознанный наследуемый компромисс семейства #285/#318, здесь не пересматривается.

### 4.3 Коллекторы (точный состав)

Сегодня `_ID_COLLECTORS`/`_ITEM_COLLECTORS` (`deletion.py:1209`, `:933`) покрывают только Record/Activity/Tag. Новые ключи:

| Ключ | ID | items | Зачем |
|---|---|---|---|
| `(Client, "records")` | да | да | источник expected из диалога (записи клиента, nullify) |
| `(Client, "visitors")` | да | да | источник expected из диалога (посетители, cascade) |
| `(Staff, "activities")` | да | **нет** | гейс expected-сверки: без коллектора гонка «появилось занятие за окно» у чистого на момент диалога сотрудника ловится не 409 stale, а 422 blocked |
| `(Location, "activities")` | да | нет | то же |
| `(Service, "activities")` | да | нет | то же |

- Material — новых ключей **не требует** (non-auto зависимостей нет).
- **items для activities-узлов не вводим:** blocked-узел никогда не подтверждается (путь архива), expected из него не строится; 409 stale-дерево для этих сущностей показывает счётчики — зафиксированная граница.
- Билдеры меток зеркалят готовые: записи — дата-однострочники (образец билдера `(Activity, "records")`), посетители — имя (образец `deletion.py:629-652`; nullable → fallback «Аноним»). PII-граница #285 D9: **без телефонов**; pytest-тест на отсутствие телефонных подстрок в items (§7).
- Фабрика коллекторов вместо ручных пар — решение плана (прецедент разрешения в #318).

### 4.4 Матрица потоков по сущностям (следствие п.1 §1)

| Сущность | Чистая (204) | Диалог | commit |
|---|---|---|---|
| Client | возможна | Mode A: записи (nullify) + посетители (cascade) + информационные auto-строки; узел посетителей несёт `cascade_preview` счётчик визитов | `{resolutions, expected}` — **единственная сущность с разрешимым commit** |
| Staff | возможна (у обычного сотрудника; у ведущего дерево не пусто из-за `masters`) | занятия есть → **blocked → только Mode B**; занятий нет → информационные auto-строки + confirm | `{expected: {}}` |
| Location / Service | возможна | то же (blocked / all-auto) | `{expected: {}}` |
| Material | возможна | только информационные auto-строки + confirm (blocked-состояния нет) | `{expected: {}}` |

Commit с непустым `resolutions` завершается успехом **только у клиента**; 422/409-ветки остальных — контракт для API-потребителей и гонок (S6/S5). Mode B («Архивировать вместо») достижим только у staff/location/service — единственных с blocked-зависимостью; у клиента и материала не показывается.

### 4.5 Владение транзакцией сверки

«Сверка и исполнение — одна транзакция» означает: сверка живёт в держателе транзакции исполнения.

- **staff** — сценарий `delete_staff` (`usecases/staff.py:463`, #326) получает параметр `expected` и выполняет сверку внутри своей транзакции — зеркало `delete_record` (`usecases/records.py:419`, принимает `resolutions` + `expected`). Роут сохраняет транспорт: формы, 404/422-маппинг, превью-ветку.
- **clients** — сценарий `delete_client` (`usecases/clients.py:74`, `@transactional`; #327 смержен 27.09) получает параметр `expected` и выполняет сверку внутри своей транзакции — тот же шаблон, что у staff; роут сохраняет транспорт: формы, 404/422-маппинг, превью-ветку. Бывший исполнитель `ClientService.resolve_delete` разобран #327.
- **services / locations / materials** — сверка в роутере в рамках session-запроса, исполнение через `GenericService._resolve_delete_core` (`generic.py:273-331`) — зеркало тегов.

## 5. Frontend: перевод обоих путей на PendingActions

Для каждой из 5 сущностей (таблица + `ClientCardModal` для клиента):

1. **api-client:** новые `dryRunDeleteX(id)` (зеркало `dryRunDeleteRecord`, `endpoints.ts:622-638`); `resolveDeleteX` меняет payload с `{resolutions}` на `{resolutions?, expected}` (зеркало `resolveDeleteTag`/`resolveDeleteRecord`). Голые `deleteX` этих 5 сущностей теряют последнего потребителя (сегодня — зонд превью в мутациях) и **удаляются** (линт-нулевая гигиена #301); IMPL-открывает grep-аудит оставшихся вызовов (e2e, скрипты).
2. **Хук `useDeleteX`** (перестройка `useStaffMutations.ts` и зеркал по образцу `useDeleteTag`/`useDeleteRecord`): первый вызов всегда `dryRunDeleteX(id)`; 204 (чистая) → optimistic-удаление + enqueue с commit `resolveDeleteX(id, {expected: {}})`; 409 + `err.dependencies` → состояние `dependencies` → `DeleteDialog` → confirm → optimistic-удаление + enqueue с commit `resolveDeleteX(id, {resolutions, expected})` — expected из **полного** дерева ответа (помощник `expectedFromDependencies`; сегодня он дублируется в `useDeleteRecord`/`useDeleteTag` — план может свернуть в общий модуль). `delayMs: 5000`. Инвалидации — только в commit; undo — без серверных вызовов.
3. **Фаза превью (новое, решение панели):** кнопка удаления в состоянии загрузки (disabled/spinner) на время dry_run — двойной клик даёт один запрос; **404 на dry_run** → тихая инвалидация семьи (строка уйдёт при refetch), диалог не открывается, тостов нет; **сеть/5xx на dry_run** → error-тост «Не удалось проверить зависимости», состояние страницы не меняется.
4. **Ошибки commit** — общий пайплайн #285 D4: 404 = тихий успех (тост конвейера не превращается в ошибку, строка не возвращается); 409 `stale_dependencies` → undo + тост «Не удалось удалить: данные изменились» + действие «Обновить» (инвалидация семьи сущности и точечного ключа модалки клиента); 422 → undo + error-тост (из UI недостижимо: заблокированный путь ведёт в архив, допустимость действий проверяется диалогом); сеть → undo + error-тост. Поведение undo при refetch/SSE в окне — наследуется конвейером, нового нет.
5. **`DeleteDialog`** — логика Mode A/B не меняется; источник дерева переходит с 409 голого DELETE на 409 `dry_run`; рендер items-строк уже общий после #318 (заголовок группы + до 10 строк + «и ещё N»); `cascade_preview`-счётчик узла посетителей рендерится как сегодня. Тосты — pending-стек конвейера («Удалено. Отменить» с кольцом), не success-тост.
6. **e2e-спеки, зовущие удаление напрямую** (`materials-delete`, `clients-delete-cascade`, `clients-delete-invalid-resolution`, `staff-delete-blocked`, `staff-delete-auto-cascade`), переписываются на новый поток (dry_run → диалог → commit).

## 6. User Scenarios

- **S1. Занятый клиент через диалог.** Админ жмёт «Удалить» у клиента с записями и посетителями: dry_run → 409 с деревом; диалог показывает поимённые строки (записи — даты, посетители — имена, до 10 + «и ещё N») и счётчик визитов посетителей; confirm → строка исчезла, тост с кольцом «Удалено. Отменить»; окно прошло → commit `{resolutions, expected}` → 204; в БД клиент удалён, записи отвязаны, посетители удалены. *(pytest-контракт + e2e: переписанный `clients-delete-cascade.spec.ts`)*
- **S2. Строка без пользовательских решений.** (а) Чистая локация: dry_run → 204 → кольцо → commit `{expected: {}}`. (б) Материал с привязками к услугам: dry_run → 409 (только auto-узел) → диалог с информационными строками + confirm → кольцо → commit `{expected: {}}`. *(pytest + e2e: `materials-delete.spec.ts` переписан)*
- **S3. Undo в окне.** В течение 5 с после confirm админ жмёт «Отменить»: строка вернулась, серверных DELETE не было. *(vitest хука + e2e)*
- **S4. Заблокированная строка — только архив.** Сотрудник с занятиями: dry_run → 409 с blocked-узлом → диалог «Архивировать вместо» (primary) → архивный POST без кольца; delete-ветка из UI недостижима. *(e2e: `staff-delete-blocked.spec.ts` дополнить)*
- **S5. Гонка окна — expected-сверка.** Между confirm и commit у клиента появилась новая запись (через API): commit → 409 `stale_dependencies` → строка вернулась, тост «Не удалось удалить: данные изменились» с «Обновить»; клиент и новая запись живы. Обратная гонка (зависимость исчезла за окно) commit не блокирует. У сотрудника-ведущего появление занятия за окно у чистого на момент диалога — тоже 409 (не 422). *(pytest subset-юниты — зеркало D7 #285)*
- **S6.
