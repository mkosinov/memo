# #397 — Страж ухода со страницы во время окна отмены (beforeunload на конвейере отложенных удалений)

Статус: draft rev2 (Gate B ждёт ОК пользователя; rev2 — правки по панели 27.09).
Источник: issue #397; спека #345 §8 п.4 (закрытие вкладки в окне кольца = тихая отмена); решение пользователя 27.09 — серверный перенос окна отклонён, выбран страж ухода.

## 1. Контекст и проблема

Отложенное удаление исполняет живая страница: пользователь подтверждает удаление, 5 секунд видит тост с кольцом отсчёта и кнопкой «Отменить», по истечении окна конвейер отправляет DELETE на сервер. Конвейер — один общий компонент на уровне приложения (`PendingActionsProvider`), через него идут удаления записей, визитов, оплат, занятий и тегов; #345 подключает к нему же 5 архивируемых сущностей и страж наследует автоматически.

Пробел: если во время окна отмены закрыть вкладку или перезагрузить страницу, таймер умирает вместе со страницей — DELETE никогда не уходит на сервер. Пользователь подтвердил удаление, «Отменить» не нажимал, а после возврата на страницу строка на месте. Удаление отменено молча, без согласия пользователя.

Замечание скаута (27.09): стражи ухода в приложении уже есть — хук `useUnsavedChangesGuard` (введён в #141 как страж грязных форм, сегодня подключён в Topbar на время сохранения расписания — единственный живой потребитель). Пробел именно в том, что конвейер отложенных удалений стража не ставит.

## 2. User Scenarios

Каждый сценарий мапится на автотест (vitest или e2e — указано у сценария).

- **С1. Спокойное удаление.** Пользователь подтверждает удаление записи, не уходит со страницы, окно дотикало — удаление выполнилось. Страж вёл себя незаметно: диалог не показывался ни до постановки в конвейер, ни после его опустевания. → vitest (страж снят после завершения отправки).
- **С2. Перезагрузка в окне — «Остаться».** Пользователь удаляет визит и в течение окна жмёт F5. Браузер показывает штатное подтверждение. Пользователь остаётся — окно дотикало, удаление выполнилось. Страж остаётся на посту: вторая попытка уйти в том же окне снова спросит. → vitest.
- **С3. Перезагрузка в окне — «Покинуть».** То же, но пользователь подтверждает уход — удаление отменено, после загрузки строка на месте. Отмена произошла с явного согласия пользователя (диалог браузера). → e2e (best-effort, предусловия в §7).
- **С4. Кнопка «Отменить» в тосте.** Пользователь удаляет оплату и тут же жмёт «Отменить» в тосте — страж снят сразу, последующий уход не спрашивается. → vitest.
- **С4а. Позднее «Отменить» (после истечения окна).** Клик «Отменить» пришёл, когда окно уже истекло и отправка летит — клик ни на что не влияет (существующая семантика #285 rev8): страж остаётся, пока отправка не завершится. → vitest.
- **С5. Уход во время отправки удаления (узкое окно).** Окно дотикало, запрос DELETE уже летит, пользователь закрывает вкладку. Страж ещё стоит: «Покинуть» — запрос может не долететь, безопасный исход «не удалять» (строка вернётся); «Остаться» — запрос завершится. → vitest. (Допущение поверх буквального текста issue — см. §8.)
- **С6. Несколько отложенных удалений.** Пользователь удаляет две записи подряд; страж стоит, пока не завершатся обе (коммиты или отмены). Одно подтверждение ухода в браузере закрывает вопрос сразу для всех незавершённых: «Покинуть» отменяет их все с согласия. → vitest.
- **С7. Навигация внутри приложения.** Пользователь удаляет тег и в окне отмены переходит на другую страницу админки (меню сайдбара). Диалог НЕ показывается: конвейер живёт на уровне приложения и переживает смену страницы, удаление выполнится. → vitest (страж не ставится при SPA-навигации — она beforeunload не возбуждает; сценарий фиксирует намеренное отсутствие перехвата).
- **С8. Истечение сессии в окне (принудительный редирект).** Пока окно отмены открыто, сервер отвечает 401 — слой авторизации принудительно уводит на страницу входа (полный переход на /login). Диалог НЕ показывается: уход навязан системой, а не пользователем; отказ в диалоге оставил бы пользователя запертым на странице, где каждый запрос отвечает 401. Удаление отменяется тихо (безопасный исход «не удалять»). → vitest (страж пропускает навигацию, помеченную как принудительная).

## 3. Behavioral Delta (что меняется для пользователя)

| Ситуация | До | После |
|---|---|---|
| Закрытие вкладки/перезагрузка в окне отмены (5 с) | Тихая отмена: строка возвращается без согласия пользователя | Браузер показывает штатное подтверждение; «Покинуть» = отмена с согласия, «Остаться» = окно дотикает, удаление выполнится; страж остаётся и спросит повторно при следующей попытке |
| Уход во время отправки DELETE (после окна) | Тихий исход неизвестности: запрос оборвался — строка вернётся | То же окно подтверждения; безопасный исход сохраняется |
| Несколько незавершённых удалений и уход | — | Одно подтверждение браузера: «Покинуть» отменяет их все с согласия |
| Истечение сессии в окне (401 → /login) | Тихая отмена | Тихая отмена, диалог не показывается (навигация навязана системой) |
| Окно отмены вне ухода | Без изменений: тост, кольцо, «Отменить» | Без изменений |
| Уход вне окна отмены (конвейер пуст) | Без диалога | Без диалога — страж снят, не надоедает |
| Навигация по страницам админки в окне | Конвейер переживает навигацию, удаление выполнится | Без изменений (диалог намеренно не ставится) |

Семантика после правки: тихая отмена возможна только по явному согласию в браузерном окне, по навязанному системой уходу (истечение сессии) либо по форс-мажору (краш браузера, выключение питания — там безопасный исход «не удалять» сохраняется намеренно). Сон ноутбука не участвует: страница переживает сон, таймер продолжается после пробуждения.

## 4. Концепт

**Выбран:** страж внутри общего конвейера, переиспользованием готового механизма. `PendingActionsProvider` вместе с картой таймеров ведёт реактивный счётчик незавершённых действий; пока счётчик больше нуля, провайдер подключает существующий хук `useUnsavedChangesGuard` (тот же, что уже сторожит сохранение расписания в Topbar). Хук ставит `beforeunload`-обработчик только на время активности и снимает его при опустевании конвейера — вне 5-секундных окон страница не затрагивается (ограничение bfcache уже задокументировано в хуке).

Отбракованные варианты:
- **Серверный перенос окна** (таймер на сервере) — отклонён пользователем 27.09: усложнение контракта ради редкого случая.
- **Страж в каждом потребителе конвейера** (записи, визиты, теги…) — размазывает гарантию по N местам, новое подключение сущности (#345 и будущие) обязано не забыть страж; нарушает скоуп «один компонент».
- **Перехват SPA-навигации** — не нужен: конвейер на уровне приложения переживает смену страницы, таймер дотикает и удаление выполнится; перехват только добавил бы диалоги без пользы (см. С7).
- **Полный редьюсер, владеющий и картой таймеров, и счётчиком** — надёжнее от рассинхрона, но переписывает стабильное ядро #285 ради правки на десяток строк; вместо этого счётчик ведётся отдельным состоянием с одним функциональным обновлением на каждый переход (см. §5.1).

## 5. Технический дизайн

### 5.1 Источник истины «есть незавершённые действия»

Сейчас состояние конвейера живёт в `useRef`-карте таймеров (`timersRef`) — она не вызывает перерисовок, и на неё нельзя подписать эффект стража. Вводится отдельное реактивное состояние — счётчик пар `{ ожидающие, отправки }` (один `useState`-объект), обновляемый **функционально** (от предыдущего значения, по одному обновлению на переход — два изменения в одном переходе никогда не дают мгновенный ноль и не мерцают стражем):

- постановка в конвейер (enqueue) нового действия → `ожидающие + 1`;
- повторная постановка того же id (дедупликация: старый таймер отменяется, создаётся новый) → **нетто-ноль** — переход отсутствует; это обязательное правило, иначе счётчик уплывает навсегда (id стабильны на сущность: `delete-record-${id}` — путь достижим повторным удалением после возврата строки рефретчем в том же окне);
- отмена кнопкой «Отменить» по защищённому пути (запись в карте ещё есть) → `ожидающие − 1`;
- истечение окна (один объединённый переход) → `ожидающие − 1`, `отправки + 1` — запись из карты удаляется до старта отправки (семантика #285 rev8 сохраняется);
- завершение отправки → `отправки − 1` — **одна точка декремента на любой исход** (успех; 404-тихий успех; ошибка с обработчиком потребителя; ошибка с откатом и тостом по умолчанию): в обработчике ошибок две ранние ветки возврата, декремент должен стоять так, чтобы их нельзя было пропустить — сетевой сбой без декремента оставил бы диалог навсегда.

Страж активен, пока **суммарный счётчик > 0** — либо есть ожидающие окна, либо отправки в полёте; это честная семантика «незавершённое действие» из issue: подтверждённое удаление либо исполнится, либо будет отменено явно, в любом моменте своей жизни в конвейере. Инвариант: `ожидающие = записи в карте таймеров`, `отправки = выполняющиеся сейчас коммиты`.

С4а (защищённый путь отмены): клик «Отменить» после истечения окна — существующий no-op, декремента нет; счётчик держится на `отправках` до завершения.

Незавершённые отправки не повторяются и не возвращаются в конвейер (как и сегодня): ошибка завершает действие — откат и тост по умолчанию либо обработчик потребителя.

### 5.2 Подключение стража

В теле провайдера: `useUnsavedChangesGuard(hasPending)`, где `hasPending` — суммарный счётчик больше нуля. Сам хук не меняется: его контракт («подключить обработчик, пока dirty; снять при очищении и размонтировании») совпадает дословно — проверено по его 19 строкам и существующему тесту. Регистрация происходит внутри эффекта, т.е. только на клиенте после гидрации — SSR-рассогласований нет. Путь импорта `@/hooks/useUnsavedChangesGuard` из контекста циклов не создаёт (хук зависит только от react).

Множественные `beforeunload`-обработчики в приложении (конвейер + Topbar) сосуществуют независимо: в современных браузерах показывается один диалог, если хотя бы один обработчик попросил подтверждение (единственный живой потребитель хука сегодня — Topbar; «грязные формы» из исходного замысла #141 в коде не подключены). Десктопный Safari требует предварительного взаимодействия пользователя со страницей — в нашем сценарии оно всегда есть (клик удаления); мобильный Safari ненадёжен — см. §6.

### 5.3 Принудительные полные переходы (классификация)

`beforeunload` возбуждается не только закрытием вкладки, но и программными полными переходами. В приложении их два:

- **Истечение сессии (401 → /login)** — навязанный системой уход. Диалог здесь вреден: отказ запирает пользователя на странице, где каждый запрос отвечает 401. Страж пропускает такую навигацию: перед полным переходом слой авторизации ставит признак принудительной навигации в крошечный отдельный модуль (`lib/forcedNavigation.ts`: установить флаг / прочитать флаг), обработчик стража видит признак и не просит подтверждения. Удаления при этом отменяются тихо — безопасный исход «не удалять».
- **Кнопка перезагрузки на полноэкранном экране ошибки** — инициирована пользователем; диалог честен («Покинуть?» = согласие отментить). Правок не требуется; если авария размонтировала дерево вместе с провайдером, страж уже снят очисткой эффекта. Размонтирование провайдера в проде не происходит (уровень приложения); в тестах и HMR обработчик снимается очисткой эффекта хука, поведение отправок при размонтировании не меняется (как сегодня).

### 5.4 Что не меняется

- Контракты `PendingAction` (id, commit, undo, onError), порядок «запись из карты удаляется до коммита» (#285 rev8), обработка ошибок коммита (#243: 404-тихий успех, ветка 5 deletion.md).
- Потребители (хуки удалений записей/визитов/оплат/тегов, занятия) — нулевые правки: страж наследуется всеми сущностями, включая 5 архивируемых из #345, автоматически.
- Серверная часть — нулевые правки.

## 6. Ограничения платформы (принятые)

- **Текст диалога штатный.** Современные браузеры показывают стандартную формулировку («Покинуть сайт?…»), свой текст не поддерживается — принято в issue как ограничение платформы.
- **Мобильный Safari** возбуждает `beforeunload` ненадёжно (может не показать диалог). Админка десктопная — принято как известное ограничение, безопасный исход «не удалять» сохраняется. Десктопный Safari требует пользовательского взаимодействия перед диалогом — в сценарии удаления оно всегда есть.
- **Форс-мажор** (краш браузера, выключение питания): диалог невозможен, удаление молча не исполнится — безопасный исход, зафиксирован в issue как намеренный.
- **bfcache:** постоянный `beforeunload`-обработчик выкидывает страницу из кэша назад/вперёд; хук уже подключает обработчик только на время активности — вне окон отмены и отправок конвейер страницы не касается.

## 7. Тестирование

- **vitest — основной уровень** (файл `__tests__/PendingActionsContext.test.tsx` расширяется). Основные утверждения — шпионы `addEventListener`/`removeEventListener` (паттерн уже существует в `__tests__/useUnsavedChangesGuard.test.tsx`); синтетическая отправка отменяемого `beforeunload`-события с проверкой `defaultPrevented` — дополнительное утверждение (jsdom сам `beforeunload` при выгрузке не возбуждает):
  - страж поставлен при постановке в конвейер; снят, когда оба счётчика пусты (все исходы);
  - дедупликация повторной постановки того же id — нетто-ноль: счётчик не раздувается, страж не залипает;
  - снятие стража на каждом исходе отправки: успех; 404-тихий успех; ошибка по умолчанию (откат + тост); ошибка с обработчиком потребителя (путь `staleAwareOnError`);
  - поздний клик «Отменить» после истечения окна (С4а): декремента нет, страж держится до завершения отправки;
  - страж держится, пока отправка в полёте (С5), и при двух незавершённых действиях (С6);
  - сосуществование: второй подключённый страж (как в Topbar) и страж конвейера не мешают друг другу — единый диалог на один уход это поведение платформы, наше — только отсутствие конфликта обработчиков;
  - принудительная навигация (С8): при установленном признаке `beforeunload` не подтверждается (`defaultPrevented === false`).
  - Если e2e-файл на этапе IMPL решено не заводить (граница ниже), минимальный пол всё равно фиксирует, что страж реально просит подтверждение: синтетическая отправка отменяемого события при незавершённом действии обязана давать `defaultPrevented === true`.
- **e2e — best-effort** (нативный диалог Chromium управляется из Playwright). Детерминированные предусловия прогона: обработчик `page.on('dialog')` зарегистрирован ДО действия; диалог гарантируется пользовательским жестом (клик удаления — он и есть жест); путь закрытия вкладки — `page.close({ runBeforeUnload: true })`, путь перезагрузки — `page.reload()` с принятым диалогом. Сценарий С3: постановка удаления, уход в окне, принять диалог → строка вернулась; отклонить → после окна строка исчезла. Если прием окажется хрупким/флеймовым на нативном диалоге — граница фиксируется: vitest-покрытие (с полом из предыдущего пункта) считается достаточным, e2e-файл не заводится. Решение принимается на этапе IMPL по факту прогона, без возврата к дизайну.

## 8. Открытые вопросы / допущения

- **Покрытие «отправок в полёте» стражем (С5)** — допущение поверх буквального текста issue (там «окно отмены»); узкое окно в доли секунды, но семантически тот же класс пробела, что и исходный. Панель простоты предлагает вынести из скоупа; честность семантики «незавершённое действие» — за покрытие. Решение за пользователем на Gate B; снимается одной строкой (минус С5 и точка «отправки» в счётчике).
- Зависимостей от #345 нет (её план не трогает конвейер); порядковое слияние любое — страж покрывает whoever уже в конвейере.
