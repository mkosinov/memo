# Спека: #368 — мёртвые props: `mode` в модалках справочников, `value` в RemoteSearchSelect

Дата: 2026-09-27 (rev2 — правки панели 6/6). Issue: [#368](https://github.com/mkosinov/memo/issues/368). Зависимости: #301 (смержена).
Тип: chore, фронтенд (frontend/admin), поведение пользователя не меняется.

## 1. Контекст и проблема

При спуске линт-порога (#301) обнаружены параметры, объявленные в контрактах фронтовых компонентов, но не используемые самими компонентами. В #301 они заглушены `_`-префиксом (контракты не трогались); этот issue — решение по существу.

Две группы:

1. **`mode` в пяти модалках справочников** (`LocationModal`, `PositionModal`, `MaterialModal`, `ServiceModal`, `TagModal`): параметр «создание или редактирование» принимается и полностью игнорируется. Фактическое различие режимов — по наличию редактируемой сущности (prop сущности пуст при создании и заполнен при редактировании). Ни одна из пяти модалок `mode` не читает.
2. **`value` в `RemoteSearchSelect`** (общий селект с поиском по серверу): контракт объявляет «управляемое» значение — внешний код сообщает компоненту текущий выбор, — но компонент игнорирует его полностью: отображение строится только из внутреннего состояния (подпись выбранного варианта либо текст поискового запроса).

Последствия сегодня:
- вызовы передают `value`, создавая ложное впечатление управляемости;
- места, которым нужен внешний сброс, решают это пересозданием компонента с нуля через смену React-ключа — таких обходов два независимых: сброс фильтров на странице фото (`resetKey`) и пересоздание поля в модалке фото (`fieldRemount`);
- пикеры тегов (в фильтрах фото, модалке услуги, модалке фото — паттерн #328) передают фиктивную пару `value={null}` + `onChange={() => {}}`, а выбор получают через опциональный `onSelectItem` — та же ложь контракта.

## 2. Решение (Gate A, выбор пользователя 2026-09-27)

Вариант **A — «честный неуправляемый»**:

- `mode`: удалить из контракта и всех вызовов пяти модалок. Поведение не меняется — параметр никем не читался.
- `value`: удалить из контракта `RemoteSearchSelect` и всех вызовов. Пересоздание компонента по ключу признаётся **штатным механизмом** внешнего сброса/подмены для неуправляемого селекта (стандартный приём React для самостоятельных компонентов), а не обходом.
- **`onChange` становится опциональным** с внутренним no-op по умолчанию. Мотив: после снятия `value` пикеры тегов всё равно передавали бы `onChange={() => {}}` — тот же класс лжи контракта. Реагирующие на выбор потребители (`PhoneInput`, поисковые поля фото) продолжают передавать `onChange` как раньше; пикеры тегов передают только `onSelectItem`. Правка пересматривает паттерн #328 в его части.
- Остальной API `RemoteSearchSelect` не трогается.

**Зафиксированное поведение (не улучшать в этом скоупе):** селект не имеет пропа начальной подписи, поэтому поле с предзаполненным id, но без пользовательского выбора, выглядит **пустым** — и выглядело так же до правки (компонент и сегодня игнорирует `value`). Это сегодняшнее поведение, не регрессия; улучшение отображения предзаполнения — вне скоупа.

Отвергнутый вариант **B — управляемый по-настоящему** (отражать внешний сброс и подмену значения): при внешней подстановке другого id селект не знает подписи варианта (имя узнаётся только при выборе из результатов поиска) — потребовалась бы новая механика (поиск по id или передача подписи рядом с id). Сегодня ни один вызов не подставляет значение извне, кроме пересоздания по ключу. Потребность может возникнуть у волны #349 (задача 8, фото-страница на URL-хук) — тогда это отдельная задача под конкретное требование, не сейчас.

## 3. User Scenarios

Все сценарии — регрессионный каркас: «работает как раньше». Поскольку удаляются только параметры, которые компоненты игнорировали, поведение по построению не меняется; сценарии фиксируют, что IMPL и ревью обязаны сохранить.

| # | Сценарий | Покрытие |
|---|----------|----------|
| US-1 | Создание записи справочника (локация, должность, материал, услуга, тег): модалка открывается, запись создаётся | Существующие e2e/smoke модалок справочников |
| US-2 | Редактирование записи справочника: модалка открыта с подставленными значениями, сохранение работает | Существующие e2e/smoke модалок справочников |
| US-3 | Страница фото, фильтры-поисковые списки (мастер/локация): выбор значения работает; «Сбросить» очищает оба списка (через пересоздание по ключу) | Существующие тесты `PhotosFilters`, e2e фото-страницы |
| US-4 | Модалка фото: открытие другой фотографии / смена поля — поля локация/занятие пересоздаются по ключу и ведут себя как сегодня; поисковое поле выглядит пустым, пока пользователь не выбрал вариант заново (зафиксированное поведение, §2) | Существующие тесты `PhotoModal`, e2e фото |
| US-5 | Добавление тега через поисковый пикер (в модалке услуги, в модалке фото, в фильтрах фото): поиск и добавление работают (реакция через `onSelectItem`) | Существующие тесты `ServiceModal` / `PhotosFilters` |
| US-6 | Форма записи, телефонное поле с поиском по мастерам: поиск, выбор, очистка крестиком | Существующие тесты `PhoneInput` |

**Известное поведение вне регрессионного каркаса (не выравнивать):**
- у пикера тега в модалке фото нет ключа пересоздания (в отличие от поисковых полей) — при смене фотографии он сохраняет набранный запрос; сегодня так, менять не нужно;
- пути «пустой результат / ошибка поиска / загрузка» селекта в каркас не входят — поведение не меняется, специально не перепроверяются.

## 4. Behavioral Delta

**Для пользователя: изменений нет** (до = после) во всех сценариях.

Техническая дельта:

- До: контракты пяти модалок объявляли неиспользуемый `mode` (заглушен `_mode` с #301); контракт `RemoteSearchSelect` объявлял неиспользуемый `value` (заглушен `_value`) и требовал `onChange` даже там, где реакция не нужна; вызовы передавали `mode`/`value`/no-op `onChange`, создавая ложное впечатление управляемости; пересоздание по ключу существовало как недокументированный обход.
- После: `mode` и `value` отсутствуют в контрактах и во всех вызовах; `onChange` опционален (внутренний no-op), пикеры тегов передают только `onSelectItem`; `_`-глушители сняты вместе с параметрами; пересоздание по ключу — документированный способ внешнего сброса неуправляемого селекта с явным инвариантом (§5.5).

## 5. Технический план (что именно меняется)

Всё во фронтенде (frontend/admin). Перечисление файлов ниже — авторитетное; grep-паттерны обязательны как страховка от пропущенного (включая передачу через разворот спреда `{...props}`).

1. **Пять модалок** (`LocationModal`, `PositionModal`, `MaterialModal`, `ServiceModal`, `TagModal`): убрать `mode` из props-типа, из деструктуризации (снять `_mode`), из всех вызовов и из тестов. Вызовы искать grep'ом: `mode="create"`, `mode="edit"`, `mode: 'create'`, а также развороты `{...props}` в местах рендера этих пяти модалок.
   **Исключены сознательно** — у них `mode` живой: `PhotoModal`, `StaffModal`, `ClientCardModal`, `ActivityDetailsModal`.
2. **`RemoteSearchSelect`**: убрать `value` из props-типа и деструктуризации (снять `_value`); `onChange` из обязательного сделать опциональным (`onChange?:`), внутренние вызовы — через `onChange?.(...)`.
3. **Вызовы `RemoteSearchSelect`:**
   - `PhoneInput` — снять `value`, `onChange` остаётся;
   - `PhotosFilters` — два поисковых списка: снять `value`, `onChange` остаётся; пикер тега: снять `value` и no-op `onChange`;
   - `ServiceModal` — пикер тега: снять `value` и no-op `onChange`;
   - `PhotoModal` — пикер тега: снять `value` и no-op `onChange`; поля локация/занятие: снять `value`, `onChange` остаётся.
   Пересоздание по ключу (`resetKey` в фильтрах фото, `fieldRemount` в модалке фото) остаётся как есть, включая отсутствие ключа у пикера тега (§3).
4. **Тесты** (пути от frontend/admin): `__tests__/RemoteSearchSelect.test.tsx` (включая `value: null` в `defaultProps` и все render-вызовы), `__tests__/PhoneInput.test.tsx` (передача `value`), `__tests__/ServiceModal.test.tsx` (`mode="edit"` / `mode="create"` в нескольких describe-блоках), `__tests__/photos/PhotosFilters.test.tsx`, `PhotoModal.test.tsx` (передача `value`). Если снапшоты рендерят `mode`/`value` — перегенерировать.
5. **Канон** (`docs/design-system.md`, строка реестра общих компонентов `RemoteSearchSelect`): дополнить описание — «селект неуправляемый: внешний сброс/подмена значения — пересозданием по ключу; сброс = сброс состояния родителя **и** бамп ключа (два независимых действия — рассинхрон молчалив); пересоздание сбрасывает фокус и внутренние процессы (штатное следствие React)». Правка канона коммитится вместе со спекой.
6. **Артефакты IMPL**: запись в `CHANGELOG.md` (секция Unreleased, формат Keep a Changelog) + status-запись `docs/status/YYYY-MM-DD-dead-props-368.md` с фактически выполненным и тронутыми файлами.

## 6. Взаимодействие с #349

Файлы фильтров фото и модалки фото пересекаются с задачей 8 волны #349 (фото-страница на URL-хук), ещё не смерженной. Диф #368 маленький; порядок не важен — ребейзит та сторона, что встаёт в main второй. Страж от случайного возврата `value`: type-check уронит передачу несуществующего пропа, плюс grep-проверка §7. Если IMPL #349 упрётся в реальную потребность подставлять значение в селект извне — рождается follow-up issue на управляемый режим (вариант B этой спеки), не раньше.

## 7. Verification

- **Явно:** линт НЕ доказывает отсутствие мёртвых props — неиспользуемое поле props-интерфейса невидимо для `no-unused-vars` (поэтому #301 мог глушить только деструктурированные). Для каждого из шести компонентов (5 модалок + селект): props-тип не объявляет поле **и** тело не читает его (grep по файлу: `mode`, `value`).
- Линт: `npm run lint` в frontend/admin — 0 предупреждений, `_mode` / `_value` отсутствуют.
- Тесты компонентов: зелёные после снятия параметров (команды и тронутые файлы фиксируются в status-записи).
- Существующие e2e: зелёные (модалки справочников, фото).
- Ручная проверка по US-1–US-6 (каждый сценарий — «как раньше», включая зафиксированное пустое поле из §2).
