# Referrer-Policy: no-referrer для админ-приложения (#384)

Дата: 2026-09-27 · Источник: issue #384 (замечание панели безопасности спеки #349, вынесенное в отдельный скоуп) · Статус: на ревью (после панели 6/6)

## 1. Контекст и проблема

Фильтры табличных страниц переезжают в URL (#349, волна в работе): текст поиска — имена клиентов, фрагменты телефонов — оказывается в адресе страницы. Параллельный канал, о котором #349 не говорит: браузер при каждом исходящем запросе прикладывает служебный заголовок Referer — адрес страницы, с которой запрос ушёл. Клик по внешней ссылке уносит этот адрес в журналы чужого сервера.

Внешние ссылки в админке сегодня две — Яндекс-карты в таблице локаций, и у обеих стоит `rel="noopener noreferrer"`: этот атрибут убирает Referer для данных конкретных переходов. Защита, таким образом, держится на ручной дисциплине — каждый будущий внешний атрибут обязан помнить про атрибут; она не покрывает подресурсы, fetch-запросы и формы. Страничная политика закрывает канал целиком и навсегда, независимо от контента.

Калибровка риска: современные браузеры по умолчанию обрезают запросную часть адреса для чужих доменов (`strict-origin-when-cross-origin`) — полный адрес с текстом поиска утекает только со старым браузером, нестандартными корпоративными настройками или расширением. Цель — убрать канал целиком, независимо от браузера и будущего контента.

## 2. User Scenarios

Каждый сценарий мапится на E2E-проверку.

1. **Администратор открывает любую страницу админки** — каждый ответ приложения несёт `Referrer-Policy: no-referrer`. Проверка: e2e читает заголовки ответов на представительном наборе маршрутов — страница логина, страница клиентов, страница локаций, страница 404, файл из `public/` (`/logo-white.png`), один чанк `/_next/static`. Набор выборочный (не исчерпывающий): он ловит потерю конфигурации целиком, но не перехватывает случай, когда отдельный будущий маршрут переопределяет заголовок.
2. **Администратор кликает «Яндекс-карты» из таблицы локаций** — браузер, руководствуясь политикой страницы, не отправляет Яндексу заголовок Referer. Проверка: e2e перехватывает исходящий запрос по внешней ссылке (Playwright route, реальной навигации в интернет нет) и ассертит, что в перехваченном запросе нет заголовка Referer; параллельно ассертится наличие политики в ответе самой страницы. Если перехват покажет себя ненадёжным в Playwright (заголовки перехвата не равны фактически отправляемым), остаётся механическая проверка заголовка из сценария 1 — решение зафиксирует план.
3. **Администратор входит в систему и работает** — ничего не ломается: защита CSRF на бэкенде построена на `Sec-Fetch-Site`, которая от политики реферера не зависит. Проверка: существующие e2e логина и сессии остаются зелёными.
4. **Разработчик поднимает дев-сервер** — заголовок присутствует в dev-режиме (`next dev`), потому что точка выставления одна на оба режима. Проверка: e2e из сценария 1 — набор гоняется против `next dev`. Прозрачное ограничение: **прод-режим (`next start`) автоматикой не покрыт** — он проверяется одним ручным пунктом готовности (§7: `curl -I` после `next build && next start`).

## 3. Behavioral Delta

| | До | После |
|---|---|---|
| Заголовок `Referrer-Policy` в ответах админки | отсутствует — действует умолчание браузера (`strict-origin-when-cross-origin`) | каждый ответ несёт `no-referrer` |
| Клик по внешней ссылке без `rel="noreferrer"` | чужой сервер получает адрес страницы (без запросной части — в современных браузерах; целиком — в старых/нестандартных конфигурациях) | чужой сервер не получает ничего |
| Клик по существующим ссылкам Яндекс-карт | Referer уже не уходит (атрибут `rel` на ссылках) | без изменений, но защита больше не зависит от атрибута на конкретной ссылке |
| Подресурсы, fetch, формы | поведение по умолчанию браузера | Referer не отправляется никогда |
| Запросы админки к собственному API | несут Referer | не несут Referer (бэкенд на нём не построен — см. §6) |
| Работа админки для пользователя | — | без изменений: ни один сценарий UI не меняется |

## 4. Концепт (выбран автоматически, Gate A)

**Единственная точка: свойство `headers` в `frontend/admin/next.config.mjs`** — внутри объекта конфигурации (`export default nextConfig`, рядом с `images`), синхронная функция, один источник `/:path*`, один заголовок `Referrer-Policy: no-referrer`. По документации Next.js заголовки проверяются до файловой системы — покрывают страницы и файлы `/public`; для хешированной статики `/_next/static` закрыт от переопределения только `Cache-Control`, остальные заголовки применяются. Действует в обоих режимах (`next dev` и `next start`) и прокидывается с приложением в любой будущей раскладке развёртывания.

Отвергнутые подходы и почему:

- **middleware.ts с выставлением заголовка** — runtime-слой на каждый запрос ради константы; сложность без поведения, которого не даёт декларативный конфиг.
- **Заголовок на reverse-proxy** — прокси в репозитории не существует (проверено разведкой: нет ни nginx/traefik/caddy, ни Dockerfile/compose), прод-топология не определена; точка вне приложения не покрывает дев-сервер и не была бы единственной.

Конфликтов с канон-доками панель консистентности не нашла; готового паттерна заголовков в репо нет — это первый security-заголовок проекта.

## 5. Скоуп: что сознательно НЕ строим, и принятые допущения

- **Только админ-приложение.** Витрина (web) — статический экспорт, вне фокуса проекта (Hold); security-заголовки для неё — отдельное решение, если/когда витрина оживёт.
- **Другие security-заголовки** (CSP, X-Frame-Options, HSTS) — не добавляем: не запрошено, каждый требует собственного разбора рисков.
- **Логирование собственного бэкенда не трогаем**: текст поиска ходит в параметрах API-запросов независимо от Referer — это осознанная цена шарящихся ссылок #349.
- **Никакой UI**: пользовательских изменений нет вообще.
- **Допущение «админка никогда не переводится на `output: 'export'`»**: при статическом экспорте Next молча игнорирует `headers()` — заголовок исчез бы без единого красного теста. Сегодня экспорт используется только витриной.
- **Допущение «прод-инфраструктура не глотает заголовок»**: если перед админкой однажды появится прокси/CDN, отдающий статику мимо Next-сервера, заголовок должен доехать до границы сам или быть продублирован на ней; разовая проверка после реального деплоя — `curl -I` живого хоста (ручной пункт готовности §7).

## 6. Технические детали и почему ничего не ломается

- **Аутентификация — cookie-сессии** (`memo_session`, `credentials: include`), не токен-заголовки (поправка к тексту issue: #247 в финальном виде приземлился как сессии). Защита от CSRF точно сформулирована: бэкенд отвергает запросы только с `Sec-Fetch-Site: cross-site`; отсутствие заголовка проходит; основная линия — только-JSON + CORS с учётными данными.
- **Same-site-ность определяется топологией** (схема + регистрируемый домен), а не политикой реферера — это изменение на неё не влияет; доказательство — зелёные e2e логина/сессии, которые гоняют запросы с cookie. Топология: админка и API живут на одном хосте за разными портами (в ручном деве :3001/:8000, в e2e-шардах :3002–3003/:8001–8002) — localhost с разными портами является same-site (порт в понятие site не входит). **Деплой-премисса (существующая, не создаваемая этим изменением):** админка и API должны оставаться в одном регистрируемом домене — иначе CSRF-проверка отвергала бы запросы независимо от этой задачи.
- **Сторонние приёмники Referer, известные по гайдам (OAuth-провайдеры, платёжные проверки), в админке отсутствуют** — внешних хендоффов нет, ломать нечему.
- **Внешние ссылки Яндекс-карт** продолжают работать: меняется только то, что защита перестаёт зависеть от атрибута на конкретной ссылке.
- **Проверка «ничего не полагается на Referer»**: разведка — регистронезависимый поиск `referr?er` по бэкенду и фронту: ноль реальных вхождений (единственное совпадение — слово «preferred» в докстринге аудита; `rel="noopener noreferrer"` на трёх вызовах — это атрибут-защита, не чтение). Повторить тем же поиском при мерже — премисса снапшотная.

## 7. Как тестируется; готово, когда

Новый e2e-тест заголовков покрывает сценарии 1–2 (ассерты заголовков на представительном наборе маршрутов + перехват исходящей внешней навигации без Referer). Регрессия: существующие e2e логина/сессии, линт, тайпчек.

**Готово, когда:**
- новый e2e заголовков зелёный против дев-сервера;
- существующие e2e логина/сессии зелёные;
- линт и тайпчек зелёные;
- `curl -I` после `next build && next start` показывает заголовок (разовая ручная проверка прод-режима);
- повторный регистронезависимый поиск `referr?er` по коду чист;
- после будущего реального деплоя — разовый `curl -I` живого хоста (вне этой задачи, пункт на момент деплоя).

## 8. Премиссы issue, исправленные разведкой; порядок слияния

- «Бэкенд на токен-аутентификации #247» → фактически cookie-сессии; CSRF на `Sec-Fetch-Site`, не на Referer. Вывод (безопасно) не изменился.
- «#349 переводит фильтры в URL» → на момент разведки волна ещё не смержена; текст поиска попадёт в адрес позже. Канал уже приоткрыт: deep-link `?id=` клиентов смержен (адрес в статусе/истории браузера), а защита внешних ссылок держится на атрибуте в разметке.
- «Клик по внешней ссылке уносит адрес» → для существующих двух ссылок Яндекс-карт неверно: у них стоит `rel="noopener noreferrer"`, и их собственные переходы Referer уже не уносят. Риск — будущие ссылки без атрибута, подресурсы, fetch, формы.
- **Порядок слияния**: изменения независимы от волны #349 (админ-конфиг против страниц/хуков), но при параллельном мерже — ребейз после #349 и повтор grep-проверки из §6 на свежем дереве.
