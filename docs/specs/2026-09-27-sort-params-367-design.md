# Спека #367 — Унификация сортировочных параметров табличных списков

Дата: 2026-09-27 (rev2 — после панели 6 ревьюеров) · Статус: Gate B (ждёт ОК пользователя) · Скоуп: backend API + общие схемы. Фронтенд не трогаем.

## 1. Контекст и цель

Решение пользователя (сессия #217, 21.09): максимально выносить общий код табличных списков — ради скорости появления новых сущностей и жёсткости контрактов.

Фактическое состояние на 27.09 (сверка с живым деревом, HEAD 98ef07c7):

**Инвентарь — 8 сущностей с сортировкой = 7 жёстких + 1 мягкая:**

| Сущность | Контракт | Резолв сегодня | Хвост (тайбрейк) |
|----------|----------|----------------|------------------|
| records | жёсткий (`RecordSortBy` Literal) | services/record.py `_sort_columns` (карта коррелированных подзапросов) | `Record.id.asc()` |
| photos | жёсткий (`PhotoSortBy`) | services/photo.py inline | `Photo.id.asc()` |
| staff | жёсткий (`StaffSortBy`, после #266) | api/v1/staff.py `_staff_order_by` | `Staff.id.asc()` |
| services | жёсткий (`ServiceSortBy`) | api/v1/services.py `_service_order_by` | `Service.id.asc()` |
| materials | жёсткий (`MaterialSortBy`) | api/v1/materials.py `_material_order_by` | `Material.id.asc()` |
| locations | жёсткий (`LocationSortBy`) | api/v1/locations.py `_location_order_by` | `Location.id.asc()` |
| tags | жёсткий (`TagSortBy`) | api/v1/tags.py `_tag_order_by` | `Tag.id.asc()` |
| **clients** | **мягкий** (`sort_by: str`) | services/client.py inline-карта + **молчаливый откат к `name`** | **тайбрейка нет** |

- Механика применения (направление + nulls-политика + хвост) скопирована в 8 мест; семантика одна: канон `asc → nullsfirst() / desc → nullslast()`. Два отклонения от «текстового повтора»: у фото nulls-выражений нет вовсе (колонки NOT NULL — политике нечего делать), у staff `specialty`/`color` — доменное исключение «пустые — в конце» в **обоих** направлениях (решение #266).
- Фолбэк при `sort_by=None` (дефолтный порядок сущности): справочники — `title asc, id asc` (locations — колонка `Location.sort_order asc, title, id`), staff — колонка `Staff.sort_order asc, first_name, id`; у клиентов/записей/фото `sort_by` имеет фиксированный дефолт-значение (`"name"` / `"date"` / `"created_at"`) и None недостижим.
- Клиентский фолбэк закреплён тестом `test_invalid_sort_by_falls_back_to_name` — он переписывается (§6).
- У клиентов `last_record` может быть NULL: по канону при `asc` клиенты без записей всплывают наверх. Это сегодняшнее поведение — сохраняется без изменений (UX-пересмотр не входит в скоуп, §5).

Цель: один общий кирпень параметров сортировки + один общий резолвер «карта колонок + `sort_by`/`sort_order` → ORDER BY», клиенты переведены на жёсткий 422.

## 3. Behavioral Delta

| Поведение | До | После |
|-----------|----|----|
| Клиенты: неизвестное `sort_by` (`banana`) | 200, молчаливый откат к `name` | **422 VALIDATION_ERROR** |
| Клиенты: значения, тоже переходящие 200→422: пустая строка (`sort_by=`), регистр/пробелы (`Name`, ` name `), любые ключи вне Literal | 200, откат к `name` | **422**. Нормализация (strip/lowercase) не вводится — жёсткий контракт |
| Клиенты: неизвестное `sort_order` (`"DESC"`, `"up"`) | 200, трактуется как `asc` | **422** (общий `SortOrder`) |
| Клиенты: равные значения колонки | порядок недетерминирован, страницы дрожат | детерминированный хвост `Client.id.asc()` |
| Клиенты: published OpenAPI-схема | `sort_by: string` без перечисления | `sort_by` — enum 7 значений (уточнение контракта OpenAPI) |
| Records / photos / staff / справочники | канон nulls + хвост, размазанный по 8 копиям | поведение строк **не меняется** (дефолты и хвосты всех сущностей перечислены в §1 и сохраняются); механика — одна общая |
| Новая сущность в будущем | скопировать `_X_order_by` с nulls-политикой | наследовать `SortParams` + передать карту в резолвер |

Потребители клиентского контракта: admin-фронт (всегда шлёт ключ из колонок таблицы — `createPagedListContext`), OpenAPI-потребители, закладки/URL #349 (формируются из тех же колонок). Окно совместимости/версионирование не требуются: единственная ломка — запросы с невалидными ключами, которые сегодня получают сортировку по имени; ни один известный потребитель такие не шлёт.

## 4. Технический дизайн

### 4.1 Общий кирпень параметров — `SortParams` (schemas/common.py, рядом с `SortOrder`)

- `SortByT = TypeVar("SortByT", bound=str)` объявляется в `common.py` рядом с моделью.
- `SortParams(BaseModel, Generic[SortByT])`: `sort_by: SortByT | None = None`; `sort_order: SortOrder = "asc"`.

**Правило дефолтов (следствие панели):** кирпень задаёт *форму*, фиксированные дефолты — у сущностей. Каждый подкласс с фиксированным дефолтом **переопределяет оба поля** своей аннотацией и значением — `None` тогда выпадает из типа вовсе:

- `RecordListParams(SortParams[RecordSortBy], PaginationParams)`: `sort_by: RecordSortBy = "date"`, `sort_order: SortOrder = "asc"`;
- фото-модель `SortParams[PhotoSortBy], PaginationParams`: `sort_by: PhotoSortBy = "created_at"`, **`sort_order: SortOrder = "desc"` — сохранение сегодняшнего дефолта обязательно** (иначе перевернётся таблица фото);
- `ClientListParams(SortParams[ClientSortBy], PaginationParams)`: новый `ClientSortBy = Literal["name", "records_count", "last_record", "total_paid", "missed_records", "created_at", "updated_at"]`, `sort_by: ClientSortBy = "name"`, `sort_order: SortOrder = "asc"`;
- дублирующий `RecordSortOrder` удаляется в пользу общего `SortOrder` (проверить использования в экспортах `schemas/__init__.py` и тестах — сегодня экспорта нет);
- у скалярных роутов справочников `sort_by: XSortBy | None = Query(None)` — None-семантика (fallback сущности) живёт только там.

Честные ограничения и страховка:

- Скалярные Query-параметры справочников не наследуют кирпень (ограничение FastAPI при смешивании с `Depends()`-пагинацией — задокументировано в `schemas/pagination.py`); их OpenAPI-описания сохраняются как есть. Дрейф-защита: общий `SortOrder`, per-сущностный Literal и единственный резолвер (собственные `_X_order_by` удаляются).
- Комбинация «generic-модель с Literal-параметром + query-инъекция» для FastAPI — не проторённая дорожка (известные шероховатости генерации OpenAPI у вложенных generic-моделей). Чек-пойнт первой задачи импл: smoke-тест, что `ClientListParams` валидирует мусорный `sort_by` → 422 и OpenAPI-схема рендерит enum; тест-страж OpenAPI входит в §6. Fallback при упоре: `sort_by` объявляется в подклассе напрямую (кирпень остаётся носителем `sort_order` + конвенции), резолвер от формы кирпня не зависит.

### 4.2 Общий резолвер — domain/sorting.py

Одна функция применения сортировки; **карты остаются у сущностей** (содержание их таблиц; у записей — коррелированные подзапросы с `correlate()` — pin регрессии #213; у **services** тоже есть коррелированный COUNT-подзапрос для `sort_by=tariffs` — тот же класс, пин в тест-плане).

Форма входа (одна и та же для моделей и скалярных роутов):

- карта: ключ `sort_by` → спецификация колонок: список выражений + nulls-политика (`"canonical"` — канон `asc→nullsfirst/desc→nullslast`; `"always_nulls_last"` — «пустые — в конце» в обоих направлениях, staff `specialty`/`color`). Политика путешествует **в карте**, per-ключ;
- параметры вызова: `sort_order` + тайбрейк-колонка (PK сущности: `id` — простой PK у всех 8);
- тайбрейк применяется последним выражением как `asc()` и политике nulls **не подчиняется** (PK — NOT NULL);
- выход: список ORDER BY-выражений;
- fallback при `sort_by=None` (скалярные роуты) остаётся у сущности — это её содержание, резолверу не передаётся.

Слои защиты от неизвестного ключа (честно, от основного к страховочному):

1. **Literal-валидация схемы → 422** — основная линия, путь пользователя;
2. **тест-страж в CI**: для каждой сущности множество значений Literal == множество ключей карты (ловит дрейф «Literal расширили, карту забыли» — реалистичное направление дрейфа);
3. резолвер при неизвестном ключе поднимает типизированное доменное исключение (`UnknownSortKeyError`), глобальный обработчик мапит его в **422** VALIDATION_ERROR (не 500) — страховка от второго входа, миновавшего Literal; тестируется юнит-вызовом напрямую.

Диалектная зависимость: `nullsfirst/nullslast` — SQLAlchemy-конструкции поверх SQL `NULLS FIRST/LAST` (PostgreSQL, SQLite 3.30+); фиксируется комментарием в модуле. Составные индексы `(sort_col, id)` под канон — вне скоупа (перформанс не цель задачи).

### 4.3 Миграция сущностей (8 мест)

| Место | Что меняется |
|-------|--------------|
| schemas/client.py | `sort_by: str` → `ClientSortBy` Literal с дефолтом `name`; `sort_order` → общий `SortOrder` |
| services/client.py — `list_clients_view` | `dict.get(..., default)` → прямая индексация карты; применение через резолвер + хвост `Client.id.asc()` |
| services/record.py — `_sort_columns` | карта подзапросов остаётся; применение (`desc/asc/nulls/хвост`) → резолвер |
| services/photo.py — inline-резолв | карта остаётся; применение → резолвер (колонки NOT NULL — фактического изменения порядка нет); дефолт `desc` сохраняется в схеме |
| api/v1/staff.py — `_staff_order_by` | карта + резолвер; `specialty`/`color` — политика `always_nulls_last`; fallback при `None` (колонка `Staff.sort_order asc, first_name, id`) остаётся у сущности; query-`sort_order` при `sort_by=None` по-прежнему игнорируется (как сегодня) |
| api/v1/services.py, materials.py, locations.py, tags.py | каждая локальная `_X_order_by` → карта + резолвер (fallback при `None` — у сущности: `title asc, id`; locations — колонка `sort_order asc, title, id`) |

Не трогаем: легаси-роут `api/v1/masters.py` (фиксированный порядок, доживает рядом со staff), сущности без сортировки.

### 4.4 Совместимость с фронтом и #349

- Фронт шлёт `sort_by` только при непустом значении и только ключами колонок (`frontend/admin/contexts/createPagedListContext.tsx`, `packages/api-client/src/endpoints.ts`) — 422-переход клиентов фронт не триггерит; при 422 фронт рендерит штатную ошибку списка (С8).
- #349 (URL-фильтры таблиц, сейчас в реализации) несёт в URL тот же формат `sort_by`/`sort_order` — контракт не расходится.

## 5. Границы — что сознательно НЕ строим

- Сортировка для сущностей, у которых её нет сегодня (`visits`, `payments`, `visitors`, `positions`, `audit-logs`) — не добавляем; отдельные фичи по потребности.
- Легаси `/masters`, фронтенд, фильтры (общий `id`-кирпень уже решён #232) — вне скоупа.
- Пересмотр nulls-UX для клиентов и других сущностей («пустые всегда внизу») и перформанс-индексы под канон — не делаем: цель — унификация механики.

## 6. Тест-план

**API-тесты:**

- **Клиенты** (`test_api_clients.py`): 422 на мусорное `sort_by` (замена `test_invalid_sort_by_falls_back_to_name`), 422 на `sort_by=`, 422 на регистр-кейс `Name`, 422 на мусорное `sort_order`; сортировка `name`/`total_paid` asc+desc; дефолт без параметров; **двухстраничная стабильность** при равных `total_paid` (данные: достаточно клиентов с `total_paid=0`, чтобы страница резалась внутри равных — паттерн `test_api_records.py:1010`); nulls-поведение `last_record` (клиенты без записей при `asc` наверху — как сегодня).
- **Записи**: регресс сортировки по вычислимым колонкам, включая `q` + client-sort (pin #213).
- **Фото**: **новый тест без sort-параметров** (дефолт `created_at desc` — страж против флипа); существующие тесты — зелёные.
- **Staff**: «пустые — в конце» для `specialty`/`color` в обоих направлениях; 422 на generic-мусор `sort_by=bogus` (сегодняшний тест ловит только легаси-ключ).
- **Справочники**: существующие 422-тесты материалов/локаций/сервисов/тегов — зелёные; regressive тест сортировки services по `tariffs` (коррелированный COUNT-подзапрос — второй пин класса #213).

**Юнит-тесты резолвера (`tests/domain/test_sorting.py`):**

- канон: `asc → nullsfirst`, `desc → nullslast`; политика `always_nulls_last` — оба направления nulls-last; тайбрейк — последним выражением, `asc`, без политики; неизвестный ключ → `UnknownSortKeyError`.
- **страж контракта**: для каждой из 8 сущностей `set(get_args(Literal))` == `set(карта)` — CI-ловушка дрейфа «Literal ⊃ карта».

**Контракт OpenAPI:** тест, что опубликованная схема `sort_by` клиентов — enum из 7 значений (страж generic-кирпня в FastAPI — чек-пойнт §4.1).

## 8. Дельта канона и DoD

- **domain-rules** (коммитится вместе со спекой после ОК): в правило общих кирпней списков добавляется сортировка — «параметры: `SortParams` (модели) / scalar `Literal` + общий `SortOrder` (скалярные роуты); применение — только общий резолвер `domain/sorting.py`; локальные `_X_order_by`-функции запрещены; дефолты и fallback — у сущности».
- **Rollout**: миграция механики сохраняет поведение каждой сущности байт-в-байт (кроме перечисленного в §3), поэтому сущности переводятся на резолвер независимо — частичный выкат безопасен на любом шаге.
- **DoD**: все тесты §6 зелёные; `grep "_order_by\|_sort_columns"` в `backend/src/api` и `backend/src/services` не находит локальных резолвов вне карт; lint ноль.

## 9. Риски

- Добавление хвоста `id` клиентам меняет порядок строк при **равных** значениях колонки (детерминизм вместо дрожания) — принимаем как цель унификации.
- Generic-кирпень + query-инъекция — не проторённая дорожка FastAPI: чек-пойнт smoke + тест OpenAPI (§4.1, §6) + объявленный fallback на прямое объявление `sort_by` в подклассах.
- Перевод 8 работающих мест на общий резолвер — риск регрессии порядка: покрывается таблицей инвентаря §1 (сохранить хвосты/дефолты), существующими тестами сортировки и новыми тестами-представителями.
