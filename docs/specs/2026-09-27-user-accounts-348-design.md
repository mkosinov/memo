# #348 — Управление учётками пользователей: телефон, сброс пароля по одноразовой ссылке, создание учётки без пароля

Дата: 2026-09-27 · Статус: Gate B (ждёт ОК) · Ревизия 2 (после панели 6/6) · Источник: issue #348 (выделено из #319)
Решения Gate A (2026-09-27, диалог с пользователем): выдача ссылки — **вариант A (ссылку видит админ, передаёт сам)**; самостоятельная заявка «Забыли пароль?» — **не строим** (станет возможна вместе с каналами доставки); каналы доставки (Max, Telegram, email, SMS) — **отдельный issue #398**, здесь только шов для них.

## 1. Суть

Учётка пользователя создаётся **без пароля**: админ указывает только телефон, система выдаёт одноразовую ссылку установки пароля, админ передаёт её сотруднику, сотрудник сам придумывает пароль. Тем же механизмом работает сброс: кнопка «Сбросить пароль» в блоке «Учётка» выдаёт новую ссылку. Телефон существующей учётки становится редактируемым. Админ никогда не придумывает и не видит пароль учётки.

## 2. User Scenarios (каждый мапится на E2E/тесты)

| № | Сценарий | Кто | Проверка |
|---|----------|-----|----------|
| S1 | Создание сотрудника с учёткой: админ вводит ФИО, должности и **только телефон** учётки; после сохранения открывается диалог со ссылкой (кнопка «Скопировать», срок действия, подсказка «передайте ссылку сотруднику»). | S8 | После установки пароля по ссылке все прежние сессии учётки завершены | сотрудник | Backend-тесты установки |

## 3. Behavioral Delta (до → после)

| Область | Было | Стало |
|---------|------|-------|
| Создание учётки | Админ вводит телефон **и придумывает пароль** | Парольного поля нет; после создания показывается одноразовая ссылка |
| Чужой пароль | Сменить нельзя вовсе | «Сбросить пароль» в блоке «Учётка» → одноразовая ссылка, сотрудник задаёт сам |
| Телефон учётки | Только при создании, далее заморожен | Редактируется в блоке «Учётка», уникальность проверяется |
| Учётка без пароля | Невозможна | Возможна: не может войти, пока не задаст пароль по ссылке |
| Блокировка входа (лестница) | Снятие — только sqladmin (любой уровень) | Установка пароля по ссылке сбрасывает всю лестницу, вкл. жёсткую блокировку |
| Роль учётки | Редактируется (#263) | Без изменений |
| Свои настройки других пользователей | own-only (#319) | Без изменений (не строим) |
| Свой пароль в меню профиля | Работает | Без изменений |
| Журнал аудита | — | Новые записи: выдача ссылки, смена телефона |

## 4. Домен и данные

- **Таблица `password_setup_tokens`**: `token` — первичный ключ, **SHA-256 дайджест** выданного токена (сырой токен живёт только в ссылке и никогда не хранится); `user_id` FK с каскадом + индекс; `expires_at` (UTC); `used_at` (NULL = не использован); `created_at`.
- **Один живой токен на учётку** — ограничение БД: частичный уникальный индекс по `user_id` среди неиспользованных токенов. Гонка двух одновременных выдач исключается на уровне базы: одна из них отклоняется.
- **Выдача** (сценарий `issue_password_link`): отклоняется для деактивированной учётки (422); в одной транзакции удаляет **все** прежние токены пользователя (и использованные тоже) и создаёт новый; срок жизни — **24 часа** (параметр сценария, по умолчанию 24 ч — тесты передают малый срок). Использованные токены удаляются при перевыпуске — таблица не растёт на учётке.
- **Установка** (сценарий `set_password_by_link`): проверка парольной политики и хэширование — **до транзакции записи** (аргоновский хэш медленный, транзакция должна быть короткой); в транзакции — поглощение токена условной записью (обновляется только строка с `used_at IS NULL`; обновилась 0 строк → «ссылка недействительна» — двойное использование исключено), проверка **активности учётки** (токен, выданный до архивации, не работает), запись нового хэша, **сброс всей лестницы блокировок** (`failed_login_attempts = 0`, `lock_level = 0`, `locked_until = NULL` — включая жёсткую блокировку 3-го уровня), **отзыв всех сессий** пользователя.
- **Тайминговая чёткость**: все отказные пути публичной установки (нет токена / истёк / использован / учётка неактивна) отвечают одинаково — «Ссылка недействительна или истекла», с фиктивной работой в дешёвых ветках, как при входе с несуществующим телефоном.
- **`password_hash` становится nullable**: NULL = пароль ещё не установлен. Все существующие учётки имеют хэш — миграция без переноса данных.
- **Вход** учёткой без пароля: отказ с обычным «неверные учётные данные» (не раскрывает причину; тайминговая чёткость через фиктивный хэш, как для несуществующего телефона).
- **Правка телефона** (сценарий `update_user_phone`): единая функция валидации телефона (используют создание и правка); занятость — явная проверка → доменная ошибка; уникальность — по точной строке, как сегодня (нормализацию `+7 999…` / `+7999…` не вводим — это изменило бы вход существующих учёток); **сессии не отзываются** (cookie-сессии не завязаны на телефон).

## 5. API

| Эндпоинт | Права | Тело | Ответ | Ошибки (коды) |
|----------|-------|-------|-------|---------------|
| `POST /api/v1/users/{id}/password-link` | админ | — | `200 {token, expires_at}` — сырой токен показывается один раз | 404; 422 `ACCOUNT_DEACTIVATED` |
| `PATCH /api/v1/users/{id}` | админ | `{phone}` (строго, лишние ключи → 422) | `200` — учётка `{id, phone, role, staff_id, password_is_set, is_active}` | 404; 422 `PHONE_TAKEN`; 422 `PHONE_INVALID` |
| `POST /api/v1/auth/password-setup/validate` | публичный | `{token}` | `200` | 422 `PASSWORD_LINK_INVALID` |
| `POST /api/v1/auth/password-setup` | публичный | `{token, password}` | `204` | 422 `PASSWORD_LINK_INVALID` (один ответ для неверной/просроченной/использованной/неактивной учётки); 422 `PASSWORD_POLICY` |

- Мини-вертикаль **users**: файл эндпоинтов `api/v1/users.py`, расширение `UserService`, сценарии в `usecases/user.py` (безельная конвенция `@transactional`). Архивирование учётки остаётся в существующем потоке карточки сотрудника (флажок D6) — в новый PATCH не переносится.
- **Оба публичных эндпоинта** регистрируются в списке анонимно доступных маршрутов (default-deny; контрактный тест держит список точным) — иначе они закрыты guard'ом. Попытки установки с недействительным токеном считаются счётчиком неудач по IP (расширение существующих счётчиков неудач входа, то же окно).
- **StaffResponse** дополняется блоком `account: {phone, role, password_is_set, is_active, link_expires_at} | null` (текущая учётка карточки; `link_expires_at` — срок живой ссылки, NULL = нет) — источник данных для блока «Учётка»; флаг `has_user` остаётся. `account = null` — учётки нет; `account.is_active = false` — учётка архивирована.
- **Ссылку собирает фронт** из текущего origin страницы: `{origin}/password-setup#token=…` — бэкенд не знает публичный адрес админки, новая настройка не нужна. Инвариант: админка и страница установки на одном origin (сегодня так); каналы доставки (#398) введут настройку публичного адреса, когда станут доставлять сами.
- **При составном создании учётки** (путь создания учётки внутри создания сотрудника) добавляется явная проверка занятости телефона — сегодня там ловит только глобальный обработчик нарушения уникальности БД; контракт ошибки тот же, что у правки. CLI-сценарий создания пользователя (служебный, разработчик) уже проверяет и **остаётся с паролем**.

## 6. Фронтенд (admin)

- **StaffModal, создание**: блок «Учётка» = телефон + роль (D10-шаблон и ручной выбор как были), парольного поля нет.
- **StaffModal, редактирование**: телефон редактируемый (сохранение через PATCH users, отдельным запросом от карточки), роль как была, флажок архивирования учётки как был; **учётка архивирована** (`is_active = false`) — блок только читаемый («Учётка архивирована»), правки нет; **учётки нет** (`account = null`) — блок скрыт. Создание новой учётки к карточке с существующей (в т. ч. архивной) учёткой невозможно — как сегодня, вне скоупа.
- **Кнопка «Сбросить пароль» / «Выдать ссылку»** (подпись по флагу `password_is_set`); под ней статус **«Ссылка выдана, действует до …»** (локальное время, из `link_expires_at`), когда живая ссылка есть. Кнопки выдачи дизейблятся на время запроса (двойной клик не гасит только что выданную ссылку).
- **Диалог ссылки** (после создания и по кнопке): поле со ссылкой + «Скопировать», строка «действует до …», подсказка «передайте ссылку сотруднику». Ссылка показывается **только в момент выдачи** — повторный просмотр невозможен по построению (сырой токен нигде не хранится); нужна новая — повторная выдача.
- **Публичная страница `/password-setup`** — вне защищённой группы маршрутов (как `/login`, клиентский гард её не трогает), переиспользует компоненты и стиль формы входа: при открытии проверяет токен (`validate`) и сразу выбирает экран — форма или «Ссылка недействительна или истекла»; форма «Придумайте пароль» + подтверждение, inline-ошибка политики (одно сообщение); успех → переход на отдельный адрес успеха («Пароль установлен, войдите с телефоном и новым паролем», кнопка «Войти») — обновление страницы не повторяет запрос. Токен передаётся **фрагментом** (`#token=`): не попадает в историю запросов сервера и в Referer; страница после чтения очищает фрагмент из адресной строки.
- **api-client**: `patchUser`, `issuePasswordLink`, `validatePasswordSetup`, `passwordSetup` + zod-схемы, тесты в `endpoints.test.ts`.

## 7. Права и принятые риски

- Выдача ссылки и правка телефона — `require_admin`. Мастер чужих кнопок не видит и сам свой телефон не меняет (как сегодня — через админа); свой пароль меняет в профиле (без изменений).
- **Осознанная граница**: админ может выдать ссылку **любой** учётке, включая другие админские (связка «сменить телефон + выдать ссылку» = перехват учётки). Это принято: компенсация — обязательные записи журнала аудита; подтверждение второго шага (step-up) не строим. Упреждающая доставка сотруднику (каналы #398) уберёт транзит ссылки через админа.
- **Ссылка в руках админа** — принятый риск варианта A: кто держит ссылку, тот задаёт пароль и снимает блокировку. Смягчение: токен одноразовый, живёт 24 ч, статус «Ссылка выдана» виден в карточке.
- Служебные поверхности разработчика (CLI-сценарий создания пользователя, sqladmin) сохраняют прямое задание пароля — это не пользовательский флоу.
- Публичная установка: полномочие — сам токен (256-битный, перебор нереален); другая публичная поверхность не появляется; недействительный токен отвечает одинаково для всех причин.

## 8. Журнал аудита

- **Журналируются** (записи сценариями в тех же транзакциях): выдача ссылки (новый тип действия, автор — админ) и смена телефона (обновление; телефон в снимке маскируется по канону аудита).
- **Не журналируется**: установка пароля по ссылке — у публичного вызова нет автора, а канон аудита гласит «нет автора → нет записи». Событие восстанавливается по связке «выдача (кто, когда) → использование токена».

## 9. Правки канона (docs/domain-rules/auth.md — коммитятся вместе со спекой)

1. Учётка может существовать **без пароля**; в пользовательском интерфейсе пароль учётки задаётся только владельцем по одноразовой ссылке — админ пароль не придумывает, не видит и не вводит (дополнение к D6). Служебные поверхности разработчика (CLI, sqladmin) — исключение, не пользовательский флоу.
2. Установка пароля по ссылке **сбрасывает всю лестницу блокировок** (`failed_login_attempts`, `lock_level`, `locked_until` — включая жёсткую блокировку 3-го уровня, которую раньше снимал только sqladmin).
3. Ссылка установки пароля — одноразовая, живёт ограниченное время, действует только последняя выданная (один живой токен на учётку гарантирует ограничение БД).

## 10. Что сознательно НЕ строим

- Каналы доставки (Max, Telegram, email, SMS) — issue #398; самостоятельную заявку «Забыли пароль?» — наследник #398.
- Правку чужих настроек пользователей — own-only по #319, полезного сценария нет.
- Отдельную страницу списка всех учёток — учётки живут в карточках сотрудников.
- Парольное поле в блоке «Учётка» — запрещено требованием.
- Повторный показ уже выданной ссылки; step-up подтверждение при действиях над админскими учётками; нормализацию телефонных номеров; реактивацию/пересоздание архивной учётки (как сегодня).

## 11. Открытые вопросы

Блокирующих нет. Зафиксировано и меняется без переделки: срок жизни ссылки 24 часа (параметр сценария); выдача для деактивированной учётки запрещена; телефон админской учётки правится тем же эндпоинтом.
