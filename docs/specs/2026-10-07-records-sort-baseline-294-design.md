# Спека: перегон визуального эталона records-table-sort-active (#294)

Дата: 2026-10-07. Статус: ревизия 3. Ревизия 2 — после панель-ревью 5 из 6 агентов (consistency-агент дважды упал на апстрим-ошибке «Endpoint is unavailable» и помечен пропущенным — вердикт по остальным). Ревизия 3 — после находки при реализации: прогон `update-snapshots.yml` 37672556417 (зелёный, на 2b1140af) вернул артефакт, байт-идентичный репозиторию (65/65 файлов) — флаг `--update-snapshots` без значения работает в режиме `changed` и перезаписывает только расходящиеся сравнения, а этот тест проходит в допуске, поэтому его эталон не перезаписывается. Решение пользователя (Gate B, вторая остановка): добавить в workflow параметр режима перезаписи. Дерево проверки: main `b94ad48a`.

## Контекст и проблема

Визуальный e2e-тест `records-table-sort-active` (клик по заголовку «Гостей» в таблице записей, ожидание глифа сортировки ↑, полностраичный скриншот с допуском `maxDiffPixels: 5000` — `frontend/admin/e2e/visual-regression.spec.ts:406-416`, конфиг records `:320-338`) сравнивает снимок с эталоном `frontend/admin/e2e/visual-regression.spec.ts-snapshots/records-table-sort-active-shard-rest-linux.png`.

Эталон записан 2026-09-11 (коммит `81d90065`, PR #268) из прогона с повреждённым состоянием тестовой базы: coarse-обработчик статуса в двух старых спеках делал delete+recreate визитов записи r1, из-за чего сид-визиты v1/v2 удалялись навсегда и пер-тестовый сброс их не восстанавливал. Источник повреждения устранил фикс `a48d86a` (2026-09-17) — но эталон остался и кодирует строку r1 как «1 гость / Отменён / 0 ₽», тогда как чистый сид даёт «2 гостя / Посещён / 6000 ₽» (`backend/src/seed/seed.py:469` — r1: VISITED, seats 2; `:482-483` — визиты v1 3500 ₽ + v2 2500 ₽; `:499` — платёж 6000 ₽). Повреждён был рантайм-стейт БД того прогона, а не сид-скрипт — сид цел и сейчас. Запись эталона идёт через тот же пер-тестовый сид-сброс, что и обычный прогон шард-rest (`visual-regression.spec.ts:568-576`, beforeEach), поэтому «чистота сида» при перегоне обеспечивается тем же механизмом, что и в каждом зелёном CI-прогоне.

Перегоны базлайнов 2026-10-07 (PR #411 `1fecaa65` — 9 файлов, PR #413 `7335caaa` — 4 файла) этот PNG не включали; PR #418 каталог снапшотов не трогал. С момента заведения спека тест семантически не менялся (единственный коммит по файлу — рефактор-переименование `4af1716b`). Сид и отображение таблиц менялись после 11.09 (статус-литералы #134, титулы #172, тарифы #284, фото-даты #341, дочерние записи #319) — перегон по построению кодирует текущее состояние main, ожидания ниже сверяются с текущим `seed.py`, а не с формулировками старого прогона.

CI при этом зелёный: на раннере шрифты совпадают, расхождение сводится к данным строки r1 и укладывается в допуск 5000 пикселей — тест проходит «по допуску, а не по совпадению». Измерение 6325 px из эпохи заведения снято локально в контейнере, где к данным добавляется шрифтовой дрейф среды (~1 % пикселей по всей странице, спека #278), и на CI не переносится. Практическое следствие: вердикт по этой таблице зашумлён — реальное изменение данных строки r1 может спрятаться в допуске, а превышение допуска выглядит необъяснимо, пока не знаешь историю эталона.

Запись эталонов — CI-only операция по канону (`docs/tests_workflow.md`: «Re-recording baselines is a CI-only operation. Always run update-snapshots.yml; never commit locally recorded PNGs»; правило сохранено и в редакции после #418). #418 не изменил механику: `testIgnore` визуальных спеков действует только локально, в CI раннер всегда исполняет визуальные спеки в `shard-rest`; `visual-check.yml` — проверочный режим (`--update-snapshots=none`), физически не записывающий эталоны.

## Концепт

В `update-snapshots.yml` добавляется вход `mode` (выбор: `changed` — нынешнее поведение, значение по умолчанию; `all` — перезаписывать все эталоны безусловно). Команда прогона параметризуется: `--update-snapshots=${{ inputs.mode }}`. Дефолт сохраняет текущее поведение конвейера для всех существующих сценариев; опция `all` даёт свежую запись и для проходящих в допуске тестов — единственный способ обновить эталон теста, который не падает.

Перегон одного эталона: запуск workflow с `mode=all` на ветке с правкой, из артефакта извлекается только `records-table-sort-active-shard-rest-linux.png`, коммитится тем же PR, что и правка workflow; мерж — по гейту зелёного CI. Других правок кода и доков нет.

Отвергнутые альтернативы:

- **Локальная запись PNG** — прямо запрещена каноном (см. выше); локальная среда и не авторитетна для пикселей (#278).
- **`visual-check.yml`** — check-only (`--update-snapshots=none`), эталоны не пишет.
- **Расширение допуска `maxDiffPixels`** — порог защищает CI-сторону от дрейфа раннера, семантика другая; решение #278: пороги не трогаем.
- **Сужение команды перегона фильтром тестов (`-g`)** (предложение панели best-practices) — вход с именем теста не заводим: правка конвейера шире необходимого. Сдерживание даёт извлечение по точному имени + проверка В2.
- **Временная ветка с нулевым порогом теста** (тест «падает» → режим `changed` его перезаписывает) — трюк ради одного раза, ноль постоянной пользы; отвергнуто пользователем в пользу параметра режима.

## User Scenarios

- **СЦ1. Разработчик или агент вносит правку в таблицу записей и отправляет PR.** Раньше: визуальный вердикт CI сравнивал снимок с эталоном, кодирующим несуществующее состояние строки r1 («1 гость / Отменён / 0 ₽»). После: эталон отражает чистое сид-состояние — пиксельный вердикт точен, изменение данных строки r1 больше не маскируется допуском в 5000 пикселей. → В3, В4.
- **СЦ2. Разработчик триажит визуальное падение таблицы записей.** Открывает эталон и видит настоящее ожидаемое состояние страницы («2 гостя / Посещён / 6000 ₽»), а не артефакт сентябрьского повреждённого прогона. → В3.
- **СЦ3. Исполнитель перегона запускает workflow и оформляет результат.** Запуск `update-snapshots.yml`, скачивание артефакта, извлечение ровно одного PNG по имени, PR; мерж — только после зелёного CI. Стоп-ветка (красный workflow, артефакт без нужного файла, расхождение шире ожидаемого, красный CI): перезапуск workflow и пересборка ветки; PR переиспользуется, пока не сменилась база. → В1, В2, В4, В5.

## Behavioral Delta

| До | После |
|---|---|
| Эталон `records-table-sort-active-shard-rest-linux.png` кодирует повреждённый прогон 2026-09-11: строка r1 «1 гость / Отменён / 0 ₽» | Эталон записан CI-средой из чистого сида: строка r1 «2 гостя / Посещён / 6000 ₽» |
| Снимок и эталон систематически расходятся на данные повреждённого прогона — тест проходит внутри допуска `maxDiffPixels: 5000` | Снимок и эталон пишутся одной CI-средой из одного чистого состояния — систематическое расхождение исчезает по построению |
| История «почему эталон выглядит так» живёт только в старом коммите-фиксе | Эталон самодокументирован коммитом перегона со ссылкой на источник повреждения `a48d86a` |

Для пользователя приложения ничего не меняется — изменяется только тестовый актив.

## Решение

1. Ветка `chore/294-records-sort-baseline` от свежего main; в `.github/workflows/update-snapshots.yml` добавляется вход `mode` (`workflow_dispatch.inputs.mode`, choice: `changed`/`all`, default `changed`, с описанием) и команда прогона меняется на `--update-snapshots=${{ inputs.mode }}` (сейчас `:118`). Ветка пушится.
2. Запустить `gh workflow run update-snapshots.yml --ref chore/294-records-sort-baseline -f mode=all` — GitHub берёт определение воркфлоу и входы с указанной ветки. Дождаться **успешного** завершения: артефакт принимается только от зелёного прогона (шаг заливки стоит с `if: always()` `:129`, красный прогон тоже оставляет артефакт частичного состояния; артефакт хранится 7 дней).
3. Скачать артефакт `updated-snapshots-shard-rest`; извлечь из него **только** `records-table-sort-active-shard-rest-linux.png` — по точному имени (например, `unzip -j`), не выбором из распакованной папки. В режиме `all` артефакт содержит перезаписанные все эталоны — в коммит идёт ровно один.
4. Коммит PNG в ту же ветку; сообщение коммита ссылается на источник повреждения (`a48d86a`) и не содержит закрывающих ключевых слов. PR с `Closes #294` в описании.
5. Мерж по гейту репозитория: `gh pr checks --watch` до exit 0, затем squash; красный CI — стоп и разбор. Перед мержем ветка ребейзится на свежий main; если после записи эталона в main попали правки, меняющие таблицу записей, или конфликтующий базлайн-PR — перегон повторяется (один workflow-запуск).

## Границы (что сознательно НЕ строим)

- Правка конвейера ровно одна: вход `mode` в `update-snapshots.yml` с дефолтом, сохраняющим нынешнее поведение. Вход с именем теста/фильтром не заводится; `test.yml`, `visual-check.yml` и остальные workflows не трогаются.
- Из артефакта не берутся никакие другие файлы: посторонний дрейф других эталонов не абсорбируется.
- Пороги `maxDiffPixels` не меняются; код, спеки, конфиги и доки не правятся.
- #419 (недетерминированное падение week-view в узком визуальном прогоне при зелёном полном CI) — отдельная карточка: механизм сравнения общий, файлы и базлайны другие.

## Издержки и риски

- **Перегон фиксирует текущее состояние таблицы на main целиком** — включая все изменения сида и отображения с 11.09 (это часть намерения). Если на main есть незамеченный визуальный дрейф таблицы записей, он станет новым эталоном. Митигация — В3: изменения обязаны ограничиться таблицей записей (строка r1 + перестановка строк); всё шире — стоп и разбор до коммита. Тот же механизм ловит широкий дрейф образа раннера с 11.09 (если он проявится — дифф выйдет за таблицу).
- **Артефакт содержит все визуальные эталоны шарда** — риск случайного захвата лишнего. Митигация: извлечение по точному имени (Решение 2) + механическая проверка В2.
- **Гонка с main и параллельными базлайн-PR**: окно между записью и мержем коротко, вероятность конфликта мала; поведение при конфликте определено (Решение 4 — перегон заново на свежем main).
