# Спека: очистка debounce-таймера RemoteSearchSelect при размонтировании

- **Issue:** #296 (fix(admin), test-debt)
- **Дата:** 2026-10-07
- **Статус:** rev3 (гейт B, решение юзера 2026-10-08: концепт и спека — ОК; регрессионный юнит-тест убран из скоупа; панель 6/6 — см. «Отчёт по панели»)
- **Скоуп:** один компонент `frontend/admin/app/components/shared/RemoteSearchSelect.tsx` (+ регрессионный юнит-тест в `frontend/admin/__tests__/RemoteSearchSelect.test.tsx`). Код приложения меняется точечно — это не fast-track.

## Контекст

`RemoteSearchSelect` — общий виджет живого поиска с задержкой: оператор набирает текст, запрос к серверу уходит не на каждый символ, а через 300 мс после последнего ввода (дебаунс), результат открывается дропдауном. Потребители: выбор посетителя в новой записи (`NewRecordTab`), фильтры и модалка фотографий (`PhotosFilters`, `PhotoModal`), услуги (`ServiceModal`), телефонный ввод (`PhoneInput`).

Механика (живое дерево, main 1764e74d):

- `RemoteSearchSelect.tsx:123` — таймер дебаунса хранится в `debounceRef`.
- `RemoteSearchSelect.tsx:170-171` — единственная очистка живёт в обработчике ввода: перед планированием нового таймера старый сбрасывается (`clearTimeout` + `setTimeout(() => search(val), 300)`).
- `search` (`:136-161`) — async: `setIsLoading(true)` → `await onSearch(...)` (колбэк родителя, там сетевой запрос) → сеттеры состояния результата → `finally setIsLoading(false)`.
- **Unmount-cleanup нет:** при размонтировании компонента (закрыли модалку, сняли панель фильтров) висящий 300-мс таймер не отменяется и срабатывает на уже размонтированном компоненте.

Тестовый фон: собственный сьют компонента использует fake-таймеры (`beforeEach`, `RemoteSearchSelect.test.tsx:8-11`) и в `afterEach` прогоняет повисшие таймеры (`:13-17`); консюмерские сьюты рендерят виджет с реальными таймерами. Vitest админки: jsdom, пул `forks`, 5 шардов в CI.

## Проблема

Issue #296 (заведён 2026-09-17 из IMPL #257) описывал гонку как «debounce teardown race — window is not defined под параллельной нагрузкой». Разведка 2026-10-07 по живому дереву корректирует механику:

- **Слова `window` в компоненте нет вообще** (0 совпадений); симптом «window is not defined» нигде в репо не зафиксирован и из текущего кода не воспроизводится. Формулировка_issue описывала состояние кода до рефакторингов 2026-09/10 (#405 и другие меняли компонент, заведённый после #221).
- **Реальная дыра — отсутствие unmount-cleanup:** таймер дебаунса переживает размонтирование. Сработав, он выполняет `search(val)` целиком: лишний сетевой запрос через `onSearch` (результат уже некому показать) и сеттеры состояния на размонтированном компоненте. В тестовом окружении под параллельной нагрузкой это работа в фазе, когда jsdom-окружение сьюта уже демонтируется (в `afterEach` чужого сьюта, после `restoreMocks`, на грани teardown пула) — источник стохастических unhandled rejection в полных прогонах. Изолированно сьют зелёный: гонка требует окна в сотни миллисекунд между unmount и срабатыванием таймера под нагрузкой.
- Ни один PR после заведения issue cleanup не добавил (#405, #365/#328, #372 касались компонента — мимо дыры).

Корректировка зафиксирована комментарием в issue (2026-10-07).

## Концепт (выбранный и отвергнутые)

**Выбран: cleanup-эффект в самом компоненте — паттерн уже живёт в репозитории.** Отдельный `useEffect` с пустым массивом зависимостей, возвращающий очистку `debounceRef` через `clearTimeout`; плюс регрессионный юнит-тест на сценарий «ввели текст → размонтировали → таймер не сработал». Прецеденты в репо: локальный хук `useDebouncedCallback` в `ClientsFilters.tsx:7-35` (дебаунс + отмена + cleanup при размонтировании на `:34`, комментарий «GH #216: no setState-after-unmount from an armed timer» — тот же класс бага, что здесь) и однострочные cleanup-эффекты размонтирования в `RecordsFilters.tsx:103` и `DataTable.tsx:81`. Для RemoteSearchSelect выбран простой cleanup-эффект, а не перенос хука: собственная механика `debounceRef` уже написана в компоненте, эффект добавляет недостающие 6 строк; прививка хука — большая правка без выигрыша (вынос хука в общий модуль — отдельная задача, см. границы).

Отвергнутые подходы:

- **Guard-флаг «компонент ещё смонтирован»** (проверка `isMounted` внутри `search`) — антипаттерн: работа продолжается и отменяется по факту, а не по причине; репозиторий такой стиль не использует (везде cleanup-эффекты).
- **Общий хук `useDebouncedCallback` с консолидацией всех дебаунсов админки** — рефакторинг живого работающего механизма сразу в 4+ компонентах ради одной дыры; расширение скоупа без пользы для issue (нарушает границы минимальной правки).
- **Харднинг только тестов консюмеров** (перевод их на fake-таймеры) без правки компонента — не закрывает дыру в рантайме: после закрытия модалки всё равно уходит лишний запрос к серверу; тест-инфра маскирует продукт-баг.

## User Scenarios

- **S1. Ввод оборван закрытием окна.** Оператор начал набирать имя посетителя (или услуги, фильтр фото) и в пределах 300 мс закрыл модалку/панель: поиск не выполняется — запрос к серверу не уходит, никакого обновления состояния не происходит. Верификация: сама правка (отдельный тест не пишем — решение юзера на гейте B, 2026-10-08); поведение живого ввода прикрывают существующие тесты и e2e (S2).
- **S2. Дебаунс при живом вводе не меняется.** Оператор быстро меняет запрос несколько раз подряд: уходит только один поиск — по последнему вводу, через 300 мс паузы; порог минимальной длины и поведение дропдауна прежние. Верификация: существующие юнит-тесты компонента без правок; e2e живого поиска (`services-tags.spec.ts`, `server-push-invalidation.spec.ts` — виджет под ними) без изменений, зелёные.
- **S3. Полный прогон без класса флейка.** Инженер или CI гоняет полный параллельный прогон vitest админки (пул forks, 5 шардов): класс «таймер дебаунса сработал после teardown окружения» структурно закрыт — повисший таймер отменяется при размонтировании. Верификация: полный локальный прогон зелёный + зелёные CI-шарды PR (DoD issue: флейк не воспроизводится в полном прогоне).
- **S4. Поведение для пользователя то же.** Задержка 300 мс, минимальная длина запроса, открытие/закрытие дропдауна, выбор значения — всё как до правки; меняется только отсутствие «хвоста» после закрытия окна. Верификация: S2-покрытие (юнит + e2e без правок).

## Behavioral Delta

- **Пользователь админки, до:** закрыл окно с живым поиском в пределах 300 мс после ввода — зависший таймер всё равно срабатывал: уходил лишний поиск-запрос к серверу (результат отбрасывался), выполнялась запись состояния в уже закрытый компонент.
- **Пользователь админки, после:** закрытие окна отменяет отложенный поиск целиком — ни запроса, ни обновлений состояния. Всё остальное поведение идентично.
- **Инженер / CI, до:** вектор стохастического падения полных прогонов (работа таймера в фазе демонтирующегося тестового окружения); симптом не воспроизводится изолированно, из-за чего класс трудно диагностировать.
- **Инженер / CI, после:** вектор закрыт в корне (таймер не переживает размонтирование); полные прогоны не содержат этого класса падений. Отдельного регрессионного теста нет (решение юзера, гейт B): контракт «после размонтирования поиск не вызывается» держится ревью правки.

## Техническое решение

1. **Cleanup-эффект** в `RemoteSearchSelect.tsx` (рядом с существующим эффектом закрытия по клику вне, `:126-134`):

   ```tsx
   // Cancel the pending debounced search when the widget unmounts.
   useEffect(() => {
     return () => {
       if (debounceRef.current) {
         clearTimeout(debounceRef.current);
         debounceRef.current = undefined;
       }
     };
   }, []);
   ```

   Сброс `debounceRef` после очистки — прецедент репо (`ClientsFilters.tsx:27-29`: «fired id must not linger»): несработавший идентификатор таймера не остаётся в ref.

   Пустой массив зависимостей корректен: `debounceRef` — ref, эффект читает только его. Cleanup выполняется синхронно в коммите размонтирования — до того, как таймер успеет сработать.

2. **Отдельный регрессионный тест не пишем** (решение юзера на гейте B, 2026-10-08): правка — 6 строк по живому паттерну репо; контракт «после размонтирования поиск не вызывается» проверяется ревью. Если тест когда-нибудь вернётся в скоуп — форма оговорена в отчёте панели (асинхронный прогон таймеров).

3. **Верификация DoD** (полный прогон): локальный полный прогон vitest админки зелёный; в CI — зелёные шарды PR. Отдельные попытки поймать стохастический флейк прогонами не делаем: как и в #291, механика установлена разведкой, воспроизведение флейка дорого и не нужно для фикса; приёмка — ревью правки плюс зелёный полный прогон.

Границы (что мы сознательно НЕ делаем):

- НЕ выносим общий debounce-хук и НЕ консолидируем инлайн-очистки других компонентов (ClientsFilters и остальные остаются как есть).
- НЕ меняем механизм дебаунса: 300 мс, `minChars`/`canSearch`/`buildParams` — потребительские пропсы без изменений.
- НЕ добавляем отмену уже ушедшего поиска-запроса (abort in-flight): `onSearch` — колбэк родителя, ответственность за сетевой слой на нём. Контракт компонента на «позднее завершение» (запрос успел уйти до размонтирования): rejection ловится локальным `catch` в `search` (`:154`), сеттеры состояния на размонтированном компоненте — отброшенные no-op, `finally setIsLoading(false)` — тот же no-op; unhandled rejection из самого компонента невозможен. Что делать с опоздавшими данными в своих сторе/кэшах — решает консюмер (сегодня ответы просто не приходят в отменённый колбэк-цикл виджета).
- НЕ трогаем консюмерские сьюты, конфиг vitest (пул forks, шарды) и настройку fake-таймеров существующих тестов.
- НЕ чиним симптом «window is not defined» отдельной правкой: в живом коде его нет (корректировка разведки); закрытие дыры таймера закрывает и его исторический источник.

## Риски и компромиссы

- **«Флейк не воспроизводится» недоказуем прогонами напрямую** — падение этого класса не зафиксировано и до фикса (одиночное наблюдение 17.09 в составе другого сьюта). Приёмка перенесена на проверяемое: ревью правки + зелёный полный прогон (регрессионный тест убран решением юзера на гейте B — защита от будущего рефакторинга только ревью). Компромисс осознанный.
- **Двойная очистка безопасна:** `clearTimeout` по уже сработавшему/несуществующему таймеру — no-op; одновременное наличие очистки в `handleInputChange` и в unmount-cleanup не конфликтует.
- **Порядок эффектов:** cleanup добавленного эффекта срабатывает при размонтировании в общем коммите — до истечения 300 мс в любом реальном сценарии (закрытие окна — событие пользователя, не гонка с таймером того же тика).
- **React-версия:** сеттеры на размонтированном компоненте в React 18 не предупреждают (предупреждение удалено в 18; репозиторий на `react: ^18`) — правка всё равно ценна: убирает лишний сетевой запрос и работу в фазе teardown тестового окружения (сам источник rejection). Остаточный путь «запрос ушёл до размонтирования» закрыт локальным `try/catch/finally` в `search` (см. границы) — no-op, не ошибка.

Правка гейта B (решение юзера 2026-10-08): регрессионный юнит-тест убран из скоупа — приёмка правки = ревью + зелёный полный прогон; замечание панели про асинхронный прогон таймеров (`advanceTimersByTimeAsync`) осталось в истории и вернётся, если тест когда-нибудь добавят.

## Отчёт по панели (rev1 → rev2)

Панель 6 ревьюеров в контейнере (D-flow): consistency SOUND (повтор после сбоя первого прогона — rc=1, пустой отчёт; повтор rc=0), security SOUND, completeness / feasibility / simplicity / best-practices SOUND_WITH_CONCERNS. Несущие утверждения ревьюеров проверены по коду перед внесением.

Принятые замечания (внесены):

- Явный контракт «позднего завершения» запроса: rejection ловится локальным `catch` в `search`, сеттеры на размонтированном — no-op; данные опоздавших ответов — ответственность консюмера (completeness, MAJOR — принят документирующей правкой границ).
- Упомянуть прецедент локального хука `useDebouncedCallback` (`ClientsFilters.tsx:7-35`, комментарий GH #216 — тот же класс бага) и обосновать выбор простого эффекта (simplicity).
- Сброс `debounceRef` после `clearTimeout` — прецедент репо «fired id must not linger» (best-practices).
- Асинхронный прогон таймеров в регрессионном тесте (`advanceTimersByTimeAsync`) вместо синхронного — act-безопасная форма (best-practices).
- Точные строки цитат: cleanup-эффекты живут в объявлениях (`RecordsFilters.tsx:103`, `DataTable.tsx:81`), а не в вызовах `clearTimeout`; DayColumn убран из цитат (его `:282` — обработчик ухода мыши, не unmount-cleanup); уточнены диапазоны `beforeEach`/`afterEach` тест-файла (consistency).

Отклонённые замечания (с причинами):

- «React 18 strict mode предупреждает о сеттерах на размонтированном» (feasibility) — предупреждение удалено именно в React 18; репозиторий на `react: ^18`, формулировка спеки верна (уточнена версией).
- `AbortController` для ушедшего запроса (best-practices, completeness-перекличка) — сознательная граница: `onSearch` — колбэк родителя, сетевой слой на его стороне; локальный `catch` уже исключает unhandled rejection из компонента.
- «`finally setIsLoading` без защиты на размонтировании» (completeness) — no-op, не ошибка; guard-флаг отвергнут выше как антипаттерн, отдельная защита не нужна (отмечено в рисках).
