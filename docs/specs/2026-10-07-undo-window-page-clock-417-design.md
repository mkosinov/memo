# Спека: окно отмены в e2e — управляемые часы вместо реальных ожиданий по 5,5 с

- **Issue:** #417 (test-debt; закрывает и гонку #291 — см. «Связанное»)
- **Дата:** 2026-10-07
- **Статус:** rev2 (панель 6/6: правки внесены; см. «Отчёт по панели»)
- **Скоуп:** тестовый код e2e (`frontend/admin/e2e/`, включая фикстуры-хелперы); код приложения не меняется.

## Контекст

В админке удаление (посещения, платежи, фото, теги, клиенты, занятия, должности, материалы) работает как отложенное: клик «×» сразу убирает сущность со страницы (оптимистичное удаление) и показывает тост с кнопкой «Отменить»; настоящее DELETE-обращение к серверу откладывается на 5 секунд. Окно целиком клиентское: таймер коммита живёт в `frontend/admin/contexts/PendingActionsContext.tsx` (обычный `setTimeout`), автоскрытие тоста — в `frontend/admin/contexts/UIContext.tsx` (обычный `setTimeout` на те же ~5 с), кольцо отсчёта — `setInterval` без обращений к системным часам. Сервер не держит таймеров удаления (разведка по бэкенду: поиск таймеров и отложенных задач пуст) — DELETE отправляет только клиент по истечении окна.

В e2e 23 ожидания истечения этого окна: 22 литеральных `waitForTimeout(5_500)` в 12 файлах спецификаций (сверенная роспись — в приложении) плюс одно замаскированное (`WINDOW_MS + 500` при `WINDOW_MS = 5_000` в спецификации стража ухода со страницы; issue считал 22 — разведка нашла 23-е, и оно окажется особым случаем, см. «Особое 23-е место»). Суммарно ~2 минуты чистого сна за полный прогон, из них ~114 секунд — в сьюте shard-rest (21 ожидание из 23). По семантике проверок: 12 ожиданий «без отмены удаление дошло до сервера» (счётчик DELETE ≥ 1 или строка исчезла из базы), 10 «отмена удержала удаление» (DELETE не ушёл, строка жива), 1 — особый буфер.

Механика `page.clock` в наборе уже знакома: 4 существующих использования (недельная сетка, визуальная регрессия) ставят часы в `beforeEach` до навигации ради стабильности дат — время там никогда не продвигается. Паттерн «пауза → перемотка» в кодовой базе ещё не опробован — поэтому план начинает с пилотного места (см. Риски).

## Проблема

- **Медленно.** Каждое из 23 ожиданий спит 5,5 секунд реального времени; полный прогон теряет на этом ~2 минуты.
- **Гонка окна (issue #291).** Пока окно тикает в реальном времени, тест, выполняющий между появлением тоста и кликом «Отменить» несколько проверок с трёхсекундными запасами, может к моменту клика опоздать за тихую границу: отмена игнорируется, строка не возвращается — ложный красный при рабочем продукте (единственный случай — 16.09.2026).
- **Существующий паттерн не переносится напрямую.** Часы, установленные на весь тест, замораживают и живые зависимости реального времени: setTimeout-бэкофф переподключения серверных событий (сам EventSource часами не подменяется — подменяются только JS-таймеры), дебаунс-поиск в полях ввода, автоскрытие тостов без отмены. Спецификации этих механик (например, офлайн-детектор соединения) обязаны жить в реальном времени.

## Концепт (выбранный и отвергнутые)

**Выбран: хелпер-обёртка «окно под управляемыми часами».** Тело работы с окном передаётся колбэком: перед колбэком часы страницы ставятся на паузу в текущем реальном времени; внутри колбэка тест выполняет действия и проверки (создание окна кликом «×», тост, скрытие строки, при undo-сценарии — клик «Отменить»); после колбэка время перематывается на 5 500 мс одной операцией и отпускается. Пока часы на паузе, окно не тикает — опоздать за границу отмены клик физически не может. Колбэк-форма гарантирует порядок «пауза до создания окна» и неотменяемость перемотки конструктивно (нельзя забыть перемотать — она в самом хелпере).

Отвергнутые подходы:

- **Глобальная установка часов в общей фикстуре** — замораживает бэкофф-переподключения, дебаунс-поиск и тосты без отмены на всём протяжении каждого теста; прямо ломает живые спецификации офлайн-детектора и поиска.
- **Частичная миграция (только горячие файлы)** — нарушает критерий приёмки issue («в e2e не остаётся ожиданий окна»); экономия неполная.
- **Ускорить иначе — распараллелить воркеры** — упирается в живое правило изоляции: фикстура сид-ресета намеренно бросает исключение при воркерах больше одного; смена модели изоляции — отдельная тема, не этого issue.

## User Scenarios

Пользователи этой работы — инженер и CI (код приложения не меняется; для пользователя админки всё как было).

- **S1. Без отмены удаление совершается.** Инженер прогоняет сценарии «удаление дошло до сервера» (12 ожиданий: теги, фото, посетители, должности, платежи, материалы, вкладка без отмены, сценарии кэшей без перезагрузки): клик «×» → окно заморожено → перемотка → синхронизация → DELETE ушёл, сущность исчезла из базы/счётчика. E2E: тесты из приложения (роспись по файлам).
- **S2. С отменой удаление не совершается.** Сценарии «отмена удержала» (10 ожиданий: посещения, платежи, фото, теги, клиенты, занятия, анонимные визиты): клик «×» → проверки внутри замороженного окна → «Отменить» без гонки (окно не тикает) → перемотка → DELETE не отправлялся, строка жива. E2E: тесты из приложения; для unify-caches US-3 — с защитами из ревизии спеки #291 (см. «Перенос наработок #291»).
- **S3. Прогон быстрее примерно на две минуты.** Полный прогон e2e (оба шарда) сокращается на ~121 секунду ожиданий; цифра ориентировочная (см. критерии приёмки). E2E: приёмочная процедура — сравнение суммы длительностей тестов в CI-репортах до/после.
- **S4. Живые зависимости реального времени не задеты.** Офлайн-детектор соединения (бэкофф переподключения), дебаунс-поиск, автоскрытие тостов без отмены работают в реальном времени — пауза часов стоит только вокруг окон отмены и снимается сразу после перемотки. E2E: существующие спецификации этих механик остаются зелёными без правок.
- **S5. Тест отмены не проходит впустую.** В unify-caches US-3 сохраняется короткая проверка «строка действительно скрылась» (бюджет 1 с вместо текущих 3 с — сужение осознанное, из спеки #291) и трекер DELETE-запросов, навешанный до создающего окно действия (уже так). E2E: US-3.
- **S6. Два окна в одном тесте работают.** Сценарий 19 unified-rows открывает окно с отменой, затем окно без отмены — хелпер применяется дважды подряд в одном тесте (легально: после отпуска часов доступна новая пауза). E2E: сценарий 19.

## Behavioral Delta

- **Пользователь админки:** ничего не меняется — правится только тестовый код.
- **Инженер / CI, до:** 23 ожидания по 5,5 с реального времени (~2 минуты сна за прогон, в основном в shard-rest); окно тикает в реальном времени — тест с медленными проверками внутри окна может опоздать с отменой и получить ложный красный (гонка #291).
- **Инженер / CI, после:** 22 ожидания перематываются мгновенной операцией (одно буферное остаётся реальным — см. «Особое 23-е место»); окно не тикает, пока тест выполняет проверки внутри него, — клик «Отменить» не может опоздать, класс тайминговых флейков вокруг окна исчезает; реальное время продолжает течь для всего, что не окно (SSE-бэкофф, дебаунсы, тосты без отмены).

## Техническое решение

**Хелпер в `frontend/admin/e2e/fixtures/helpers.ts`** (общий дом хелперов; сегодня хелпера часов нет — 4 существующих использования копипастят строку установки). Форма — колбэк-обёртка:

```
await withUndoWindow(page, async () => {
  /* клик «×», проверки тоста/скрытия строки, (при undo) клик «Отменить» */
});
```

Механика по шагам (точные имена и сигнатуры — план):

1. **Пауза:** поставить часы страницы на паузу в текущем реальном времени (`page.clock.pauseAt(<сейчас>)` — установка и пауза одной операцией; простая `install()` не останавливает время — окно продолжало бы тикать). Таймеры, запланированные до паузы, остаются реальными и дотикают сами.
2. **Колбэк:** тело теста внутри окна. Ограничение: ничего, зависящего от реального времени (новый ввод с дебаунсом, ожидание SSE-событий), — часы стоят.
3. **Перемотка:** промотать 5 500 мс (`page.clock.fastForward(5_500)`) — таймер коммита, автоскрытие тоста срабатывают вместе и мгновенно; кольцо отсчёта (`setInterval`) при одной перемотке выполняет колбэк интервала не более раза и «перепрыгивает» в конец — ни один из 23 тестов промежуточные тики кольца не проверяет (при появлении такой проверки — пошаговая перемотка).
4. **Отпускание:** `page.clock.resume()` — время идёт дальше. Публичного способа снять подмену таймеров («uninstall») у Playwright нет: до конца жизни страницы таймеры остаются подменёнными, но тикают в реальном темпе; следующему тесту достаётся свежая страница (существующая механика набора). Фейк-время к этому моменту убежало вперёд на 5,5 с от реального — хвосты правимых тестов дат не проверяют (сверено по росписи); при появлении такой проверки — пересмотреть место.
5. **Синхронизация после перемотки (обязательна):** события запросов доходят до слушателей асинхронно, поэтому ассерты счетчиков и базы выполняются не мгновенно после перемотки:
   - позитивные («DELETE ушёл», ≥ 1 / строка исчезла) — через существующий хелпер `commitDeleteWait` (в `fixtures/helpers.ts`, ожидание на стороне Node, часам неподвластно);
   - негативные («DELETE не отправлялся», = 0) — после короткого реального буфера (порядка сотен миллисекунд; точное значение калибрует план): регрессия «отмена не работает» должна успеть проявиться событием запроса до проверки.

**Замена 22 литеральных мест:** каждое `waitForTimeout(5_500)` заменяется на обёртку (пауза ставится до создающего окно действия, перемотка — после проверок внутри окна) плюс синхронизация по правилам выше. Семантика проверок не меняется: что тест доказывал ожиданием — то и доказывает перемоткой.

**Перенос наработок #291 (только unify-caches US-3):** короткая проверка «строка скрылась» (бюджет 1 с, сужение с текущих 3 с) после клика «×»; трекер DELETE навешан до клика «×» (уже так); финальная проверка «DELETE не отправлялся ни разу» остаётся. Остальные места переносятся без изменения семантики проверок.

**Особое 23-е место (замаскированное) — НЕ мигрирует.** `pending-delete-unload-guard.spec.ts:159` (`WINDOW_MS + 500`) стоит после перезагрузки страницы: окно создавалось кликом в старом документе, и его таймер, по механике браузера и собственному комментарию теста, умер вместе с выгруженным документом. Часы нового документа этим мёртвым таймером не управляют — перемотка ничего не доказывает. Ожидание здесь — реальный буфер-доказательство: «если бы таймер каким-то образом пережил выгрузку, за полное окно DELETE успел бы уйти». Замена буфера мгновенной проверкой изменила бы то, что доказывает тест (маскировала бы регрессию «таймер пережил выгрузку»). Место остаётся единственным намеренным реальным ожиданием окна; выпавшая экономия — 5,5 с из ~126 с.

Границы (что мы сознательно НЕ делаем):

- НЕ ставим часы глобально (фикстура уровня сьюта/теста по умолчанию) — заморозит реальные зависимости; только точечно вокруг окон.
- НЕ трогаем спецификации, живущие в реальном времени (офлайн-детектор, серверные события), и НЕ меняем их ожидания.
- НЕ трогаем остальные `waitForTimeout`-литералы (500/300/… мс — короткие паузы не окна) и НЕ меняем 4 существующих использования часов (визуальная стабильность дат — другая задача).
- НЕ меняем код приложения (таймеры контекстов, тосты, кольцо — как есть) и конфиг Playwright.
- НЕ добавляем фиксированные даты в паузу часов: тесты функциональные, даты не стабилизируются (в отличие от визуальных базлайнов).

Критерии приёмки (по issue, уточнены разведкой и панелью):

- В e2e не остаётся литеральных ожиданий окна: `waitForTimeout(5_500)` / `waitForTimeout(5500)` — ноль вхождений (паттерн не задевает собственные `fastForward(5_500)` — ищем только waitForTimeout). Единственное исключение — намеренный реальный буфер `WINDOW_MS + 500` в unload-guard (обоснование выше).
- Сценарии отмены стабильны: ≥3 полных прогона ОБЕИХ шардов (shard-rest — 21 место, shard-schedule — 1) зелёные; сводки флейков до/после ухудшения не показывают.
- Экономия времени — цифра ориентировочная: сумма длительностей тестов в CI-репортах до/после; параллельная работа #415 (шарды, репортер) меняет те же сводки — при конфликте замеров цифра помечается оценкой, а не замером.

## Риски и компромиссы

- **Паттерн «пауза → перемотка» в кодовой базе не опробован** (4 существующих использования только ставят часы до навигации и время не продвигают; комментарий репо «install до goto» относится к стабильности дат, не к подмене таймеров живой страницы). Смягчение: план начинает с пилотного места — unify-caches US-3 (одно окно, undo, наработки #291) — и только после зелёного прогона переносит на остальные 21.
- **Порядок «пауза до создания окна» обязателен** — таймер, запланированный до паузы, реален и перемоткой не управляется; колбэк-форма хелпера делает нарушение порядка невозможным.
- **Замороженное время в колбэке** — всё, что внутри, идёт по стоящим часам: дебаунс нового ввода не сработает, спонтанные таймеры окружения (SSE-тосты) замрут до отпускания. Ограничение «внутри — только работа с окном» снимает; дебаунс, начатый ДО паузы, дотикает реально.
- **Асинхронность событий после перемотки** — без обязательной синхронизации (шаг 5) позитивные ассерты дали бы ложный красный, негативные — ложный зелёный; синхронизация предписана для каждого места.
- **Серверных таймеров нет** — перемотка клиентских часов не может вызвать преждевременное или двойное удаление; если бэкенд когда-нибудь заведёт серверное окно/отложенную задачу, механику придётся пересмотреть (пометка на будущее, не скоуп).
- **Убегание фейк-времени на +5,5 с к хвосту теста** — хвосты правимых тестов дат не проверяют (сверено); отмечено в шаге 4.

## Отчёт по панели (rev1 → rev2)

Панель 6 ревьюеров в контейнере (D-flow): completeness NEEDS_REVISION, consistency / feasibility / simplicity / best-practices SOUND_WITH_CONCERNS (consistency — после одного перезапуска: сбой апстрима модели), security SOUND («атакуемой поверхности нет»). Несущие утверждения проверены по коду перед внесением (включая сверку спорных мест unified-rows и unload-guard).

Принятые замечания (внесены):

- **Блокер «установка часов не замораживает время»** (completeness, best-practices): замена «install» на явную паузу `pauseAt` + называние точных API (`fastForward`, `resume`; публичного uninstall нет) — без этого гонка #291 не устранялась (completeness).
- **Блокер «23-е место не подходит под механическую замену»** (completeness; подтверждено по коду): ожидание после перезагрузки — буфер-доказательство мёртвого таймера; исключено из миграции с обоснованием, критерий приёмки переформулирован (completeness).
- Ассерты после перемотки требуют синхронизации: позитивные — существующий `commitDeleteWait`, негативные — короткий реальный буфер (completeness MAJOR, consistency MAJOR).
- Обёртка-колбэк вместо «двух операций»: порядок и неотменяемость перемотки гарантированы конструкцией (simplicity).
- Multi-window (два окна в одном тесте, сценарий 19) — явно разрешён (completeness MAJOR).
- Критерий стабильности — оба шарда, не только shard-rest (completeness MAJOR).
- Роспись всех 23 мест таблицей (приложение) — сверена по коду (completeness MINOR, consistency MINOR; попутно исправлены две классификации скаута: US-2 и сценарии 16/16b — истечение без отмены, не «отмена удержала»).
- Метрика экономии помечена ориентировочной, конфаунд #415 признан (completeness MINOR).
- Точные grep-паттерны критерия «не остаётся» (completeness MINOR).
- Кольцо при одной перемотке выполняется не более раза — оговорка (best-practices).
- Уточнение про SSE: часами подменяется только setTimeout-бэкофф, не сам EventSource (best-practices).
- Пилот одного места перед переносом остальных + пояснение про комментарий «install до goto» (consistency MINOR, feasibility MAJOR).
- Сверка бюджета US-3: 3 с → 1 с — осознанное сужение из #291 (consistency MINOR).

Отклонённые замечания (с причинами):

- «Mid-test установка часов противоречит конвенции репо» (feasibility, в жёсткой форме) — комментарий «до goto» относится к задаче стабильности дат; подмена таймеров на живой странице поддерживается Playwright; различие зафиксировано в рисках, пилот закрывает остаточный риск.
- «Ограничение „минимум работы внутри“ не гарантирует отсутствия ранее вооружённых таймеров» (feasibility MAJOR) — так и задумано: ранее вооружённые таймеры реальны и дотикают сами; риск-формулировка уточнена, менять механику не требуется.
