# Спека: харднинг e2e-теста undo в unify-caches (US-3) — стабилизация вокруг окна отложенного удаления

- **Issue:** #291 (test-debt)
- **Дата:** 2026-10-07
- **Статус:** rev2 (панель 6/6: правки внесены; см. «Отчёт по панели»)
- **Скоуп:** только тестовый код `frontend/admin/e2e/unify-caches.spec.ts` (тест US-3); код приложения не меняется.

## Контекст

В админке есть механика отложенного удаления с отменой: клик «×» на строке посещения сразу убирает строку из таблицы (оптимистичное удаление) и показывает тост с кнопкой «Отменить»; настоящее DELETE-обращение к серверу откладывается на 5 секунд. Если за окно нажали «Отменить» — строка возвращается, запрос так и не уходит; если не нажали — по истечении окна удаление совершается.

Механика в приложении: `frontend/admin/contexts/PendingActionsContext.tsx` (очередь отложенных действий: таймер коммита, отмена, тихий no-op при поздней отмене — запись удаляется из очереди до срабатывания коммита), тост живёт в `frontend/admin/contexts/UIContext.tsx` (автоскрытие через те же ~5 с).

Тест `frontend/admin/e2e/unify-caches.spec.ts`, US-3 «undo restores the row and no DELETE was sent» (строки ~193–258 на main 5d90a560) проверяет полный цикл: удалить → отменить → строка вернулась, DELETE не отправлялся. Трекер запросов — `page.on('request')`.

**Замечание о нумерации:** issue #291 называет тест «US-2» — это ошибка источника (доклада #94); тест с отменой — US-3, а US-2 в том же файле — другой тест («удаление остаётся удалённым после переключения вкладки», без отмены). Метка была неверна уже на базе #94; разведка 2026-10-07 подтвердила по живому дереву.

## Проблема

16.09.2026 в полном регрессионном прогоне (workers=1, режим shard-rest) US-3 упал один раз; отдельно и в CI — стабильно зелёный. Повторов с 17.09 не зафиксировано. Разведка по живому дереву:

- **Гонка тайминга внутри 5-секундного окна.** Между появлением тоста и кликом «Отменить» тест выполняет четыре проверки: тост виден (до 3 с), строка скрыта (`not.toBeVisible`, до 3 с), DELETE-счётчик не рос (мгновенно), кнопка «Отменить» видна (до 3 с, `unify-caches.spec.ts:238-239`). Худший случай — ≈9 с проверок съедает 5-секундное окно с запасом: к моменту клика запись уже удалена из очереди, отмена — тихий no-op, строка не возвращается, ассерт возврата (3 с) падает. Какой именно ассерт упал в прогоне 16.09 — лог не сохранился; атрибуция механике гонки — реконструкция по коду (единственный согласованный механизм, объясняющий «зелёный отдельно / красный в сьюте»).
- **Ассерт возврата строки — 3 с.** Под compile-нагрузкой полного прогона рендер возвращённой строки может занять больше; клик при этом был своевременным.
- Усилитель «синтетические DOM-события» уже устранён перезаписью #138 (19.09): вход в тест — реальная навигация и реальный клик; сама гонка окна не тронута — тело US-3 не менялось с даты создания issue.
- Код приложения с 17.09 менялся многократно (#285, #286, #243, #284, #324, #345, #397), но семантика тайминга окна отмены не менялась.

## Концепт (выбранный и отвергнутые)

**Выбран: точечный харднинг US-3 — «минимум работы внутри окна, широкий таймаут после клика».** Внутри 5-секундного окна тест делает только то, без чего клик «Отменить» невозможен (готовность тоста); всё медленное и всё проверяемое без ограничения во времени — после клика. Паттерны уже живут в этом же файле и соседних спеках; репозиторий уже принял такой стиль (poll-ассерты, ожидания с явными бюджетами).

Отвергнутые подходы:

- **`page.clock` для US-3** (детерминированное окно без реального ожидания) — дубль уже заведённой карточки #417 (Backlog: page.clock вместо 22 реальных ожиданий по 5,5 с во всех спеках, включая этот тест). Механизм будет сделан там одним скоупом; дублировать его в #291 — двойная работа и конфликт скоупов.
- **Аннотированный скип с тегом `deferred:`** (вторая ветка DoD issue) — потеря e2e-покрытия ключевой пользовательской механики отмены; тест зелёный во всех прогонах с 17.09 (одиночный флейк за историю). Скип не оправдан.

## User Scenarios

Пользователи этой работы — инженер и CI (код приложения не меняется; для пользователя админки всё как было).

- **S1. Отмена внутри окна, полный цикл.** Инженер (или CI) прогоняет US-3: удалили строку → строка скрылась → тост → «Отменить» нажимается в первые секунды окна → строка вернулась в таблицу → за всё время DELETE-запрос не отправлялся. E2E: US-3 (переработанный).
- **S2. Стабильность под нагрузкой полного прогона.** CI гоняет весь сьют shard-rest (компиляция на лету, медленный рендер); US-3 больше не зависит от того, сколько времени съели рендер и проверки до клика — бюджет проверок внутри окна ограничен 5 с против текущих ≈9 с. E2E: US-3 в составе полного прогона; приёмка — ≥3 полных прогона сьюта без падений US-3 (см. «Критерий приёмки»).
- **S3. Честный красный при реальной поломке.** Если сломалась механика отмены (строка не возвращается) или оптимистичного удаления (строка не скрывается — ловится 1-секундной проверкой шага 2), US-3 красный с различимой причиной: мягкая диагностика при падении показывает DELETE-счётчик и момент клика, «реальная регрессия» и «остаточная гонка границы» различимы по журналу. E2E: US-3 (свойство ассертов и диагностики; контролируется ревью плана).
- **S4. Оптимистичное удаление остаётся под полным покрытием.** Полная (3-секундная) проверка «строка скрыта сразу после клика ×» остаётся в файле — её несёт US-2 («удаление остаётся удалённым»), где она выполняется вне гонки с окном отмены; в US-3 остаётся ограниченная 1-секундная версия против пустого прогона. E2E: US-2 (без изменений).

## Behavioral Delta

- **Пользователь админки:** ничего не меняется — правится только тест.
- **Инженер / CI, до:** US-3 в полном прогоне может упасть из-за гонки: четыре проверки с бюджетами до 3 с (тост, скрытие строки, счётчик, кнопка) в худшем случае занимают ≈9 с и съедают 5-секундное окно отмены → клик «Отменить» попадает после тихой границы → строка не возвращается → красный тест при рабочем продукте; плюс ассерт возврата с бюджетом 3 с падает на медленном рендере.
- **Инженер / CI, после:** US-3 стабильно зелёный в полном прогоне: бюджет проверок внутри окна ограничен 5 с (обычно — доли секунды), клик выполняется сразу после гейта готовности кнопки; возврат строки ждётся с широким бюджетом (10 с); семантика проверок (скрытие, возврат, отсутствие DELETE, истечение окна) сохранена целиком, при падении причина различима по диагностике. Длительность теста не растёт (новых реальных ожиданий нет; финальное ожидание истечения окна 5,5 с остаётся как есть).

## Техническое решение

Переработка US-3 (только тело теста, `frontend/admin/e2e/unify-caches.spec.ts`). Трекер DELETE-запросов `page.on('request')` навешивается в сетапе до клика «×» — как в текущем тесте; порядок «трекер раньше действия» обязателен и сохраняется.

1. Клик «×» на строке — как сейчас.
2. Строка скрылась (оптимистичное удаление): `not.toBeVisible` c бюджетом 1 000 мс — ограниченная проверка, чтобы US-3 не проходил впустую при регрессии оптимистичного удаления (если удаление сломано — честный красный здесь, а не зелёный «возврат» несуществовавшего ухода).
3. Готовность тоста: ассерт `[data-testid="toast-info"]` содержит «Удалено», бюджет 3 000 мс (сигнал, что окно тикает).
4. Готовность кнопки: кнопка «Отменить», скоупированная тостом (не глобальный локатор — защита от strict-mode при второй подходящей кнопке на странице), видима, бюджет 1 000 мс — последний гейт перед кликом (actionability-ожидание самого клика не должно тратить окно).
5. Немедленный клик «Отменить». Между 4 и 5 — никаких ассертов и ожиданий.
6. Возврат строки: ассерт видимости строки посещения, бюджет 10 000 мс (дефолт `expect.timeout` из `playwright.config.ts`) — после клика ограничения окна нет, отмена уже произошла.
7. Финал без изменений: `waitForTimeout(5_500)` (истечение окна) + ассерт «DELETE не отправлялся ни разу» по трекеру. Позиция ожидания — после реальных действий теста: с клика «×» к этому моменту прошло ≥5,5 с реального времени в любом раскладе, окно гарантированно истекло, «ложный зелёный» из-за недожданного окна невозможен.

Бюджет времени внутри 5-секундного окна (между кликом «×» и кликом «Отменить»): 1 с (скрытие) + 3 с (тост) + 1 с (кнопка) = до 5 с в предельном случае деградации всех трёх подряд, в норме — доли секунды. Против текущих ≈9 с худшего случая — вдвое короче, и предельный случай требует одновременной деградации трёх проверок, а не одной.

Диагностика при красном (различение причин падения): перед жёсткими ассертами возврата и финальным «no-DELETE» тест фиксирует мягкую диагностику — текущее значение DELETE-счётчика и момент клика «Отменить» относительно клика «×» (attach к `testInfo` или soft-вывод). При падении возврата-ассерта отчёт показывает, успел ли клик, и уходил ли DELETE — «реальная регрессия отмены» и «остаточная гонка границы» различимы по журналу.

Выносимые из US-3 проверки и их новое место:

- «DELETE не отправлялось до отмены» как отдельная промежуточная проверка — сводится к финальному ассерту «не отправлялся ни разу за весь тест» (сильнее: покрывает обе фазы одним утверждением; значение счётчика видно в диагностике при падении).
- Полная (3-секундная) проверка «строка скрыта» остаётся в US-2 того же файла, где она выполняется без гонки с окном отмены (удаление без отмены). В US-3 остаётся ограниченная 1-секундная версия (шаг 2).

Границы (что мы сознательно НЕ делаем):

- НЕ вводим `page.clock` — это скоуп #417 (он же заменит финальное `waitForTimeout(5_500)`).
- НЕ меняем код приложения (таймеры `PendingActionsContext`/`UIContext`, поведение тихого no-op остаются как есть).
- НЕ пытаемся воспроизвести флейк прогонами (DoD-ветка «reproduced ≥1/3») — разведка установила корневую механику, воспроизведение дорого и не нужно для фикса.
- НЕ трогаем остальные тесты файла и конфиг Playwright (если при реализации всплывёт нехватка общего 60-секундного бюджета теста — точечный `test.setTimeout` для US-3, не конфиг).

Критерий приёмки (S2, DoD issue): корневая причина установлена разведкой (DoD-ветка «root cause identified» — выполнена), фикс = харднинг ожиданий (эта спека); приёмка — не менее 3 полных прогонов сьюта shard-rest без единого падения US-3 (CI и/или локально по дев-воркфлоу), результат фиксируется в PR.

## Риски и компромиссы

- **Проверка «строка скрыта» в US-3 урезана до 1 с** — компромисс между «минимум работы внутри окна» и «тест не проходит впустую»: полная версия остаётся в US-2 (без гонки с окном), 1-секундная ловит грубую регрессию оптимистичного удаления в самом US-3. Встречный риск — ложный красный на экстремально медленном первичном коммите рендера; принят: к моменту проверки страница уже отрисована (auto-wait клика «×» прошёл), падение раннее и легко диагностируется, в истории тестов эта проверка не падала и с меньшим бюджетом ожидания.
- **Бюджет 10 с на возврат строки** — не маскирует поломку: при сломанной отмене условие не станет истинным и тест честно красный; при медленном рендере — зелёный. Дефолт `expect.timeout` = 10 000 мс подтверждён по `playwright.config.ts`.
- **Общий бюджет теста 60 с.** Худший путь складывается из: автосид-ресет фикстуры (внутри таймаута теста), навигации хелпера входа (несколько ассертов по 5 с), окна проверок до 5 с, возврата до 10 с, финального ожидания 5,5 с, экшн-таймаутов кликов (до 15 с каждый по конфигу) и finally-очистки. Арифметика предельного случая близка к лимиту — при реализации контролировать: если не хватает — точечный `test.setTimeout` для US-3 (см. границы), не конфиг.
- **Остаточная гонка границы** — не устранена полностью: предельный случай «одновременно деградировали все три внутриоконные проверки (1+3+1 с)» оставляет клик у самой границы. Против текущего положения (≈9 с худший, деградация любой одной проверки уже опасна) риск сжат на порядок; полное устранение — за `page.clock` (#417).
- **Атрибуция исходного падения 16.09** — реконструкция (лог прогона не сохранился); спека опирается на живую механику кода, а не на трейс того прогона.

## Отчёт по панели (rev1 → rev2)

Панель 6 ревьюеров в контейнере (D-flow): completeness NEEDS_REVISION, consistency / feasibility / best-practices SOUND_WITH_CONCERNS, simplicity SOUND; security дважды дал отчёт ниже порога размера — формально skipped, содержимое обоих — «атакуемой поверхности нет» (спека меняет только тестовый код). Несущие утверждения ревьюеров проверены по коду перед внесением.

Принятые замечания (внесены):

- Вернуть ограниченную проверку «строка скрыта» (1 с) — без неё US-3 мог проходить впустую при регрессии оптимистичного удаления (completeness, MAJOR).
- Диагностика при красном (DELETE-счётчик + момент клика) — различение причин падения (completeness, MAJOR).
- Гейт-ассерт кнопки «Отменить» (1 с, скоуп тоста) перед кликом — actionability клика не должен тратить окно; скоуп закрывает strict-mode риск глобального локатора (completeness, feasibility).
- Математика худшего случая: четыре проверки ≈9 с, а не «3+3» (consistency, completeness — подтверждено по коду `unify-caches.spec.ts:238-239`).
- Критерий приёмки для S2: ≥3 полных прогонов сьюта (completeness).
- Честный расчёт 60-секундного бюджета (фикстура, навигация, экшн-таймауты, finally) и оговорка про `test.setTimeout` (completeness).
- Оговорка об атрибуции: лог падения 16.09 не сохранился (completeness).
- Явная фиксация порядка «трекер раньше клика ×» (best-practices).

Отклонённые замечания (с причинами):

- «Заменить `waitForTimeout(5_500)` — антипаттерн, ложный зелёный при CI-замедлении» (feasibility MAJOR, best-practices) — позиция ожидания после реальных действий гарантирует ≥5,5 с от клика «×»; замена механизма — скоуп #417, дублировать нельзя.
- «Дефолт `expect.timeout` = 10 с не проверен» (feasibility MAJOR) — подтверждено по `playwright.config.ts` двумя другими ревьюерами, ссылка в спеке.
- «Трекер `page.on('request')` может пропустить sendBeacon» (feasibility) — трекер существует в тесте с даты его создания и спекой не меняется; риск не относится к правке.
- «US-2 не подтверждён» (feasibility) — подтверждён по коду (`unify-caches.spec.ts:134`, проверки `:165-168`, `:178-184`).
