# #311 — Обязательная секция визуальных проверок в дизайн-спеках

- Issue: #311
- Дата: 2026-10-08
- Поток: standard (концепт утверждён пользователем на Gate A, протокол auto-design)
- Статус: rev3 — гейт B пройден 2026-10-08. Решения пользователя: зеркало superagents включено в объём; канонический маркер N/A; канон обязан задавать формулировку проверяемых пунктов (не проза). rev2 — после панели 6 ревьюеров (прогнана на сессионной модели: контейнер приостановлен, модель хостовых панельных агентов была недоступна)

## Контекст и проблема

Конвейер memo заканчивает визуальные фичи финальной сверкой «как выглядит»: скрипт
`scripts/visual-compliance-check.sh` читает из дизайн-спеки секцию
`## Visual Compliance Checks`, извлекает машинные проверки (строки с `data-testid`,
`aria-*`, текстом интерфейса в кавычках), запускает Playwright и сверяет экран с
требованиями. Строки без машинных подсказок попадают в MANUAL_REVIEW и не влияют
на вердикт.

Разведка 2026-10-08 установила:

1. Хостовые скиллы, через которые пишутся все спеки (`design-phase`, `auto-design`),
   о секции не знают. Результат: 0 из 43 спек за 18.09–08.10 её несут.
2. Скрипт при пустом списке проверок пишет предупреждение и возвращает успех
   (раздел «Extract Checks from Spec», `scripts/visual-compliance-check.sh`): гейт
   G4.5 проходит впустую, визуальная сверка фактически не выполняется.
3. Требование «UI-спеки несут секцию» уже есть в каноне контейнерного архитектора
   (`.opencode/agents/architect.md`, Step 2 п.3), но месяц не исполнялось — правило
   без механизма исполнения не работает.
4. Вызов скрипта из `.opencode/skills/subagent-driven-development/SKILL.md` идёт по
   несуществующему пути `.opencode/scripts/visual-compliance-check.sh` (скрипт живёт
   в `scripts/`).
5. Политики одного гейта расходятся: architect.md гоняет цикл фикса (3 итерации
   кодера), subagent-driven-development останавливается сразу.

Файлы с теми же правилами живут в каноне superagents (`~/dev/superagents`):
`architect.md`, `subagent-driven-development`, канон фазы дизайна с перечнем
обязательных секций спеки. По правилу самого architect.md общее изменение сначала
правится в каноне superagents, затем синхронизируется в memo.

## Решение (концепт утверждён пользователем 2026-10-08; детали — после панели)

1. **Контракт спеки.** Каждая новая спека несёт секцию `## Visual Compliance Checks`:
   - визуальная фича — чек-лист из **проверяемых пунктов, а не прозы** (решение
     пользователя 2026-10-08): каждый пункт = конкретный элемент интерфейса +
     проверяемое утверждение о нём, и **хотя бы один пункт несёт машинную подсказку**
     (`data-testid`, `aria-*`, текст интерфейса в кавычках); строки ручной проверки
     допустимы только рядом хотя бы с одной машинной;
   - невизуальная фича — маркер не-применимости `- N/A` (см. грамматику ниже).
     Визуальность определяется на фазе дизайна и фиксируется в спеке, а не решается
     в момент прогона.
2. **Механизм исполнения.** Скрипт ужесточается, код возврата 3 «спека без
   визуальных проверок» возвращается в трёх случаях: секции нет; секция пустая;
   секция без маркера N/A, в которой ноль машинных подсказок (панель: без этого
     дыра «гейт впустую» выживала бы в самом вероятном виде — прозаический чек-лист).
   Явный N/A — зелёный «not applicable» без запуска Playwright.
3. **Маршрут красного.** Код 3 — дыра дизайна, а не баг кода: цикл фикса кодером НЕ
   запускается. Архитектор докладывает менеджеру; менеджер возвращает карточку в
   `In Design` существующим механизмом (комментарий на issue + статус), пользователь
   уведомляется отчётом сессии. Код 1 (проверки провалены) — прежний цикл фикса;
   код 2 — инфраструктура. Вызывающая сторона обязана ветвиться по буквальным кодам
   1/2/3 (обёртка «любой ненулевой = ошибка» допустима только в test-all.sh).
4. **Канон-дом.** Формат секции и контракт N/A живут в `design-phase` SKILL.md;
   коды возврата — единственный канон в шапке скрипта (самодокументация исполняемого
   файла), скиллы несут указатели. `auto-design` и architect.md — краткие указатели;
   subagent-driven-development — исправленный путь вызова и маршрут кода 3.

## User Scenarios

- **US-1.** Дизайн-сессия пишет спеку визуальной фичи → секция несёт чек-лист
  проверяемых пунктов, хотя бы один с машинной подсказкой → парсер извлекает
  проверки, сверка выполняется.
  E2E: расширение `scripts/test-visual-compliance-parser.js` — образец секции с
  `data-testid`/`aria-*`/кавычками даёт automatable-проверки.
- **US-2.** Дизайн-сессия пишет спеку невизуальной фичи → секция содержит только
  маркер N/A → скрипт завершается успехом «not applicable» без Playwright и без
  проверок окружения (сервер не нужен). E2E: тест парсера (N/A → applicable false,
  пустой список) + smoke скрипта (exit 0, «not applicable» в выводе, машина без
  dev-сервера).
- **US-3.** IMPL завершён, спека без секции, с пустой секцией или без единой машинной
  подсказки → код 3 с сообщением, каким действием это лечится (возврат в дизайн)
  → менеджер возвращает карточку в `In Design` (комментарий + статус), код не
  правится. E2E: тест скрипта на трёх вариантах → exit 3; маршрут — правки
  architect.md/manager.md, проверяются ревью спеки/плана.
- **US-4.** Локальный `test-all.sh` продолжает проходить по канарейке
  `2026-06-19-current-user-scenarios.md`. Канарейка сегодня не несёт ни одной
  машинной подсказки (8 строк прозы) — по новому контракту она получает минимум
  одну строку с машинной подсказкой по живым `data-testid` приложения, остальной
  текст секции не трогается. E2E: smoke-прогон скрипта по канарейке (exit 0).
- **US-5.** Автор спеки узнаёт о контрактной дыре до имплементации: скилл
  design-phase после написания секции прогоняет парсер без Playwright и видит
  «ноль машинных подсказок / нет секции» на месте, а не после целого цикла кодинга.
  E2E:covered US-1 тестами парсера; строка инструкции — ревью спеки/плана.

## Behavioral Delta

| Роль | До | После |
|---|---|---|
| Дизайн-сессия (хост) | секция не требовалась | обязана определить визуальность: чек-лист проверяемых пунктов (не проза) с ≥1 машинной подсказкой или N/A |
| G4.5 (контейнер) | спека без секции или без подсказок → «успех» впустую | код 3, красный |
| Менеджер (контейнер) | дыра спеки не детектировалась | возврат карточки в `In Design` по коду 3, без цикла фикса |
| Скрипт сверки | 0 проверок → предупреждение + exit 0 | нет секции/пусто/без подсказок → exit 3; N/A → «not applicable» без Playwright |
| test-all.sh | канарейка без подсказок, зелёный впустую | канарейка с ≥1 подсказкой; тесты парсера и smoke подключены в прогон |
| Харнесс-доки | требование только в architect.md, битый путь в скилле | канон в design-phase, указатели, путь починен, маршрут кода 3 в architect/manager/subagent-driven |
| Канон superagents | те же дыры в копиях скиллов | зеркальная правка трёх файлов канона (после ОК пользователя) |

## Технические детали

- **Грамматика N/A.** Канонический маркер: единственная содержательная строка
  секции, после тримма равная `- N/A` или `N/A` (регистр не важен). Длинное тире и
  прочие начертания НЕ принимаются: дефис/среднее тире опознаются ненадёжно и молча
  превращают секцию в обычный чек-лист (решение панели, два ревьюера независимо).
  Отменяют маркер только другие строки-маркеры чек-листа; прозаические абзацы и
  горизонтальные линии — нет (парсер их уже пропускает). Правило применяется только
  когда обычный разбор дал ноль машинных подсказок и покрывает все три имени секции
  (`Visual Compliance Checks` / `UI Verification` / `Visual Checks`).
- **Порядок стадий скрипта** (панель: иначе N/A-ветка невозможна без живого сервера):
  аргументы → существование файла спеки → парсинг → [нет секции → exit 3] → [N/A →
  печать вердикта «not applicable» и немедленный exit 0, до проверок зависимостей,
  dev-сервера, Playwright, генерации отчёта] → [применимая секция → прежний конвейер].
- **Сбой парсера ≠ дыра спеки.** `|| true` на вызове парсера убирается: ненулевой
  выход парсера → exit 2 (инфраструктура), нулевой выход с нулём проверок →
  по контракту выше. Файл checks.json перезаписывается в начале каждого прогона
  (протухший результат прошлого прогона не должен выдаваться за сегодняшний).
- **Форма checks.json.** Голый массив → объект `{ "applicable": bool, "checks": [...] }`.
  Это ломающее изменение, но потребитель один — сам скрипт; правятся ровно два
  внутренних места: подсчёт `CHECKS_COUNT` (`.length` → `.checks.length`) и чтение
  массива в генерируемом Playwright-раннере. Стадия отчёта при N/A-выходе не
  вызывается (results.json не существует — ранний выход выше).
- **Коды возврата.** 0 — прошли (или not applicable); 1 — есть проваленные; 2 —
  инфраструктура; 3 — спека без визуальных проверок. Таблица в шапке скрипта —
  единственный канон кодов.
- **Защита от подмены (панель, безопасность).** Маршрут кода 3 у менеджера включает
  проверку по истории git: если секция спеки менялась после утверждения спеки
  (гейт B), возврат не выполняется молча — NEEDS_APPROVAL: вероятен обход гейта
  дописыванием N/A поверх проваленной сверки. Сообщение кода 3 адресует возврат
  карточки в дизайн, а не «добавь секцию или N/A» (не подсказывать обход как
  равноправный вариант).
- **Попутно (в ту же правку скрипта, оценка безопасности):** пути в вызовах
  `node -e` передаются аргументами процесса вместо интерполяции в JS-строку.
- **Правки харнесс-доков:**
  - `design-phase` SKILL.md — канон: обязательная секция, два наполнения, грамматика
    N/A, канонический шаблон формулировки пункта и запрет сплошной прозы (решение
    пользователя 2026-10-08): строка вида
    `- [ ] <элемент интерфейса> — <проверяемое утверждение>` с машинной подсказкой
    (`data-testid="…"`, `aria-label="…"`, текст интерфейса в кавычках «…») хотя бы в
    одном пункте; пример канонической строки и пример нарушения (сплошная проза —
    не пункт) приводятся в скилле; требование ≥1 машинной подсказки; шаг
    самопроверки парсером после написания;
    fast-track (без спеки) контракт не касается; если спека в fast-track всё же
    пишется — несёт N/A;
  - `auto-design` SKILL.md — краткий указатель на канон;
  - `.opencode/agents/architect.md` — Step 2 п.3: указатель на формат + грамматика
    N/A; Step 4.5: явная ветка кода 3 (не цикл фикса, доклад менеджеру) и кода 2;
  - `.opencode/agents/manager.md` — маршрут кода 3: детерминированный возврат
    (комментарий + `In Design`) с git-проверкой неприкосновенности секции; сегодня
    возврат — решение пользователя, для кода 3 вводится исключение (решение
    пользователя 2026-10-08);
  - `.opencode/skills/subagent-driven-development/SKILL.md` — исправленный путь
    `scripts/visual-compliance-check.sh`, маршрут кода 3, для кода 1 — указатель на
    политику architect.md (канон цикла фикса);
  - **канон superagents (решение пользователя 2026-10-08 — включено)**: зеркальная
    правка трёх файлов — `architect.md` (строка секции + Step 4.5),
    `subagent-driven-development` (путь + маршрут), канон фазы дизайна (перечень
    обязательных секций, включая шаблон формулировки пунктов).
- **Тесты и прогон** (панель: тесты парсера сегодня не исполняются нигде):
  обновлённый `test-visual-compliance-parser.js` (US-1/US-2 + фиксация обработки
  код-блоков внутри секции и канонического заголовка `##`) и два smoke скрипта
  (код 3; N/A без сервера) включаются в `scripts/test-all.sh`. test-all трактует
  любой ненулевой код сверки как красный — не меняется.
- **Не меняем (границы объёма).** 43 спеки 18.09–08.10 не перерабатываются; CI
  (`.github/workflows/`) не трогается; скриншот-механика и семантика MANUAL_REVIEW
  сохраняются; полная переработка текста канарейки за пределами добавления одной
  машинной подсказки — нет.

## Риски

- Ручной прогон по старой спеке без секции получит код 3 — сообщение называет
  точное лечащее действие (возврат в дизайн / N/A при не-визуальной фиче).
- Форма checks.json меняется ломающе — потребитель один (сам скрипт), оба места
  правки перечислены; тесты закрывают.
- Обход гейта подменой секции закрыт менеджерской git-проверкой + формулировкой
  сообщения кода 3; полная автоматическая сверка неприкосновенности не строится
  (дорого, лишний механизм).
- Панель прогнана на сессионной модели (контейнер приостановлен, модель хостовых
  панельных агентов `GLM-5.3-Flash` исчезла из каталога) — состав перспектив
  сохранён, вердикты получены; при восстановлении контейнера перепрогон не требуется.
