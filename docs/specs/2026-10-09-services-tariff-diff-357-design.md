# Спека: обновление тарифов услуги на месте + мягкая ссылка посещения (#357)

- **Дата:** 2026-10-09, ревизия 3 (панель 6/6: пять отчётов + консистенс на longcat с опозданием — свёрстано; Gate B pending)
- **Проблема:** GH issue #357
- **Поток:** стандартный дизайн (спека → панель → план)

## Контекст (самодостаточно, issue не нужен)

Справочник услуг: услуга (service) имеет список тарифов (tariff: название, описание, цена, возрастная аудитория). Посещение (visit) — строка внутри записи (record) — при создании выбирает тариф и хранит:

- `price` / `custom_price` — **снимок** цены на момент создания; все суммы и статистика (итог записи, «Потрачено» клиента, статусы оплаты) считаются только по этим полям, из тарифа ничего не выводится;
- `tariff_id` — необязательная (nullable) ссылка на строку тарифа; используется только для показа ярлыка «название тарифа + цена» у посещения (VisitorRow, таблица посещений в модальном окне записи) и переподбора при редактировании. Фильтров, аналитики и экспортов через эту ссылку нет; диалоги семейства удалений уже умеют показывать посещение без тарифа как «Без тарифа, {цена}».

**Текущая механика обновления услуги.** Сервисный слой при обновлении услуги пересоздаёт ВСЕ тарифы: стирает все строки тарифов услуги и вставляет их заново с новыми идентификаторами. Так делают оба маршрута: полное обновление (PUT `/api/v1/services/{id}`) — всегда, и частичное (PATCH) — когда поле `tariffs` присылается. Форма редактирования в интерфейсе всегда присылает полный набор полей, включая весь список тарифов, т.е. обычное «поменял цену → сохранить» пересоздаёт все тарифы. Отдельного маршрута правки одного тарифа не существует — тарифы управляются только списком внутри услуги.

**Поломка.** Внешний ключ `visits.tariff_id → tariffs.id` без `ondelete` (запрет удаления занятой строки). Как только у тарифа появляется хоть одно посещение, стереть его строку нельзя: пересоздание падает ошибкой целостности → API отвечает 422 INTEGRITY_VIOLATION (общая ошибка «нарушена целостность базы», без деталей). В сид-данных так «заняты» 4 услуги из 7 (s2, s3, s5, s7): **любое** сохранение такой услуги невозможно — даже правка названия или тегов. E2e-тесты обходят это выбором «свободных» услуг и PATCH без тарифов.

**Тот же разрыв в удалении услуги.** Семейный сценарий удаления услуги стирает её тарифы, не договариваясь с посещениями, — удаление услуги с посещениями на её тарифах падает о ту же защиту базы.

## Концепт (согласован с пользователем 2026-10-09)

Два решения, каждое необходимо; ни одного недостаточно по отдельности:

1. **Обновление тарифов на месте (diff по идентификатору).** Схема записи тарифа получает необязательное поле `id`. При обновлении услуги сервер сравнивает присланный список с существующим по `id`: строка с известным `id` (найден среди тарифов этой услуги) — обновляется в той же строке таблицы, идентификатор сохраняется; строка без `id` — вставляется как новая; `id`, не найденный среди тарифов услуги (чужой или протухший после параллельного удаления), — 422 валидации с указанием строки (молчаливая вставка нового ряда прятала бы ошибки формы и порождала дубли); строка, чей `id` отсутствует в присланном списке, — удаляется. Идентификаторы уже круговоротят через форму редактирования (форма переносит их от ответа сервиса к следующему сохранению), интерфейсу менять почти ничего; обязательная сопутствующая правка — клиентская схема типов, которая сегодня молча отбрасывает идентификатор (см. api-client ниже).
2. **Мягкая ссылка посещения (SET NULL).** Внешний ключ `visits.tariff_id` получает поведение «при удалении тарифа — обнулить ссылку». Удаление тарифа разрешено всегда: посещения сохраняют строку и цену-снимок, ссылка обнуляется, ярлык тарифа у посещения исчезает. Тот же режим уже используется в схеме (фотографии без владельца, журнал аудита). Почему без diff этот шаг опасен: пересоздание всех тарифов при каждом сохранении превратилось бы из громкой ошибки в тихую массовую потерю ссылок у всех посещений услуги.

Инвариант «при создании посещения тариф выбран» остаётся заботой интерфейса (форма уже требует/подбирает тариф, включая автоподбор по возрасту); контракт создания посещения не меняется.

## Behavioral Delta (что меняется для пользователя)

| Сценарий | До | После |
|---|---|---|
| Сохранить правку занятой услуги (цена тарифа, название, теги, материалы) | Невозможно: общая ошибка базы 422 | Сохраняется успешно |
| Правка цены/названия тарифа | (для «свободных» услуг) строка пересоздаётся с новым идентификатором | Тариф сохраняет тот же идентификатор; посещения продолжают ссылаться |
| Удалить тариф, на который есть посещения | Блокирует всё сохранение услуги | Удаляется; посещения сохраняют цену, теряют ярлык тарифа |
| Удалить услугу с посещениями на её тарифах | Падает ошибкой базы | Проходит; посещения остаются с ценой, без ссылки |
| Сохранение устаревшей формы (тариф удалён в другой сессии) | Молчаливая пересборка строк, дубли | 422 с указанием строки — форма перезагружается |
| Создание посещения, выбор тарифа в форме | — | Без изменений |

Побочный эффект для истории: у посещений, чей тариф удалили, ярлык тарифа исчезает навсегда (название в посещении не хранится); при следующем редактировании записи тариф будет предложен заново. Суммы и статусы не меняются ни в каком сценарии.

## User Scenarios

Каждый сценарий отображается на E2E-тест (US-1..US-4 — в действующую спеку `frontend/admin/e2e/services-crud.spec.ts`, US-5 — в спеку семейного сценария удаления услуги; сид: s5 «Ручная лепка» с занятыми тарифами t5a/t5c, s7 «Морской пейзаж» с t7a/t7c).

- **US-1. Правка существующего тарифа занятой услуги.** Администратор открывает s5, меняет цену и название тарифа t5a, сохраняет → успех; повторное открытие формы показывает новые значения; у существующих посещений ссылки и цены-снимки не изменились. E2E: открыть s5 → правка цены и названия → сохранить → успех; проверка API: `id` тарифа совпал с исходным, `visits` без изменений.
- **US-2. Удаление занятого тарифа.** Администратор удаляет из списка тариф t5c (есть посещения), сохраняет → успех; у прежних посещений t5c ярлык тарифа скрылся (бейдж исчез), цены не изменились; последующее редактирование записи с таким посещением сохраняется с пустым выбором тарифа. E2e: правка s5 с удалением t5c → сохранение ок → у затронутых посещений `tariff_id = null`, `price` прежний.
- **US-3. Добавление тарифа к занятой услуге.** Администратор добавляет новый тариф в s7, сохраняет → новая строка появилась, существующие тарифы не пересозданы (идентификаторы стабильны). E2E: добавить тариф → сохранить → `id` t7a/t7c неизменны, у нового есть `id`.
- **US-4. Правка услуги без изменения тарифов.** Администратор меняет только название s5 → тарифы не пересозданы (идентификаторы стабильны, посещения при делении не отвязались). E2E: правка названия → сохранить → все `id` тарифов совпали с исходными. Регресс на тихий churn.
- **US-5. Удаление услуги с занятыми тарифами.** Администратор удаляет услугу s7 через семейный сценарий (сверка ожиданий) → удаление проходит; её посещения остались в записях с ценой и без ссылки на тариф («Без тарифа»). E2E: dry-run → подтверждение → запись содержит прежние посещения, `tariff_id = null`, суммы записи не изменились.

## Технические изменения

**Backend.**
1. Схема `TariffUpdate` (и вложенный в `ServiceUpdate` список): необязательное поле `id: str | None`. Дубликат `id` в одном списке → 422 валидации.
2. `ServiceService.update` / `ServiceService.patch`: общий helper тарифного diff — по `id`: найденный у этой услуги → `UPDATE` строки; без `id` → `INSERT`; не найденный у услуги (чужой или протухший) → 422 валидации; отсутствующий в присланном списке → `DELETE`. Весь diff выполняется в одной транзакции (действующий декоратор транзакции сервисного слоя). Семантика отсутствия поля — по действующему контракту, различается по глаголам: PUT — полная замена, отсутствие поля = пустой список = удалить все (текущий код при отсутствии поля уже стирает все тарифы); PATCH — отсутствие поля или `null` = тарифы не трогаются. Пустой список `[]` легален на обоих маршрутах (услуга без тарифов возможна и при создании — схема допускает пустой список).
3. Миграция Alembic: пересоздать FK `visits.tariff_id → tariffs.id` с `ondelete=SET NULL` (drop + create constraint; данные не трогаются). Таблицы небольшие (десятки–сотни строк) — стандартная миграция без `CONCURRENTLY` достаточна; downgrade пересоздаёт строгий FK, уже обнулённые ссылки остаются нулями. ORM-связь Visit→Tariff каскадов не получает — обнуление делает база. В тестах на SQLite обязательна pragma `foreign_keys=ON`, иначе `ondelete` молча не работает.
4. Семейный сценарий удаления услуги не меняется: тарифы стираются раньше строки услуги в одной транзакции (как сегодня); стирание больше не упирается в защиту базы, посещения отвязываются автоматически на уровне базы.

**api-client (`packages/api-client`).** Обязательная правка: тарифная схема записи (`TariffCreateSchema`, вложена в `ServiceUpdateSchema`) сегодня молча отбрасывает неизвестные ключи — идентификатор тарифа не доходит до запроса. Добавить необязательное поле `id` в тарифную схему. Метод `updateService` не меняется.

**Фронтенд (admin).** Существенная часть — ничего: форма уже переносит `id` тарифов в сохранении. Проверить и зафиксировать тестом, что вложенный список тарифов не вырезает `id` при пересборке формы. Поведение ярлыка посещения при отсутствии тарифа не меняется — бейдж скрывается (так уже в коде); источник цены ярлыка — текущая цена тарифа (существующее поведение), суммы при этом всегда из снимка посещения.

**Канон-правки (едут этим же PR спеки после Gate B).**
- `docs/domain-rules/services.md`: «Tariffs are hard-deleted and recreated on every Service update» → «Tariffs are updated in place by id: matched rows updated, new inserted, removed deleted; deleting a referenced tariff nulls the visit link (price snapshot stays)».
- `docs/domain-rules/visits.md`: правило ссылки — nullable, `ondelete=SET NULL`; цена-снимок первична, ссылка справочная; посещение переживает удаление тарифа.

## Границы (что сознательно НЕ делаем)

- Не заводим отдельный маршрут правки одного тарифа — тарифы управляются списком внутри услуги, как и раньше.
- Не меняем контракт создания посещения и требовательность формы к выбору тарифа — это слой интерфейса, он уже работает; услуга без тарифов возможна и сегодня, отдельно не валидируется.
- Не строим сценарий развязки «отвязать N посещений» перед удалением тарифа — мягкая ссылка делает его ненужным; undo для отвязки не заводим.
- Не добавляем подсказку «использован в N посещениях» у строки тарифа в форме (осознанность удаления) — украшение, при желании отдельной задачей позже.
- Не меняем источник цены ярлыка посещения (текущая цена тарифа вместо снимка посещения) — существующее поведение, отдельная задача при желании.
- Не заводим оптимистичную блокировку/версионирование обновления услуги — конкуренция решается «последний выигрывает», как сегодня.
- Не батчим операции diff (executemany/CTE) — списки тарифов состоят из единиц строк.
- Не трогаем workaround в e2e `services-tags.spec.ts` (выбор «свободных» услуг) — тесты остаются как есть; новые сценарии US-1..US-5 добавляются отдельной спекой.
- Аудит-журнал не расширяем: тарифы не являются аудит-сущностью и ей не становятся.

## Допущения и риски

- Цены-снимки и суммы не зависят от тарифа ни в одном потребителе (проверено разведкой по коду: итоги записи, «Потрачено», статусы оплаты, аудит — всё по сохранённым полям посещения).
- Конкурирующие сохранения одной услуги — последний выигрывает, как и сегодня; diff не расширяет окно гонки по сравнению с текущим пересозданием (в обоих случаях строки, отсутствующие в присланном списке, удаляются). Устаревшая форма (параллельное удаление тарифа) получает честный 422 вместо молчаливых дублей.
- Обнуление ссылки необратимо (название тарифа в посещении не хранится) — принято пользователем осознанно.
- Панель: пять отчётов штатно; consistency-ревьюер дочитан со второй попытки на longcat (первая — таймаут 25 минут, сессия возобновлена с требованием выдать отчёт) — три находки сверстаны в эту ревизию: несуществующее имя e2e-файла (`services.spec.ts` → действующий `services-crud.spec.ts`), неверное утверждение про отбрасывание идентификатора клиентской схемой, уточнение обязательности правки клиента.
