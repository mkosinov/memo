# Спека: применение ответа PATCH посещения к кэшу по проекции полей запроса (#359)

- **Дата:** 2026-10-09, ревизия 2 (панель 5/6: completeness NEEDS_REVISION, feasibility/simplicity/best-practices SOUND(_WITH_CONCERNS), security SOUND; consistency — skipped: оба прогона невалидны — первый умер по апстриму, второй разобрал чужую спеку #357 из каталога спек рабочей копии; находки ревизии 1 сверстаны ниже)
- **Проблема:** GH issue #359 (найдено при IMPL #284, follow-up №2)
- **Поток:** стандартный дизайн (спека → панель → план)

## Контекст (самодостаточно, issue не нужен)

Запись (record) содержит таблицу посещений (visit — строка записи: клиент, тариф, цена, статус оплаты). В таблице посещений модального окна записи клетки редактируются на месте: возраст, тариф, цена, статус. Анонимное посещение (без клиента) при заполнении имени/возраста превращается в именованное: создаётся посетитель, и посещению проставляется ссылка на него.

**Механика изменений на сервере.** Частичное обновление посещения — истинный PATCH: необязательные поля, сервер пишет в строку только поля, присутствовавшие в теле запроса. Два одновременных PATCH с разными полями (например `visitor_id` и `tariff_id`+`price`) не портят данные на сервере — каждый трогает свои колонки. Ответ каждого PATCH — плоский список колонок строки (`id, record_id, visitor_id, tariff_id, price, custom_price, status, created_at, updated_at`), снятый в транзакции этого запроса; имени клиента и названия тарифа в ответе нет — интерфейс берёт их из отдельных справочников в кэше.

**Механика применения ответа на клиенте.** Мутации правки клеток посещения после ответа сервера записывают объект посещения целиком в кэш записи (React Query: канонический ключ записи + зеркала в списках записей), в порядке прибытия ответов; инвалидации после таких правок нет — кэш-синхронизация ответом и есть механизм обновления. Исключение — смена статуса: она сегодня делает инвалидацию (рефетч) вместо записи ответа.

**Поломка.** Смена возраста анонимной строки — одно действие пользователя — отправляет сразу два запроса: PATCH `visitor_id` (назначение созданного посетителя) и PATCH `tariff_id`+`price` (переподбор тарифа по возрасту). Оба не ждутся (fire-and-forget). Ответ «тариф» сериализуется из строки, ещё не знающей про нового посетителя (и наоборот). Кто из ответов пришёл последним — тот перезаписывает объект посещения в кэше целиком, затирая чужое поле. До ближайшего рефетча (другая мутация, открытие окна заново) таблица может показывать «Аноним» при назначенном сервером клиенте или старый тариф/цену после подтверждённой смены; итоговая сумма записи считается по кэшу и наследует устаревшую цену. То же окно возникает при любых двух быстрых правках разных клеток одной строки (тариф + статус, цена + статус) и при двух быстрых правках одной клетки (цена): поздно прибывший старый ответ откатывает значение.

Разведка по живому дереву подтвердила: серверная часть корректна, блокировок/версионирования не требуется; дефект — только в применении ответа к клиентскому кэшу. Предложенные в issue альтернативы (сериализация запросов, версионирование) решают не ту проблему: данные на сервере не расходятся.

## Концепт

Механизм из двух правил, зеркальных дисциплине сервера («тронул только свои колонки»):

1. **Проекция.** Ответ PATCH применяется к строке кэша только по полям, присутствовавшим в теле запроса; значения — из подтвердившего их ответа сервера. Поля не из запроса ответом правки не затираются никогда — порядок прибытия ответов перестаёт портить чужие поля.
2. **Защита от гонки одного поля.** По каждому полю побеждает последний **выпущенный** запрос, а не последний прибывший ответ: мутация ведёт счётчик правок по посещению, запрос помнит свой номер и состав своих полей; ответ записывает поле, только если по этому полю не выходил более поздний запрос. Две быстрые правки одной клетки не откатываются поздним старым ответом.

Отвергнутые альтернативы (разведка + панель):

- **Версионирование/блокировки на сервере** — добавляет контракт (версии, отказ 409 устаревшей записи), чтобы починить клиентский кэш; данные сервера корректны и так, а честные одновременные правки разных полей начало бы ложно отклонять.
- **Сериализация PATCH одной строки на клиенте (очередь/мьютекс)** — тот же видимый результат ценой ожидания и нового механизма; порядок ответов не гарантирует порядок транзакций, т.е. и это не лечит первопричину.
- **Инвалидация запроса записи вместо записи ответа (канонический паттерн TanStack «invalidate в onSettled»)** — действующая архитектура репозитория — кэш-синхронизация ответом без рефетча (отдельный модуль, закреплён в каноне); переход на инвалидации — смена архитектуры всего слоя записей, не этой задачи. Единственное серверное производное родительской записи, зависящее от правок клеток, — статус записи — обновляется рефетчем смены статуса (см. ниже); итог записи считается на клиенте по кэшу посещений.

Смена статуса посещения подводится под общий механизм: своё поле (`status`) она теперь применяет проекцией из ответа, а её действующая инвалидация остаётся — она обновляет статус родительской записи (бейдж), который сервер пересчитывает при смене статуса посещения.

## Behavioral Delta (что меняется для пользователя)

| Сценарий | До | После |
|---|---|---|
| Смена возраста анонимной строки (имя+возраст за одно действие) | Строка может показаться «Аноним» при назначенном клиенте — до ближайшего рефетча | Строка сразу именованная, тариф/цена новые |
| Две быстрые правки разных клеток строки (тариф + статус, цена + статус) | Поздний ответ может откатить чужую правку клетки | Обе правки стоят одновременно |
| Две быстрые правки одной клетки (цена) | Поздний более ранний ответ может вернуть старое значение | Побеждает последняя правка; итог записи от её цены |
| Смена статуса посещения | Строка обновляется по рефетчу | Строка — сразу из ответа; статус записи (бейдж) — рефетчем, как раньше |
| Число запросов, контракты API, данные на сервере | — | Без изменений (рефетч смены статуса сохраняется) |

## User Scenarios

Каждый сценарий отображается на E2E-тест. US-1..US-3 — новая спека `frontend/admin/e2e/visits-patch-consistency.spec.ts` с детерминированным порядком ответов: перехват `page.route` PATCH посещений, выбранный ответ удерживается асинхронным хендлером (пауза ≥ 0.5 с перед пропуском — запас против джиттера CI; ожидания через waitFor, не фиксированные паузы). Прецеденты перехвата в спеках `activity-deferred-delete.spec.ts`, `client-phone-typeahead.spec.ts`. US-4..US-5 — регрессия действующих спек.

- **US-1. Возраст анонимной строки.** Администратор в записи с анонимным посещением выбирает имя и возраст → строка сразу показывает имя клиента и переподобранный тариф с ценой, не откатываясь в «Аноним». E2E: перехват PATCH `visitor_id`, удержание его ответа (ответ `tariff_id`+`price` проходит раньше), отпускание → в строке клиент и новый тариф/цена; проверка API: посещение содержит и `visitor_id`, и новый `tariff_id`/`price`.
- **US-2. Две правки разных клеток.** Администратор меняет тариф и сразу статус → в строке стоят обе правки. E2E: выбор тарифа, ответ его PATCH приходит свободно; тут же смена статуса, ответ статуса удерживается и отпускается последним (его инвалидация-рефетч тогда читает состояние после обоих коммитов) → строка содержит новый тариф/цену и новый статус, бейдж статуса записи обновлён.
- **US-3. Две правки цены.** Администратор дважды быстро правит цену → в строке и в итоге записи второе значение. E2E: правка цены, ответ удерживается; вторая правка цены, её ответ проходит → отпустить первый ответ → строка и итог записи показывают вторую цену (поздный старый ответ не откатывает).
- **US-4. Обычное назначение клиента (без гонки).** Анонимная строка получает имя/возраст в спокойном темпе → текущее поведение сохраняется (строка именованная, тариф переподобран). E2E: действующие проверки превращения анонимного посещения проходят без изменений.
- **US-5. Undo удаления посещения.** Удаление посещения и отмена — восстановление строки из снимка работает как раньше. E2E: действующие проверки undo удаления посещения проходят без изменений.

## Технические изменения

**Фронтенд (admin), только клиент — сервер не трогаем.**

1. `lib/cache/recordCacheSync.ts`: новый helper частичной правки посещения, построенный на действующей машинерии обхода кэша (канонический ключ записи + зеркала списков, существующий обходчик; нового реестра ключей не заводим). Семантика: (а) перезаписать только перечисленные поля; (б) `updated_at` — неявное всегда-применяемое поле из ответа (в теле запроса его нет); (в) посещения нет в кэше — ничего не делать (строка удалена или кэш сброшен; истину вернёт рефетч — «зомби»-вставка удалённой строки запрещена); (г) новые ссылки на объекты (иммутабельная сборка, не мутация поля in place) — иначе дедупликация структур TanStack пропустит ре-рендер; (д) список полей — по ключам сериализованного тела запроса (JSON; ключ со значением `undefined` в тело не попадает и полем не считается).
2. `hooks/useRecordMutations.ts`, правки посещений: мутация ведёт по посещению монотонный счётчик правок; каждый запрос фиксирует номер и состав полей; ответ вызывает helper только с полями, не перекрытыми более поздним запросом. Проекция выполняется только на успехе — путь ошибки не меняется (действующие тосты/восстановление, у превращения анонимной строки — действующий сверочный GET). Смена статуса дополнительно применяет своё поле проекцией (инвалидация для бейджа записи сохраняется).
3. Прочие записыватели объекта посещения не меняются: создание/анонимное создание вставляют новую строку (целиком — корректно), undo удаления восстанавливает снимок целиком (авторитетное последнее состояние удалённой строки), рефетчи остаются полными записывателями.
4. Юнит-тесты (vitest): проекция полей; null-значение поля запроса очищает поле кэша (не пропускается); ответ, перекрытый более поздним запросом, не пишется; посещение отсутствует в кэше — no-op; зеркала списков обновлены; иммутабельность ссылок.

**Канон-правки (едут этим же PR спеки после Gate B).**

- `docs/domain-rules/visits.md`: правило кэша — ответ PATCH посещения применяется к кэшу записи проекцией по полям тела запроса, по полю побеждает последний выпущенный запрос; цельная перезапись строки из ответа правки запрещена.
- `docs/domain-rules/records.md`: дополнение к правилу кэш-синхронизации записи — конкурентные правки посещения сходятся без инвалидации; рефетч не требуется; смена статуса сохраняет рефетч только ради статуса родительской записи.

## Границы (что сознательно НЕ делаем)

- Не меняем сервер: нет версионирования, блокировок строк, compare-and-swap, изменений контракта PATCH.
- Не строим очередь/сериализацию запросов правок на клиенте и не добавляем задержек к действиям пользователя.
- Не переводим слой записей на канонический паттерн TanStack «инвалидация в onSettled» — действующая архитектура кэш-синхронизации ответом закреплена в каноне; её смена — отдельная архитектурная задача, не эта.
- Не меняем путь ошибок правок клеток (тосты, сверочный GET превращения) — проекция только на успехе.
- Не синхронизируем две вкладки браузера в реальном времени — у вкладок разные кэши, лечит их рефетч по фокусу (действующее поведение).
- Не трогаем гонку перерасчёта статуса родительской записи на сервере (чтение-запись без блокировки в транзакции правки посещения): окно микроскопическое, самолечится любой следующей правкой; кандидат в отдельную задачу при проявлении в реале.
- Не меняем путь обновления справочника посетителей кэша после создания посетителя — действующее поведение превращения строки сохраняется как есть.
- Не проецируем серверные производные поля вне тела запроса (если сервер когда-нибудь начнёт пересчитывать их при правке): такие поля подхватятся ближайшим рефетчем; в текущем контракте их нет.
- Undo удаления сохраняет цельную восстановку снимка — отдельные сценарии консолидации undo не строим.

## Допущения и риски

- Ответ PATCH посещения плоский и отображается на колонки строки один-к-одному (проверено разведкой по схеме и мапперу маршрута) — проекция по ключам запроса полна и не теряет значимых полей.
- Имя клиента в строке берётся из отдельного справочника посетителей, а не из ответа правки (разведка); справочник наполняется действующим механизмом превращения строки до/вместе с проекцией `visitor_id` — закреплено регрессией US-4, отдельной синхронизации не заводим.
- Остаточное окно рефетча: рефетч (например, от смены статуса или чужой мутации) может перезаписать строку устаревшим снимком, только если его GET прочитал строку до чужого коммита, а ответ пришёл после ответа правки (джиттер сети) — редкий транзиент, самолечится любым следующим рефетчем; механизм не строим.
- Ошибка более поздней правки того же поля оставляет поле на последнем подтверждённом значении до ближайшего рефетча — существующий класс поведения ошибок, не расширяем.
- Порядок транзакций на сервере не определён: для разных полей это ненаблюдаемо (колонки не пересекаются), для одного поля порядок на сервере и в клиентском счётчике совпадают в штатных случаях (запросы выпускаются из одного клиента по порядку); сетевой реролл обоих запросов одной клетки — за границами задачи.
- Панель: consistency-ревьюер пропущен (два невалидных прогона: апстрим-сбой и разбор чужой спеки из рабочей копии — модель ушла в каталог `docs/specs` мимо поданного файла); уязвимость панели (слабой модели доступен весь каталог спек) — кандидат на ужесточение сценария панели отдельным решением пользователя.
