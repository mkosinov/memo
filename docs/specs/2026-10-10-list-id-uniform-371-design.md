# Спека #371 — Единый вход GET-списков: одна модель-как-query, `?id=` на всех

Дата: 2026-10-11 (rev4 — после второй панели; rev3 — смена концепта по решению пользователя на гейте B: форма «модель целиком как query» для всех GET, включая одиночные скалярные) · Статус: Gate B (ждёт ОК пользователя) · Скоуп: backend API. Фронтенд и api-client не трогаем.

## 1. Контекст и цель

Механизм машинного сужения списков (`?id=X&id=Y` — повторные query-ключи, набор UUID) заведён задачей #232: им владеют поле `id` модели `PaginationParams` (`schemas/pagination.py`) и общий хелпер `ids_in_predicate` (`repositories/search.py`). Контракт работает не везде, а форма входа списков размазана по двум местам декларации — модели и сигнатуре обработчика.

**Полная инвентаризация GET-маршрутов (46, сверка с живым деревом 2026-10-11):**

| Класс | Маршруты | Судьба |
|---|---|---|
| Уже форма 3 (модель-как-query) | clients, records, records/view, photos (свои `*ListParams`), masters (`PaginationParams` напрямую, скаляров нет) | не трогаем (**5**; их словарные `/all` — часть конверсий ниже) |
| Форма «Depends-модель + скалярные сиблинги», `?id=` молча игнорируется | services, visitors, activities, payments, materials, tags, staff, visits, audit-logs, positions | **конверсия** (10) |
| Гибрид: Depends + сиблинг `id` + скаляры — `?id=` работает, но контракт в двух местах | locations | **конверсия** (1) |
| Чисто-скалярные GET (один параметр в сигнатуре) | 5 × словарные `/all` **со** `status` (services, materials, locations, staff, masters), фото-галерея `/web` (`activity_id`), итоги оплат `/totals` (`record_ids`), поиск клиента `/get` (`phone`) | **конверсия** (**8** маршрутов с параметрами) |
| Без query-параметров | health, me, my, user_settings, SSE events, авторы аудита, все точечные `GET /{id}`, словарные `/all` тегов и должностей | вне задачи |

Итого конверсий: **19 маршрутов** (11 пагинированных + 8 одиночных). Проводная дельта только у десятки (появляется работающий `?id=`); остальные 9 — чисто структурные, провод не меняется.

Цель (решение пользователя, гейт B rev2): **вход каждого GET-маршрута с query-параметрами — одна pydantic-модель, инжектируемая как `Annotated[<Model>, Query()]`**. Никаких скалярных сиблингов и миксов «Depends-модель + скаляры» в дереве не остаётся. Новые фильтры любых списков с этого момента заводятся полями схем, а не аргументами сигнатуры. Попутно `?id=` начинает работать единообразно на всех 16 пагинированных списках.

Ограничение FastAPI (PR #12481), породившее зоопарк форм: query-модель нельзя смешивать со скалярными query-параметрами одного обработчика; кроме того, под `Depends()` list-поле модели (`id`) молча классифицируется как тело и теряется. Обе проблемы снимаются одним ходом — все параметры (включая `id`) живут в модели, а модель инжектируется как query.

## 3. Behavioral Delta

| Поведение | До | После |
|---|---|---|
| `?id=X&id=Y` на 10 эндпоинтах | неизвестный ключ, молча игнорируется, полный список | **пересечение**: остаются только записи из набора, удовлетворяющие всем остальным фильтрам; дедуп повторов, ≤100 различных (`MAX_LIST_IDS`) |
| `?id=<мусор>` (не-UUID, пустое значение, `X,Y` одной строкой, >100 различных) на 10 эндпоинтах | молча игнорируется | **422 VALIDATION_ERROR** — как на шести работающих (#232) |
| `?id=<несуществующий, но валидный UUID>` на 10 эндпоинтах | полный список | пустой список (200) — сужение не расширяет видимость |
| OpenAPI: параметр `id` | не опубликован на 10 эндпоинтах | опубликован на всех 16 пагинированных списках |
| 5 нетронутых списков + 8 одиночных GET | — | **провод не меняется** (те же ключи/дефолты/422; FastAPI разворачивает поля query-модели в те же индивидуальные параметры — перегенерация клиентов не нужна). Для десятки единственная проводная новинка — работающий `id`; `page`/`per_page` у них и сегодня на проводе |
| Форма входа в коде | 3 формы: модель-как-query (5), Depends+скаляры (10), Depends+сиблинг+скаляры (1), плюс 8 скалярных GET | **одна форма**: модель-как-query на всех GET с параметрами; `Depends(PaginationParams)` и сиблинг-паттерн исчезают из дерева |
| Фронтенд / api-client | — | не меняются (потребителей `?id=` на десятке нет — разведка; API внутреннее) |

## 4. Технический дизайн

### 4.1 Одиннадцать пагинированных списков — `XListParams` через кирпни

Каждому — свой класс в схеме своей сущности, композицией живых кирпней: `SortParams[<своё Literal>]` (механика #367) + `PaginationParams` (несёт `page`/`per_page`/`id`). Обработчик: `params: Annotated[XListParams, Query()]`, чтение `params.<поле>`; все скалярные строки сигнатуры уходят. Инвентарь (дефолты — как сегодня, пин для регресса С8):

| Эндпоинт | Класс (состав) | Переносимые поля |
|---|---|---|
| services | `ServiceListParams(SortParams[ServiceSortBy], PaginationParams)` | `status=ACTIVE`, `q` (мин 2 / макс 100), `material_id` |
| materials | `MaterialListParams(SortParams[MaterialSortBy], PaginationParams)` | `status=ACTIVE`, `q` (2/100) |
| tags | `TagListParams(SortParams[TagSortBy], PaginationParams)` | `q` (2/100) |
| staff | `StaffListParams(SortParams[StaffSortBy], PaginationParams)` | `status=ACTIVE`, `q` (2/100) |
| locations | `LocationListParams(SortParams[LocationSortBy], PaginationParams)` | `status=ACTIVE`, `q` (2/100); `id` приезжает наследованием `PaginationParams`, сиблинг `IdListQuery` удаляется |
| visitors | `VisitorListParams(PaginationParams)` | `q` (2/100); scope-зависимость остаётся зависимостью (не query-параметр) |
| activities | `ActivityListParams(PaginationParams)` | `date_from`, `date_to`, `q`, `service_id` |
| payments | `PaymentListParams(PaginationParams)` | `record_id` |
| visits | `VisitListParams(PaginationParams)` | `record_id` |
| audit-logs | `AuditLogListParams(PaginationParams)` | `user_id`, `action`, `entity`, `entity_id`, `date_from`, `date_to` |
| positions | `PositionListParams(PaginationParams)` | — (только унаследованные) |

- Ограничения скаляров переводятся в поля один-к-одному: `min_length/max_length` → `Field(...)`, перечисления и `date` — те же аннотации; ни одно Query()-свойство одиннадцати списков не теряется (сверка разведки).
- Поле `id` унаследовано от `PaginationParams` и **по построению зеркалит** контракт сиблинг-алиаса: тот же тип элементов (UUID-only), тот же `BeforeValidator` дедупа до капа, тот же `max_length=100` → 422 (`uuid_parsing`/`too_long`). Идентичность поведения на всех 16 списках закрепляется матрицами С1/С3.
- Механика сортировки #367 не меняется: карты ключей и `apply_sort` остаются, ветка «`sort_by=None` → дефолтный порядок сущности» остаётся у маршрута — меняется только место чтения значения (`params.sort_by` вместо скаляра). Ветвление сотрудников по значению сортировки (выбор ветки сервиса) сохраняется на `params.sort_by`.
- Мастера остаются при `Annotated[PaginationParams, Query()]` — уже форма 3, пустой подкласс не заводим.

### 4.2 Восемь одиночных скалярных GET — в схемы (решение пользователя: фильтрам расти в моделях)

| Маршруты | Модель | Поле (дефолт — как сегодня, сверен) |
|---|---|---|
| 5 × словарные `/all` со `status` (services, materials, locations, staff, masters) | один общий класс `ArchiveStatusParams` | `status: ArchiveStatus = ACTIVE` (у всех пяти сегодня `Query(ArchiveStatus.ACTIVE)` — сверено по коду) |
| фото `/web` (публичная галерея) | `PhotoWebListParams` | `activity_id` (UUID; мусор → 422 как сегодня) |
| оплаты `/totals` (агрегат) | `PaymentTotalsParams` | `record_ids: list[str]` (повторные ключи, кап 200 → 422 `too_long` — как сегодня) |
| клиенты `/get` (lookup по телефону) | `ClientPhoneLookupParams` | `phone` (мин 3 → 422 как сегодня) |

Одно-полевые классы — сознательное решение пользователя (единая форма; фильтрам расти в схемах), а не функциональная необходимость — наблюдение ревью простоты принято к сведению. Словарные `/all` тегов и должностей без параметров — не трогаем. Примечание на будущее (не эта задача): если `/all` обрастёт содержательными фильтрами — это сигнал консолидировать его с основным списком, а не расширять.

### 4.3 Сервисный слой: три зазора (без изменений к rev2)

1. `StaffService.list_join_masters`: параметр `ids` + `ids_in_predicate(Staff.id, ids)` в базовую выборку **до** join-размножения строк и **до** счётного подзапроса — строки и total сужаются согласованно (каждая строка сужаемого сотрудника исчезает целиком, fan-out расхождение не даёт); арбитр — тест С5, обязательный до слияния.
2. `VisitService.list`: параметр `ids` + предикат после фильтра `record_id`, до счётного подзапроса.
3. `list_audit_logs`: параметр `ids` + конъюнктивный предикат к существующим фильтрам, до счётного запроса.

**Инвариант композиции:** предикат `ids` добавляется конъюнктивно в тот же WHERE — сужение пересекается с любыми фильтрами и охватом и не может их обойти (валидный UUID вне охвата → 200 + пусто). Строчно-уровневого разграничения видимости у списков нет — однотенантный доступ персонала, охрана на уровне маршрута; сохранность guard'ов в 19 переписанных сигнатурах закрепляется явно (§6).

### 4.4 Чистка: форма «Depends + скаляры» исчезает из дерева

- `IdQueryParam` (`schemas/pagination.py`) и локальный `IdListQuery` (`api/v1/locations.py`) удаляются — потребителей не остаётся.
- Все `Depends(PaginationParams)` исчезают; `PaginationParams` остаётся базовым кирпнем, всегда инжектируемым через `Annotated[..., Query()]`.
- Устаревшие докстринги переписываются: оговорка о Depends-дропе list-полей (`pagination.py`), замечание `SortParams` «фолбэк живёт только у скалярных роутов» (`common.py`).

### 4.5 Стражи (двое: контракт на проводе + форма в коде)

- **Страж контракта (OpenAPI)**: CI-тест читает **сгенерированную** схему приложения (`app.openapi()` — query-модель уже развёрнута в индивидуальные параметры), и каждый GET-маршрут с `response_model = PaginatedResponse[...]` обязан объявлять query-параметр `id`. Предикат точный (16 списков отвечают этим конвертом; bare `/all` со плоским `response_model=list[...]` и SSE не попадают). Класс стража #367: сегодня зелёный по построению, ценность — первый новый список без контракта падает на первом CI-прогоне.
- **Страж формы (структурный, из ревью best-practices)**: CI-греп-тест по `backend/src` — запрещены `IdQueryParam`, `IdListQuery`, `Depends(PaginationParams)`. Форма инъекции на проводе не видна, поэтому OpenAPI-страж дрейф формы не ловит — структурный страж ловит (возвращение старой формы падает прогоном).

### 4.6 Проверенные опоры и чек-пойнты (ответ панели осуществимости)

Центральное допущение — «query-модель с list-полем корректно разворачивается в повторные ключи `?id=`» — **не гипотеза, а живой прод-факт**: клиенты, записи и фото работают в этой форме с #232 (`ClientListParams(SortParams[ClientSortBy], PaginationParams)` иsiblings), их `?id=`-сужение покрыто существующим тестом пагинации (`test_api_pagination_params.py` держит списки `?id=`-энфорсеров). Композиция кирпней `SortParams[...] + PaginationParams` — живой прецедент #367. Чек-пойнты импл на всякий случай: (1) первая конверсия любого из 11 списков стартует со smoke-прогона `?id=X&id=Y` + сверки OpenAPI; (2) первая конверсия со scope-зависимостью (visitors/activities) — smoke со scope (их существующие тесты уже гоняют scope и остаются регресс-сеткой).

## 5. Границы — что сознательно НЕ строим

- **Новые фильтры/сортировки** где их нет — не добавляем; задача про форму входа и контракт `id`. Новые появятся полями схем.
- **Фронтенд и api-client** — без потребителей `?id=` параметры в клиент не добавляем (паттерн сериализации повторных ключей уже есть в clients).
- **Консолидация `/all` с основными списками** — не эта задача (см. примечание §4.2).
- **SSE `/events`**, маршруты без query-параметров — вне задачи.
- **Апгрейд FastAPI** ради снятия #12481 — вне скоупа (форма «всё в модели» легальна без обходов; регрессионный риск всего приложения не обоснован).
- **Кап на сырые (до дедупа) повторы `?id=`** отдельным лимитом — не вводим: граница унаследована от #232 без изменений (потолок задаёт длина URL на стороне сервера/прокси; кап 100 различных значений сохраняется).

## 6. Тест-план

**API-тесты (`backend/tests/`):**

- **Сужение (С1)**: параметризованный тест по 7 «готовым» — строки + **total**; `?id=X&id=X` → дедуп; `?id=<валидный несуществующий>` → 200 + пусто; `?id=X&page=<за диапазоном>` → 200 + пусто.
- **Пересечение фильтров (С2)**: services — архивная услуга при дефолтном `status=ACTIVE` → пусто; явный `status=ARCHIVED` + активная → пусто.
- **422 (С3)**: параметризованно × 10 — мусор, пустое значение, запятая-склейка, 101 различный.
- **Регресс форм (С4)**: локации — сужение/422 как раньше; positions — сужение; OpenAPI публикует `id` на 16 списках. Матрицы сужения/422 прогоняются по всем 16, не только по 10.
- **staff (С5)**: **обе ветки** — строки + total под `?id=` (включая join-ветку с `ids`-зазором).
- **visits (С6)**: `record_id` + `id` вместе.
- **audit-logs (С7)**: `?id=` в сочетании с `user_id`/`action`/`entity`/`entity_id`/датами.
- **С8-регресс**: существующие тесты 5 нетронутых списков, всех 11 конверсий и 8 одиночных маршрутов — зелёные без правок ожиданий; дефолты сверяются по таблицам §4.1–4.2; новые 422-пины одиночных: `status=<мусор>` на `/all`, не-UUID `activity_id` на `/web`, `phone` короче 3 на `/get`, `record_ids` сверх 200 на `/totals`.
- **Охрана маршрутов**: одна без-аутентификационная проверка (401/403) на конвертированном маршруте — pin сохранности guard'ов в переписанных сигнатурах.
- **Служебный тест пагинации** (`test_api_pagination_params.py`): списки эндпоинтов расширяются сознательно (10 новых `?id=`-энфорсеров; локации уже были).
- **Стражи (§4.5)**: OpenAPI-страж (16 × `id`) + структурный CI-греп (запрещённые паттерны старой формы).

## 7. Поправки разведки к премиссам issue

- Пункт 1 issue («id уже enforced через PaginationParams у view-builder'ов») уточнён: работает форма `Annotated[Model, Query()]`, а не Depends.
- Пункт 3 issue («перевести на Annotated Query») — верное направление, но больше, чем предполагал автор: аннотированная форма требует **всех** параметров обработчика внутри модели (смешивание со скалярами запрещено #12481), поэтому конверсия тянет перенос каждого скалярного фильтра в схему — не одну строку на эндпоинт.
