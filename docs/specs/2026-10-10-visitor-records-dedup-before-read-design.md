# Спека #380: одно чтение строки на мутацию — дедупликация SELECT в путях посетителей и записей

- Issue: #380 (источник — ревью IMPL журнала действий #344, отложенное замечание архитектора; коммиты-носители дубля: PR #376).
- Дата: 2026-10-10. Статус: рев.1 после панели (4 отчёта основного прогона + перезапуск двух упавших; правки вшиты), готова к Gate B.
- Поток: стандартный DESIGN. Классификация fast-track предложена на Gate A и отклонена пользователем: правка меняет подписи методов сервисного слоя и их документированные контракты («только типы-значения») — это открытый вопрос контракта, быстрый трек его не допускает.

## Контекст и проблема

Журнал действий (#344) фиксирует состояние «как было» до каждой мутации. В трёх путях эта «до»-строка читается из базы дважды за один запрос — один раз ради журнала, второй раз самой мутацией:

1. **Удаление посетителя (одиночное).** `VisitorService.delete` читает строку посетителя для метки журнала (`backend/src/services/visitor.py:253`), затем ядро каскада `_delete_cascade` перечитывает ту же строку (`backend/src/services/visitor.py:219`).
2. **Полное изменение записи (PUT).** Сценарий `update_record` читает `existing` для «до»-половины diff (`backend/src/usecases/records.py:279`), затем `RecordService.update_row` перечитывает строку (`backend/src/services/record.py:527`).
3. **Частичное изменение записи (PATCH).** То же: `patch_record` читает `existing` (`backend/src/usecases/records.py:372`), `RecordService.patch_row` перечитывает (`backend/src/services/record.py:556`).

Чтение `BaseRepository.get` / `RecordService.get` всегда исполняет SQL-SELECT (`backend/src/repositories/generic.py:287`, `backend/src/services/record.py:418`) — карта идентичности сессии повторный запрос не убирает. Итог: каждый такой мутационный запрос несёт один лишний SELECT. Поведение (ответы API, содержимое журнала) корректно — избыточен только запрос.

Скаут-разведка 2026-10-10 подтвердила все три места по живому дереву (вердикт `actual`); поздние правки этих файлов (#345/#401, #324, #327, #357, линт-волны) дубль не убрали. Ложных дублей нет: `delete_record` уже переиспользует свой пробный read для метки журнала (`usecases/records.py:477` → `:514`), пути создания before-read не имеют.

## Концепт (согласован на Gate A): «одно чтение на мутацию»

Строка читается один раз в начале сценария и передаётся вниз — в метод, выполняющий мутацию, — необязательным параметром. Без параметра метод читает сам, как сейчас: у методов остаются оба режима, поведение остальных вызывающих не меняется.

- `_delete_cascade(db_session, visitor_id, *, visitor=None)` — одиночное удаление передаёт уже прочитанную для журнала строку; каскад клиента вызывает без параметра (см. границы). Ядро проверяет rowcount удаления строки посетителя: 0 затронутых строк → `False` (паритет с нынешним поведением «перечитал — нет строки — False», см. «Гонки» ниже).
- `update_row(db_session, id, *, existing=None, …)` — сценарий передаёт строку, с которой уже снял «до»-значения.
- `patch_row(db_session, id, fields, *, existing=None)` — то же для частичного изменения.

Приём параметра защищён проверкой соответствия: `existing.id == id` (и `visitor.id == visitor_id`); расхождение — `ValueError`. Это программная ошибка вызывающего, не пользовательский ввод; проверка снимает риск молчаливого журнала «не по той строке» при будущем неверном использовании. Явно переданный `existing=None` трактуется как «параметр опущен» — метод читает сам; отдельного состояния «вызывающий знает, что строки нет» параметр не несёт (такой вызывающий не вызывает мутацию вовсе).

Почему параметр необязательный, а не обязательный (по замечанию simplicity-панели): у `_delete_cascade` он обязан быть необязательным — каскад клиента вызывает ядро без строки; у `update_row`/`patch_row` прямые сервисные тесты вызывают методы без предпрочтения; цена двойного режима — одна строка ветвления. Обязательный параметр дал бы три разные формы на трёх местах и перестроил бы сервисные тесты — дороже без выигрыша.

Альтернатива «передавать словарь/DTO вместо ORM-строки» отклонена: мутация пишет через живой ORM-объект — словарь не убирает внутреннее чтение, значит не решает задачу.

Соответствие канону (`docs/domain-rules/service-layer.md`): правило 4 коридора запрещает помощникам принимать **чужие** объекты; здесь передаётся собственная строка сервиса, которая и так пересекает границу слоя в обе стороны (`get` возвращает ORM-строку записи, `update_row`/`patch_row` возвращают её же). Докстринги `update_row`/`patch_row` — `"Value-typed parameters — no foreign ORM/schema objects"` (`backend/src/services/record.py:525`) и `"Value-typed input only"` (`record.py:554`) — уточняются: значения — по-прежнему правило; исключение — необязательный параметр уже прочитанной собственной строки.

Прецеденты в дереве (переиспользуем, не изобретаем): `_resolve_delete_core` читает строку один раз и строит метку журнала из того же объекта (`backend/src/services/generic.py:323` — чтение, `:376` — метка); `delete_record` переиспользует свой пробный read для метки (`backend/src/usecases/records.py:514`).

## Правила неизменности (стражи)

- **Инвариант #344 §4.2:** «до»-половина diff фиксируется ДО первой мутации в сессии. Захват `_old` из `existing` остаётся выше вызова `update_row`/`patch_row` — порядок не меняется, исчезает только второе чтение внутри метода.
- **Журнал байт-в-байт идентичен:** diff-значения берутся из той же строки того же состояния; форма `changes`, маскирование, label — без изменений.
- **Отсутствующий id:** прежние ответы (None/False → 404 на уровне API), в журнале ничего (§4.1 канона журнала: нет строки — нет записи).
- **Число SELECT на мутацию не растёт:** в трёх путях ровно минус один; новых запросов не появляется.

## Гонки и границы транзакции (по итогам панели)

Факт границы: сценарное чтение и мутация выполняются в ОДНОЙ транзакции `@transactional` (канон, правило 6: транзакция = граница бизнес-действия; правило 5 запрещает вложенные декорированные вызовы). Передаваемый объект — живая строка текущей сессии, не отсоединённая и не из чужого снимка; «устаревание между транзакциями» в этой схеме не возникает.

Окно гонки «строку удалили конкурентно между чтением сценария и записью»: ширина окна НЕ меняется — момент первого чтения и момент записи те же, меняется только владелец первого чтения (метод вместо сценария). Сегодня окно уже разделено на два среза с разным исходом: «исчезла до внутреннего чтения» → чистый 404, «исчезла между внутренним чтением и флешем» → ошибка ORM-флеша (StaleDataError) → 500. После правки всё окно ведёт себя как второй срез (404-под-срез поглощается существующим 500-режимом). Приложение рассчитано на немногих администраторов; конкурентное удаление той же строки — патологический сценарий, уже сегодня дающий 500 в части окна. Решение: принять и зафиксировать здесь, новых блокировок не строим.

Паритет одиночного удаления посетителя восстанавливается дёшево и полностью: `_delete_cascade` с переданной строкой проверяет rowcount `DELETE` строки посетителя — 0 затронутых → `False` → прежний ответ 404. Фантомная запись журнала в этом окне (метка delete ставится до ядра каскада и коммитится при `False`) существует и сегодня — правка не ухудшает, сохраняем как есть.

Замечание панели «передавать dict/DTO вместо ORM-объекта» отклонено: мутация пишет через живой ORM-объект, словарь не убирает внутреннее чтение (см. §Концепт).

## User Scenarios

Сценарии — мутационные потоки, чьё видимое поведение не меняется (задача — снять лишний запрос, не тронув поведение):

- **US-1. Удаление посетителя.** Администратор удаляет посетителя; тот исчезает из записи, в журнале одна запись delete с прежними label и before-снимком. Покрытие: `test_audit_explicit.py` (точные `changes`), API/e2e-проверки удаления посетителя.
- **US-2. Полное изменение записи.** Администратор сохраняет полное редактирование записи; значения меняются, журнал содержит update diff прежней формы по тем же полям. Покрытие: `test_audit_explicit.py`, `test_api_records.py`, e2e записи.
- **US-3. Частичное изменение записи.** Администратор правит комментарий или цену записи; diff только по этим полям, прежней формы. Покрытие: `test_audit_explicit.py`, `test_api_records.py`, e2e записи.
- **US-4. Несуществующий идентификатор.** Удаление/изменение по несуществующему id — прежний ответ 404, журнал пуст. Покрытие: существующие негативные тесты трёх путей.
- **US-5. Каскад удаления клиента не меняется.** Администратор удаляет клиента с посетителями; каскад работает как раньше (эти пути задача не трогает — страж регрессии). Покрытие: `delete_family_full_contract.py`.

## Behavioral Delta

Для пользователя ничего не меняется: ни ответы API, ни содержимое журнала действий, ни интерфейс. Единственная дельта — внутренняя, на один SELECT меньше в трёх мутационных запросах:

| Путь | Было (чтений строки на запрос) | Станет |
|---|---|---|
| DELETE посетителя (одиночное) | 2 | 1 |
| PUT записи | 2 | 1 |
| PATCH записи | 2 | 1 |

## Границы (что сознательно НЕ делаем)

- **Каскад удаления клиента не трогаем** (`backend/src/usecases/clients.py:223` вызывает `_delete_cascade` без строки): там нет журнального дубля (дети каскада не журналируются, §8 канона журнала), а правка задела бы тестовые подмены `_delete_cascade`.
- **Глобально не переводим чтения на `session.get`/identity map** (`BaseRepository.get`, `RecordService.get`). Возражение best-practices-панели («Session.get — документированный доступ к карте идентичности, ноль изменений подписей») отклонено по существу: смена семантики глобальна и молчалива для ВСЕХ читателей — попадание в карту идентичности не замечает конкурентного удаления строки вплоть до флеша (сегодняшний повторный SELECT замечает: нет строки → None → 404) и не обновляет уже загруженные атрибуты свежесоммитёнными значениями. Три явные правки с видимыми подписями честнее неявной смены видимости данных во всех путях разом; в дереве уже был комментарий с заблуждением на эту тему (`backend/src/services/generic.py:321`).
- **Не добавляем тесты подсчёта SQL-запросов:** приёмка в issue сформулирована субъектно — снятие дубля сверяется кодом ревью; байт-идентичность diff сторожат существующие точные тесты журнала. Возражение best-practices-панели (счётчик запросов как страж от тихого отката оптимизации) — открытое решение пользователя на Gate B; если принять, это одна узкая задача плана (подсчёт SELECT на трёх путях через слушатель движка в одном тест-файле), до решения не закладывается.
- **Не меняем механизм журнала:** накопление, автосбор репозитория, сериализацию, маскирование — вне задачи.
