# Спека: метка «visits» в событийной сетке удалений (#375)

- Issue: #375 (зависимость #327 закрыта)
- Дата: 2026-10-10
- Поток: STANDARD

## Контекст

Админ-приложение обновляет открытые экраны через события: после каждой операции сервер рассылает пакет с перечнем изменившихся сущностей (событийная сетка), фронт по каждой метке инвалидирует соответствующие кэши запросов. Сегодня два пути удаления стирают посещения из базы, но не называют их в пакете — метка `visits` в них специально отключена (паритет рефакторинга #327, закрытие дыры вынесено в #375 решением пользователя 2026-09-26):

1. **Каскадное удаление клиента** (сценарий `delete_client`, execute-ветка с резолюциями): посещения посетителей физически стираются пакетным методом, сетка пакета — `{clients, records, photos, visitors, client_tags}` без `visits`.
2. **Одиночное удаление посетителя** (`VisitorService.delete`): сетка `{visitors}` без `visits`.

Механизм включения уже существует и спроектирован ровно для этого: пакетный метод удаления посещений принимает `mark_visits: bool = True`; оба пути выше передают `False` явно. Третий путь — удаление посетителя через окно разрешения конфликтов (resolve-delete) — метку уже ставит (значение по умолчанию) и не меняется.

Свойства событийного пакета (существующая семантика, ничего не меняется): пакет несёт только имена изменившихся видов сущностей — сетку, без идентификаторов строк, поэтому размер пакета не зависит от объёма удаления; эмиссия происходит только при коммите транзакции — откат выбрасывает накопленные метки целиком (визуальных «фантомных» обновлений при сбое не бывает); метка ставится по факту вызова удаления, в том числе при нуле затронутых строк (mark by dispatch fact — как безусловные метки нуллификации), а накопитель имеет семантику множества — повторные метки не дублируются.

Фронт к метке готов: `visits` входит в список распознаваемых сущностей, карта инвалидаций ведёт её в семейство записей (посещения — часть записи, отдельного кэша посещений нет).

Уточнение разведки (зафиксировано комментарием в issue): в каскаде удаления клиента экраны записей обновляются уже сегодня — метка `records` присутствует в сетке и инвалидирует то же семейство, куда ведёт `visits`. Реальное видимое устаревание существует только в одиночном удалении посетителя: сетка `{visitors}` инвалидирует лишь список посетителей. Правка в обоих путях сохраняется по критериям приёмки issue: событийная модель должна называть все фактические изменения данных — на неё могут завязаться будущие потребители событий (например, веб-приложение для клиентов).

## User Scenarios

- **US-1.** Администратор удаляет посетителя; в соседней вкладке открыта таблица «Записи». Таблица обновляется сама: посещения удалённого посетителя исчезают из строк, счётчики мест пересчитываются — без ручного обновления страницы. → E2E: две страницы, удаление в одной, изменение таблицы в другой.
- **US-2.** Администратор удаляет посетителя; открыта карточка клиента на вкладке записей. Список записей карточки обновляется сам — посещения удалённого посетителя пропадают без перезагрузки. → E2E: удаление в одной панели, обновление вкладки в другой.
- **US-3.** Администратор удаляет клиента каскадом (с резолюциями, включающими удаление посещений посетителей); в соседней вкладке открыта таблица «Записи». Таблица обновляется сама (как и раньше — через метку `records`), а событийный пакет теперь честно называет и посещения: сетка execute-пакета — `{clients, records, photos, visitors, client_tags, visits}`. → E2E: обновление таблицы; сетка дополнительно фиксируется юнит-тестами сценария.

## Behavioral Delta

- До: после одиночного удаления посетителя открытые экраны «Записи» и карточка клиента показывают его посещения до ручного обновления страницы; после каскадного удаления клиента событийный пакет не называет стёртые посещения.
- После: сервер включает метку `visits` в оба пакета; открытые таблица «Записи» и карточка клиента обновляются сами сразу после одиночного удаления посетителя. Видимая дельта у каскада клиента отсутствует (экраны обновлялись и раньше) — меняется состав события, не поведение экранов.
- Не меняется: механизм рассылки (накопитель меток внутри транзакции), поведение фронта (карта инвалидаций уже содержит `visits`), тост «Данные обновлены» (один на пакет, без изменений), все прочие событийные сетки.

## Решение

1. Сценарий `delete_client` (фаза 7, вызов пакетного удаления посещений посетителя): снять подавление — метка `visits` ставится. Ожидаемая сетка execute-пакета: `{clients, records, photos, visitors, client_tags, visits}`. Цикл фазы 7 стирает посещения всех посетителей клиента безусловно — резолюции касаются иных сущностей, поэтому метка появляется в сетке при любом наборе резолюций, включая «чистого» клиента без записей.
2. `VisitorService.delete`: то же — сетка `{visitors, visits}`; докстринг метода больше не заявляет отсутствия метки. Вместе с ним обновляются сопутствующие тексты подавления в сценарии `delete_client` (докстринг сценария и инлайн-комментарий фазы 7) — после правки они стали бы ложными.
3. Фронт: без изменений.
4. Осознанное изменение контракта, не паритет #327: зафиксированные сетки в тестах обновляются на новые значения.

## Тесты

- `tests/test_events_emit.py`, тест сетки resolve-удаления клиента: ожидаемая сетка пополняется `visits`; комментарий о подавлении метки (паритет спеки #327 §8) снимается со ссылкой на #375. Маршрут resolve-удаления исполняет сценарий `delete_client` — изменение теста транзитивно, сам маршрут не правится.
- Юнит-тесты сетки сценария `delete_client` (полная семья / чистый клиент / отдельный тест подавления метки): сетки пополняются `visits`; тест подавления инвертируется и переименовывается (метка теперь присутствует).
- Одиночное удаление посетителя: событийного emit-теста этого пути сегодня нет — добавляется с сеткой `{visitors, visits}`. Тест подавления параметра у пакетного метода (`mark_visits=False` подавляет метку) остаётся без изменений: параметр и его контракт сохраняются, подавление снимается только у двух точек вызова.
- Охрана без изменений: resolve-путь удаления посетителя (окно конфликтов) уже ставит метку значением по умолчанию — его тесты не правятся.
- E2E по US-1–US-3: удаление в одной странице, наблюдение обновления в другой; серверная сетка в E2E не проверяется (её держат юнит-тесты), связка «метка → семейство кэша» на фронте уже зафиксирована существующим дрейф-тестом карты инвалидаций.

## Границы

- Не строим: отдельное кэш-семейство посещений на фронте; покрытие точечного ключа отдельной записи `['record', id]` (существующее ограничение карты инвалидаций — открытая детальная карточка записи обновится только при повторном открытии); изменение сеток других сценариев; правки resolve-пути удаления посетителя (окно конфликтов — уже корректен).
- Точка роста (вне скоупа): при появлении веб-приложения для клиентов (#279) метка `visits` доступна его подписчикам без доработок сервера.
