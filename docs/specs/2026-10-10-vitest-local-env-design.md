# Спека: локальное vitest-окружение admin — зелёный полный прогон на любой машине (#389)

Статус: черновик до Gate B (рев. 3 — после панели, зондов и выбора пользователя: пин Node 26 + флаг + UTC; рев. 2 рассматривала шим — снят).
Дата: 2026-10-10/11. Поток: стандартный (спека → панель → план).

## Контекст и диагноз

Полный прогон `npx vitest run` в `frontend/admin` на машине разработчика красный, на CI — зелёный. Разведка (10.10, авто-DESIGN #389) нашла две независимые причины; обе — окружение, не прод-код и не ассерты тестов.

### Причина 1 — глобальный `localStorage` из новых Node затеняет Storage из jsdom

- Симптом: 308 падений в 18 тест-файлах, `TypeError: localStorage.clear is not a function` в `beforeEach`/`afterEach` и тестах, читающих `localStorage.getItem` (GridSettingsContext, UIContext, UserSettingsContext, LocationsTable, ServicesTable, StaffTable, ClientsTable, RecordsTable, DataTable, Topbar, usePersistedState, AuditLogTable, CellHeight, ClientQuickCard, ColumnPicker, DayView, ServicesPage, recordsColumns).
- Механизм: некоторые новые Node сами определяют глобальный `localStorage` — урезанную заглушку без рабочих методов (`getItem`/`setItem`/`clear` все `undefined`; для работы требует флага `--localstorage-file`). Тестовая среда jsdom не перезаписывает уже существующие глобалы Node, поэтому тесты видят заглушку вместо полноценного `Storage` из jsdom. Воспроизведено и в чистом node: `node -e "localStorage.clear()"` даёт ту же ошибку.
- Диагностика зонда: заражены и `globalThis.localStorage`, и `window.localStorage` тестового окружения — это одна и та же ссылка на заглушку.
- Охват по версиям (прямые докер/хост-зонды, октябрь 2026): 22 — заглушки нет; 23 — есть; 24 — нет; 25 — есть; 26 — объекта-заглушки нет (остаточный шум-предупреждение при обращении, гасится флагом). Включали фичу в 23-й, убирали в 24-й, вернули в 25-й — экспериментальная, отсюда качели.
- Почему CI зелёный: CI стоит на Node 22 (`.github/workflows/test.yml`, `node-version: 22` в четырёх джобах — `frontend-tests`, `frontend-checks`, `shard-script-checks`, `e2e-tests`), где заглушки нет — jsdom-Storage встаёт как обычно.
- В репо нет собственного localStorage-шима; `sessionStorage` в коде и тестах admin не используется вовсе.

### Причина 2 — тесты форматирования времени ожидают UTC

- Симптом: `__tests__/recordsColumns.test.tsx` рендерит `activity_start = 2026-06-15T10:00:00Z` и ожидает `10:00`; в таймзоне Europe/Moscow ячейка даёт `13:00` (форматирование через `lib/datetime.ts`, локальная зона).
- Нигде в конфигах/воркфлоу/скриптах TZ не закреплена (grep — ноль). CI-раннеры всегда UTC — потому зелёный.
- Охват шире одного теста: по свежему прогону в контейнере с TZ=Europe/Moscow (комментарий в #403, 09.10) — 9 TZ-чувствительных падений (исходно в #403 называлось 3); все закрываются пином TZ=UTC. Точный состав покажет полный локальный прогон на IMPL (DoD).

## Решение (концепт; выбор пользователя 11.10)

Зафиксировать окружение тестов целиком в репозитории — версию Node (одна точка правды), поведение Web Storage и таймзону — так, чтобы локальный прогон и CI совпадали на любой машине. Три правки, все — инфраструктура; прод-код и ассерты не трогаем.

1. **Пин Node 26 — единая версия в CI и в контейнере.** CI: новый файл `.nvmrc` со значением `26` (мажор-пин: патчи и минорные внутри ветки обновляются; ветка живая: на дату спеки current, LTS-статус 28.10.2026, сопровождение до 2029); все четыре места `node-version: 22` в `.github/workflows/test.yml` (джобы `frontend-tests`, `frontend-checks`, `shard-script-checks`, `e2e-tests`) заменить на `node-version-file: .nvmrc`. Локальная среда автора — контейнер opencode (тесты запускаются только там): базовый образ контейнера `~/dev/opencode/docker/opencode/Dockerfile` переведён с `FROM node:24-bookworm` на `FROM node:26-bookworm` (правка внесена 11.10, вне репозитория memo — инфраструктура); вступает в силу при пересборке контейнера (`docker compose build opencode && docker compose up -d opencode` из `~/dev/opencode/docker`), пересборку выполнять в момент, когда контейнерные сессии свободны — пересоздание убивает процессы внутри (инцидент 19.09). Установка Node на хосте не требуется (автор тесты на хосте не запускает; хостовая 25.9 остаётся зелёной благодаря флагу, если когда-нибудь понадобится).
   Граница пина: остальные воркфлоу с собственным `node-version: 22` — `web-checks.yml`, `visual-check.yml`, `update-snapshots.yml` — остаются на 22 и в рамки данной спеки не входят (web-приложение и вспомогательные визуальные/снапшотные прогоны; их перевод на `.nvmrc` — отдельная тема при желании). Заявление «версия в одном месте» относится к тестовому прогону admin: CI читает `.nvmrc`, контейнер — свой Dockerfile.
2. **Выключить встроенную заглушку Web Storage — флаг, без всякой эмуляции.** В `frontend/admin/vitest.config.ts` в секцию `test` добавить `execArgv: ['--no-experimental-webstorage']` — Node перестаёт создавать свою заглушку в тестовых воркерах, jsdom ставит своё полноценное родное хранилище во всей полноте, как всегда делал на версиях без заглушки. Проверено зондами: на 25.9 полный больной прогон зелёный без шима; флаг валиден и безвреден на 22, 23, 24, 26 (на 26 дополнительно гасит шум-предупреждение). Ничего не подменяется — выключается помеха; «нехватки механизмов» нечему возникнуть, в тестах родное хранилище тестовой среды.
   Пин и флаг решают разные задачи и не заменяют друг друга: пин — воспроизводимость и сопровождаемость окружения (одна живая версия у автора и CI); флаг — зелёность прогона на любой Node ≥22.4 независимо от пина (машина вне пина — например, сегодняшняя 25.9 автора или соседняя 23.11 — остаётся зелёной благодаря флагу).
3. **TZ = UTC.** В `frontend/admin/vitest.config.ts` сразу после шапки-импортов, до `defineConfig`, выставить `process.env.TZ = 'UTC'`: присваивание выполняется при загрузке модуля конфига в главном процессе vitest, все дочерние процессы наследуют env — приём не зависит от типа пула (официальные доки vitest предупреждают, что `test.env.TZ` не действует на пулах `threads`/`vmThreads`; на текущем `forks` работает — проверено — но привязан к пулу, поэтому не выбираем; через присваивание в конфиге порядок относительно хойстящихся ESM-импортов не гарантирован — механизм работает именно наследованием env процессами, что зонды подтвердили). Проверено зондом: при хостовой Europe/Moscow time-тесты зелёные.

Отвергнутые альтернативы (зафиксированы, чтобы не возвращаться):

- **Только флаг + TZ, без пина версии** — зелёность достигается на любой Node ≥22.4, и это самый узкий скоуп (рекомендация simplicity-ревью). Отклонено пользователем 11.10: цель шире зелёности — зафиксировать окружение (одна живая версия у автора и CI, сопровождаемость), иначе разъезд «CI на одном, хост на другом», породивший issue, остаётся. Зелёность машин вне пина при этом сохраняется флагом.
- **Шим `MemoryStorage` в setup** (~20 строк, рев. 2) — снят по решению пользователя: эмуляция, которой справедливо не доверяют («может не хватить механизмов»); остаётся в Notes запасным приёмом на единственный случай — исчезновение флага из Node раньше фикса апстрима vitest.
- **Пин 25.9** (стоящая у автора) — рабочая схема, но закрепляет мёртвую с 01.06.2026 ветку без обновлений безопасности; отвергнуто пользователем после сверки графика релизов.
- **Остаться на CI Node 22 без пина** — сохраняет разъезд окружений, породивший issue.

Поглощение дублей: TZ-часть этой спеки закрывает vitest-тему открытого issue #403 (пин TZ=UTC для vitest-дат; его комментарий от 09.10 прямо называет пин в конфиге закрывающим решением) и #460 — та issue предлагала две опции, «задокументировать» ИЛИ «зафиксировать в конфиге тестов»; данный дизайн исполняет вторую, так что закрывать её следует как исполненную, а не как отменённую. После мержа реализации #389 оба закрыть с комментарием-обоснованием.

## Границы (что сознательно не делаем)

- Не меняем прод-код, ассерты и setup-файл тестов (`__tests__/setup.ts` остаётся одной строкой).
- Не переписываем time-тесты на «TZ-независимые» вычисления: пин окружения проще, совпадает с фактическим окружением CI и не размножает логику. Существующие in-file пины `process.env.TZ` в пяти тест-файлах (datetime, datetime-dst, recordsTimeParity, timezone-dnd-bug, CopyLastWeekPopover) НЕ трогать: внутри своего форка их присваивание сильнее глобального пина, это рабочая изоляция, а не дублирование.
- Не трогаем e2e-инфраструктуру и шардирование vitest в CI (темы #420, #373), структуру воркфлоу — кроме замены значения версии Node на чтение `.nvmrc` во всех четырёх джобах `test.yml`. Воркфлоу `web-checks.yml`, `visual-check.yml`, `update-snapshots.yml` остаются на Node 22 (перевод — отдельная тема).
- Локальная пересборка контейнера opencode на `node:26-bookworm` — инфра-шаг вне PR (Dockerfile уже поправлен); выполнять в тихое время, по готовности — не блокирует IMPL: на текущей Node 24 контейнера прогон уже зелёный (флаг+UTC не зависят от версии), после пересборки — тот же результат на 26.
- Если после фиксов полный локальный прогон вскроет иные окруженческие падения (за пределами двух описанных групп) — это отдельный issue, не расширение данного.

## User Scenarios

- **US-1.** Разработчик запускает полный `npx vitest run` в `frontend/admin` в контейнере opencode — прогон зелёный, ошибок `localStorage.clear is not a function` нет; одинаково зелёный до пересборки контейнера (Node 24) и после неё (Node 26). Проверка сценария: полный прогон в контейнере.
- **US-2.** CI прогоняет те же тесты на той же версии из `.nvmrc` (все четыре работы `test.yml`: vitest-шарды, frontend-checks, shard-script-checks, e2e) — зелёный, без регресса. Проверка: зелёный CI у PR реализации.
- **US-3.** Время в юнит-тестах форматирования одинаково на любой машине: полный прогон в TZ=Europe/Moscow даёт тот же результат, что в UTC (контейнер живёт в Europe/Moscow — закрывает все 9 TZ-чувствительных тестов из комментария #403). Проверка: полный прогон в контейнере зелёный.
- **US-4.** Окружение тестов задаётся репозиторием и инфраструктурой декларативно: версия Node — в `.nvmrc` для CI и в базовом образе контейнера (`node:26-bookworm`) для локальных прогонов; таймзона и Web Storage — в конфиге тестов. Машина вне пина (любая Node ≥22.4, включая хостовую 25.9 автора) всё равно даёт зелёный прогон благодаря флагу — пин защищает сопровождаемость, а не зелёность. Проверка: прогон US-1/US-3 без вручную установленных переменных окружения.

## Behavioral Delta

- До: полный vitest-прогон admin зелёный только в конфигурации CI (Node 22 + UTC): на окружениях с заглушкой (хост 25.9, где прогон и воспроизводился) — 308 падений из-за Node-заглушки `localStorage`; в контейнере (Europe/Moscow) — до 9 TZ-чувствительных падений; версия Node нигде не зафиксирована (CI 22, хост 25.9, контейнер 24).
- После: полный прогон зелёный в контейнере и в CI без ручных действий (а на любой Node ≥22.4 вне пина — благодаря флагу); версия Node определена декларативно (`.nvmrc` для CI, `node:26-bookworm` в Dockerfile контейнера); тестовое время всегда UTC; Web Storage в тестах — родной jsdom (заглушка Node выключена флагом). Прод-код, ассерты и состав тестов не меняются.

Риски и Notes:

- Все три механизма проверены зондами на живых окружениях (Node 22/23/24/25/26 — докер и хост; больной прогон на 25.9 зелёный с флагом+UTC, без шима); остались масштабная проверка (полный прогон) и CI.
- Переезд e2e-джоба на Node 26 (next 14.2.35, @playwright/test ^1.52) не проверялся зондами — арбитр зелёный CI у PR; при красноте e2e на 26 решение на поверхности: починка совместимости либо временный возврат одного джоба на 22 с комментарием (раскол осознанный и видимый, не тихий). После пересборки контейнера на 26 — беглый e2e-прогон в контейнере (smoke).
- Node 26 на дату спеки — current (LTS 28.10.2026, EOL 2029): пин на свежую чётную ветку осознан; регрессии до LTS-промоушена прикрывает зелёный CI у PR.
- `.nvmrc` с мажорным `26` плавает по патчам (CI может взять не самый свежий 26.x без `check-latest`) — компромисс «свежесть важнее бит-в-бит воспроизводимости» принят сознательно.
- `@types/node` в `frontend/admin` остаётся `^20` — type-check консервативнее рантайма 26; подъём типов — отдельная тема, к зелёности прогона отношения не имеет.
- Флаг `--no-experimental-webstorage` экспериментальный: если Node стабилизирует фичу и уберёт флаг, конфиг упадёт громко с «bad option» — заметно и чинимо; запасной приём на этот случай — шим `MemoryStorage` из рев. 2 (эскиз сохранён в истории спеки), upstream-решение — фикс в Vitest 5 (конфликт Node-глобалей с окружениями, requires Node ≥22.12).
- На Node <22.4 флаг невалиден — вне зафиксированного диапазона, не встречается.
- Node 26 без флага печатает шум-предупреждение при обращении к localStorage — флаг гасит и его.
- Панель читает чистый клон origin/main — спека самодостаточна: диагноз, зонд-факты и механизм описаны здесь целиком.
