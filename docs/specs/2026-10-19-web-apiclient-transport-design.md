# Спека #479: веб на единый транспорт `@memo/api-client` — второй fetch-стек удалить, данные живые

- Issue: [#479](https://github.com/mkosinov/memo/issues/479)
- Дата: 2026-10-19, рев. 10 (фактические правки план-ревью 20.10: мок локаций уже удалён мержем #491/#492 — Изменение 3 сжато; `POST /records` остаётся админским эндпоинтом, явно)
- Зависимости: нет. Связана: #499 (клиентские учётки и реальное бронирование — вынесено из этой задачи), #480 (экспорт TS-юнионов), #493 (лимиты, формат телефона, fetch-metadata, фото-контракт), #497 (нейминг get/list + `.strict()` по всем зеркалам).

## Контекст

Веб-приложение (`frontend/web`) ходит в API двумя путями:

1. **Живой путь** — расписание (`useSchedule`) уже через `@memo/api-client`: `getActivities`, `getMasters`, `getServices`, `getLocations` с zod-разбором ответов.
2. **Самодельный путь** — собственный fetch-клиент с собственным базовым URL (`app/lib/api/client.ts`), собственный класс ошибок с другим порядком аргументов (`app/lib/errors.ts`), не понимающий контракт `{detail, code}`, и локальные DTO, разошедшиеся с контрактом (`WebPhotoResponse`, `LocationDTO`, `Tariff` в оверлее бронирования).

Разведка по живому дереву (2026-10-19) уточнила картину: самодельный путь почти весь мёртв — запрос веб-фото и функция создания записи не вызываются интерфейсом ниоткуда; галерея — зашитый мок (мок локаций уже удалён мержем #491/#492 — хук локаций читает справочник через api-client); форма бронирования при нажатии «Записаться» показывает экран успеха, не отправляя ни одного запроса. Приложение не в проде.

Бэкенд к гостевому сценарию готов: `POST /api/v1/records` сознательно публичный (комментарий в роутере: «the booking route stays public»), схема создания записи несёт гостевые поля — `phone` на записи и `name`/`age` на визитах («Phone-based / Name-based — for web frontend»); `GET /api/v1/photos/web` отдаёт публичные фото (`is_public=true`).

## Решение Gate A (уточнено 20.10)

Направление «всё живое» с границей «замена транспорта на готовую библиотеку». По итогам Gate B граница уточнена: в этой задаче — единый транспорт и живые данные чтения (локации, галерея; расписание уже на api-client). Гостевое бронирование и клиентская авторизация выделены в отдельную траекторию #499: анонимные вызовы `/my` запрещены (401) до аутентификации, гостевая запись потребует подтверждённого телефона. Мок-локации и мок-галерея удаляются.

## Цели

1. Единственный транспорт веба — `@memo/api-client` (клиент, `ApiError`, типы, zod-разбор ответов). Самодельный клиент, класс ошибок и локальные DTO удаляются.
2. Секции «локации» и «галерея» питаются реальными данными; публичная витрина фото становится фильтром `is_public` общего списка.
3. Зеркало `RecordCreate`/`RecordUpdate` в `@memo/api-client` выравнивается с бэкенд-контрактом (`.strict()`).
4. Анонимный доступ к полному созданию записи закрывается требованием `records:write`.

## Нецели (сознательно не строим)

- Гостевое бронирование и клиентская авторизация — #499 (раздел «Вынесено»); форма бронирования веба остаётся в текущем декоративном виде.
- Лимиты/анти-спам, формат телефона, `verify_fetch_metadata`, чистка идентификаторов из публичного фото-контракта — #493.
- E2E-харнес для `frontend/web` — не существует; создание — отдельная задача. Проверки сценариев этой спеки — vitest.
- Приватная бронь (`BookingPrivateOverlay`, `PrivateBookingView`, `to-booking-dto`) — чистый UI-поток без сети, не затрагивается.
- #480 (экспорт TS-юнионов статусов), #497 (нейминг get/list + `.strict()` по всем зеркалам) — отдельные задачи.
- Геолокационный выбор ближайшей локации (`findNearestLocationId` — заглушка TODO) — без изменений.

## Вынесено в отдельную задачу (#499): клиентские учётки и реальное бронирование

Решения 20.10: анонимные вызовы `/my` запрещены (401) до аутентификации; вход клиента — подтверждение номера телефона кодом (лимиты — #493), сессия — непрозрачная cookie, как у сотрудников; роль «клиент» без `records:write`, «моё» определяется сессией. Реальное бронирование — `POST /my/records` под сессией со строгой схемой `MyRecordCreate`: телефон обязателен, цена выводится сервером из тарифа (`price` в визитах становится необязательным), идентификаторы клиента/посетителей с провода запрещены. Кабинет — чтение по сущностям: `GET /my/records` (с визитами), `GET /my/photos`, `GET /my/payments`; агрегатного «выдай всё» эндпоинта нет. Веб-форма: счётчики мест по реальным тарифам услуги, опциональная таблица «Указать имена посетителей» (имя + возраст + тариф read-only; места без имени — анонимные визиты), услуга без тарифов — счётчик мест и «Стоимость уточняется», ошибки — сообщение с data-testid и повторной отправкой. Скоуп-функциональность живёт на сессиях, JWT не вводится.

## Контрактные опоры (готовое в `@memo/api-client`)

| Потребность | Функция | Возврат |
|---|---|---|
| Локации | `getLocations()` | `PaginatedResponse<LocationResponse>` (zod) |
| Публичные фото | `getPhotos({ is_public: true })` — общий список с фильтром; витрина `/photos/web` и `getWebPhotos` удаляются | `PaginatedResponse<PhotoResponse>` (zod) |
| Создание записи | `createRecord(data)` — полный контракт (админка); гостевое создание — #499 | `RecordResponse` (zod) |

Общий клиент пакета: тот же `NEXT_PUBLIC_API_URL`, cookie-сессии, таймауты 30/120 с, разбор `{detail, code}` и дерева зависимостей 409 в `ApiError`. Веб ничего своего поверх не добавляет.

Структура после миграции:

```mermaid

    "useSchedule" --> "api-client"
    "useLocations" --> "api-client"
    "useGallery" --> "api-client"
    "api-client" --> "backend GET /activities /masters /services /locations"
    "api-client" --> "backend GET /photos?is_public=true (публичный фильтр общего списка)"
```

## Изменение 1: выравнивание зеркала `RecordCreate` в `@memo/api-client`

`RecordCreateSchema` (packages/api-client) разошлась с бэкендовым `RecordCreate` (`extra="forbid"`):

- **визиты**: добавить `name?: string`, `age?: number | null`, `tariff_id?: string | null` — эти поля уже есть в бэкенд-контракте визита (name-based режим), зеркало отражает их для точности. Статус визита и обязательный `price` остаются (в контракте есть; необязательная цена — за #499).
- **запись**: убрать `status` и `seats` — бэкенд их в создании не принимает (`extra="forbid"` → 422 при отправке); места считаются как `len(visits)`. Единственный живой вызов в админке (`useRecordMutations`) шлёт `activity_id`, `client_id`, `visits` — удаление полей из типа его не ломает (проверено по коду; остальные потребители — только тесты пакета, переписываются вместе с зеркалом).
- **`.strict()` на зеркале** — устоявшийся паттерн пакета для паритета с `extra="forbid"` (см. соседние write-схемы с явными комментариями): рантайм-разбор отвергает посторонние поля так же, как бэкенд, а не молча вырезает.
- **расцепить `RecordUpdateSchema`** с `RecordCreateSchema.partial()`: PUT-контракт бэкенда — собственная форма (`activity_id` обязателен, `client_id`, `comment`, `custom_price`, `visits` полной заменой; `status`/`seats` отсутствуют и там). Зеркало обновления описывается отдельно и тоже `.strict()`; тесты пакета, использующие `seats` в create/update (`schemas.test.ts`), переписываются под контракт.

Юнит-тесты зеркала: тип и рантайм-парс допускают name-based визиты (`name`/`age`/`tariff_id`) и отвергают `status`/`seats` на уровне записи.

## Изменение 2: удаление самодельного стека в `frontend/web`

Удаляются целиком:

- `app/lib/api/client.ts` (свой fetch, свой базовый URL);
- `app/lib/errors.ts` (`ApiError` с другим порядком аргументов, `Result<T>` — потребителей нет);
- `app/lib/api/photos.ts` и `WebPhotoResponse` (`app/lib/model/dto/photo.ts`);
- `app/lib/api/records.ts` (мёртвый `createRecord` с ручной сборкой визитов);
- `LocationDTO` (`app/lib/model/dto/location.ts`) — осиротела после удаления мок-файла `lib/api/locations.ts` мержем #491/#492;
- `app/lib/api/gallery.ts` (мок из 8 стоковых фото) и `GalleryPhotoDTO` (`app/lib/model/dto/gallery.ts`);
- `app/lib/api/activities.ts` (пустая заглушка) и `app/hooks/useActivities.ts` (мёртвый deprecated-хук).

Вью-модели и мапперы переписываются на типы `@memo/api-client`: `LocationView` сужается до полей контракта (`id`, `title`, `address` — поля `hours`/`photo_url` были мок-специфичны и интерфейсом не читались); галерейная вью-модель строится из `PhotoResponse`.

Сопутствующий артефакт: скилл `frontend-clean-architecture` (`.opencode/skills/`) предписывает вебу слой `lib/api` + `lib/errors` + `model/dto` — после миграции это противоречит коду. Скилл обновляется вместе с задачей: транспорт веба = `@memo/api-client`, слой самодельных DTO упразднён.

## Изменение 3: локации — общий кеш и чистка остатков

Мок локаций уже удалён мержем #491/#492: `useLocations` читает справочник через `getLocations` из `@memo/api-client`, но на `useState`/`useEffect` и с локальным классом ошибок. Задача: перевод хука на react-query — ключ `['locations']`, та же функция и те же параметры запроса, что в `useSchedule` (`staleTime` 300 000, `gcTime` 600 000) — общий кеш с единой политикой, один запрос на страницу; отказ от локального `ApiError`; `LocationView` сужается до полей контракта (`id`, `title`, `address` — `hours`/`photoUrl` мок-специфичны и интерфейсом не читались). Фильтр по архивности не добавляется (та же выдача, что у расписания; YAGNI).

## Изменение 4: галерея — публичные фото

Галерея переезжает на общий список фотографий с фильтром публичности (решение 20.10; унификация по образцу #371 — фильтр вместо отдельной витрины): маршрут `GET /photos/web` и функция `getWebPhotos` удаляются, к `PhotoListParams` добавляется фильтр `is_public`. `useGallery` переписывается на react-query поверх `getPhotos({ is_public: true, per_page: 12 })` (ключ `['photos', 'public']`); показ ограничен 12 фото на главной (запрашиваемой страницей). Фото в секции: `url` = `filename` — контрактное строковое поле; по сиду это готовые пути вида `/images/...` (проверено по сиду, отдельного файлового эндпоинта у фото нет). Рендерятся только same-origin пути и `http(s)`-URL — посторонние схемы и хосты отбрасываются. Подпись = названия тегов фото через « · », без тегов — без подписи. Единое правило отсутствия данных: загрузка, ошибка запроса или пустая выдача — секция галереи не рендерится (в фильтре локаций при ошибке остаются опции по умолчанию). Секция несёт `data-testid="guest-gallery"` — машинный якорь визуальной проверки.

## Изменение 5: закрытие анонимного полного создания записи (backend)

**`POST /api/v1/records` остаётся рабочим эндпоинтом администрации** — добавляется требование `records:write`, как у остальных мутаций записей; скоуп мастера («только свои активности») не меняется. Анонимный вызов полного контракта закрывается (401); для вошедших админа и мастера поведение прежнее — телефон опционален, клиент по идентификатору, явная цена визита — переопределение. Публичный статус снимается и из перечисления `auth/public.py` (комментарий «POST stays public» устаревает). Гостевого контракта в этой задаче нет — реальное бронирование целиком в #499.

Тесты (pytest): анонимно → 401; админ с явной ценой → 201 (переопределение работает); админ без телефона → 201. Существующие e2e админки не затрагиваются (ходят с сессией).

- `backend` (pytest): фильтр `is_public` общего списка фото; удаление маршрута `/photos/web` (его тесты снимаются); `POST /records` анонимно → 401 и регресс полного контракта (Изменение 5).
- Ручной smoke после имплементации: `dev.sh` (uvicorn + web), сидовые локации/фото.

## Риски и открытые вопросы

- **Контент-пустоты**: галерея и фильтр пусты, пока данные не заведены/не отмечены `is_public`. Приложение не в проде — принято пользователем на Gate A.
- **Доверие клиенту на публичном создании записи** — снято с этой задачи: полный контракт закрыт требованием `records:write` (Изменение 5), гостевого контракта здесь нет. Правила цены/идентификаторов/телефона живут в #499 (строгая схема `MyRecordCreate`), лимиты и формат телефона — #493.
- **Идентификаторы владельца в публичном фото-контракте** (`client_id` в выдаче общего списка) — осознанно остаётся до #493.
- **`filename` как URL**: поле рендерится с allowlist (same-origin / `http(s)`); заведение картинок — ответственность админки.
