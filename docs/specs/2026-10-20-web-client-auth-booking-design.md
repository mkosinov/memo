# Спека #499: клиентские учётки и реальное бронирование из веба — срез «вход + форма»

- **Issue:** #499 (срез по Gate A; чтение кабинета вынесено в #513)
- **Дата:** 2026-10-20, рев.2 (после панели — исправления §4.1/§4.2/§5 и уточнения)
- **Статус:** черновик до Gate B
- **Решения Gate A (пользователь, 2026-10-20):** объём — только вход и форма бронирования; момент входа — при отправке формы плюс отдельный вход через пункт меню «Личный кабинет»; селектор канала подтверждения остаётся видимым, но нерабочим.
- **Смежные траектории:** #513 (чтение кабинета, depends-on: #499), #493 (пересборка зависимости — §11), #479 (закрытие публичного гостевого создания записи), #476/#485 (транспорт доставки кода).

## 1. Контекст

Веб-приложение клиента (`frontend/web`) сегодня не умеет бронировать по-настоящему: форма бронирования — статический макет (тарифы нарисованы от максимальной цены услуги, отправка не уходит на сервер, «успех» — локальный флаг), «кабинет» — заглушка с полем телефона. У клиентов нет учёток: единственный способ создать запись из веба — публичный гостевой эндпоинт, который принимает цену визита и идентификаторы клиента/посетителя с провода (его закрытие — отдельная траектория #479, не эта спека).

Эта спека вводит клиентские учётки с входом по подтверждению телефона кодом и настоящее бронирование из веб-формы: `POST /api/v1/my/records` со строгой схемой, где цена считается сервером из тарифа, а владелец определяется сессией.

Инфраструктура, которая переиспользуется как есть: сессии сотрудников (непрозрачная cookie + таблица сессий, скользящее время жизни), принцип «владелец из сессии» на профиле сотрудника (`/api/v1/my`), паттерн счётчиков неудач по телефону/IP (анти-перебор входа, in-memory), компонент счётчика мест в вебе, контракт api-client с тарифами услуг.

## 2. Границы

**Строим:**
- подтверждение номера телефона кодом (запрос/проверка, лимиты, подставной транспорт для разработки);
- клиентская учётка: роль `client`, связь учётки с карточкой клиента, клиентская сессия (отдельная cookie, тот же механизм);
- `POST /api/v1/my/records` — бронирование из веба, строгая схема, цена из тарифа на сервере;
- `GET /api/v1/my/client` — кто вошёл (для формы и кабинета); выход — существующий `/api/v1/auth/logout`, расширенный на клиентскую сессию;
- живая веб-форма: реальные тарифы услуги, счётчики мест, опциональные имена посетителей (имя/возраст/тариф), ошибки с повторной отправкой, успех по факту 201;
- вход при отправке формы (шаг «подтвердите телефон») и экран входа в пункте меню «Личный кабинет».

**Не строим (осознанно):**
- чтение кабинета — `GET /api/v1/records|photos|payments` под `/my` и экраны «мои записи/фото/платежи» — #513;
- доставку кода реальным каналом (SMS/Telegram/WhatsApp/Max) — транспорт подключит система оповещений #476; до неё вход в production недоступен (честный 503, §4.2);
- отправку подтверждений о записи по каналу (селектор канала в форме остаётся нерабочим — контрактного поля нет);
- изменения публичного гостевого `POST /records` (его судьба — #479/#493);
- JWT и какие-либо токены кроме существующих непрозрачных сессий;
- восстановление/смену номера клиентской учётки (телефон — ключ учётки; смена номера = новая учётка);
- серверные пер-тарифные квоты мест (счётчики по тарифам — UI; сервер проверяет только общую вместимость активности — существующая проверка);
- браузерный e2e-харнес для `frontend/web` — в репозитории его нет (e2e есть только у админки); сценарии закрываются парой pytest + vitest (§6).

## 3. Серверная часть: учётка и роль

- В `UserRole` добавляется значение `client`. **В матрицу `ROLE_PERMISSIONS` роль не добавляется**: отсутствие роли в матрице даёт пустой набор прав (существующий защитный поиск `.get(role, frozenset())`), а инвариант-тест матрицы «ровно admin + master» не трогается. Клиентские эндпоинты авторизуются не правами, а фактом клиентской сессии (как профиль сотрудника на `/my`).
- `User` получает необязательную связь 1:1 с клиентом: колонка `client_id` (FK → `clients`, unique, nullable) — зеркалит существующую связь `staff_id` → сотрудник. Миграция + индекс.
- Клиентская учётка создаётся **только** потоком подтверждения телефона (§4.2), при первом успешном вводе кода на новый номер: `user(role=client, phone)` + карточка клиента по существующей семантике «найди-или-создай по точному телефону» (только активные карточки; при дублях карточек с одним телефоном привязка к первой активной, порядок — стабильная сортировка списка). Уникальность `users.phone` уже гарантирована БД; конкурентные `verify` на один новый номер: конфликт вставки ловится, строка перечитывается, поток продолжается (идемпотентный вход).
- Создание учётки соблюдает существующее правило гарантированной дочерней записи настроек (правило #319): строка пользовательских настроек создаётся в той же транзакции. При успешном подтверждении выставляется `phone_is_confirmed = true`.
- **Инвариант «клиентская учётка без пароля» закрепляется и enforced:** установка пароля по одноразовой ссылке отклоняет роль `client`; парольный вход `/auth/login` отказывает роли `client` (защита на случай случайно заданного пароля). Парольный null-guard входа уже не даёт войти учёткам без пароля.
- Резолверы не пересекаются: staff-резолвер не меняется и читает только `memo_session`; клиентская сессия резолвится отдельной зависимостью `require_client_session` — только `memo_client_session`, `role=client`, активная учётка (`users.is_active`). Архивация карточки клиента админом связь не разрывает и вход/бронирование не блокирует — владелец определяется по `client_id` учётки, история остаётся единой.

## 4. Серверная часть: подтверждение телефона и сессия

### 4.1 Код

- Таблица `otp_codes`: `phone` (ключ), `code_hash`, `expires_at`, `created_at`. Живёт **один код на телефон** — новая отправка заменяет прежний код (ротация).
- `code_hash` — **HMAC-SHA-256 с серверным перцем** (ключ в настройках окружения, вне БД; сравнение за постоянное время). Плоский SHA-256 для 6-значного кода не допускается — пространство перебирается мгновенно при утечке дампа.
- Код — 6 цифр, время жизни **5 минут**. Успешная проверка **атомарно поглощает код** (строка удаляется в той же транзакции с выдачей сессии) — код одноразов.
- Попытки ввода: не более **5 неудачных вводов за 15 минут на телефон**; счётчик живёт отдельно от строки кода и **не сбрасывается повторной отправкой** (ротация кода не обновляет бюджет догадок).
- Лимиты отправки — одно окно **15 минут**, существующий стор in-memory счётчиков: **5 отправок на телефон**, **20 на IP**, **не более 5 разных номеров с одного IP**. Все отказы `verify` дополнительно считаются в IP-счётчик. Превышение → 429 `AUTH_LOCKED_OUT`, единое сообщение.
- Просроченные строки кода удаляются при любом обращении к телефону (запрос/проверка); фоновая чистка не заводится (TTL 5 минут, объём ничтожен).
- Допущение: счётчики in-memory — осознанно; модель развёртывания проекта — один процесс (как у существующих счётчиков неудач входа). При появлении multi-instance/#483 (Redis) лимиты переезжают в общий стор.

### 4.2 Транспорт и эндпоинты подтверждения

Транспорт — интерфейс, выбор **fail-closed**: без явно настроенного транспорта запрос кода отвечает **503** `NOTIFY_TRANSPORT_UNAVAILABLE` (включая staging/preview — любое окружение кроме точно `development`). Реализации:
- **dev-транспорт**: включается только при точном совпадении `ENV == "development"`; пишет в лог **маскированную** запись (телефон + идентификатор кода, без сырого кода); в ответе запроса кода поле `dev_code` — тоже только при `ENV == "development"` (для тестов и ручной проверки; тот же принцип, что демо-пароли сида, но default-deny по окружению).
- **production-транспорт** — подключит #476/#485; до него production честно отвечает 503. При 503 веб показывает в шаге входа «Вход временно недоступен» (US-4).

Эндпоинты:

| Метод | Путь | Поведение |
|---|---|---|
| POST | `/api/v1/auth/otp/request` | тело `{phone}`; валидация телефона доменным валидатором (422 `PHONE_INVALID`); ответ **всегда 202** на любой валидный номер — телефон сотрудника не отличается от прочих (код молча не отправляется и не пишется — оракула перечисления нет); успех → код записан, вызван настроенный транспорт |
| POST | `/api/v1/auth/otp/verify` | тело `{phone, code}`; проверка HMAC-дайджеста+срока+попыток атомарно с поглощением кода; успех → находится/создаётся клиентская учётка (§3), выдаётся клиентская сессия, ответ 200 `{phone, name}` (имя — из карточки клиента, может быть `null`); отказ — единое сообщение; все отказы — в IP-счётчик |

Выход: отдельного эндпоинта нет — существующий `POST /api/v1/auth/logout` расширяется: удаляет предъявленную сессию **любого вида** (какая cookie предъявлена — та сессия и отзывается), идемпотентен.

Публичность: пара OTP-роутов **явно добавляется** в `PUBLIC_ROUTES` (точные пары метод+путь); контракт-тест «у каждого роута зависимость или allowlist» остаётся арбитром.

Обе точки подтверждения (request/verify) защищаются сверкой `Origin` против CORS-списка при наличии заголовка (несовпадение → 403) — выдача сессии не должна быть доступна чужой странице; существующая линия `Sec-Fetch-Site` на аутентифицированных мутациях не меняется. Смежное наблюдение (вне среза): у существующего `/auth/login` та же логин-CSRF развилка — отдельной задачей при необходимости.

### 4.3 Клиентская сессия

- Таблица сессий и механика — существующие: непрозрачный токен, скользящее окно 7 дней простоя / абсолют 30 дней, мгновенный отзыв удалением строки.
- Cookie — **отдельное имя** `memo_client_session` (те же атрибуты: `HttpOnly`, `SameSite=Lax`, `Secure` в production, `Path=/`). Отдельное имя — чтобы сессии клиента и сотрудника не затирали друг друга в одном браузере (сайт и админка ходят к одному API-источнику). Обе cookie могут ходить на общие пути API — осознанное допущение (перекрёстное предъявление невозможно: §3, резолверы читают каждый своё имя).
- `GET /api/v1/my/client` (клиентская сессия) → `{phone, name}` — для формы и экрана кабинета.

## 5. Серверная часть: бронирование `POST /api/v1/my/records`

- Доступ: `require_client_session` + защита аутентифицированных мутаций (`Sec-Fetch-Site` как у мутаций профиля сотрудника) + сверка `Origin` при наличии заголовка. CORS: точные origin с правом credentials; значение `*` при включённых credentials запрещено конфигурацией. Origin веб-приложения добавляется в список.
- Схема `MyRecordCreate` (`extra="forbid"`, все посторонние поля — 422):

```text
{
  "activity_id": uuid,
  "phone": str,            // контактный телефон записи; обязателен, доменная валидация (422 PHONE_INVALID)
  "comment": str | null,
  "visits": [              // 1..20 элементов
    { "name": str | null, "age": int | null, "tariff_id": uuid | null }
  ]
}
```

- Из провода принципиально отсутствуют: `client_id`, `visitor_id`, `price`, `custom_price`, `notify`, `status` — владелец только из сессии, уведомления в этой ветке не отправляются (каналов доставки ещё нет), статус — серверный дефолт.
- **Цена — только сервером, и ноль невозможен для платной услуги:** если у услуги активности есть тарифы, `tariff_id` **обязателен** в каждом визите (422 `TARIFF_REQUIRED`); визит с `tariff_id` → цена тарифа. Цена 0 — только для услуги без тарифов («Стоимость уточняется», US-2). `tariff_id` обязан принадлежать услуге этой активности — чужой тариф → 422 `TARIFF_NOT_FOUND`. Тарифы услуги загружаются одним запросом (без по-визитных обращений к БД).
- Визит без имени → анонимный визит (существующая семантика). Границы `age` и длины строк — как у существующей схемы визита.
- Создание использует существующий сценарий создания (та же транзакционная запись + визиты) и **наследует его проверки явно**: несуществующая активность → 404, превышение вместимости активности → 409 (существующая проверка). Отличия два: клиент фиксируется сессией (без поиска/создания по телефону), цена визитов вычисляется сервером.
- Мягкий анти-спам (то же окно 15 минут, тот же стор): не более **20 записей и суммарно 40 визитов за 15 минут** на клиентскую учётку → 429. IP-лимита на создание нет — вход уже ограничен лимитами кода.
- Ответ **201** `MyRecordResponse`: `{id, activity_id, start, comment, visits: [{name, age, tariff_id, price}]}`, где `start` — дата проведения из активности записи; без служебных полей (без `record_id` у визитов, без timestamps, без статусов визитов).

## 6. User Scenarios

Браузерного e2e-харнеса для `frontend/web` в репозитории нет; каждый сценарий закрывается парой проверок: **pytest** (серверный контракт, `backend/tests/`) + **vitest** (поведение веб-компонентов, `frontend/web`). Заведение playwright-харнеса для веба — отдельная задача, не этого среза.

| # | Сценарий | Проверки |
|---|---|---|
| US-1 | Аноним с главной открывает форму активности, выбирает места по тарифам, указывает имена части мест, отправляет → шаг «подтвердите телефон» → код → запись создана, виден экран успеха | pytest: полный контракт `POST /api/v1/my/records` (владелец из сессии, цены из тарифов, анонимные визиты); vitest: оверлей на реальных тарифах, шаг кода, успех по 201 |
| US-2 | Услуга без тарифов: один счётчик мест, «Стоимость уточняется», запись создаётся с ценой 0 | pytest: активность без тарифов → визиты с ценой 0; pytest-зеркало: услуга с тарифами + визит без `tariff_id` → 422 `TARIFF_REQUIRED`; vitest: рендер одиночного счётчика и подсказки |

| US-4 | Неверный или просроченный код → понятная ошибка в шаге подтверждения; лимиты соблюдаются; при недоступном транспорте (503) — «Вход временно недоступен» | pytest: попытки/срок/ротация кода, лимиты отправки, поглощение кода при успехе, 503 без транспорта; vitest: ошибки шага кода, сообщение 503 |
| US-5 | Уже вошедший клиент отправляет форму сразу (без шага кода); пункт меню «Личный кабинет» ведёт на экран входа анонима / вошедшему — телефон и выход | pytest: `GET /api/v1/my/client`, выход через `/api/v1/auth/logout` для обеих сессий; vitest: экран кабинета, меню |
| US-6 | Чужой `tariff_id`, постороннее поле в теле, пустой список визитов, мусорный телефон → 422, запись не создаётся | pytest: `extra="forbid"`, `TARIFF_NOT_FOUND`, `TARIFF_REQUIRED`, `PHONE_INVALID`, `min_items=1` |

## 7. Behavioral Delta

| Что | Было | Станет |
|---|---|---|
| Форма бронирования | тарифы нарисованы от максимальной цены; «отправка» — локальный флаг | реальные тарифы услуги (счётчик на каждый), создание записи на сервере |
| Услуга без тарифов | «Детский/Взрослый» от максимума | один счётчик мест + «Стоимость уточняется», записаться можно (цена 0) |
| Имена посетителей | нет (все места безымянные) | опциональная таблица имя+возраст+тариф; пустые имена уходят анонимными визитами |
| Вход клиента | не существует | подтверждение телефона кодом: шаг при отправке формы и экран «Личный кабинет» в меню |
| Страница `/booking` | мок с одной захардкоженной активностью | удаляется; форма живёт в оверлее карточки активности на главной |
| Кабинет | заглушка с полем телефона | экран входа (телефон → код); после входа — телефон и «Выйти» (разделы — #513) |
| Селектор канала (Telegram/WhatsApp/Max) | виден, ничего не делает | без изменений: остаётся видимым и нерабочим (контрактного поля нет) |
| Ошибки формы | нет | блок ошибки с `data-testid` и повторной отправкой; состояние загрузки/ошибки тарифов в оверлее |
| Сервер | роли admin/master; клиентских эндпоинтов нет | роль `client`, клиентская сессия, `/auth/otp/*`, `/my/client`, `POST /my/records` |

## 9. Безопасность

- Телефон сотрудника в OTP-входе неотличим: запрос кода отвечает 202 на любой валидный номер, для номеров сотрудников код молча не генерируется/не отправляется — оракула перечисления учёток нет.
- Парольный вход для клиентских учёток закрыт на двух рубежах: ссылка установки пароля отклоняет роль `client`; `/auth/login` отказывает роли `client`.
- Код хранится только HMAC-SHA-256 с серверным перцем (вне БД), сравнение за постоянное время; сырой код не пишется в логи (маскированная запись). Один живой код на телефон, одноразовость — атомарное поглощение при успехе; бюджет попыток не обновляется ротацией.
- Транспорт fail-closed: без явной настройки — 503 в любом окружении; `dev_code` и dev-транспорт — только при точном `ENV == "development"`.
- Разделение сессий: staff-роуты не принимают клиентскую cookie и наоборот (резолверы читают каждый своё имя cookie + проверяют роль).
- IDOR в `/my/records` невозможен конструктивно: `client_id` только из сессии, `visitor_id`/`custom_price`/`price` отсутствуют в схеме, `tariff_id` проверяется принадлежностью услуге активности, платная услуга не бронируется без тарифа (нулевая цена недостижима).
- CSRF: аутентифицированные мутации — существующая линия `Sec-Fetch-Site`; точки выдачи сессии (OTP request/verify) и мутация брони — сверка `Origin` против CORS-списка при наличии заголовка (несовпадение → 403). CORS: точные origin, `*` при credentials запрещён.
- Единые отказные сообщения и тайминги на шагах кода (без перечисления телефонов/учёток).

## 10. Правила домена

С спекой вместе правится `docs/domain-rules/auth.md`: новый раздел «Клиентская аутентификация (#499)» (роль `client` вне матрицы прав, OTP-поток, лимиты, отдельная cookie, таблица кодов, инвариант «без пароля»), строка allowlist про анонимное бронирование обновляется ссылкой на #499/#479, в Relationships добавляется `User → optional 1:1 Client`. `docs/domain-rules/records.md` — строка о способе создания записи клиентом (владелец из сессии, цена из тарифа).

## 11. Зависимости и смежные траектории

- **#493 (сейчас `depends-on` у #499) — пересборка.** Пункты #493, относящиеся к публичному `POST /records` (цена из тарифа для анонима, запрет `client_id`/`visitor_id` анониму), теряют предмет после закрытия публичного создания (#479, `records:write`); в этом срезе те же цели достигаются собственной строгой схемой (включая доменную валидацию телефона на точке брони и анти-спам лимиты). Остаётся в #493: чистка служебных полей из публичного фото-контракта. Предложение на Gate B: снять `depends-on: #493` с #499 (срез самодостаточен), остаток #493 зафиксировать комментарием в самом #493.
- **#479:** порядок независим — `createMyRecord` не пересекается с судьбой публичного `createRecord`; обе спеки сходятся в том, что анонимное гостевое создание закрывается.
- **#513:** чтение кабинета поверх клиентской сессии (создана здесь).
- **#476/#485:** реальный транспорт доставки кода; до него production отвечает 503 на запрос кода (осознанное частичное включение фичи в production). Обязательство для #476: при подключении реальной доставки — суточные квоты на получателя/IP и защита от SMS-pumping (платный трафик), мониторинг аномалий отправки.
- Смежное наблюдение (вне среза): логин-CSRF развилка у существующего `/auth/login` — та же природа, что закрыта здесь для OTP-точек; при необходимости — отдельная задача.

## 12. Допущения

- Телефон — ключ клиентской учётки; повторный вход другим номером создаёт другую учётку. Перенос истории между номерами — вне среза (не запрашивалось).
- Телефон хранится одной канонической строкой во всех трёх местах (учётка, карточка клиента, строка кода) — как подтверждён при входе; нормализация форматов номеров не вводится (существующая точная семантика поиска).
- Дубль карточек клиента с одним телефоном (телефон клиента неуникален): привязка к первой активной карточке по стабильной сортировке — существующая семантика поиска по точному телефону.
- Имя из формы брони не перезаписывает имя карточки клиента (карточку наполняет админ; синхронизация — #513 по надобности).
- Лимиты — стартовые константы сценария (не правила домена): код 6 цифр, TTL 5 минут, 5 попыток ввода, окно 15 минут: 5 отправок/телефон, 20/IP, 5 разных номеров/IP, 20 записей и 40 визитов/учётка.
- Счётчики лимитов in-memory — один процесс (модель проекта); обе cookie ходят на общие пути API — остаточный риск записи только факта наличия сессии.
- Префикс `__Host-` для клиентской cookie не вводится до перехода на HTTPS (сломает http-доступ к dev-стендам не через localhost); отметить при развороте HTTPS.
