# Инфраструктура доставки оповещений — часть 2 (#483)

Дата: 2026-10-21 · Статус: рев.3 после второго панельного ревью (полировка механизмов) · Семейная спека: `docs/specs/2026-10-11-notify-system-476-design.md` (рев.4) · ADR: `docs/decisions/008`, `009`, `011`, `012`, **`013`** (транспорт; заменяет ADR 010) · Часть 1 (#482) в main

## 1. Контекст

Часть 1 (#482) доставила подсистему доменных событий целиком на выключенном каркасе: таблицы `domain_events` / `notify_tasks` / `notify_task_attempts` / `notify_templates`, транзакционный журнал, диспетчер с тремя циклами (`python -m src.notify.dispatcher`, exit-гейт по `NOTIFY_ENABLED`), сценарий «новая запись» с рендером, порт `NotifyQueue` с внутрипроцессной `FakeQueue`. Настройки `NOTIFY_ENABLED` / `NOTIFY_POLL_INTERVAL` / `NOTIFY_CHANNEL_PRIORITY` / `NOTIFY_REENQUEUE_AFTER` и валидатор принудительного выключения при `ENV=testing` уже в `backend/src/core/config.py`.

Транспортного слоя нет: `REDIS_URL` отсутствует, зависимости очередей нет, скелета воркера нет, включённого тестового контура нет. При включённом флаге диспетчер бежит на `FakeQueue` с громким предупреждением — заявленная заглушка границы части 1 (выбор адаптера в `dispatcher.main()`).

Часть 2 строит транспортную инфраструктуру: адаптер очереди на Redis, скелет воркера, настройку `REDIS_URL`, Redis в dev/e2e-стеках и включённый тестовый контур. Всё про логику доставки — части 3–5 (#484–486).

**Смена транспорта против семейской рев.3.** Семейная спека предписывала arq (ADR 010) с запасным вариантом «собственные Redis Streams». Панельное ревью этой спеки (6 ревьюеров, исследовательская проверка) дало факты против arq: проект переведён автором в режим «только критические исправления» (закреплённый issue #510, октябрь 2025), зависимость заперта потолком `redis>=4.2,<6`, клиент только асинхронный (порт `NotifyQueue` синхронный), а параметр постановки в именованную очередь легко перепутать (`_queue_name`; неверное имя молча уходит в kwargs джоба). Дополнительно: собственные надёжные списки на LIST+Lua для статусных категорий противоречат текущим рекомендациям Redis (механизм «хотя бы один раз» — Streams + consumer groups с нативным PEL и возвратом зависших). Решение: **транспорт — Redis Streams + consumer groups напрямую через redis-py, без библиотеки очередей** (ADR 013, заменяет ADR 010; семейская спека правится до рев.4 тем же коммитом). Это активация запасного варианта самого ADR 010, не новое направление.

## 2. Что строим и что не строим

Строим:

1. зависимость `redis` (redis-py; пол версии в `pyproject.toml` по конвенции репозитория — аннотированные минимальные версии, образец `jinja2>=3.1.6`) и адаптер очереди на Redis Streams — реализация протокола `NotifyQueue` (§3.1);
2. контракт inbound-события `notify:inbound` — фиксация формата и правил валидации (§3.2);
3. настройку `REDIS_URL` с правилами отсутствия и безопасности (§3.3);
4. скелет воркера — вторая процесс-точка входа (§3.4);
5. Redis в dev-стеке (`--notify`) и включённый режим e2e-стека (§3.5);
6. включённый тестовый контур: маркер, стражи, CI-джоба, включённый e2e (§3.6).

Не строим (границы части 2):

- потребление `notify:tasks`, реестр каналов, перебор по приоритету, транспортные ретраи и настройка `NOTIFY_SEND_RETRIES`, публикация статусов воркером — часть 3 (#484); `NOTIFY_SEND_RETRIES` вводится там же вместе с потребителем (отклонение от семейской строки «настройки» в рев.4: неиспользуемая настройка — лишнее);
- канал Telegram и первые производители inbound-событий — часть 4 (#485);
- админка доставок/шаблонов — часть 5 (#486);
- потребители `notify:inbound` — задел двусторонности, потребителей в пилоте нет; ретенция и подтверждение входящих (что делать с непрочитанными) — решение с первым продюсером (#485);
- лидер-выборы и многоинстансовость: допущение «один диспетчер и один воркер на инстанс Redis» фиксируется документально (§3.1), guards не строятся (dev/CI-контуры изолированы);
- CLI инспекции очереди, мониторинг Redis — нет.

## 3. Решения

### 3.1 Адаптер очереди — Redis Streams

Модуль `backend/src/notify/redis_queue.py`, класс `RedisQueue` — реализует протокол `NotifyQueue` (`queue.py`) напрямую через **синхронный** клиент `redis.Redis` (пакет `redis`). Диспетчер вызывает методы очереди из своих асинхронных циклов через `asyncio.to_thread` — синхронный вызов обёрнут в поток, событийная петля не блокируется; правка точек вызова в `dispatcher.py` входит в объём части 2 (протокол порта не меняется). Воркер (часть 3) — самостоятельный процесс, использует клиент так же.

- **Три стрима**: `notify:tasks` (вниз), `notify:statuses` и `notify:inbound` (вверх). Запись — `XADD` с приблизительным потолком длины (`MAXLEN ~ 10000`; при достижении потолка запись не отклоняется — Redis подрезает старейшие сам): очередь транспортна, реальная ретенция — таблицы БД (ADR 008), потолок только ограничивает рост и срок хранения PII-несущих записей в Redis.
- **Потребительские группы**: `worker` для `notify:tasks` (появится в части 3), `dispatcher` для `notify:statuses` и `notify:inbound`. Группа создаётся при старте процесса-потребителя (`XGROUP CREATE ... MKSTREAM`; подавляется только конкретно `BUSYGROUP` — уже существует, прочие ошибки — громко, глотать `ResponseError` целиком запрещено). Имя потребителя уникально на живой процесс (например `dispatcher-<pid>`; уникальность имени в группе корректна — возврат зависших записей идёт на уровне группы через `XAUTOCLAIM`); при штатной остановке — `XGROUP DELCONSUMER` (для потребителя без записей в PEL), чтобы не копить призраков-потребителей.
- **`enqueue_task`** — `XADD notify:tasks` с payload задачи (семейская §4.2) одним полем. До части 3 записей некому читать — они копятся под потолком MAXLEN; перезаливка из БД (уже в части 1) переживает полную чистку Redis.
- **`claim_statuses` / `claim_inbound`** — `XREADGROUP` (неблокирующее чтение, батч; имена потребителей — выше), элементы возвращаются наружу с техническим ключом `_qid` — идентификатором записи стрима (конверт; подчёркивание = зарезервирован транспортом, полевые контракты семейской §4.2/§4.3 не меняются). **`ack_status` / `ack_inbound`** — `XACK` по `_qid`. Дубль ack безвреден. Записи стримов — недоверенный вход: перед записью в БД диспетчер валидирует их (словарь стадий, существование задачи); payload задач валидирует воркер части 3 (канал в реестре, адрес, длина текста) — правило фиксируется сейчас, исполняется с появлением потребителя.
- **`reclaim_hanging`** — `XAUTOCLAIM` при старте диспетчера: возврат зависших в PEL записей (упавший прошлый процесс) в доставку своей группы. Параметры: цикл по курсору до исчерпания (`0-0`), `min-idle-time` не меньше `NOTIFY_REENQUEUE_AFTER`, явный `COUNT`; записи, уже удалённые подрезкой MAXLEN (третий элемент ответа `XAUTOCLAIM`), невосстановимы — журнал и терминально, из PEL они уходят тем же вызовом. Анти-паттерн «сливать собственный PEL чтением `XREADGROUP 0` в каждом цикле» запрещён — он сбрасывает idle-время и держит записи вечно ниже порога возврата.
- **Методы продюсера** `publish_status` / `publish_inbound` (вне протокола, зеркально `push_*` у `FakeQueue`) — `XADD` в соответствующие стримы; в части 2 их используют маркированные тесты, в части 3 — воркер.
- **Громкость отказов**: исключения транспорта не глушатся — в журнал идут класс и сообщение исключения и идентификаторы записей, без тел сообщений и с маскированием адресов; подключение: пул соединений с явным `max_connections` (≈10), `socket_timeout` больше любого BLOCK-параметра чтения (диспетчер читает неблокирующе — BLOCK не используется; запас — требование и воркеру части 3), retry-политика клиента задаётся явно, без тихих автоматических ретраев (в redis-py ≥6 ретраи включены по умолчанию — отключаются явно). Отказ соединения не роняет циклы диспетчера: очередной тик повторяет попытку, отказ остаётся громким в журнале.
- **Выбор адаптера в `dispatcher.main()`**: заглушка части 1 удаляется. `queue is None` и `REDIS_URL` непуст → `RedisQueue`; при включённом флаге и пустом `REDIS_URL` — выход с кодом 2 и стабильным сообщением «notify: transport not configured» (без значения URL). При заданном, но недоступном Redis — PING при старте, отказ громко, выход с кодом 2 (не молчаливое вращение циклов). `FakeQueue` остаётся только тестовой реализацией части 1.
- **Сбой постановки не сжигает попытки события**: исключение адаптера в точке постановки не увеличивает `attempts` события (сегодня любое исключение в обработчике сценария увеличивает — после 3 событие умирает с `processing_error`); задача остаётся «в очереди» в БД, восстановление — цикл перезаливки по `NOTIFY_REENQUEUE_AFTER`. Правка диспетчера входит в объём части 2. Неудачная постановка увеличивает тот же счётчик перезаливок, что и успешная (сегодня `reenqueues` растёт только после успешной постановки — при мёртвом транспорте вечный churn без терминального состояния): по достижении `REENQUEUE_CAP` задача переводится в «не доставлено» с ошибкой транспорта — существующий путь потолка, бесконечных повторов нет.
- **Один писатель в БД** — диспетчер (ADR 009); воркер БД не читает.

### 3.2 Контракт inbound-события

Формат `notify:inbound` фиксируется здесь (порт сегодня объявляет его непрозрачным словарём); производители появятся начиная с части 4:

```json
{"channel": "telegram", "external_address": "+7…", "kind": "text", "text": "…", "task_id": 456, "occurred_at": "<UTC>"}
```

- `task_id` — идентификатор задачи доставки, к которой относится ответ (единое имя с семейскими §4.2/§4.3); `occurred_at` — время внешнего сообщения, UTC; все ключи обязательны; `text` ≤ 4000 символов.
- Источник только нормализует сообщение в этот формат; вся обработка — расширения-обработчики в процессе диспетчера (семейская §3.6).
- **Правила потребления** (закрепляются вместе с контрактом, исполняет диспетчер с части 3): `channel` валидируется по реестру каналов, `kind` — по словарю пилота (`text`); неизвестное значение — журнал (идентификаторы, без текста сообщения) + `XACK`; отдельный стрим для отбракованных не заводится — вернёмся к нему с первым потребителем. `external_address` — строка ≤ 20 символов; формат-валидация — с первым продюсером (#485, адрес пилота — телефон). Потребитель сверяет `external_address` с адресом канала задачи `task_id` — несовпадение обрабатывается как невалидное (защита от перепутанных или подменённых ответов между клиентами). Дедупликация по `task_id` сознательно не строится — повторная обработка безвредна, принятый дубль (семейская §4.4).
- **Граница доверия на записи**: в стрим пишет только транспортный контур подсистемы; инстанс Redis выделен контуру (§3.5), отдельная учётка записи не заводится до появления внешних продюсеров (#485 пересмотрит).

### 3.3 Настройка `REDIS_URL`

- `REDIS_URL: str = ""` — пустая строка = транспорт не настроен. Семантика запуска — §3.1/§3.4. Документируется в `backend/.env.example` плейсхолдером.
- `ENV=production` + `NOTIFY_ENABLED=true`: `REDIS_URL` обязателен и обязан быть `rediss://` с учётными данными — иначе фатальная ошибка старта (образец — `_resolve_secret_key` для `SECRET_KEY`); неаутентифицированный и незашифрованный транспорт в production не повышается.
- URL — прикладное секретное значение: тип поля `SecretStr` (не раскрывается в `repr`/`model_dump`), ошибки валидации настроек не раскрывают ввод, в логи и тексты ошибок URL не попадает (в сообщениях только факт «не настроен / недоступен»).
- Прочие настройки части 1 не меняются. `NOTIFY_TEST_CONTOUR` не вводится: включённый контур §3.6 управляется переменными самой среды запуска, предохранитель `ENV=testing` остаётся как есть (срабатывает там, где ENV реально выставлен — например, в тестах настроек части 1).

### 3.4 Скелет воркера

Модуль `backend/src/notify/worker.py`, вход `python -m src.notify.worker` — вторая процесс-точка входа той же кодовой базы (ADR 009 — воркер без БД).

- Выключенная подсистема: запись в журнал и выход 0 — симметрично диспетчеру.
- Включённая: те же fail-fast-гейты, что у диспетчера (пустой `REDIS_URL` → код 2; недоступный Redis по PING → код 2), затем обработчики SIGTERM/SIGINT (как у диспетчера) и холостой цикл ожидания с одной стартовой записью в журнале «worker skeleton: delivery logic ships in #484».
- Скелет **не читает** `notify:tasks`: потребление с пустой логикой теряло бы записи (группа создана, но записи копились бы в PEL без обработки — часть 3 строит чтение `XREADGROUP` и обработку). Скелет проверяет связку «процесс стартует, гейты и обработчики сигналов работают, связь есть» — это и есть S5.

### 3.5 Стеки

Compose-файлов в репозитории нет и не появляется: «стеки» — это `dev.sh` (локальный) и `scripts/e2e-shard-start.sh` (e2e). Изоляция: контур подсистемы использует **выделенный** инстанс Redis — молчаливое переиспользование чужого отвечающего инстанса запрещено (payload несёт телефоны и тексты записей; писали бы в чужое состояние). Конфиг выделенного инстанса: без eviction (`maxmemory-policy noeviction`) — выталкивающие политики молча выбрасывают записи стримов.

- **dev.sh**: флаг `--notify` — на этот запуск выставляет `NOTIFY_ENABLED=true` и `REDIS_URL=redis://localhost:6379/0`; занятость порта проверяется до запуска дочернего процесса — занят чем угодно → остановка с сообщением (освободить порт или задать `REDIS_URL` явно — осознанный выбор другого инстанса); свободен — запуск `redis-server` дочерним процессом с `--save "" --appendonly no` (без файла состояния на диске — PII-записи не переживают рестарт; окно потери — транспорт, ретенция в БД; гаснет вместе со стеком); затем диспетчер и скелет воркера.
- **e2e-стек**: включённый режим переменной окружения `NOTIFY_E2E_ENABLED=1`. Изменения скрипта перечислены: собственная пара портов вне диапазона шардов (по умолчанию бэкенд 8005, веб 3006 — шарды занимают 8001–8004/3002–3005; значения задаются параметрами окружения на случай локальных параллельных запусков); `REDIS_URL` берётся только из явно переданного значения (CI-джоба передаёт адрес своего сервис-контейнера; локальный запуск без явного `REDIS_URL` поднимает дочерний `redis-server`); запуск диспетчера дочерним процессом; расширение trap-очистки на новые дочерние процессы (redis, диспетчер — сегодня trap гасит только бэкенд и веб). Режим по умолчанию ничего не меняет: четыре штатных e2e-шарда остаются без Redis (семейская US-7). Игнор `ENV` где-либо: не делаем — глобальный `ENV` рулит поведением приложения (пропуск миграций в lifespan, монтаж админ-маршрутов), его смена в общем `.env.test` ломает штатные шарды.
- Redis-контур эфемерен: CI — сервис-контейнер, локально — дочерний процесс; сид-данные тестовые, реальных PII в контуре нет.

### 3.6 Включённый тестовый контур

- Маркер `redis` регистрируется в `backend/pyproject.toml`.
- Страж исполнения: декоратор `skipif` по отсутствию `REDIS_URL` в среде — локальный прогон без Redis остаётся зелёным без фильтров (декоратор, а не вызов `pytest.skip` в теле — трекер пропусков сканирует безликие вызовы динамически, декларативный страж не плодит их).
- Файлы `backend/tests/test_notify_redis_*.py`: адаптер против настоящего Redis — постановка и чтение задачи, надёжное чтение статусов (claim/ack/reclaim через группы), перезаливка после полной чистки Redis, fail-fast-гейты запуска (пустой URL, недоступный Redis), громкость отказов (исключение транспорта не глушится, попытки события не сжигаются). Каждый тест работает в выделенном индексе БД Redis (или с уникальным префиксом ключей) и чистит своё состояние — детерминизм на машине разработчика, где может жить и dev-контур.
- CI (`.github/workflows/test.yml`): новая джоба `notify-tests` — сервис-контейнер Redis, закреплённый по дайджесту (образ линии `redis:7`, healthcheck `redis-cli ping`), `REDIS_URL` в окружении, прогон `pytest -m redis`; джоба обязана падать, если выполнено 0 маркированных тестов или все пропущены (страж пустого зелёного — механическая проверка количества выполненных). Джоба `backend-tests` не меняет команду вовсе — инвариант US-7 «стандартный прогон не требует Redis» проверяется её неизменностью и отсутствием Redis в её окружении; чтобы новые модули `redis_queue.py` и `worker.py` (в стандартной джобе почти не исполняются — тесты контура скипаются) не сдвигали порог покрытия 80%, они исключаются из измерения покрытия по образцу `src/seed/*` (`[tool.coverage.run] omit` с указателем: модуль измеряется контуром `notify-tests`).
- Включённый e2e в той же джобе после юнит-слоя: стек `e2e-shard-start.sh` в режиме `NOTIFY_E2E_ENABLED=1` (`REDIS_URL` — сервис-контейнер джобы) и один Playwright-сценарий S1; после него — маркированная проверка очереди (в стриме ≥ 1 задача, payload §4.2 корректен). Полные 4 шарда не затрагиваются.

## 4. User Scenarios (часть 2; тип проверки указан явно — финальное закрепление E2E за планом)

- **S1 — включённый стек** (E2E): стек поднимается с включённой подсистемой и Redis; создание записи с чекбоксом «отправлять оповещения» на будущего клиента проходит штатно, UI записей не изменился; задача появляется в настоящем стриме Redis с готовым текстом и адресом канала (утверждение об очереди — маркированный бекенд-тест того же контура).
- **S2 — стандартный прогон без Redis** (инвариант, US-7): полный pytest и 4 штатных e2e-шарда проходят без Redis; журнал событий пишется, диспетчер и воркер не стартуют. Проверка: неизменность основной джобы и шардов, отсутствие Redis в их окружении.
- **S3 — fail-fast-гейты конфигурации** (unit): `NOTIFY_ENABLED=true` без `REDIS_URL` — диспетчер и воркер завершаются с кодом 2 и стабильным сообщением «notify: transport not configured»; заданный, но недоступный Redis — отказ по PING при старте, тоже код 2.
- **S4 — переживание чистки Redis** (маркированный интеграционный): работающий диспетчер, полная чистка Redis — задачи «в очереди» перезаливаются из БД не раньше `NOTIFY_REENQUEUE_AFTER`; тест состаривает `updated_at` напрямую (предпочтительно — детерминизм) или переопределяет порог малым значением (2 с) — без двухминутного ожидания; дубль допустим (семейская §4.4).
- **S5 — скелет воркера** (unit): `python -m src.notify.worker` — выключено: тихий выход 0; включено: гейты, PING, обработчики сигналов, холостой режим без чтения очереди.

## 5. Behavioral Delta

**До:** оповещения — выключенный каркас: включённый диспетчер бежит на `FakeQueue` с предупреждением, воркера нет, стеки и CI не знают Redis; ненастроенный транспорт не обнаруживается.

**После:** по умолчанию для пользователя ничего не меняется — флаг выключен, процессы не стартуют, стандартные тесты и e2e идут без Redis. Появляется включённый контур: `dev.sh --notify` поднимает выделенный Redis + диспетчер + скелет воркера; CI прогоняет маркированные тесты и включённый e2e против настоящего Redis; включённая подсистема с ненастроенным или недоступным транспортом падает при старте с понятной причиной вместо молчаливой работы вхолостую.

## 6. Первая задача — смоук транспорта

Короткий эксперимент в ветке задачи: `redis-py` под Python 3.12+, `XADD`/`XREADGROUP`/`XACK`/`XAUTOCLAIM` против локального Redis 7, обёртка адаптера поверх синхронного клиента. Результат — краткий отчёт комментарием в #483 (требование семейской §8 сохранено: решение о транспорте подкреплено проверкой; пороговых развилок нет — arq отклонён на данных панели, альтернативы SAQ/streaq — воркер-фреймворки поверх тонкого порта, лишний слой).

## 7. Риски

- **Очередь без потребителя до части 3**: в включённом контуре записи копятся под потолком MAXLEN и перезаливаются из БД с дублями — принято контрактом (§4.4 семейской спеки); включённый e2e не ассертит точное число записей (только «≥ 1 и корректный payload»).
- **MAXLEN стирает старейшее**: при переполнении без потребителя теряются старейшие записи стрима (запись не отклоняется — Redis подрезает сам); потеря безвредна, пока строка задачи жива в БД (перезаливка восстановит), полный отказ транспорта завершается потолком перезаливок (§3.1).
- **Стоимость включённого e2e**: полный стек (сборка web/admin) ради одного сценария; если джоба окажется тяжёлой — e2e-слой отключается флагом до #484, маркированные тесты остаются (решение — в плане, не в спеке).
- **Занятый порт 6379 в dev**: остановка с сообщением, тихого обхода нет; переиспользование чужого инстанса запрещено (§3.5).
- **Допущение одного инстанса**: два диспетчера на одном Redis — двойная обработка; фиксируется документально (§2), пилотные контуры изолированы.
