# #513: клиентский кабинет — чтение /my (записи/фото/платежи) + экраны

- Issue: #513 (выделено из #499 решением Gate A 2026-10-20)
- Дата: 2026-10-22 · статус: черновик до Gate B
- Семья: #499 — клиентские учётки и бронирование (спека `docs/specs/2026-10-20-web-client-auth-booking-design.md`, план `docs/plans/2026-10-21-web-client-auth-booking-plan.md`); #479 — web потребляет только `@memo/api-client`; #480 — TS-юнионы статусов экспортированы из api-client; #497 — нейминг `list*` для коллекций (цель для новых функций).
- depends-on: #499. Клиентская сессия (роль `client`, зависимость `require_client_session`, `GET /api/v1/my/client`), экран `/cabinet` и вход кодом по телефону на момент написания существуют только в открытом PR #523; спека #513 целится в main после его мержа и опирается на контракт этих сущностей из спеки #499.

## Контекст

После #499 клиент входит в веб-кабинет по телефону с одноразовым кодом и бронирует занятие (`POST /api/v1/my/records`). Экран `/cabinet` после входа показывает только телефон и кнопку выхода — разделы чтения отложены в #513 (план #499, задача 9: «без заглушек разделов (#513)»). Гостевая галерея фото живёт на публичном `GET /photos` c фильтром `is_public=true`. Сегодня у клиента нет способа увидеть свои записи и платежи (чтение требует staff-прав `records:read` / `payments:read`, которых у роли `client` нет и не будет), а свои фото — только опосредованно: публичная галерея показывает лишь опубликованные и без понятия «моё».

## Что строим (концепция, Gate A)

1. Три эндпоинта чтения под `/api/v1/my/*`, по одному на сущность; агрегатного «выдай всё» эндпоинта нет (решение Gate A #499, подтверждено здесь):
   - `GET /api/v1/my/records` — свои записи с визитами, составное представление с датой/временем занятия и названием услуги;
   - `GET /api/v1/my/photos` — все свои фото, включая непубличные, с признаком публикации;
   - `GET /api/v1/my/payments` — свои платежи с кратким контекстом занятия.
2. Схемы ответов без служебных полей: отдельные per-endpoint схемы (канон дома — per-endpoint наборы типов, без свёртки алиасов); владелец определяется только клиентской сессией — параметров выбора клиента во входе нет.
3. Экраны веб-кабинета: `/cabinet` получает три раздела-под-маршрута — `/cabinet/records` («Мои записи»), `/cabinet/photos` («Мои фото»), `/cabinet/payments` («Мои платежи»); `/cabinet` после входа редиректит на `/cabinet/records`.

Отклонённые альтернативы (фильтр расхождений Gate A):

- **Переиспользовать админские `GET /records` / `GET /photos` / `GET /payments` с фильтром по клиенту** — нарушает правило гранулярного доступа REST (другой контракт = отдельный эндпоинт; объектный уровень — фильтром в сервисе); записям и платежам дополнительно требовались бы staff-права, которых у роли `client` нет. Отсеяно правилом репозитория.
- **Агрегатный `GET /my/cabinet` одним вызовом** — прямо исключён решением Gate A #499 («агрегатного эндпоинта нет»), три экрана живут на своих страницах и загружаются независимо.
- **Форма разделов (табы на одной странице вместо под-маршрутов)** — различие только во внутреннем устройстве UI; выбраны под-маршрута: прямые адреса и якоря E2E.

## Разрешение вопросов из задачи

- **Публичность фото.** `GET /my/photos` возвращает все фото клиента — и публичные, и непубличные — с признаком `is_public`. Клиент видит, какие его фото опубликованы в общей галерее; публичная галерея (`GET /photos?is_public=true`) не меняется. Управление публикацией из кабинета не входит в эту задачу (признак ставит сотрудник).
- **Статусы оплат.** У платежа в модели нет статуса — только сумма, способ (`cash` / `card` / `transfer`, необязательный) и дата. Нового поля или концепта статуса оплаты не вводим: «Мои платежи» показывают сумму, способ, дату и связь с занятием. Статус каждого визита (`waiting` / `visited` / `missed` / `cancelled`) клиент видит на экране «Мои записи» — по одному на посетителя.

## Контракт API

Общее для трёх эндпоинтов:

- Доступ — зависимость `require_client_session` из #499: она читает только клиентскую куку `memo_client_session` (отдельная от staff-куки `memo_session`, тот же механизм строк сессий) и пропускает только роль `client`; объектный уровень — фильтрация по владельцу в сервисе (`user.client_id`). Нет клиентской сессии или сессия не клиентская (в том числе staff-токен, скопированный в клиентскую куку) → единый 401 `AUTH_UNAUTHORIZED`, как без сессии (реализация #523). Права-токены (`records:read` и т.п.) не используются: роль `client` в `ROLE_PERMISSIONS` не входит (решение #499).
- Пагинация — кирпич `PaginationParams` как есть (`page` / `per_page` + унаследованный машинный `?id=` сет-фильтр #232 — канон всех пагинированных списков, закреплён структурным тестом), конверт `PaginatedResponse[Item]` (`items` / `total` / `page` / `per_page`). Собственных полей и фильтров по содержимому `/my`-списки не добавляют.
- Сортировка фиксированная, параметров сортировки нет: записи — по моменту начала занятия по убыванию, при равенстве `id` по возрастанию; фото и платежи — по `created_at` по убыванию, при равенстве `id` по возрастанию (канон фото: детерминированный тай-брейк против «плавающих» границ страниц). Визиты внутри записи — по `id` по возрастанию.

### GET /api/v1/my/records

Свои записи (владелец — клиент сессии) с визитами. Элемент `items[]` — одна запись:

| Поле | Тип | Что это |
|---|---|---|
| `id` | UUID | идентификатор записи |
| `activity_date` | date | дата занятия (из начала занятия) |
| `activity_start` | time | время начала занятия |
| `activity_end` | time | время окончания занятия = начало + длительность (в модели занятия хранятся только начало и длительность) |
| `service_title` | string | название услуги (каноническое имя составных чтений) |
| `comment` | string \| null | комментарий записи (его оставляет и клиент при бронировании, и персонал) |
| `visits[]` | массив | визиты записи, по посетителю, по `id` по возрастанию |
| `visits[].id` | UUID | идентификатор визита |
| `visits[].visitor_name` | string \| null | имя посетителя; `null` для безымянного места (легально по домену) — на экране «Посетитель» |
| `visits[].status` | VisitStatus | статус визита: `waiting` / `visited` / `missed` / `cancelled` |
| `visits[].price` | integer | цена визита в рублях: снапшот, зафиксированный при создании; при наличии визитового `custom_price` — он, иначе сохранённый `price`. Тариф на чтении не участвует (инвариант #357: цена визита — снимок на момент создания, никогда не выводится из тарифа при чтении) |

Записной `custom_price` (переопределение итога записи целиком) не показывается: экран отдаёт по-визитные цены, а фактические суммы оплат клиент видит на «Мои платежи».

Не входят (служебное): `client_id`, `activity_id`, `seats`, `status` записи (колонка модели; клиенту отдаётся только статус визита), `custom_price`, `tariff_id`, `visitor_id`, `record_id`, `created_at` / `updated_at` записи и визитов.

### GET /api/v1/my/photos

Все фото клиента (владелец — клиент сессии), без фильтрации по публичности. Элемент `items[]`:

| Поле | Тип | Что это |
|---|---|---|
| `id` | UUID | идентификатор фото |
| `filename` | string | файл — тот же идентификатор, что в публичной галерее; рендер тем же механизмом |
| `is_public` | boolean | признак публикации в общей галерее |
| `tags` | string[] | названия тегов фото (сервер разрешает связи M2M в названия; объекты-теги с идентификаторами остаются в admin-контракте) |
| `created_at` | datetime | дата появления |

Не входят: `client_id`, `client_name` (запросчик — сам клиент), `service_id`, `activity_id`, `location_id`, `updated_at`.

### GET /api/v1/my/payments

Платежи записей клиента (платёж «свой», если связанная запись принадлежит клиенту сессии). Элемент `items[]`:

| Поле | Тип | Что это |
|---|---|---|
| `id` | UUID | идентификатор платежа |
| `amount` | integer | сумма в рублях |
| `method` | `cash` / `card` / `transfer` / null | способ оплаты; `null` допускается моделью — на экране «Способ не указан» |
| `created_at` | datetime | дата платежа |
| `record` | объект | краткий контекст занятия: `id` (UUID), `activity_date` (date), `service_title` (string). Платёж всегда связан с записью: `record_id` — обязательный FK, платежи удаляются вместе с записью; ветки `null` не существует |

Не входят: `updated_at`; полных данных записи в контексте нет.

### Ошибки

- 401 `AUTH_UNAUTHORIZED` — нет клиентской сессии или сессия не клиентская (единый код, реализация #523).
- 422 — некорректная пагинация (общий канон валидации query).
- Иные коды не появляются: фильтров по содержимому и идентификаторов во входе нет, чужие данные недостижимы фильтром владельца.

## Экраны веб-кабинета

- `/cabinet` (оболочка из #523; на main сейчас заглушка с телефонной формой без логики — #523 превращает её в рабочую оболочку): анониму — форма входа (телефон + код); вошедшему — редирект на `/cabinet/records`.
- Навигация кабинета: три ссылки-раздела «Мои записи» / «Мои фото» / «Мои платежи», активный подсвечен; телефон клиента и кнопка «Выйти» — из #523 (данные `GET /my/client`).
- `/cabinet/records` — карточки занятий по убыванию даты: дата, время (начало–окончание), услуга, свой комментарий; внутри — строка на посетителя: имя (для безымянного места — «Посетитель»), статус на русском, цена. Русские подписи статусов: `waiting` — «Ожидает», `visited` — «Состоялось», `missed` — «Пропущено», `cancelled` — «Отменено». Пусто → «У вас пока нет записей» и ссылка на страницу бронирования.
- `/cabinet/photos` — сетка фото тем же механизмом рендера, что гостевая галерея (статическая раздача файлов; `is_public` фильтрует только списки, не байты — план подтверждает путь рендера для непубличных имён); на каждом фото бейдж публикации: `is_public=true` — «Опубликовано», иначе — «Не опубликовано». Пусто → «У вас пока нет фото».
- `/cabinet/payments` — строки по убыванию даты: сумма, способ на русском (`cash` — «Наличные», `card` — «Карта», `transfer` — «Перевод», `null` — «Способ не указан»), дата, занятие (услуга + дата). Пусто → «У вас пока нет платежей».
- Постраничная навигация внизу каждого списка при выходе за одну страницу (условный элемент — проверяется компонентными тестами, в Visual Compliance Checks не входит).
- Компоненты: примитивы web (`MKCard`, `Pill`, `Button`) и новые лёгкие list-компоненты web; `DataTable` админа не используется (web и admin — разные приложения, web на `@memo/api-client` и своих компонентах, канон #479).

## Behavioral Delta

До: после входа (после #523) клиент видит в кабинете только телефон и кнопку выхода; свои записи, фото и платежи ему недоступны нигде (чтение требует staff-прав; фото — только публичные в общей галерее).

После: в кабинете три раздела. «Мои записи» — занятия с датой, временем, услугой, посетителями, статусами и ценами. «Мои фото» — все свои фото, включая непубличные, с признаком публикации. «Мои платежи» — сумма, способ, дата и связь с занятием. Гостевая галерея, админ-приложение и публичные контракты не меняются.

## User Scenarios

- С1. Клиент входит в кабинет и видит свои записи: дата/время, услуга, посетители, статусы, цены. → E2E: вход → `/cabinet/records`, карточки записей сида.
- С2. Изоляция данных: клиент видит только свои записи, фото и платежи. → E2E: сущности второго клиента сида отсутствуют на всех трёх экранах.
- С3. Клиент видит все свои фото, включая непубличные, с признаком публикации. → E2E: непубличное фото сида видно в кабинете с бейджем «Не опубликовано» и отсутствует в гостевой галерее.
- С4. Клиент видит историю платежей с контекстом занятия. → E2E: `/cabinet/payments`, строка с суммой, способом, датой и услугой.
- С5. Аноним без сессии на разделе кабинета видит форму входа и никаких данных. → E2E: `/cabinet/records` без сессии → форма входа.

## Тесты

Backend (pytest):

- контракт каждого эндпоинта: состав полей ответа, отсутствие служебных полей (списки «не входят» выше), конверт пагинации, 422 на некорректную пагинацию;
- 401: без клиентской куки и со staff-токеном в клиентской куке — единый код 401;
- изоляция: второй клиент не видит чужие записи/фото/платежи;
- цена визита — снапшот: при наличии визитового `custom_price` возвращается он, иначе сохранённый `price`; чтение к тарифу не обращается (инвариант #357);
- `visitor_name: null` для безымянного места; порядок строк детерминирован (тай-брейк по `id`);
- фото: непубличные возвращаются наравне с публичными;
- платеж: контекст занятия присутствует всегда; `method: null` проходит контрактом.

Web (vitest, компонентные):

- рендер трёх списков на фикстурах, пустые состояния, русские подписи статусов и способов (включая `null` — «Способ не указан», безымянное место — «Посетитель»), бейдж публикации, постраничная навигация при выходе за страницу.

E2E (новый playwright-проект web — первый для приложения, входит в задачу):

- конфиг и клиентская сессия-фикстура по потоку входа #523 (storageState; код входа достаётся напрямую из тестовой БД — SQL-хелперы по образцу `seed-ids`);
- порт web-e2e стека — собственный сид-стек по канону dev-workflow (шардовые/динамические порты), не порт playground `:3101`;
- сид-дельта входит в задачу: в существующем сиде все фото публичные (`is_public: true`) и принадлежат одному клиенту — нужны ≥1 непубличное фото клиента кабинета (С3) и сущности второго клиента: записи, фото, платежи (С2); точный состав — план по факту сида #523 (семейство client-auth приходит с ним);
- сценарии С1–С5 выше.

## Границы (не делаем)

- Управление публикацией фото из кабинета (изменение `is_public`) — нет.
- Отмена/изменение записей из кабинета — нет.
- Фильтры и пользовательская сортировка на экранах — нет (сортировка фиксированная).
- Агрегатный эндпоинт «всё сразу» — нет.
- Новый концепт статуса оплаты — нет.
- Изменения админа, публичной галереи и публичных контрактов — нет.

## api-client

Новые функции (нейминг `list*` для коллекций — цель #497, новый код следует целевому канону): `listMyRecords`, `listMyPhotos`, `listMyPayments` — со своими per-endpoint наборами типов; статус-юнионы переиспользуются из экспортов #480.
