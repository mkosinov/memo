# Спека: редактирование занятия — честная календарная дата вместо «открытая неделя + день недели» (#553)

- Дата: 2026-10-25
- Приложение: admin (расписание)
- Продолжение: спека `docs/specs/2026-10-23-schedule-create-form-unified-design.md` (#280) сознательно заморозила семантику редактирования («в том числе сохраняется её сегодняшняя конвертация даты в "открытая неделя + день недели" — перенос редактирования на честные календарные даты — отдельная задача, не эта»). Эта спека — та задача; устраняется режимный перекос, оставленный унификацией форм.
- Предыстория уже влита в main (#280, PR #561, коммит `f1178579`; проверено на `origin/main`): форма создания — общая разметка с редактированием (`ActivityForm.tsx`, вкладки-обёртки `CreateActivityTab.tsx`/`SettingsTab.tsx`); создание отправляет полную дату-время — `addActivity` принимает необязательный `start` и при его наличии пропускает значение в payload как есть (ветка с комментарием «GH #280», `ScheduleDataContext.tsx`); тост создания — «Создано: <услуга> — <дата по-русски>, <ЧЧ:ММ>» через `formatDateRu`; общие хелперы даты-времени — `frontend/admin/lib/datetime.ts` (`composeLocalISO`, `snapMinutes`, `formatDateRu`, `dayIndexToDate`).
- Бэкенд-контракт и api-client: без изменений. `PATCH /api/v1/activities/{id}` уже принимает полную дату-время в `start` (серверный `ActivityPatch.start: datetime | None`; клиентская `ActivityPatchSchema.start` — строка полной даты-времени).
- Ревизия 2 (2026-11-13, гейт B, решения пользователя): модалка НЕ закрывается при переносе в другую неделю — карточка остаётся доступной для правки, занятие живёт на выбранной дате; прошедшие даты подтверждены разрешёнными.

## Контекст и проблема

Админ редактирует занятие во вкладке настроек модалки занятием (instant-patch: каждое изменение поля применяется сразу). Поле «Дата и время» свободно — календарь нативного `datetime-local` позволяет выбрать любую дату, в том числе в другой неделе. Но отправка сегодня теряет выбранную дату:

- вкладка конвертирует выбор в «номер дня недели + минуты» и выбрасывает саму дату (`SettingsTab.tsx`: из значения поля берутся только `dayOfWeek = (date.getDay() + 6) % 7` и `snappedMinutes`);
- контекст расписания собирает дату занятия обратно как «календарная дата ОТКРЫТОЙ недели + номер дня + минуты» (`ScheduleDataContext.tsx`, `updateActivityFn`: `composeLocalISO(dayIndexToDate(currentWeek, updates.dayIndex), updates.startMinutes)`).

Следствие: админ выбирает в форме вторник следующей недели — занятие молча переезжает на вторник открытой недели. Перенести занятие в другую неделю через форму нельзя; выбор чужой недели искажается без предупреждения. Создание после #280 шлёт полную дату напрямую — получился режимный перекос: создание на любую дату, редактирование только внутри открытой недели.

Drag&drop в сетке использует ту же ветку `dayIndex + startMinutes` — для него семантика «открытая неделя» корректна по построению (перетаскивание возможно только внутри видимой сетки), эта правка его не затрагивает.

## Концепт

Редактирование зеркально созданию (#280, паттерн `CreateActivityTab.tsx`): форма передаёт полную дату-время, контекст расписания отправляет её в API напрямую. Три точки правки:

1. **Вкладка редактирования** (`SettingsTab.tsx`, instant-patch поля даты-времени): вместо `{ startMinutes, dayIndex }` отправлять `{ start: composeLocalISO(datePart, snappedMinutes) }` — выбранная дата больше не выбрасывается; хелперы `composeLocalISO`/`snapMinutes` уже общие (вынесены при #280).
2. **Контракт обновления** (`ScheduleDataContext.tsx`): в union-тип обновления занятия добавляется необязательное поле `start?: string` (полная локальная дата-время, ISO). В `updateActivityFn` приоритетная ветка: есть `start` → `payload.start` уходит как есть; нет → прежняя конвертация `dayIndex + startMinutes` от открытой недели (её единственные отправители после правки — drag&drop сетки и штампы слотов; их код не меняется). Преемственность семантики уже есть в коде: `addActivity` после #280 принимает тот же union «готовый `start`» с той же приоритетностью.
3. **Тост успеха при изменении даты-времени** — сегодня instant-patch молчит (тосты в модалке только на ошибки и на создание записи). Так как занятие может уехать из открытой недели и «исчезнуть» из сетки, успешный патч даты-времени сопровождается тостом в общем тост-стеке (#261): вид — `info` (дефолт `showToast`, тестид `toast-info`), текст зеркален созданию — «Сохранено: <услуга> — <дата>, <время>» (форматирование `formatDateRu` из общего `lib/datetime.ts` — тот же источник, что у тоста создания). Точка wiring (уровень модалки или вкладки) — план; остальные поля instant-patch остаются молчаливыми.

Отвергнутые альтернативы:

1. **Полная унификация wiring создания и редактирования в один компонент с двумя режимами** — пере-архитектура масштаба #280; #280 сознательно оставил два wiring-файла при общей разметке (`ActivityForm.tsx`), повторное слияние не запрошено и удваивает риск регрессии эталона. Не строим.
2. **Выбор недели в форме (week picker) вместо полной даты** — повторная реализация механизма, который уже есть: календарь поля даты-времени уже выбирает любую дату; новая сущность «неделя» дублирует её и расходится с паттерном создания.
3. **Отправка «неделя относительно открытой + день недели» вместо полной даты** — углубляет контракт PATCH сущностью, которой сервер не знает (серверное `start` — полная дата-время); лишний слой конвертации на обоих концах.

## Границы скоупа (что мы сознательно НЕ строим)

- **Drag&drop и штампы слотов — не трогаем**: их семантика «открытая неделя + день недели» корректна по построению (взаимодействие возможно только внутри видимой сетки); код `useDnD` и ветка `dayIndex + startMinutes` не меняются.
- **Сервер и api-client — без изменений**: поле `start` в PATCH уже принимает полную дату-время; меняется только источник значения на клиенте.
- **Разметку и якоря формы редактирования — не меняем**: `input-datetime` и остальные `input-*`/`settings-*`/`select-*`/`toggle-private` якоря не трогаются (критерий незаметности рефактора из #280 сохраняется); гарантия «зелёные без правки ожиданий» касается якорей, разметки и существующих тестов drag&drop/конвертации — payload-ассерты самой вкладки редактирования (форма начинает слать `start` вместо `dayIndex + startMinutes`) правятся законно, это и есть предмет изменения.
- **Тосты на остальные поля instant-patch — не вводим**: услуга/мастер/локация/приватность остаются молчаливыми; тост только у даты-времени, где занятие может покинуть открытую неделю.
- **Прошедшие даты — разрешены, как и сегодня**: календарь поля уже свободен, навигация по неделям уходит в прошлое, сервер дату не валидирует; новый запрет не вводится (отдельное решение — вне скоупа).
- **Массовый перенос занятий, повторяющиеся занятия — вне скоупа.**

## Контракт после

- Union обновления занятия: `{ start?: string; dayIndex?: number; startMinutes?: number; …прочие поля }`; `start` приоритетен: при его наличии `dayIndex`/`startMinutes` молча игнорируются; отправителей, шлющих оба набора сразу, нет и не планируется (форма — только `start`, сетка — только `dayIndex + startMinutes`; оба сразу — отдельный юнит-ассерт, документирующий приоритет). Частичная отправка `dayIndex` без `startMinutes` игнорируется и сегодня (условие обоих полей) — сохраняется.
- `payload.start` PATCH — полная локальная дата-время ISO (`composeLocalISO(datePart, minutes)`), байт-в-байт паттерн создания.
- Пустое/частичное значение поля `datetime-local` (очистка эмитит пустую строку) — патч не отправляется вовсе (guard на пустую дату в отправителе); «сломанный» `start` в PATCH невозможен по построению.
- Тост успеха патча даты-времени: вид `info` → `toast-info`, текст «Сохранено: <название услуги> — <дата по-русски>, <ЧЧ:ММ>».
- Модалка после переноса: остаётся открытой при любом успешном патче даты-времени — и внутри открытой недели (как сегодня), и при переносе в другую неделю (решение гейта B, ревизия 2): занятие продолжает существовать на выбранной дате, карточка исчезает из открытой недели по рефетчу кэша (существующая инвалидация после мутации), а дальнейшие правки instant-patch применяются к тому же занятию по id. Это работает по построению: сетка хранит занятие для модалки в собственном локальном состоянии-снимке (не ищет его в данных недели), время жизни модалки не зависит от наличия карточки в видимой неделе.
- Ошибка PATCH (сеть/валидация): существующая семантика без изменений — error-тост (`parseApiError`), оптимистическая запись откатывается, поле хранит выбранное значение; нового поведения не вводится.

## User Scenarios

- **US-1. Перенос в другую неделю.** Админ открывает занятие открытой недели, выбирает в календаре дату следующей недели, поле применяется (instant-patch) → модалка остаётся открытой, занятие исчезает из открытой недели (по рефетчу кэша, не мгновенно), тост называет выбранную дату; переход к следующей неделе (`date-nav-next`) — занятие стоит на выбранной дате. E2E: сид-неделя 2026-06-01, перенос занятия на 2026-06-09, проверка в обеих неделях + тост + ассерт «модалка открыта» после патча; ожидание исчезновения карточки — по рефетчу (ответ GET activities), не только по тосту.
- **US-2. Перенос внутри открытой недели.** Админ меняет день и/или время в пределах открытой недели → занятие переезжает в пределах той же недели, как сегодня. E2E: смена дня недели через форму, занятие в новой колонке той же недели.
- **US-3. Правка только времени.** Админ меняет только время, не трогая дату → дата сохраняется, время меняется. E2E: смена времени через форму без смены дня.
- **US-4. Drag&drop не изменился.** Админ перетаскивает карточку занятия в сетке → перенос в пределах открытой недели по-прежнему работает (ветка `dayIndex + startMinutes` не тронута). E2E: существующий drag-тест сетки (`schedule.spec.ts`, «activity card remains visible after drag») зелёный без правки ожиданий.
- **US-5. Закрытие без изменений.** Админ открывает и закрывает форму, ничего не меняя → ни одного PATCH не уходит. E2E: счётчик сетевых запросов без патчей.

## Behavioral Delta

| Аспект | До | После |
|---|---|---|
| Дата при сохранении формы редактирования | выбор любой даты молча переносится в открытую неделю (отправляется только день недели + минуты) | занятие сохраняется ровно на выбранную календарную дату и время (в т.ч. в другой неделе) |
| Перенос занятия в другую неделю через форму | невозможен | возможен; занятие «уезжает» из открытой недели в свою |

| Модалка после переноса в другую неделю | — (перенос невозможен) | остаётся открытой; занятие доступно для правки на выбранной дате (карточку можно продолжать редактировать по id) |
| Даты в прошлом | выбор молча искажается в открытую неделю | честно сохраняются (запрета нет и сегодня на сервере; новый запрет не вводится) |

| Сервер, api-client, разметка и якоря формы | — | без изменений |

Для пользователя: календарь в редактировании начинает значить то, что показывает — выбранная дата и есть дата занятия; пропадает молчаливое искажение выбора чужой недели.

## Тесты

- **Юнит** (`frontend/admin/__tests__/`): контекст расписания — при `start` в обновлении `payload.start` уходит как есть (конвертация от открытой недели не вызывается); при `dayIndex + startMinutes` — прежняя конвертация (существующие тесты конвертации зелёные без правки ожиданий); оба набора сразу — побеждает `start` (документирующий приоритет ассерт); вкладка редактирования — поле даты-времени отправляет `start`, а не `dayIndex + startMinutes`; пустое значение поля — патч не отправляется; тост при патче даты-времени показывается, на остальных полях — нет.
- **E2E** (`frontend/admin/e2e/`): `activity-details-modal.spec.ts` — US-1 (перенос на 2026-06-09, модалка остаётся открытой, навигация неделями, тост), US-2, US-3, US-5; `schedule.spec.ts` §5 — US-4 без правки ожиданий. Паттерны: фиксированная сид-неделя (`SEED_WEEK_MONDAY = 2026-06-01`), закреплённый часовой пояс, программная установка значения `datetime-local` (`input-datetime`) — все уже используются этим файлом.
- **Визуальная регрессия**: не затрагивается (разметка формы не меняется).

## Риски

- **Двойная семантика в union обновления** (`start` | `dayIndex + startMinutes`) — задокументирована в типе и приоритетом в `updateActivityFn`; прецедент уже живёт в `addActivity` после #280. Защита от смешения: отправители строго разделены (форма — только `start`, сетка — только `dayIndex + startMinutes`).
- **«Исчезновение» занятия из открытой недели** после переноса — ожидаемое поведение, смягчено тостом с выбранной датой (тот же приём, что зафиксирован в спеке #280 для создания). Модалка остаётся открытой на собственном снимке занятия — правки «исчезнувшей» карточки продолжают применяться по id (решение гейта B, ревизия 2).
- **Кэш-транзиент**: оптимистическая запись патча попадает в кэш открытой недели и покидает его только по рефетчу после инвалидации — исчезновение карточки не мгновенное (секунды); e2e ждёт рефетча (см. US-1), не только тоста.
- **e2e-дата вне сид-недели** — перенос всегда на фиксированную дату сида (2026-06-09), расширения сида и новых фикстур не требуется.
