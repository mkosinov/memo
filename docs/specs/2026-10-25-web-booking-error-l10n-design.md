# Спека: локализация ошибок бронирования в web по кодам (booking-error)

- Issue: #538
- Дата: 2026-10-25. Ревизия: **рев.2 (2026-11-24)** — актуализация после влива задачи
  #551 (вместимость) и решения Gate B (вариант А, ОК владельца 2026-11-24).
- Статус: согласована (Gate B пройден).
- Связанное: #634 «свободные места и вместимость в карточке занятия» — превентивная
  задача (milestone v1), в скоуп этой спеки НЕ входит.

## Контекст

Клиентский сайт (frontend/web) после среза «вход + форма бронирования» (#499, PR #523)
показывает ошибки создания записи так: хук `useCreateMyRecord` прогоняет ошибку API
через `structuredServerMessage` (frontend/web/app/lib/errors.ts), а тот при наличии
в ответе структурного кода (`detail.code`) возвращает серверный текст `detail.message`
как есть.

Спека рев.1 писалась под факт «два английских рейз-сайта доезжают до клиента». Пока
спека ждала Gate B, задача #551 (вместимость занятий 0–99, влита 2026-11-21) сменила
текст первого из них: страж вместимости теперь кладёт в `message` русский текст из
серверного словаря — `ERROR_MESSAGES[ACTIVITY_AT_CAPACITY]` = «Недостаточно мест»,
без чисел. В коде оставлен комментарий с мотивацией: web показывает серверный текст
напрямую, поэтому текст стража — пользовательский; статус 409 и код не менялись.
Состояние на сегодня (проверено по живому коду 2026-11-24):

- 409 `ACTIVITY_AT_CAPACITY` — сервер отдаёт русский текст «Недостаточно мест»
  (backend/src/domain/record_visits.py, следствие #551); web уже показывает его как
  есть. Английской утечки здесь больше нет, и числа N/M в сообщении больше не
  приезжают.
- 404 `ACTIVITY_NOT_FOUND` — по-прежнему английский «Activity not found»
  (backend/src/usecases/my_booking.py) — единственная оставшаяся утечка.

Прочие коды, достижимые в этом флоу (`TARIFF_REQUIRED`, `TARIFF_NOT_FOUND`,
`AUTH_*`), сервер уже отдаёт русским текстом.

В admin-приложении существует устоявшийся паттерн: словарь код → русский текст
(`CODE_DEFAULTS` в frontend/admin/app/lib/api/parseApiError.ts). Ветка извлечения
чисел N/M из английского сообщения сервера (регулярка `/(\d+)\/(\d+)/`) после #551
стала мёртвой — чисел в сообщении больше нет, admin показывает базовый текст
«Недостаточно мест». Это принятый побочный эффект #551, в скоуп этой спеки он не
входит (возврат чисел — возможная будущая задача через структурные поля).

Отдельный факт для полноты картины: на бэкенде уже есть свой словарь русских
текстов по кодам (`ERROR_MESSAGES`, backend/src/errors.py) — теперь он живой
источник текста «мест нет» (см. выше), а для `ACTIVITY_NOT_FOUND` держит
системную формулировку «Активность не найдена», которую web не показывает
(перехватывает своим словарём, см. Решение).

## Отвергнутые альтернативы

### 1. Чинить 404 на сервере (следовать прецеденту #551)

После #551 сильнейший исходный аргумент против серверной правки (регулярка admin
зависит от английского формата) для 404 неприменим: admin перекрывает тексты по
коду своим словарём `CODE_DEFAULTS` и смене серверного сообщения не подвержен.
Смена `ERROR_MESSAGES[ACTIVITY_NOT_FOUND]` на «Занятие не найдено» починила бы web
вообще без правок фронтенда — ровно путь прецедента #551 («текст стража
пользовательский, потому что web показывает его напрямую»).

Отвергнуто сознательно (решение Gate B, 2026-11-24): канон «тексты интерфейса
принадлежат приложению-потребителю» — серверный словарь хранит формулировку языка
админ-системы («Активность не найдена»), web несёт свою формулировку языка клиента
сайта («Занятие не найдено»); правка текста сайта тогда не требует релиза бэкенда.
Издержка: для кода 404 живут два параллельных текста (серверный + web), и web-словарь
вообще существует. Цена разворота решения мала: убрать 3 записи web-словаря и
поменять одну строку на сервере.

### 2. Показывать числа в тексте «мест нет» (рев.1: «Недостаточно мест: занято N из M»)

Рев.1 обещала извлекать числа N/M регуляркой из серверного сообщения. После #551
числа в сообщении не приезжают — формулировка с числами недостижима без правки
бэкенда (структурные поля в 409). Отвергнуто решением владельца (вариант А,
2026-11-24): частый случай «перебора» (форма не показывает занятость, счётчик не
ограничен) закрывается превентивной задачей #634 (показ «Свободно N из M» / «Мест
нет» на карточке + ограничение суммы счётчиков свободными местами); остаточные 409 —
редкая гонка, где серверного текста «Недостаточно мест» достаточно.

## Решение

1. В frontend/web/app/lib/errors.ts появляется словарь `CODE_MESSAGES`
   (код → русский текст) на 3 кода:
   - `ACTIVITY_NOT_FOUND` → «Занятие не найдено»;
   - `TARIFF_REQUIRED` → «Выберите тариф для каждого места»;
   - `TARIFF_NOT_FOUND` → «Тариф не найден».
   Записи для `ACTIVITY_AT_CAPACITY` в словаре НЕТ: серверный русский текст
   «Недостаточно мест» доезжает до клиента через существующий pass-through без
   правок (вариант А).
2. `structuredServerMessage(err, fallback)` получает один промежуточный шаг ПЕРЕД
   текущей логикой: если у ошибки есть код и код найден в словаре — вернуть текст
   словаря. Дальше логика без изменений: код есть, но не в словаре → серверский
   `message`; кода/структуры нет → общий `fallback`, переданный вызывающим кодом.
3. Никакого извлечения чисел и никаких регулярок в web нет (рев.1-шаг упразднён
   вместе с числами в сообщении; буквальное зеркалирование admin-регулярки больше
   не имеет объекта).

### Границы (что сознательно НЕ делаем)

- НЕ трогаем бэкенд: оба рейз-сайта (409 и 404) остаются как есть; API-контракт
  не меняется, словарь web — презентационный слой клиента.
- НЕ трогаем admin: его словарь `CODE_DEFAULTS` отдельный и остаётся источником
  для своих мест использования; его мёртвая ветка извлечения чисел — принятый
  побочный эффект #551, здесь не реанимируется и не удаляется.
- НЕ включаем в web-словарь коды входа/OTP (`AUTH_*`, `PHONE_INVALID`,
  `NOTIFY_TRANSPORT_UNAVAILABLE`): их серверные тексты уже русские, формулировки
  сервера остаются для них источником; поведение экрана входа не меняется вовсе.
  Словарь web сознательно не копирует admin-тексты этих кодов — admin пишет про
  парольный вход администратора, web — про вход клиента по одноразовому коду,
  тексты обязаны отличаться.
- НЕ строим параметризованный механизм сообщений (коды с плейсхолдерами и т.п.):
  после #551 параметризованных сообщений в этом флоу нет вообще.
- НЕ показываем числа мест в ошибке 409 и НЕ трогаем показ занятости в карточке/форме
  — это скоуп #634 (milestone v1).

### Достижимые коды вне словаря — проверено и принято

- **Анти-спам-гейт брони** (первая проверка при создании записи: 20 записей /
  40 визитов на аккаунт за 15 минут) отвечает 429 `AUTH_LOCKED_OUT` с русским
  текстом «Слишком много неудачных попыток входа, попробуйте позже» — текст о
  входе, но событие редкое, по сути верное («слишком много попыток, позже»), код
  общий с экраном входа, словарь по коду поверхности не различает. Принято как
  есть, без отдельного текста для формы брони.
- **`PHONE_INVALID`** (422, в сообщение сервер кладёт сам введённый телефон)
  недостижим из формы: клиентская валидация телефона (libphonenumber-js,
  «RU») блокирует отправку невалидного номера. В словарь не входит.
- Прочие ошибки унаследованного сценария создания записи — только 404/409,
  обработанные выше; других английских текстов в этом флоу нет.

## User Scenarios

1. **US-1. Мест нет.** Клиент отправляет бронь на занятие, где все места заняты
   (сервер: 409 `ACTIVITY_AT_CAPACITY`) → в блоке ошибки видит русский текст
   «Недостаточно мест» — серверный текст как есть, без чисел. Поведение web с
   21.11.2026 (#551) уже такое; сценарий остаётся регрессионной булавкой против
   возврата английского серверного текста. Проверка: E2E (в сиде есть занятия с
   capacity=1 — «Индивидуальный МК» и другие; тест бронирует единственное место,
   повторная отправка даёт 409 и русский текст без английского).
2. **US-2. Занятие исчезло.** Клиент отправляет бронь на занятие, которое уже
   удалено (сервер: 404 `ACTIVITY_NOT_FOUND`) → видит «Занятие не найдено».
   Единственное реальное изменение поведения в этой задаче. Проверка: E2E
   (между открытием формы и отправкой тест удаляет занятие прямой записью в
   тестовую БД — фикстура `sqlite-exec` из web-e2e).
3. **US-3. Коды тарифов — страховка контракта.** Коды `TARIFF_REQUIRED` /
   `TARIFF_NOT_FOUND` (422) включены в словарь текстами, совпадающими с
   сегодняшними серверными. Через форму они недостижимы (посылка строится из
   счётчиков тарифов: для платной услуги tariff_id присутствует по построению,
   для бесплатной null принимается) — достижимы только гонкой устаревших
   данных, поэтому поведение экрана не меняется вовсе, а записи словаря
   фиксируют текст на случай будущих изменений сервера.
   Проверка: юнит-уровень (словарь маппинг + компонентный тест с реалистичной
   `ApiError`); E2E не пишем — сценарий требует гонки, флейко по построению.
4. **US-4. Незнакомый код.** Сервер вернул структурную ошибку с кодом, которого
   нет в словаре (будущий код) → показан серверский текст сообщения, как сегодня.
   Проверка: юнит-уровень (`structuredServerMessage`); E2E невозможен без мока
   сервера, противоречащего канону прогонов против реального API.
5. **US-5. Вход не изменился.** Ошибки экрана входа по одноразовому коду
   (неверный код, блокировка, 503) показываются прежними текстами — их коды в
   словарь не входят, поведение `structuredServerMessage` для них идентично
   текущему. Проверка: юнит-уровень хелпера + существующие тесты экрана входа
   без правок ожиданий.

## Behavioral Delta

- До: при 404 (занятие удалено) клиент видит «Activity not found».
- После: при 404 — «Занятие не найдено».
- При 409 (мест нет) — «Недостаточно мест» — не меняется этой задачей: русский
  серверный текст доезжает как есть с 21.11.2026 (#551); числа мест в ошибке не
  показываются (социум — #634).
- Остальные тексты ошибок бронирования и все тексты экрана входа не меняются.

## Тестовая стратегия

- Юнит (frontend/web/app/lib/__tests__/errors.test.ts, расширение): код в словаре
  → текст словаря (404 и оба тарифных); код capacity → серверский `message` как
  есть, включая русский «Недостаточно мест», без попыток извлечь числа; код вне
  словаря → серверский message; без кода → fallback. Существующий тест с моком
  (код capacity, русский message) остаётся зелёным без правок: он теперь попадает
  в pass-through-ветку (записи capacity в словаре нет), ожидаемый текст тот же.
- Компонентный (BookingOverlay): монтаж с реалистичной ошибкой
  `ApiError(404, "Activity not found", "ACTIVITY_NOT_FOUND")` → в `booking-error`
  текст «Занятие не найдено» (фиксирует настоящую утечку — сегодня моки подставляют
  русский текст и пропускают её); второй случай — `ApiError(409, "Недостаточно
  мест", "ACTIVITY_AT_CAPACITY")` → текст как есть.
- E2E (web-e2e, инфраструктура существует: собственный playwright-конфиг,
  globalSetup с реальным OTP-входом сида-клиента, фикстуры доступа к тестовой
  БД): US-1 (capacity=1 из сида: первая бронь занимает место, вторая отправка →
  409 и русский текст «Недостаточно мест», английского нет), US-2 (удаление
  занятия через `sqlite-exec` между открытием формы и отправкой → «Занятие не
  найдено», английского нет).

## Visual Compliance Checks

Машинная проверка раннера — одна, на статически достижимом элементе (точка входа
в сценарии). Блок ошибки формы бронирования и ошибки экрана входа живут внутри
интерактивных флоу (открытие оверлея брони, ввод кода) и статическому раннеру
недостижимы — покрыты web-e2e US-1/US-2/US-5 (ассертят тот же
`data-testid="booking-error"` / текст) и ручной проверкой:

- [ ] карточка занятия "Индивидуальный МК" на странице расписания — рендерится при
  загрузке страницы, по клику открывает форму бронирования (вход в сценарии
  US-1/US-2) url="/"
- [ ] блок ошибки формы бронирования — при 409 «мест нет» показывает русский текст
  «Недостаточно мест» и не содержит английского "seats occupied" — web-e2e US-1
- [ ] блок ошибки формы бронирования — при удалённом занятии показывает
  «Занятие не найдено» и не содержит "Activity not found" — web-e2e US-2
- [ ] экран входа по одноразовому коду — при неверном коде показывает прежний
  русский текст «Неверный код подтверждения или истёк срок действия» — web-e2e US-5
