# Сервис доменных событий (DomainEventsService) — архитектурная спека (#580)

Рев.2 (панель 7 ревьюеров внесена, 2026-11-08 — хостовый прогон: бесплатный тир провайдера лежал). Семья #476; выносит журнал доменных событий из подсистемы оповещений в самостоятельный сервис. Решение и развилки — диалог с пользователем 2026-11-08, гейт A: концепт 1 (чистая выноска, переименование notify → notification — отдельная волна #581, после #580 и до IMPL #486).

## 1. Контекст и цель

Журнал `domain_events` сегодня принадлежит пакету `src/notify`: модель `DomainEvent` лежит в его моделях, отметка `processed_at` на строке события — однопотребительская (её ставит диспетчер оповещений, закрывая событие для всех остальных потребителей), цикл поллинга журнала — первый цикл диспетчера (части 1–4 семьи #476 влиты: #482, #483, #484, #485). Продюсерская сторона при этом универсальна: аккумулятор `mark_domain_event` + вставка в `@transactional` не импортируют модели оповещений.

Цель — `DomainEventsService` (`src/domain_events`): журнал остаётся источником истины, ретранслятор публикует события в Redis Streams по одному стриму на тип, внешние сервисы подписываются группами потребителей. Notification — первый подписчик; его диспетчерский цикл чтения журнала заменяется чтением группы. Поведение для конечных пользователей (клиентов, мастеров, администраторов) не меняется.

Разведка (3 скаута, 2026-11-08, вердикт actual): связность мала — вне пакета журнал держат 3 точки (регистрация моделей, транзакционная обвязка, продюсер записей); транспорт стримов извлекается из `redis_queue.py` в общий хелпер; каркас процесса (`run_loop` + сигналы) уже вынесен в `process.py`.

## 2. Принятые решения

1. **Механизм — стрим + группа потребителей** (ADR 013 — та же механика, что `notify:tasks`/`notify:statuses`/`notify:inbound`). Pub/Sub не подходит: без сохранения, отвалившийся подписчик теряет сообщения.
2. **Журнал в SQLite остаётся источником истины** (transactional outbox): событие коммитится в той же транзакции, что и запись домена. Прямая запись в Redis из транзакции запрещена — двойная запись без атомарности.
3. **Ретранслятор — отдельный процесс**, единственный читатель хвоста журнала; публикует в стрим типа. Поллинг не исчезает — сворачивается в одну точку.
4. **Один стрим на тип события**: `domain_events:<тип>`. Подписка сервиса = группа потребителей на стримах нужных типов; разные сервисы — разные группы, каждая получает всё независимо.
5. **События «жирные»** — со замороженным снимком (контракт §4.1 семейной спеки #476 сохраняется): подписчик читает из БД только предикаты, данные сообщения — из снимка.
6. **`processed_at` на строке события умирает.** Журнал — чистые данные. Защита от дублей — у подписчика: у notification **вводится** частичный уникальный индекс корней цепочек `UNIQUE(event_id, scenario) WHERE parent_task_id IS NULL` (рев.2, находка панели: сегодня уникальность «событие × сценарий» достигалась отметкой `processed_at` в транзакции сценария — индекса в схеме никогда не было; голый индекс по всей таблице ломал бы цепочки каналов ADR 014 — продолжение наследует пару корня). Зеркало подтверждений (XACK) в БД не делается: результат обработки материализуется строками задач подписчика.
7. **Гарантия «как минимум один раз»** сквозная; дубли поглощаются идемпотентностью подписчика.
8. **Реестр типов в коде**, не в БД: тип декларируется константой, стрим-ключ выводится из типа. Неизвестный тип в `mark_domain_event` — ошибка на марке (fail fast, в транзакции).
9. **Переименование notify → notification — вне задачи** (#581). Новый модуль рождается с чистыми именами (`src/domain_events`, `domain_events:*`, `DOMAIN_EVENTS_*`); пакет оповещений остаётся на старом имени до #581.

## 3. Архитектура

### 3.1 Модуль `src/domain_events`

Состав:

- `models.py` — `DomainEvent` (переезд из `src/notify/models.py`, таблица `domain_events` не переименовывается — миграция не трогает имя таблицы);
- `journal.py` — аккумулятор продюсера (переезд из `src/notify/journal.py` полной поверхностью: `open_journal` / `reset_journal` / `draw_events` / `pending_events` / `mark_domain_event` — блок `finally` обвязки зовёт `reset_journal`, потерять нельзя) + валидация типа по реестру;
- `types.py` — реестр типов (§3.2);
- `relay.py` — процесс ретранслятора (§3.3, вход `python -m src.domain_events.relay`);
- `subscribe.py` — публичный API подписки (§3.4): хелпер потребителя группы поверх общего транспорта.

Транзакционная обвязка (`src/services/decorators.py`) меняет ленивый импорт `src.notify.journal` → `src.domain_events.journal`; вставка строк `DomainEvent` перед коммитом — без изменений логики. Регистрация моделей (`src/models/__init__.py` и `alembic/env.py`) переключает импорт `DomainEvent` на новый пакет. Продюсер записей (`src/usecases/records.py`) меняет импорт марки; сборщик снимка `new_record` (`build_new_record_snapshot`) переезжает из `src/notify/snapshots.py` к продюсеру — продюсер не импортирует пакет оповещений (сборка снимка — продюсерская обязанность по семейскому §4.1).

### 3.2 Реестр типов

```python
@dataclass(frozen=True)
class EventType:
    code: str          # "new_record"
    description: str   # человекочитаемое, для логов/админки

def register_type(code: str, description: str) -> None: ...
def stream_key(code: str) -> str:      # f"domain_events:{code}"
def require_type(code: str) -> None    # ValueError на незарегистрированный
```

- Типы задаются декларативным словарём в `types.py` (рев.2: без импорт-побочных саморегистраций — поведение не зависит от графа импортов, тесты потребителя без импорта продюсера видят те же типы). Пилот: один — `new_record`.
- `mark_domain_event` валидирует тип через `require_type` на марке: неизвестный тип — `ValueError` внутри транзакции → откат доменного изменения вместе с событием. Цена ошибки программирования — немедленный сбой, а не тишина в журнале. Недостижимость сбоя на публичном маршруте фиксируется тестом полноты реестра (тип пилота зарегистрирован). Старый тест «unknown type logged and stays pending» (поллинг диспетчера) заменяется негативной веткой марки.

### 3.3 Ретранслятор

Отдельный процесс, вход `python -m src.domain_events.relay`. Переиспользует:

- `run_loop` + `install_signal_handlers` — переезд `src/notify/process.py` в нейтральный `src/util/process.py` (notify переключается на него импортом);
- конструкцию движка БД по образцу диспетчера (`DBManager`, прагмы busy_timeout/WAL наследуются);
- `asyncio.to_thread` для каждого вызова Redis;
- общий транспорт стримов (§3.6).

Цикл (одна итерация):

1. Прочитать батч журнала: `published_at IS NULL ORDER BY occurred_at, id` — `POLL_BATCH_SIZE = 20`; курсор по состоянию строк (прецедент — прежний цикл диспетчера, «no id > last»).
2. Для каждой записи — `XADD` в стрим её типа (§4.1), через `to_thread`.
3. Батч целиком опубликован → одним коммитом проставить `published_at = utc_now()` каждой строке. Транспортный сбой на шаге 2 → батч не помечается, повтор на следующем тике; попыток/ошибок на строке не храним — транспортный сбой глобален, не пособытиен. Пособытийный НЕ-транспортный сбой (неисправимый payload — баг кода) выделяется отдельно: строка помечается опубликованной с ошибкой в логе (одна битая строка не стопорит хвост навечно; журнал хранит данные, `--republish-since` повторит после исправления).
4. Каждый тик логирует глубину неопубликованного хвоста (row count) — отставание видно оператору до того, как оно станет потерей (рев.2, панель).

Падение между XADD и отметкой → повторная публикация дубля при рестарте — принято (§4.3). Флаг `--republish-since <ISO>`: напечатать число попавших строк (dry-run), затем переиздать окнами ≤ MAXLEN с пометкой `published_at` между окнами (рев.2: одним потоком переиздание обрезало бы собственную голову) — процедура восстановления после потери Redis (§4.5), идемпотентность подписчиков поглощает дубли.

### 3.4 Подписка

Подписка внешнего сервиса = группа потребителей на стриме типа. Обеспечение группы (`XGROUP CREATE id=0 MKSTREAM` — читать с начала) — на старте подписчика. Публичный API — `src/domain_events/subscribe.py`:

```python
class Subscriber:
    def __init__(self, redis_url, group: str): ...          # группа = имя сервиса
    def ensure(self, streams: list[str]) -> None: ...        # XGROUP на каждом стриме (имена валидируются по реестру типов)
    def claim(self, streams, count) -> list[ClaimedEvent]    # XREADGROUP > неблокирующе
    def ack(self, stream, qid) -> None                       # XACK
    def reclaim(self, streams, min_idle_ms) -> list[...]     # XAUTOCLAIM — возврат зависших
    def close(self) -> None                                  # keep_if_pending: потребитель с непустым PEL не снимается
```

`ClaimedEvent` — распарсенная запись стрима (§4.1). Правила подписки (рев.2, панель):

- **Идемпотентность обязательна** (§4.3) — включая переигровку истории: поздний подписчик (группа создана недели спустя) получает удержанную обрезкой историю стрима; старше обрезки — только восстановлением из журнала.
- **Имя группы глобально уникально**: группа = подписчик; два сервиса в одной группе делят записи между собой (каждая запись уходит одному) — тихая потеря для обоих. Именование — часть публичного контракта.
- **`close` держит потребителя с непустым PEL**: `XGROUP DELCONSUMER` уничтожает учёт выдачи — неподтверждённые на остановке записи должны пережить рестарт (прецедент — close воркера, `keep_if_pending`).
- Возврат зависших — на старте процесса подписчика **и периодическим циклом** (интервал — константа модуля; уведомлениям — четвёртый цикл диспетчера, рев.2: прецедент `reclaim_hanging` стартовый, без периодического цикла повторы сценария случались бы только при рестарте процесса).

### 3.5 Notification — первый подписчик

Диспетчер оповещений теряет цикл поллинга журнала; вместо него — цикл чтения группы:

- группа `notification` на стриме `domain_events:new_record`; обеспечение группы на старте; claim батчем → сценарий → ack; четвёртый цикл — периодический возврат зависших (§3.4);
- обработчик сценария `handle_new_record` не меняется по логике решения (предикаты — живые чтения по идентификаторам из снимка; снимок — единственный источник данных текста), меняется источник входа и три шва:
  - идемпотентность: проверка `event.processed_at` уходит (колонки нет); **вводится** частичный уникальный индекс `uq_notify_tasks_event_scenario_root (event_id, scenario) WHERE parent_task_id IS NULL` (корни цепочек и skipped; продолжение цепочки наследует пару корня и индексом не накрывается) — повторная выдача события ловится существованием корня (IntegrityError → «уже обработано» → ack); сегодня такой индекс отсутствует — миграция §4.2 добавляет (рев.2, панель);
  - гроссбух попыток сценария (замена колонок `attempts`/`processing_error` события): новая таблица `notify_event_attempts(event_id, scenario, attempts, last_error)`, `UNIQUE(event_id, scenario)`. Ошибка сценария: инкремент попытки; при `attempts < 3` запись не подтверждается (периодический возврат зависших повторит), при 3 и выше — подтверждение с парковкой (повторная выдача паркованного события перейпаркуется без ретраев — гроссбух уже на пороге). Порог `MAX_SCENARIO_ATTEMPTS = 3` — константа модуля;
  - **транспортное исключение попыток не сжигает** (наследие #483 «три мёртвых тика Redis не убивают событие», рев.2): `StreamTransportError` в точке постановки в очередь — без инкремента гроссбуха, запись остаётся неподтверждённой (возврат PEL повторит), закоммиченная задача добирается циклом перезаливки;
- циклы статусов и входящих (`notify:statuses`, `notify:inbound`), перезаливка, цепочки каналов — без изменений;
- воркер доставки — без изменений (ADR 009: без БД).

### 3.6 Общий транспорт стримов

Из `src/notify/redis_queue.py` в нейтральный `src/streams/transport.py` извлекаются общие механики (по разведке — конструктор уже параметризован url/префиксом/потребителем):

- конструкция пула (ретраи выключены, socket timeout), `connect_or_exit` (fail-fast, код 2);
- нормизация сбоев: `NotifyTransportError` → общий `StreamTransportError` (в notify остаётся псевдоним для совместимости тестов);
- `_publish` (XADD c MAXLEN_APPROX), `_claim` (XREADGROUP > неблокирующе + конверт `_qid`), `_ack`, `_ensure_group` (id=0 MKSTREAM, BUSYGROUP подавлен), **сырой XAUTOCLAIM** (передача PEL), `_is_missing_group` (NOGROUP-восстановление), `ping`/`close` (правило keep_if_pending — §3.4).

Общее ядро отдаёт сырой XAUTOCLAIM; обёртка «повторный XADD + ack» остаётся на `RedisQueue` (семантика свежей доставки для очереди задач; для доменных событий повторный XADD на каждом возврате churn-ило бы стрим ретранслятора — рев.2, панель). `RedisQueue` (notify) сохраняет свой API (методы-глаголы notify), делегируя общему ядру. Ретранслятор использует подмножество публикации; `Subscriber` (§3.4) — подмножество потребления. Обрезка стримов доменных событий: `MAXLEN_APPROX = 10_000` (журнал — архив; последствие и процедура — §4.5, §8). `run_loop` переезжает в `src/util/process.py` с параметризованным префиксом лога (сегодня зашит «notify dispatcher»).

## 4. Контракты

### 4.1 Запись стрима

Стрим `domain_events:<тип>`; одна запись = одно событие. Поля:

```json
{"event_id": "<uuid>", "type": "new_record", "occurred_at": "<ISO naive UTC>",
 "snapshot": {…замороженный снимок §4.1 семейной спеки…}}
```

Событие самодостаточно: подписчику не нужно читать `domain_events` для содержания — только для предикатов, если этого требует его сценарий. Снимок обязателен: марка зарегистрированного типа без снимка — та же `ValueError` валидации (NULL-снимок в стрим не публикуется, рев.2).

### 4.2 Модель `domain_events` (после)

Было: `type, occurred_at, snapshot, processed_at, attempts, processing_error` + частичный индекс `ix_domain_events_pending WHERE processed_at IS NULL AND processing_error IS NULL`.

Стало: `type, occurred_at, snapshot, published_at` + частичный индекс `ix_domain_events_unpublished WHERE published_at IS NULL`. `AbstractModel` (id UUID, created_at/updated_at) — без изменений. Миграция:

- добавить `published_at`; бэкфилл `published_at = <момент миграции>` для строк с `processed_at IS NOT NULL` **и** для строк с `processing_error IS NOT NULL` (рев.2, панель: припаркованные старым конвейером события считаются потреблёнными — переиздание мёртвых событий с свежим циклом попыток и возможными задним числом уведомлениями не делаем);
- снять `processed_at`, `attempts`, `processing_error`; заменить индекс;
- у подписчика: новая таблица `notify_event_attempts(event_id, scenario, attempts, last_error)` и **частичный уникальный индекс** `uq_notify_tasks_event_scenario_root (event_id, scenario) WHERE parent_task_id IS NULL` — с предварительной проверкой существующих дублей корней (сегодня их быть не может: `processed_at`-guard работал; проверка — страховка миграции).

### 4.3 Гарантии и идемпотентность

- Продюсер → журнал: атомарно (та же транзакция) — без изменений.
- Журнал → стрим: как минимум один раз (дубль при падении между XADD и отметкой). Порядок внутри типа — best-effort `(occurred_at, id)` одним ретранслятором, но дубли при переиздании и окна восстановления приходят вне порядка (рев.2, панель): подписчики не имеют права опираться на порядок стрима — детерминизм строится по данным события, не по порядку доставки. Между типами порядок не гарантируется.
- Стрим → подписчик: как минимум один раз (PEL + XAUTOCLAIM). Подтверждение — после материализации результата (у notification — после коммита задачи/пропуска/парковки); парковка (3 неудачи) тоже подтверждается — возврат зависших не должен бесконечно тянуть припаркованное.
- Дедупликация — на подписчике: `UNIQUE(event_id, scenario)`. Уведомления уже соответствуют (семейная §4.4); новые подписчики обязаны проектировать идемпотентность с первого дня — это часть публичного контракта подписки.

### 4.4 Настройки

- `DOMAIN_EVENTS_ENABLED: bool = False` — гейт процесса (зеркало `NOTIFY_ENABLED`);
- `DOMAIN_EVENTS_POLL_INTERVAL: float = 1.0` — тик ретранслятора;
- `REDIS_URL` — общий, без изменений. Батчи/пороги — константы модулей (не настройки), по прецеденту notify.

### 4.5 Порядок переключения (миграция и эксплуатация)

Развёртывание: остановить диспетчер (старый цикл поллинга) → прогнать миграцию (§4.2) → запустить ретранслятор и новый диспетчер. `dev.sh` получает ребёнка `relay` рядом с диспетчером/воркером (под флагом `--notify`, как остальные). Окно переключения: события, зафиксированные после остановки и до старта ретранслятора, не теряются — они не опубликованы и будут опубликованы при старте (курсор по состоянию строк).

Потеря Redis (стёртые стримы/группы): пересоздание групп на старте подписчиков (NOGROUP уже обрабатывается транспортом); события, чья раздача потеряна, восстанавливаются прогоном `python -m src.domain_events.relay --republish-since <ISO>` от точки потери (dry-run счёт строк → окна ≤ MAXLEN, §3.3) — дубли поглощаются идемпотентностью. Аналогично обрезка MAXLEN при долгом простое подписчика: записи за пределами backlog недоступны из стрима — тот же прогон от нужной точки (журнал — архив, источник повтора). Процедура — §8 рисков, фиксируется в domain-rules.

## 5. User Scenarios

Сервис внутренний; «пользователи» — сервисы-продюсеры, сервисы-подписчики, оператор. Каждый сценарий закрыт тестом (бэкенд-интеграционные, контур CI `notify-tests` расширяется; веб-e2e неприменимо — фронт не меняется).

1. **Продюсер помечает событие** — сценарий записи фиксирует `new_record` в своей транзакции; событие в журнале; ретранслятор публикует его в `domain_events:new_record`; порядок и батч: 2–3 события одного типа вставляются в обратном `(occurred_at, id)` порядке — порядок прибытия в стрим строго `(occurred_at, id)`, потолок батча 20 (рев.2: преемственность теста `test_poll_respects_batch_size_and_occurred_at_order`, данные различают порядок). Тест: `test_domain_events_redis_publish`.
2. **Notification получает событие через группу** — claim → решение (успех/пропуск с причиной) → задача → ack; вход диспетчера переключён со чтения журнала на группу. Тест: адаптация `test_notify_scenarios`/`test_notify_dispatcher` на вход через группу (судьбы старых тестов: транзакционные тесты журнала едут вместе с модулем; тесты поллинг-цикла удаляются с заменой; тест частичного индекса переписывается под новый предикат).
3. **Ретранслятор упал между фиксацией и публикацией** — рестарт допубликовывает непомеченное; дубль (упал между XADD и отметкой) не создаёт вторую задачу; ассерт фиксирует ДВЕ записи в стриме (дубль реально доставлен — тест не проходит вакуумно, рев.2) и одну задачу-корень. Тест: `test_domain_events_relay_restart`.
4. **Сценарий подписчика падает** — ошибка растит гроссбух попыток; запись не подтверждается; периодический возврат зависших повторяет (ассерт на цикл, не на ручной вызов, рев.2); после 3 неудач — подтверждение с парковкой; ассерт: PEL пуст для события после парковки (возврат с `min_idle_ms=0` ничего не возвращает). Транспортная ошибка попыток не сжигает — отдельная ветка того же теста. Тест: `test_notify_scenario_attempts_ledger`.
5. **Redis стёрт** — группы пересоздаются на старте; прогон `--republish-since` восстанавливает раздачу (dry-run счёт, окна); дубль поглощён; событие СТАРШЕ точки не переиздаётся (рев.2: граничное условие `>=`). Тест: `test_domain_events_wipe_recovery` (по образцу `test_notify_redis_s8_recovery`).
6. **Второй тип/второй подписчик** — реестр принимает новый тип; стрим создаётся; вторая группа получает свои события независимо от первой; негативная ветка: незарегистрированный тип → `ValueError`, доменная строка и событие откатились вместе (рев.2). Тест: `test_domain_events_registry_multi`.
7. **Миграция переключения** — бэкфилл: `processed_at IS NOT NULL` → `published_at` проставлен и не переиздаётся; `processing_error IS NOT NULL` → тоже потреблён; непотреблённые остались NULL и публикуются после переключения; корни задач без дублей после индекса. Тест: `test_domain_events_migration` (стиль `test_notify_migration`, рев.2).

## 6. Behavioral Delta

- **Клиент/мастер/администратор (веб):** без изменений — фронт, API, тексты и ход доставок не меняются.
- **Оператор:** появляется процесс `python -m src.domain_events.relay` в `dev.sh` и деплое (гейт `DOMAIN_EVENTS_ENABLED`); повтор ошибок сценария замедляется — периодический возврат зависших PEL (порог простоя ~120 с) вместо поллинга каждую секунду: 3 попытки укладываются в минуты, а не секунды; деплой требует порядка «стоп диспетчера → миграция → старт ретранслятора и диспетчера»; события, припаркованные ошибкой старым конвейером, после переключения не переигрываются (считаются потреблёнными, рев.2).
- **Разработчик:** новый публичный контракт `src/domain_events` (реестр типов, `mark_domain_event`, `Subscriber`); диспетчер уведомлений читает группу, а не журнал; columns `processed_at`/`attempts`/`processing_error` события удалены — состояние потребления живёт у потребителя.

## 7. Границы (не строим в #580)

- Переименование notify → notification — #581 (после #580, до IMPL #486).
- `src/events` (инвалидация кэша SSE, аудит) не трогаем и не объединяем: у кэша другой транспортный контракт (мгновенный in-memory fanout), у аудита — свои правила (актёр, маскирование). Три аккумулятора (`mark_changed`, `mark_audit`, `mark_domain_event`) механически похожи — унификация не является целью.
- Реестр типов — только код, без БД-справочника и без админки типов.
- Точечный повтор одного припаркованного события (сброс строки гроссбуха) — крючок для админки #486, здесь не строим; до неё восстановление — только оконный `--republish-since`.
- Нет dead-letter-стримов (парковка — гроссбух подписчика), нет сквозного порядка между типами, нет автоперепубликации при потере Redis (процедурный `--republish-since`).
- Админка #486 строится после обеих волн, на новом контракте; её локальная спека переписывается (ссылки на журнал/поллинг устаревают).

## 8. Риски реализации

- **Переключение живого конвейера:** диспетчер в проде ходит в журнал; порядок деплоя (§4.5) обязателен, окно переключения непустое безопасно (курсор по состоянию строк). Митигируется: миграция бэкфиллит `published_at` уже-обработанному.
- **Темп повторов ошибок сценария** замедляется (PEL-возврат ~120 с против 1 с). Осознанная плата за увод состояния потребления из БД; деградации нет — ошибки сценария редки (отсутствие шаблона), 3 попытки за ~4 мин достаточны.
- **Обрезка стрима при долгом простое подписчика** (>10 тыс. событий одного типа): записи уходят из стрима, журнал сохраняет всё; восстановление — `--republish-since`. 10 тыс. — запас на порядки больше пилотного темпа.
- **Снимок с персональными данными в стримах (рев.2, панель — безопасность).** Жирное событие несёт имя и телефон клиента и публикуется в Redis ДО предикатов подписчика (согласие на момент публикации не проверено). Сегодня Redis видел только пост-гейтивые payload задач (телефон в адресе — уже там); новый слой — пре-гейтивые копии всех событий, удержание до 10 тыс. Решение: принять — Redis уже внутри границы доверия (доступ по `REDIS_URL`, внутренний транспорт), удержание ограничено, SQLite-журнал содержит то же самое; фиксируется в domain-rules (читатели стримов = сервисы с реквизитами Redis, логирование payload запрещено). Альтернатива — худеть payload до реестро-разрешённых полей — ломает ADR 014 (заморозка снимка) и переводит предикаты на live-чтения: отклонена.
- **Двойная бухгалтерия границ:** после выноски `src/domain_events` не должен импортировать notify; канонический список шва один (рев.2, панель): продюсеру — реестр типов, марка и (для пилота) сборщик снимка; подписчику — `Subscriber` и реестр (имя стрима); notify импортирует `subscribe` и реестр; граница фиксируется тестом импорт-направлений (по прецеденту линта границ).
