# #586 Спека: SMS-транспорт OTP — продовая реализация `OtpTransport` поверх Notificore

> **Решение владельца 2026-11-24:** вход по SMS перенесён из v1 в v1.1 — в v1 клиент подтверждает телефон звонком (#593). Спека действует для v1.1; «Контекст» ниже описывает исходное решение 2026-11-08 и в рев.3 не переписан.

- Дата: 2026-11-10. Статус: DESIGN, рев.3 — панель 7 ревьюеров внесена (рев.2), журнал попыток отправки добавлен по решению владельца на гейте B (рев.3). Гейт A прошёл авто-ОК единственной концепцией.
- Связанное: #587 аккаунт SMS-провайдера (задача владельца: ключ и имя отправителя приходят оттуда); #499 §4.2 — исходный дизайн OTP-шва (`docs/specs/2026-10-20-web-client-auth-booking-design.md`); исследование API — `docs/research/2026-11-10-notificore-sms-api.md` (коммитится вместе со спекой).
- Словарь — пост-переименованный (волна #581 влита): `NOTIFICATION_TRANSPORT_UNAVAILABLE`, пакет `src/notification/`.

## Контекст

Вход web-клиента — одноразовый код (OTP) на телефон. Шов `OtpTransport` (`backend/src/auth/otp_transport.py`, Protocol `send(phone, code)`) сегодня имеет только dev-реализацию: во всех окружениях, кроме `ENV=development`, код не отправляется, эндпоинт `POST /auth/otp/request` честно отвечает 503 `NOTIFICATION_TRANSPORT_UNAVAILABLE` («Вход временно недоступен»). Без транспорта веб-бронирование в проде не работает: сессия клиента выдаётся только после подтверждения телефона.

Решения владельца: OTP доставляется SMS (2026-11-08); провайдер — Notificore (2026-11-10), обычные SMS с общим именем отправителя; смена провайдера в будущем должна быть дешёвой — интерфейс не завязан на Notificore-специфику.

Данные OTP сегодня (`backend/src/auth/otp.py`): строка на телефон (`phone` — PK, новая отправка заменяет строку), сырой код в БД не попадает (HMAC с перцем), TTL кода 5 минут (`OTP_TTL`). Идентификатора попытки в данных нет — см. §Архитектура.

## Границы

Строим:

- продовую реализацию `OtpTransport`: SMS через HTTP API Notificore v1.0;
- провайдер-агностичный слой: транспорт «sms» + тонкий Notificore-клиент за интерфейсом провайдера;
- **журнал попыток SMS-отправки** (дописываемая таблица, одна строка на отправку — конверт без кода; см. §Журнал попыток) — решение владельца на гейте B;
- служебный скрипт разового запроса статуса сообщения у провайдера по `reference` из журнала — инструмент разбора инцидентов «код не пришёл»;
- конфигурацию: ключ и имя отправителя вне git; fail-closed/fail-fast сохраняются;
- маскирование: сырой код и ключ провайдера не логируются и не покидают бекенд (§4.2 #499);
- тесты: контракт провайдера, транспорт, fail-closed/fail-fast, маскирование, журнал, интеграционные сценарии эндпоинтов.

Осознанно НЕ строим в v1:

- непрерывный трекинг статусов доставки (приём вебхуков `callback_url`, фоновый опрос) — формат вебхука не документирован провайдером, потребителя непрерывной картины в v1 нет; статус ДОСТАЁТСЯ разово по требованию (скрипт по `reference` из журнала) — этого хватает разбору инцидентов; `callback_url` не передаём; накопление статусов станет осмысленным при появлении потребителя (админ-экран, аналитика) — журнал попыток уже копит данные для привязки;
- очередь/фоновая отправка — шов `OtpTransport` синхронен по запросу (§4.2 #499), очередь ради ~100 SMS/мес — ре-имплементация механизма `src/notification/` без выгоды; доменное событие об исходе отправки не порождаем: потребителей нет (уведомлениям не нужен, аналитике хватает журнала, аномалии режут гейты лимитов), а исход известен после коммита — это не аутбокс, а лог, и его честная форма — журнал попыток;
- автоматические ретраи отправки — при сбое пользователь видит честный 503 и перезапрашивает код; последствие принятого риска «таймаут ≠ недоставка» описано в §Риски;
- новые лимиты — гейты #499 §4.1 остаются (окно 15 мин: 5 отправок/телефон, 20/IP, 5 разных телефонов/IP, 5 ошибок верификации → 429 `AUTH_LOCKED_OUT`); #493 закрыт и лимитов для OTP не требует; остаточный риск SMS-флуда оценён в §Риски;
- 2FA-продукт Notificore — не используется (требует индивидуальное имя отправителя с абонплатой; решение владельца в исследовании);
- селектор провайдера в конфиге — смена провайдера требует нового класса клиента и деплоя в любом случае; переключение одной переменной окружения ничего не экономит (находка панели: ветка в валидаторе, wiring и матрице тестов без проверяемого потребителя).

## Концепция (гейт A — авто-ОК)

Единственная концепция: **тонкий провайдер-адаптер под существующий шов**. Отсеянные альтернативы:

- «202 всегда, отправка в фоне» — нарушает честный fail-closed §4.2 (пользователь ждёт SMS, которое не придёт) и требует очереди; устранена правилом домена.
- «Реализовать `OtpTransport` методами пакета `src/notification/` (каналы/реестр)» — ре-имплементация чужого механизма: каналы живут в воркере над Redis Streams, OTP-отправка синхронна в пути запроса; шов раздельный by design (§4.2 #499). Переиспользуем только паттерн объектной заглушки канала в тестах.

Требование сменяемости провайдера: вся Notificore-специфика (база URL, заголовок `X-API-KEY`, путь, формат ответа, коды ошибок) сосредоточена в одном классе `NotificoreClient` за интерфейсом `SmsProvider`. Смена провайдера = новый класс клиента + одна строка в wiring; транспорт, шов `OtpTransport` и сценарные тесты не меняются.

## Notificore: факты API (выжимка из исследования; докам провайдера не доверяем — см. §Риски)

- API v1.0: база `https://api.notificore.ru/rest/`, авторизация заголовком `X-API-KEY: live_…|test_…`. Ключ — ЛК «Интеграции и API»; тестовый начинается с `test_`.
- Отправка: `POST …/rest/sms/create` (клиентский путь — `sms/create` относительно базы), JSON-тело. Поля: `destination:"phone"`, `body`, `msisdn` — `7XXXXXXXXXX` (код страны без `+`), `reference` — клиентский идентификатор сообщения ≤32 симв. `[a-zA-Z0-9]`, дедуплицируется провайдером (повтор → error 23), `originator` — имя отправителя ≤11 симв. (без него отказ: error 25), `validity` — срок жизни, сек. `callback_url` не используем.
- Формат ответа нестабилен между поколениями доков: живыми вызовами подтверждена обёртка `{"result":{"error":0,"errorDescription":…,"id":"…","price":…,"currency":"RUB"}}`; часть статей документирует плоскую форму `{"error":"0","id":…}` и коды ошибок строками. Клиент обязан терпеть обе формы и код ошибки строкой или числом (см. §Архитектура).
- Успех = код ошибки 0 + присутствует идентификатор сообщения; всё остальное (HTTP ≠ 2xx, код ошибки ≠ 0, таймаут, сеть, успех без идентификатора) — ошибка отправки.
- Подтверждено живыми вызовами 10.11: тестовый ключ + `originator:"ArtStudio"` → успех, цена RUB, сегментная тарификация.
- Шаблон текста: **«Код для входа в MEMO: {код}»** (~30 символов, 1 сегмент). Имя отправителя общее (чужое), бренд называет текст — требование владельца.

## Архитектура

Слои (новые файлы в `backend/src/auth/`, рядом с `otp_transport.py`):

1. **`SmsProvider`** (Protocol, модуль `sms_provider.py`): `async send(to_msisdn: str, text: str, reference: str) -> str` — возвращает идентификатор сообщения провайдера; любая неудача — исключение `SmsProviderError`.
2. **`NotificoreClient`** — единственный Notificore-знающий класс: база URL, таймаут и путь `sms/create` — его константы (в конфиг не выносятся: пользователей у них нет, тесты идут через инъекцию httpx-транспорта, а не переопределение URL); держит ключ (`SecretStr`), имя отправителя; формирует JSON-тело, заголовок `X-API-KEY`; парсинг терпим к обеим формам ответа и к коду ошибки строкой/числом; идемпотентен к отсутствию `id` при нулевой ошибке (это ошибка отправки); **любая** неудача (HTTP ≠ 2xx, ошибка API, таймаут, сеть, успех без id) → `SmsProviderError`, причину формулирует без тела запроса и заголовков (там код OTP и ключ).
3. **`SmsOtpTransport`** — реализация `OtpTransport`: строит текст по шаблону, конвертирует телефон, генерирует `reference = uuid4().hex` (32 hex-символа — ровно лимит формата провайдера; уникален на каждую отправку — серверный дедуп провайдера никогда не срабатывает и не подавит повторную отправку), делегирует провайдеру. Никакого знания Notificore.
4. **Шов `OtpTransport` не меняется**: сигнатура `send(phone, code)` прежняя; `reference` — внутренность SMS-транспорта, дев-транспорт и юзкейс не затронуты. Панель заблокировала исходный вариант «reference = идентификатор OTP-попытки»: у строки OTP (`phone` — PK) нет идентификатора попытки, а его введение — колонка, миграция и второй изменённый шов (`issue()` возвращает только код) ради потребителя, которого в v1 нет (ретраи и опрос статусов мы не строим).
5. **Wiring** (`get_otp_transport()` в `otp_transport.py`): `OTP_TRANSPORT="dev"` → dev-транспорт (только `ENV=development`, как сегодня); `OTP_TRANSPORT="sms"` → `SmsOtpTransport(NotificoreClient(...))` напрямую, без селектора; `""`/unknown → `None` → 503 (как сегодня).
6. **HTTP-клиент**: httpx (сегодня в бекенде исходящего HTTP нет; httpx — тестовая зависимость, переносим в продовые). На объёме ~100 SMS/мес — `async with httpx.AsyncClient(timeout=…)` на вызов: ноль механизмов жизненного цикла (ни синглтона, ни shutdown-хука, ни проблем с event-loop в тестах), потеря переиспользования соединений на этом объёме несущественна (находка панели: ленивый синглтон без shutdown-хука — задокументированная ловушка).

### Порядок операций в юзкейсе (меняется)

Сегодня (`backend/src/usecases/otp_login.py`): `issue()` пишет строку кода → `transport.send()` → коммит сессии принадлежит вызывающему и происходит только при успехе; сбой отправки откатывает строку, а HTTP-вызов до 5 с идёт внутри открытой транзакции (SQLite — единственный писатель: write-lock на всё время вызова, риск `database is locked` для параллельных писателей).

Новое: **строка кода фиксируется в БД до вызова провайдера** (issue → коммит → send). Что это даёт: HTTP-вызов вне открытой транзакции; строка при сбое отправки не откатывается, а протухает по своему TTL (5 мин) — недоставленный код никому не выдаётся, повторный запрос заменяет строку (PK — телефон); docstring-контракт юзкейса «код не пишется и не считается» верен только для случая «транспорт не сконфигурирован» — обновляется вместе с реализацией.

Счётчики гейтов #499 §4.1: проверка на входе (`otp_send_gate`) не меняется; регистрация (`register_otp_send`, in-memory) переносится на **успешную** отправку — сбой провайдера не расходует лимит телефона (иначе 5 неудачных попыток во время сбоя запирали бы телефон на 429 ещё на 15 минут после восстановления). Семантика лимита становится «5 доставленных кодов на телефон за окно».

### Конвертация телефона

Телефоны хранятся и приходят в шов канонической строкой `+7XXXXXXXXXX` (нормализации в домене нет — `src/domain/phones.py`). Транспорт снимает `+`; результат, не матчащий `7\d{10}`, — ошибка отправки → 503. Никаких догадок о кодах стран: чужой номер не превращается в правдоподобный MSISDN (находка панели).

### Журнал попыток SMS-отправки

Дописываемая таблица `otp_sms_attempts` (домен auth, рядом с `otp_codes`; Alembic-ревизия на создание) — одна строка на отправку, переживает ротацию кодовой строки (PK `otp_codes` — телефон, новая отправка её заменяет). По образцу таблицы попыток уведомлений (`notification_task_attempts`), но без задач/цепочек/воркера — конвейера нет, записывает сам транспорт.

Колонки: `id` (uuid), `phone`, `reference`, `provider_message_id` (nullable — при отказе его нет), `outcome` (`accepted` | `rejected`), `error_code` и `error_text` (nullable, код и текст ошибки провайдера), `created_at`.

Правила:

- пишется после исхода отправки (успех — `accepted` + id провайдера; любая ошибка — `rejected` + код/текст), в том же запросе, отдельной транзакцией;
- **никогда не хранит**: текст сообщения (текст = код), ключ провайдера, тело HTTP-запроса — только конверт;
- ретеншн не настраиваем: ~100 строк/мес, копим.

Разбор инцидента «код не пришёл» (сценарий поддержки): журнал отвечает «приняли ли провайдера, что ответил», статус у оператора — разовым запросом `GET /rest/sms/reference/{reference}` служебным скриптом `backend/scripts/` (по образцу `generate_telegram_session.py`; ключ из окружения, вывод — статус и время). Непрерывный трекинг — см. §Границы.

## Конфигурация

`backend/src/core/config.py` + `backend/.env.example` — 2 новые переменные (минимум ручек; база URL, таймаут, validity — константы клиента):

| Переменная | Значение | Смысл |
|---|---|---|
| `OTP_TRANSPORT` | `""` (дефолт) / `dev` / `sms` | селектор транспорта; пусто = fail-closed 503; `sms` разрешён во всех окружениях, включая development (с `test_`-ключом — локальная проверка проводки) |
| `NOTIFICATION_SMS_API_KEY` | `live_…`/`test_…` | ключ провайдера; `SecretStr` по конвенции секретов репо (`REDIS_URL`, `TELEGRAM_API_HASH`), ключ не отражается в repr/логах/сообщениях валидатора |
| `NOTIFICATION_SMS_ORIGINATOR` | строка ≤11 симв | имя отправителя; значение даёт #587 (общее имя/`ArtStudio`) |

Валидатор настроек (fail-fast, срабатывает при `OTP_TRANSPORT=sms` в любом окружении — поведение определяется собственными правилами, а не «по образцу» `OTP_PEPPER`, который продовый с dev-фолбэком):

- пустой ключ или пустое имя отправителя → ошибка старта (ошибка конфигурации видна сразу, а не 503 на каждом запросе);
- имя отправителя длиннее 11 символов → ошибка старта (иначе проходит старт и ломается на каждом запросе: error 25 Invalid originator);
- `ENV=production` и ключ начинается с `test_` → ошибка старта: тестовый ключ отвечает успехом, не доставляя SMS, — тихий разрыв fail-closed (пользователь застрял бы на «введите код» без ошибки); в staging/development `test_`-ключ разрешён.

Отсутствие транспорта как таковое (`OTP_TRANSPORT=""`/unknown) остаётся мягким fail-closed → 503, как сегодня. Секреты — только окружение; `.env.example` с пустыми значениями и комментарием.

## Поведение при сбоях

| Ситуация | Ответ клиенту | Состояние |
|---|---|---|
| `OTP_TRANSPORT=""`/unknown | 503 `NOTIFICATION_TRANSPORT_UNAVAILABLE` | как сегодня: код не пишется, лимиты не тратятся; журнал попыток не пишется (попытки не было) |
| `sms` с битым конфигом (нет ключа/имени, длинное имя, test-ключ в проде) | приложение не стартует | fail-fast валидатор |
| Notificore: сеть/таймаут/HTTP ≠ 2xx/ошибка API/успех без id | 503 `NOTIFICATION_TRANSPORT_UNAVAILABLE` | строка кода записана и протухает по TTL; лимит телефона не расходуется; в журнале — `rejected` с кодом ошибки; повторный запрос — через действующие гейты |
| Успех | 202, SMS отправлена | регистрация в счётчиках гейтов; в журнале — `accepted` + id провайдера |

Сценарий «ошибка провайдера» не создаёт оракула перечисления: 503 глобален для всех телефонов. Статусы 202/429/503 и тела ответов не меняются — фронт правок не требует.

## Логирование и маскирование

- Логгеры по канону репо `memo.<пакет>.<модуль>`: `memo.auth.sms_provider`, `memo.auth.otp_sms` (существующий `memo.auth.otp_transport` дев-транспорта не мигрирует — шов один, модули разные).
- Логируется: маскированный телефон, `reference`, идентификатор сообщения провайдера, исход и длительность вызова.
- **Никогда** — ни в логах, ни в ответах API (вне development), ни в текстах и цепочках исключений: сырой код OTP и ключ провайдера. Нормализация ошибок клиента не включает тело запроса и заголовки. `test_assert`: US-4.
- `validity` = TTL кода из `OTP_TTL` (300 с): сообщение не живёт дольше кода; верхний кап провайдера неизвестен, но 5 минут — далеко от любых ограничений, отказ провайдера покрыт общим путём 503.

## User Scenarios

- **US-1 «Код приходит по SMS»**: клиент вводит телефон → 202 → SMS «Код для входа в MEMO: {код}» → ввод кода → сессия. Тест: интеграционный `POST /auth/otp/request` со стабом на уровне `SmsProvider` — asserting 202, текст по шаблону, reference-строка не пустая; web-e2e входа на dev-транспорте остаётся зелёным (регресс). Форма HTTP-запроса (заголовок, тело) ассертится только в контракт-тесте клиента — у стаба `SmsProvider` этих фактов нет (дедуп ассертов панели).
- **US-2 «Честный отказ при сбое провайдера»**: провайдер недоступен → клиент видит «Вход временно недоступен» (503). Тест: стаб поднимает ошибку → 503; следом повторный запрос проходит через гейты (лимит не сожжён), при исчерпании — 429 (существующее поведение гейтов).
- **US-3 «Несконфигурированное окружение не пускает»»: без транспорта/unknown → 503 везде, кроме development; `sms` с битым конфигом — не стартует. Тесты: действующий fail-closed набор + юнит-тесты валидатора (пустой ключ/имя, длинное имя, `test_`-ключ при `ENV=production`).
- **US-4 «Ничего не утекает»**: сырой код и ключ провайдера отсутствуют в логах и ответах вне development — включая путь сбоя. Тест: капча всех записей логгеров `memo.auth.*` и тел ответов в обоих сценариях (успех US-1 и сбой US-2), ассерты на тексты исключений.
- **US-5 «Инцидент разбираем по журналу»**: владелец при разборе «код не пришёл» видит в журнале попыток все отправки по телефону (исход, ошибку провайдера, время), а статус у оператора получает разовым запросом по `reference` из журнала. Тест: интеграционные ассерты журнала (записи `accepted`/`rejected` появляются с правильными полями, текст сообщения и ключ в них отсутствуют); скрипт статуса — контракт на заглушке клиента.

## Тесты

- **Контракт `NotificoreClient`** (инъекция httpx-транспорта — `httpx.MockTransport`, сеть не трогаем): JSON-тело (все поля, `destination:"phone"`, `validity` = 300 по значению), заголовок `X-API-KEY`; обе формы ответа (обёрнутая и плоская), код ошибки строкой и числом; ошибки: HTTP 4xx, HTTP 5xx, код ошибки ≠ 0, таймаут, успех без id → `SmsProviderError`; текст ошибки не содержит тело запроса и ключ.
- **`SmsOtpTransport`** (объектный стаб провайдера): конвертация `+7…` → `7…`; неканонический телефон → ошибка; текст по шаблону; reference — 32 hex, уникален между вызовами.
- **Wiring**: матрица `OTP_TRANSPORT` = `""`/`dev`/`sms`/unknown × `ENV` (dev вне development → None — как сегодня).
- **Валидатор конфига**: `sms` + пустой ключ/имя/длинное имя → ошибка старта; `test_`-ключ при `ENV=production` → ошибка старта; `test_` в staging/development — проходит.
- **Журнал попыток**: после успеха — строка `accepted` с id провайдера и reference; после сбоя — `rejected` с кодом/текстом ошибки; текст сообщения и ключ в журнале отсутствуют; миграция таблицы — roundtrip.
- **Скрипт статуса**: контракт на заглушке клиента — запрос по `reference`, вывод статуса; ключ читается из окружения.
- **Интеграционные (TestClient + стаб `SmsProvider`)**: US-1 (202, отправка с текстом шаблона); US-2 (503 при сбое, повторный запрос не сжигает лимит телефона, исчерпание гейтов → 429); US-3 (существующие fail-closed кейсы зелёные).
- **US-4 маскирование**: успех и сбой — код и ключ не встречаются в записях логгеров, телах ответов и текстах исключений.
- **Регресс**: `test_auth_otp_api.py`, тесты лимитов — без правок ожиданий, кроме переноса регистрации счётчика (см. §Архитектура).

## Риски и принятые остаточные риски

1. **Боевое имя отправителя**: тестовый канал принял `ArtStudio` до одобрения; боевой ключ при том же имени дал error 5 — гипотеза: нужно одобрение имени операторами (идёт, #587) или значение общего имени. Вопрос поддержке открыт (исследование, вопросы 1–2). Не блокирует имплементацию: значение приезжает через `NOTIFICATION_SMS_ORIGINATOR`, тесты на заглушках.
2. **Модерация сообщений**: у провайдера есть модерация (обычно ≤5 мин, отключаемая по запросу); для OTP задержка недопустима. Подтвердить применимость к сервисным SMS через API и условия отключения; при необходимости отключить до продового запуска. Сценарий «202 есть, SMS нет» покрывается пользовательским перезапросом кода.
3. **Дубликаты SMS при таймауте** (принятый остаточный риск вместо ретраев): таймаут ≠ недоставка — истёкший на нашей стороне вызов мог доставить SMS; перезапрос кода заменяет строку (PK — телефон), пользователь получит вторую SMS с новым кодом, обе валидны 5 минут — безопасно, но задокументировано.
4. **SMS-флуд и стоимость** (принятый остаточный риск): пер-телефонный кап 5 доставленных кодов за 15 минут глобально ограничивает бомбёжку одного номера (~50 ₽/окно по прайсу); IP-гейты (20/IP, 5 телефонов/IP) режут массовую рассылку с адреса. Глобальный дневной бюджет отправки — рычаг на будущее, в v1 не строим.
5. **Дрейф доков провайдера** (нейтрализован кодом): формат ответа и обязательность полей меняются между поколениями статей — клиент парсит обе формы и не строит выводов из HTTP-статуса API-ошибок; живая проверка 10.11 зафиксирована в исследовании.
6. **Первый исходящий HTTP в бекенде**: прецедент задаётся этой спекой (httpx, per-call клиент с таймаутом) — новый класс рисков отсутствует.
