# Спека #598 — Модалка занятия: постоянная высота 85dvh + кнопка «Создать» в футере

Дата: 2026-11-12. Статус: рев.2.1 — plan-reviewer (хостовый прогон): форм-ассоциация кнопки снята — `<form>` в create-вкладке не существует (submit — обработчик кнопки), «сохранение Enter» было ошибочным обещанием; рев.2 — панель 6/7 внесена; выделено из #595 по решению пользователя (независимые коммиты и PR для независимого отката); концепт подтверждён на Gate B #595.

## 1. Контекст (факты живого кода)

- Оболочка модалок — общий `Modal`: контейнер `flex flex-col overflow-hidden max-h-[85vh] max-w-2xl` (small-вариант `max-h-[60vh] max-w-lg`), высота авторазмерная по контенту; скролл сегодня живёт во внутренних div-ах потребителей (обёртка тела в `Modal` — `overflow-hidden`). Проп `footer` существует (модалка занятия в create-режиме передаёт `footer={null}`).
- Модалка занятия `ActivityDetailsModal`: create-режим — вкладка создания (`CreateActivityTab`) с кнопкой «Создать» (`data-testid="btn-create-activity"`) inline внизу скроллящегося тела; edit/quickAdd — вкладки «Настройки»/«Клиент»/… с футером-кнопкой удаления занятия.
- **История фикс-высоты (установлена панелью ревью #595):** фикс 80vh введён волной #92 (жалоба #74 — окно «прыгает» при переключении вкладок «Настройки»/«Клиент»); затем #262 умышленно заменил фикс на потолок из-за двух дефектов — мёртвое пустое место на коротких формах и клиппинг последнего поля (контейнер `overflow-hidden` без владельца скролла). Решение #262 закреплено тестом-замком `ModalShell.test.tsx` (регэкс `/h-\[\d+vh\]/` — запрет класса фикс-высоты у контейнера; **регэкс не матчит `dvh`** — замок будет расширен, §4).
- Состояние кнопки «Создать»: `canSave`/`submit` живут внутри вкладки создания; `saving` уже поднят в модалку (существующий колбэк `onSavingChange`) — переносу кнопки нужен подъём только `canSave`/`submit`. Существует e2e `modal-no-jump.spec.ts` (US-M09, #156) — уже ассертит стабильность высоты диалога в пределах 5px при переключении вкладок.

## 2. Концепт (подтверждено пользователем 2026-11-12)

1. **Постоянная высота `h-[85dvh]` модалки занятия во всех режимах** (create + edit/quickAdd) через опциональный проп фиксированной высоты общего `Modal`. Суперсед #262 осознанный и только для этой модалки: дефект-1 (пустое место) принимается (§10), дефект-2 (клиппинг) закрывается владельцем скролла (§4). Тест-замок уточняется под «дефолт без фикса + фикс опциональным пропом».
2. **Кнопка «Создать» — в фиксированный нижний футер** create-режима, вне скроллящегося тела; testid сохраняется.

## 3. Границы (сознательно не строим)

- **Остальные модалки и small-вариант не трогаем**: проп опционален, все прочие потребители `Modal` сохраняют авторазмерное поведение.
- **Футер edit/quickAdd не меняется**: там остаётся существующая кнопка удаления занятия.
- **Мультивыбор локаций и вместимость — не здесь** (#595): обе задачи независимо откатываемы (разные коммиты и PR, решение пользователя). Пересечение файлов (`ActivityDetailsModal`, `CreateActivityTab`) не конфликтует семантически: кнопка и высота — здесь, поле локации — там; порядок слияния любой, второй PR ребейзится.
- **Общей «сетки высот» модалок не строим** — один проп с одним потребителем.

## 4. Поведение

- Общий `Modal` получает опциональный проп класса фиксированной высоты контейнера (имя — за планом); при заданном классе контейнер перестаёт быть авторазмерным, структура `flex flex-col overflow-hidden` сохраняется. Фикс-класс **дополняет** контейнер, а не заменяет `max-h-[85vh]` из базового класса: потолок остаётся на месте и безвреден (85dvh ≤ 85vh, при фиксе он не активен) — дефолтные потребители и замок по-прежнему видят один и тот же базовый класс.
- **Владелец скролла — внутренний div вкладки-потребителя, не общий wrapper**: у обоих режимов модалки занятия внутренний контейнер уже `flex-1 flex flex-col overflow-y-auto` — добавляется только `min-h-0` (flex-потомок обязан мочь сжиматься ниже контента, иначе фикс-высота клиппит — закрытие дефекта-2 #262). Обёртка тела в общем `Modal` не трогается (§3 — остальные модалки вне игры); на скролл-контейнере `overscroll-behavior: contain` — прокрутка не «протекает» на страницу под модалкой.
- `ActivityDetailsModal` передаёт фикс-высоту `h-[85dvh]` **во всех режимах**: create-окно всегда высокое, edit-окно перестаёт «прыгать» при переключении вкладок (исходная жалоба #74).
- Единица `dvh`: безвредна на десктопе (совпадает с `vh`), страхует мобильные браузеры с динамическими тулбарами; прецедент в репо — `Overlay` веб-клиента. Браузеры админки — современный десктопный Chrome/Edge (`dvh` поддержан с Chrome 108, e2e закреплён на Desktop Chrome), поэтому отдельный fallback-механизм не строится; если визуальный гейт поймает среду без `dvh` — inline-каскад `height: 85vh; height: 85dvh` как задокументированный запасной вариант (не строится превентивно). Число 85 совпадает с канонным потолком default-модалок; исторический фикс #92 был 80vh — берём 85 для единообразия с потолком.
- **Футер create-режима**: кнопка «Создать» (`data-testid="btn-create-activity"` сохранён) рендерится в футере `Modal`, всегда видна без прокрутки; disabled при `!canSave || saving` — как сегодня у inline-кнопки. Подъём состояния — **минимальный мост**: вкладка публикует наверх `canSave` и `submit` колбэками/регистрацией (точная механика — за планом; подъём всей формы состояния — НЕ делать: `canSave` выводится из ~8 локальных полей); `saving` уже поднят (`onSavingChange`). Формы (`<form>`) во вкладке создания не существует — submit везде обработчик кнопки; футерная кнопка работает тем же механизмом клика, ввод `<form>` ради Enter-отправки не заявляется (её нет и сегодня; рев.2.1 — прежняя строка «Enter сохраняется» была ошибочной). Inline-кнопка из тела формы удаляется. Скроллящееся тело получает тестид (селектор геометрических ассертов US-2).
- Тест-замок `ModalShell.test.tsx` уточняется планом: дефолтный контейнер по-прежнему без фикс-класса, контейнер с пропом — с фикс-классом; **регэкс замка расширяется на `dvh`** (сегодня матчит только `vh` — `h-[85dvh]` прошёл бы незамеченным, и суперсед #262 тихо регрессил бы через новую единицу).

## 5. Контракт

- **API и домен: без изменений** — задача чисто фронтендовая (оболочка модалки + подъём состояния кнопки).
- **Фронтенд-типы**: опциональный проп высоты у `Modal`; внутренний подъём состояния кнопки — контрактом не является.

## 6. User Scenarios (каждый → E2E)

1. **US-1. Постоянная высота во всех режимах.** Высота контейнера модалки (`data-testid="activity-details-modal-container"`) ≈ 85% высоты окна и не меняется при переключении вкладок «Настройки»/«Клиент» — реализуется **расширением существующего `modal-no-jump.spec.ts`** (#156, ассерт стабильности в 5px) данными, дающими заведомо разную натуральную высоту вкладок (без этого условия тест зелёный и при авторазмере — дефект дискриминации); ассерт геометрический, класс-строка — только юнит-замок.
2. **US-2. Кнопка вне скролла.** Кнопка «Создать» (`data-testid="btn-create-activity"`) рендерится в футере: её bbox внутри bbox модалки и вне скроллящегося тела + hit-test `elementFromPoint` в центре кнопки (клик не перехватывает перекрывающий слой), bbox футера в пределах вьюпорта. Носитель — `dayview-slot-create` (create-поток). Скроллящееся тело получает тестид для стабильного селектора.
3. **US-3. Клиппинг не возвращается.** Длинный контент тела (вкладка со списком) прокручивается до последнего элемента — дефект-2 #262 не воспроизводится.

## 7. Behavioral Delta (до → после)

| Аспект | До | После |
|---|---|---|
| Высота модалки занятия | авторазмерная ≤85vh, «прыгает» между вкладками | постоянная h-[85dvh] во всех режимах |
| Кнопка «Создать» | inline внизу скроллящегося тела | фиксированный нижний футер, видна без прокрутки |
| Клиппинг контента | возможен на длинных вкладках (overflow-hidden) | тело владеет скроллом, контент достижим |
| Остальные модалки / API / домен | — | без изменений |

## 10. Риски и допущения

- **Пустое место на коротких формах** (дефект-1 #262) — принято осознанно как плата за постоянство высоты: и create-форма с 7 полями, и короткие edit/quickAdd-вкладки (например, «Клиент» с одной записью) оставят свободное место внизу. Альтернатива «контент-размер + max-h + опциональный min-h» (рекомендуемая дизайн-системами форма) осознанно отвергнута — пользователь ратифицировал именно постоянную высоту 85 (Gate B #595).
- **85dvh на низких окнах** — не выше действующего потолка 85vh, деградации нет.
- **Пересечение с #595** шире «кнопка здесь — поле там»: оба PR правят `CreateActivityTab` (мост canSave/submit здесь — поле локации там) и одни визуальные базлайны; семантически правки независимы (разные механики, разные регионы поведения), операционно — второй PR ребейзится и перегенерирует базлайны. Откат любого PR по-прежнему не ломает другой.
