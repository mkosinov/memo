# #600: приватные занятия (is_private) не видны клиентам в web

- **Issue:** #600
- **Дата:** 2026-11-12
- **Ревизия:** 4 — концепция публичного неймспейса выбрана владельцем 2026-11-12 (после гейта A; рев.1 «ветвление по роли на общем маршруте» отвергнута, ограничение issue «только вырезание строк» отменено тем же решением). Рев.3 = панель 7/7 внесена (хостовый запуск: контейнерный флеш-тир не выдал ни одного отчёта за 25 минут): позитивный контроль посева, паритет 404 в бронировании, предикат в пробе существования, детерминированная сортировка, дефолт окна дат, ключ кэша с датами, явный `per_page`, удаление записей из allowlist, зеркальная правка auth.md. Рев.4 = гейт B: точечный маршрут `/api/v1/public/activities/{id}` отложен владельцем до появления потребителя (рекомендация 3 ревьюеров принята).
- **Зона:** backend (новые публичные маршруты + охрана старых) + api-client + web (переезд на публичные маршруты)
- **Трек:** STANDARD

## Контекст

Флаг `is_private` занятия означает «не для клиентов», но нигде в публичной выдаче не фильтруется. Разведка 12.11 подтвердила все пункты issue против живого дерева (вердикт **actual**):

- `GET /api/v1/activities` публичен (анонимный доступ) и отдаёт приватные строки; параметра `is_private` в контракте списка нет вовсе.
- `GET /api/v1/activities/{id}` публичен: аноним читает приватное занятие по id.
- Схема ответа одна на всех (`ActivityResponse`) — анониму уходят `is_private`, `comment`, `master_id`, метки времени.
- Клиент может записаться на приватное занятие по id: `POST /api/v1/my/records` проверяет только существование занятия.
- Web-фронтенд про `is_private` не знает и ходит в общий список; расписание собирается целиком из данных списка (точечный эндпоинт web не использует).

Текущие потребители флага (не меняются): пропуск приватных при копировании недели (сервер), ромб-пометка в админке.

## Решение

**Выделенные публичные маршруты чтения занятий** по образцу публичных фото (неймспейс ADR-015): минимальная схема для сайта, приватные исключены на сервере, старые общие маршруты закрываются от не-персонала.

1. **`GET /api/v1/public/activities`** — публичный список (анонимный доступ, allowlist в `src/auth/public.py`). Параметры: `date_from`/`date_to` (необязательные, тот же канон целых дней; при отсутствии `date_from` окно по умолчанию — от текущей даты: аноним без параметров не получает дамп всей истории, сайту обе границы не нужны — он всегда передаёт обе) + стандартный пагинационный кирпич. Конверт — тот же `PaginatedResponse`. Порядок детерминированный: `start` по возрастанию, `id` — tiebreaker (образец публичных фото фиксирует сортировку ради стабильной пагинации). Из выдачи исключаются занятия с `is_private = true` (предикат NULL-безопасен, эквивалент `IS NOT TRUE`). `occupied` считается как в общем списке (публичная выдача не пассивная — сайт показывает места).
2. **Точечный публичный маршрут сознательно не строится** (решение владельца, гейт B): потребителя нет — сайт собирает расписание целиком из списка, прецедент публичных фото точечного маршрута не имеет. Когда появится потребитель (например, глубокие ссылки на занятие) — добавим аддитивно: публичная схема + **404** на приватный id, телом и статусом неотличимый от несуществующего.
3. **Публичная схема `ActivityPublicResponse`** — ровно то, что читает расписание сайта (проверено разведкой по мапперу web): `id`, `service_id`, `master_id`, `location_id`, `start`, `duration`, `capacity`, `occupied`. Не уходят никогда: `is_private`, `comment`, `record_info`, `created_at`/`updated_at`, `service_title`. Ссылки-UUID остаются: сайт джойнит справочники на клиенте — это осознанно, серверный джойн — волна #584. `record_info` (по семантике «инфо клиентам») не включён: web его сегодня не читает; будущее добавление — аддитивное расширение схемы, контракт не ломает.
4. **Старые общие маршруты становятся только для персонала**: `GET /api/v1/activities` и `GET /api/v1/activities/{id}` получают охрану чтения персонала по образцу существующей охраны записи; аноним и клиентская сессия → **401**. Записи обоих GET-маршрутов занятий удаляются из `PUBLIC_ROUTES` (+ строка докстринги модуля) — контракт-тест не ловит случай «охранён, но всё ещё в allowlist». Зеркальная правка дом-правила `auth.md` (раздел Public Access): занятия покидают перечень анонимных словарей — в точности прецедент фото #493. Анонимных потребителей, кроме сайта (переезжает), у старых маршрутов нет — проверено разведкой и панелью. WRITE-маршруты занятий не трогаются (охрана записи уже есть). Поведение персонала не меняется: админ видит все занятия, мастер — свои приватные в сетке, точечное чтение `getActivity` в админке продолжает работать.
5. **Бронирование `POST /api/v1/my/records`**: ссылка на приватное занятие → **404** (не 409 «нет мест» и не 422) — та же семантика «как несуществующее». Проверка приватности — в том же запросе существования (предикат в WHERE пробы), до валидации тарифа: проверка после тарифа раскрывала бы факт существования боковым каналом (422 на приватном против 404 на несуществующем). Публичные маршруты эту дыру сами не закрывают, поэтому фикс остаётся в скоупе.
6. **Web переезжает на публичные маршруты**: api-client — `getPublicActivities` по образцу `getPublicPhotos` (тонкая функция, zod-схемы `ActivityPublicResponseSchema` + пагинационная обёртка, request-shape тесты); хук расписания переключается на `getPublicActivities`, ключ кэша сохраняет сегменты дат: `['activities','public', date_from, date_to]` (сегодняшний ключ несёт окно — терять его нельзя). Вызов передаёт явный `per_page=100`: сегодня сайт запрашивает окно до 30 дней без `per_page` и молча получает серверный дефолт 20 строк — усечение уже живёт на старом маршруте и чинится здесь, потому что место вызова и так правится. Маппер расписания не меняется: он читает те же 8 полей.
7. **Один PR на всё** (backend + api-client + web): внешний перерыв контракта исключён — других анонимных потребителей нет.

## Пользовательские сценарии

- **US-1.** Анонимный посетитель сайта на неделе с приватным занятием не видит его в сетке web-расписания. → web e2e, без storageState.
- **US-2.** Клиент пытается записаться на приватное занятие по id — отказ «не найдено» (404), запись не создаётся. → web e2e, клиентская сессия (storageState).
- **US-3.** Аноним обращается к старым общим маршрутам занятий (список и точечное) — 401 без персональной сессии персонала. → backend unit.
- **US-4.** Мастер видит свои приватные занятия в админ-сетке (ромб на карточке). → admin e2e регрессионный страж.
- **US-5.** Копирование недели по-прежнему пропускает приватные занятия. → существующий admin e2e `copy-last-week` остаётся зелёным без правок.

## Behavioral Delta

| Поверхность | До | После |
|---|---|---|
| Аноним, расписание сайта | приватные занятия видны | приватных нет (сайт на публичном списке) |
| Аноним/клиент, чтение по id | 200 с полным телом на общем маршруте | 401 (точечного публичного маршрута нет — отложен до потребителя) |
| Аноним, старые `GET /activities`, `GET /activities/{id}` | полные данные всем | 401 без сессии персонала |
| Клиент, запись на приватное по id | запись создаётся | 404, запись не создаётся |
| Публичная схема занятий | полная `ActivityResponse` (11+ полей, включая `is_private`, `comment`) | урезанная `ActivityPublicResponse` (8 полей) |
| Сайт, окно с >20 занятиями | молча обрезается до 20 строк (дефолт сервера) | до 100 на страницу (явный `per_page`) |
| Админ и мастер (сетка, ромб, копирование недели, скоуп, `getActivity`) | — | без изменений |

## Не меняется

- Копирование недели (пропуск приватных — правило дом-правила activities), ромб в админке, скоуп-модель мастера (`get_scoped`, `EMPTY_SCOPE`), WRITE-маршруты занятий.
- Клиентский джойн web: строки со ссылками на сущности, отсутствующие в публичных справочниках, по-прежнему пропускаются маппером (как сегодня); серверное сужение по архивности — территория #584/#601.
- Кабинет клиента `/my`: записи на приватные занятия, созданные до фикса, остаются видны их владельцу; чистки не делаем — прод-данных нет.
- Композиция галереи #576 (фото услуги/занятий в деталях web-расписания): строится по занятиям публичной выдачи — приватные туда не попадают; проверить на IMPL #576 при приземлении.
- Локализация ошибок брони (#538, In Design): 404 уже в контракте бронирования как «занятие не найдено» — кейс ложится в него без правок карты кодов.
- Волна ADR-015 (#584): продолжает публичные словари; занятия уходят в `/public` сейчас решением владельца (2026-11-12), не дожидаясь волны.

## Тесты

Backend (unit, FastAPI TestClient):

- публичный список: анониму доступен; в посеве ПАРА «приватное + обычное» на одной неделе — ассерт присутствия обычного рядом с отсутствием приватного (позитивный контроль: «отсутствие всего» не должно проходить тест); `date_from`/`date_to` работают; окно по умолчанию от сегодня; конверт пагинации; `occupied` посчитан; сортировка `start`+`id`; схема ровно из 8 полей (лишних нет).
- старые маршруты: аноним → 401; клиентская сессия (кука `memo_client_session`, как выдана) → 401; персонал → как раньше (мастер видит свои приватные в списке и точечно). Случай «клиентский токен в персональной куке» даёт 403 — давняя семантика стека охраны, не пиним.
- бронирование: приватный `activity_id` → 404, тело совпадает с несуществующим id; прямым SQL-запросом (`query_db`) — записи не создано; обычный → по контракту.
- allowlist: маршрут публичного списка открыт анонимно; записи старых GET-маршрутов занятий из `PUBLIC_ROUTES` удалены (`src/auth/public.py`).

api-client: request-shape тесты `getPublicActivities`/`getPublicActivity` по прецеденту `getPublicPhotos` (`endpoints.test.ts`).

Web e2e (фикстуры: посев приватного занятия через `sqlite-exec`/`db-query`; НЕ трогать фиксированную визуальную неделю — приватной строки в ней нет, добавление сломало бы визуальные базлайны админа):

- US-1: сетка без приватного (ассерт отсутствия — паттерн `toHaveCount(0)`); в посеве — пара «приватное + обычное», ассерт присутствия карточки обычного обязателен (позитивный контроль);
- US-2: попытка записи клиентской сессией → 404;
- US-4: мастер-сессия (фикстура `master-session`), приватное занятие СВОЕГО мастера в открытой неделе, ассерт ромба на карточке; ромб — SVG без собственного testid — план добавляет стабильный селектор (мелкая правка админки в этом же PR). Страж под админ-сессией не проверял бы слово «свои»;
- US-5: существующий `copy-last-week` зелёный без правок.

Бэкенд-суит занятий миграции не требует: `api_client` в conftest логинит сида-админа (персональная сессия на весь суит), единственный голый TestClient — тест охраны POST copy-week — остаётся валидным. В PR проверить, что новых голых анонимных вызовов не появляется.

## Риски и допущения

- Клиентская сессия приравнена к анониму везде: старые маршруты → 401, публичные — без привилегий. Отдельной ветки «клиент видит больше анонима» в этом issue нет.
- `service_title` нет в публичной схеме (сайт джойнит сам): у будущего прямого потребителя публичного API без справочников названий не будет — для v1 осознанно (потребитель один — сайт).
- Точный механизм охраны чтения старых маршрутов — право `activities:read` (существует, владеют admin и master); план пинит механику по образцу существующей охраны.
- Разрыв совместимости анонимного доступа к старым маршрутам — намеренный; потребителей, кроме сайта, нет (проверено разведкой и панелью). Выкат: уже открытые вкладки сайта до перезагрузки получают 401 на старом списке — кратковременно, самолечится перезагрузкой; принимаем.
- Rate limiting на анонимных маршрутах в репо нет вообще (включая действующий `/public/photos`) — позиция уровня репозитория, не этого PR; кандидат в отдельный вопрос, не блокирует #600.
