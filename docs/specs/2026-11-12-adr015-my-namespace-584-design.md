# Спека: /my-реструктуризация — волна ADR-015 (#584)

Рев. 5, 2026-11-13 (правки пользователя): «кто я» отдаёт данные учётки (`id`, `phone`, `email`) + список `roles`; аудит пишет все резолвнутые роли; кука `memo_session` → `memo_staff_session` переносится В ЭТУ волну; `/portrait` → `/avatar`; §1 переписан, чтобы «сегодня» не читалось как «останется»; таблица §4.3 починена. Рев. 4: `personas` → `roles`, упрощение языка. Рев. 3: настройки под ветками. Рев. 2: панель 7/7. Рев. 1: Gate A.

## 1. О чём задача, простыми словами

**Как сегодня (это описание СТАРОГО состояния — всё перечисленное меняется):**

- **Профиль сотрудника** — `GET/PUT /api/v1/my` и `POST /api/v1/my/portrait`. Пускает только кука сотрудника `memo_session`.
- **Кабинет клиента** — `GET /api/v1/my/client` («кто я» клиента) и плоские пути `GET /api/v1/my/records|photos|payments`, `POST /api/v1/my/records` — без сегмента `client`. Пускает только кука клиента `memo_client_session`.
- **Настройки** — `/api/v1/user-settings`, отдельный остров (только сотрудники).
- **«Кто я» для админки** — `/api/v1/auth/me`, четвёртый остров.

Проблемы: путь `/my` не говорит, чьи это данные (сотрудника? клиента?); кабинет клиента болтается на плоских путях рядом с профилем сотрудника; права и мастер-снапшот живут в отдельном `/auth/me`; имя куки сотрудника (`memo_session`) не говорит об аудитории; всё это нарушает конвенцию ADR-15.

**Как станет после волны:**

| Путь | Кто пускается | Что отдаёт |
|---|---|---|
| `GET /api/v1/my` | любая валидная кука (обе проверяются) | данные учётки + список ролей |
| `/api/v1/my/client/...` | только кука клиента `memo_client_session` | «кто я» клиента, записи, фото, платежи, бронирование, настройки |
| `/api/v1/my/master/...` и `/api/v1/my/admin/...` | только кука сотрудника `memo_staff_session` | профиль + права (+ мастер-секция в master-ветке), аватар, настройки |
| `GET /api/v1/auth/me` | — | эндпоинт удаляется |

Кукa сотрудника переименовывается `memo_session` → `memo_staff_session` (пара кук зеркалит аудитории). Прод не запущен, поэтому старые пути и старое имя куки не поддерживаем — просто переезжаем.

## 2. Закреплённые решения

1. **`GET /my` — данные учётки + список ролей.** Ответ — сама запись учётки (идентификационные поля: `id`, `phone`, `email`) плюс `roles` — перечень ролей, привязанных к запросу. Имя поля — `roles`: слово уже живёт в домене, новое не вводим. Данные карточек (профиль, кабинет) отдают ветки, а не этот эндпоинт. Секреты и внутренняя механика (пароль, лестница блокировок, флаги подтверждений, внутренние связи) в ответ не входят — это не идентификационные поля.
2. **Состав списка ролей = допуск веток.** Роль появляется в списке тогда и только тогда, когда одноимённая ветка ответит этому же запросу 200. Один источник правды для роутинга фронта.
3. **Ветки строгие.** Клиентская ветка пускает только клиентскую сессию, стафф-ветки — только сессию сотрудника. Человек с двумя учётками (обе куки в браузере) работает в обоих приложениях одновременно, без переключателя.
4. **Совмещение админ+мастер** сохраняется: одна учётка, `role=admin` + флаг мастер-секции; профиль один, мастер-секция — из master-ветки.
5. **`/auth/me` удаляется сразу** после миграции админ-приложения, без переходного периода (прода нет). `login` и `logout` не трогаются.
6. **Кука сотрудника переименовывается**: `memo_session` → `memo_staff_session` — в этой же волне, вместе со стражами и e2e. Карточка учёток (§3) переименование больше не несёт.

## 3. Предпосылки (проверены по коду)

- Кабинет клиента (#513/#499) уже смержен: плоские пути существуют, контракты проверены — переезжают как есть, меняются только пути.
- Комбинированной проверки кук не существует — строится с нуля по ADR-15.
- **Совмещение «сотрудник + клиент» на одном телефоне сегодня невозможно** — и это отдельная задача, не эта волна. Сегодня у учётки одна роль, телефон в таблице учёток уникален, и запрос кода на телефон сотрудника молча ничего не выдаёт. Откроется задачей переворота связей учёток (связь `user_id` переедет на карточки `clients`/`staff`; один человек = одна учётка = один телефон; карточка клиента привязывается к существующей учётке). **Контракт этой волны к тому готов:** когда совмещение придёт, человек с обеими куками просто получит `roles: ["client", "master"]` — ничего в волне менять не придётся.
- Строки в тексте задачи #584 устарели: методы клиента API живут в других местах (перечислено в §9).

## 4. Контракты

### 4.1. `GET /api/v1/my` — «кто я»

Как работает проверка:

- Резолвятся **обе** куки, каждая — «чисто»: без побочной записи актёра в журнал (резолв и журналирование разделяются; существующая функция резолва не меняется — добавляется новая, чистая, с нулевым радиусом разрыва).
- Актёр журнала — **одна запись**: первичная учётка (сотрудника, если его кука валидна, иначе клиентская), и в записи указываются **все резолвнутые роли списком** — не только побеждающая (решение пользователя 2026-11-13). Проигравшая проба по-прежнему не создаёт своей записи.
- Ни одной валидной куки → 401.

Ответ — новая схема `MyWhoamiResponse`: данные учётки + роли.

```jsonc
{
  "id": "…",                              // учётка
  "phone": "+7…",                         // телефон учётки
  "email": "…" | null,                    // у клиентских учёток почты нет → null
  "roles": ["client", "master"]           // подмножество из client/master/admin; порядок не важен
}
```

Правила состава ролей (список = допуск веток, см. решение 2):

- `"admin"` — кука сотрудника `memo_staff_session` резолвилась, роль учётки `admin`;
- `"master"` — кука сотрудника резолвилась, роль `master` **или** у учётки есть мастер-секция;
- `"client"` — клиентская кука резолвилась, роль `client`.

Страховка симметрии: роль попадает в список только при валидной куке «своей» аудитории. Кука клиента не может штатно оказаться в `memo_staff_session` (клиентские учётки без пароля, эту куку выдаёт только парольный вход), но фильтр на месте — от нештатных форм.

### 4.2. Ветка клиента `/api/v1/my/client/*`

Гард прежний (`require_client_session`: только клиентская кука). Всё содержимое — сегодняшние контракты #513/#499 без изменений, меняются только пути:

| Было | Станет | Контракт |
|---|---|---|
| `GET /my/client` | `GET /my/client` | `{phone, name}` — «кто я» кабинета; бутстрап веб-приложения |
| `GET /my/records` | `GET /my/client/records` | записи с визитами, пагинация (#513) |
| `POST /my/records` | `POST /my/client/records` | бронирование (#499); проверки `verify_fetch_metadata` + `verify_origin` сохраняются |
| `GET /my/photos` | `GET /my/client/photos` | фото клиента (#513) |
| `GET /my/payments` | `GET /my/client/payments` | платежи (#513) |
| — | `GET/PUT/PATCH/DELETE /my/client/settings*` | настройки клиента — см. §4.4 |

Роутеры кабинета (`my_client.py`, `my_reads.py`) объединяются в один файл ветки.

### 4.3. Ветки сотрудника `/api/v1/my/master` и `/api/v1/my/admin`

**Один роутер, два статических префикса.** Динамический path-параметр запрещён: он тенил бы соседние `GET /my/client` и настройки-ветки по порядку регистрации роутеров (блокер панели рев.2; статические префиксы делают порядок монтирования нерелевантным, неизвестная ветка даёт естественный 404).

Что отдают ветки, по таблицам (модель данных: `staff` — карточка любого сотрудника: имя, фамилия, портрет, должности; `masters` — расширенная секция мастера (специальности, поля расписания), опциональная, 1:0..1 от карточки; приватные данные — отдельная строка на учётку):

- **`/my/admin`** — профиль сотрудника: карточка `staff` + приватные данные + права. У чистого админа карточки нет — половина профиля просто пустая (как сегодня).
- **`/my/master`** — то же самое **плюс мастер-секция** (`masters`) и её снапшот. Отделять «admin → только staff, master → только masters» нельзя: чистому админу нечего показать из `masters`, а чистому мастеру нужна и карточка `staff` (имя, аватар, личные данные) — он тоже сотрудник.

Допуск ветки — в точности состав списка «кто я»:

- `/my/admin/*` — роль `admin`;
- `/my/master/*` — роль `master` **или** есть мастер-секция. Так совмещённый админ+мастер берёт секцию из master-ветки, а стан «роль master, секции нет» (достижим: явная роль бьёт шаблон должностей, снятие секции — не понижение) не теряет доступ к своему профилю;
- нет валидной куки сотрудника (аноним или только клиентская кука) → 401 единым конвертом;
- валидная кука сотрудника чужой ветки → 403.

Маршруты (одни и те же обработчики под обоими префиксами; сегодняшний `my.py` переезжает):

| Маршрут | Что делает | Ответ |
|---|---|---|
| `GET /api/v1/my/master` и `GET /api/v1/my/admin` | профиль + права | `MyStaffProfileResponse` = сегодняшний профиль + `user_id`, `phone`, `email`, `permissions: [str]`; в master-ветке дополнительно мастер-секция и её снапшот |
| `PUT /api/v1/my/master` и `PUT /api/v1/my/admin` | правка профиля | тело то же (`MyProfileUpdate`), `verify_fetch_metadata` сохраняется |
| `POST /api/v1/my/master/avatar` и `POST /api/v1/my/admin/avatar` | загрузка аватара (бывший `/my/portrait`, переименован решением 2026-11-13) | `AvatarResponse {avatar_url}` (бывший `PortraitResponse`); контракт загрузки без изменений: multipart, 5 МБ, JPEG/PNG/WebP |

Права и email переезжают сюда из `/auth/me`; сборка ответа логина переиспользует существующий сборщик.

### 4.4. Настройки — под ветками

Сегодняшний роутер `/user-settings` (все методы, схемы, семантика «только свои») переезжает под ветки; корневого `/my/settings` нет:

- **стафф-экземпляр** монтируется под `/my/master/settings` и `/my/admin/settings` — та же учётка, те же строки (ветка — адрес аудитории, не другие данные);
- **клиентский экземпляр** — `/my/client/settings` под клиентским гардом: строки у клиентских учёток уже создаются при рождении учётки; потребителя в интерфейсе пока нет — готовая поверхность, методы в api-client появятся вместе с потребителем.

### 4.5. Удаление `/auth/me`

- Эндпоинт и его запись в `PUBLIC_ROUTES` удаляются; пин-тест точного равенства списка теряет одну запись.
- Общий файл с волной #606 (словари): #606 правит тот же пин-тест — порядок мерджей задаёт перебазирование.

## 5. Миграция потребителей

**api-client** (`packages/api-client`):

- `getMe()` удаляется; новый `getMyWhoami(): MyWhoami | null` (401 → null, как сегодня у `getMe`).
- **Исключение 401-перенаправления — точечное**: сегодня в `client.ts` 401 не редиректит на логин только для путей на `/api/v1/auth/`. Добавляем исключение «метод GET + точный путь `/api/v1/my`» — и никак иначе: расширение префиксом `/my` молча отключило бы редирект при истёкшей сессии для всех веток. Юнит-тест: 401 на `GET /my` → редиректа нет; 401 на `/my/master` → редирект есть.
- `getMyStaffProfile(branch)`, загрузка аватара → `/avatar`, настройки с веткой, кабинетные пути — по контрактам §4.
- Zod-схемы: `MyWhoamiSchema` (учётка + `roles`), `MyStaffProfileSchema`; `AuthMeSchema` остаётся только для логина.

**Кука `memo_staff_session`** (переименование в этой волне): константа на бэкенде (`SESSION_COOKIE`), выдача в логине, чтение стражами, очистка в logout; на фронтах кука httpOnly — по имени её фронт не читает; правятся файлы e2e `storageState` (имена кук захардкожены) и фикстуры, сеансные тесты бэкенда.

**Админ-приложение** (`AuthContext`): бутстрап и refresh — цепочка «`getMyWhoami()` → `getMyStaffProfile(branch)`». Ветка: `"master" ∈ roles ? "master" : "admin"`. Матрица отказа по шагам:

| Что случилось | Результат |
|---|---|
| whoami 401 | гость |
| whoami 200 без стафф-роли в списке | гость |
| parse-ошибка (любой шаг) | сброс сессии + переброс ошибки наверх |
| профиль 401 (сессия умерла между вызовами) | гость, снапшот сбросить — мёртвой куке нельзя оставлять живую оболочку |
| сетевая ошибка | бутстрап → гость; refresh → сохранить имеющийся снапшот |

`login`/`logout` не меняются. Настройки (Topbar) ходят в ту же вычисленную ветку.

**Веб-кабинет**: правка только в api-client (пути); бутстрап кабинета остаётся на `GET /my/client`, поведение при 401 не меняется.

Принятая цена: бутстрап админки — 2 запроса вместо одного (whoami → ветка); окно между вызовами закрыто правилом «профиль 401 → гость».

## 6. Проверка кук — механика

- Новая чистая функция резолва (без записи актёра); **существующий резолв не меняется** — его журналирование остаётся при `require_session`, `require_client_session` и опциональном скоупе публичных маршрутов (третий потребитель).
- Комбинированная проверка — только у «кто я»: два чистых резолва → пустой список ролей → 401; затем ровно одна запись актёра — первичная учётка (сотрудник при наличии), с полным списком резолвнутых ролей (решение 2026-11-13).

## 8. Behavioral Delta (до → после)

- `GET /my`: профиль сотрудника → «кто я»: данные учётки (`id`, `phone`, `email`) + список ролей (любая кука).
- Кука сотрудника: `memo_session` → `memo_staff_session` (все пересаживаются, прода нет).
- Профиль: `GET/PUT /my` + `/my/portrait` → `GET/PUT /my/master|/my/admin` + `/my/master|/my/admin/avatar`; ответ богаче (права, email; мастер-секция — в master-ветке).
- Кабинет: плоские `/my/records|photos|payments` → `/my/client/records|photos|payments`; бронирование → `POST /my/client/records`.
- Настройки: `/user-settings*` → `/my/master|/my/admin/settings*`; появляется `/my/client/settings*` (готовая поверхность без потребителя).
- `GET /auth/me` → 404.
- Внешне интерфейсы не меняются; знание о второй роли появляется на уровне API, показ в UI — вне волны.

## 9. Тесты

- **Контракты «кто я»**: поля учётки (`id`, `phone`, `email`; у клиентской учётки `email: null`) и состав списка — только стафф-кука (`[master]`/`[admin]`/`[admin, master]`), только клиентская (`[client]`), обе; невалидная (просроченная/мусорная) кука — роли в списке нет, но не 401; пустой список → 401. Пароль/лок-поля/внутренние связи в ответе отсутствуют.
- **Допуск веток**: клиентская кука на стафф-ветке → 401; стафф-кука на `/my/client` → 401; мастер без роли admin на `/my/admin` → 403; админ без мастер-секции на `/my/master` → 403; «роль master без секции» на `/my/master` → 200; совмещённый админ+мастер — обе ветки 200 (в admin без мастер-секции, в master — с секцией и снапшотом). Настройки: обе стафф-ветки 200 на одних строках; клиентская ветка — только клиентская сессия.
- **Кука**: логин выдаёт `memo_staff_session`; старое имя `memo_session` больше нигде не принимается (стражи её не видят); e2e `storageState` сидируются новым именем.
- **Аудит**: шпион на записи актёра — ровно один вызов на «кто я», актёр = первичная учётка, роли в записи = полный резолвнутый список (ловит и двойную запись, и потерю ролей).
- **CSRF-пины**: каждая переехавшая мутация (включая `/avatar`) несёт свой набор проверок (`verify_fetch_metadata`, на бронировании — плюс `verify_origin`) — явным тестом на маршрут.
- **Адаптация**: тесты профиля/кабинета/настроек на новые пути; пин-тест allowlist (−`/auth/me`); walk-тест закрывает новые пути автоматически; комментарий в `test_delete_matrix_guard.py`; тесты, читавшие `/auth/me` (`test_auth_guards`, `test_client_session_api`, `test_session_fixtures`, `test_master_scope_contract`).
- **api-client**: `endpoints.test.ts` — «кто я», профиль ветки, настройки с веткой, кабинетные пути, `getMe` в блоке удалённых; отдельный юнит на исключение 401-редиректа (обе стороны).
- **Админ unit**: `AuthContext.test.tsx` — успех цепочки и обе ступени отказа.
