# Спека: флаг «не показывать в web» для локаций (#601)

- Ревизия: 4 (2026-11-12: метка переключателя «Видно клиентам» с прямой связкой — решение владельца, инверсии больше нет; рев.3 — панель 7/7: блокер PUT-схемы, позитивный контроль тестов, зеркальная правка auth.md, boolean-ловушки модалки, схема сужена до 4 полей; рев.2 — переименование `is_web_hidden` → `is_public`, полярность положительная, `true` = видна; рев.1 — исходная редакция).
- Концепт: А — публичный маршрут-словарь по образцу #600 (выбор владельца на Gate A, 2026-11-12).
- Зависимость: `depends-on: #600` — публичный маршрут занятий и предикат брони создаются там; #601 расширяет их и не реализуем раньше.
- Связанные: #584 (волна ADR-015 — публичные справочники `/public/*`); #601 становится первым кирпичом волны для локаций, #584 поглощает результат.

## 1. Контекст и проблема

Локация (площадка) сегодня скрывается с сайта единственным способом — архив. Архив означает «выведена из работы»: площадка пропадает не только из web, но и из админки — из сетки расписания (по умолчанию; тумблер «показывать архивные» в личных настройках) и из форм создания занятий (дропдаун фильтрует архивные). Владельцу нужны площадки, невидимые клиентам, но полностью рабочие для персонала (штатная, частная площадка).

Текущее состояние анонимного доступа (проверено по живому дереву 2026-11-12):

- `GET /api/v1/locations` — постраничный список, в белом списке анонима (`backend/src/auth/public.py`); серверный дефолт страницы — 20. Web тянет его без размера страницы → молчаливое усечение списка локаций до 20.
- `GET /api/v1/locations/{id}` — точечный маршрут, в белом списке анонима; web его никогда не вызывает (потребителя нет).
- `GET /api/v1/locations/all` — полный список одним массивом; уже защищён правом `locations:read` (анониму недоступен). Именно его используют админ-дропдауны и словарь сетки.
- Web читает у локации только `id, title, address, location_hint`; страница «локации» в web — статичная заглушка, данных не читает. Остальные 12 полей полной схемы web не использует.
- Занятия архивной локации выпадают из web-расписания клиентской сборкой (строка без локации отбрасывается) — в API они остаются.
- Серверной проверки «локация активна» при создании занятия нет и сейчас (API принимает любую локацию; асимметрия с проверкой активности мастера) — зафиксировано как оговорка, не чинится здесь (см. §8).

## 2. Решение

### 2.1. Флаг `is_public`

- Колонка `is_public` (boolean, NOT NULL, server_default `true`) в таблице локаций; миграция alembic.
- Полярность положительная: `true` = показывается на сайте (по умолчанию), `false` = скрыта. Имя согласовано с публичным неймспейсом `/public`; в CSV пусто = видна (конвертация даёт `true`).
- Схемы: `is_public` живёт в `LocationBase` (наследуют `LocationCreate` и `LocationUpdate`) и добавляется в `LocationPatch` отдельно (патч не наследует базу). Редактирование в админке сохраняется каноническим PUT с полным `LocationUpdate` (`extra="forbid"`) — без флага в PUT-схеме каждое сохранение модалки падало бы 422 (находка панели, подтверждена по коду). PUT-полезная нагрузка модалки несёт текущее значение флага — канон `is_private` у занятия. Все response-схемы локации отдают `is_public`. Вычисляемых алиасов не вводим (`archived` остаётся единственным).
- Семантика: «скрыта с сайта, внутри админа полностью рабочая». Не влияет ни на что в админе: сетка, формы создания занятий, дропдауны, записи, отчёты — локация со флагом ведёт себя как обычная активная.

### 2.2. Публичный маршрут-словарь `GET /api/v1/public/locations`

- Открыт анониму: запись в `PUBLIC_ROUTES` (default-deny контракт T7 пополняется).
- Полный список одним массивом, без пагинации и без параметров вообще — по образцу админского `/all` (решение владельца 2026-11-12: «на админских эндпоинтах полный список отдаётся — тогда и тут так же»). Потолок `BARE_LIST_MAX_ROWS` как у `/all`.
- Отдаёт только неархивированные локации (`archived = false`) с `is_public = true` (колонки `status` у модели нет — активность выражается мягким удалением; находка панели).
- Сортировка `sort_order ASC, title ASC, id ASC` — детерминированная (дефолт справочников #205 §4.4, как в админском `/all`; порядок выдачи несёт сервер — отдельное поле сортировки клиенту не нужно).
- Схема `LocationPublicResponse` — ровно 4 поля: `id, title, address, location_hint` (`address`, `location_hint` nullable); лишних ключей нет (канон #600: публичная схема — ровно то, что читает сайт; `sort_order` из рев.2 убран панелью как не читаемое web). Остальные поля полной схемы анониму не отдаются.

### 2.3. Охрана старых маршрутов (механизм #600)

- Из `PUBLIC_ROUTES` удаляются `("GET", "/api/v1/locations")` и `("GET", "/api/v1/locations/{id}")` — с надгробными комментариями по образцу photos/masters.
- Оба маршрута получают право `locations:read`: аноним и клиент → 401, персонал → как раньше.
- `GET /api/v1/locations/all` уже несёт `locations:read` — не меняется.
- Зеркальная правка дом-правила `docs/domain-rules/auth.md` (раздел Public Access: локации уходят из перечня анонимных словарей, появляется `GET /api/v1/public/locations`) и докстринги модуля `backend/src/auth/public.py` — по образцу #493/#600 (находка панели, трое независимо).

### 2.4. Переезд web на публичный словарь

- Новая функция api-client `getPublicLocations()` + zod-схема `LocationPublicResponseSchema` (4 поля; именование по прецедентам `PhotoPublicResponseSchema` / `ActivityPublicResponseSchema` — находка панели).
- `useLocations` и `useSchedule` (web) берут локации только из публичного словаря; вызов старого постраничного списка из web удаляется. Усечение до 20 исчезает вместе со старым вызовом.
- Точки переезда (полный перечень, находка панели): оба хука; типизация словаря в сборке расписания (карта локаций получает публичный тип вместо полного ответа); разворачивание конверта в хуке расписания — публичный словарь отдаёт голый массив, приведение к постраничному конверту уходит.
- Карта-view-модель локации web (`to-location-vm`) принимает 4-полевой объект без потерь: больше web не читает.
- Страница «локации» web — статичная заглушка, не трогается.

### 2.5. Занятия скрытых и архивных локаций (поверх #600)

- Публичный список занятий `GET /api/v1/public/activities` (создаётся имплементацией #600) дополняется join-фильтром: исключаются занятия, чья локация архивирована ИЛИ скрыта флагом. Аргументация: #600 уже решил класс серверной фильтрацией («скрытое не покидает сервер»); сужение выдачи по архивности локаций #600 осознанно оставил территории #584/#601 — #601 закрывает обе условия одним join.
- Бронирование: проба существования занятия в брони (предикат 404 для приватных из #600) расширяется — занятие локации архивированной или скрытой → 404. Прямого UI-пути к такой брони нет (US-2 прячет занятие из интерфейса) — это защита от брони по прямому id.
- Клиентская сборка web-расписания сохраняет свой skip-строку-без-локации как есть (второй слой, не единственный).

### 2.6. Админ: форма и таблица

- В декларативный конфиг полей локации (`locationFields`) добавляется тип `boolean`; рендер — переключатель-кнопка `role="switch"` с `aria-checked` и `data-testid="toggle-is-public"` по образцу `toggle-private` занятия (`ActivityForm`). Поле «Видно клиентам» доступно и при создании, и при редактировании.
- Связка прямая, без инверсии: `checked = is_public` (метка «Видно клиентам» — решение владельца 2026-11-12; находка панели об инверсии закрыта неймингом).
- Boolean-ветки в механике модалки (находка панели): инициализация полей сегодня даёт не-числу пустую строку — для boolean-поля дефолт `true`; сборка полезной нагрузки передаёт его как boolean, не строку (иначе 422).
- Таблица локаций: у локации с выключенным «Видно клиентам» — бейдж «Не в web» рядом с названием, по образцу бейджа «Архив». Фильтр по видимости в строке фильтров не добавляется (§8).

### 2.7. Предзагрузка прод-справочников

- `backend/seed-data/locations.yaml`: колонка `is_public` во всех записях (текущие 3 локации — `true`).
- `src/seed/reference.py`: приём и применение поля (natural keys по названиям — канон предзагрузки).
- CSV владельца: колонка «видно клиентам» (выровнена с меткой переключателя — решение владельца 2026-11-12); правило конвертации: пусто/«да» = `is_public: true`, «нет» = `is_public: false` (отдельного канона конвертации в репозитории нет — правило фиксируется здесь, находка панели).

### 2.8. Дом-правила

`docs/domain-rules/locations.md` пополняется: семантика `is_public`; отличие от архива — архив = «выведена из работы» (скрыта везде, в админе по умолчанию выключена), `is_public = false` = «скрыта только с сайта, в админе полностью рабочая»; публичный словарь отдаёт только активные и нескрытые.

## 3. Поведенческая дельта (Behavioral Delta)

| Кто | Было | Станет |
|---|---|---|
| Владелец | спрятать площадку с сайта можно только архивом — она выпадает из админ-форм и сетки | переключатель «Видно клиентам» выключил — с сайта исчезла, в админе полностью рабочая |
| Посетитель сайта | видит все активные площадки и их занятия | скрытые площадки и их занятия не видны нигде: фильтр, расписание |
| Клиент с прямой ссылкой | мог забронировать занятие любой активной площадки | бронь занятия скрытой (или архивной) площадки по прямому id → 404, запись не создаётся (гость без сессии и сегодня получает 401 — не меняется) |
| Аноним в API | 3 открытых маршрута локаций, полная схема, усечение списка до 20 | 1 маршрут-словарь `GET /api/v1/public/locations`: 4 поля, полный список; старые маршруты — 401 без персонала |
| Публичный список занятий (после #600) | содержал бы занятия архивных и скрытых локаций | исключает их серверно |

## 4. Пользовательские сценарии (User Scenarios)

- **US-1.** Владелец скрывает площадку с сайта: открывает локацию в админке, выключает «Видно клиентам», сохраняет. В админе площадка и её занятия остались (сетка, дропдауны создания), на сайте площадка исчезла из фильтра, её занятия — из расписания. → admin-e2e: переключатель в модалке (создание и редактирование), бейдж в таблице, сетка и дропдауны без изменений; проба публичного словаря из admin-e2e (см. §6).
- **US-2.** Посетитель сайта не видит скрытую площадку нигде: фильтр локаций без неё, расписание без её занятий. → web-e2e.
- **US-3.** Клиент (после OTP-входа) не может забронировать занятие скрытой площадки по прямому id: его нет в публичной выдаче занятий, запрос брони по id → 404, запись не создаётся. → web-e2e под клиентской сессией (storageState), прямая API-проба брони без UI-пути; гость без сессии до предиката не доходит — 401 (находка панели).
- **US-4.** Владелец возвращает площадку: включает «Видно клиентам» — площадка и её занятия появляются на сайте снова. → тот же admin-e2e/web-e2e цикл, что US-1/US-2 (фаза «включил → проверил»).
- **US-5.** Владелец переносит прод-справочник локаций с колонкой «не показывать в web»: предзагрузка применяет флаг, контрольный прогон сходится. → тест reference-сида (не e2e).

## 5. Visual Compliance Checks

- [ ] страница админки «Локации» — у скрытой локации («Видно клиентам» выключен) виден бейдж "Не в web" рядом с названием — url="/locations"
- [ ] модалка локации (открывается кликом по строке — вне машинного прогона; автоматизация сценария закреплена за admin-e2e, §6): есть переключатель «Видно клиентам», состояние сохраняется после сохранения и повторного открытия

## 6. Тестирование

- Backend unit/интеграционные: публичный маршрут отдаёт только неархивированные и публичные; схема ровно из 4 ключей (лишних нет — утёкшее лишнее поле должно краснить); детерминированная сортировка; потолок строк; охрана старых (401 анониму/клиенту, 200 персоналу с `locations:read`); контрактный тест T7 — новая запись в белом списке, старые две удалены; join-фильтр публичного списка занятий (архивная и скрытая локации); предикат брони 404 с паритетом тела (ответ на скрытый id неотличим от ответа на несуществующий) и SQL-проверкой, что запись не создана.
- Позитивный контроль (канон #600; блокер панели): фикстуры всех трёх слоёв — backend, admin-e2e, web-e2e — сидят пару «скрытая + видимая» локации, у каждой — занятие в отображаемом окне; каждый ассерт отсутствия сопровождается ассертом присутствия видимой контрольной («отсутствие всего» не проходит тест).
- admin-e2e (`locations-web-hidden.spec.ts`): US-1/US-4 — переключатель при создании и редактировании, бейдж, позитивная форма «неизменности» админки (карточка занятия скрытой локации видна в сетке; локация присутствует в опциях дропдауна создания занятия — донор обратного правила `schedule-archived-visibility.spec.ts`), включение «Видно клиентам» (возврат, US-4); проба публичного словаря — анонимный запрос без куки на `GET /api/v1/public/locations` после выключения «Видно клиентам» (сокрытия): скрытой нет, контрольная есть (прецедент зонда публичного словаря — cabinet-спека; термин «readiness-проба» из #600 означает правку globalSetup и здесь не используется — находка панели).
- web-e2e: US-2 — фильтр и расписание без скрытой площадки и её занятий, с позитивным контролем видимой; US-3 — бронь по прямому id под клиентской сессией → 404, запись не создана; US-4 — после включения «Видно клиентам» (фаза админ-цикла) локация и её занятия присутствуют в фильтре и расписании.
- Сид: применение `is_public` из YAML и контрольный `--check` (US-5); фикстура теста несёт обе полярности (минимум одна `is_public: false` — иначе молчаливый пропуск колонки остаётся зелёным, находка панели); маппинг «да/нет/пусто» конвертации — строкой в план.

## 7. Миграция

Alembic: колонка `is_public` boolean NOT NULL server_default `true` в таблице локаций. Существующие строки получают `true` (поведение не меняется до снятия флага).

## 8. Не меняется / вне скоупа

- Серверная проверка «локация активна/не скрыта» при создании занятия — не появляется (асимметрия с мастерами известна и зафиксирована; отдельная задача, если понадобится).
- Фильтр «не в web» в строке фильтров таблицы локаций — не делаем (бейдж достаточно).
- Точечный публичный маршрут `/public/locations/{id}` — потребителя нет (как #600 отложил `/public/activities/{id}`); при появлении потребителя заводится отдельно.
- Страница «локации» web (заглушка «в разработке») — не трогается.
- Остальная волна #584 (публичные справочники остальных сущностей, реструктуризация `/my`, депрекация `/auth/me`) — не здесь.
- Поведение архива — не меняется вообще.
- Кэширующие заголовки публичных словарей (`Cache-Control`/`ETag`) — одним решением в волне #584, не точечно здесь (находка панели best-practices).

## 9. Ограничения и риски

- Часть §2.5 опирается на несуществующий ещё маршрут #600 — имплементация #601 строго после #600 (`depends-on`).
- Переезд web на публичный словарь меняет источник данных фильтра и расписания — риск регрессии точечный (4 поля покрывают всё чтение web, проверено по живому дереву и панелью).
- Публичная схема сознательно урезана до 5 полей: любое новое поле для web — отдельное решение (расширение схемы, не «вернуть полную»).
