# Спека #595 — Мультивыбор локаций при создании занятия (N событий одним действием)

Дата: 2026-11-12. Статус: рев.4 — панель 7/7 внесена (BLOCKER TanStack v5: per-call колбэки `mutate` срабатывают только для последнего вызова — подтверждено документацией; счётчик колбэков заменён промисным контрактом). Сплит с #598 и вместимость по умолчанию каждой локации — решения пользователя от 2026-11-12.

## 1. Контекст (факты живого кода)

- Создание занятия в админ-сетке: модалка `ActivityDetailsModal` (режим `create`) рендерит `CreateActivityPanel` → единственная вкладка `CreateActivityTab` с общей формой `ActivityForm` (та же форма служит вкладкой редактирования `SettingsTab`).
- Локация в форме — одиночный поисковый комбобокс `Combobox` (контейнер `data-testid="create-location"` в create-режиме). Список локаций приходит из справочника (`getAllLocations({ status: 'all' })`), в сиде 3 локации.
- Условие доступности кнопки «Создать» (`canSave`): выбраны мастер, услуга, локация; непустое дата-время; длительность «ЧЧ:ММ» > 0; вместимость ≥ 1 (пустое поле блокирует, 0 в payload не уходит — канон create-формы #280).
- Вместимость автозаполняется от `defaultCapacity` выбранной локации (повторный выбор перезаписывает; нет дефолта → 0 → блокировка до ручного ввода). Длительность автозаполняется от услуги.
- Отправка — кнопка «Создать» (`data-testid="btn-create-activity"`) inline внизу формы (высота модалки и переезд кнопки в футер — отдельная задача #598, здесь не трогаются); один вызов `addActivity` → `POST /api/v1/activities` с одиночным обязательным `location_id` (FK, NOT NULL). Контракт `addActivity` — fire-and-forget с колбэками `onSuccess`/`onError`.
- Конфликт-валидации слотов нет by design (инвариант домена, #258/#259): пересечения занятий допустимы — N созданий в разных залах (и даже у одного мастера) легальны.
- Прецедент мульти-локации в UI: копирование недели (`CopyLastWeekPopover` — явные чекбоксы локаций, контракт `locations: list[str]`); мульти-фильтр локаций в топбаре.
- Слот-префилл create-формы (`CreateDefaults`) несёт только дату и минуты; локация сегодня не предзаполняется ничем, включая открытие из колонки локации в дне-по-локациям.

## 2. Концепт (Gate A, выбор пользователя 2026-11-12)

1. **Чекбоксы локаций в форме создания.** Поле локации в create-режиме становится группой чекбоксов (по одному на локацию списка справочника). Одно нажатие «Создать» создаёт N независимых событий — та же услуга, мастер, дата-время, длительность и приватность; различие только в локации (и вместимости — см. п. 2). Контракт и модель данных не меняются: N вызовов существующего эндпоинта.
2. **Вместимость — по умолчанию каждой локации.** При ровно 1 отмеченной — прежний поток (автозаполнение `defaultCapacity` с возможностью ручной правки). При 2+ — ручной ввод не требуется: каждому событию назначается `defaultCapacity` его локации; зал без умолчания блокирует «Создать» с названием зала.
3. **Предзаполнение галочки локации из дня-по-локациям:** клик по пустому слоту в DayView предотмечает чекбокс локации колонки (подтверждено пользователем на Gate B).

## 3. Границы (сознательно не строим)

- **Не меняем контракт и модель**: никакого батч-эндпоинта и никакого массива `location_id` у события — у события всегда ровно одна локация (FK NOT NULL). Локаций в справочнике единицы; массовое тиражирование недель уже закрыто копированием.
- **Общего переопределения вместимости при 2+ нет** (все залы одной цифрой) — по умолчанию каждой локации достаточно; индивидуальная правка — через редактирование созданного события.
- **Редактирование занятия не трогаем**: вкладка настроек сохраняет одиночный комбобокс локации.
- **Высоту модалки, футер и положение кнопки «Создать» не трогаем** — отдельная задача #598 (независимые коммиты и PR для независимого отката, решение пользователя 2026-11-12). Кнопка остаётся inline в теле формы, как сегодня.
- **Конфликт-валидацию не добавляем** (инвариант домена): параллельные создания в разных залах легальны, предупреждений о пересечении нет.

## 4. Поведение

### 4.1. Форма: чекбоксы локаций

- В create-режиме поле локации рендерится группой чекбоксов: каждая строка — чекбокс + название локации; состав и порядок списка — те же, что у сегодняшнего комбобокса (справочник локаций, включая архивированные — как сегодня). Готовый дропдаун `MultiSelect` (мульти-фильтр топбара) сознательно не используется: локаций единицы — явная группа читабельнее без клика; прецедент явных чекбоксов — копирование недели.
- Контейнер группы сохраняет `data-testid="create-location"`; каждый чекбокс получает `data-testid="create-location-check"` (машинная проверяемость).
- Доступность: группа получает имя через `<fieldset><legend>` («Локация»); каждая строка — настоящий `<label>` с чекбоксом (единый источник имени для скринридеров, дублирующий `aria-label` не используется); подсказки блокировки («У зала…») — `aria-live="polite"`: недоступная disabled-кнопка не анонсирует причину скринридеру.
- Список локаций грузится тем же источником, что комбобокс сегодня: пока не загружен — группа пуста (как пустой список комбобокса), после загрузки чекбоксы появляются; предзаполненный префилл-ид живёт в состоянии и отмечается по прибытии списка. При рефетче выбранные id, которых больше нет в справочнике, отбрасываются из набора.
- Состояние формы: массив выбранных id локаций. `canSave`: ≥1 отмеченной локации + прежние условия (мастер, услуга, дата-время, длительность > 0) + условие вместимости из §4.2.
- Вкладка редактирования (`SettingsTab`) не меняется — общий `ActivityForm` разветвляет поле локации по режиму (create → группа чекбоксов, edit → прежний комбобокс).

### 4.2. Вместимость

- **Ровно 1 локация (по клику пользователя):** поле вместимости как сегодня — автозаполняется `defaultCapacity` этой локации (повторная смена набора до ровно 1 перезаписывает), редактируется вручную; нет дефолта → 0 → блокировка до ручного ввода (канон #280).
- **2 и более локаций:** поле вместимости скрывается; вместо него строка-подсказка «Вместимость — по умолчанию каждого зала». Каждому событию при отправке назначается `defaultCapacity` его локации. Умолчание считается незаданным, если поле отсутствует **или равно 0** (канон вместимости ≥ 1); хотя бы одна отмеченная локация без умолчания блокирует «Создать», подсказка называет первую такую по порядку чекбоксов: «У зала «{название}» не задана вместимость» (0 в payload не уходит).
- После частичного сбоя (§4.3) при программном переходе набора к ровно 1 поле появляется уже заполненным умолчанием оставшейся локации — единое правило: при 2+ ручного ввода не существовало, терять нечего.

### 4.3. Отправка: N событий одним действием

- Кнопка «Создать» (сохраняет `data-testid="btn-create-activity"`, остаётся inline в теле формы — футер в #598) отправляет для каждой отмеченной локации вызов `addActivity` с одинаковыми мастером, услугой, `start`, длительностью, приватностью; различие — `locationId` и вместимость (умолчание его локации при 2+; значение поля — при ровно 1).
- **Завершение N вызовов — промисами, не колбэками** (панель, подтверждено документацией TanStack Query v5 «Consecutive mutations»: колбэки, переданные в `mutate`, срабатывают один раз и только для последнего вызова, а состояние наблюдателя `isPending` отражает лишь последний вызов — счётчик колбэков недосчитывает, лок не снимается). `addActivity` расширяется: внутренний вызов переводится на `mutateAsync`, метод **возвращает промис** и сохраняет колбэки для существующих потребителей (вызываются по resolve/reject). Create-вкладка ждёт `Promise.allSettled` N промисов — saving-лок до завершения последнего; на состояние наблюдателя/`mutationKey` вкладка не полагается. На время полёта поля и чекбоксы заблокированы (disabled).
- **Полный успех (N из N)**: форма закрывается; тост успеха — при N=1 прежний текст («Создано: {услуга} — {дата}, {время}»), при N≥2 «Создано занятий: N ({услуга} — {дата}, {время})». Дата в тосте — из значения поля (канон #280).
- **Частичный сбой (0 < K < N)**: форма остаётся открытой с введённым; **успешные локации автоматически снимаются с чекбоксов** (повторная отправка не создаёт дубликатов — жмутся только оставшиеся); тост ошибки «Создано K из N ({услуга}): {сообщение ошибки первой неудавшейся локации по порядку чекбоксов}». Прочие поля не сбрасываются.
- **Полный сбой (0 из N)**: форма открыта, ничего не снимается, после снятия лока поля разблокированы; тост при N≥2 — «Создано 0 из N ({услуга}): {сообщение первой ошибки по порядку чекбоксов}», при N=1 — как сегодня (сообщение из `parseApiError`; его сетевой фолбэк покрывает отказы без ответа).

### 4.4. Предзаполнение из дня-по-локациям

- Слот-префилл (`CreateDefaults`: дата + минуты) расширяется опциональным `locationId`: клик по пустому слоту в **DayView** (день по локациям — колонка = локация) предотмечает чекбокс локации этой колонки (ровно 1 → сработает автозаполнение вместимости). Действует только в режиме колонок-по-локациям; режим мастер-колонок и view-only архивные колонки DayView префилла не дают. Открытие из WeekView/тулбара — без предотметки.
- Шов: сегодняшний колбэк открытия получает только день+минуты — идентификатор колонки пробрасывается пер-колоночным замкнутым обработчиком или расширением сигнатуры (за планом); WeekView делит обработчик и остаётся без предотметки.

## 5. Контракт

- **API: без изменений.** `POST /api/v1/activities` вызывается N раз, тело прежнее (одиночный `location_id`). Валидация бэкенда не меняется (`check_master_active` остаётся на каждом вызове).
- **Фронтенд-типы**: `addActivity` расширяется — начинает **возвращать промис** (`mutateAsync` внутри; колбэки сохранены для существующих потребителей, обратной поломки нет); `AddActivityInput` прежний; `CreateDefaults` получает необязательный `locationId` (+ проброс идентификатора колонки через шов открытия DayView, §4.4); состояние формы — массив id локаций (внутреннее, контрактом не является).

## 6. User Scenarios (каждый → E2E)

1. **US-1. Создание в 2 залах одним действием.** Отмечены 2 локации с разными умолчаниями вместимости → «Создать» активна без ручного ввода вместимости → в сетке дня-по-локациям 2 карточки, у каждой вместимость его зала; тост «Создано занятий: 2 (…)», форма закрылась.
2. **US-2. Единственная локация — прежний поток.** Отмечена 1 локация → вместимость автозаполнилась и редактируется; создание → 1 карточка, прежний тост.
3. **US-3. Зал без умолчания блокирует.** Отмечены 2+ локации, у одной нет `defaultCapacity` → «Создать» заблокирована, подсказка называет зал.
4. **US-4. Частичный сбой.** 2 локации, один POST отвечает 500 (мок) → тост «Создано 1 из 2 (…)», форма открыта, чекбокс успешной локации снят; повтор шлёт ровно 1 запрос → успех → форма закрыта.
5. **US-5. Предзаполнение из дня-по-локациям.** Клик по пустому слоту колонки DayView → открытая форма имеет предотмеченный чекбокс локации колонки, вместимость автозаполнена.

## 7. Behavioral Delta (до → после)

| Аспект | До | После |
|---|---|---|
| Выбор локации при создании | одиночный комбобокс | группа чекбоксов, 1..N локаций |
| Создание одного занятия в 2 залах | форма заполняется дважды | одно действие → 2 события |
| Вместимость при 2+ локациях | — (не возникало) | по умолчанию каждой локации, без ручного ввода |
| Зал без умолчания вместимости | блокировка при одиночном выборе | блокировка с названием зала (при 2+ отметках; при ровно 1 — прежний канон #280) |
| Частичный сбой мульти-создания | — (не возникало) | форма открыта, успешные локации сняты, тост «Создано K из N» |
| Клик по слоту в DayView | локация не предзаполнена | чекбокс локации колонки предотмечен |
| Редактирование/контракт/модель/высота модалки | — | без изменений (высота — #598) |

## 8. Тесты

- **E2E (admin, Playwright)**: новый spec-файл мультивыбора — US-1 (включая ассерт вместимости каждой из 2 карточек по умолчаниям залов); US-3; US-4 (мок фейлит POST по `location_id` из тела запроса — при N параллельных одинаковых URL порядок вызовов недетерминирован, матчинг по телу делает тест детерминированным и локализуемым; на каждый ожидаемый ответ — отдельный wait, каждая ветка `page.route` завершается fulfill/continue).
- **US-2 и US-5** несёт модифицированный `dayview-slot-create`: прежний одиночный поток **со шагом ручной правки вместимости** перед отправкой (редактируемость поля на уровне e2e) + ассерт предотмеченного чекбокса при открытии из DayView + негатив: открытие из режима мастер-колонок — ни один чекбокс не отмечен.
- **Правка существующих спеков со сменой комбобокса на чекбоксы**: `dayview-slot-create`, `schedule-saving-toast`, `admin-clicks-empty-slot` (2 выбора + 1 упоминание в таблице заполнения), `schedule-empty-week` (3, включая выбор двух локаций); юниты `CreateActivityTab.test.tsx` (4 вхождения), `ActivityDetailsModal.test.tsx`. E2E `activity-details-modal` правки не требует (create-локацию не использует, edit не меняется). Числа вхождений при исполнении пересчитать grep'ом по `create-location`.
- **Юнит (vitest, admin)**: `CreateActivityTab` — при ровно 1 (клик) автозаполнение умолчанием и ручная правка; при 2+ поле скрыто, блокировка с названием первого по порядку зала без умолчания (отсутствует или 0); после частичного сбоя успешные id сняты, при переходе к ровно 1 поле появляется с умолчанием оставшейся; блокировка `canSave` при 0 локаций; **правило порядка ошибки exercised: 2 отказа с колбэками/промисами, завершающимися в обратном порядке чекбоксов, — тост несёт сообщение первой по порядку чекбоксов**; полный сбой 0 из 2 — чекбоксы не сняты, тост со счётчиком; текст тоста N=1 и N≥2; блокировка полей на время полёта; подсказки блокировки — aria-live.
- **Бэкенд**: не тестируется — не меняется.

## 10. Риски и допущения

- **Идемпотентность N POST (принятый риск)**: запрос, зафиксированный сервером, но потерявший ответ (таймаут сети), оставит локацию отмеченной — повторный «Создать» создаст дубликат; блокировка полей на время полёта этот случай НЕ покрывает. Дубликат виден в сетке и удаляется штатно; инструмент одиночного администратора, домен без уникальностей слотов (инвариант D8) — идемпотентность-ключи не строим (YAGNI; названный хвост при появлении повторов на практике).
- **Инвалидация кэша**: хуковый `onSuccess` мутации инвалидирует семейство `activities` на каждом вызове — N параллельных даёт N инвалидаций (дедуп react-query их полностью не глотает). Решение сразу: единая инвалидация по завершении всех вызовов (вкладка/хук — за планом).
- **Архивированные локации в один клик**: в комбобоксе до архивной нужно было дошагать поиском, в чекбоксе — один клик; состав списка прежний (паритет с сегодня), возросшая лёгкость случайного выбора архивной локации — принятый риск.
- **Параллельные POST** — бэкенд без конфликт-валидации (инвариант домена), порядок создания не важен.
- **Дубликаты при повторе после частичного сбоя** исключены автоматическим снятием успешных чекбоксов; повторная отметка успешной локации вручную — осознанный выбор пользователя (легально по домену).
- **Предзаполнение DayView — часть #595**, отдельно не выделяется: сплит пользователя — 2 темы (мультивыбор/высота), дальнейшее дробление не велено.
- **Скрытие поля вместимости при 2+** меняет высоту тела формы — допустимо: модалка авторазмерная (высота — отдельная тема #598).
- **e2e-локаторы**: шаги «выбрать локацию в комбобоксе» в существующих тестах меняются на «отметить чекбокс» — полный список в §8.
