# Спека: #576 — публичные фото услуги и её занятий в деталях расписания (web)

Рев.3 — решение пользователя на гейте B (12.11): галерея деталей = **объединение**
фото услуги и фото её занятий (дополняют, не заменяют), порядок — сначала прямые
фото услуги, потом фото занятий; лимит миниатюр 20; видимость владельца не
проверяется. Фолбэк-механика рев.2 удалена (один запрос). Семантика объединения
совпадает с существующим предикатом админ-списка («variant A», #211 §6.7) —
панель рев.2 предлагала ровно эти две ветки, выбрана объединяющая.

Рев.2 — после панели 7 ревьюверов: отдельный параметрический кирпич публичного
маршрута, ветка ошибок хука, различающие тесты, a11y-контракт полосы.

## 1. Проблема (для читателя, не видевшего issue)

Гость открывает веб-страницу студии и смотрит расписание мастер-классов. Скоуп v1
(`docs/release/v1-2026-12-01.md`, строка «Клиент видит расписание мастер-классов:
описание, фото») требует показывать фото. Сегодня:

- карточки и детали занятия показывают **обложку** — `image_url` из описания услуги
  (`buildSchedule.ts:96` подставляет `service.image_url`); это работает и не трогается;
- все остальные фото (модель `Photo`, GH #211 — 4 варианта владельца: клиент /
  услуга / занятие / локация, максимум один по CHECK `ck_photos_single_owner`)
  гостю в контексте занятия недоступны: публичный эндпоинт
  `GET /api/v1/public/photos` (ADR-015, #583) отдаёт только общую ленту без
  фильтра по владельцу, а в полезной нагрузке расписания поле `photos`
  жёстко пустое (`buildSchedule.ts:100`) — мёртвое поле, закреплённое тестом
  (`buildSchedule.test.ts:166`).

Issue #576 заявлял причину «маппер выбрасывает фото». Проверка по живому дереву
уточнила: обложка через маппер проходит; выбрасывается (и никогда не заполняется)
отдельное поле `photos`, а главное — у гостя **нет способа получить** фото
конкретного занятия или услуги. Текст задачи частично устарел: `toActivityView`
из диагноза — адаптер на главной странице, галерея после #583 ходит в
`/api/v1/public/photos`.

## 2. Решение (Gate A + правка гейта B — концепция пользователя)

Исследованные альтернативы (шаг 0) отпали после проверки фактов: «фото в полезной
нагрузке расписания» дублировал бы уже работающий механизм обложки; «подбор фото
из общей галереи по тегам» хрупок (нет гарантии тегирования). Выбран вариант
пользователя — **догрузка публичных фото по открытию деталей**:

1. **Карточки расписания не меняются** — обложка услуги уже показывается.
2. Гость открывает детали занятия → фронт делает **один запрос**
   `GET /api/v1/public/photos?service_id=<услуга>` (рев.3: объединяющая
   семантика — прямые фото услуги **и** публичные фото всех занятий этой
   услуги; фолбэка и переопределения нет).
3. UI: под главной картинкой — горизонтально скроллящийся ряд миниатюр
   (не более 20): сначала прямые фото услуги, затем фото занятий; внутри
   групп — от новых к старым. Главная по умолчанию = обложка услуги (как
   сегодня); клик по миниатюре ставит её на место главной; обложка — первая
   миниатюра ряда (клик возвращает).
4. Нет фото у услуги и её занятий — ряда нет, только обложка.

Почему фильтр, а не новое поле в контракте занятий: веб-страница расписания
остаётся одно-запросной (фильтрация нужна только при открытии деталей), а
публичный эндпоинт уже построен минимальной аудиториальной схемой — расширение
на один необязательный параметр не расширяет утечку (id услуг и так публичны в
каталоге; `is_public=True` остаётся принудительным).

## 3. User Scenarios (каждая → проверяющий тест)

| # | Сценарий | E2E |
|---|---|---|
| US-1 | У услуги есть свои фото и у её занятия есть фото: гость открывает детали → ряд = обложка, затем **фото услуги, затем фото занятия** (порядок проверяется); клик по миниатюре меняет главную; клик по обложке-миниатюре возвращает обложку | `frontend/web/e2e/activity-photos.spec.ts` US-1 |
| US-2 | Только у услуги есть фото (у занятий нет): ряд = обложка + фото услуги | там же US-2 |
| US-3 | Только у занятия есть фото (у услуги своих нет): ряд = обложка + фото занятия | там же US-3 |
| US-4 | Нет фото ни у услуги, ни у её занятий: ряда нет, главная = обложка | там же US-4 |

US-1 различающий: фикстура обязана дать фото обеим группам и проверить порядок —
иначе потеря группировки (все вперемешку) осталась бы зелёной.

## 4. Behavioral Delta (before → after)

| Аспект | Before | After |
|---|---|---|
| Детали занятия | только обложка услуги | обложка (главная, по умолчанию) + ряд ≤20 миниатюр: прямые фото услуги, затем фото её занятий; клик по миниатюре меняет главную; ряд скроллится влево/вправо |
| Карточки расписания | обложка услуги | без изменений |
| `GET /api/v1/public/photos` | общая лента, фильтры владельцев не подключены | + необязательный фильтр `service_id` (объединяющая семантика: услуга + её занятия) |
| Поле `photos` в веб-модели расписания | всегда `[]` (мёртвое, закреплено тестами) | удалено вместе со всей цепочкой и пинами тестов |
| Общая галерея на странице | лента всех публичных фото | без изменений |

## 5. Вне объёма (не переоткрывать)

- Галерея в оверлеях записи (`BookingActivityOverlay`) — обложка остаётся как есть.
- Пагинация/догрузка ленты миниатюр: один запрос `per_page=20` (предел
  пользователя, рев.3); больше 20 фото владельцев молча усекаются, догрузка — вне объёма.
- Фильтр `activity_id` на публичном маршруте не добавляется: после отказа от
  переопределения (рев.3) потребитель один — галерея услуги; понадобится — добавим позже.
- Назначение владельца фото в UI админки: API создания/правки фото уже принимает
  `service_id`/`activity_id` (`PhotoCreate`), удобство админ-UI не трогаем.
- Фотографии клиента (`client_id`) и локации как источники миниатюр — нет.
- #547 (мёртвые URL сид-фото в общей галерее) — отдельная задача; e2e здесь
  использует собственные статические фикстуры, а не сид.

## 6. Требования

### 6.1 Публичный маршрут (`backend/src/api/v1/public.py`, `src/services/photo.py`)

- Новый параметрический кирпич `PublicPhotoListParams(PaginationParams)` — только
  `service_id: str | None` (типизация по прецеденту `client_id` в
  `PhotoListParams`). Маршрут переключается с `PaginationParams` на него,
  инъекция `Annotated[..., Query()]` — без скалярных параметров рядом (правило
  репозитория «no scalar-param mixing», fastapi #12481).
- **Не** `PhotoListParams`: он несёт `q`/`tag_id`/`is_public`/`sort_by` и прочие
  админ-фильтры (`schemas/photo.py:115-128`) — их активация на анонимном
  маршруте расширяла бы поверхность.
- Предикат `service_id` — **объединяющий** («variant A», как в общем запросе
  `services/photo.py:467-473`): `Photo.service_id == X OR Activity.service_id == X`
  через LEFT OUTER JOIN. Публичный композит переиспользует эту ветку.
- Порядок ответа при `service_id` — двухгрупповой: сначала прямые фото услуги,
  затем фото занятий; внутри групп закреплённые `created_at desc`, `id asc`.
  Без фильтра порядок прежний (`created_at desc`, `id asc`).
- Инвариант `is_public=True` принудительно; схема ответа не меняется
  (`PhotoPublicResponse`: `id`, `filename`, `tags` — идентификаторы владельца
  наружу не отдаются, группа принадлежности тоже).
- Фильтр по несуществующему id → пустой список (не 404); прочие неизвестные
  параметры по-прежнему игнорируются.
- Видимость владельца не проверяется (решение пользователя, рев.3): единственный
  контур видимости — `is_public` самого фото.
- Докстринг маршрута обновить: «Owner filters are not wired» → описать фильтр
  `service_id`, объединяющую семантику и двухгрупповой порядок.

### 6.2 api-client (`packages/api-client`)

- `PhotoPublicListParams` (`endpoints.ts:395`) расширяется полем
  `service_id?: string` (передаётся в query-string).
- Zod-зеркало ответа не меняется. Юнит-тесты: параметр попадает в URL.

### 6.3 Веб-модели и мапперы (`frontend/web/app/lib`)

- `WebScheduleDTO` уже несёт `serviceId` (`buildSchedule.ts:79`, ассерт в
  `buildSchedule.test.ts:146`) — изменений нет. Поле добавляется в цепочку
  ниже: `ScheduleView` (`to-schedule-vm.ts`), адаптер `page.tsx`,
  `ActivityView` — чтобы `ActivityDetail` знал id услуги.
- Мёртвая цепочка `photos` удаляется целиком:
  - `WebScheduleDTO.photos` (`buildSchedule.ts:100`) и пин
    `buildSchedule.test.ts:166` (`expect(dto.photos).toEqual([])`) — ассерт
    удаляется, не заменяется (`serviceId` уже закреплён строкой выше);
  - `ScheduleView.photos` (`to-schedule-vm.ts:24`) и пины его теста
    (`to-schedule-vm.test.ts:33, 108-114, 187`);
  - `guestPhotos` в адаптере `page.tsx` и `ActivityView` + мёртвый маппер
    `to-activity-vm.ts:17` (`guestPhotos: raw.guest_photos`; рендером не
    используется — удалить или править вместе с его тестом и фикстурами).

### 6.4 Хук догрузки (`frontend/web/app/hooks`)

- Новый `useServicePhotos(serviceId)`: react-query, **один** запрос
  `getPublicPhotos({ service_id, per_page: 20 })`. Результат —
  `GalleryPhotoView[]` (пустой массив = ряда нет).
- Ошибка запроса пробрасывается (стандартные ретраи react-query): ряда нет,
  обложка не блокируется. Фолбэка нет — он не нужен (одна группа данных).
- Маппинг через существующий `toGalleryPhotoView` (тот же allowlist `toAllowedUrl`
  и подпись из тегов) — без копий логики; порядок массива = порядок ответа API.
- Политики кэша — как у `useGallery` (`staleTime: 300_000`, `gcTime: 600_000`),
  ключ `['photos', 'public', 'service', serviceId]`. Префиксная связь с
  `['photos', 'public']` галереи — намеренная (инвалидация галереи обновит и
  миниатюры); сегодня в вебе `invalidateQueries` нет.

### 6.5 UI деталей (`frontend/web/app/ui/ActivityDetail.tsx`)

- Под блоком главной картинки — ряд миниатюр: `flex`, `overflow-x-auto`,
  `no-scrollbar` (паттерн `GuestGallery.tsx:19`; компонент не переиспользуется
  напрямую — у него разметка секции страницы, а не миниатюрный ряд в оверлее),
  каждая миниатюра ~64–80 px.
- Состав ряда: обложка услуги (первая, клик возвращает её в главную) + до 20 фото
  ответа API в его порядке (фото услуги, затем фото занятий). Главная по
  умолчанию — обложка; `src` меняется локальным состоянием, без перезапросов.
- Обложки нет (`image_url = NULL`, `ServicePatch` nullable): миниатюра обложки
  и дефолт главной опускаются, главная по умолчанию — первое фото ряда;
  нет фото и обложки — блок картинки без изменений (поведение сегодня).
- Доступность: ряд скроллится с клавиатуры (`tabindex="0"`, `role="group"`,
  `aria-label`), миниатюра — нативная `<button>` с описательным `aria-label`,
  активная — `aria-current="true"`, стили `:focus-visible`.
- Картинки миниатюр: `loading="lazy"`, `decoding="async"`, явные `width`/`height`
  (против CLS); главная — без `lazy`.
- Машинные хинты: `data-testid="activity-photo-main"` на главной картинке,
  `data-testid="activity-photo-strip"` на контейнере ряда,
  `data-testid="activity-photo-thumb"` на каждой миниатюре.
- Ряд не рендерится, когда ответ после allowlist пуст.

### 6.6 Тесты

- Backend (`/api/v1/public/photos`):
  1. `service_id` → публичные прямые фото услуги **и** публичные фото её
     занятий (различающий кейс: фото услуги + фото занятия услуги + чужое фото
     услуги/занятия + непубличные — в выборке только первые две группы);
  2. порядок двухгрупповой: прямые фото услуги раньше фото занятий, внутри
     групп `created_at desc` (≥2 фото в каждой группе с разными датами);
  3. несуществующий id → пустой список;
  4. без фильтра — прежняя общая лента и порядок (регресс) + выборка с
     фильтром ⊆ выборка без фильтра (утечка-инвариант).
- Web unit: хук (один запрос с `service_id`, ошибка → пусто/ряда нет); проброс
  `serviceId` в `ScheduleView`; рендер полосы (порядок миниатюр = порядок
  ответа, клик меняет главную, пустой набор — ряда нет, a11y-атрибуты на месте).
- Web e2e (`activity-photos.spec.ts`, фикстуры по канону `cabinet-photos.spec.ts`:
  статические filename из `frontend/web/public/images/`, фото создаются через
  API с владельцем `activity_id`/`service_id`, `is_public: true`): US-1…US-4.

### 6.7 Domain rules (`docs/domain-rules/photos.md`)

- Строка-правило композиции: миниатюры галереи деталей занятия = обложка
  `image_url`, затем публичные прямые фото услуги, затем публичные фото её
  занятий; видимость владельца не проверяется (контур один — `is_public` фото).

## 8. Риски и совместимость

- **Публичный эндпоинт получает фильтр** — поверхности не расширяет: `is_public`
  принудителен, схема ответа прежняя, id услуг уже публичны (каталог). Видимость
  владельца не проверяется — единственный контур видимости `is_public` фото
  (решение пользователя, тест-инвариант 4 страхует утечку).
- **Объединяющая семантика = админ-предикат «variant A»** — публичный композит
  переиспользует существующую ветку запроса; расхождение с админом только в
  порядке (двухгрупповой на публичном маршруте).
- **Вес ответа расписания не растёт** — догрузка только при открытии деталей,
  один запрос ≤20 фото.
- **Мёртвое поле `photos` удаляется** — внутренние модели веба, контракт наружу
  не менялся (поле всегда приезжало пустым); пины тестов правятся вместе с цепочкой.
- **>20 фото усекаются** — принято для v1 (§5), догрузка позже.
- **Кэш-ключи** — префиксная связь с галереей намеренная; `invalidateQueries`
  в вебе сегодня нет.
