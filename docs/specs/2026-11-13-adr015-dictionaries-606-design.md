# #606 — Волна ADR-015 (словари): /public/masters|services, гарды bare GET, флаг видимости услуг, миграция веб-формы

- **Issue:** #606 (`depends-on: #600, #601` — оба закрыты, смержены)
- **Решение:** ADR-015 clause 4 (`docs/decisions/015-api-url-audience-namespaces.md`) — миграция справочников; черновик волны — спека #493 §5/§9.
- **Дата:** 2026-11-13, рев.4 — 2026-11-14. Рев.2 — панель 7 (хост-запасной прогон). Рев.3 — решения пользователя на Gate B: флаг «не показывать в web» для услуг (зеркало #601), поля деталей (`description`, `min_age`, `max_age`) и `specialty` в витринной услуге; показ в текущем UI НЕ строим — чистый транспорт под будущий экран деталей (вариант 2). Рев.4 — панель рев.3 (6× SOUND_WITH_CONCERNS, 1× NEEDS_REVISION, блокер один): семантика записи флага переписана по канону #601 (PUT модалки несёт значение, патч — отдельной строкой), фотогалерея закрыта терминами видимости услуги, флаг в списке полей аудита услуг, `_PUBLIC_GETS` и клиентская ветка 401 в тестах, владелец адаптации под #599, порядок и сборка тегов, `description: str`, чистка устаревших обоснований локаций.
- **Проверка актуальности (разведка 2026-11-13):** partially stale — половина волны уже в main (#600: `/public/activities` + гарды; #601: `/public/locations` + гарды). Остаток волны — предмет этой спеки: голые GET мастеров/услуг/тегов. Поправка внесена комментарием в issue.

## 1. Контекст и проблема

Веб-форма записи (`frontend/web/app/hooks/useSchedule.ts`) собирает расписание из 4 справочников. Занятия и локации уже переведены на витринные маршруты (#600/#601). Masters и services форма до сих пор читает с staff-маршрутов: `GET /api/v1/masters` и `GET /api/v1/services` (полный админ-контракт) находятся в `PUBLIC_ROUTES` — аноним получает их целиком. Теги публичны дважды (`GET /tags`, `GET /tags/{id}`), хотя внешне нужны только вложенными в услугу.

Класс проблемы — «аноним получает полный админ-контракт» — ADR-015 предписывает закрыть: витринный минимум в `/public/*`, полный контракт — только по read-праву. Дополнительно (решение пользователя, Gate B рев.2): услугам нужен флаг «не показывать в web» — точное зеркало #601 для локаций.

## 2. Границы

Строим:
1. `GET /api/v1/public/masters` — витринный минимум.
2. `GET /api/v1/public/services` — витринная схема услуг: поля формы записи + поля деталей (`description`, возрасты) + `specialty` (транспорт без показа — решение пользователя, вариант 2).
3. Гарды на 5 маршрутов: `GET /api/v1/masters`, `GET /api/v1/services`, `GET /api/v1/services/{id}`, `GET /api/v1/tags`, `GET /api/v1/tags/{id}` — удаление 5 записей из `PUBLIC_ROUTES`.
4. Миграция веб-формы + api-client-методы.
5. Флаг видимости услуги `is_public` — зеркало #601 (локации): миграция, админ-UI, серверная фильтрация витрины услуг, витрины занятий И витрины фото, бронь по прямому id → 404, аудит, сид.

Не строим (осознанно):
- **Показ полей деталей в текущем UI** (решение пользователя, вариант 2): `description`/`min_age`/`max_age`/`specialty` едут в витринный контракт насквозь, отображение появится вместе с экраном деталей услуги; оверлей бронирования не меняется.
- **`/public/tags` не появляется** — анонимного потребителя списка тегов нет (форма теги отдельно не тянет, приходят вложенными в услугу; разведка подтвердила). Осознанное сужение волны относительно формулировки ADR-015 clause 4, который перечисляет tags среди «minimal `/public/*` variants»: без потребителя витринный эндпоинт — мёртвая поверхность. Теги получают только гарды.
- **Витринные by-id эндпоинты** (`/public/masters/{id}`, `/public/services/{id}`) — потребителей нет, прецедент #493 закрывает by-id гардом.
- **Rate limiting на `/public/*`** — отдельная задача #609. Туда же: `Cache-Control`-заголовки для `/public/*` (сегодня их нет на всём бэкенде), формулировка «422-потолок — ошибка, не зависящая от клиента» и вопрос анонимной документации API (`/docs`, `/openapi.json` — до-существующая поверхность, данными не течёт).
- **Видимость фото ЛОКАЦИЙ** — соседняя поверхность с той же дырой, что закрываем для услуг (фото скрытой локации остаются в галерее — унаследовано из #601): вне этой волны, наблюдение-кандидат в отдельную задачу (§8).
- **Контракты staff-маршрутов не меняются**, кроме одного легитимного дополнения: staff-схема услуги получает поле `is_public` (чтение/запись флага в админке) — так же, как #601 дополнил схему локации.

## 3. Решение

### 3.1. `GET /api/v1/public/masters`

Голый JSON-массив без параметров (канон `/all` и прецедент `GET /public/locations`, #601).

- **Фильтр серверный:** только действующие мастера (`masters.is_active = true`) — как у staff-списка; архивный мастер в витрину не попадает.
- **Схема `MasterPublicResponse`** (витринный минимум из задачи «имя, специальность, фото»):

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | str | ключ для сшивки с занятиями |
| `first_name` | str | |
| `last_name` | str | |
| `specialty` | str | непустая, как у источника (`MasterViewResponse.specialty: str`; #599 сохраняет тип — меняется источник значений, см. §3.5) |
| `avatar_url` | str \| None | фото; единственное nullable-поле схемы — зеркалит staff-контракт |

  Не входят (staff-контракт): `color`, `sort_order`, `archived`, `created_at`, `updated_at`.
- **Порядок закреплён:** `sort_order ASC, first_name ASC, id ASC` — как у staff-списка.
- **Потолок:** `BARE_LIST_MAX_ROWS` (1000), при превышении 422 (`BareListLimitExceededError`) — как всякий голый список; про цену этого режима для витрины — §5.
- **Запись в `PUBLIC_ROUTES`:** `("GET", "/api/v1/public/masters")`.

### 3.2. `GET /api/v1/public/services`

Голый JSON-массив без параметров (тот же канон).

- **Фильтр серверный (форс, как у #601):** только активные И видимые услуги (`is_active = true` AND `is_public = true`); архивная или скрытая услуга в витрину не попадает.
- **Схема `ServicePublicResponse`** — поля формы записи + поля деталей (транспорт) + `specialty`:

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | str | ключ для сшивки с занятиями |
| `title` | str | |
| `description` | str | непустая, как у источника (колонка NOT NULL, в сиде дефолт `""`); пустая строка = нет описания |
| `image_url` | str | непустая, как у источника (`ServiceBase.image_url: str`); пустая строка = нет картинки |
| `specialty` | str | название направления; сегодня свободный текст, после мерджа #599 — значение справочника (тип не меняется); фильтр по направлению строится группировкой по строке |
| `min_age` | int | детали: возраст от |
| `max_age` | int \| None | детали: возраст до; null = без верхнего предела |
| `tariffs` | `list[ServicePublicTariff]` | `{id, title, price}` — диапазон цен и выбор тарифа при записи; порядок наследует порядок связи ORM, как в staff-контракте (отдельного `order_by` у тарифов нет и там) |
| `materials` | `list[ServicePublicMaterial]` | `{title, description, note}` — «что взять с собой»; порядок `title ASC, id ASC` как в staff-контракте |
| `tags` | `list[str]` | строки-названия, **отсортированы по названию серверно** (прецедент `PhotoPublicResponse`, #493 — `sorted(tag.title)`); сборка — явным маппером элементов, НЕ `model_validate` по ORM-объектам (pydantic не превратит `Tag` в `str` — наивная валидация даёт 500) |

  Не входят (staff-контракт): `duration` (форма берёт длительность из занятия), `record_info`, `created_at`, `updated_at`, `archived`, `is_public`.
- **Загрузка вложений — жадная:** `selectinload`/`joinedload` тарифов, тегов и связей с материалами в view-функции (прецедент `ServiceService.list_all`); наивное копирование вида локаций #601 — у них вложений нет — упадёт под async SQLAlchemy с `MissingGreenlet`.
- **Инвариант вложенных строк:** у тарифов и материалов нет отдельного пути архивации — архивируются только вместе с услугой (сегодня `Tariff.is_active` никто не сбрасывает; если будущая фича заведёт архивацию строки, витрина обязана это учесть — иначе замолча протечёт).
- **Порядок закреплён:** `title ASC, id ASC` — как у staff-списка без явного `sort_by`.
- **Потолок:** тот же `BARE_LIST_MAX_ROWS` (1000) → 422.
- **Запись в `PUBLIC_ROUTES`:** `("GET", "/api/v1/public/services")`.

### 3.3. Гарды bare GET и зеркала контрактов

| Маршрут | Право |
|---|---|
| `GET /api/v1/masters` | `masters:read` |
| `GET /api/v1/services` | `services:read` |
| `GET /api/v1/services/{service_id}` | `services:read` |
| `GET /api/v1/tags` | `tags:read` |
| `GET /api/v1/tags/{tag_id}` | `tags:read` |

Механика — существующая фабрика `require_permission(...)` (депенденси на маршруте), как у `/all`-вариантов этих же роутеров и у locations/activities после #600/#601. У мастера роль имеет все 3 права (`ROLE_PERMISSIONS`), у админа `*` — staff-потребители не меняются. У мастеров витринного by-id нет вообще (роутер не имеет `GET /{id}`) — закрывать нечего.

Из `PUBLIC_ROUTES` (backend/src/auth/public.py) удаляются 5 записей: `GET /masters`, `GET /services`, `GET /services/{id}`, `GET /tags`, `GET /tags/{id}`; добавляются 2 из §3.1/§3.2. Итог: allowlist сжимается с 5 словарных записей до 2 витринных.

**Зеркала контрактов (обязательные, по прецедентам волны):**
- **Docstring-история `public.py`** пополняется строкой про #606.
- **Дом-правило `docs/domain-rules/auth.md`** (раздел Public Access) — перечисление анонимных словарей обновляется: masters/services/tags уходят из перечня, добавляются 2 витринных маршрута. Прецеденты: #493 §6.7, #600 (задача 4), #601 — все три волны правили этот раздел явно.
- **Дом-правило `docs/domain-rules/services.md`** — правило видимости зеркалом #601 (см. §3.6). Правки дом-правил точечные: в `tags.md`/`staff.md` публичность словарей не описана. (Заметка о точечном стейджинге чужих правок #551 снята в рев.4: правки #551 уже в HEAD, рабочее дерево дом-правил чистое на 2026-11-14.)
- **Скоуп-контракт мастера** (`backend/tests/test_master_scope_contract.py`, `ALLOWED_UNSCOPED`): добавляются 2 записи `("GET", "/api/v1/public/masters"|"services")` с обоснованием по образцу строки `/public/locations`; у 5 закрываемых словарных записей обновляются обоснования — текст «dictionary read (acting masters, public + masters:read)» и аналогичные теряют слово `public` (маршруты перестают быть публичными). Попутно в том же файле чистятся 2 записи ЛОКАЦИЙ (`GET /locations`, `GET /locations/{id}`), чьё обоснование «public + locations:read» протухло ещё с #601 — тот же класс устаревания. Без новых записей пин-тест скоуп-контракта красный — оба новых маршрута немонтированного модуля обязаны иметь явную запись («unscoped by design»).
- **Матрица публичных GET** (`_PUBLIC_GETS` в `backend/tests/test_auth_guards.py`) — тест «публичная поверхность цела» параметризован этим списком; все три волны-прецедента правили его. Минус 3 словарных записи (`/masters`, `/services`, `/tags`), плюс 2 витринных.

### 3.4. api-client и веб-форма

- **api-client** (`packages/api-client`): 2 метода по прецеденту `getPublicPhotos`/`getPublicLocations`:
  - `getPublicMasters(): Promise<MasterPublicResponse[]>` — голый массив;
  - `getPublicServices(): Promise<ServicePublicResponse[]>` — голый массив.
  Схемы `MasterPublicResponse`, `ServicePublicResponse` (+ вложенные `ServicePublicTariff`, `ServicePublicMaterial`) зеркалят §3.1/§3.2. Оба метода получают юнит-тесты URL+схема по прецеденту `getPublicLocations`/`getPublicPhotos` (`endpoints.test.ts`).
- **Смена конверта — часть миграции, не деталь реализации.** Сегодня хук разбирает постраничный конверт: `useSchedule.ts` читает `(rawData[i] as PaginatedResponse<...>)?.items ?? []` для услуг и мастеров. Витринные методы возвращают голый массив (как `getPublicLocations`) — хук переходит на прямое значение, а сигнатуры `buildWebSchedule`/маппера меняют типы параметров `ServiceResponse`/`MasterViewResponse` → `ServicePublicResponse`/`MasterPublicResponse` (поля совпадают, типы — нет: staff-схемы несут лишние поля). Буквальная замена двух имён функций без правки конверта даст `.items` от массива → `undefined` → пустой справочник → молча выпавшие карточки.
- **`buildSchedule.ts`:** теги услуги теперь строки — `buildTagSet` принимает `string[]` (сегодня `{title}[]`). Поля деталей (`description`, возрасты, `specialty`) маппер не читает — транспорт насквозь.
- **Staff-методы:** `getServices` остаётся (его читают `ServicesContext` и `PhotoModal`, оба под аутентифицированной сессией с правом). **`getMasters` удаляется из api-client в этой же волне.** Потребители метода после миграции формы — только тесты, и они мигрируют вместе с удалением (находки панели рев.3):
  - `frontend/admin/__tests__/useReactQueryHooks.test.tsx` и `useRecordData.test.tsx` — импортируют `getMasters` напрямую и ассертят «не вызывался» (моки `vi.mock` переживут, typecheck упадёт на импорт несуществующего экспорта) — ассерты и моки переводятся на `getAllMasters`;
  - `packages/api-client/src/endpoints.test.ts` — снимается describe-блок `getMasters` с матрицей вызовов (~10);
  - админка мастеров читает через `getAllMasters` → `/masters/all` — не затрагивается.
  Бэкенд-маршрут `GET /masters` (постраничный staff-список) остаётся жить под гардом.
- **Юнит-тесты веба мигрируются вместе с хуком** (иначе падают по имени мока): `useSchedule.test.tsx` и `useLocations.test.tsx` — мок-фабрика `@memo/api-client` дополняется `getPublicMasters`/`getPublicServices` (заглушки — голые массивы вместо конвертов); `buildSchedule.test.ts` — фикстуры перетипизируются с staff-схем на витринные, теги строками.

### 3.5. Порядок с родственными задачами

- **#584 (In IMPL, /my-волна):** общий файл `public.py` и общий пин-тест `test_equals_spec_allowlist_exactly` (#584 удаляет `/auth/me`, #606 — 5 словарных записей). Порядок мерджей не ограничен: второй по счёту ребейзит конфликт в одном файле и в одном тесте (правило зафиксировано обеими спеками).
- **#599 (In IMPL, справочник направлений) — пересечение плотнее, чем «независимые колонки»:** ревизия #599 **удаляет** текстовые колонки `services.specialty` и `masters.specialty`, заменяя их связями (`specialty_id` FK / M2M у мастеров). Поле `specialty: str` в ответах #599 сохраняет (склейка названий), так что витринные КОНТРАКТЫ §3.1/§3.2 не меняются — но оба новых витринных view читают `specialty` как атрибут модели, и после #599 атрибут становится связью: нужен жадный груз и пересборка значения. **Владелец адаптации — второй по счёту мерджер** (у #599 свой N+1-гвард): если первым идёт #599, адаптацию делает IMPL #606 сразу; если первым #606 — #599 ребейзится и доезжает груз в витринных view. Дополнительно: обе задачи добавляют alembic-ревизию на одну голову (`c1d3e5f7a9b1`) — второй мерджер перекидывает `down_revision` (иначе две головы, `upgrade head` падает).
- **#609 (rate limiting):** будущая задача поверх всех `/public/*`; туда же кандидаты из §2 (Cache-Control, /docs, формулировка про 422) и наблюдение про ленту расписания из §8.

### 3.6. Флаг видимости услуги `is_public` — зеркало #601

Механика переносится с локаций (#601, спека `2026-11-12-locations-web-visibility-601-design.md`) построчно, включая ловушки, которые та волна закрывала явно:

- **Модель и миграция:** колонка `services.is_public` boolean NOT NULL, server_default `true` (прецедент миграции `c1d3e5f7a9b1_add_is_public_to_locations`). Существующие строки получают `true` — поведение не меняется до снятия флага.
- **Staff-контракт — канон #601, без вариаций (блокер панели рев.3 закрыт именно так):**
  - `ServiceBase.is_public: bool = True` — наследуется `ServiceResponse`/`ServiceCreate`/`ServiceUpdate`; `null` для bool невозможен (422 схемой);
  - PUT — full-replace: **модалка услуги НЕСЁТ текущее значение флага в полезной нагрузке** (явный перечень полей модалки дополняется `is_public` — канон #601 «полезная нагрузка модалки несёт флаг»); отсутствие поля в PUT означает дефолт `true` — семантики «отсутствует → сохранить» в PUT НЕ существует (сервисный слой применяет все ключи подряд — `setattr` без фильтрации None);
  - `ServicePatch.is_public: bool | None = None` — ОТДЕЛЬНОЙ строкой (патч не наследует базу, как `LocationPatch` в #601): отсутствует/null → сохранить; `is_public` добавляется в `NOT_NULL_FIELDS` сервиса (зеркало `location.py`).
- **Админ-UI:** переключатель «Видно клиентам» в модалке услуги (field-config по образцу локаций) + бейдж «Не в web» у скрытой в таблице услуг. Скрытая услуга в админке полностью рабочая: сетка, формы, создание занятий за неё — донор обратного правила `schedule-archived-visibility`.
- **Витрина услуг (§3.2):** форсированный `is_public = true` в фильтре.
- **Витрина занятий (`list_public_activities_view`):** предикат дополняется join-терминами `Service.is_active = true AND Service.is_public = true` — занятие архивной ИЛИ скрытой услуги не покидает сервер (join 1:1 по PK, дублей не даёт). Примечание к дельте: сегодня занятия архивных услуг в витрине показываются — этот термин чинит тот же класс утечки, что #601 починил для локаций (см. §5).
- **Витрина фото (`list_public_photos_view`) — поверхность, которой у локаций не было (находка панели рев.3, два ревьювера):** предикат галереи дополняется терминами видимости услуги-владельца (`Service.is_active = true AND Service.is_public = true`) — как для общего фида, так и для сужения `?service_id=` (прямые фото услуги и фото её занятий; зонду скрытого id — пустой ответ, паритет с несуществующим). Без этого переключатель недодаёт обещанное: фото скрытой услуги остаются на сайте.
- **Бронь по прямому id:** предикат существования занятия в брони (расширялся #600 → #601) получает те же термины услуги — бронь занятия скрытой/архивной услуги → **404 с паритетом тела** (ответ неотличим от несуществующего id), запись не создаётся. Гость без сессии до предиката не доходит — 401 (не меняется).
- **Аудит (находка панели рев.3):** журнал услуг строится явным списком `_SERVICE_MARK_FIELDS`, а не авто-сбором репозитория (как у локаций) — `is_public` ДОБАВЛЯЕТСЯ в список: переключение «скрыл/показал» пишет строку аудита, а PUT, меняющий только флаг, больше не даёт пустой диф (сегодня пустой диф пропускается целиком — действие стало бы невидимым).
- **Копирование недели (`copy_week`) — сознательное допущение:** занятия скрытой услуги продолжают копироваться (админ-инструмент, фильтр копирования не трогаем) — на сайт их не пускают join-термины витрины.
- **Сид:** `is_public` в YAML-модели сида услуг (`reference.py`), маппинг «да/нет/пусто», контрольный `--check`; фикстуры несут обе полярности (минимум одна `is_public: false` — иначе молчаливый пропуск колонки остаётся зелёным).
- **Дом-правило `services.md`:** строка-зеркало правила локаций — «`is_public = false` скрывает услугу только с сайта: её нет в публичном справочнике, её занятия исключены из витрины серверно, её фото не отдаются галереей, бронь по прямому id → 404. В админе услуга полностью рабочая. Скрытие с сайта ≠ архив».

## 5. Behavioral Delta

- **Аноним:** до — `GET /masters`, `/services`, `/services/{id}`, `/tags`, `/tags/{id}` отдают полные админ-контракты; после — 401. Витринная замена: `/public/masters`, `/public/services` (урезанные поля). Внешних анонимных потребителей вне репо не найдено (разведка).
- **Клиент (сессионная кука клиента):** то же 401 на 5 закрываемых маршрутах — у клиентской сессии нет staff-прав (проверяется явно, шаблон #601).
- **Гость сайта, вид:** на текущих данных карточки те же. **Объём выборки меняется честно, а не «данные те же»:** сегодня форма вызывает словарные методы без параметров и сервер отдаёт первую страницу с дефолтом `per_page=20` — при справочнике длиннее 20 строк сайт молча терял хвост (маппер выбрасывает занятия без услуги/мастера); после миграции витрина получает полный список до `BARE_LIST_MAX_ROWS` (1000). Это исправление скрытой обрезки, дельта проявится только когда справочники перерастут 20 записей (на сид-данных 7 услуг — незаметно).
- **Гость сайта, отказ витрины:** потолок 1000 становится достижимым для анонима — при >1000 активных услуг/мастеров `/public/*` ответит 422; ошибку хук выносит наружу (оверлей записи показывает статус ошибки), но сетка расписания остаётся пустой без диагностики. Известный и принятый режим (канон голых списков ADR-015/#601); кандидат на мягкий потолок/пагинацию — #609.
- **Скрытие услуги (новое, решение пользователя):** администратор получает способ убрать услугу с сайта, не трогая её в админке. До — любая активная услуга была видна сайту целиком; после — скрытая исчезает из справочника, расписания и фото-галереи (включая зонд по id), её занятие нельзя забронить по прямой ссылке (404), переключение оставляет след в журнале аудита. Попутно чинится та же утечка, что #601 закрыл для локаций: занятия архивных услуг сегодня показываются в витрине — после join-терминов не покидают сервер.
- **Сотрудник:** без изменений — те же маршруты, те же контракты (+1 читаемое/записываемое поле `is_public` у услуги); гард пропускает по правам роли.
- **Админ-фронтенд:** + переключатель «Видно клиентам» и бейдж «Не в web» у услуг; остальное без изменений.

## 8. Открытые допущения

- Теги: только гарды, без `/public/tags` — закреплено (анонимный потребитель отсутствует; сужение волны относительно ADR-15 clause 4 помечено в §2).
- `specialty` в витринном мастере: прямое требование задачи («имя, специальность, фото»); в витринной услуге — решение пользователя под будущий фильтр по направлению (группировка по строке; id-идентификатор не добавляем до серверного фильтра).
- Поля деталей (`description`, `min_age`, `max_age`) — транспорт без показа (решение пользователя, вариант 2): текущий UI (карточка + оверлей бронирования) не меняется, отображение появится с экраном деталей.
- Вне репо анонимных потребителей 5 закрываемых маршрутов нет — допущение разведки.
- Удаление `getMasters` из api-client — находка панели; бэкенд-маршрут остаётся. Потребители-тесты мигрируют (§3.4). Внешний потребитель метода — откат одной строкой.
- Фото ЛОКАЦИЙ не фильтруются по видимости локации (дыра, унаследованная из #601; для услуг закрываем в §3.6) — кандидат в отдельную задачу; в этой волне не трогаем.
- Лента расписания ограничена со стороны хука `per_page: 100` на 30-дневное окно — тот же класс тихой обрезки, что §5 чинит для словарей; вне волны, кандидат в #609.
- Занятия скрытой услуги продолжают копироваться копированием недели — сознательное допущение (§3.6), фильтр копирования не чинить.
- 422-потолок витрины, Cache-Control, `/docs` — осознанно вне волны, кандидаты в #609 (§2, §5).
