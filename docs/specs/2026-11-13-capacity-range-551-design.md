# Спека #551: диапазон вместимости — занятия 0–99 (0 = «запись закрыта»), локации 1–99

- Дата: 2026-11-13 · Issue: #551 · Родитель: #280 (дочернее) · Приложение: app:core (+admin/web формы)
- Статус: на гейте B (рев.3 — симметрия 0–99 для обеих сущностей, решение пользователя; рев.2 — все находки панели внесены; панель 551-2026-11-13: первый прогон в контейнере 2/7, хост-фолбэк 5/5)

## Решения дизайн-фазы (Gate A, решение пользователя 2026-11-13)

1. **Вместимость занятия легальна в диапазоне 0–99.** 0 — осознанная семантика «запись закрыта», а не мусор: защита мест и так не пускает никого на занятие с вместимостью 0 (409 `ACTIVITY_AT_CAPACITY`). Сценарий «временная приостановка записи» закрывается нулём без отдельного механизма.
2. **Вместимость локации легальна в диапазоне 0–99** (рев.3, решение пользователя — симметрия с занятиями). 0 у локации означает «вместимость не задана» и не имеет операционного эффекта: бронирование идёт по занятиям, скрытие с сайта и из админа — отдельные механизмы (`is_public`, архив). Опасность «тихого растиражированного закрытого занятия» закрыта НЕ диапазоном, а правилами формы (см. US-6): ни автозаполнение, ни мультисоздание не копируют 0 в новые занятия молча. Прежний верхний предел 500 отменён.
3. **Валидация только на эндпоинтах** (Pydantic-схемы записи → 422 вне диапазона). Ограничение уровня БД (CHECK) сознательно не строится — решение пользователя («просто фильтрация на эндпоинтах»). Единственный штатный путь записи мимо схем — недельное копирование (`copy-week`, прямой ORM-вставкой по канону #242): оно клонирует существующие строки как есть, то есть значения наследуются от источника, который при создании прошёл валидацию эндпоинта (новых вне-диапазонных значений путь не создаёт). Сид и e2e-фикстуры пишут напрямую, их значения внутри диапазона.
4. **Миграции данных нет.** Исторические нули легальны у обеих сущностей (у занятий — «закрытые» записи, у локаций — «не задана»). Значений вне диапазонов в репозиторных данных нет: демо-сид создаёт 10 занятий вместимостью 4–10 (`backend/src/seed/seed.py:171,253,514`), локации сида и предзагрузки прода — 8/10/12 (`seed.py:372-376`, `backend/seed-data/locations.yaml`). Живая прод-база из репозитория недоказуема; так как границы кладутся только на схемы записи (см. техдизайн), легаси-значения не ломают чтение — перед выкатом достаточно информационной проверки (см. бэкенд). Легаси-локация с 0 полностью редактируема (0 проходит валидацию как «не задана»); создание занятия с ней блокируется правилом «нет вместимости» (см. US-6).
5. **Это разворот решения #280 от 2026-10-23** («нулевой вместимости по домену не существует; у локаций 1–500»): 0 теперь легален у обеих сущностей (у занятий — состояние «закрыто», у локаций — «не задана»). Инвариант #280 «пустое поле никогда не отправляет 0» сохраняется полностью — различаем «не решил» (пустое → блок) и «решил закрыть» (явно вписанный 0 → проходит).
6. Явный переключатель «запись закрыта» (сохранение прежней вместимости при закрытии) **сознательно не строится** — гипотетический сценарий; если появится, 0 остаётся дешёвым носителем семантики, а переключатель добавляется отдельной задачей.

## Отклонения от текста issue (проверено скаутом по живому дереву)

- Issue предлагал валидацию «≥ 1» — заменено решением Gate A: занятия 0–99, локации 1–99 (вместо прежних 1–500 у локаций).
- «Пересчитать исторические нули из `defaultCapacity` локации» — снято: пересчёт не нужен, нули легальны; и `defaultCapacity` — это псевдоним фронта для того же поля `capacity` локации, отдельного поля в бэкенде нет.
- «Источник нулей во фронте закрыт» — уточнение: одиночное создание закрыто гейтом ≥ 1; в мультисоздании (#595) для локации без вместимости полезная нагрузка по-прежнему содержит 0 — после этой спеки такие нули легальны («закрыто»), а валидная локация (1–99) копируется как раньше.
- Заявление «в базе могут лежать занятия с capacity=0» — правдоподобно, но из репозитория недоказуемо (демо-сид создаёт занятия, но с вместимостью 4–10, нулей не вносит); миграция не требуется, вопрос снят.

## User Scenarios (каждая → E2E-тест)

- **US-1. Админ закрывает запись при создании.** Админ открывает форму создания занятия, вписывает вместимость 0, нажимает «Создать» — занятие создаётся; на карточке занятия в сетке вместо счётчика «N/M» отображается «Запись закрыта · N» (число записей видно); клиент на web не может записаться (409 «мест нет»). → admin e2e (создание с 0) + web e2e (попытка записи на закрытое занятие).
- **US-2. Админ снова открывает запись.** Правка занятия с вместимостью 0: вписывает 12 — мгновенный патч уходит, карточка показывает «0/12». Существующие записи сохраняются. → admin e2e (правка 0 → 12).
- **US-3. Пустое поле никогда не отправляет 0.** Создание: пустая вместимость блокирует «Создать». Правка: очистка поля не отправляет патч и не записывает 0 в состояние поля. → admin e2e (гейт создания) + vitest (тишина патча при правке — слой модуля, в e2e не дублируется).
- **US-4. Границы диапазона занятия.** −1 и 100 отклоняются (сервер 422; форма не отправляет), 0 и 99 принимаются. → pytest (contract) + vitest (форма).
- **US-5. Границы диапазона локации.** 100 отклоняется (форма: «Максимум: 99»; сервер 422), 0 («не задана»), 1 и 99 принимаются. → pytest (contract) + admin e2e (модалка локации).
- **US-6. Копирование вместимости из локаций не создаёт «закрытых» молча.** Мультисоздание (2+ локации): вместимость копируется из локаций с явной вместимостью (1–99); локация с 0 («не задана») блокирует «Создать» с подсказкой «У зала … не задана вместимость». Одиночное создание с локацией без вместимости: поле автозаполняется пустым, «Создать» заблокирован до явного ввода (автоподставленного нуля не существует). → существующий admin e2e multi-location-create (факты с capacity 8) + vitest на одиночный автозаполнен-пустой кейс.

## Behavioral Delta (что меняется для пользователя)

| Сценарий | Было | Стало |
|---|---|---|
| Создание занятия с вместимостью 0 | Невозможно: «Создать» заблокирован | Явно вписанный 0 создаёт «закрытое» занятие (пустое поле по-прежнему блокирует) |
| Автозаполнение при легаси-локации без вместимости (одиночное создание) | В поле подставлялся 0, гейт ≥ 1 блокировал «Создать» | В поле подставляется пустое — блок до явного ввода сохраняется |
| Правка занятия на 0 / из 0 | Значение < 1 молча не применялось | 0 применяется патчем (закрыть/открыть запись); существующие записи занятия сохраняются, новые → 409 |
| Очистка поля при правке | Молча писала 0 в состояние поля (патч не уходил) | Патч не уходит, 0 в состояние не пишется |
| API занятий (create/update/patch), вместимость вне 0–99 | Принималось любое целое | 422 (чтение легаси-строк вне диапазона не ломается — границы только на запись) |
| API локаций (create/update/patch), вместимость вне 0–99 | Принималось любое целое (известный пробел) | 422; 0 легален как «не задана» (чтение легаси-строк не ломается) |
| Форма локации, границы | min 1, max 500 | min 0 («не задана» легальна), max 99 («Минимум: 0» / «Максимум: 99» из конфига поля) |
| Карточка занятия с вместимостью 0 | «N/0», заполнение 0% | «Запись закрыта · N» — число записей остаётся видимым |
| Исторические нули в занятиях | Мусор от старого бага формы | Легальные «закрытые» записи |
| Запись клиента на занятие с 0 | 409 «мест нет» | Без изменений: 409 «мест нет» (= «запись закрыта») |

## Технический дизайн

### Бэкенд

- **Границы кладутся ТОЛЬКО на схемы записи — не на Base** (главная правка рев.2 после панели; 3 рецензента независимо): `ActivityCreate` и `ActivityUpdate` → `capacity: Field(ge=0, le=99)`; `ActivityPatch.capacity` → `Field(default=None, ge=0, le=99)` (действует только при явной передаче); `LocationCreate` и `LocationUpdate` → `Field(ge=0, le=99)` (0 = «не задана»); location-patch — optional-форма того же. Почему не Base: `ActivityResponse(ActivityBase)` (`backend/src/schemas/activity.py:70`) и `LocationResponse(LocationBase)` (`backend/src/schemas/location.py:124`) наследуют те же классы, а роуты ре-валидируют ответы через `response_model` (`backend/src/api/v1/activities.py:92,143,174,228`; `locations.py:80,142`) — граница на Base превратила бы легаси-строку вне диапазона в **500 на каждом чтении** списка/расписания (старый API принимал «любое целое», у старой формы локаций предел был 500 → значения 100–500 в проде исключить нельзя), а правка «открыть форму и починить вместимость» стала бы недостижимой. Чтение остаётся без границ: легаси читается, форма даёт поправить. Явный `capacity: null` в PATCH равен «не указано» (generic-патч пропускает None; поле NOT NULL, очистки нет). Прецеденты формы: `backend/src/schemas/payment.py:15` (`gt=0`) и `:42` (optional-вариант).
- 422 — стандартное поведение FastAPI при ошибке валидации Pydantic; отдельных хендлеров не нужно. Прецедент теста: `backend/tests/test_api_payments.py:180` (`test_totals_over_cap_returns_422`).
- **Гвард записи** `check_activity_capacity` (`backend/src/domain/record_visits.py:97`, математика сравнения `:120-127`; вызовы из `services/visit.py:212` и `usecases/records.py:165,336,425`): при переполнении → 409. С capacity 0 гвард даёт мгновенный 409 любой попытке записи — семантика «запись закрыта» получается без изменений кода гварда; требуется явный тест (сегодня проверен только случай «заполнено до предела», `test_record_visits.py:62`).
- **Записи при закрытии сохраняются:** перевод вместимости в 0 ничего не каскадирует — существующие записи живут, новые бронирования → 409. Занятие может оказаться «переполненным» (occupied > capacity, например 8 записей при capacity 5) — это предсуществующее поведение (правило «capacity ≥ occupied» никогда не enforcement), процент заполнения считается как раньше.
- **Перед выкатом (информационно, не блокер):** одноразовый подсчёт живой прод-базы на значения вне диапазонов (занятия < 0 или > 99; локации < 1 или > 99) — чтобы знать легаси-хвост заранее; с границами только на запись он ничему не мешает.

### Фронт (frontend/admin)

- `app/components/modal/ActivityDetailsModal/ActivityForm.tsx:219-229`: input вместимости `min={1}` → `min={0}`, добавить `max={99}`; идентификаторы и `data-testid` сохраняются (`create-capacity` в создании, `input-capacity` в правке).
- `CreateActivityTab.tsx:125-131` (`canSave`): одиночная ветка `Number(capacity) >= 1` → «явно введено значение 0–99»: `capacity !== '' && Number(capacity) >= 0 && Number(capacity) <= 99` (состояние поля — `number | ''`, пустое блокирует «Создать» как сейчас). Мульти-ветка (`firstWithoutDefault`, блок «У зала … не задана вместимость») без изменений: легаси-локация с 0 по-прежнему блокирует.
- **Автозаполнение при переключении набора локаций — правка рев.2 (BLOCKER панели), обобщено в рев.3:** `applyLocationSet` (`CreateActivityTab.tsx:171-178`) сегодня заполняет поле как `loc?.defaultCapacity ?? 0` — локация с «не заданной» (0) вместимостью подставила бы в поле 0, и новый гейт молча разрешил бы «Создать»: закрытое занятие создалось бы без явного решения админа. Стало: канон #595 «missing OR 0 counts as no default» распространяется на одиночный режим — поле заполняется вместимостью локации только если она ≥ 1, иначе пустым — блок сохраняется до ручного ввода, как требует инвариант #280.
- `SettingsTab.tsx:83-93` (`handleCapacityChange`): патч уходит при явном значении 0–99 (включая 0); пустое поле — патч не уходит и 0 в состояние не пишется (проверять исходную строку на пустоту до `Number()`); значение вне 0–99 — патч не уходит. Молчание при невалидном вводе — осознанное (установленный паттерн мгновенного патча: сегодня значение < 1 тоже молча игнорируется).
- **Легаси-занятие с вместимостью > 99** (старый API принимал любое целое): читается и парсится (границы только на запись), правится по всем полям, кроме вместимости (PATCH несёт только изменённое поле — capacity не трогается); сама вместимость правится только на значение 0–99.
- `app/(main)/locations/components/locationFields.tsx:55`: конфиг поля вместимости `min: 1, max: 500` → `min: 0, max: 99` (сообщения «Минимум: 0» / «Максимум: 99» подставляются автоматически из `LocationModal.tsx:215-219`; 0 — легальное «не задана», сохранение с 0 проходит).
- **Zod api-client — правка рев.2: только write-схемы, read-схемы не трогаем.** `packages/api-client/src/schemas.ts:749` — request-схема локации (`LocationCreateSchema`): `.min(1).max(500)` → `.min(0).max(99)` — паритет с серверным контрактом записи. (Обоснование рев.1 «ответ с capacity 99+ перестал бы парситься» неверно: ответы парсит `LocationResponseSchema` с безграничным `z.number()` — она остаётся без границ, чтобы легаси-строки читались.) Write-схемы занятий (строки 221/384/411/436 — тела create/update/patch) зеркалят сервер: `.min(0).max(99)`. Response-схемы остаются `z.number()` без границ.
- `ActivityCard.tsx:35,220,249`: при `capacity === 0` карточка показывает «Запись закрыта · N» (N = число занятых мест — счётчик сохраняется, админ видит записи закрытого занятия) вместо доли «N/M» и процента заполнения (заполнение не считается).

### Осознанно не строится

- Переключатель «запись закрыта» с памятью о прежней вместимости (решение 6 выше).
- CHECK-констрейнт в БД и миграция данных (решения 3–4).
- Отдельный бейдж «закрыто» в web-расписании для клиента: закрытость выражается существующим поведением записи (409 «мест нет»); если понадобится явная индикация — отдельная задача.
