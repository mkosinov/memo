## 1. Контекст и решение владельца

Прод-данные предзагрузки (справочники студии: локации, услуги, материалы, тарифы, сотрудники, должности, направления) в репо НЕ коммитятся — решение владельца 13.11. Развилка по входу загрузчика решена владельцем: **загрузчик читает CSV напрямую**, промежуточный YAML упраздняется (конвертер CSV→YAML рассмотрен и отклонён: лишний артефакт). Один формат на всём пути: владелец правит CSV (Excel/Google Sheets) → загрузчик вливает его в БД.

Целевой поток:

```
uv run python -m src.seed.reference --csv <file.csv> --check   # проверка без БД
uv run python -m src.seed.reference --csv <file.csv> --dry-run # прогон в откатываемой транзакции, БД не меняется
uv run python -m src.seed.reference --csv <file.csv>           # заливка
```

`--check` и `--dry-run` взаимоисключающие (совместное использование — ошибка argparse, exit 2). Коды выхода: 0 успех, 1 ошибка данных/файла, 2 ошибка вызова (argparse).

## 2. User Scenarios

«Пользователь» фичи — владелец-оператор. Каждому сценарию соответствует интеграционный pytest-тест CLI (бэкенд-утилита без web-UI — канонный для repo аналог E2E, прецедент: спеки #586/#484):

1. **Проверить свой CSV перед заливкой.** Владелец экспортировал лист в CSV, запускает `--check` — зелёная сводка (число сущностей по секциям) без обращения к БД; на кривом файле — ошибка с номером строки, файл не меняется.
2. **Посмотреть, что изменится.** `--dry-run` выполняет все операции в транзакции и откатывает её, печатая итоговую сводку; база не меняется. (Это существующая семантика слоя записи — не пред-прогонка плана.)
3. **Залить справочники в пустую БД прода.** Одна транзакция создаёт всё: направления, локации, услуги (+вложенные материалы/тарифы), сотрудников (+блок master, должности), встроенные должности по фиксированным id; сводка совпадает с ожидаемой.
4. **Перезалить поверх существующих данных.** Повторный прогон идемпотентен: обновления по natural keys (title / first_name+last_name), точная синхронизация наборов связей, ничего не дублируется.
5. **Отклонить битый файл.** Нечисловая цена, неизвестная секция, ссылка на несуществующую услугу/материал/должность/направление — ошибка с номером строки CSV, БД не тронута.
6. **Проверить шаблон из репо.** `--csv backend/seed-data/prod-seed-template.csv --check` зелёный — шаблон всегда валиден как fixture и как инструкция по заполнению.

## 4. Формат CSV (контракт входа)

Эталон — реальный файл владельца (`/Users/mkosinov/dev/prod-seed.csv`, 65 строк; в репо не попадает — см. §5.4 про .gitignore).

### 4.1 Механика файла

- Кодировка UTF-8; BOM допустим и снимается при чтении (`utf-8-sig` принимает и файл с BOM, и без — реальный файл с BOM, экспорт Google Sheets обычно без). Чтение: `csv.reader(..., strict=True, newline='')` — битая кавычка («a,"b"c») → ошибка, а не молчаливая склейка.
- Разделитель `;`; кавычки по RFC 4180 (`"` — внутри поля может быть `;`, пример: `"Мастер; Администратор"`); переводы строк LF или CRLF.
- Файл один; секции идут друг за другом:
  - **маркер-строка секции** — название секции в 1-й колонке, остальные ячейки пустые; непустая хвостовая ячейка в маркер-строке → ошибка с номером строки;
  - следующая строка — шапка секции (1-я колонка пустая, дальше имена колонок);
  - далее строки данных (1-я колонка пустая);
  - полностью пустые строки между секциями пропускаются; хвостовые пустые ячейки шапки игнорируются (в реальном файле есть);
  - **повтор маркера уже встречавшейся секции → ошибка** (двух `locations` не бывает);
  - порядок секций свободный (разбор собирает секции, кросс-валидация идёт после) — парсер не зависит от порядка.
- Номер строки в ошибках/предупреждениях — номер **начала записи** (кавычка может переносить строки внутри поля; `line_num` модуля csv указывает на конец записи — парсер отслеживает начало). Многострочные поля в кавычках допустимы.
- Несуществующий путь/каталог вместо файла, файл без единой секции → внятная ошибка, exit 1.

### 4.3 Групповые правила master_* (секция staff)

- Блок master собирается, если **хотя бы одна** `master_*` колонка непуста; иначе все девять колонок должны быть пусты.
- Частичное заполнение (например `master_color` без `master_specialty`) → **явная ошибка с номером строки** (не молчаливый сброс блока и не сырая pydantic-ошибка).
- Внутри собранного блока: `master_specialty` обязателен (D5 #599 — живой блок несёт ≥1 направление); `master_color` обязателен (`#RRGGBB`); `master_is_active` пустая → `True` (задокументировано в README); `master_tags` — список через `;`, может быть пустым.

### 4.4 Типизация колонок (проверка типов у источника)

- Числовые (`capacity`, `sort_order`, `min_age`, `max_age`, `duration`, `price`) — int; нечисловое значение → ошибка с номером строки (урок 13.11: типы проверяются у источника, не у вывода).
- Пустая числовая колонка: null — **только** там, где поле модели `int | None` (`max_age`, `sort_order`); для `capacity`/`min_age`/`duration`/`price` пустая → ошибка с номером строки.
- Пустая строковая колонка = `""`; для полей модели `str | None` (`description` тарифа, `note` связки) — тоже `""` (нормализация «пустое → NULL» остаётся в слое записи, не меняется).
- Булевы (`is_public`, `master_is_active`) — `True`/`False` без учёта регистра; иное или **пустая** → ошибка с номером строки (исключение — групповое правило §4.3 для `master_is_active` в несобранном блоке). Парсер сам разбирает литералы и передаёт в модели настоящие bool/int — lax-режим pydantic не задействован.
- `audience` — строго `kid`/`adult`/`all`; иное или пустая → ошибка с номером строки.

### 4.5 Потери, шапки и предупреждения

- **Без молчаливых потерь.** Шапка секции проверяется поимённо: **отсутствие обязательной колонки → ошибка** с номером строки; **лишняя колонка (вне контракта) → предупреждение** с перечем «секция + колонка» (правило владельца из issue; типовая причина — опечатка в имени колонки видна в перече). Дубликат имени колонки в шапке → ошибка.
- Строка данных короче или длиннее шапки секции → ошибка с номером строки (молчаливой обрезки нет; типовая причина лишних ячеек — незакавыченное `;` внутри текста).
- Ссылки на названия, отсутствующие в этом же CSV (service_title, material_title, теги) — **ошибка** (существующая кросс-валидация сохраняется и строже nice-to-have из issue о «предупреждении»).

### 4.6 Существующие проверки — сохраняются целиком

Natural keys (title / first_name+last_name), валидации дубликатов, `max_age < min_age`, цвета `#RRGGBB`, точная синхронизация наборов связей, одна транзакция, идемпотентность, встроенные должности по фиксированным id, **ошибка** об архивных сущностях (`_require_active` — прерывает прогон, это не предупреждение). Меняется только текст сообщений: ссылки на «файл YAML» заменяются на номер строки CSV (ассерты тестов на тексты сообщений обновляются; ассерты поведения — нет).

### 4.7 Теги — честная семантика при прогоне с пустыми тегами

Реальный CSV владельца: секции `tags` нет, все тег-колонки пусты. Поведение неизменного слоя записи при прогоне: сущности-теги только добавляются (существующие не удаляются), но тег-связи перечисленных в CSV сущностей синхронизируются точно по колонкам → пустые колонки означают «связи у этих сущностей очищаются». На пустом прода это no-op. Это осознанное поведение текущего слоя (гарантия «слой записи не меняется» из issue); README фиксирует: «наполнять теги — колонками + секцией `tags` одновременно».

### 4.8 Направления — контракт после #599

Модели и применитель (`_apply_specialties`, upsert по `lower(title)`) берутся у #599 как есть — парсер кормит их же данными, что и YAML-загрузчик #599 («#612 меняет только парсер», спека #599 §6):

- секция `specialty` — список названий справочника (§4.2);
- `services.specialty` — название-ссылка, обязательное (услуга без направления недопустима — RESTRICT #599); резолв без учёта регистра; неизвестное название → ошибка с именем значения;
- `staff.master_specialty` — список названий через `;`; D5: живой master-блок с пустым списком → ошибка;
- значения секции upsert-ятся по `lower(title)` — регистр/повторы значений не ломают прогон.
