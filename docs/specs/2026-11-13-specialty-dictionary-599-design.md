# Спека: Справочник направлений (specialty) — отдельная таблица (#599)

Рев. 3 — 2026-11-13, статус: Gate B пройден (решения юзера внесены — §11). Рев.1 выправлена по панели 7 ревьюеров (3 «нужно пересмотреть»: ложная предпосылка про пустую master-секцию; незакрытые архивные услуги в контракте удаления; заголовок без нормализации); рев.3 — решения юзера по четырём допущениям: вкладка «Направления» у услуг вместо отдельной страницы, лимит 100, сортировка «как была», DDL-миграция + одноразовый пересид dev.
`depends-on:` — пусто (открытые #612 и #606 независимы, см. §6 и §10).

## 1. О чём задача, простыми словами

Направление студии («живопись», «керамика») сегодня — свободный текст в двух местах: у услуги одно значение (до 20 символов, обязательное), у сотрудника-мастера — строка через запятую без лимита, обязательная при наличии мастер-секции. Проверяется только длина: «Живопись» и «живопись» для системы — два разных направления, опечатки не ловятся, в админке поле вводится вручную, без выпадающих списков. Направление читают: сортировки таблиц услуг/сотрудников, группировка мастеров в шапке админки, подбор замены архивному мастеру при «копировать прошлую неделю», список направлений в `/my`-профиле мастера. Публичный сайт (web) поле не читает вообще.

Решение: справочник — отдельная таблица «Направления»; услуга ссылается на одну запись (обязательно), сотрудник — на несколько; в админке — выбор из справочника и страница управления справочником. Прод-база пуста, миграции прод-данных не нужны; меняются dev-сид и формат предзагрузки.

## 2. Закреплённые решения

1. **Одна таблица `specialties`**, услуга — FK `specialty_id` (ровно одно, обязательное), сотрудник — M2M `staff_specialties`. Старые текстовые колонки (`services.specialty`, `masters.specialty`) удаляются.
2. **Название нормализуется при записи** (обрезка краёв, схлопывание внутренних пробелов, NFC-нормализация; пустое/пробельное → 422) и хранится нормализованным. **Уникальность без учёта регистра** — функциональный уникальный индекс по `lower(title)`; «Живопись»/«живопись» — одна запись (мотивация задачи). Коллизия → 409 `SPECIALTY_TITLE_TAKEN`, определяется **поимкой IntegrityError** этого индекса (не SELECT-предпроверкой — без гонки).
3. **Управление «Направления» — третья вкладка страницы услуг** (решение юзера 13.11: «в админке поместить в услуги, там где услуги-материалы-направления»): переключатель вида Услуги / Материалы / Направления по образцу материалов (свой URL-state с префиксом, свой провайдер серверной пагинации, монтируется только видимый вид — #349); модалка и механика удаления — по образцу должностей (семейный контракт). Отдельного пункта сайдбара и маршрута нет; вкладка видна при праве `specialties:read` (как «Материалы» при `materials:read`).
4. **Удаление направления** — маршрут по семейному контракту удалений (#324-семья, зеркало позиционного роута); семантика зависимостей не позиционная: ссылки услуг — видимая **блокирующая** (авто-разрешения нет — услуга без направления недопустима; в счётчик входят **все услуги, включая архивные** — превью совпадает с проверкой FK); связки сотрудников — **auto-cascade** по образцу материалов (#207), карточки переживают. Точный контракт — §4.2.
5. **Формат ответов сохраняет строковые поля отображения**: у услуги остаётся `specialty: str` (название) + добавляется `specialty_id`; у мастера-секции остаётся `specialty: str` (названия через «, », по алфавиту) + добавляется `specialty_ids`. Пишут клиенты по id; отображающий код таблиц и шапки не меняется.
6. **Инвариант D5 сохраняется без ослабления**: при наличии мастер-секции направления обязательны (пустой набор → 422 `SPECIALTY_REQUIRED`, как сегодня пустая строка). Правка против рев.1: «секция без направлений» сегодня запрещена — ничего не релаксируем.
7. **Публичного чтения направлений нет** — сущность внутренняя (как Должности/Материалы); публичная выдача и гард-волна словарей — #606 после v1. Web-контракт не меняется (web поле не читает — проверено; единственный web-след — e2e-фикстура, §5).
8. **Лимит названия 100 символов** (как у Должностей); старый лимит 20 умирает вместе с колонкой.
9. **Сортировки сохраняют ключ `specialty`** в whitelist (URL-state совместим). Семантика у сотрудников: по **отображаемой строке направлений** (§4.5). Дефолтный порядок списка сотрудников (`sort_order ASC, first_name ASC, id ASC`) не меняется — решение юзера 13.11 «сортировка как была»; кнопка сортировки по колонке «Направление» остаётся (требование задачи «сортировка должна остаться рабочей») и сортирует по отображаемой строке.

## 4. Контракты

### 4.1. Модель и миграция БД

- Таблица `specialties` (`models/specialty.py`, класс `Specialty`, `AbstractModel` — hard-delete семейство, как Теги/Должности): `title: String(100)`, таймстампы базовой модели.
- Уникальность: **функциональный индекс `UNIQUE (lower(title))`, пишется в миграции вручную** (`op.create_index(..., sa.text("lower(title)"))` — автогенерат выражение-индекс не выносит).
- `services.specialty_id` — FK → `specialties.id`, `nullable=False`, `ondelete=RESTRICT`, **с явным индексом** на колонку (FK не индексируется автоматически; индекс нужен сортировочному JOIN и проверке RESTRICT).
- M2M `staff_specialties` — зеркало `staff_positions`: **составной PK `(staff_id, specialty_id)`**, оба FK `ondelete=CASCADE`, `passive_deletes=True`; **дополнительный индекс по `specialty_id`** (каскад и поиск со стороны справочника; PK покрывает только направление staff→specialty).
- Колонки `services.specialty` и `masters.specialty` дропаются.
- **Миграция — только структура (DDL), без конвертации данных** (решение юзера 13.11: dev-данные один раз пересоздаются хорошим сидом): создаёт `specialties` + оба индекса, `staff_specialties`, добавляет `services.specialty_id` (NOT NULL FK + индекс), дропает старые текстовые колонки. Прод пуст — накат тривиален. На **непустой** dev-базе ADD COLUMN NOT NULL упадёт со штатной ошибкой базы — это ожидаемое поведение: одноразовый пересид dev по канону dev-workflow (пересоздание базы + сид; точную команду фиксирует план).
- **Downgrade**: удаляет новые структуры и возвращает текстовые колонки пустыми (данные не восстанавливаются — dev-only удобство, прод пуст).

### 4.2. API справочника `/api/v1/specialties`

Зеркало `/api/v1/positions` (минимальный справочник) — включая отсутствие собственных фильтров и сортировки:

| Method | Path | Поведение |
|---|---|---|
| GET | `/api/v1/specialties` | Пагинированный список (кирпич #205), **без `sort_by`** — фиксированный порядок `title ASC, id ASC` (как у позиций); `?q=` и своих фильтров нет |
| GET | `/api/v1/specialties/all` | Голый массив, `BARE_LIST_MAX_ROWS = 1000` → 422; источник выпадающих списков |
| POST | `/api/v1/specialties` | Создание (нормализация §2.2); коллизия → 409 `SPECIALTY_TITLE_TAKEN` |
| PATCH | `/api/v1/specialties/{id}` | Переименование; та же нормализация и проверка; переименование в собственный регистровый вариант — успех (своя строка не конфликтует с индексом) |
| DELETE | `/api/v1/specialties/{id}` | Семейный контракт (#324-семья): порядок проверок форма → probe (404) → dry_run/commit. `?dry_run=true` превью / commit `{resolutions, expected}`. Зависимости: **services** — видимая блокирующая (`allowed_actions: []`): занята услугами → 409 `has_dependencies`, узел «Услуги: N», счётчик — **все услуги, включая архивные** (превью совпадает с RESTRICT по всем строкам; авто-разрешения нет); **staff_specialties** — auto-cascade (образец — материалы #207): commit `{"resolutions": {}}`, карточки сотрудников переживают. Свободная запись (нет ни услуг, ни сотрудников) — лист: превью 204, commit `{expected: {}}` |

- Ответы: `SpecialtyView {id, title, created_at, updated_at}` + Create/Update-схемы.
- **Механика 409**: коллизия определяется поимкой `IntegrityError` функционального индекса (inspect constraint + `rollback()`) — SELECT-предпроверка допускается как UX-быстрый путь, но не единственная защита (TOCTOU → 500 недопустим).
- **Гарды** — зеркало позиционного роута поимённо: `_READ_GUARD = require_permission("specialties:read")`, `_WRITE_GUARD` = permission `specialties:write` + `verify_fetch_metadata` (CSRF). Общего router-wide гарда в кодовой базе нет — полагаться на него нельзя.
- Код ошибки `SPECIALTY_TITLE_TAKEN` добавляется в `errors.py` (enum + карта сообщений).

### 4.3. Услуги: запросы и ответы

- `ServiceCreate`: вместо `specialty: str` — `specialty_id: UUID` (обязательное; неизвестный id → 422, явная предвалидация по образцу материалов #223).
- `ServiceUpdate` (PATCH): `specialty_id: UUID | None`; **отсутствует → сохранить текущее; явный `null` → 422** (обнуление невозможно — поле обязательное).
- `ServiceView`: сохраняет `specialty: str` (название из связи, только чтение) + добавляет `specialty_id: UUID`.
- **Без N+1**: списки/`/all`/GET догружают направление одним `joinedload` (many-to-one) — в одном ряду с уже догружаемыми тегами/тарифами/материалами.
- Сервисный слой: `NOT_NULL_FIELDS` в `services/service.py` обновляется на `specialty_id`; отдельная проверка «специальность обязательна» на этом поле больше не нужна (NOT NULL FK).

### 4.4. Сотрудники: master-секция

- Вход (create/PUT/PATCH карточки): `specialty_ids: list[UUID]` — полная замена набора (hard-replace, как `position_ids`); неизвестный id → 422; **дубликаты в списке дедуплицируются**; после дедупа **>50 id → 422** (защита от write amplification).
- **Инвариант D5 (без изменений)**: мастер-секция присутствует ⇒ `specialty_ids` непустой; пустой набор при живой секции → 422 `SPECIALTY_REQUIRED` («Укажите специальность мастера»). Без мастер-секции направлений нет.
- Ответ master-секции: `specialty: str` — названия через «, », **по алфавиту** (было: порядок ввода) + `specialty_ids: list[UUID]`.
- `MasterView.specialty` (только чтение, расписание): та же joined-строка из связей.
- **Без N+1**: список сотрудников догружает связи направлений (`selectinload` — M2M на пагинированном списке).
- Путь записи: `services/master.py` (`_require_section_fields` — проверка непустоты набора вместо непустой строки; strip/CSV-хелперы удаляются) **и `usecases/staff.py`** (`_write_section:129-144` кормит секцию в `upsert_extension`; `:356` читает секцию).
- Фронт: `StaffModal.tsx` (чекбоксы) **и `StaffTable.tsx:145,181`** (сборка payload master-секции) переходят на `specialty_ids`.

### 4.5. Сортировка

- Whitelist-ключи остаются `specialty` у обеих сущностей (URL-state совместим).
- Услуги: ключ — `Specialty.title` через JOIN (семантика прежняя: одно направление).
- Сотрудники: ключ — **та же строка, что видит пользователь**: корреляционный **скалярный подзапрос** `string_agg(title ORDER BY title, ', ')` по связям (одно выражение — и для ответа, и для ORDER BY; НЕ GROUP BY по внешнему запросу — совместимо с `apply_sort`/пагинацией и тайбрейком `id asc`). NULL (нет master-секции) — в конце (`always_nulls_last`), как сегодня. Разметка aggregate-ключа в `SortKeySpec` — новое для реестра сортировок; диалекты PG+SQLite (SQLite ≥3.30 для nulls-политик) — проверка в плане. Запрет локальных резолверов (`_overview.md`) не нарушается: выражение живёт в `domain/sorting.py`.

### 4.6. Прочие читатели направления

- **Группировка мастеров в Topbar** (`groupMastersBySpecialty`): читает ту же joined-строку — поведение без изменений.
- **Копирование недели, ремап архивного мастера** (`services/activity.py`): пересечение наборов направлений по **id связей** вместо нижнерегистрового сравнения CSV. Следствие авто-cascade (удаление направления отвязывает и архивных мастеров): будущие ремапы учитывают только живые связи — раньше текст CSV переживал всё; одна фраза в `activities.md` (§10).
- **`/my`-профиль**: ответ `MyProfileResponse.specialties: list[str] | None` — форма не меняется, список из связей по алфавиту. **`MyProfileUpdate.specialties` остаётся «принимается-но-игнорируется»** (D5, `schemas/my.py:250`) + юнит-тест на это; набор направлений пишут только админские staff-маршруты — мастер не может сам себе менять направления.
- **Аудит** (`events/audit.py`): подписи/снапшоты несут **название вместе с `specialty_id`** — после переименования исторические записи читаются под своим на тот момент названием (id рядом со строкой).

## 6. Сид и предзагрузка прода

- **Dev-сид** (`seed/seed.py`): названия направлений из нынешних литералов становятся записями справочника; услуги и мастера связываются по ним. Данные делаются «один раз хорошими» (решение юзера 13.11): в сид входит ≥3 направлений и минимум один сотрудник с 2+ направлениями, введёнными НЕ по алфавиту — это же различающие данные сценария 2 и тестов сортировки.
- **Предзагрузка** (`reference.py`): новый файл `seed-data/specialties.yaml` (список названий) + `_apply_specialties` — upsert по `lower(title)` (образец `_apply_positions`); `services.yaml`: поле `specialty` остаётся названием-ссылкой; `staff.yaml`: CSV-строка `specialty` заменяется списком `specialties: [названия]`.
- **Резолв названий — без учёта регистра** (по `lower(title)`): «живопись» в YAML находит запись «Живопись»; неизвестное название → ошибка загрузки с именем значения. Старый CSV-ключ `specialty` в `staff.yaml` → **ошибка загрузки** (шаблон обновляется тем же коммитом; тихий игнор маскирует опечатки; политика «игнорировать с предупреждением» остаётся у CSV-секции #612).
- **#612** (загрузчик читает CSV напрямую, YAML упраздняется): не предшественник и не последователь — #599 дополняет текущий YAML-загрузчик одной секцией, #612 переводит весь загрузчик на CSV и переносит секцию. **Стыковка: `_apply_specialties` принимает список названий независимо от формата файла** — #612 меняет только парсер. Объём двойной работы — одна функция-применитель.
- **#575** (прод-данные): названия направлений в CSV юзера конвертируются в ссылки при заливке — как заявлено в задаче, данные не пропадают.

## 8. Behavioral Delta (до → после)

- **Услуга, поле «Направление»**: ручной текст ≤20 символов → выбор одного направления из справочника (обязательное).
- **Сотрудник, направления**: CSV-строка в порядке ввода, без лимита → мультивыбор из справочника; в ответе названия по алфавиту; обязательность при живой мастер-секции — **как и было** (D5 сохранён).
- **Дубли и регистр**: «Живопись» и «живопись» — разные направления → одна запись (уникальность без учёта регистра + нормализация пробелов); опечатка-регистр больше не создаёт фантом.
- **Админка**: не было управления направлением → страница «Направления» (создать/переименовать/удалить; занятое услугами — включая архивные — не удаляется: 409 с деревом; связки сотрудников отвязываются автоматически).
- **Лимит названия**: 20 (услуги) → 100 (справочник).
- **Сортировка сотрудников по направлению**: по всей CSV-строке в порядке ввода → по отображаемой алфавитной строке направлений (без master-секции — в конце, как было). Услуги — без изменений.
- **Группировка в Topbar, ремап архивного мастера при копировании недели, `/my`-профиль, аудит**: пользовательски тот же результат; механизм — справочник. Побочное следствие удаления направления: будущие ремапы копирования недели видят только живые связи (раньше текст CSV переживал всё).
- **Web и публичные контракты**: без изменений; публичного чтения направлений нет (решит #606). Мастер по-прежнему не может менять свои направления через `/my`.

## 9. Тесты

- **Юнит-бэкенд, справочник**: нормализация названия (trim/пробелы/NFC; пустое → 422); 409 через IntegrityError-путь (и UX-предпроверка); переименование в свой регистровый вариант — успех; гарды: чтение без `specialties:read` — 403, запись без `specialties:write`/CSRF — отказ.
- **Юнит-бэкенд, delete-family**: занято активной услугой → 409 с деревом; занято **только архивной** услугой → 409 (счётчик всех услуг); только сотрудники → commit `{"resolutions": {}}` → отвязка + 204; лист → 204.
- **Юнит-бэкенд, услуги**: неизвестный `specialty_id` → 422; явный `null` в PATCH → 422; **PATCH без поля — направление сохраняется**; N+1-гвард (число запросов на списке не растёт с числом строк).
- **Юнит-бэкенд, master-секция**: D5 — секция без `specialty_ids` → 422 `SPECIALTY_REQUIRED`; неизвестный id → 422; дедуп дубликатов; >50 → 422; hard-replace набора; N+1-гвард selectinload.
- **Юнит-бэкенд, сортировка**: различающие данные — сотрудник A: ввод «Керамика», «Живопись» → ответ `specialty = "Живопись, Керамика"` (не порядок ввода); сотрудник B без master-секции — при сортировке asc B в конце, при desc тоже в конце (`always_nulls_last`); услуги — сортировка по названию направления.
- **Юнит-бэкенд, прочее**: ремап копирования недели — пересечение по id (данные: пересекающиеся связи → ремап; непересекающиеся → skip); `MyProfileUpdate.specialties` — принимается и **игнорируется** (набор не меняется); аудит-снапшот несёт `specialty_id`; `/my`-ответ — названия из связей по алфавиту.
- **Юнит-бэкенд, сид/загрузчик**: `_apply_specialties` upsert по регистру; резолв ссылки без учёта регистра; неизвестное название → ошибка с именем значения; старый ключ `specialty` в `staff.yaml` → ошибка.
- **Миграция**: на пустой базе — up создаёт структуру (таблицы, оба индекса, NOT NULL), down чист; на непустой dev-базе — штатное падение NOT NULL (документированный одноразовый пересид, §4.1).
- **Юнит-фронт/api-client**: обновлённые схемы (дельта контракта), `schemas.test.ts`/`endpoints.test.ts`; `packages/domain` — без правок (строка сохраняется).
- **E2E**: таблица §7.

## 10. Дом-правила (одним коммитом со спекой)

- **Новый файл `docs/domain-rules/specialties.md`** — Fields/Invariants (нормализация, lower-уникальность, D5-связка, «нет публичного чтения до #606») / API (без sort_by, гарды поимённо) / List contract / Delete semantics (§4.2: services — блокирующая с подсчётом всех услуг, staff_specialties — auto-cascade по образцу материалов) / Relationships (сортировка по отображаемой строке, ремап по id, сид по lower).
- `services.md`: строка поля `specialty` → `specialty_id` (FK, справочник); лимит 20 упразднён.
- `staff.md`: master-секция — `specialty` CSV → M2M `staff_specialties` (вход `specialty_ids`, ответ joined-строка по алфавиту; **инвариант непустоты при живой секции сохраняется**); сортировочная строка — «по отображаемой строке направлений».
- `activities.md` (copy-week): пересечение направлений — по id связей; удаление направления сужает будущие ремапы (связи архивных мастеров отвязываются каскадом).
- `_overview.md`: строка Master («specialties M2M»), новая строка Specialty, сортировочный канон — упоминание aggregate-ключа (скалярный подзапрос) как допустимого выражения в `SortKeySpec`.

## 11. Решения гейта B (13.11, юзер — зафиксировано)

1. **Управление направлением** — не отдельная страница/пункт сайдбара, а **третья вкладка страницы услуг** рядом с «Материалами». Внесено в §2.3, §5, §7, VC.
2. **Лимит названия 100** — принят (§2.8).
3. **Сортировка сотрудников — «как была»**: дефолтный порядок списка (`sort_order`) не меняется; кнопка сортировки по колонке «Направление» остаётся (требование задачи) и сортирует по отображаемой строке направлений. Внесено в §2.9, §4.5.
4. **Миграция — только структура (DDL)**; dev-данные один раз пересоздаются хорошим сидом (без конвертации на месте). Внесено в §4.1, §6, §9.
