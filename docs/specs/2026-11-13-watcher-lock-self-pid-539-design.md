## 1. Контекст и механизм дефекта

Вотчер авто-реализации — фоновый скрипт в контейнере opencode: каждые 180 с сканирует доску, подбирает следующую карточку `Ready to IMPL` и запускает manager-сессию; он же ведёт reconcile, janitor и hang-check. При его молчаливой смерти весь IMPL-конвейер стоит: карточки уходят в мёртвую очередь без каких-либо сообщений.

Механика дефекта:

- Лок `/tmp/auto-impl-watch.lock` хранит pid процесса-вотчера (`auto_impl_watch.sh:105`). `/tmp` контейнера переживает рестарт, pid-namespace при рестарте создаётся заново.
- Цепочка загрузки контейнера детерминирована: boot-дети получают одни и те же маленькие номера (в обоих инцидентах вотчер получил pid 10).
- Страж затухшего лока (`:98-104`, усилен 2026-10-04): лок считается живым, если pid жив (`kill -0`) И `/proc/<pid>/cmdline` содержит ровно путь скрипта вотчера (`grep -Fxq` построчно; строка сравнения — жёстко зашитый канонический путь `$REPO/.opencode/scripts/auto_impl_watch.sh`, не путь фактического запуска).
- Свежий экземпляр проверяет этим **сам себя**: его pid совпал с записанным в локе прошлой эпохой, командная строка совпадает по определению → «watcher already running (pid N)» → `exit 1`.
- Выход происходит **до** записи лока и установки ловушки очистки (`:105-106`) — затухший лок не перезаписывается и ловит каждый следующий рестарт.
- Инциденты: 22.10 21:55 (~3 ч тишины доски) и 13.11 01:11 (7 ч, 01:11 → ручной перезапуск 08:23). Оба — самосовпадение: живой двойник сканировал бы доску, а доска молчала; проверявший экземпляр сам и был pid 10.
- Лог: `/root/.local/state/opencode/auto-impl-watch.log`. Скрипт стартует с `set -uo pipefail` (без `-e`).

## 2. Выбранный концепт «А»: самоопределение по pid (Gate A 2026-11-13)

Условие «лок жив» дополняется проверкой **чужести** pid: лок считается живым только если `lock_pid != $$`.

- `lock_pid == $$` — маркер прошлой эпохи: свой pid в локе мог написать только предыдущий экземпляр с тем же номером (текущий ещё ничего не писал). Проверка проваливается → поток падает в существующую ветку перезаписи (`echo $$ > LOCK` + ловушка) → вотчер продолжает работу. При самосовпадении штатный путь пишет в лог отличимую строку (например `stale lock replaced (self-match pid N)`) — класс инцидента #539 становится видимым в разборах.
- `lock_pid != $$` и все признаки живого вотчера — это **настоящий второй вотчер**: отказ сохраняется как сегодня (штатный путь: сообщение + `exit 1`), чужой живой лок не трогается.
- Безопасность перезаписи при самосовпадении: живой процесс с командной строкой ровно канонического пути вотчера — это вотчер; если это я сам, двойника нет, перезаписывать лок безопасно.
- Страж выполняется на верхнем уровне скрипта (не в подоболочке): `$$` в bash — pid верхнего процесса, и только там правило «свой pid = прошлой эпохи» корректно. Не переносить в функции, вызываемые из подоболочек.
- Содержимое лока валидируется как число (`^[0-9]+$`) до `kill -0` и сравнений; пустое/мусорное содержимое → ветка затухшего лока (детерминированно).
- Ловушка очистки (`trap rm -f EXIT`) **не переносится** до стража: перенос сделал бы отказ «уже запущен» удаляющим чужой **живой** лок — открылась бы гонка параллельных вотчеров. Затухший лок при самосовпадении чистится сам: провал проверки падает в ветку перезаписи, где стоят и запись, и ловушка.

## 3. Сознательно НЕ строим

- **`boot_id + pid` в локе** (предложение текста задачи) — снято с доказательством 2026-11-13: одноразовый контейнер из того же образа показал `boot_id`, идентичный контейнеру opencode (`4de8c7ce-2f75-4efb-9236-7e0e6cfe3a4c`, ядро linuxkit 7.0.14). boot_id принадлежит виртуальной машине Docker и меняется только с её перезагрузкой; при рестарте контейнера он не меняется, и вариант деградирует до сегодняшнего поведения — оба инцидента повторились бы.
- **Паспорт инкарнации (`pid + starttime + boot_id`)** — machinery для недостижимых здесь сценариев. Дополнение рев.2: командная строка процесса — не токен идентичности против противника (подделывается `exec -a`/`prctl`), но модель угроз здесь — одиночный root-контейнер без недоверенных процессов; спуфинг не входит в модель угроз, и канонический путь в `cmdline` достаточно отличает «вотчер» от «не-вотчер».
- **Перевод лока на `flock`** (канонический примитив для single-instance-скриптов; в репо есть прецеденты: `scripts/lib/test-lock.sh`, `flock -w 2400 9` в `panel_review.sh`; в контейнере flock есть, util-linux 2.38.1). Отвергнут для **этого** скрипта: вотчер порождает долгоживущие дети (`opencode run` manager-сессии живут часами), которые унаследовали бы fd лока и держали бы блокировку после смерти вотчера до своего завершения — новый экземпляр не смог бы стартовать, и мы получили бы тот же класс молчаливого простоя, который чиним. Обход (закрытие fd в каждом месте спавна) множит поверхности отказа. Flock остаётся каноном для будущих скриптов без долгоживущих детей.
- **Супервизор/обёртка авторестарта** — против конвенции «вотчеры без супервизоров».
- **Атомарность двойного одновременного старта** (гонка «оба прочитали пустой лок → оба стартовали») — существующее ограничение сегодняшнего кода; фикс его не расширяет и не сужает. Вне скоупа.
- **Smoke-тест штатного (флагless) пути в живом контейнере** — отвергнут: вход в цикл = скан и захват доски (тестовый экземпляр может украсть готовую карточку `Ready to IMPL`), а переключение `auto-impl.enabled` для холостого хода гоняется с живым вотчером за общее состояние. Изолированный одноразовый контейнер с заглушкой репозитория — непропорциональный харнесс для однострочного условия. Штатный путь прикрывается эксплуатационно (§6.5).

## 4. Behavioral Delta

| Сценарий | До | После |
|---|---|---|
| Рестарт контейнера (stop/start) | вотчер выходит с «already running (pid N)» по самосовпадению; доска молчит до ручного перезапуска (факты: 3 ч и 7 ч); инцидент невидим в логе | вотчер распознаёт свой pid в локе как маркер прошлой эпохи, пишет отличимую строку `stale lock replaced (self-match pid N)`, перезаписывает лок и входит в цикл; доска сканируется с первого интервала |
| Ручной запуск второго вотчера при живом первом | «already running (pid N)», выход | без изменений: отказ, чужой живой лок не тронут |
| Затухший лок с мёртвым/посторонним/мусорным pid | перезапись и старт (мусорное содержимое — по факту того же кода, без явной валидации) | без изменений по исходу; содержимое явно валидируется как число |
| Лок отсутствует | обычный старт | без изменений |

## 5. User Scenarios

Спека fast-track: E2E-слоя нет, каждый сценарий закреплён за механической проверкой из §6.4/§7.

- **S1. Рестарт контейнера.** Оператор перезапускает контейнер opencode; после старта вотчер сам поднимается и сканирует доску — карточка, переведённая в `Ready to IMPL`, подхватывается без ручного вмешательства. → T1 (+ RED-демонстрация §7).
- **S2. Ручной двойник.** Оператор стартует второй экземпляр при живом первом; второй отказывается, первый продолжает, лок живого не удалён. → T2.
- **S3. Затухший лок.** После аварийной смерти вотчера лок остался с мёртвым (T3) или посторонним живым (T4) pid; новый экземпляр перезаписывает его и стартует.
- **S4. Чистый старт.** Лока нет (первый запуск / ручная чистка); экземпляр стартует штатно. → T5.

## 6. Изменения

### 6.1 Условие стража (несущая правка, ~2 строки)

В `auto_impl_watch.sh` условие живого лока дополняется `[ "$lock_pid" != "$$" ]` и числовой валидацией содержимого лока (`^[0-9]+$`; не-число → затухший лок). Штатный путь при самосовпадении пишет отличимую строку `stale lock replaced (self-match pid N)` до перезаписи. Английский комментарий стража (`:89-97`) дополняется правилом самосовпадения со ссылками на оба инцидента (#539: 2026-10-22, 2026-11-13) и пометкой «страж — только на верхнем уровне скрипта» (семантика `$$`).

### 6.2 Режим `--check-lock` (шов верификации)

Скрипт принимает флаг `--check-lock`: выполняет **страж целиком** — с перезаписью настроенного `$LOCK` в ветке «старт разрешён» — печатает решение на stdout и выходит. Семантика по пунктам:

- запись идёт **только в переопределённый `AUTO_IMPL_LOCK`** (§6.3); без установленного `AUTO_IMPL_LOCK` режим отказывается работать (защита от мутации прод-лока диагностическим запуском);
- пропускаются: основной цикл, `exec >>"$LOG"`, установка ловушки очистки (иначе выход теста удалил бы проверяемый лок);
- обязательное предусловие `/proc` (`[ -d /proc ]`); без него — явный отказ, а не молчаливое «лок затух»;
- решения печатаются различимыми маркерами: `SELF-MATCH` (свой pid), `STALE` (мёртвый/посторонний/мусорный/отсутствующий), `DUPLICATE` (живой двойник).

Коды возврата режима: `0` — старт разрешён (лок отсутствовал/затух/самосовпадение, лок перезаписан); `3` — живой двойник (отказ, лок нетронут); `2` — неправильное употребление (нет `AUTO_IMPL_LOCK`, нет `/proc`, неизвестный аргумент); `1` — прочая ошибка. Код двойника отделён от кодов ошибок, чтобы сломанный скрипт не мог дать ложный пролёт теста. Штатный путь (без флага) ведёт себя как сегодня, включая ловушку и `exit 1` на двойнике.

### 6.3 Переопределяемый путь (для тестов)

`LOCK` берётся из окружения с текущим значением по умолчанию: `AUTO_IMPL_LOCK` (по умолчанию `/tmp/auto-impl-watch.lock`). Тесты работают на временных путях и физически не могут задеть прод-лок живого вотчера. Переопределение `LOG` не вводится: в режиме `--check-lock` лог не пишется, а штатный путь всегда использует прод-лог (мертвая ручка не заводится).

### 6.4 Тест-скрипт `.opencode/scripts/test_auto_impl_watch_lock.sh`

Bash, English-тело, `set -euo pipefail`. Никогда не входит в основной цикл, не трогает прод-пути и **никогда не запускает проверку из канонического пути** (каноническая строка используется только как содержимое `cmdline`-фейков и живёт в страже как зашитая константа). Проверки:

- **T1 (S1, форма инцидента #539):** `AUTO_IMPL_LOCK=$T bash -c 'echo $$ > "$T"; exec bash "$WATCHER" --check-lock'` — `exec` сохраняет pid, поэтому лок содержит pid самого проверявшего с «вотчерской» командной строкой. Ожидание: `rc=0`, stdout-маркер `SELF-MATCH`, лок перезаписан. До фикса этот сценарий даёт `rc=1` — тест красный на старом коде, зелёный на новом.
- **T2 (S2, живой двойник):** пустышка `bash -c 'exec -a "<каноническая строка>" sleep 30' &` (argv[0] подменён на канонический путь → `cmdline` совпадает), её pid в лок; проверяющий запускается **дочерним процессом** (без `exec`, свой `$$`). Ожидание: `rc=3`, содержимое лока не изменилось, пустышка жива на момент ассерта; после ассерта пустышка прибивается. Окно 30 с + проверка живости перед ассертом — чтобы медленный прогон не сделал тест флейковым.
- **T3 (S3a, мёртвый pid):** в локе pid заведомо завершённого короткоживущего процесса → `rc=0`, маркер `STALE`, лок перезаписан.
- **T4 (S3b, посторонний живой pid):** в локе pid оболочки теста (живая, командная строка не вотчер); проверяющий — дочерний процесс (свой `$$`, чтобы исход не спутался с самосовпадением) → `rc=0`, лок перезаписан на pid проверявшего.
- **T5 (S4, лока нет):** → `rc=0`, лок создан.

### 6.5 Эксплуатация после мержа (вне PR)

Подтянуть фикс в клон контейнера (`git -C /root/workspace/memo pull`) и перезапустить вотчер. Остановка живого вотчера — **только по явной команде юзера**, якорным pkill из шапки скрипта (`^…$` обязательны — без них pkill снимает entrypoint-обёртку, инцидент 2026-09-20). Штатный (флагless) путь автотестом не покрыт (§3, §9) — поэтому после перезапуска человек проверяет хвост лога: строка `=== auto-impl watcher start …` и отсутствие «already running». Шапка-usage скрипта (`:12-18`) дополняется флагом `--check-lock` и `AUTO_IMPL_LOCK`.

## 7. Verification (механические проверки, fast-track)

Правило доставки: изменённые файлы доставляются в контейнер `docker cp` **в песочницу** (`/tmp/verify-539/`), никогда не поверх живого канонического файла — bash читает скрипт лениво по fd-офсету, и подмена байт под работающим интерпретатором может рассинхронить его разбор (тот же класс молчаливой смерти, который чиним).

RED-демонстрация (обязательна ДО правки): временная копия старого скрипта с подменёнными путями (sed: `LOCK` и `LOG` → временные) и дописанным `exit 0` сразу после строки ловушки (чтобы не войти в цикл), запуск в форме T1 c `exec -a "<каноническая строка>"` (у старого кода нет проверки чужести — совпадение даёт только cmdline) → ожидание `rc=1` с «already running». GREEN: тот же рецепт на новом коде → `rc=0` + маркер `SELF-MATCH`.

Основной прогон (после правки):

```
docker cp <repo>/.opencode/scripts/{auto_impl_watch.sh,test_auto_impl_watch_lock.sh} opencode:/tmp/verify-539/
docker exec opencode bash -c 'AUTO_IMPL_LOCK=/tmp/verify-539/t.lock; export AUTO_IMPL_LOCK; bash /tmp/verify-539/test_auto_impl_watch_lock.sh'
```

Зачёт: RED показал `rc=1` на старом коде; T1–T5 все зелёные на новом. Без прогона в контейнере фикс не считается верифицированным (на хосте macOS нет `/proc` — проверка принципиально контейнерная).

## 9. Риски и ограничения

- Режим `--check-lock` — новая поверхность скрипта; принято осознанно (сняло бы «проверил код — выглядит верно» вместо реальной механики). Ветка размещается первыми строками скрипта, до `cd`/`mkdir`/редиректа лога; misuse-код `2` не пересекается с кодом двойника `3` и ошибок `1`.
- **Хвост покрытия:** флагless штатный путь автотестами не покрыт — проверяется эксплуатационно при деплое (§6.5, человек и так делает pull+restart с проверкой хвоста лога). Отвергнутые альтернативы — §3.
- Мусорное `AUTO_IMPL_LOCK` в окружении штатного запуска увело бы вотчер на чужой лок (прецедент допустимости env-настроек: `AUTO_IMPL_INTERVAL`). Риск мал в контролируемой среде контейнера; дополнительно режим `--check-lock` без этой переменной запрещён.
- Содержимое лока читается из world-writable `/tmp`: числовая валидация принята; symlink/подмена лока приняты как ограничение (однотенантный root-контейнер, все процессы — свои).
- Командная строка — не токен идентичности против противника; модель угроз — одиночный root-контейнер без недоверенных процессов (§3).
- T2 защищён от флейка окном 30 с и проверкой живости пустышки перед ассертом; отказ громкий (код меняется с 3 на 0), локализуемый.
- Тесты не переписывают живой канонический файл (`docker cp` только в песочницу, §7).
