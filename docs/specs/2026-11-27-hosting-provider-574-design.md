# 574 — VPS-хостинг прода (Selectel): выбор провайдера, создание сервера, домены

Дата: 2026-11-27 (рев.2 после панели) · Задача: #574 (закрывается PR IMPL-этапа) · Милстоун: v1 (релиз 2026-12-01)

## Контекст и цель

Релиз v1 — 2026-12-01. Деплой-стек зафиксирован на Docker Compose (#616, стек в main через PR #629): три контейнера — `edge` (nginx, единственный терминатор TLS + статический экспорт web), `backend` (FastAPI, 1 процесс), `admin` (Next.js standalone); база SQLite на бинд-маунте; образы тянутся из ghcr.io готовыми, на сервере ничего не собирается; наружу публикует только edge (80/443); деплой — из GitHub Actions по SSH (`deploy/deploy.sh <tag>`).

Оставалось выбрать VPS-провайдера в РФ и создать сервер. Владелец уточнил настоящую цель: **сервис должен открываться у клиентов с мобильного во время режимов «белых списков»** (ограничения мобильного интернета, особенно актуально для Сочи).

Исследование (4 разведки, 27.11.2026) установило честный потолок: при **строгом** белом списке малый сервис недостижим при любой конфигурации — оператор фильтрует по связке «IP + имя сайта (SNI)», официальный перечень закрытый (~120 позиций), попадание только через ходатайство федерального ведомства в Минцифры. Поэтому выбор провайдера покупает: (а) максимальный шанс в **мягких** режимах (фильтрация и троттлинг различаются по регионам/операторам), (б) техническую пригодность к возможной будущей заявке в перечень (требования: статический IP /32, все мощности в РФ), (в) устойчивость к обычным сбоям. Частичное прикрытие шатдаунов уже есть бесплатно: вход по звонку (#597) не зависит от мобильного интернета, по Wi-Fi/проводным сетям списков нет.

## Зафиксированные решения

1. **Провайдер: Selectel.** Реестр провайдеров хостинга РКН подтверждён по официальной выгрузке от 30.10.2026 (АО «Селектел»). Сильнейший среди «обычных» VPS сигнал выживания подсетей при белых списках: 3 независимых сообществских источника ([хаб списков](https://github.com/hxehex/russia-mobile-internet-whitelist), ручные сканы MTS, [гид](https://github.com/kort0881/russia-whitelist/blob/main/guides/whitelisted-hosting.md) от 2026-11-19), включая целые подсети /22, проверенные вручную. Лучшая репутация стабильности из финальной тройки. Отклонены: **Timeweb Cloud** (дешевле на несколько сотен ₽/мес, но массовый сетевой сбой 17–18.11.2026, до 700 тыс. сайтов, — попадает точно в окно репетиции и релиза; сигнал выживания средний), **Beget** (восстановление после успешной атаки с уничтожением данных завершилось только 25.11.2026), **RuVDS** (ни одного наблюдения выживания подсетей во всех списках), **Yandex Cloud** (сильнейший сигнал вообще, но ×2–3 к цене и облачное обвес), VK Cloud / cloud.ru / MTS (дороже при слабом или неотделимом сигнале; cloud.ru не найден в выгрузке реестра РКН). **Стартовый режим — тест**: владелец до финального утверждения проверяет достижимость Selectel во время ограничений.
2. **Конфигурация VM:** 2 vCPU, 2 ГБ RAM, 30 ГБ SSD/NVMe, Ubuntu 24.04 LTS, KVM, ЦОД Москва или СПб, **1 выделенный статический публичный IPv4**, плюс 2 ГБ swap-файл (`vm.swappiness=10`) — защита от OOM-kill при пиках деплоя. Старт с 2 ГБ — решение владельца; апгрейд тарифа возможен позже без переезда.
3. **Домены:** канон — `colourmountains.ru`; кириллический **цветныегоры.рф** (punycode `xn--b1acfa3biol7a6ce.xn--p1ai`; регистрация слитного варианта подтверждена whois 27.11.2026) — постоянный редирект `301` на канон; `www.colourmountains.ru` — тоже `301` на канон. `www.цветныегоры.рф` — **вне скоупа** (без DNS-записи и без SAN). Кука сессии остаётся host-only на каноне.
4. **TLS:** **один SAN-сертификат на три имени** — `colourmountains.ru`, `www.colourmountains.ru`, `xn--b1acfa3biol7a6ce.xn--p1ai` (три имени соответствуют mount-контракту: ровно одна пара `fullchain.pem`/`privkey.pem` в `/opt/memo/certs`, префлайт деплой-скрипта требует именно её). Выпуск и продление через certbot **на хосте** (вне контейнеров); в `-d` имена передаются в punycode (`xn--b1acfa3biol7a6ce.xn--p1ai`); certbot ставится из snap (в apt Ubuntu 24.04 — 2.9.0, недостаточный для ARI и перехода Let's Encrypt на 64-дневные сертификаты с 2027 — механика продления в #617). Обязателен deploy-hook: `docker exec edge nginx -t && docker exec edge nginx -s reload` — обновлённый файл на хосте невидим контейнеру до reload. Приёмка включает `certbot renew --dry-run --run-deploy-hooks`.
5. **Снапшоты Selectel — аварийный слой, не замена бэкапам**: live-VM-снапшот crash-consistent (не app-consistent для SQLite+WAL), хранится на том же оборудовании, удаляется вместе с томом, не скачивается. Расписание — еженедельное + ручной снапшот перед каждым релизом. Основная защита базы — вне сервера, её политику назначает #618.
6. **Заявку в перечень Минцифры не подаём** (см. «Границы»).
7. **Минимальный этаж мониторинга** (входит в IMPL): ежечасная внешняя проба `https://colourmountains.ru/api/v1/health` из scheduled-воркфлоу GitHub Actions (раннеры вне РФ, доступность не зависит от белых списков) с уведомлением о провале. Наблюдение за памятью и диском, алерты об истечении сертификата — последующий хвост за #617/#619, здесь не внедряются.

## User Scenarios

1. **Владелец открывает сервис с телефона.** `https://colourmountains.ru` отдаёт web-приложение по валидному TLS. Проверка: запрос с внешнего хоста — HTTPS 200; `openssl s_client`/`openssl x509 -text` по сертификату — SAN-набор ровно три имени (канон, www, punycode-IDN); ответ `Set-Cookie` сессии несёт `Secure; HttpOnly; SameSite=Lax` (Secure включён значением `ENV=production` в `production.env`). Шаги входят в приёмку ранбука #619.
2. **Клиент приходит с не-канона.** Матрица хостов: по HTTPS `colourmountains.ru` отдаёт приложение; `www.colourmountains.ru` и `xn--b1acfa3biol7a6ce.xn--p1ai` отдают `301 https://colourmountains.ru` с **сохранением пути и запроса**; по HTTP все имена идут через существующий port-80 catch-all (301 → `https://$host`) — для `.рф` это два хопа, приемлемо (браузеры пытаются HTTPS первым). `www.цветныегоры.рф` вне скоупа — DNS-записи нет, соединение не резолвится. Проверка: `curl -sI "https://xn--b1acfa3biol7a6ce.xn--p1ai/services?x=1"` → `301` и `Location: https://colourmountains.ru/services?x=1` (точное сохранение пути и query); то же для `www`; ручная проверка в браузере. На `.рф`/`www` куки не ставятся: редирект отдаётся на уровне nginx до любых ответов приложения.
3. **Новая версия доезжает до прода.** Релизный тег деплоится из GitHub Actions по SSH; контейнеры здоровы. Проверка: прогон `deploy/deploy.sh` на сервере + приёмочные пробы ранбука #619 (статус compose, healthcheck).
4. **Сервер можно восстановить.** Снапшот создаётся по расписанию и восстанавливается в новую VM. Проверка: разовый restore-drill (восстановление в чистую VM, сайт поднимается, `PRAGMA integrity_check` на восстановленной базе проходит), затем регулярное расписание.
5. **Сервис доступен во время режима ограничений.** Приёмка **наблюдением владельца** (доступность с мобильного в Сочи в период ограничений — прецедент #597) + механическая проверка: IP сервера присутствует в актуальных сообществских списках выживших подсетей (источники: [хаб](https://github.com/hxehex/russia-mobile-internet-whitelist) и компаньоны `escapingworm/russia-whitelist`, `chebur-net/russia-mobile-whitelist`; процедура — сверка /24 выданного адреса со скачанными CIDR-списками). Исполнитель — владелец вместе с этим сеансом при создании сервера. Если выданный IP из «мёртвой» подсети — пересоздание сервера с другим IP **до** остальной настройки (процедура в «Готовности к белым спискам»).

## Behavioral Delta

- **Было:** прод-сервера нет; деплой-стек (#616/#629) в main, но применить его некуда; домены не указывают ни на что; сайт из интернета недоступен.
- **Стало:** сервер в РФ (Selectel, 2 ГБ + swap) принимает трафик трёх имён; не-каноны редиректят на канон одним хопом по HTTPS; релизы доезжают из GitHub Actions по SSH; TLS валиден на три имени и продлевается с deploy-hook reload; снапшоты настроены как аварийный слой; работает ежечасная внешняя проба доступности; проверка достижимости при белых списках — регулярная процедура владельца с механической сверкой IP.

## Требования

### Виртуальная машина и ОС

- Selectel Cloud, KVM; 2 vCPU (burst допустим), 2 ГБ RAM, ≥30 ГБ SSD/NVMe; Ubuntu 24.04 LTS; ЦОД Москва или СПб.
- Выделенный статический публичный IPv4 (отдельный адрес, «/32» в терминах возможной будущей заявки), не shared/NAT.
- 2 ГБ swap-файл, `vm.swappiness=10`.
- Docker CE из официального репозитория + compose-плагин v2 (скрипт деплоя терпит и v1 — «VPS docker vintage unknown»); bash; python3 на хосте (health-проба деплой-скрипта); certbot из snap + штатный systemd-таймер продления (apt-версия 2.9.0 недостаточна — см. решения).

### Сеть и SSH

- Фактический контроль «наружу только 80/443» — сама публикация портов в compose (только edge публикует `80:80` и `443:443`; backend/admin портов не имеют). Фаервол поверх (Selectel security group / `DOCKER-USER`) — документированная опция, не обязательство v1.
- SSH: отдельный non-root пользователь с sudo; `PasswordAuthentication no`, `PermitRootLogin no`, вход только по ключу; `ufw limit 22/tcp`. Ужесточение до `restrict,command=`-обёртки деплой-ключа и pinned `known_hosts` — документированное последующее улучшение, не v1 (деплой-скрипт scp'ится при каждом запуске, обёртка требует фиксированного пути — отдельная механика).
- Исходящий доступ к ghcr.io (pull образов) — приёмочная проба обязательна (деградация GitHub из РФ с мая 2026); документированный обход — переменная `MEMO_REGISTRY_PREFIX` (зеркало/Docker Hub, поддержка уже в деплой-скрипте); зеркало наполняется только при фактическом провале pull-пробы.
- Исходящий доступ certbot к серверам Let's Encrypt (ACME).

### Хост-пути и env (уже требуются деплой-скриптом из main)

- `/opt/memo/env/production.env` (0600, рендерится из GitHub Secrets на каждом деплое); **обязательное значение `ENV=production`** — от него зависит Secure-флаг сессионной куки (`secure=settings.ENV == "production"`).
- `/opt/memo/data` (SQLite + WAL, chown 1001:1001);
- `/opt/memo/media` (+ `media/public`);
- `/opt/memo/certs` (fullchain.pem + privkey.pem, ro-маунт в edge), `/opt/memo/acme`.

### SSH-секреты деплоя

- Секреты `DEPLOY_SSH_HOST` / `DEPLOY_SSH_USER` / `DEPLOY_SSH_KEY` в GitHub Secrets заполняет владелец после создания сервера.

### DNS

- Три A-записи: `colourmountains.ru` (`@`), `www`, `xn--b1acfa3biol7a6ce.xn--p1ai` (IDN в punycode) → IP сервера. `www.xn--…` — записи нет (вне скоупа).
- DNS-хостинг: **Яндекс** (текущий, российский — критерий РФ-DNS выполнен); A-записи меняются в панели Яндекса, перенос NS не требуется.
- Держатель домена проходит верификацию через Госуслуги (ЕСИА) — требование к операциям с доменами .ru/.рф с 01.09.2026 (продление, смена DNS). Технической проверки в репо нет и не предусматривается — обязательство владельца; **до смены A-записей** владелец убеждается, что доступ к ЕСИА работает (иначе смена DNS задержится).

### Edge: редирект не-канонов (единственное IMPL-изменение deploy-файлов)

- **Механика — по образцу существующего port-80 catch-all**: в существующем 443-сервере добавляется `map $host` + server-level `if ($…) { return 301 https://colourmountains.ru$request_uri; }` для хостов `www.colourmountains.ru` и `xn--b1acfa3biol7a6ce.xn--p1ai` (и любых не-канонов). **Без новых location-станз и без второго server-блока** — страж расхождения `deploy/verify-edge.sh` (stage 1: verbatim-зеркало location-станз 443 в smoke-конфе) не задевается; server-level return не является location-станзой. Статус `301` (стандарт постоянного переноса домена): методы-сохраняющий `308` рассматривался и отклонён — POST-запросы на не-каноны невозможны (приложение всегда загружается на каноне и ходит в API по same-origin).
- Порт 80 не меняется: catch-all `301 https://$host$request_uri` остаётся (ACME-путь `^~ /.well-known/acme-challenge/` уже исключён из редиректа и обслуживает выпуск сертификата для всех трёх имён; server-level if на 80 не добавлять — он перебил бы ACME для не-канона).
- Smoke-конфа редирект не упражняет (server-level механика вне зеркала location) — редирект покрывают живые приёмочные пробы сценария 2.
- Сертификат — один SAN на три имени (см. решения); редирект обязан работать и по HTTPS, и работает: 443-сервер обслуживает все имена этим сертификатом.
- Кука сессии: host-only на каноне; после редиректа на не-каноне куки не ставятся — редирект происходит до ответов приложения (приёмка проверяет отсутствие `Set-Cookie` в 301-ответе).
- HSTS (`max-age=31536000`) уже стоит в 443-сервере — не меняется.

### Готовность к белым спискам (чек-лист, проверяется при создании)

- [ ] нет зарубежного CDN/прокси перед сервисом — TLS терминирует edge на российском IP;
- [ ] DNS-хостинг в РФ;
- [ ] **проверка выданного IP — первый шаг после создания сервера** (до установки Docker и любой настройки): скачывать CIDR-списки хаба и компаньонов, сверять /24 выданного адреса; при промахе — пересоздать сервер / запросить другой IP (проверка до любой настройки делает промах дешёвым — минуты и ноль работ);
- [ ] IP статический, выделенный;
- [ ] продление TLS не зависнет в период ограничений (deploy-hook + `certbot renew --dry-run --run-deploy-hooks` в приёмке; запасной план — в «Рисках»).

### Снапшоты

- Автобэкапы Selectel (снапшоты VM): еженедельное расписание + ручной перед каждым релизом. Аварийный слой; снапшот live-VM для SQLite+WAL — crash-consistent, но восстановимость из такой копии — штатная механика recovery SQLite, drill сценария 4 проверяет её на практике. Консистентный бэкап базы вне сервера — за #618 (там же политика RPO).

## Границы (сознательно НЕ делаем)

- **Заявка в перечень Минцифры не подаётся**: включение — только через ходатайство федерального ведомства, для соло-сервиса бронирования шансы близки к нулю. Примечание (не требование): текущая конфигурация (РФ-хостинг, статический отдельный IP, мощности в РФ) случайно удовлетворяет техническим требованиям заявки, если вопрос когда-нибудь вернётся.
- **Failover-сервер / второй провайдер** — нет (восстановление из снапшота).
- **CDN / WAF / внешняя DDoS-защита** — нет (чужие общие IP — гарантированная смерть при белых списках).
- **Апгрейд RAM до 4 ГБ** — отложен по решению владельца (старт с 2 ГБ).
- **Редирект-домены остаются в #574** (отклонено предложение вынести): изменение — одна map-конструкция в edge, перенос в отдельную задачу стоит дороже самой правки; «созданный сервер» в результате задачи подразумевает открывающийся сайт на доменах владельца.

## Швы

- **#616 / PR #629** (деплой-стек, в main) — архитектуру compose не меняем; единственное изменение deploy-файлов — map+return редиректа в `deploy/nginx.conf` (страж `verify-edge.sh` и smoke-конфа не трогаются).
- **#617** — регламент выпуска/продления сертификатов: deploy-hook reload, certbot из snap (ARI/64-дневные серты 2027), алерты продления. Здесь — первичный выпуск на новом сервере и dry-run приёмка.
- **#618** — бэкап/восстановление тома `/opt/memo/data` вне сервера (основной слой для БД); снапшоты Selectel — дублирующий аварийный слой.
- **#619** — ранбук приёмки прода; сценарии 1–3 проверяются его шагами.
- **#597** — вход по звонку; прикрытие при шатдаунах, не трогается.

## Риски

- **Лотерея IP**: провайдер не гарантирует выдачу из «выживающей» подсети — обязательная проверка сразу после создания (см. чек-лист) + пересоздание при промахе.
- **Деградация GitHub из РФ** (с мая 2026): pull из ghcr.io проверяется приёмкой; обход — `MEMO_REGISTRY_PREFIX`, зеркало наполняется только при фактическом провале.
- **Коллатеральные блокировки Let's Encrypt**: **НУЦ Минцифры — крайний резерв, не полноценный план**: его сертификаты не доверяют основные браузеры (Chrome/Safari/Firefox/Edge) — годится только как аварийный обход для узкого круга клиентов. Основная защита — уведомление о неудаче продления (#617) и заменяемость: любой другой публичный ACME CA (например ZeroSSL) подключается той же механикой certbot.
- **Финальная цена Selectel** видна только в конфигураторе при заказе; снапшоты — платная опция.
- **Строгий белый список**: web недостижим с мобильного при любой конфигурации; прикрытие — вход по звонку (#597), Wi-Fi/проводные сети, бронирование по телефону. Перспективные выходы из потолка (вне скоупа, кандидаты в v1.x): бот/мини-приложение внутри мессенджера из перечней операторов (состав варьируется: VK, Max, местами Telegram — бронирование внутри белого-списочного приложения решает самую жёсткую развилку); заявка в перечень через региональное ведомство (министерство курортов/туризма региона при росте бизнеса); анонсированный механизм для МСП в Минцифры (на 27.11.2026 не подтверждён) — текущая конфигурация заявко-пригодна.
