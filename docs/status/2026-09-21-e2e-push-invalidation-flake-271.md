## Goal

Полные CI-прогоны shard-rest перестают красить спеку `server-push-invalidation` из-за
тайминговой гонки push-утверждений с циклом переподключения SSE-канала: окно
`PUSH_WINDOW` покрывает один полный цикл реконнекта (10 с вместо 5 с), утверждения С3
получают ограниченный повтор (бюджет 1), а падение печатает диагностику (какая попытка,
какое утверждение, началось ли перечитывание, был ли трафик событий) до внешнего таймаута
набора (120 с). Затрагивается только тестовый слой.

## Root-cause (структурный, спека §2)

Три независимых механизма съедали 5-секундное окно push-утверждений:

1. **Окно равно pacing'у реконнекта:** сервер шлёт `retry: 5000` — один обрыв соединения
   занимает всё окно целиком.
2. **Вытеснение подписчика на сервере:** очередь hub на 64 события; под нагрузкой шарда
   (два полных стека на одной машине) переполнение реалистично.
3. **Процессорная конкуренция шарда:** sibling-спеки замедляют и доставку событий,
   и перечитывание; цепочка С3 удлинилась после #286 при таймауте теста 60 с.

Вывод: 5 с систематически меньше одного цикла реконнекта → поднять окно, дать
ограниченный повтор, пересчитать бюджет таймаута.

## Summary of Changes (per task)

- **T1 — baseline «до» правки (small, test-execution only, правок кода нет):** флейк
  **НЕ воспроизведён** локально — 3 попытки × 27 тестов = **81/81** зелёных, 0 flaky
  (`/tmp/opencode/271-task1-baseline*.log`). Механика — шардовая среда
  (`scripts/e2e-shard-start.sh`), точечный прогон `server-push-*.spec.ts`, проект
  shard-rest, `--repeat-each=3`; проверка осознанно пониженной точности (нет
  sibling-нагрузки rest-шарда), авторитетный гейт — CI (спека §5e/§7.1). Живого
  «до»-падения для приложения к PR нет.
- **T2 — окно 10 с + таймаут 120 с (trivial, `74cf2911`):**
  `frontend/admin/e2e/fixtures/server-push.ts` — `PUSH_WINDOW 5_000 → 10_000`
  (одна разделяемая константа: 10 с покрывают один цикл реконнекта `retry: 5000` +
  рукопожатие и остаются втрое ниже app-wide staleTime 30 с; инвариант «тест не проходит
  за счёт протухания кэша» — 10 с × (1+1 повтор) = 20 с < 30 с); комментарий-обоснование
  обновлён; вместе с константой сдвинулись утверждения С1/С4, хелпер тоста обновления и
  офлайн-спека (всем — больше запаса). Заголовочный блок `server-push-invalidation.spec.ts`
  синхронизирован (устаревшее «PUSH_WINDOW = 5s»). Там же на блоке набора —
  `twoPages.setTimeout(120_000)` (test-level override; глобальный `playwright.config.ts`
  не тронут): worst-case цепочка С3 ≈90 с, диагностика обязана успеть напечататься.
- **T3 — inline-повтор С3 + диагностика исчерпания (standard, `25e7e3d5`, `56587530`):**
  локальная обёртка в файле спеки (без общей фикстуры, без нового DSL), бюджет **1 повтор**
  на утверждение (макс. 2 попытки), две семантики:
  - `passiveRearm` — пассивное пере-вооружение (DB-poll и push-1: то же ожидание с новым
    таймаутом, без ре-навигации);
  - `envelopeRetry` — push-2 конвертом из трёх ожиданий (`waitForResponse` GET
    `/api/v1/records/view` + переход «Записи» + `recordRow not.toBeVisible`); повтор
    конверта целиком, с повторным переходом (`recordRow` входит в конверт и отдельного
    бюджета не получает — арифметика «два push-конверта по 2×10 с» из спеки сохранена).
  Кэш-обходящих действий (перезагрузка страницы, обход кэша) в повторе нет, суммарное
  наблюдение < staleTime 30 с. Съеденный повтор печатает `console.warn` с именем
  утверждения — зелёный прогон остаётся интерпретируемым (см. §1 спеки о flaky-пометках).
  При исчерпании бюджета — агрегирующая ошибка: номер попытки, имя утверждения, обе
  ошибки и метаданные трафика через `openFrameLogger(browser)` — независимый
  контекст-слушатель SSE к бэкенду (как в офлайн-спеке; подписки страниц не затрагиваются),
  точный дельта-счётчик кадров с начала попытки, а для конверта — взведён/сработал ли
  `waitForResponse` (началось ли перечитывание). Только счётчики и факты — никогда тела
  кадров/ответов, URL с query-параметрами, токены; логгер закрывается в `finally`
  (нет утечки соединения между тестами). С2 и офлайн-спека не тронуты.
  Ревью: compliance — 2 итерации (2 minor закрыты в `56587530`: точный дельта-счётчик
  кадров вместо накопительного + откат whitespace в S5); quality ✅.
- **T4 — локальная верификация (small, test-execution only):** после правок обе push-спеки
  через ту же шардовую механику, `--repeat-each=3` — точечно **15/15** и финально
  **27/27** зелёных (`27 passed` × повтор), 0 failed, 0 flaky; предупреждений о съеденных
  повторах в логе **нет**; `tsc --noEmit` чисто; eslint 0 errors / 36 pre-existing warnings
  (бюджет 38). Живого «после»-срабатывания повтора зафиксировать не удалось — обёртка на
  локальных прогонах ни разу не покидала первую попытку.
- **T5 — CI DoD-верификация (standard): В ПРОЦЕССЕ** — три подряд полных shard-rest
  прогона на PR (в каждом сводка Playwright по `server-push-invalidation`: failed=0 **и**
  flaky=0) + разовая ручная анти-маскировка (перехват маршрута `**/api/v1/events` с abort
  в контексте страницы A → С3 обязан упасть; не коммитится). Результаты в статус-файле
  **намеренно не фиксируются** до завершения — место для них в описании PR.
