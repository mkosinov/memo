## Goal

Инвентарь на 27.09: 8 сущностей с сортировкой = 7 жёстких контрактов + 1 мягкая (клиенты с
молчаливым откатом к `name` и без тайбрейка); механика применения (направление + nulls-политика +
id-хвост) скопирована в 8 мест. Цель — один общий кирпень параметров `SortParams` + один общий
резолвер «карта колонок + `sort_by`/`sort_order` → ORDER BY», клиенты переведены на жёсткий
контракт (мусорный ключ → 422 вместо молчаливой сортировки по имени). Поведение всех остальных
сущностей — байт-в-байт; фронтенд не тронут.

## Summary of Changes (per task)

- **T1 — резолвер (standard):** `backend/src/domain/sorting.py` — `SortKeyMap`/`SortKeySpec` +
  `apply_sort` (канон `asc → nullsfirst / desc → nullslast`, per-key политика
  `always_nulls_last`, тайбрейк `id asc` последним выражением, вне nulls-политики — PK NOT NULL);
  `UnknownSortKeyError` в `domain/errors.py` → 422 через глобальный хендлер в `main.py`; юнит-контракт
  резолвера `tests/domain/test_sorting.py` (`49120fd8`).
- **T2 — кирпень SortParams (standard):** `SortParams(BaseModel, Generic[SortByT])` в
  `schemas/common.py` рядом с `SortOrder`; правило дефолтов — кирпень задаёт форму, фиксированные
  дефолты переопределяются подклассом (records `"date"/"asc"`, photos `"created_at"/"desc"`,
  clients `"name"/"asc"`); жёсткие params-модели клиентов/записей/фото; `RecordSortOrder` (дубль
  `SortOrder`) удалён. Generic-кирпень + query-инъекция FastAPI сработали как есть — объявленный в
  спеке §4.1 fallback (прямое объявление `sort_by` в подклассе) не понадобился (`3b0dab3e`).
- **T3 — клиенты на жёсткий контракт (standard):** `ClientSortBy` Literal из 7 колонок, мусорный
  `sort_by` (`banana`, пустая строка, регистр/пробелы) и `sort_order` → **422 VALIDATION_ERROR**
  вместо молчаливого отката к `name` (тест фолбэка переписан в тест 422); детерминированный хвост
  `Client.id.asc()`; полный sort-набор тестов. Follow-up консолидация — один класс применения
  клиентского sort-набора, дубли удалены, пины усилены (`81406c81` + `3b0c8ca6`).
- **T4 — записи и фото на резолвер (small):** карты сортировки остались у сущностей (у записей —
  коррелированные подзапросы с `correlate()`, pin регрессии #213), применение (`desc/asc/nulls/хвост`)
  — только через резолвер; inline-резолв `services/photo.py` удалён; страж фото-дефолта
  `created_at desc` (`f7ce4000`).
- **T5 — staff и справочники на резолвер (standard):** `api/v1/staff.py` — карта + резолвер с
  политикой `always_nulls_last` для LEFT JOIN-вычислимых `specialty`/`color` («пустые — в конце» в
  обоих направлениях, #266); `services/materials/locations/tags` — локальные `_X_order_by` удалены,
  карты у сущностей; скалярные роуты справочников — `sort_by: XSortBy | None = Query(None)` +
  общий `SortOrder`, fallback при `None` (дефолтный порядок сущности) остаётся у сущности (`6309f1a1`).
- **T6 — стражи контракта + CHANGELOG (small):** параметризованный CI-страж Literal==карта для всех
  8 сущностей (ловит дрейф «Literal расширили, карту забыли» в обе стороны); OpenAPI-страж —
  `sort_by` клиентов в опубликованной схеме — enum из 7 значений; CHANGELOG-запись (`ec9c8e3d` +
  `22324fde`).

## Behavioral Delta

Ровно §3 спеки: **клиенты** — неизвестный `sort_by`/`sort_by=`/регистр-кейсы/неизвестный
`sort_order` → 422 (было 200 с молчаливым откатом к `name`); равные значения колонки —
детерминированный порядок через границу страниц (`Client.id.asc()`); OpenAPI `sort_by` — enum из 7
значений. **Все остальные сущности** (records, photos, staff, справочники) — поведение строк
не изменилось (дефолты и хвосты §1 сохранены), изменилась только механика — одна общая.
