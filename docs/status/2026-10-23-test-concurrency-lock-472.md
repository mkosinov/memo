## Проблема

В контейнере opencode на одной машине могут одновременно работать 2 IMPL-сессии; когда тяжёлые
прогоны перекрываются (полный `test-all.sh` против быстрого гейта другой сессии), холодный старт
стеков замедляется сверх лимитов ожидания — прогон падает на старте при исправном коде
(инцидент ce9500; смежные проявления того же класса нагрузки — #462, #495). Механизма
ограничения числа одновременных тяжёлых прогонов не было ни в одной точке входа.

Панель и разведка вскрыли два дефекта ожидания готовности, не зависящих от нагрузки:

1. **Лимиты противоречивы и разбросаны** — инлайн-счётчики итераций в трёх местах вместо
   дедлайнов: в режиме «порт ещё не открыт» оркестратор сдавался за ~60 с (середина бюджета
   стека — путь инцидента ce9500), в режиме «порт слушает, но не отвечает» терпение
   растягивалось до десятков минут.
2. **Слепота к смерти внутри циклов опроса** — мёртвый процесс выжигал бюджет молча
   (смерть вне циклов ловил сторож #448 и собственный тик стека, дыра — именно в опросе).

## Что выполнено

1. **Дедлайны стенового времени + живость опроса (T1 `26b4e425`, standard)** — единый источник
   лимитов в `scripts/lib/shard-helpers.sh`: `READY_BUDGET_BACKEND_S=60`,
   `READY_BUDGET_FRONTEND_S=120` (значения сохранены; дедлайн срезает патологический хвост
   висящих curl), `READY_ORCHESTRATOR_S = 60 + 120 + 180 = 360`; шаг цикла не длиннее остатка
   дедлайна (curl `--max-time` ограничен остатком, сон усечён); цикл бэкенда стека проверяет
   `kill -0 $BACKEND_PID` на каждом шаге, фронтенд-цикл — `FRONTEND_PID` и `BACKEND_PID`;
   смерть любого — немедленный фатальный провал с хвостом лога умершего.
2. **Маркер готовности + ожидание оркестратора по маркерам (T2 `a63163d1`, standard)** —
   обёртка стека пишет маркер `SHARD_READY_MARKER` сразу после успешного опроса фронтенда,
   ДО warmup (семантика перекрытия стадий сохранена, буфер 30 с не тронут); маркер живёт в
   свежем per-run каталоге и удаляется при старте стека (пролежавший не подделает готовность);
   переменная не установлена (CI/ручной запуск) — записи нет. `test-all.sh` прекращает
   дублировать HTTP-опрос: ждёт маркеры обоих осколков с потолком `READY_ORCHESTRATOR_S`,
   каждый тик проверяет живость обёрток — смерть = немедленный провал с хвостами логов;
   исчерпание потолка — провал с хвостами логов стеков.
3. **Замок тяжёлых прогонов (T3 `f90e67d7` + правки ревью `62063cff`, standard)** — обёртка
   `scripts/with-test-lock.sh <команда...>` + встроенный самозахват `test-all.sh` в самом
   начале, ДО ветки `SEQUENTIAL=1` (все формы вызова: прямой запуск, `pnpm test:all`,
   pre-push hook). `flock` на дескрипторе-владельце без наследования детьми (смерть владельца,
   включая `kill -9`, освобождает замок мгновенно; сироты не держат); фиксированный путь
   `${MEMO_TEST_LOCK_PATH:-/root/workspace/.memo-heavy-tests.lock}` — файл никогда не
   удаляется (unlink ломает взаимное исключение по inode); реентерабельность через
   `MEMO_TEST_LOCK_HELD=1`; очередь: первая попытка немедленно (`flock -n`), далее повтор
   каждые `MEMO_LOCK_POLL_S` (300 с) со статус-строками «[lock] занят, ожидание N/M мин»,
   потолок `MEMO_LOCK_WAIT_S` (3600 с) по фактическому ожиданию, сон усечён до остатка;
   исчерпание потолка — код 75 «машина занята чужим тяжёлым прогоном»; обход без замка
   (однострочное уведомление, подавляется при `CI=true`): каталог замка недоступен / нет
   бинарника `flock` / `MEMO_TEST_LOCK_DISABLE=1`; соотношение с seed-замком — сознательно
   разные идиомы. Правки ревью: опечатка «бинарника», имя потолка в контракте, пробел в
   Usage, пер-ранковые pkill-маркеры L3/L4.
4. **Dryrun-сценарии замка (T4 `d6af030d`, standard)** — новые наборы
   `scripts/lib/test-lock.dryrun.test.sh` (50 кейсов) и `scripts/test-all.dryrun.test.sh`
   (20 кейсов): US-1 сериализация двух прогонов, US-2/US-3/US-4 (в т.ч. без очереди при
   свободной машине), US-7 (реентерабельность/сквозной запуск), F9 — один inode двух сессий;
   набор замка подключён в dryrun-стадию `test-all.sh`.
5. **Сценарии с реальным стеком + контрольный прогон очереди (T5, small)** — без изменений в
   репо: US-5/US-6 с реальным стеком и контрольный прогон очереди — все PASS, времена
   0.21 с / ≈0.05 с / 157.4 с / старт ≤POLL; зафиксировано комментарием в issue #472
   (issuecomment-6364433506).
6. **Канон запуска (T6 `1c46a0ca` + `a8170428`, small)** — `docs/tests_workflow.md` +
   `.opencode/skills/dev-workflow/SKILL.md`: перечень тяжёлых точек с примерами команд,
   правило тяжести по наборам (полный pytest / полные наборы vitest — под замком; одиночные
   файлы, типы, lint — без), очередь/75/обход, батч-паттерн гейта (один вызов обёртки на весь
   батч), запрет оборачивания `test-all.sh`, соотношение с seed-замком; фактическое поведение
   pre-push (hook no-op — замка не берёт, push не ждёт; ожидание до 1 ч/статусы/rc 75 живут в
   G7 fast suite и самозахвате test-all), сверено с `tests_workflow.md`.
